# VAL-7b/c — RPM step-response reduction

**Status:** verified offline tooling; physical measurements remain VAL-7. Python 3 standard library only. [Baseline evidence](../../../docs/research/validation/VAL-7b/README.md), [uncertainty evidence](../../../docs/research/validation/VAL-7c/README.md).

```sh
python3 research/validation/rpm-step/test_reduce.py
python3 research/validation/rpm-step/test_uncertainty.py
python3 research/validation/rpm-step/reduce.py research/validation/rpm-step/example.synthetic.json
```

The CLI prints a deterministic JSON report. Invalid input exits 1 with no partial report. Reports retain the input and SHA-256 hashes of its exact bytes and the reducer. Preserve the original file alongside the report. No aircraft parameters are written.

## Recording contract

Use one throttle step per record. Identify engine, propeller, fuel, throttle endpoints, installation and operating conditions in `configuration`; identify the raw recording, clock synchronization, sensor filtering and corrections in `notes`/`source`. An audio-derived RPM series requires independently checked harmonic selection and window timing; audio extraction is outside this tool.

Supply initial and final RPM from identified **steady windows**, with their averaging and uncertainty method. Never substitute the last transient sample for the final equilibrium. Record command time on the sample clock and retain observations before the step and through the 90% crossing. The tool does not establish endpoint stability or instrument calibration from a declaration.

The [example](example.synthetic.json) is invented, generated by `fixture()` in [test_reduce.py](test_reduce.py): 2,000 → 10,000 RPM, command at 2 s, lag 0.25 s and delay 0.08 s. Its exact crossing knots are an algebra fixture, not a field recording or a sampling-rate recommendation.

| Input | Contract |
| --- | --- |
| `format` | `openrc-rpm-step v1` |
| `evidence` | `synthetic` or `measured` |
| `configuration`, `notes` | Nonempty descriptions |
| `command_time` | Quantity in `s`, on the same clock as samples |
| `initial_rpm`, `final_rpm` | Distinct nonnegative steady quantities in `rpm` |
| Quantity | `{value, unit, u, kind, source}`; finite value, nonnegative standard uncertainty `u`, nonempty source |
| `series` | `{kind, source, time_u_s, rpm_u, samples}` |
| `samples` | At least three `[time_s, rpm]` pairs; strictly increasing times, finite nonnegative RPM |
| `kind` | `synthetic`, `measured` or measurement-`derived`; synthetic inputs refused in measured campaigns |
| Optional `uncertainty_model` | Exactly `independent-inputs v1`; explicit agreement to the assumptions below |

Unknown fields, duplicate JSON keys, numeric strings/booleans, nonfinite numbers, incomplete crossings and missing onset are refused. No sorting, smoothing or extrapolation is performed. Provenance labels cannot authenticate measurements.

Uncertainties describe one standard deviation in the stated input unit. `series.time_u_s` and `rpm_u` describe each sample. Zero excludes an uncertainty term; it does not mean unknown. Without `uncertainty_model`, values are retained and `measurement_uncertainty.status` is `not_requested`; no independence assumptions are inferred from old records.

## Optional measurement uncertainty

`"uncertainty_model": "independent-inputs v1"` declares mutually independent errors in the two endpoint estimates, command timestamp, each RPM sample and each sample timestamp. This assumes endpoints were estimated from separate windows outside the supplied transient series. Do not opt in when shared calibration/clock errors, overlapping endpoint windows, time/RPM correlation or sensor filtering make this independence assumption inappropriate. Those correlations need a future explicit acquisition model; prose alone does not propagate them.

The reducer propagates signed analytic sensitivities through each interpolated crossing, then through rise time, lag, delay and the 63.2% consistency residual. Reused endpoints and shared sample indices retain their induced covariance. The report includes `u_s` (one combined standard uncertainty), signed input contributions in seconds and the complete output covariance matrix in seconds squared. Command uncertainty cancels from rise time, lag and the consistency residual, but remains in delay and command-relative crossings. No uncertainty is inferred for RMSE or the other observed-response diagnostics.

Local derivatives apply only while crossing segments and time order stay fixed. A declared **estimated screening multiplier of 3** checks endpoint separation, adjacent timestamp ordering, all sample-to-threshold margins through each first crossing and crossing/command ordering. Any unresolved margin or repeated crossing gives `status: unavailable`, reasons and `metrics: null`; nominal response diagnostics remain available. All-zero uncertainty permits exact threshold knots. Screening is a heuristic for local linearization, not a confidence level, simultaneous probability guarantee or nonlinear uncertainty bound. Near a threshold knot, even small RPM noise can choose a different segment and slope.

`status: available` means a first-order calculation passed that screen under the declared model. It excludes interpolation bias, intersample motion, omitted acquisition correlations and model discrepancy. Keep sampling-support intervals separate from standard uncertainties; adding them as variances would invent a probability distribution. The existing result v1 gains an additive `measurement_uncertainty` object; nominal crossing, residual and diagnostic values are unchanged.

## Reduction and interpretation

Normalize either step direction as `z = (RPM - initial)/(final - initial)`. For each of 0.1, `1-exp(-1)` and 0.9, select the first segment with `z_left < threshold <= z_right` and interpolate linearly. A first crossing before command time is refused as a synchronization/record-selection mismatch; it is never silently skipped. Threshold plateaus keep the first arrival. An observed post-command 10% crossing may still imply a negative diagnostic delay, which is retained.

For the diagnostic model `z = 1-exp(-(t-command-delay)/tau)` after onset, zero before:

- `rise_10_90 = t90-t10`
- `tau = rise_10_90/ln(9)`
- `delay = t10-command + tau*ln(0.9)`
- `t63_consistency_error = t63-command-delay-tau`

This solves two crossing equations; it is not a least-squares fit. Output includes residuals for **every** sample in input order, normalized/RPM RMSE, maximum residual, reversal magnitude, repeated crossings, overshoot and minimum normalized response. Any reversal is a sample-level observation, not proof of a statistically significant physical reversal. RMSE uses equal sample weights, so dense portions of an irregular record carry more weight. A good in-sample fit is not independent validation.

Each crossing retains its adjacent sample indices and times. `tau_sampling_support_s` and `delay_sampling_support_s` propagate those time brackets through the two equations (clipping the lag lower limit at zero). They bound the diagnostic under that bracket assumption; they are **not confidence intervals**, do not include measurement/endpoint uncertainty and cannot reveal intersample oscillations. The same-interval 10%/90% case is explicitly flagged as under-resolved.

Negative delay, overshoot, reversals and repeated crossings remain visible as warnings; they are not clamped away. No universal residual or response-time acceptance threshold is imposed. The apparent lag includes the measurement chain, radio/servo dynamics and installed engine/propeller response. Do not copy it directly into `propulsion.lag`, especially for shaft-balance or turbine aircraft. Use repetitions, separate up/down steps, matched operating conditions and held-out observations before changing a model.
