# Offline fixed-roster checkpoint proof

This research-only draft exercises same-build continuation with the real `FlightSession`, companion `Manager`, and agent pilot. It captures a two-agent Club-field/Stik fleet at common tick 137, transports the record through `CheckpointJson`, restores a newly configured detached fleet, explicitly resumes it offline, and compares 240 subsequent player/companion physical frames and command/controller frames byte-for-byte against the uninterrupted branch.

The fixture uses the normalized default lake and calm weather, the real ground-surface table, and the complete default scenery collision inventory with field lights. The record carries player and per-agent weather, lake, surface-table, and collision-world identities. The report embeds the complete current source/data SHA-256 map and the lossless checkpoint carrier is written under `D:/OpenRCsimulator-AFC-work/evidence/checkpoints/`.

Run it from the repository root with the pinned native engine:

```powershell
python tools/godot/run_checked.py --out-dir D:/OpenRCsimulator-AFC-work/evidence/checkpoints/runner --warnings-as-errors --timeout 120 --require-text "PASS offline fleet checkpoint continuation" -- .tools/Godot_v4.7.2-stable_win64_console.exe --headless --path app --audio-driver Dummy --script res://../research/ai-companions/checkpoints/test_fleet_checkpoint.gd
```

`fleet_checkpoint_candidate.gd` is an offline-only staging seam. `validate_record()` validates exact envelope keys, the complete in-scope source/data path set and current bytes, profile/config/world/environment identities, player and roster clocks, normalized commands/trims, controller schema, and the bounded future input tape before restore. The lossless payload is capped at the native `CheckpointJson` 16 MiB limit; controller snapshots have depth, node, per-string, and aggregate-byte bounds. Restore accepts only a detached, unused tick-zero fixture with the expected manager owner and fixed roster. It restores controller locals before sessions, rolls back a controller that mutates and then refuses, and rolls back all staged session/controller changes if a later FlightSession restore unexpectedly refuses. A rollback failure still requires discarding the detached fixture. `FlightSession.restore_checkpoint()` leaves sessions paused in recorded-input mode; the caller explicitly resumes only after offline checks.

An optional mutable controller must implement both `snapshot_state()` and `restore_state(state)`. The snapshot must be a bounded Variant-only dictionary. Restore must return a dictionary containing boolean `ok=true`. Its current source SHA must be present in the complete manifest and match the file on disk. The protocol has a direct positive/negative compatibility check against `reachable_pilot_r2.gd`'s current method pair. The fallback saves base-pilot fields only for the exact pinned base-pilot SHA; any new mutable base-pilot code must use the explicit method pair.

The controller SHA in this baseline remains `1d5699fa89d219b26e6ff7dc58a797eb61f67152e9d9aedc64f5de1ca684615c`.

This proof is not AFC-22 completion or a product checkpoint feature. It excludes Main/live-session restore, hot admission/retirement and generation changes, weather/configuration migration, incident/runway/activity scheduler state, inter-aircraft contacts, scenery damage, shared-world transitions, and a fleet event journal. It makes no cross-platform replay claim and does not establish flight realism.
