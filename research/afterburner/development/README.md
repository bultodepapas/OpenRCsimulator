# Afterburner visual-study fixtures

These files are **proposed lab data**, not production aircraft JSON, Godot resources, an implemented feature, an executable test suite, or a source of measured turbine behavior. The originating OpenRC source snapshot is `ad21070798bfb9658785576a9c0b8bfc9a71fc7f`; its engine pin is `4.8.beta2.official.cafc17a19`. No Godot or Blender launch, hardware capture, or rendered-profile evaluation was performed to prepare them. The draft schema IDs are local names for this handoff and carry no production compatibility guarantee.

- [visual_profiles.json](visual_profiles.json) supplies three independent art directions, the common coordinate and appearance contracts, one reusable procedural noise recipe, suggested per-outlet state, and conservative starting bounds.
- [capture_cases.json](capture_cases.json) supplies 34 planned paired or multi-condition cases. Every case is `not_run`. Each includes a question, conditions, required renderers, a native 1080p baseline, and the evidence expected; a few explicitly declare a higher-resolution, reduced-internal-resolution, or Forward+-only comparison.

The restrained RC study starts with a blue/cyan plume and **cells disabled**. The bright aperture is gas emission; a separate hot-metal or interior-glow channel starts disabled. A core may be integrated into one shell or rendered as a separate layer after comparison. The violet/pink full-scale reference study has deliberately weak nozzle-stationary cells; it is not calibrated to an RC engine. The cosmetic LED is an independent annulus with no gas plume, particles, haze, or mapping to physical augmentation. The numbers in all three profiles are starting art controls rather than observations, and the reference-study profile is not a claim that a stock P100-RX has an afterburner. A real visual or physical installation must be identified and validated elsewhere.

## Implementer handoff

1. Resolve a validated visual outlet anchor and finite, nonzero exhaust direction. The study geometry extends along its own **+Z**. The current smoke resolver uses local **−Z** as its exhaust direction, so use a local Y rotation of π under that resolver or build an equivalent right-handed basis. Admit finite, nonsingular, orientation-preserving transforms with orthogonal axes and positive uniform scale; apply the resolved transform and authored diameter exactly once. Reject nonuniform scale, shear, reflection, invalid directions or missing geometry with an actionable diagnostic instead of guessing a pose. Set and test an explicit numerical tolerance in the eventual adapter.
2. Interpret every `*_d` dimension as a multiple of the authored visual nozzle diameter **D**. The optional `0.05 m` fixture is an illustrative value, corresponding to the existing approximate 0.025 m visual radius; it is not a measured nozzle or a physical force area. At this example scale the RC study's nominal length is `8.4 D = 0.42 m`. Compute conservative bounds from the largest enabled geometry and deformation; update them when dimensions, shader displacement or parent scale change.
3. A physical installation may publish its **accepted actual AB state** through a presentation adapter; the ring instead consumes a separate cosmetic signal. The normalized visual level modifies only appearance. Do not derive engine thrust, fuel use, temperature, or an acoustic law from these files. The test tapes in the cases are synthetic presentation inputs, not an aircraft model.
4. Store texture and shader resources as immutable shared assets where safe. Keep the engine/outlet identities, current level, pose-aligned presentation timestamp, bounded phases, per-view detail LOD and optional particle histories independent. Advance presentation once, even if more than one viewport renders. Starting globally Effects Off creates no AB-owned resources; On to Off releases those resources and suspends AB updates after deferred cleanup, with separately owned shared caches accounted for explicitly. Reserve an explicit particle-data contract before adding flipbooks: current OpenRC smoke uses `CUSTOM.z` as a seed, while the pinned standard material uses it to select an animation frame. Do not overwrite it silently.
5. Treat the noise recipe as **linear scalar data**, not an sRGB color texture. Authored RGB colors are sRGB and need one conversion into the active renderer's working space; alpha is coverage and emission gains are relative art multipliers. Set repeat and mip filtering deliberately. The engine source shows the first deferred noise update runs synchronously; prepare it during loading and measure cold cost. Connect the completion signal before triggering generation, track already-ready and failure/teardown states, and never wait indefinitely. If testing 3D noise, the pinned invalid-RID `get_data()` path logs an error and returns an empty vector, so a null-only check is insufficient.
6. Start with the mesh/core and the selected appearance alone. Optional particles, dynamic lighting, distortion, volumetric fog, and higher-cost texture work need separate comparisons and resource budgets. For world-space particles, use the existing smoke system's swept-birth and single-carrier-velocity principles; pinned Compatibility does not support manual GPU emission or sub-emitters. Do not silently fall back to a different renderer or claim matching GPU pixels from a fixed seed.

## Capture and evidence policy

The common baseline requests **1920×1080 actual output and 1920×1080 internal pixels**, native scale, before 1440p/4K. A window size or a 720p internal reconstruction does not establish this. Check the actual drawable, internal viewport, renderer/backend, GPU/driver, camera, exposure, shader/asset identity, VSync and cap. Run Compatibility, Mobile and Forward+ where the actual target supports them; cases with renderer-specific prerequisites say so. LAB-013 explicitly compares a verified lower internal resolution; LAB-014 follows 1080p with higher native resolutions.

The sequence begins with direction, rear/core and occlusion cases (LAB-001–007), then readability, weather and pixel/LOD comparisons (008–017), lifecycle and moving-particle behavior (018–026), and resources, multiview/lake, Effects Off and performance (027–034). The 34 IDs are proposals for a future owner; they do not assert that an existing debug bridge command, AB profile loader, viewport, planar reflection, or event-injection seam already exists. If a prerequisite is absent, record the case as blocked or unsupported in the future evidence record; do not call it passed.

For LAB-034, the existing plan proposes a +0.5 ms combined frame-p95 allocation, not a measured result. The seven alternating 60-second pairs and activity/simulation-time checks are also a proposed protocol. Keep timing runs separate from screenshots and GPU readbacks. Compare the same accepted session/tape with presentation Off and On; report the difference and spread on named hardware. If caps, background noise or incomplete activity obscure the difference, report an inconclusive comparison.
