# Independent review of follow-up evidence contracts

Reviewed against checkout `00610ce3df391560dc195444d797bb81f2f83270`; production runtime and research tool code were not edited. This review reads the retained synthetic fixtures, checked receipts, production source and the independent modes analysis. It does not claim that malformed reports occurred during a stock campaign, that the ordinary 60 m floor was reached, or that any calculated stability represents a physical aircraft.

## Card duration and labels

The production `power_step` starts at 400 m, changes throttle at 1 s and requests a 31 s flight (`research/flight-test/card_power.gd:146–174`). The audited subclass changes only that test's safety floor to **399 m**, so this is an intentionally shortened scenario, not evidence of a problem at the standard **60 m** floor (`research/ugly-stik-audit-2026-11-15/follow-up-01/evidence_contract_probe.gd:1–26`; `research/flight-test/flight_test.gd:56–57`).

The checked trace records the idle case to 3.1208 s and the 25% case to 5.2208 s, measured from flight start; the power step starts at 1 s. Nevertheless both rows contain numeric 5-, 10-, 20- and 30-second-after-step height and speed fields, each set to their last recorded value. Both rows say `completed=true`, and the whole result says `valid=true` (`evidence/card-floor.json`). The mechanism is explicit: `_row_at` clamps a requested time to the last recorded row, `power_step` reads it under the requested future label, and `completed` checks absence of a crash (`research/flight-test/flight_test.gd:427–428`; `research/flight-test/card_power.gd:185–188,203–219`). The report does contain `reached_floor_s` and readable floor-stop notes: the stop is **not wholly hidden**. “Completed” currently functions as a no-crash flag, so the contract defect is interpreting that flag and the numeric time-labeled fields as full requested-duration coverage; it is not evidence of a wrong simulator trajectory. At least the hands-off path has another time-clamping use (`flight_test.gd:1271–1283`); audit other consumers individually, since some maneuvers intentionally stop on completion.

The checked receipt `evidence/checks/card-floor/report.json` says `ok=true`, exit 0, complete, **zero errors and one warning**. Warnings were not fatal. The warning is Godot's NaN-to-null conversion at `flight_test.gd:216`; do not describe this as a zero-diagnostic run.

**Repair criterion:** record the actual terminal trace timestamp, requested target time and stop reason separately; a metric at `t = 1 + N` must use an actual recorded sample/interpolation covering that time or be explicitly unavailable, never relabel an earlier endpoint. Keep “stopped at floor,” “crashed/faulted,” “intentionally completed,” and “full duration reached” distinct so the scientifically meaningful early stop remains visible. Version the card or declare a compatibility plan if field semantics change. Test a full-duration control, stop just before/at/after each target, one-tick boundaries, and the explicit stop-callback path; compare correct results and note that loop `t_end` and last trace timestamp can differ by one tick.

## Wrapper failures preserve too little evidence

The **positive control is valid**: the corrected fixture includes mass and start-speed metadata, returns exit 0, and writes a log, manifest and summary. Do not use the prior incomplete test fixture as a finding against production.

For the timeout fixture, a real Python child prints both streams before timing out. `TimeoutExpired.stdout` and `.stderr` contain bytes, but `run.py:150–156` keeps stdout only if it is a string and ignores stderr. The saved `run.log` is effectively empty and the manifest says `script_errors: 0`, even though the deliberately injected stderr included an `ERROR:` line (`evidence/tool-evidence.json`). The wrapper correctly marks `exit: timeout` and itself returns **exit 1**. The issue is lost diagnostic evidence and a misleadingly complete-looking error count on an already-failed run; it is not a successful timeout or a demonstrated Godot failure.

The separate injected malformed JSON and valid JSON without `results` raise `JSONDecodeError` and `KeyError` at `run.py:164–170` before that job writes `run.log` and before the aggregate `run.json` is written (`:186–204`). In these single-job fixtures the subprocess has returned, but the runner aborts without either evidence file. A real uncaught exception is a failing run, not an exit-zero false pass. An exception in a multi-job map can also prevent the aggregate manifest even if other jobs have returned; the present fixture establishes the single-job case, and the multi-job consequence follows from the map construction.

**Repair criterion:** persist bounded, explicitly marked stdout and stderr before parsing; handle both bytes and text with a defined decoding policy; retain timeout/termination and partial-output status. Catch malformed/missing/structurally invalid profile data per job and finish a manifest distinguishing child exit, parse failure, roster, identity, warning/error counts and whether those counts cover complete captured output. Preserve every other job's receipt. Test both timeout streams, stderr-only error, malformed JSON, missing or wrongly typed `results`, nonzero child exit, and a mixed good/bad parallel batch. Maintain the documented distinction that a completed card reporting `valid: false` is a scientific result, not necessarily an execution failure.

## Comparison gate and coverage

`compare.py` is an evidence comparison tool, not an aircraft-validation tool. Its `--fail-on-change` tests whether any listed values changed; by itself it does not assert a sufficiently populated or valid comparison.

* **Empty existing output directories:** the probe gets exit 0 and “0 change(s)” with no aircraft and no metrics compared. The summary does not state a zero-aircraft coverage count.
* **Disjoint tests under `--shared-tests`:** the tool exits 0 even though it explicitly reports zero shared tests and zero values, and names each omitted test. This is visible in the report but can be misread by an automated exit-code gate as unchanged evidence.
* **Duplicate table cases:** two rows share the same case ID; changing the first row from 5 to 500 while leaving the second at 10 is not detected. `flatten` writes both into the same keys and the later value wins (`research/flight-test/compare.py:22–40`). A nonduplicate 5-to-500 control correctly exits 1 and reports the change. This does not establish that stock cards currently emit duplicate IDs; it shows how such a malformed or future report could mask a change.
* **Candidate-only aircraft:** the updated probe includes the same baseline aircraft in both outputs plus an additional candidate aircraft; the comparator exits 0 and does not list the additional profile. Source shows it discovers aircraft from the baseline only (`compare.py:71–77`). This can be an intentional baseline-only policy, but the result does not certify equal fleet coverage.

**Repair criterion:** an evidence-acceptance mode should require a declared, nonempty common aircraft/test/value coverage and expose counts, missing sides and invalid/unavailable observations before returning a success verdict. Reject duplicate case identifiers before flattening, or preserve unique row identities without silently overwriting values. Compare both aircraft rosters; permit intentional omissions/additions or partial card comparisons only under a clearly reported policy. Preserve useful nonempty `--shared-tests` behavior and do not turn an intentionally invalid-but-equal test into a physics success. Test empty, disjoint, one-sided aircraft, duplicate IDs with differing fields/order, normal changes, identical valid results, intentional shared subsets and valid/invalid transitions. Severity is high **for anyone treating exit 0 as proof of equivalent covered results**; these fixtures do not show damage to past comparisons with independently verified coverage.

## Independent challenge of modal conclusions

The saved FS-64V static card actually reports at its **20 m/s start case** `short_period_hz=0.070`, `short_period_zeta=1.378`, no phugoid, and a projected spiral time to half of 15.8 s (`../evidence/fleet-static/stik-glow-fs64v-4t/profile.json`). The modes diagnostic used a checked pinned-engine run with zero categorized errors/warnings (`evidence/checks/modes/report.json`); its captured matrices are in `evidence/modes.json`. The separate SciPy analysis is `evidence/modes-analysis.json`.

At 17 m/s the projected longitudinal spectrum has a slow conjugate pair about −0.512 ± 0.137i and a faster pair. At 18 m/s the slow-region spectrum consists of real roots about −0.766 and −0.323 while the faster complex pair remains. At 20 m/s the projected roots include −16.182 ± 4.938i, −11.343, −1.027 and −0.190 s⁻¹. The production heuristic assumes the lone complex pair is phugoid, removes a real root nearest −V/lag length, and labels the other two real roots an overdamped short period (`app/physics/flight_modes.gd:72–96`); the card then suppresses the faster reported phugoid (`research/flight-test/flight_test.gd:1144–1167`). The sampled evolution **supports a likely label reversal under that heuristic**, not a uniquely established physical mode identity: speed points are sparse, and frequencies alone do not prove which modes should retain a name across a root collision. The diagnostic no-lag model at 20 m/s also has two similar slow real roots, so the presence of a lag state is not necessary for this observed split. It does not prove the underlying aircraft's physical damping.

For the same 20 m/s trim and captured 9×9 full Jacobian, SciPy finds a positive real root +0.05705 s⁻¹. The isolated lateral block instead has a slow real root −0.04381 s⁻¹, while the projected longitudinal roots are also stable. Thus the diagonal-block estimates omit a positive root of the **captured coupled matrix**; they cannot establish stability of that matrix. Do not call this a proven “spiral sign reversal”: no coupling homotopy or mode continuation proves that the two real roots have the same identity. The production source itself labels the outputs projections and says off-block couplings are omitted (`app/physics/flight_modes.gd:54–61,100–107`). This is local, frozen-control and frozen-RPM analysis at calm sea-level conditions; propulsion loads still change with airspeed at fixed RPM. It omits evolving shaft, fuel and servo states and is not a nonlinear session or hardware-flight stability result (`flight_modes.gd:1–4,23–44`; `app/physics/trim.gd:48–56,70–76`).

A small eigenpair residual tests the eigensolver **for the captured matrix**, not whether the underlying derivative is converged or physically correct. In a separate read-only reanalysis of that same saved matrix (Python 3.12.14, NumPy 2.3.5, SciPy 1.17.0), applying the consistent similarity transform `A′ = D A D⁻¹` for velocity/wake in mm/s and angles/rates in degrees preserves the root +0.0570518635 s⁻¹ but changes its reported 2-norm eigenvalue condition number from **3.65 to 59.08**. A condition value computed in mixed units is therefore not an intrinsic robustness bound; nor are raw cross-block matrix entries comparable without scaling. The extended checked capture now includes the full 9×9 matrix at h = 10⁻⁷, 10⁻⁶ and 10⁻⁵. I independently recomputed the positive root as +0.0570518636012, +0.0570518634955 and +0.0570518633795 s⁻¹, respectively; the replicated h = 10⁻⁶ matrix matches the captured production matrix element-for-element. This supports finite-step stability of that root at this condition over the tested steps, but three steps in the same coordinates and replicated RHS do not establish global derivative convergence, correct model structure, nonlinear response or physical validity.

**Modal acceptance criteria:** broaden the full-Jacobian central-difference study using coordinate-scaled perturbations and independent derivative implementations; check the signed root and eigenpair residuals with independent algorithms and compare with automatic/analytic derivatives or finite perturbations where practical. Track invariant modal subspaces continuously over a finer trim-speed sweep and deliberate coupling homotopy; scale state coordinates consistently before interpreting eigenvectors/participations. Report mode-label confidence and individual real roots when classification is ambiguous, rather than forcing every real pair into a named mode. Check matched small nonlinear perturbations with the same frozen assumptions, then add explicit servo/shaft/fuel dynamics and native/session conditions as a separate study. Physical qualification requires measured airframe evidence, not this synthetic/model-only result.
