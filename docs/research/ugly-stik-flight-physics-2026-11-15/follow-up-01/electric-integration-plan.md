## Findings and priorities

1. **ORG-02, confirmed by source and checked engine probe:** both ideal and finite-pack Electric 6S have named wheel bindings and an applied physical wheel profile but no reviewed *statistics* landing-support row. This intentionally fails closed, but a normal clean touchdown can stay open until a departure or flight end, and landing success is not credited. The default no-profile rest height also affects the takeoff and rearm clearance gate. A dedicated row was mechanically derived and agrees with the loader and contact validator; human role review and actual-adapter tests remain before a future code change is accepted.
2. **ORG-03, confirmed by source:** the runway visual fixture selects the ideal input for Electric 6S, whereas a fresh Home preference defaults to finite pack. Its receipt records only the aircraft ID, and its comparison joins frames by view/time without checking source identity; thus a mode or aircraft change can masquerade as an ordinary visual/physics difference. The current tool is a technical ideal-source fixture, not evidence for a finite-pack Home flight. No current capture was executed.
3. **Additional provenance limitations, confirmed by source:** statistics retains the accepted input hash per flight but groups ideal/pack by aircraft ID, and a closed record does not explicitly identify the resolved support profile. Existing logs and cost receipts have stronger source binding. These are distinct from a claim that any cost or flight log used the wrong source.

I read both JSON files and accumulated inventory mass and moments in their original order, as the loader does in `app/physics/aircraft_data.gd:486`, `:552`, `:576`. The ideal and pack files contain equal 20-item `inventory` arrays and equal `landing_gear` objects. SHA-256 below is over exact input-file bytes:

The source datum is not the support profile's body frame. For source point `p` and inventory CG `c`, the loader computes body FRD `[c.x - p.x, p.y - c.y, c.z - p.z]` (`aircraft_data.gd:612–647`). Authored physical IDs are reattached in order (`:279–285`); the contact contract carries IDs, indices, and the derived positions (`app/physics/aircraft_contact_contract.gd:57–110`). Physical wheel-profile application decorates contacts and does not change their positions (`app/physics/wheel_profiles.gd:96–120`). The appropriate **candidate**, independently calculated from the Electric input, is:

| Index | Stable support ID / wheel name | Authored datum `[aft,right,up]` m | Candidate body FRD `[forward,right,down]` m |
| ---: | --- | --- | --- |
| 0 | `contact_main_left` / `main_left` | `[0.215, -0.18, -0.2531]` | `[-0.0941, -0.18, 0.25778446764371277]` |
| 1 | `contact_main_right` / `main_right` | `[0.215, 0.18, -0.2531]` | `[-0.0941, 0.18, 0.25778446764371277]` |
| 2 | `contact_nose` / `nose` | `[-0.136276, 0.0, -0.249925]` | `[0.257176, 0.0, 0.2546094676437128]` |

The natural proposed classification is main IDs `[contact_main_left, contact_main_right]` and stop IDs `[contact_main_left, contact_main_right, contact_nose]`. The checked probe validated both accepted source files, these IDs, indices and points against the existing contact-map validator. This describes the authored simulator support geometry and is consistent with the source names. An independent review still needs to confirm these roles; this software check does not certify the aircraft's real gear or performance.

The existing basic Stik row in `app/statistics/profiles.gd:34–42` has the same role names but **different CG-relative positions**. Its main X is `-0.105607562648019` m and Z is `0.253308375964654` m, versus electric X `-0.0941` m and Z `0.25778446764371277` m. The offsets, approximately `+0.011507562648019` m X and `+0.004476091679059` m Z, exceed the profile's `1e-6` m per-coordinate tolerance (`profiles.gd:9`, `:247–291`, `:331–339`). Reusing or aliasing the basic row therefore fails the current geometry validator and would be wrong even if that validator were weakened. The synthetic electric demo rows are similarly not substitutes for this installed stock Electric's current CG.

Following `_rest_pitch` and `_rest_height` (`profiles.gd:295–328`), both electric files yield:

```text
dx = 0.257176 - (-0.0941) = 0.351276 m
dz = 0.2546094676437128 - 0.25778446764371277 = -0.003175 m
rest_pitch = atan(dz / dx) = -0.009038230749287 rad = -0.5178524762 degrees
rest_height = mean(z*cos(rest_pitch) - x*sin(rest_pitch)) = 0.256923452624336 m
clearance = max(0.25 m, 0.1*1.524 m) = 0.25 m
```

The basic's same wheel positions relative to the LE give the same geometric pitch but a different CG-relative rest height of about `0.252343537178618` m. These are the profile's uncompressed geometric reference values, not a measured ground stance or physical sag.

`Profiles.resolve` starts with `landing_available=false`, empty support indices and reason `unreviewed_aircraft_profile`; only an ID-specific row plus matching model identity, span, contact IDs, count, indices and geometry admits support (`profiles.gd:149–205`, `:247–291`). The existing test deliberately lists the Electric 6S as unreviewed and checks both source modes (`app/tests/test_flight_statistics_detector.gd:10–20`, `:119–169`, `:196–234`); physical wheel reuse is expressly not the statistics review. The source-derived row above has **not** been installed.

### Consequences for recording and presentation

- With no reviewed profile, the adapter's `intended_support` and `stop_support` are false even when wheel compression identifies physical contact (`app/statistics/fixed_wing_adapter.gd:78–86`, `:123–133`). A clean incident-free stationary contact therefore cannot accumulate the support/stop windows needed for a completed landing. It can stay `contact_pending`; if it subsequently gets sustained rearm clearance it resolves as an unknown `bounce_departure` with `classification_unavailable`, while `end()` resolves an open episode as unknown `ended_before_resolution` (`app/statistics/detector.gd:178–185`, `:335–406`). Incident and terminal paths have separate behavior, so do not describe every contact as automatically unknown. Existing unreviewed tests drive synthetic samples and exercise end/interruption, takeoff, speeds and terminal crash; they are not a real landing trial (`test_flight_statistics_detector.gd:196–234`).
- There is a separate clearance effect even before successful landing classification. An unreviewed profile sets `rest_height_m=-1.0` and, for this span, `clearance_m=0.25`; the adapter therefore tests no contact plus `CG height above local terrain >= -0.75 m`. With the candidate row it would test `>= 0.506923452624336 m` (`profiles.gd:153–165`, `fixed_wing_adapter.gd:123–128`). The detector still requires 1.0 s for liftoff and 2.0 s for contact rearm (`app/statistics/rules.gd:9–17`, `detector.gd:317–325`, `:388–392`). This is a code-derived gate difference, not an observed false takeoff; a real-adapter regression is needed because existing synthetic samples set `clearance_ok` themselves.
- The reducer counts successful landings as full stops plus touch-and-go, counts unknown separately, and excludes unknown from `landing_rate`'s success-plus-failure denominator (`app/statistics/reducer.gd:201–216`, `:228–235`). A closed unresolved flight can increase the ended count without increasing completed count; abandoned/restarted/other non-completed outcomes also interrupt the completed-flight streak under the rules in `:254–279`. Whether a record is marked partial is determined by observation continuity/outcome, not by the mere absence of a reviewed profile (`:205–210`, `app/statistics/service.gd:300–306`).
- The summary screen can show “no resolved touchdowns yet” and a clean-stop fraction without explaining missing profile coverage. Unknown episode totals appear under More statistics; expanded history may show a retained landing event/reason, subject to the event cap, but does not identify the missing Electric support profile (`app/ui/statistics_screen.gd:465–487`, `:514–532`, `:702–733`, `:812–858`; `service.gd:360–378`). Recommend a concise coverage indication where an unsupported current flight or recorded unknown episodes are shown, without calling unknown a failed landing.
- `app/app_root.gd:3426–3442` attaches the accepted session's input SHA-256, and `service.gd:258–264` persists it as flight `config_hash`. The reducer selects by aircraft identity, not by that hash (`reducer.gd:45–62`), so ideal and pack sorties are combined in the same aircraft aggregate. The record context/history UI has no battery-mode label (`app/statistics/record_view.gd:11–53`, `app/ui/statistics_screen.gd:665–712`, `:746–785`); this is grouping and discoverability, not a wrong hash. Mode should only be attached to a historic hash when exact source bytes and version are known; otherwise show unknown.
- `rules_version` and the aircraft hash do not by themselves prove whether the support row existed at flight time. `profile_version` exists in the resolved profile (`profiles.gd:8`, `:153–155`) and its active detector snapshot (`detector.gd:194–208`), while normal ended records store `rules_version`/`config_hash` and the active context is cleared on end (`app/statistics/schema.gd:28–37`, `service.gd:500–508`). If per-flight coverage provenance is needed, consider an additive, bounded profile/coverage marker on new records with legacy value unknown; verify schema and backward readers before choosing its precise contract. This need not imply a global rules-version bump when the classification thresholds themselves are unchanged.

## ORG-03: runway capture and comparison source identity

Fresh Home preferences default to `pack`, though a persisted user choice can select `ideal` (`app/app_state/preferences.gd:53–55`, `:164–166`, `app/ui/home.gd:1554–1568`). Home passes the chosen mode into Main (`app/app_root.gd:1340–1346`, `:1499–1500`); Main selects `Catalog.data_for` and defaults an unspecified stock mode to the catalog default (`app/main.gd:625–626`, `:858–864`). The catalog entry's primary `.data` is the ideal file; `.battery_data` is the finite-pack file (`aircraft_catalog.gd:69–78`, `:316–328`).

The runway fixture independently does `_session.setup(Catalog.entry(aircraft).data)` (`app/scenery/runway_scenario.gd:114–127`), so its Electric 6S run selects ideal fixed voltage. Its manifest records the canonical aircraft ID, scenery, start, engine/renderer, times and per-frame image hashes and state, but no actual aircraft data path, input hash or source mode (`runway_scenario.gd:103–106`, `:193–202`). The word “battery” in `research/flight-test` means a test card and must not be interpreted as evidence of pack mode.

The comparison issue goes beyond a missing label. `tools/scenery/scenario.sh:14–17`, `:25–28` automatically compares a new run with the immediately preceding one in that output root. `tools/scenery/scenario_report.py:98–127` matches frames by `(view, t_s)` and reports `physics changed`, `visual-only change` or `identical` based on sampled state and images; it does not compare aircraft ID, aircraft input path, hash or source mode first. Its HTML identifies the current aircraft but not the previous aircraft/source (`scenario_report.py:130–143`). A caller can therefore intentionally or accidentally compare different aircraft or source modes without that distinction in the verdict. The comparison is useful as a difference report, but its verdict is only about those sampled fields/images, not proof that sources or all physical laws matched. Historical manifests without a source identity must remain **unknown**, even if their ID or filename looks familiar.

The basic glow default remains its original input, with electric mode marked not applicable. 2. Do not claim that a requested CLI mode succeeded when the accepted source disagrees. Preserve human-readable aircraft ID and current frame fields. Decide whether additions are safely additive to v1 or require a new version by checking all actual consumers; `scenario_report.py` currently reads known keys and tolerates extra JSON keys, but that alone is not proof for unknown external consumers.
3. In `scenario_report.py` and HTML/history, show current and previous source identities plus a separate comparison-compatibility status such as same, changed, or unknown/legacy. Deliberate source changes should still produce state/image differences with the change prominently labelled; do not universally reject different hashes, because before/after aircraft-data comparisons are useful. Refuse to claim a like-for-like energy-source comparison when either identity is absent or differs. Keep sync results distinct from source comparability and numerical change verdicts.
4. Test basic legacy/default compatibility, Electric ideal and pack selection/actual hashes, invalid/unsupported mode refusal, same-ID/same-hash comparison, same-ID/different-hash comparison, different IDs, and old manifests lacking identity. Check that the report never fills legacy mode from current preferences/defaults. Use a fresh output root and preserve the baseline: `scenario.sh` rotates `latest`/`previous` and prunes old history (`tools/scenery/scenario.sh:14–17`, `:30–38`). Preserve generated receipts and compare real accepted hashes, not just filenames; separately retain the renderer/engine/environment information needed for visual comparisons. A headless code test or synthetic manifest test does not by itself qualify rendered behavior.
