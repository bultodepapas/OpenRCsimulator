## Ownership and freshness, step by step

| Transition | Current production behavior and implication |
| --- | --- |
| Enumerate and select | The registry changes generation on reconnect/identity change and removes lost selections (`app/input/controller_registry.gd:37–72`, `:93–111`). The managed service attaches an explicit flight owner and passes its current profile (`app/input/controller_service.gd:169–188`). `FlightSession.apply_controller_selection` disconnects the old reader, pauses and reconnects the selected owner (`app/sim/flight_session.gd:1957–1985`). `RcInput.connect_device` clears axis history and arming (`app/input/rc_input.gd:76–126`, `:559–568`); device-ID equality by itself is not a durable identity lease. |
| Event arrival | `FlightSession._input` forwards the event's device number, axis and value; `on_motion` checks that number, range and finiteness, then records a per-axis `_seen` boolean and the event value (`app/sim/flight_session.gd:1821–1828`; `app/input/rc_input.gd:231–262`). The event record has no event sequence, timestamp, connection generation, focus epoch or profile epoch. A fresh LOW throttle event sets separate throttle evidence. |
| Poll and arm | Every subsequent poll independently overwrites all ten stored axes with the reader's current numbers (`app/input/rc_input.gd:287–322`). For a raw absolute radio, LOW event evidence plus a LOW poll arms; a contradictory HIGH poll clears LOW evidence (`:376–393`). Other primary axes need no event or verified live snapshot. The managed session uses `radio.sticks()` as commands and feeds the shaped result into the simulation when allowed to run (`app/sim/flight_session.gd:3070–3112`, `:4205–4215`, `:4262–4265`). This is the path underlying C1. |
| Ordinary menu hold | `hold` disables AUX and pauses, but only managed gamepads are asked to requalify; a radio ordinarily keeps readiness (`app/sim/flight_session.gd:1928–1939`; `app/input/rc_input.gd:198–220`). The session continues non-integrating polls while held or paused (`app/sim/flight_session.gd:3060–3079`); releasing the hold is distinct from resuming. Preserving a trusted radio's held absolute value may be intentional. |
| Focus loss and recovery | On managed focus loss, the shell invokes `controller_focus_lost`, which clears seen/axes and LOW evidence, disarms, disables AUX and pauses (`app/app_root.gd:2966–3002`; `app/sim/flight_session.gd:1998–2003`; `app/input/rc_input.gd:198–220`). However, `on_motion`/radio `poll` have no focus argument; a LOW event and non-integrating LOW poll **after the last loss reset** can arm while still paused (`app/input/rc_input.gd:253–260`, `:376–386`). The checked reader probe confirms `armed=true` from that injected ordering with `integrate=false` and no roll event; it does not model the operating system focus state. The project requests joypad input in the background (`app/project.godot:40–42`), but actual platform delivery is untested. If those calls occur while unfocused, recovery evidence can precede focus return; the code does not require an additional radio reset on focus-in. A later HIGH event or HIGH poll revokes pending focus rearm, and the managed session still needs its applicable launch/Continue path. This is a conditional input-contract question, not an observed background flight or proven OS behavior. |
| Profile replacement | The direct `RcInput.use_profile` path deliberately preserves radio diagnostic `_seen` and raw axes across a radio-to-radio activation while clearing arming and LOW evidence (`app/input/rc_input.gd:142–160`, `:522–555`). Existing `app/tests/test_rc_axis_history.gd:58–67` explicitly checks this distinction. For the usual managed service selection, `apply_controller_selection` disconnects/reconnects and clears reader history; do not generalize the direct-reader history behavior to that path. |
| Disconnect and failure | Reader disconnect clears state, and managed flight loss pauses, idles and requires a new explicit selection (`app/input/rc_input.gd:164–175`; `app/sim/flight_session.gd:1988–1995`). Nonfinite data faults the reader (`app/input/rc_input.gd:235–243`, `:314–321`); managed polling routes errors to loss handling (`app/sim/flight_session.gd:3060–3066`). These guards do not prove that a finite, held-looking value is live when a backend silently stops updating without reporting loss. |

## New counterexamples and bounded interpretations

**1. `_seen` alone cannot qualify the command.** Inject a valid radio profile; deliver a roll event `+0.8`, deliver a LOW-throttle event, and then poll throttle LOW while the independent roll poll returns `0.0`, with no intervening roll event delivered to the reader. `_seen[roll]` is true and the radio arms, but `sticks().roll` is normalized from the polled `0.0`, not the event's `+0.8` (`app/input/rc_input.gd:235–250`, `:317–322`, `:421–427`, `:448–458`). The checked probe observes `armed=true`, `has_axis_sample(roll)=true` and returned roll `0.0` in this sequence. This does not establish which number better describes a real stick: the poll may race ahead of a queued motion event, or a backend may return stale data. It establishes that a proposed repair of C1 that merely checks all existing `_seen` bits does not prove the values actually used by flight correspond to those events.

**2. `_seen` is historical diagnostic state, not a mapping lease.** With a configured raw radio, send axis 4 event `+0.6`, then replace the profile via `use_profile` so axis 4 becomes roll. The checked probe observes `has_axis_sample(4)=true` after activation although no event arrived after that activation; throttle arming is nevertheless reset and still requires new LOW evidence. `app/input/latency_patch.gd:147–168` uses `has_axis_sample` to decide whether a visible diagnostic marker is active. That marker's “move selected axis” check therefore establishes that an event has occurred in the retained history, not that the current polled value is fresh or that the event happened after the new mapping. A separate authority/evidence structure is preferable to redefining the intentionally retained diagnostic history; update the diagnostic's wording or evidence contract if it needs stronger freshness claims.

**3. “Armed” is route-specific motor/readiness language, not necessarily a surface interlock.** With an absolute radio connected and unarmed, a finite roll input still appears in `sticks().roll`, while returned throttle is zero (`app/input/rc_input.gd:448–458`). Managed flight refuses Continue with a connected unarmed reader and while paused does not publish radio commands (`app/sim/flight_session.gd:2275–2306`, `:3073–3079`). The checked reader probe returns roll `0.8` and throttle `0.0` with `armed=false`; source analysis shows that the technical/direct route can publish such surface commands without radio arming: its arm and pause checks are conditional on `external_controller_selection` (`:2277–2288`, `:3081–3112`, `:3127–3147`). `--quick-flight` is a documented direct route (`app/app_root.gd:529–531`; `app/main.gd:1–4`, `:610`). Live surfaces with a disarmed motor can support preflight inspection; neither this review nor the source establishes a requirement to suppress all surfaces. Treat this as a route-specific contract/documentation decision. If a future freshness repair makes the **session** wait for trusted controls, apply the same declared policy deliberately to both routes rather than assuming `armed` means all-channel validity. Distinguish readiness from throttle arm, and preserve trim/preflight surface inspection when intended.

**4. Continuity cannot be inferred from silence alone.** A stationary radio that emits only changes and a radio whose last value has become silently stuck can produce the same event stream and repeated finite poll values. The available reader state does not distinguish those situations. A blanket “no recent event means disconnect” timer would incorrectly disarm quiet devices. Conversely, an old event bit or repeated poll is not proof of ongoing hardware communication. Stronger guarantees require a backend-provided current snapshot/heartbeat, device report sequence, explicit health signal, or qualified physical/backend behavior. Mark the remaining case unknown; never claim a software-only timer detects every frozen controller.

## Calibration isolation, persistence and exceptional routes

* **Before completion:** `RcCalibration` creates its own candidate and deep-copies compatible AUX instead of editing the supplied active dictionary (`app/input/rc_calibration.gd:63–75`). Invalid sweep/confirmation data resets the current sweep or keeps the wizard on that step; already finished stages remain wizard-local (`:151–165`, `:182–255`). The preflight wizard cancels on focus loss, interruption, disconnect or invalid sample, and emits a copied candidate only on completion after LOW/FULL/LOW verification (`app/ui/radio_calibration_setup.gd:74–90`, `:100–135`, `:159–194`). Home Controls merges completion into a copied draft and records the generation; Cancel leaves the draft unchanged, and explicit Save is the activation/persistence boundary (`app/ui/controller_setup.gd:553–608`; `app/app_root.gd:2167–2193`). Existing tests exercise cancellation and changed identities (`app/tests/test_controller_preflight_calibration.gd:48–52`, `:73–81`, `:100`, `:119`). These are source/test intentions, not newly run UI results.
* **Managed in-flight completion:** a positive connection-generation lease is required at start and rechecked at completion; failed persistence retains a deep-copied, generation- and device-bound pending candidate with an error instead of the session applying it directly (`app/sim/flight_session.gd:1857–1895`). Home offers that pending candidate only for the matching current device, key and generation, and clears it when saved or discarded (`app/app_root.gd:2104–2120`). Disconnect clears pending (`app/sim/flight_session.gd:1988–1995`). The checked probe injects a rejecting persistence callback and observes unchanged active profile with a generation-12 pending draft; that isolated callback is not a real storage failure or proof of rollback under I/O failure. `ControllerService.save_calibration` merges/validates before its transactional save (`app/input/controller_service.gd:406–420`); the save path snapshots storage, saves, attempts activation, and requests restoration on refusal (`:654–675`). Setup's broader transaction also restores store/cache/roles/runtime, reporting failures explicitly (`:507–529`, `:554–589`). Rollback is attempted and failure surfaced; it cannot be claimed unconditionally atomic if the storage restore itself fails. Existing hardening tests specify rejection and restored storage/profile cases (`app/tests/test_controller_profile_hardening.gd:272–295`, `:395–408`); they do not establish that every filesystem or power-loss failure was tested here.
* **Direct/legacy completion:** `advance_calibration` applies a completed candidate to the reader first, then checks legacy identity uniqueness and attempts persistence; an ambiguous identity or save error yields `radio calibrated, NOT saved (error ...)` but does not roll back the already activated candidate (`app/sim/flight_session.gd:1881–1907`; `app/input/controller_profile_store.gd:235–273`; `app/input/rc_calibration.gd:320–333`). Cancelling before completion only drops the wizard and leaves the previous active profile (`app/sim/flight_session.gd:1910–1914`). The checked probe uses two injected identical legacy identities: the candidate changes the active center from `0.0` to `0.2`, and the session reports `NOT saved (error 22)` without attempting a filesystem save. Thus a completed-but-unsaved calibration can affect the **current direct session** while remaining absent from durable storage; this is not proof of silent corruption because the error is displayed and session-only application may be intentional. The direct route also replaces the profile from the wizard's narrow result instead of using the managed profile merge, so preserving other profile metadata/behaviors must be evaluated explicitly before promising full-profile continuity. If the intended semantics are transactional, retain the old runtime profile until save succeeds or provide an explicit, accurately labeled session-only choice; if session-preview is intended, clearly state that the current flight uses the new calibration even though a restart will not load it. Do not silently change either policy.
* **Boundary assumption:** standard service attachment binds the managed persistence callbacks (`app/input/controller_service.gd:169–182`). The session's completion branch falls back to legacy behavior if `external_controller_selection` is true but `persist_controller_profile` is invalid (`app/sim/flight_session.gd:1884–1905`). This is a source-visible misconfiguration boundary, not proof that normal Home loses its callback. A stricter managed contract could reject/retain a candidate if its service disappears, rather than implicitly changing persistence routes; test the real owner lifecycle first.

The C2 outlier case remains different: a bad endpoint **accepted as a valid measurement** can be completed and saved; ordinary Cancel protects the old profile only while cancellation actually happens. A reviewable candidate and explicit confirmation do not establish physical correctness of its measurement.

## Minimum defensible contract and alternatives

**Recommended design:** separate diagnostic history, command values, and permission to publish a complete flight-input snapshot.

1. Give an input owner an immutable token identifying selected device/connection generation plus a focus/input-acceptance epoch and a mapping revision. Invalidate authority on loss, selection change, focus loss, invalid input, profile remap and detected backend discontinuity. A raw ID or `_seen` boolean alone is not that token. Increment the mapping revision only for a meaningful flight-input mapping/calibration change; saving an unchanged profile or editing unrelated UI preferences should not require another radio sweep. Require event/poll observations to be tagged at acquisition where the backend permits; old queued events arriving after an epoch change cannot be proven new merely because delivery is late.
2. For each primary raw-radio axis, qualify an actual value for the current token before granting the **flight readiness** that managed or direct sessions use. A supported backend's verified fresh snapshot can qualify a stationary axis without any gesture, provided the backend contract establishes axis validity and identity. Otherwise prompt the pilot to move each missing mapped control once and restore the intended position, showing which checks remain. Preserve all mapped control signs and transmitter mix/rates/expo; do not impose another expo/dead zone, centered dwell on radios, arbitrary servo filtering or a new continuing event-frequency timeout. LOW throttle remains a distinct motor-arm rule. A quiet device then remains flyable after an explicit one-time check instead of being falsely timed out. For a focus-sensitive policy, accept reacquisition only while the app is genuinely focused and start a new epoch on focus return; document whether an ordinary in-app menu requires a new epoch.
3. Keep the actual output tied to a qualified coherent value: either use a sequenced authoritative event stream and its last value, or accept a backend snapshot with a documented ordering/validity guarantee. If event and poll disagree without an ordering proof, quarantine or requalify the affected input at a boundary rather than treating a past `_seen` as evidence for the new poll. A mandatory fail-stop on every transient mismatch might make racing backends unusable; characterize real ordering first and choose a bounded retry/settling policy. Do not imply this detects silent mid-flight failure in the absence of hardware continuity evidence.
4. Keep the existing verified standard-gamepad path: it checks focused selected handle, generation, connected/known identity and mapped standard axes (`app/input/controller_service.gd:191–207`; `app/input/rc_input.gd:182–189`, `:323–353`). It may accept a stationary or deflected controller immediately on a verified snapshot (`:345–375`). Do not force a radio sweep or center gesture on that trusted path. Loss of an established verifier already disarms/faults according to hold/flight state (`:329–338`).

An alternative is to accept the existing polled snapshot after an explicit pilot control check and label the guarantee “pilot confirmed,” with a one-time warning rather than per-axis evidence. It is simpler and may support radio firmware that cannot generate observable events for some axes, but cannot automatically prove each channel or ordering; the pilot may affirm a stale value. Another is a separately qualified raw-device snapshot provider, with no gesture, but it requires backend/platform qualification. A hidden timeout or replacing unknown raw zero with a guessed center is neither equivalent to these contracts nor a proof of the actual hardware position.

**Implementation ownership, for a later patch:** `app/input/rc_input.gd` should own values and per-axis qualification rather than making `_seen` do double duty; `app/input/controller_service.gd` and `controller_registry.gd` should supply identity/generation and qualified backend health; `app/sim/flight_session.gd` and `app/app_root.gd` should own focus/selection/mapping transitions and readiness gating; `app/ui/pause_menu.gd`/Controls and `app/input/latency_patch.gd` should explain incomplete qualification without implying unwarranted freshness. Keep calibration candidate/commit handling with `rc_calibration.gd`, `controller_service.gd`, `controller_setup.gd` and the session as appropriate. Audit helicopter/multirotor and direct consumers before altering shared `RcInput.sticks`, `_seen`, or `armed`; a fixed-wing-only session gate may be a safer first integration if common contracts differ.

## Acceptance matrix for a proposed repair

| Scenario | Required observable outcome |
| --- | --- |
| Raw radio, offset center, only throttle reports | No unqualified roll/pitch/yaw value reaches a runnable flight; show exactly which axis needs evidence. LOW alone must not qualify the others. |
| Event says `+0.8`, subsequent unordered poll says `0.0` | The code does not assert that `_seen` proves the polled value fresh. Apply the documented ordering/settling policy and either use a qualified value or hold/requalify. |
| Quiet event-on-change radio after all axes qualified | Remains ready indefinitely while held still; no generic per-axis age timeout. A reported disconnect or focus/owner boundary still invalidates the applicable epoch. |
| Focus out, background motion/LOW, focus in | No pre-return background event silently counts as post-return proof if the chosen policy promises focused reacquisition; require a focused snapshot/gesture and explicit Continue where that route requires it. Separately test platforms that do not deliver background motion. |
| Disconnect and same-ID reconnect, select another device, or remap | Old authority cannot transfer to the new token; unchanged diagnostics may retain a visibly historical record. A new owner requires its own qualified axes. Test queued out-of-order events where the backend exposes ordering. |
| Verified live mapped gamepad, centered or deflected | Existing focused/selected/generation proof accepts the live snapshot without a mandatory sweep, new deadband, neutral dwell, or lost rate-throttle state; loss/recovery follows existing verified rules. |
| Radio shaping and controls | Identical qualified physical-axis values before/after the change yield identical signed normalization, transmitter shaping, throttle and trims. No double expo, imposed center, swapped channel, or unrequested travel reduction. |
| Ordinary hold and direct route | A radio's intended held controls, throttle policy and preflight surface inspection behave as specified; managed and direct flight publication rules are explicit rather than inferred from the word `armed`. |
| Cancel, invalid step, focus/disconnect during calibration | Active profile and durable store remain as specified; preflight draft remains unchanged on cancellation; generation change refuses candidate activation. |
| Managed rejection after write, and rollback failure | Verify old runtime/cache/bytes and signal order when restoration succeeds; inject failed restore and assert the surfaced failure and non-resumable recovery state without claiming atomic success. |
| Direct duplicate identity or storage failure | Assert the chosen documented policy: session-only activation with prominent NOT-saved indication, or unchanged active profile/explicit preview. Verify subsequent restart and metadata continuity under that policy. |

**Still required:** relevant existing tests under checked execution where not already evidenced elsewhere, negative/rollback injection at the real service boundary, native controller report/sequence capture for quiet and moving radios, focus loss/recovery on target Windows/macOS/Linux backends, real transmitter mixes and shared UI/flight controller, and a pilot-visible flow. None is physical qualification merely because a synthetic assertion passes.
