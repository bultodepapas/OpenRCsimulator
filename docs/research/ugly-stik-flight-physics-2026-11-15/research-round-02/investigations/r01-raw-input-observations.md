# R01 — Raw input observations and freshness

**Decision: prototype/measure first.** Define what each number proves before using it to grant radio flight readiness. The reader accepts motion events and a replaceable poll source; neither a finite value nor an event alone proves a fresh hardware report. Preserve the separately qualified standard-gamepad route while investigating raw devices.

**Second-round update.** [S2-01](../second-round/s2-01-pinned-input-backend.md) inspected the exact beta2 source: the normal Godot poll reads an event-fed axis cache, which Godot updates before dispatching the same event. OpenRC's ordinary flight initialization disables accumulation and the pinned agile-flushing default is off, so the injected event/poll mismatch below is a real reader-seam counterexample but has not been established in that normal path. Some raw-axis initialization paths suppress the first motion event, with device/backend and virtual-device exceptions; actual initial availability and ongoing hardware health remain device-specific and unqualified.

## Current implementation and evidence

At runtime baseline `08f0c08348395c0d6d9f7e224f66460828f59a7f`, `FlightSession._input` forwards device, axis and value to `RcInput.on_motion`; on the raw-radio path, its per-axis `_seen` records that *an* event occurred. A verified gamepad poll can also establish `_seen` for mapped axes. `RcInput.poll` subsequently overwrites all ten axes using the supplied reader callable, and `sticks()` normalizes these polled values (`app/sim/flight_session.gd:1821–1828,3059–3112`; `app/input/rc_input.gd:231–262,289–322,448–458`). The checked prior follow-up injected roll event `+0.8`, a low-throttle event and a poll returning roll `0.0`; it observed `_seen` true, radio armed and roll `0.0`. That is a reproducible reader-level sequencing counterexample, not evidence which value was physically correct. See [follow-up input contract](../../follow-up-01/input-contract-and-repair-plan.md) and its retained seven-check receipt. No new engine or device test was run for R01.

Godot's [beta2 release](https://github.com/godotengine/godot-builds/releases/tag/4.8-beta2) identifies commit `cafc17a192acf67903910a68aeb3c076c0907a4b` (29 October 2026; IN-S01). The [4.7 controller documentation](https://docs.godotengine.org/en/4.7/tutorials/inputs/controllers_gamepads_joysticks.html) says desktop Windows, macOS and Linux use SDL3 since 4.5; specialized hardware is less tested (IN-S02). The [latest Input API](https://docs.godotengine.org/en/latest/classes/class_input.html) calls `get_joy_axis` the current axis value (IN-S03). This unstable documentation is not a beta2 ordering or report-freshness guarantee.

SDL3's [axis getter](https://wiki.libsdl.org/SDL3/SDL_GetJoystickAxis) returns a current value but also returns zero on failure (IN-S04); its distinct [initial-axis API](https://wiki.libsdl.org/SDL3/SDL_GetJoystickAxisInitialState) returns a boolean indicating whether an initial value exists (IN-S05). [SDL_UpdateJoysticks](https://wiki.libsdl.org/SDL3/SDL_UpdateJoysticks) describes automatic event-loop updates under stated conditions (IN-S06). These are SDL 3.2+ contracts, **not** proof that Godot exposes the initial-value boolean, delegates a poll directly to those calls, or delivers a new hardware sample for every call. The first pass did not inspect the exact beta2 implementation. S2-01 subsequently inspected it: the vendored version header declares SDL 3.4.16, while the same commit's third-party inventory says 3.4.12; that discrepancy is not a separate runtime-version measurement. Godot issue [#111231](https://github.com/godotengine/godot/issues/111231) reports a Windows T.16000M on 4.5/4.6-dev with unmapped joystick axes lost when mapped as a gamepad (2025–26, IN-S07). It is a concrete compatibility lead, not a beta2 regression or proof affecting RC transmitters.

## Contract alternatives

1. **Qualified snapshot:** a backend supplies the values used, connection and mapping generation, per-axis availability and a documented observation boundary. Trust only within its validated OS/engine/device domain. A snapshot's initial-value availability is still not proof of later continuous hardware communication.
2. **Event-owned axes:** use the value from a suitable event rather than combining its historical `_seen` bit with an unqualified reader value; maintain an explicit epoch and a way to acquire stationary or held-at-connect values. Requiring every axis to *move* after selection can strand a quiet, change-only radio and may require an undesirable gesture.
3. **Unqualified fallback:** keep values visible for setup/inspection while readiness remains explicitly unknown; ask for a deliberate, clear pilot check only if it has a specified and testable product contract. Manual confirmation cannot establish ongoing link health.

Never claim a periodically repeated poll or arbitrary event-age timeout is a heartbeat. A stationary radio and a silently frozen but connected radio can produce identical values and no change events. Backend heartbeats/report counters, an explicit health signal or independently verified device-specific guarantees are needed to distinguish them.

## Integration and acceptance

Keep diagnostic history (`has_axis_sample`) distinct from authority; its direct radio-to-radio remap retention is intentional in existing tests. Bind any new authority to the selected flight owner, connection generation, mapping and focus epoch, with defined handling for queued older events (R03). Exercise both direct and managed session paths. Test offset centers, nonzero axes held before connect, event/poll disagreement in both orders, missing primary axes, remap, reconnect with reused handle, held stationary controls and nonfinite readings. Verify focused trusted-gamepad zero/held controls and Continue semantics remain unchanged. Native traces should record OS, build, device/firmware, USB/Bluetooth, backend mapping, event and poll order and independent hardware observations; lack of an event must not be reported as proof of disconnect.

**Disposition: prototype/measure first.** The existing callback contract lacks enough provenance to select a universally safe automatic repair. The pinned driver has now been inspected in S2-01; acquire native traces and adopt only a qualified observation source with the above regressions.
