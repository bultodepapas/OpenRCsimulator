# NITRO-02 — Installed two-stroke and four-stroke candidates

2026-10-13. **Both engine families are implemented and playable as experimental installations. Physical/pilot and release acceptance remain open.** [Operating/configuration guide](../../../GLOW-ENGINES.md), [plan](../../../plans/RC_NITRO_ENGINE_REALISM_PLAN.md), [2T calibration dossier](../NITRO-2T/README.md), [4T calibration dossier](../NITRO-4T/README.md), [audio evidence](../NITRO-audio/README.md).

## Implemented and tested

- Separate ported 360° and valve/intake/pumping 720° mean-cycle kernels, independent maps and fuel accounting; no family-wide power or efficiency multiplier.
- Closed finite-fuel aircraft extension; manufacturer-constrained candidate engine profiles and two generated propeller combinations per family. Exact engine/installation bytes participate in identity and replay.
- RK-stage engine/propeller/body coupling; a passive annular propeller surrogate; forward windmill breakaway, stopped drag and visible refusal of unsupported reverse rotation.
- Transport-driven mixture, servo/charge/fuel response, temperature feedback, opportunity/success counters, warm starter, cut, stall, overheating and exact nonnegative tank exhaustion.
- Fixed-body-datum variable mass/CG/full inertia with co-moving efflux; independent force/momentum fixtures, no phantom inertia-derivative torque.
- Separate catalog selections, stable Stik renderer adapter, mixture/cut/start controls, telemetry, versioned checkpoints and trace recording, procedural 2T/4T native sound.
- Propeller diameter drives the rendered blade/blur, aerodynamic load and inventory. Relative shaft inertia includes the full inventory propeller polar plus estimated crank inertia; changing props changes their acceleration and gyroscopic contribution.

The ground solver correctly refused stationary idle starts when calculated idle thrust exceeded the wheels' static hold. Glow runway starts therefore use a stopped warm engine; explicit starting releases the aircraft into ordinary force-driven rolling. The software test commands full throttle, then elevator after three seconds, and checks both installations climb. It does not fit or validate a real takeoff distance.

## Reproduce

From the repository root (Windows; use the same pinned Godot on other platforms):

```powershell
python research/glow-engines/build_profiles.py --check
python research/glow-engines/build_installations.py --check
python research/glow-engines/verify_integration.py --godot .tools/Godot_v4.7.2-stable_win64_console.exe --out C:/temp/glow-proof --parse-all
& ./.tools/Godot_v4.7.2-stable_win64_console.exe --headless --path app --script ../research/glow-engines/flight_bench.gd -- --hz=240 --out=C:/temp/glow-240.json
```

Repeat the flight experiment at 480 and 960 Hz. Run timing separately from other test processes. The experiment records each family's cruise, throttle-up/down/cut, rich mixture, lean mixture, exhaustion and takeoff trajectory. Output is model-generated evidence, not observed engine or aircraft data.

`python research/glow-engines/refinement_report.py --check` verifies the retained trajectories, exact configuration identities and regenerated report. `packaged_smoke.py --godot <editor> --pack <exported.pck> --out <fresh-directory>` checks compiled resources; use `--godot <exported-executable> --exported` for a native application. `mutations.py --godot <editor> --out <fresh-directory>` reproduces the disposable formula faults.

The standalone `endurance_bench.gd` runs from `--headless --path app --script ../research/glow-engines/endurance_bench.gd`; it takes minutes and refreshes the canonical endurance JSON/log. `-- --validate-only` checks both initial setups without running the long experiment.

## NITRO-03 pilot-review protocol

The [protocol generator](../../../../research/glow-engines/pilot_review.py) and [blank review template](pilot-review-template.json) make the experienced-pilot review runnable. The template status is `not_performed`: no participant, physical Stik baseline, pilot maneuver, sound/vibration measurement, or acceptance result is represented. Generate the operator schedule and a separate participant-facing card sheet with a fixed seed, then validate the saved record without changing it:

```powershell
python research/glow-engines/pilot_review.py --seed 20261013 --out docs/research/glow-engines/NITRO-02/pilot-review-template.json --pilot-cards-out C:/temp/glow-pilot-cards.json
python research/glow-engines/pilot_review.py --validate docs/research/glow-engines/NITRO-02/pilot-review-template.json
python research/glow-engines/test_pilot_review.py
```

The schedule contains 48 simulator trials: two repetitions of six maneuvers for each family, each run once with procedural audio and once muted. The six cards cover warm idle/transitions, takeoff/climb, cruise, throttle loading, engine-out glide and an idle/mid/full sound review. Within each family, exactly six of twelve paired trials run audio-on first and six muted first; the family-block order and pair order use the recorded SplitMix64 seed. Pilot cards expose only an opaque token and maneuver steps. They do not expose family, profile, propeller or audio condition.

The frozen simulator baselines are the catalog Stik builds `stik-glow-55ax-2t` with candidate profile `os_max_55ax_candidate` and APC Sport LP12070 12×7, and `stik-glow-fs64v-4t` with candidate profile `os_fs_64v_candidate` and Master Airscrew K Series 14×6. The template records SHA-256 hashes for each generated aircraft, installation and profile input. These generated maps, lifecycle parameters and the audio timbre are experimental/inferred; timbre and vibration amplitudes are authored, not measured. The generated APC 13×6 alternatives are excluded because this review uses the currently selectable catalog defaults.

Run the pinned Godot build without user arguments to open Home, then have the operator select the scheduled catalog aircraft and **Runway** start while the pilot is away from the display. The direct `--quick-flight` route starts airborne and is unsuitable for these runway trials. In Home, explicitly set the default field, calm/default weather, daylight, pilot view, Runway start and one fixed overlay preset; these preferences persist between sessions, so inspect them before each block. Use the same calibrated Mode 2 USB transmitter/gamepad and `normal` rates throughout; record device axes, reversals, deadband, display resolution, app build/PCK hashes and any deviation. Keyboard fallback is arrows for roll/pitch, A/D for rudder and S/W for throttle, but it is digital and must be declared. The physical engine keys are F6 cutoff, F7 starter, F8 lean to 0.85× nominal mixture, F9 rich to 1.15×, R reset and T trace start/stop. Leave F8/F9 unused for the baseline schedule. Each card begins with R, T, F7, five seconds at idle, a three-second ramp to full throttle and takeoff to the session's fixed safe height; record any idle ground roll and do not force a static hold. The takeoff/climb card scores this sequence; other cards use it to reach the test height. Stop and save the trace with T after the maneuver, then record its path and SHA-256 in the operator record.

The app has no pilot-facing family-label hide switch. Do not rely on its UI to conceal identity: select and start the scheduled aircraft off-screen, then cover the lower-left family/engine HUD and any other visible family/profile text with a recorded external monitor mask/crop for the full pilot view. Check the displayed image before each block and record any label exposure as a failed family blind. Keep the overlay preset identical across conditions; do not enable developer overlays. The operator schedule and Windows Volume Mixer must stay out of the pilot's view. Use the same output device and fixed simulator-application volume at 50 percent for audio-on, set only that application's mixer level to zero for muted trials, and keep master volume and other sound processing fixed. Mixer percentage is a repeatable setting, not a calibrated sound-pressure level. The sound condition itself is audible and therefore cannot be blinded; conceal its assignment before each run and record the pilot's post-rating condition guess. Leave sound ratings blank for muted trials.

Before simulator A/B, a named pilot familiar with both real baseline installations must complete labeled reference/familiarization blocks. For each physical article, record its airframe build and weight/CG/inertia, engine serial/hours, exact propeller and condition, plug/silencer, measured fuel batch/recipe/density, atmosphere/wind and calibrated tachometer, temperature, fuel and flight instruments. The candidate profiles use a 72/10/18 volume-percent methanol/nitromethane/castor blend and treat lubricant as inert; matching the recipe controls blend composition but does not validate castor-oil energy/chemistry. Mark other blends as fuel-mismatched. Verify the chosen fuel against the exact MAX-55AX documentation before testing: the retained 55AX manual has a fuel-paragraph applicability conflict. O.S.'s [MAX-55AX specification](https://www.os-engines.co.jp/english/line_up/engine/air/aircraft/catalog/15612.htm) and [field observation](https://www.os-engines.co.jp/web_content/202102/index1.html) identify the 12×7/No.8 reference setup, but the reported NITRO-X Standard Red 15-18 result at 3 °C is a single observation on a different blend. O.S.'s [FS-64V specification](https://www.os-engines.co.jp/english/line_up/engine/air/single/catalog/3AY00.html) and [flight review](https://www.os-engines.co.jp/web_content/202210/index_1.html) provide the 14×6/NITRO-X reference configuration and qualitative pilot observations from a Spacewalker II; neither is matched Stik validation. For actual sound reference, save tach-synchronized recordings with calibrated microphone position and conditions; the [NIST model-aircraft method](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nbsir75-693.pdf) supplies measurement guidance, not a sound-level prior for these engines.

After every simulator run, the pilot records 1–7 handling-similarity, response-predictability, workload and confidence ratings, plus a specific discrepancy. Record sound realism only when audio is on; obtain family/audio guesses after the ratings. A family passes pilot review only after an experienced pilot familiar with its real baseline completes the schedule and labeled reference, no material unexplained discrepancy remains, and each reported difference is supported by a trace or reference observation. Any unresolved discrepancy, family-label exposure, missing reference or safety-relevant mismatch leaves that family open or not accepted. The plan's numeric RPM, torque/power/thrust, throttle, fuel/endurance, temperature, flight, sound and vibration budgets remain separate physical acceptance gates. The generator and tests verify a reproducible schedule and blank record only; validation of a record is not a pilot pass.

## Interpretation and remaining gates

The manufacturer rated power/RPM points constrain both profiles. MAX-55AX APC12×7 additionally has a single-condition static RPM observation used for a **conditional** surrogate-chord fit; the alternate APC13×6 is an inference, not a held-out measurement. FS-64V uses its own manufacturer constraints and analogous four-stroke research, with inferred shape/transients/thermal/propeller coefficients. The two dossiers retain disagreements, assumptions and uncertainty. This implements the user's permission to infer missing parameters; it does not relabel estimates as measured calibration.

Changes from the dated NITRO-01 fixture include FS-64V low-RPM torque hypotheses, an inferred high-RPM unloading tail, rich-combustion zero-completion support, and explicit manufacturer recommended versus numerical supported maxima. Old source hashes and standalone evidence remain historical, not silently refreshed.

Mean-cycle refinement is not a crank-angle pressure/compression oracle. Mechanical high-frequency torque ripple, measured vibration/mount response, propeller side-force/P-factor/wake qualification, full propeller data coverage, matched real-engine transients/flow/temperature, flight observations and experienced-pilot trials remain unclosed. The measured native debug-build physics cost exceeds the plan's 500 µs release target. Neither family is certified physically validated or release-qualified by these software checks.
