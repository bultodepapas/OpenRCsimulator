# OpenRC Aircraft Creator

## Final implementation specification

Revision 6 · 7 November 2026 · OPEN RC SIMULATOR

Companion developer pack: [OpenRC_Aircraft_Import_Developer_Pack.zip](https://chatgpt.com/library?file_id=libfile_fde3_f-d7da7cf1aee48191a693f93b4d0d8429_ac5d15b10f548191b3cb750779cf7c10&account_id=personal).

This specification consolidates the integration plan, player journey, follow-up investigations and independent audit into one implementation contract. It is addressed to the lead developer and the aircraft, physics, presentation, storage and UI owners. The intended product is a guided Aircraft Creator: a player imports a model, describes the aircraft, chooses and edits supported equipment and controls, paints it, tests an exact configuration, returns to edit, and saves reusable aircraft and skins.

**Implementation can begin with the contracts and work packages below. Production availability remains conditional on the explicit evidence gates.** No Creator implementation, current-application runtime test, numerical qualification campaign or real-aircraft calibration was completed while preparing this revision. New test cases in this handoff are marked `not_run`. Existing probes retain their original revisions and limitations.

This document is the controlling design. The earlier UI journey and audit remain supporting history. Where this revision changes a proposal, the decision register states the replacement. The developer pack contains the same Markdown source, proposed contracts, module registry, work backlog, acceptance matrix, player guide and historical evidence. These planning files are not installed runtime schemas.

## 1 Product result and delivery boundaries

The player should be able to bring a locally stored STL or an admitted embedded GLB into the existing Workshop, see it immediately after safe admission, confirm orientation and real size, supply the required physical information, and reach a test flight without first publishing a named aircraft. The visual model and the flight model have separate sources of truth. A mesh supplies geometry and, for supported GLB content, materials and separable parts. A complete, evidence-labelled physical definition supplies mass distribution, aerodynamics, propulsion, controls, contact and launch behavior.

The initial complete flight slice is a new estimated conventional electric aircraft with a single tractor installation, three logical control axes, four conventional visual control roles where parts exist, no wheels, and independently qualified Airborne and Hand launch. Its energy model is finite and explicitly selected. The first reference path uses a complete component inventory; guided inverse mass/CG fitting follows that working path. The full first player release also includes Original/solid appearance, local generated paint, compatible PNG/skin import, named skins, saved drafts, published revisions and the edit–test–return loop. A development milestone with only one qualified equipment package is useful; the release must expose only the packages actually qualified, with no decorative motor choices.

Fixed tricycle and taildragger hardware and Runway start follow the first gearless slice. Gasoline and glow packages, symmetric flaps and the bounded elevon family are separate increments. Canard and V-tail need their own physical contracts and qualification. **Imported retractable landing gear is the final capability phase.** Neither an unsupported type card nor a visual animation makes a configuration flyable.

A single versioned `CreatorSupportManifest` drives visible file filters, enabled cards, allowed parameter domains, documentation and test enumeration. Its availability entries are the conjunction of implemented provider, qualified package/combination, matching engine/backend and passed platform release receipt. Compile-time flags alone do not make a feature qualified. Production builds can disable a module while retaining its saved metadata and an actionable explanation.

## 4 Runtime architecture and public service contracts

### 4.1 Trusted boundary

The UI submits data-only authoring intents. Import services capture bounded source bytes and return an `InspectedSource` owner after format/resource admission. A preview-only builder consumes that owner before datum or physics is complete. The compiler separately resolves pinned packages, emits complete aircraft bytes and reconstructs accepted physics through the checked loader. A resolver returns immutable aircraft owners for published sources; a separate compiler entry produces an owner for an unsaved complete candidate. The flight builder consumes that aircraft owner to create a fresh visual instance. Qualification and live startup consume one frozen flight configuration. The session installs one `VehicleModel` into `Simulation`; the common kernel receives no uploaded scripts and gains no aircraft-ID branches. [S02–S05]

`AcceptedAircraft` is a trusted `RefCounted` owner, constructed only by the resolver/compiler factory after validation. GDScript privacy is an ownership convention, so public accessors return defensive copies of primitive arrays, dictionaries and bytes. A deserialized dictionary containing `ok=true` is never an accepted handle. A handle contains no arbitrary user path, callable or script. It owns verified closure references until released. An ordinary imported flight uses a `PublishedOrigin`; an unsaved trial uses a `DraftOrigin`.

| Proposed service | Signature and result | Owner and failure rule |
| --- | --- | --- |
| `CreatorSourceImporter` | `capture_and_inspect(request, reservation) -> SourceInspectionResult` | Returns an immutable `InspectedSource` with captured bytes/hash, counts and safe source-space visual description. No aircraft-physics acceptance is implied. |
| `ImportedDefinition` | `parse_partial(bytes)` and `validate_complete(snapshot, support) -> DefinitionResult` | Partial drafts may be incomplete; complete definitions must satisfy all required fields and relations. |
| `ImportedAircraftCompiler` | `compile_candidate(snapshot: DraftSnapshot, pins: PinnedInputs) -> CandidateResult` | Returns an `AcceptedCandidate` only after exact-byte physical/profile validation and numerical-domain admission. |
| `FixedWingAircraftResolver` | `resolve_published(ref: SourceRef, policy) -> ResolveResult` | Resolves catalog, currently accepted legacy variant or indexed imported revision. Rotorcraft remains on its own route. |
| `AircraftData` extension | `load_bytes_checked(bytes, expected_id, profile_provider) -> DataResult` | Parses and hashes the same captured bytes, validates full v2 and explicitly applies energy/wheel or no-gear dependencies. |
| `UserAircraftBuilder` preview | `build_preview(inspected_source, provisional_visual_state, token) -> PreviewBuildResult` | Isolated source/display-coordinate instance with unresolved physical fields allowed. Camera fit is visual only; it cannot produce a flyable handle. |
| `UserAircraftBuilder` flight | `build_checked(accepted, appearance_snapshot, build_token) -> VisualBuildResult` | Main-thread construction; returns a fresh detached instance with confirmed datum, actual hinges and optional rotor. Frees partial instances on failure. |
| `PaintBindingProvider` | `layout_for(inspected_or_accepted_visual)` and `stage_appearance(layout, appearance_snapshot) -> AppearanceResult` | Accepts the closed Original/published/draft appearance union, verifies exact mapping/layout/content and applies instance-owned materials atomically. |
| `CreatorStore` | `save_draft`, `save_recovery`, `publish_aircraft`, `publish_skin`, `archive`, `import_bundle` | Each takes immutable inputs, operation ID and expected version/digest; all writes use the root lock and index transaction. |
| `ImportedTrial` | `freeze_candidate(accepted, launch_request, environment, input, solver) -> FreezeResult` | Owns exact physical/presentation/dependency closure and a draft or published origin. Does not publish an aircraft. |
| `ImportedStartQualification` | `qualify(frozen_trial, operation_token) -> QualificationResult` | `ok` means assessed; `available` requires the selected start to commit without unauthorized substitution. |
| Root flight bridge | `request_trial(frozen_trial, qualification_receipt, departure_token)` | Compares requested/checked/actual identity, stages visuals and physical start, then honors explicit commit outcome. |
| `CreatorJobScheduler` | `reserve`, `submit`, `invalidate`, `drained`, `release` | Counts aggregate resources across editor, retained flight and jobs; cancellation invalidates adoption before resources are released. |

Use a common result envelope `{ok, value?, diagnostics, operation_id}` for non-flight services. `value` is absent on failure. Diagnostics are `{code, severity, step_id, field_path, message_key, arguments, remedy_id, source_digest?}`. Display strings are localized at the UI boundary. `operation_id` identifies an attempt; it is not proof of acceptance. Successful persistence additionally returns transaction ID, committed index generation, exact record identity and readback status. Qualification additionally returns `available`, requested start, reason code and the exact receipt.

The preview route is `capture_and_inspect` → `InspectedSource` → `build_preview`; it remains available while orientation, datum or physics is incomplete. The flight route is `DraftSnapshot` → `compile_candidate` → `AcceptedCandidate` → `freeze_candidate` → `FrozenTrial` → qualification → root start transaction. `resolve_published` instead produces `ResolvedAircraft`, which supplies the same accepted-aircraft interface. Both flight routes share checked bytes, visual and flight services. The unsaved origin cannot be written into Home preferences or mistaken for a published library entry. The selected appearance is captured independently through `AppearanceSnapshot`, so unsaved paint can be tested without publishing a skin.

## 5 Data contracts and exact identity

### 5.1 Record inventory

Every durable new record has a closed `format` discriminator and versioned writer ID. Unknown required versions fail with an actionable compatibility state. A draft can preserve unsupported selections and raw text for later editing; it cannot bypass complete-definition admission. Nested records use exact schema branches and typed blob references rather than arbitrary dictionaries. Reuse the existing closed aircraft-v2 schema for emitted physics. The contract registry defines required/optional fields and semantic checks; leaf schemas are implemented and reviewed in PR-01 before readers accept external records.

Identifiers are lowercase UUID v4 for user aircraft/drafts/skins, SHA-256 lowercase hex for byte identities, and stable domain IDs for components. The top-level physical ID is `user-aircraft-<uuid>`. Component IDs follow the current v1 lowercase snake_case rule and are unique across the physical groups; do not use display names, array positions or content hashes as component IDs. A reordered or renamed part keeps its ID. Retired IDs are never reused for a different part. [S04]

### 5.2 Serialization policy

The new writer policy is `openrc-json-bytes-v1`. It uses the pinned engine's sorted-key, full-precision JSON output as a chosen encoding, with valid UTF-8, no BOM and one final LF. Structural keys are the closed ASCII identifiers declared by the schema. Valid Unicode string values retain their code points without implicit normalization. All floating values are finite and negative zero is normalized to positive zero for these new records. Domain scalars are float64; count/revision/generation fields use decimal integer tokens in `[0, 9007199254740991]`, with positive lower bounds where required. These fields cannot be fractions, exponent notation or values rounded into range.

Extend the strict token scanner with schema-path integer checks **before** JSON numeric conversion. Existing `StrictJSON` already checks bounded grammar, duplicate decoded keys, Unicode validity and finite numeric conversion, but does not establish this new exact integer-token contract. The older Store integer helper is not sufficient either. The new scanner rejects unknown fields, malformed token spans and ambiguous decoded keys; it preserves current stock parsing semantics through a new entry point. [S06]

Serialize an immutable record once, capture its byte array, compute SHA-256, and parse those same bytes through the checked reader. Retain and export those exact bytes. Hash verification never reserializes a parsed record. Equivalent JSON with different whitespace or numeric spelling may have a different identity. This is intentional and requires no RFC 8785 claim. Upgrading Godot or the writer creates a new writer ID for newly authored records; readers retain old accepted bytes and do not silently rewrite them.

Use domain-labelled structured payloads such as `{format:"openrc-trial-identity v1", ...typed pins...}` rather than concatenating unframed strings. A receipt's own digest is outside its hashed payload, avoiding a self-hash cycle. The requested/checked/actual comparison uses captured exact receipt bytes and validated typed context fields; independently serialized dictionaries are not assumed byte-identical. Dirty-state comparison uses normalized authoring content plus raw buffers and is deliberately separate from storage-byte identity.

Physical raw bytes, accepted derived-model identity, dependency-closure identity, visual/layout identity, skin content and full trial each have separate fields. A paint-only edit reuses exact physical bytes and recompilation evidence where valid, but changes the presentation/full-trial identity and its caches. Replacing geometry can change the source of physical dimensions and must revalidate all affected fields. Existing `data_sha256` includes ID/provenance, and legacy no-gear identity also includes a registry input; do not rename those existing hashes as purely physical semantics. [S03, S07]

### 5.3 Persistent and transient origin rules

`SourceRef` contains published/catalog selection only. A legacy variant initially resolves only the current accepted manifest/backup; a numbered revision file alone is not evidence of publication. Add a proposed `Store.capture_published_exact(id, expected_revision, expected_hash)` that acquires the same per-variant guard used by save/delete/restore, validates the accepted current or backup manifest, captures the exact record and complete dependency bytes, then releases the guard. Existing `load_variant` does not provide this locked exact-byte snapshot. The Creator root lock does not protect the separate legacy store. If both locks are needed, acquire Creator root first, then legacy variant guard, never the reverse. A busy or abandoned legacy guard fails closed; use its existing explicit recovery policy, not lock theft. Alternatively leave the legacy resolver provider unavailable while preserving the old variant route. Historical legacy resolution remains unavailable until that store gains an explicit accepted publication index. Its base, compiler and descriptor pins are immutable; replacing them creates a new variant UUID. [S07]

A new never-saved draft receives a draft UUID immediately and an aircraft UUID before its first complete compilation. `compile_candidate` returns an accepted owner with `DraftOrigin{draft_id, edit_generation, candidate_digest}`. That owner retains all exact bytes required for qualification, startup, restart and return. It does not read the original file-picker path again. Unsaved changes to a published aircraft use the same route with a base published reference for later CAS. Test fly creates no named aircraft revision and changes no Home preference. Saving later may produce a published revision with the same physical bytes, but it does not mutate the already running trial's origin.

## 6 Durable storage and publication protocol

### 6.1 Root and process ownership

Use a dedicated `user://aircraft_creator/` root. Proposed layout: stable `writer.lock`; atomically replaced `current.json` and `previous.json`; immutable hash-addressed `objects/<prefix>/<sha256>`; and bounded `staging/<transaction_uuid>/`. Content kind is checked from the typed reference, not inferred by executing an extension. Never accept an arbitrary record-supplied path. Root resolution rejects symlinks/aliases that cannot be canonicalized safely and unqualified filesystem types.

Add a narrow trusted Creator I/O utility for OS-owned locking, atomic replace, qualified durability primitives and bounded streaming decompression. Its version-pinned zlib dependency and platform builds need licence/toolchain receipts; it is a data utility, not a flight solver. On POSIX use a verified advisory lock primitive such as `flock`; on Windows use a verified equivalent such as `LockFileEx`. The implementation must test actual semantics and packaging on each target. The stable lock file is never renamed, deleted or recreated while the store exists; all writer, recovery, repair and package-import operations honor the lock. The owning process holds it for service lifetime. Process death releases the OS lock. A directory timestamp or PID file is never authority to steal ownership.

Lock results distinguish `acquired`, `busy`, `unsupported` and `error`. A busy secondary process can browse verified immutable published records but cannot edit, save, publish or write recovery. The UI explains that another instance owns editing. An unavailable/unsupported primitive disables Creator writing rather than falling back to an unsafe lock. Stock operation remains on its existing route. Initial support is qualified local desktop filesystems; network shares, cloud synchronization semantics and Web/mobile storage require separate qualification.

Because accepted bytes are immutable and physical deletion is disabled, secondary readers need no reader leases in this initial version. They capture a coherent accepted pointer/index generation, then verify the immutable referenced closure. An inconsistent or corrupt read retries a bounded number of times and then refuses; it never reads unindexed staging. Later physical collection requires reader coordination or exclusive maintenance, a complete retention-root inventory, crash recovery and independent tests before enablement.

### 6.2 Transaction sequence and commit point

Each operation carries an idempotent transaction UUID and expected entity revision/digest, even though one process owns writes. This CAS prevents stale in-process drafts, asynchronous saves and recovery decisions from overwriting a newer snapshot.

1. Under the root writer owner, capture and validate the accepted pointer/index and expected entity versions. Reject a conflict before allocating publication outputs. Reserve exact prospective object, index, backup and recovery space under quota and actual free-space checks.
2. Capture immutable input bytes and closure. Serialize new records once. Verify all pinned existing dependencies and reject missing, changed or unsupported inputs. Build the prospective root index in memory without changing live metadata.
3. Write each new immutable object into same-filesystem transaction staging, flush as qualified, read back, check length/digest and parse/validate the relevant record. Publish content-addressed object files without overwriting an existing different object. Identical existing bytes are reused after verification.
4. Write and read back the immutable new `RootIndex`, including its transaction ID, generation and predecessor pin. At this point every new file is still unaccepted because `current.json` has not changed.
5. Atomically preserve the previous accepted pointer into `previous.json`, then atomically replace `current.json` with the new pointer. The latter replacement is the logical commit point. Use the platform adapter's qualified file and parent-directory persistence sequence; record the durability mode.
6. Read back the accepted pointer and its complete required closure. Return the committed generation and record reference only when verified. The UI acknowledges the captured snapshot, preserving any newer edits as dirty.

Failure before the commit point retains the old accepted index. Staged/orphan objects remain unaccepted and consume bounded space until explicit safe maintenance; a restart never promotes the highest filename or index generation. Failure after commit cannot be reported as an ordinary rollback. If readback outcome is uncertain, keep the editor and all data, stop further writes, resolve the current pointer under the lock and reconcile by transaction ID. If it identifies the new transaction and validates, report success; if the old pointer remains, report uncommitted failure; if neither is trustworthy, enter read-only recovery. Do not blindly retry into a second revision.

On startup, validate current pointer and closure first. If they fail, offer recovery from the previous accepted pointer only after it validates; preserve corrupt and orphan bytes for diagnosis. An empty store is initialized under lock. Never infer validity from a serialized `ok` flag. A process-interruption test demonstrates one guarantee; power-loss durability requires separately qualified flush/directory behavior. Until that evidence passes, state the narrower interrupted-process guarantee.

Aircraft revision publication includes a selected draft appearance as a newly published skin revision and its closure in the same root-index transaction; the resulting aircraft points to Original or a real published skin. Show that current skin/name in the publication summary. `Save skin` can publish it independently; `Save draft` retains the draft `AppearanceSnapshot` and exact pixels without adding a gallery revision. Test fly never publishes either. A successful aircraft publish updates its own accepted entity pointer; it does not silently rewrite a separately named draft record. The live editor may acknowledge the explicit publish snapshot as its baseline while preserving both durable identities.

### 6.3 Archive and storage exhaustion

Archive changes listing metadata; it does not delete physical data or invalidate an old reference. Removing the selected skin requires an explicit alternative selection or Cancel. Published historical revisions, named drafts, recovery primary/backups, live Undo/Redo, staging, retained trials, restart inputs and exports keep their bytes. Initial storage has no automatic eviction, history pruning or garbage collection. Explain that archive will not reclaim disk space.

The development policy caps accepted/staging Creator storage at 4 GiB with a 64 MiB minimum emergency reserve for recovery/index completion. That reserve is not assumed to hold a complete draft closure: source and paint bytes can be larger than the 4 MiB envelope. Before adopting a source/skin change as recoverable, dynamically reserve and persist every new closure blob plus current/previous snapshot, index and staging overhead; reuse verified durable blobs by digest. If the full upper bound does not fit, refuse adoption or explicitly preserve the live edit with `Recovery unavailable for these changes` and Save/export guidance. Never display `Recovered` or `Saved` for an envelope whose referenced bytes are not durable. Reject a new operation before staging if its bound crosses quota or actual disk headroom; retain the last accepted root and live draft. User-visible storage settings may increase the cap after a free-space check; they do not bypass per-file/parser limits. This is an engineering admission policy, not a measured hardware capacity claim. Target qualification may lower it in a new policy revision.

Recovery is coalesced by changed content, with a two-second idle debounce and a thirty-second maximum dirty interval while input remains active, subject to one serialized write per draft. A page/camera-only change does not create a continuous write stream. Identical content does not create another revision. Check quota before each actual write, including immutable index/recovery generations accumulated by this initial append-only policy. Safe cleanup may remove only never-installed private staging owned by a completed/abandoned transaction after checking that no accepted index references it; installed orphan objects and old accepted objects remain protected until a separately qualified collector exists. Exercise repeated autosave and interrupted publication near quota, and show the storage/recovery failure without losing the live document.

### 6.4 Portable import and export

Use a new `.orcaircraft` data-only bundle with an explicit `openrc-aircraft-bundle v1` manifest. Built-in package dependencies may be included with licence/provenance or pinned as explicit required dependencies; a fresh-install portability test must show which closure policy succeeds. No Python, Blender, Godot scene/script or arbitrary path is executed to use a bundle.

Export captures one accepted index generation and copies exact bytes after verification. An unsaved draft must first be saved/published for this published-aircraft export route; a separate draft backup export is a distinct later format. Import first validates archive central/local headers, safe unique entry IDs, declared sizes/offsets/features and a bounded manifest. Then stream each entry into private staging with hard actual per-entry/total output and expansion limits, computing CRC and SHA-256 during decompression. Reject excess, truncated or mismatched actual output before publication; declared sizes are never allocation authority. Reject traversal, absolute paths, symlinks, case-fold aliases, duplicate entries, encryption, nested archives and undeclared content. Use store-generated internal paths only.

### 7.3 Capture and STL parsing

Check file size before full read, then capture one bounded immutable byte buffer and hash it. A changed original path is irrelevant after capture. Parser, source inspection, engine append and persistence consume that same captured identity; never validate a path and then reread it for loading. A file-picker path remains transient local UI information, not a trusted record field.

Harden the pinned MIT STL-IO candidate `62ecf09a6276337eb712dd0fc2b41de2926b4cc2` or implement an equivalently bounded adapter. Preserve its licence if code is reused. Binary detection uses header/count/length consistency, including checked `84 + 50 × count` arithmetic; an ASCII-looking `solid` header alone does not select the parser. The accepted binary subset requires exact facet payload length and treats nonstandard color attributes as unsupported appearance. Never silently interpret competing STL color conventions.

ASCII parsing consumes the complete grammar and input, including `facet normal`, `outer loop`, exactly three `vertex` records, `endloop`, `endfacet`, and the declared `solid`/`endsolid` structure. Accept documented whitespace and exponent syntax with finite coordinates; reject trailing garbage, missing vertices, malformed keywords and overflow. The fixture without a final LF remains a supported complete-file test. Validate all positions and computed bounds; recompute finite normals from winding and flag inconsistent provided normals. Initially reject exact zero-area or nonfinite cross products and triangles that become degenerate/nonfinite after the accepted render conversion; do not silently discard thin triangles using an arbitrary epsilon. Report underflow/precision refusal with re-export guidance. No automatic watertightness or flight-volume inference is promised.

### 7.4 GLB preflight before engine code

Validate magic, version, declared total length, 4-byte alignment, chunk order/type/length and checked offsets. Strictly parse JSON, validate each supported object shape and every index. Accept one contained buffer; reject all buffer/image URIs, data URLs, unsupported required/used extensions and arbitrary extras that would invoke behavior. Initial scope is triangle primitives with supported position/normal/UV/tangent/color attributes and index types, rigid nodes and core metallic/roughness materials. Reject skins, skeletons, animation, morph targets, cameras, lights, compressed mesh/texture extensions and sparse accessors until each has its own adapter. Optional metadata may be discarded only by a documented nonbehavioral rule.

Validate the entire node graph, including unreachable nodes: child/root indices in range, no duplicate child edge, no self-edge or cycles, at most one parent, valid selected-scene roots and all depth/count limits. Use an iterative bounded traversal so preflight itself cannot overflow the call stack. Validate finite matrix/TRS, normalized nonzero quaternion, nonzero admitted scales and no unsupported shear. Require `matrix` or TRS, never both. Normalize accepted rigid transforms once; first release refuses reflected/negative-scale or otherwise unsupported transforms with “Apply transforms and re-export,” rather than trusting renderer-dependent winding. The earlier negative-scale probe remains evidence of what the engine retained, not a reason to advertise it.

Check bufferView/accessor byte ranges with overflow-safe offset/stride/count calculations, valid component alignment, min/max consistency where required, index bounds and finite vertex/normal/UV data. Validate all referenced resources before decode. Each embedded image must be PNG by declared MIME **and** signature; reject mismatch without fallback sniffing. Factor and extend the stock PNG precheck: bounded IHDR, legal depth/color/compression/filter/interlace, bounded chunks, one coherent stream, required data/end structure, CRC verification, no trailing bytes and rejection of independently expandable `iCCP`, `zTXt`, `iTXt` metadata. Initial allowed chunks are IHDR, PLTE, tRNS, IDAT, IEND and bounded sRGB/gAMA/cHRM/pHYs; reject other chunks with re-export guidance. Existing PNG checks provide reusable policy, not proof that every new check already exists. [S08]

Before the engine decoder, the trusted bounded inflater streams concatenated IDAT through a fixed 64 KiB scratch buffer and enforces the exact decompressed scanline byte count derived from IHDR, bit depth/color channels and all nonempty Adam7 passes if interlaced. Check filter-byte range, stream end and integrity; reject excess, truncated or extra compressed stream data. This bounds malformed IDAT expansion as well as declared image dimensions. The API accepts a hard output limit and stops at the first excess byte; it never allocates from an untrusted declared expanded size. Count actual output and temporary copies in the aggregate reservation. The same bounded streaming primitive supports ZIP deflate with per-entry and total limits. Each target build must pass adversarial expansion tests before decoding is enabled.

Only then call `GLTFDocument.append_from_buffer` with that exact captured byte array, a fresh `GLTFState`, explicit empty base path and the trusted extension registry. Empty base path is not an access-control mechanism; rejecting all URI-backed input is the protection. Both append and scene generation remain on the main thread initially because append may create image textures. Reject any unexpected generated node class, script, animation behavior or unsupported resource before attaching the scene. On return, retain the private result, yield to process queued cancel/close/replacement input, then generation-check before adoption. A blocked event loop cannot acknowledge cancellation mid-call. Retain raw-engine cycle fixtures only for disposable externally timed engine experiments; ordinary app tests must prove preflight rejects them without invoking the loader. [E01, E02, H02]

### 9.2 Authoring contract and deterministic compilation

Source anchors: [S02–S06, S07].

### 9.4 Reference package inventory and mass properties

Source anchors: [S29, S31].

Create a **new** source-reviewed conventional trainer reference package, including a bounded geometry and hardware domain, complete aero/stall/control evidence, complete motor/propeller/ESC/battery package, mass-component definitions and known limitations. Review licences and applicability; pin bytes and label borrowed or estimated coefficients and tables. `synthetic_stik_electric_4s.json` is a useful conventional software fixture only: it retains glow-donor mass stations and virtual balance and its own description disclaims real-aircraft validation. `turbo_lumber_evolution.json` illustrates inventory shape but also uses estimates; neither becomes a universal donor or a measured preset. The package owner must provide defensible values and qualification evidence before enabling a user-facing preset; absence leaves it unavailable.

Start with explicit complete component inventory, including airframe, motor, propeller/rotor, ESC, pack, servos, mounts and actual accessories. Each item has stable ID, positive mass, LE position, dimensions and source, with fuel/battery identity where required. Resolve packaged hardware once; do not add an installed motor or battery on top of donor masses. Compute `M=Σmᵢ`, `C=Σ(mᵢpᵢ)/M`, and the full symmetric tensor about C from each box's centroid inertia plus `mᵢ[(rᵢ·rᵢ)I − rᵢrᵢᵀ]` in FRD. Store `[Jxx,Jyy,Jzz,Jxy,Jxz,Jyz]` as matrix entries; off-diagonals are negative products, not unnegated source products. Reject nonfinite intermediates, nonpositive mass, singular/nonpositive tensor and a plan-CG mismatch, then enforce `1 − J_rot(aᵀJ⁻¹a) > 0` for a valid locked carrier. A three-axis inertia comparator is plausibility evidence, not an inertia measurement; require usable positive reference entries rather than relying on a zero divisor.

A later quick-fit may solve only positive, bounded estimated airframe residual masses or authorized movable parts at declared stations, holding actual hardware fixed. Solve total mass and three first moments under those bounds; report the achievable CG interval or conflict when infeasible. Never move measured hardware, invent balancing mass or overwrite computed CG. Show estimated inertia and sensitivity. Implement this only after the independently tested explicit-inventory compiler; a mass scalar alone is not an aircraft model.

### 9.5 Aerodynamics and physical controls

Source anchors: [S03, S18, S19].

Reference geometry is an equivalent rectangular or tapered planform; emit `S`, span `b`, reference chord `S/b` and an ARP, plus root/tip chords for taper. Enforce the ordinary loader bounds and its 1% area relations in addition to a **narrower package-qualified** domain. For tail, assign area, LE position, lift slope, control effectiveness and incidence with provenance. Retain all required global coefficient, damping, drag, control, stall-envelope and surface parameters from the selected compatible package; author the package with a clear transformation and applicability rule for every permitted physical edit. A mesh is not an aerodynamic wind-tunnel solver. The current law uses a global coefficient oracle plus six equal-area local wing strips and surface approximations; `reference_coefficients.CLadot` is historical evidence, not a newly simulated alpha-dot law.

Regenerate fin-coupled fields whenever `S`, `b`, the ARP or vertical-tail geometry changes. With `B=fin.lift_slope*fin.area/S`, `dx=fin.x−ARP.x`, `dz=fin.z−ARP.z`, and `cy=B*fin.control_effectiveness`, emit `CYdr=cy`, `Cndr=−cy*dx/b`, `Cldr=cy*dz/b`, `Cnb=B*dx/b+body_cn_beta`. When those optional terms exist, also emit `Clb=−B*dz/b+wing_body_cl_beta` and `CYb=−B+body_cy_beta`. The loader requires a positive aft arm and agreement within `1e−8`; label the generated values derived, not independently measured. Recompute other package-coupled terms only under the package's documented model or reject the edit. The derived wing section-slope solve must be finite and feasible in `[0.1,50] 1/rad`; the current stall envelopes require realizable extrema, ordered blend limits outside the ±8° oracle and completion by 90°. Internal consistency does not validate flight handling.

`ControlSurfaces.surface_deflections_deg` is the source of truth for conventional signs: positive roll raises the right aileron, the left moves oppositely, and optional down-going throw cannot exceed up-going throw. `deflections_from_surfaces` supplies aerodynamic signs; the renderer consumes the accepted actual servo state via `FlightSession.surface_angles_deg` and the manifest/hinge mapping. One logical elevator may drive two visual hinges; static/no-hinge visuals must be explicitly identified as such. A preview must never suggest physical movement for an unbound hinge, and a rendered reversed hinge cannot silently reverse flight forces. The three physical logical states remain roll, pitch and yaw; four visual surfaces do not create independent servo hardware. Device rates/expo reshape pilot input; they are distinct from physical endpoint and actuator response, and calibrated radio behavior must be described according to its existing input path. The existing optional out-of-trim rigging offset acts on aerodynamics only; identify it separately rather than claiming that it is rendered servo travel.

The field `servo_full_throw_time` means the common neutral-to-maximum normalized travel time, 0.01–2 s in the current parser. Each tick `rate=1/time` and `actual += clamp(target−actual, −rate*dt, rate*dt)`; a full-negative to full-positive command takes approximately `2*time`, sampled to within a tick. The same normalized rate yields different degrees/second for different endpoint throws. A manufacturer's seconds per 60° is contextual evidence until an explicit, verified linkage conversion exists. Independent surface rates, nonlinear linkages, torque/hinge-load dynamics and elevon servo saturation beyond the current mixer need separate capabilities.

### 9.6 Power package installation and starts

Source anchors: [S20–S22, S28, S38, S39].

Expose a named, compatible power package selector, not arbitrary Ct/Cp curves or an unexplained power scalar. Each package specifies motor Kv, **winding-equivalent** resistance, no-load current and voltage/RPM/temperature context; ideal-motoring identity ESC and relevant LVC; propeller diameter, positive rotor inertia and source-labelled Ct/Cp tables versus advance ratio; installation axis/geometry; and finite battery data with matching installed mass. Tables have at least two finite rows, first advance ratio zero, strictly increasing abscissae and positive static Ct/Cp; enforce the existing bounds and package-specific operating limits. Actual shaft power, input current, RPM and thrust depend on the computed operating point, air density and inflow; a rated-watts label is not thrust. Do not imply reverse, regeneration, multi-motor, arbitrary power-free or unsupported propwash behavior.

Treat the physical hub LE point as the source of truth. A CG-only edit keeps the fixed hub and ARP in LE coordinates and recomputes the authored LE-ordered `thrust_line_offset = hub_LE − reference_inventory_CG_LE`; the runtime performs its own LE-to-FRD conversion. Moving the motor/propeller changes their declared inventory locations, CG, full inertia, hub and force arm, axis/angles, visual location and swept-disc clearance. Shaft angles currently accept the parser's bounded down/right values; do not double-subtract CG. For a later admitted combustion package with optional slipstream, hub translation also regenerates its separate LE wake hub and revalidates shaft/coverage; stationary tail roots stay fixed. A CG-only rebase preserves wake hub and tail roots. Reject inconsistent duplicated hubs or defer wake-bearing movable installations.

`fixed_voltage` is an infinite ideal bus. `ocv_resistance` is a finite source requiring complete capacity, resistance, auxiliary current, initial SOC and valid monotone OCV/SOC table. `pack_ecm` additionally requires exact bundled pack/cell hashes, mount inventory ID and matching mass, allowed chemistry/energy source, initial weak-cell/thermal state and LVC configuration. Bind the selected branch to the imported trial; do not let the stock Workshop ideal-mode default silently replace it. A changed pack capacity or cell count requires new bytes and identity. User pack sources need a bounded verified resolver or remain unavailable.

Propose an immutable `InitialElectricContext` carrying the actual battery kind, exact normalized initial charge/SOC, pack block including temperature and weak-cell/RC state where applicable, ESC/LVC/controller state, local atmosphere, and the law/version identities needed by the selected model. Construct it from the frozen model and **actual start position/environment** before solving. Extend `Propulsion.steady_operating_point` through a new versioned entry point accepting this block; keep its old 288.15 K stock wrapper unchanged. Thread the same context through `Trim.solve`, `CruiseTrim.solve_level_at_throttle`, `LaunchTrimCache` exact key and detached worker arguments, qualification, startup and reset; preserve old APIs as wrappers with historical behavior. Invalidate cache hits and staged adoption when any effective context changes. Current SOC already participates in the model; the demonstrated source mismatch concerns pack temperature and other accepted state/controller context, not a claim that SOC is always ignored.

For **airborne**, install normalized field/weather and selected energy first, solve trim against that context, then initialize the same block, ESC state, throttle, servo and RPM; verify residuals rather than assuming equilibrium. For **hand launch**, a new versioned per-aircraft profile supplies evidence-bearing release height, ground speed, body pitch, velocity trajectory, throttle and one of the currently supported runway-axis directions. Confirm terrain, clearance and model suitability; a gearless predicate by itself is insufficient. Form body attitude and ground velocity independently, sample local wind and atmosphere at the actual release point for every weather type, compute hub-relative air velocity, and solve the selected shaft against the same initial electric context. If no supported positive-RPM root exists, refuse with a reason; stopped/coasting initialization requires its own law. Retain the current stock hand wrapper and historical law identity; do not silently rewrite its ordinary-wind behavior. Its existing 1.9 m release height, 6.5 m/s speed, 5° climb and full-throttle constants are historical implementation values, not a qualified generic launch profile.

For the later **runway** start, first obtain a prerequisite airborne trim using the same accepted context, then prepare the runway-specific zero-throttle, stopped electric shaft and contact/stiction equilibrium using the actual field and weather. Do not use airborne RPM as the runway initial RPM. Gearless aircraft do not promise benign belly landings under terminal-hull policy; a different intended-hull support requires its own admitted module and tests. Each choice is independently evaluated: a valid airborne trim does not guarantee safe hand launch or a runway start. Qualification must confirm the requested start committed at tick zero and is ready without an observer fault; unavailable starts never silently substitute another choice. That scratch-session commit does not publish a live trial.

### 9.7 Fixed gear and capability progression

Source anchors: [S27, S28, S30].

A later fixed-gear record requires at least three unique named contacts with correct tricycle/taildragger placement relative to the **derived** CG, valid support polygon/load, spring/damping/travel and steering, tire friction and stiction, visual wheel-bottom alignment, rotor/ground clearance and an explicit selected wheel profile. Pin both the selected profile hash and exact registry-byte hash; they are different identities. The existing `WheelProfiles.apply_selected_profile` takes a path, so custom sources need a proposed bounded provider rather than invented API support. Check each profile/contact correspondence, spin relaxation, effective wheel mass, reserve travel and existing timestep bounds. `coupled_thin_ring_compliance_v1` is currently launch-unavailable. Braking exists for properly admitted fixed hardware; it is neither automatic nor a promise of differential brakes. Correct any stale trace text as part of that feature while preserving actual observed input/telemetry.

Fuel adds explicitly distinguished gasoline versus glow packages, installed engine/tank/fuel inventory, finite-flow and live mass/CG/inertia, start-fill, energy identity and compatible trim; existing legacy internal naming is not a player fuel label. Simulated flaps require the complete symmetric aero, actuation, visual, mix, speed-warning and lifecycle module, not an isolated switch. Elevons require the existing tailless family, exact clipping/mixing, supported sweep/coverage and the required equivalent fin; this does not establish a finless wing. Canard and V-tail/ruddervator require new registered physical surface interactions, mixer and saturation, trim/stall assumptions, rendering and evidence. Do not compile them as conventional from a silhouette. Retraction comes last: supported fixed-gear profile and contact foundations first, then time/drag, 2–513 uniformly sampled LE contact positions per support, down-end consistency, supported visual rig, weight-on-wheels interlock, intermediate contact approximation, replay/reset and clearance; do not promise unmodeled doors, loads or failures.

### 9.8 Numerical identity and evidence gates

Source anchors: [S01, S14, S21, S36].

The loader's legal range establishes **input and physics consistency**, not stable integration or realism. Check finiteness after every computation, including coordinates, moments, inverse inertia, divisions, interpolation, roots and predicted states. Refuse overflow, invalid dimensions, duplicate/unknown fields and IDs, unsupported modules, broken relations, nonpositive denominators, unstable roots and stale dependencies. Never turn invalid data into readiness by clamping or guessing. Enforce the central versioned finite development ceilings before allocation and throughout parsing and compilation, including the 2 MiB definition/compiled-record limit, 256 inventory entries and 128 hull points. These ceilings are admission controls, not measured platform qualification; preserve the separate platform gates and keep failures diagnosable.

`FlightSession._electric_step_supported` currently enforces a 0.25 source-feedback ratio; it does **not** bound every coupled propeller/aero mode. For each advertised package, transform, start, production tick and effective backend, a numerical owner must pre-register interior, edge and adverse combined cases, initial states, same-duration control/throttle transients, metrics and tolerances **before** measurement. Compare production step with successively finer steps on the same inputs; inspect force/moment, position/attitude/rate, rotor speed, current, charge/energy and failure status, including a deliberately stiff table/inertia candidate that passes the old source-only guard. Establish a defensible conservative analytic/runtime bound or restrict the domain to independently justified qualified cells/combinations; a few endpoints do not prove a continuous nonlinear volume. Pass only when refinement converges within predeclared, reviewed tolerances and the runtime rejects outside the accepted domain; otherwise narrow the domain or keep the package unavailable. Numerical tolerances and any calibrated coefficients must be justified and preregistered by their owners; the central finite development ceilings and product latency targets remain explicit engineering policies, not measured performance evidence. This is numerical verification, separate from physical validation.

For initial imported M2/M3 flights explicitly request and pin the effective `gdscript_reference` implementation at 240 Hz; do not inherit catalog native qualification or silently fall back to another backend. A native imported path is a separately qualified domain/backend extension. Stock keeps its existing native-request/fallback policy.

Freeze a versioned qualification receipt containing source/compiled/dependency identities; production `dt`; requested and **effective** backend plus implementation identity; shaft integrator; physics/energy/control/launch law versions; normalized field, full effective weather/atmosphere; input/servo policy; initial energy and controller state; start profile and choice. Configure qualification, candidate launch and restart from the same receipt. `FlightSession.setup` currently performs an internal reset: select the frozen configuration before setup and compare effective identities before root publication; if a pre-reset check is necessary, explicitly factor a deferred-setup seam. Dispose a mismatched private candidate while recording any reset it actually committed. Any later permitted backend fallback must be visible and freshly qualified before launch. Current `WorkshopStartQualification` creates a reference-default session while `Main` requests native; nominally similar starts therefore do not prove equivalent configurations.

Track two separate outcomes: `physical_reset_committed` records the existing FlightSession reset receipt, including a disposable qualifier or private candidate; `root_trial_published` records the later change of active root ownership. A rejected reset has `physical_reset_committed=false`. Before root publication, any fault or context mismatch disposes the private candidate and preserves the old root/editor; if its reset committed, record that fact and never call it rolled back. A successful qualification scratch reset does not publish the trial. After root publication, or on an active-session restart, `committed=true, ready=false, status=observer_fault` means the new accepted physical state remains paused. Never commit twice or claim rollback. Initial fault UI offers diagnostics and guarded Return only, with no repair Retry.

Reset rebuilds the chosen start from its frozen context through the existing prepare/commit transaction. Checkpoints must verify model, full layout, timestep, backend/law, environment and auxiliary state; new state needs versioned save/restore and refusal coverage. Restoring a checkpoint is paused recorded-input replay, not a complete live-session save; legacy missing launch provenance stays unknown. Preserve stock exact replay under its old identity; any intentional law change needs a new identifier and baseline. Flight-log comparisons use the same complete input tape, config and source; inspect `complete` and `solver_changed`, and do not claim cross-platform byte identity without evidence. Successful software replay or refinement does not establish aircraft realism.

### 10.3 Eight canonical steps

Unless a saved draft or an explicitly applied qualified package supplies a value, required values start **unresolved**: no numeric zero, assumed unit, hidden physical default or invented range. Each exact field shows unit, domain from the current schema/package, provenance `Manual`, `Measured`, `Borrowed`, `Estimated` or `Calculated` (derived), an inline message and a link to help. Sliders are offered only with a meaningful finite domain and pair with exact entry. Enter or focus loss commits valid input; invalid text remains visible and does not replace the last accepted value. Review can navigate directly to every issue. Controls below describe target behavior; packages and dimensions are enabled only once the related owner qualifies them.

1. **`import` — Import.** Show Choose model…, Open draft…, accepted-format help, and an empty model outline with “Choose a model to see it here.” Initial format targets are qualified binary/ASCII STL and bounded embedded GLB; picker filters list only admitted formats. On selection show filename, `Inspecting model…`, indeterminate progress and Cancel import. On admission say `Model imported`; failure identifies the file, reason and remedy. Replacement inspects a candidate without touching the current source; `Replace model?` enumerates actual affected source mapping, fields, moving-part/paint bindings and selection. Confirm only if its source and draft generations still match. Cancel/refusal preserves source, buffers, skin, history and preview. Confirm is one history command covering those domains; undo requires all old retained assets or fails atomically with Review missing file. Strict image/graph admission belongs to the import service, and UI must not claim a synchronous, non-interruptible loader can cancel mid-call.

2. **`orient_size` — Orient and size.** Controls: nose axis and up axis selectors; Model units selector (initially `Choose units`); known wingspan exact value in m or chosen length unit; visual marker and numeric source-space x/y/z coordinates for the wing-leading-edge centerline datum; front/side/top and Confirm orientation. Pick or type a datum and label its evidence. No origin or bounding-box center is assumed. Confirm only finite, nondegenerate, nonconflicting axes, known units, positive span and an explicit datum, under the import/authoring owner’s actual bounds. Apply `p_structural = scale × rotation × (p_source − datum_source)` once to source vertices and source-derived landmarks; manually entered structural-frame SI points or dimensions are not transformed again. Unit interpretation of the imported source is separate from deliberately resizing the physical aircraft. Datum or transform changes invalidate affected bindings and start checks. Without a model show `Import a model first` and Go to Import; retain invalid text and show its unit and remedy.

3. **`aircraft_layout` — Aircraft layout.** Show Conventional, Flying wing, Canard and V-tail cards with text explanations. Conventional becomes enabled only with its admitted compiler; other cards remain `Not available yet` until separately qualified. Inputs include wingspan, length, root/tip or governing chord and wing area, tail position/area and other preset-required dimensions, in m and m², with declared reference axes. An explicit compatible, versioned **Use starting values** preview lists all fields it will change and applies as one undo command; it cannot fabricate a measurement. Where a dimension is independently adjusted, show the dependent relation and what stays fixed; display physical dimension overlays. If the physical dimensions do not reshape the visual, say `Flight dimensions differ from the visual model`. Impossible geometry or missing aerodynamic assumptions link to the relevant field; a picture alone never supplies coefficients.

4. **`weight_balance` — Weight and balance.** Inputs: ready-to-fly mass in kg; requested balance position in m in the structural frame; component inventory mass in kg and x/y/z positions in m; supported battery/fuel initial state. Show estimated or measured provenance and calculated total mass, derived CG and inertia with distinct target and actual markers. Show components expands the inventory; Calculate balance may vary only explicitly estimated free values and reports residual and feasible limits. Missing/inconsistent mass, an infeasible target or unqualified inertia blocks compilation; never move measured equipment, overwrite derived CG or invent ballast. Installed real hardware retains declared mass/dimensions during any airframe resize unless replaced.

5. **`power_mount` — Power and mount.** Electric, Gasoline and Glow cards start unavailable until a corresponding complete, versioned motor/engine, propeller, controller, energy source and installation package is admitted. First flight enables a qualified electric package; fuel choices explain their later gates. Choose package shows identity, source/estimate, limits, installed masses and every changed dependent input before Apply. Edit mount provides x/y/z in m, thrust angles in degrees and a preview axis/clearance overlay using the package's actual bounded domain. Expose initial charge and temperature only as supported by the selected pack, with units, field atmosphere and initial controller state; the exact accepted state goes to qualification/start/reset. A change invalidates mass/CG, clearance and starts. No descriptive `watts` slider substitutes for an operative torque/propeller/energy model. Combustion hub/wake effects remain gated to the supported law.

6. **`controls_ground` — Controls and ground.** For conventional layout show aileron, elevator and rudder direction and physical travel in degrees, direction check, bound hinge mapping and Show movement. Existing conventional data requires positive throws in the admitted 1–60° range; direction reversal needs an explicit physical/input/visual sign contract, not a negative maximum. Separate physical throw, device-dependent rate/expo and common **Neutral to full command time**, in seconds; the existing common time is 0.01–2.0 s, and a full negative-to-positive travel nominally takes twice as long before step rounding ([aircraft_data.gd](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/physics/aircraft_data.gd), control validation; [control_actuators.gd](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/physics/control_actuators.gd)). A fused STL says `Controls simulated · visual is static`; show movement is enabled only for actual bindings and never moves the whole aircraft as a fake surface. Configure flaps opens an incomplete module draft only when supported; Apply changes capability only after its full module validates. Ground initially selects No gear; fixed tricycle/taildragger remain disabled until their contact, profile and start gates, and retracts are the last wave. Disabled controls explain what is missing.

7. **`paint_skins` — Paint and skins.** The selected appearance is a closed Original/published/draft AppearanceSnapshot; an unsaved skin carries a UUID, edit generation and exact layout/group/pixel bytes without a published revision. Test fly freezes those pixels without adding a gallery revision. The gallery starts with read-only **Original**, then saved named skins, unsaved preview and Add skin. Offer Generate paint, Upload image…, Import skin…, Duplicate, Rename, Save skin, Select, Restore Original, Export template… and Hide/archive only when their providers and current state allow them. Generated local patterns use a versioned algorithm, parameters and repeatable variation seed. A PNG is checked for admitted bytes/resource limits and explicitly assigned to a paint group; its mere validity does not prove atlas alignment. Let the player inspect top, both sides and underside. A layout pin hashes the source, verified source-index-to-runtime node/primitive/slot mapping, UV set and transform, sampler and projection algorithm/parameters; names are labels. Multiple groups support partial PNG replacement without changing other groups. Preserve sRGB/linear, alpha, culling and nonpaint PBR properties; stage material updates atomically. Show atlas seams and overlap. A versioned package binds exact model/layout/paint-group identities, lists safe entry IDs, sizes and full digests, and rejects scripts, unsafe paths and external URIs. Preserve stock `.orskin` semantics separately. A plain STL is neutral/solid until a qualified mapping exists. Missing UV or incompatible layouts show Use Original, Create mapping if available, or Choose another skin; selecting an alternative is explicit.

   A duplicate creates an **unsaved** skin draft with a new UUID, suggested name and unchanged original; Cancel saves nothing. Duplicate labels may match but rows show revision and short ID. A rename of a saved skin creates metadata revision without changing pixels or old pins. Original cannot be renamed or removed. Archive selected skin only after Choose another skin or Cancel; restoring an archived entry makes it selectable. Archive changes listing metadata and does not reclaim disk space. Initially there is no physical garbage collection, automatic eviction or stored-revision history pruning: published revisions, drafts, recovery, history, staging, trials/restarts and exports retain their bytes. Quota exhaustion blocks new staging with a remedy; future collection requires a separately qualified reader-coordination and retention protocol. Never silently replace a missing pinned appearance. Physics-only replay and optional visual-replay retention use their own explicit contracts.

8. **`review_test` — Review and test.** Summarize source, layout/dimensions, mass/CG, power, controls/gear, appearance, provenance and issue links; show Unknown for unsupported metrics. Display field and full effective weather, and Airborne, Hand launch, Runway cards. Airborne is visibly selected for a new candidate, but starts as `Not checked`; the selected start remains selected on refusal. Hand launch becomes available for the first qualified gearless profile; runway waits for qualified fixed gear. Show `Not checked`, `Checking start…`, `Start unavailable: reason` or `Ready for this trial`. Check start freezes/checks without flying; Test fly can perform the same check then launch only on success. Cancel check immediately invalidates its launch intent. A condition or appearance edit during the check requires a fresh action. Save aircraft validates and publishes a named aircraft revision independently of whether its selected start qualified; Save draft preserves incomplete work. Test fly may use an unsaved, complete candidate; it never publishes, creates a named revision or changes Home preferences. Estimates are disclosed, not a realism or safety score.

### 10.4 Document history and persistence state machines

The authoring controller owns one mutable logical document and publishes immutable `CreatorViewState` copies with `{draft_id, aircraft_id?, base_published_source_ref?, document_revision, step_id, accepted_fields, field_buffers, issues, appearance_snapshot, preview_state, readiness_by_start, save_state, recovery_state, operation_generations}`. A persistent `SourceRef` always denotes a published or catalog selection; it never stands in for an unsaved candidate. Allocate `draft_id` before a model, name or aircraft identity exists. Once established, an aircraft may own multiple independently named drafts, each pinned to its base revision and own recovery namespace. Save draft as copy allocates a new draft ID for the same aircraft; Save aircraft as copy creates a distinct aircraft ID. Allocate the aircraft UUID before first complete compilation. Display names are never keys.

Each field retains `{raw_text, unit_at_entry, locale_at_entry, edit_start_raw, parse_status, accepted_SI, provenance}`. Parse the entire string according to that captured locale and unit; reject empty, nonfinite, overflow, ambiguous or out-of-range values, with no `to_float`-style partial parse. A locale or unit display change converts from the accepted SI quantity, never reinterprets an unresolved buffer. For an active invalid buffer, keep its captured unit/locale and ask the player to correct, cancel, or explicitly discard it before converting that field. Do not round-trip an accepted value through its shortened display text. A valid equivalent entry normalizes on commit. Saving an unchanged invalid buffer may yield a clean draft that still blocks publication/flight. Escape restores the edit-start buffer, including an already-invalid value. A changed buffer immediately invalidates dependent readiness.

A discrete edit is one command with before/after source, mapping, physical, visual, buffer and dependency references. A drag captures once at gesture start; preview cheap feedback and invalidate readiness on the first actual change, then commit once and debounce expensive compilation/checking. A no-op drag preserves Redo; cancel restores the before snapshot. History owns retained assets until eviction; undo/redo restores the whole command or refuses atomically on missing dependencies, then increments revision and invalidates downstream results. Undo need not persist across app restarts. Existing Workshop history has a limit of 32 and snapshots recipe/presentation; Creator needs a separately specified bounded command/asset budget and cannot pretend the stock snapshots cover new domains ([workshop.gd](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/ui/workshop.gd), `_history_snapshot`, `_restore_history`).

| Event | Required transition and failure behavior |
| --- | --- |
| New/open | Create provisional identity or load a named snapshot, raw buffers, source pins, step and camera; unresolved/missing dependencies remain explicit. Opening a published aircraft creates a new editable draft at Review, based on its immutable revision. |
| Save draft | Capture immutable content + raw buffers and UI state; name on first explicit save. Under the process-owned root lock, use expected version/digest, stage and verify objects, then publish the root index and read back. Precommit disk, quota or CAS failure preserves the previous accepted index and live draft. A postcommit uncertain readback stops further writes and reconciles by transaction ID; do not blindly retry or claim rollback. |
| Publish aircraft | Commit valid pending fields; compile and validate source/physics/appearance; publish an immutable revision under the root index with expected base revision. Precommit failure preserves the prior accepted revision; uncertain postcommit readback reconciles by transaction ID without duplicate publication. Stale base offers Save aircraft as copy, Reload saved aircraft with dirty guard, or Cancel. A separately saved draft is not overwritten; start readiness is independent. |
| Recovery | A separate versioned, bounded data-only per-draft snapshot stores partial content, buffers, referenced assets and editor state. Compare expected digest (`missing` or exact digest) and writer/session identity while the process owns the qualified OS root lock; CAS still rejects stale snapshots within that process. Recovery is emergency data, never named save or publication. Restore/Later/Discard are explicit; Later preserves bytes and pauses unsafe overwrite. A busy, unsupported or uncertain lock makes Creator read-only; never steal it by age or PID. Stock recovery/backup are separate. |
| Dirty exit | Back to Workshop, switching draft and quitting offer Save draft and leave, Discard changes, Keep editing; focus Keep editing initially. Save failure keeps the dialog. Discard authorizes this departure only and cannot delete a saved revision, another draft, trial or unrelated recovery. |

Keep `last_explicit_baseline` as the exact normalized content **and raw buffers** acknowledged by the most recent explicit save in this editing session, with separate durable named-draft and published-revision identities. Dirty compares current content against that baseline; step, camera, focus and scroll do not dirty it. On save start capture the logical snapshot, expected storage version and monotonic operation ID; serialize each immutable record once with versioned `openrc-json-bytes-v1` and hash those exact captured UTF-8 bytes. Dirty comparison of normalized content plus raw buffers is independent of byte identity; no canonical cross-producer equality is claimed. Then on successful durable readback acknowledge exactly that snapshot, not whatever happens to be in the editor at completion. If the user edited meanwhile, the newer content stays dirty. Serialize writes to the same destination and ignore stale UI callbacks, but do not erase or deny an authorized durable save merely because its initiating view disappeared. Undo to the acknowledged baseline clears dirty. Recovery never updates the explicit baseline. Root-owned departure must wait for a requested save outcome before deciding whether to leave. If content changes after the captured save, the departure must re-guard the newer state or keep editing; an older successful snapshot cannot authorize losing newer edits.

### 10.5 Asynchrony trial and departure

Every import, preview, skin decode/generation, thumbnail, compile, save and check has an owner token `{host_instance, draft_id, operation_kind, operation_generation, captured_document_revision, relevant_source/layout/skin/start identities}`. Apply a completion only if the owner is alive and active, its token is current and all relevant identities match. New edits, undo, replacement, changed selection, dialog cancel and trial freeze invalidate affected generations; camera/step movement alone does not invalidate a physical candidate. Canceled work may continue to drain: immediately suppress publication but hold its aggregate reservation for geometry, decoded images, mipmaps, preview/old flight, staging, workers and measurable GPU allocation until actual release. Queue or refuse when insufficient, showing `Waiting for resources` or an actionable remedy. Only qualified thread-safe data work runs on workers; scene-tree and presentation ownership remain on the main thread. In particular, qualify the pinned engine’s embedded-image processing at GLB append, not only at scene attachment.

| Trial state | Event and guard | Commit-aware result |
| --- | --- | --- |
| Editing → checking | Commit valid fields; `DraftSnapshot → compile_candidate → AcceptedCandidate → freeze_candidate → FrozenTrial`; capture request ID and exact conditions. | Disable launch; cancellation or any relevant change returns to editing and invalidates launch intent. No `SourceRef` or saved revision is fabricated. |
| Checking → ready/refused | Receipt contains assessed identity and whether the requested start committed in the disposable qualifier. | Qualification never publishes a live trial. Refusal preserves selection, root world and editor; `ok` alone is not `available`. |
| Ready → starting | Require requested = checked identity and current source/dependencies; build a private candidate while the previous root flight/editor remain retained. Track `physical_reset_committed` separately from `root_trial_published`. | A fault, cancellation or identity mismatch before root publication disposes the candidate and preserves the previous root and editor. If the private physical reset committed, record that fact; do not claim it rolled back. |
| Starting → trial or paused fault | Compare actual effective identity and selected start with the receipt before root publishes the trial. | Successful `root_trial_published` switches visible ownership once. A later observer/presentation fault leaves the accepted trial paused, with diagnostics and guarded Return to Workshop. No observer-repair Retry is offered initially. A disallowed mismatch refuses; an allowed fallback must be disclosed and requalified before publication. |
| Trial → restart | Root first resolves current recording generation and submits the same frozen receipt. | On an active session, a rejected physical reset preserves the previous state; if the reset commits and an observer faults, retain the accepted new state paused. Show diagnostics and guarded Return; do not offer observer-repair Retry or repeat the reset implicitly. |
| Trial → return | Root resolves trial recording, then tears down trial and restores retained host and prior world. | Same live step, buffers, undo/redo, scroll, focus and camera; old flight remains paused. Next edit invalidates affected checks. |

The frozen identity includes exact source/model and compiled physical inputs, appearance revision/layout/content, all dependency pins, selected launch and release profile, field, full normalized weather **and atmosphere**, supported input setup, initial pack/controller context, production fixed timestep, requested and effective backend/implementation, integrator and law versions. A preset name alone is insufficient. Qualification, actual startup and restart must match that frozen identity; a successful tick-zero start or schema pass does not prove numerically stable flight or physical realism. Existing `trial.gd` freezes stock-style data, and `main.gd` builds a Workshop trial with stock default livery before applying its profile; imported appearance needs explicit end-to-end propagation ([trial.gd](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/workshop/trial.gd), `freeze`; [main.gd](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/main.gd), `livery`).

For Return and Restart reuse root `_begin_exit_request`; for Quit include both trial and retained-flight recorders plus applicable ground recorder. Root owns request generation, session holds, input suppression, modal ownership and focus from draft decision through recording, statistics and terminal commit, including frame gaps. A window-manager close first dismisses the active exclusive modal; a later close initiates quit. Dirty Discard sets an authorization scoped to this request; after all trace/statistics decisions succeed, clear only that draft’s matching recovery index reference using expected-digest CAS at **terminal commit**. Physical bytes are not garbage-collected initially. Trace Stay or statistics Cancel restores the live unsaved document and exact recovery bytes, and releases only holds owned by this request. An explicit save already completed remains durable. Recovery CAS conflict at terminal cleanup must not delete newer bytes; report/preserve them.

Trace decisions bind `{departure_generation, recorder_identity, recording_generation}`. Use [TraceRecovery](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/ui/trace_recovery.gd) semantics: Retry, Discard recording and continue, or Stay; reconcile a manual save; reject stale dialog actions and require a fresh decision for a later recording on the same recorder. A failed stop retains pending trace data but recording may already be stopped. Mask held keyboard/menu edges, preserve independent controller/radio policy, and reject duplicate or stale callbacks; do not impose a new radio-neutral policy without its owner’s contract ([app_root.gd](https://github.com/bultodepapas/OpenRCsimulator/blob/997e212784dbf873a7b054ddbbc68e7905495adf/app/app_root.gd), `_begin_exit_request`, `_hold_exit_sessions`, `_hold_exit_input`, `_advance_trace_exit`, `_complete_exit_request`).

## 11 Source aware integration beyond the wizard

### 11.1 Home and saved aircraft

Add a My aircraft section backed by the accepted Creator index. Its cards display name, preview, source type, revision, estimated/calibrated scope where evidenced, and availability reason. Selecting a card produces a published `SourceRef`; it never smuggles an imported ID through `Catalog.canonical_id` or falls back to the stock default. An unavailable or missing record stays selected with Resolve, Restore dependency, Choose another aircraft or Cancel. Opening it in Workshop creates an editable draft based on that exact revision.

Audit every current Home use of catalog defaults. In particular, `_show_start_choice` currently rewrites unavailable modes, `set_battery_mode` can substitute ideal power, fuel selection can reset from catalog assumptions, and the Fly button separately checks catalog capability. The imported branch preserves the player's selected start and energy/fill and derives availability from the accepted source. A disabled choice exposes its reason; no silent Runway-to-Hand/Airborne or finite-to-ideal substitution is permitted. Existing stock and rotorcraft behavior remain on their own routes. Exercise Home → root → Main → `FlightSession`, not only a resolver unit test. [S12]

Version preferences with an optional published source branch, while preserving old catalog IDs and controller preferences. During migration, retain a valid old selection as catalog; a missing imported record is an explicit unavailable selection. A draft origin never enters preferences. On application downgrade, unsupported Creator metadata must not corrupt the stock preference record; keep the new namespace separate and preserve unknown newer saved files for a compatible version.

### 11.2 Presentation consumers

Route preview, thumbnail, camera framing, propeller blur, surface animation, contact overlays, crash presentation and audio through accepted capabilities and visual metadata. Current datum/name caches that infer state from catalog ID must not return a silent zero datum for an imported source. The accepted visual instance owns its confirmed datum; geometry, CG, propeller hub, hull and wheels share the same scale/frame conversion. Preview and actual flight must use the same builder and appearance provider, with independent instances and generation guards.

Source-aware audio selects a supported generic powertrain profile by accepted propulsion type and operating outputs; missing custom sound is explicit and can use a documented generic profile. It does not load user-supplied executable resources. A model without a visible propeller does not receive fake rotating airplane geometry. Crash presentation begins with bounded terminal-hull effects and a static wreck; optional fragment binding is separately scoped. Unknown smoke mounts, companions, missions, scripted scenarios, repair economics or activity-specific assets remain unavailable until their own provider and admission contracts exist. [S09, S11]

### 11.3 Flight identity and transaction outcome

Before a candidate can start, resolve the exact frozen source, appearance, dependency closure, launch profile, field, weather/atmosphere, input setup, initial energy/controller state, production timestep and effective backend/law identities. The first imported release explicitly requests `gdscript_reference` at the production 240 Hz tick. Existing catalog native behavior is unchanged. Imported native evaluation needs a separate qualified domain and implementation receipt; catalog coverage is not automatically imported coverage.

Use a typed transaction outcome with `assessed`, `available`, `physical_reset_committed`, `root_trial_published`, `observer_fault`, `accepted_identity` and diagnostics. There are two commit scopes: a reset commits state inside one `FlightSession`; root later publishes a newly prepared candidate as the active trial. Current `setup` performs a reset internally, and the disposable qualifier also commits resets; neither event alone is live root publication. Complete rejectable byte/dependency/visual checks and compare the effective candidate identity before root publication. If a future path requires comparison before reset itself, factor a deferred-reset setup API explicitly rather than assuming stock setup already defers it. [S01, S13]

The chosen initial policy is to dispose a faulty or mismatched **private** candidate before root publication and preserve the prior root/editor/recorder. Its receipt still records whether its internal physical reset committed; disposal is not rollback of that reset. Once root publishes a trial, or for a restart inside an already active session, an accepted physical reset with observer/publication failure leaves that accepted flight paused. Expose diagnostics and guarded Return; an observer-repair Retry is unavailable until an idempotent repair operation is separately implemented and qualified. Recording-save Retry retains its existing meaning. No path implicitly repeats a commit. A postpublication identity mismatch pauses/refuses further stepping and records a fault, rather than relabelling accepted state as an uncommitted failure.

The qualifier's current 16-second elapsed-time check occurs after synchronous setup/reset returns. It is not a preemptive watchdog. Preserve finite work limits, honest pending/cancel state and generation checks; hard timeouts require separately qualified isolation or preemption. Check start can cache a passing receipt only for its complete frozen key and support-policy version. Appearance changes may reuse separately keyed physical trim results, but require a new full trial receipt. Start, environment or energy changes invalidate the corresponding physical qualification as well. [S14]

Ordinary saved-aircraft flights and Workshop test flights retain their distinct statistics/credit rules. Preserve the current noncredit Workshop behavior. If normal imported sessions participate in statistics, use the stable physical aircraft ID and explicit source metadata; verify the actual accepted observer path and landing rules before awarding credit. A first successful tick is not a recorded landing, a handling score or evidence of safe real-world operation.

### 11.4 Replay and reset

Reset uses the same frozen inputs and effective implementation as the original trial. Checkpoints and recordings identify the full state layout, model/closure, law/backend, timestep and environment; newly introduced continuous/auxiliary state must have versioned save/restore coverage. Old records without launch provenance remain explicitly unknown rather than being retroactively labelled as a new exact start. Preserve historical stock replay identities. Physics-only replay should not require the original visual mesh if the recorded physical format supports it; any promised visual replay requires retained exact visual/skin bytes.

Do not expose imported CLI/scenario/AI companion selection merely because a source resolves. Those entry points need the same accepted-handle boundary, activity compatibility and recording rules. The first release may keep them unavailable with explicit diagnostics. This avoids a second path that bypasses the wizard's validation or selects stock defaults for an unknown ID.

## 12 Resource ownership and asynchronous work

### 12.1 Job state machine

Every asynchronous operation has a stable owner token containing host instance, draft ID, operation kind/generation, captured document generation and the relevant source/layout/appearance/configuration identities. States are `queued`, `reserved`, `running_data`, `running_engine`, `awaiting_adoption`, `committed`, `discarding`, `drained` or `failed`. A cancelled operation immediately loses adoption permission once cancellation is received, but keeps its resource reservation until its actual work and cleanup finish. A failed save that already crossed the storage commit point follows persistence reconciliation, not the disposable-job path.

The scheduler admits at most one heavy import/paint operation and one detached data worker under the initial policy. Replace obsolete queued previews with the newest relevant request; do not accumulate unbounded thumbnail/import/decode work. Compilation over immutable primitive data may run off-thread only after its dependencies and called APIs are proven thread-safe. Scene tree operations, `GLTFDocument.append_from_buffer`, scene generation, material/texture creation and UI adoption stay on the main thread initially. Do not assume that append is a pure byte parser because scene generation is separate.

Before a synchronous engine stage, render a clear stage message. While the event loop is blocked, the app cannot observe a new Cancel click or redraw progress. After append/build returns, hold the private result and reservation, yield through the event loop to process queued cancellation/close/replacement intents, then check ownership/generation and adopt atomically or discard. Show `Cancellation pending` only after a request is actually received. No source bytes, scene or partial material application are published by a stale completion.

This central lifecycle owns cleanup on every failure path: captured buffer, parsed arrays, generated mesh, textures, scene, staging files and reservation. Old preview and retained flight resources remain counted while a candidate is built. Use allocation-failure/error injection where the runtime permits it; do not claim recovery from process termination without exercising recovery on restart. The platform gate measures peak RSS/texture allocation and worst admitted synchronous stall, including embedded image decode and postprocess. If the proposed subset cannot meet the registered limits, lower admission ceilings or implement a separately qualified asynchronous/isolation strategy before release.

### 13.3 Definition of done for every capability PR

Each PR identifies its existing source seam and new data version, states what user-visible behavior becomes available, and lists unsupported combinations. Acceptance backlinks do not add circular PR prerequisites. ### 14.2 Required hostile and edge fixtures

Keep tiny independently constructed fixtures with expected results. Include binary STL whose header starts with `solid`, exact/short/extra payload, absurd facet count, ASCII bad keyword/number/missing facet terminator, no-final-LF complete file, NaN/Inf/overflow, duplicate/degenerate vertices and finite extreme scale. GLB cases include valid rigid tree, disconnected cycle, self-cycle, two-parent child, repeated root, out-of-range reference, depth limit, duplicate names, shared meshes, multi-primitive material mapping, unsupported animation/skin/sparse accessor, external/data URI, reflected transform and buffer/stride overflow. Cyclic files must be rejected without an engine invocation.

Image fixtures include valid rectangular PNG, indexed/alpha variants in the supported decoder policy, MIME/signature mismatch, malformed IHDR/chunk/CRC, forbidden compressed metadata, excessive pixels/chunks and multiple images that pass individually but exceed the aggregate cap. Bundle fixtures include path traversal, case-fold duplicate, symlink, duplicate member, undeclared member, malformed manifest, missing closure, expansion bomb and same-ID/different-bytes conflict. A valid untagged wrong-template PNG must be accepted as an image but require visual alignment review; do not invent an automatic semantic compatibility result.

For physical known answers, use simple asymmetric component boxes to test all six tensor entries and a fixed-vs-moving hub. The arithmetic example `rho=1.225 kg/m3`, `n=100 rev/s`, `D=0.3 m`, `Ct=0.1`, `Cp=0.05` gives `T=9.9225 N` and `P=148.8375 W`; it is a unit-test fixture, not a measured aircraft or qualified propeller. Use independently computed expected values and explicit tolerances. Servo timing uses neutral-to-end versus full-crossing cases; launch tests separate body pitch, trajectory and actual local wind.

### 14.3 Failure injection boundaries

Storage injection points cover before object write, midwrite, after object flush, after readback, before index publish, after index blob, after previous pointer update, before/after current pointer replace, and after commit before UI acknowledgement. Restart after each point: resolve the old or new accepted transaction according to the actual commit point, never an orphan. Include postcommit unreadable pointer and later reconciliation, process death while holding lock, disk exhaustion after admission, expected-version conflict and repeated recovery saves near quota. A saved snapshot does not include referenced bytes that never became durable.

Lifecycle injection covers source replacement while import drains, editor destruction after save commit, Cancel queued during engine append, stale skin/thumbnail/check callback, paused prior flight with recorder, failure before trial physical commit, accepted observer fault after commit, Return/Restart/Quit trace failure, manual trace save during a dialog, generation-1 discard reused against generation 2, and statistics cancellation after draft Discard. Compare editor/recovery bytes and owner state, not only visible labels. An explicitly completed Save stays saved after later cancellation.

## 15 Player guidance and in product wording

The player README is part of the feature, not an optional developer note. Provide an offline Read the guide action within Creator, with focus return and exclusive modal behavior.
