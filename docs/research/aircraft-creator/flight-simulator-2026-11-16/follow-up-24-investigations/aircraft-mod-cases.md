# Aircraft modification case investigations R07–R12

**Product-direction update:** the later [automatic wizard contract](../../../../plans/flight-simulator-import-wizard.md) owns current delivery acceptance: in-app conversion, questions only for unresolved data and editable results. Earlier preparation/manual-step recommendations in this dated evidence are optional development/recovery proposals; underlying format and physics findings remain unchanged.

Part of the [24-investigation follow-up](README.md). The [feature plan](../../../../plans/flight-simulator-aircraft-import.md) owns acceptance and implementation; [tools and fixtures](tooling-and-fixtures.md) turns these findings into a proposed evaluation backlog.

**Date:** 2026-11-16. Research only; no aircraft was imported or flown in OpenRC. Sources are public project pages, version histories, and first-person reports inspected as text. I did not download packages, binaries, or authored models. A source page's declaration is evidence of the author's intent and stated release, not an independent measurement or a grant to redistribute. All proposed fixtures below are newly authored analogues unless a separate component-by-component rights review explicitly permits otherwise.

## R07: C152X and simulator updates

**Question.** C152X and its JPLogistics successor

**Question.** Can an accessible, single-engine C152 mod serve as a complete conventional-aircraft fixture, and what does its update history say about source observations?

**Sources.** [DRF30q C152X repository and README, v0.17, changelog dated 2020-10-14](https://github.com/DRF30q/C152X); [C152X forum launch and cold-start reports, 2020-09-04–05](https://forums.flightsimulator.com/t/c152x-realism-mod/252690); [FrettFS's performance-tuning proposal and correction, 2020-09-18](https://forums.flightsimulator.com/t/c152x-realism-mod/252690?page=8); [JPLogistics C152 project announcement and changelog, 2020–2021](https://forums.flightsimulator.com/t/msfs-c152-community-v1-0-0-updated-09-10-2021/309284); [JPLogistics hotfix for MSFS 1.12.13.0, 2020-12-23](https://forums.flightsimulator.com/t/msfs-c152-community-v1-0-0-updated-09-10-2021/309284?page=13).

**Inspection and evidence.** C152X is the accessible predecessor used here alongside the requested JPLogistics case. Its README identifies v0.17 as an overlay: it does not create a new aircraft selection or directly modify the original base files. It describes changes to stall speeds, the piston engine, fuel capacity, gauges and electrical behavior. The author chose a 115 hp engine and long-range tanks to match the displayed instruments; those are authored variant decisions, not independently established data for every real C152. The repository page exposes the patch folder and README; no root license is shown there. That observation does not establish rights to code, model, texture, or stock assets. The project is **a stock-dependent modification, not a standalone model or a cleared CI asset**. JPLogistics credits DRF30q and TheFrett and builds on the same stock C152, but is a distinct project and release line.

The forum contains useful first-person qualification limits. Gilandred reported the avionics failed to turn on at manual cold start and Cradle77 separately reported the same cold-start symptom; the author issued a new version hoping to address it. FrettFS initially described performance tuning with a negative-drag spoiler workaround, then realized the simulator had reset weight and balance and updated the proposal. Do not assume the first workaround was merged into C152X v0.17. JPLogistics later reported that base changes in simulator 1.12.13.0 caused serious issues and temporarily removed its flight-model changes in v0.9.3b while retaining other functionality. That is a developer report, not an independent reconstruction of the failure.

**Plan change and fixture.** Capture the selected *base revision plus exact overlay and variant* as separate evidence-bearing inputs. If a base cannot be supplied or precedence is unknown, report unresolved physics/visual closure instead of treating the patch as an aircraft. Build an original small trainer fixture in three layers: known base, partial configuration override, and a changed-base counterexample. Check that readings cite their actual source and that absent overlay fields do not turn into guessed values. Include a restart/launch-state distinction only when its owning Creator gate exists. Keep the physical values observational until explicit adoption provenance is implemented.

**Status / confidence.** High confidence in patch classification and the documented hotfix; medium on generalizing any historical failure to other releases. Rights and full source closure were not established. A small single-tractor aft-tail shape is relevant to the initial RC workflow, but this real aircraft cannot be used as the required redistributable fixture on present evidence.

## R08: C172 mod dependencies

**Question.** C172 AS1000 paired visual and realism overlays

**Question.** What happens when two separately authored improvements to the same conventional aircraft are selected together?

**Sources.** [MGouge425 C172SP AS1000 Realism Mod listing and version history, v1.4.3, 2025-08-12](https://flightsim.to/addon/43049/asobo-c172sp-as1000-realism-mod); [Bagolu C172SP AS1000 Improvement listing, v1.15.2, 2024-05-14](https://flightsim.to/addon/40194/cessna-172sp-skyhawk-as1000-improvement); [Bagolu announcement, 2023-01-02](https://forums.flightsimulator.com/t/update-cessna-172sp-skyhawk-as1000-improvement-mod-freeware-bagolu/567533); [Bagolu compatibility break and v1.3.4 fix report, 2024-05-12](https://forums.flightsimulator.com/t/cessna-172sp-skyhawk-as1000-improvement-mod/541811/54).

**Inspection and evidence.** MGouge425's listing classifies this as a modification of the MSFS 2020 default C172SP AS1000, including floats and skis variants. It says engine, flight-model, weight and balance parameters changed, with details in a package documentation file that was **not** downloaded. Its v1.4.3 public changelog says ground-effect lift and flap lift/drag/pitch were retuned and float free-castering steering was disabled because of the author's reported simulator behavior. Bagolu describes a separate replacement overlay, with added interior objects, animations, removable fairings and saved state; it replaces the default selection rather than proving a standalone exterior. The listings claim compatibility between current versions, and Bagolu says the mod is not compatible with MSFS 2024. These are release-specific author claims.

A concrete historical interaction is stronger evidence than the compatibility label. On 2024-05-12 Bagolu reported that the preceding update broke the angle-of-attack indicator when both mods were installed: the realism mod's `system.cfg` lacked `circuit.49` for stall warning. Bagolu subsequently reported MGouge425 had included it in v1.3.4. This is a co-mod author's report and reported fix, not an independent reproduction or proof of how all versions resolve conflicts. Both are **stock-base-dependent patches**; their selection in the hangar says nothing about a complete authoring glTF. MGouge425 states that Microsoft assets were used under Microsoft's Game Content Usage Rules; that is not an identified permission to redistribute them in OpenRC. No component-level reuse grant was established for Bagolu either.

**Plan change and fixture.** Display the chosen base, each optional overlay and its version independently, and identify two inputs that define the same effective file or logical value. Do not invent load precedence or combine them based on folder order: require documented precedence and a tested adapter rule, or mark the effective value conflicted. Use a newly written stock-base/physics-overlay/visual-overlay fixture with two incompatible revisions: one missing a referenced circuit and one explicitly repaired. It should produce a targeted missing-reference or conflict diagnostic, then a distinct repaired report; it must not run the imported circuit code. Keep float/skis contact behavior out of the first gearless flight domain. The conventional airframe shape still makes this a good source-report scenario once the player provides lawful source and a prepared exterior.

**Status / confidence.** High for the stated versions, explicit dependency, and author-reported compatibility incident; lower for actual package contents and resolution semantics, which require local source inspection and separate permission. No inference from “compatible” to open license, complete geometry or simulator-equivalent flight is warranted.

## R09: Savage Carbon geometry and balance

**Question.** Savage Carbon bush-plane conversion

**Question.** Does a popular taildragger with a recognizable model provide transferable values for a first electric RC aircraft?

**Sources.** [GotGravel Savage Carbon forum description and changelog, v2.1.0, 2022-12-27](https://forums.flightsimulator.com/t/update-savage-carbon-stol-realism-mod-v2-10-dec-27-2022/311661); [GotGravel on CG and engine-placement error, 2020-11-03](https://forums.flightsimulator.com/t/update-savage-carbon-stol-realism-mod-v2-10-dec-27-2022/311661?page=3); [user braking report, 2020-11-06](https://forums.flightsimulator.com/t/update-savage-carbon-stol-realism-mod-v2-10-dec-27-2022/311661?page=7); [user landing and nose-over report, 2020-11-23](https://forums.flightsimulator.com/t/update-savage-carbon-stol-realism-mod-v2-10-dec-27-2022/311661?page=20); [GotGravel Savage Obstruction installation, 2021](https://forums.flightsimulator.com/t/new-savage-obstruction-bigger-is-better/385921).

**Inspection and evidence.** The author explicitly requires the default Savage Cub for Carbon even though Carbon appears as a new hangar aircraft. The package is therefore **a stock-dependent conversion**, not an independently complete source model. No source repository or component reuse license was established from these pages. The sibling Obstruction likewise declares the stock Cub dependency; appearance as a separate aircraft or a free download is not evidence that either includes a reusable base. The author lists 29-inch wheels, a 165 hp engine, an 82-inch prop, suspension and a 60-degree flap setting. That describes a bush configuration, not an RC electric installation.

The changelog gives unusually concrete provenance. In a 2020-11-03 developer post GotGravel said the simulated engine had been placed 20 cm too far forward, affecting braking and easy nose-dips; the author proposed correcting CG and improving brakes. Later v1.1.1 notes record an enlarged visual prop, changed prop angle, changed aircraft weight, wheels moved forward, and lowered bushwheel drag. Version v1.8.0 adopted the modern propeller model; v2.0.0 retuned the flight model around the simulator's CFD features; v2.1.0 further changed CFD, surface response and ground handling. These observations are developer-reported revisions, not measured RC coefficients. On November 6 CaptHawkeye50 separately reported the previous braking nose-dip no longer occurred after v1.0.2; the user was only then installing v1.0.3, so this does not independently prove the engine-position explanation. Rexbo47 later reported a nose-over during an unusually high-wind landing with braking. Neither account establishes a defect in current v2.1.0.

**Plan change and fixture.** Keep CFG datum, empty/loaded CG, engine/prop position and each wheel contact independent, and record which revision each belongs to. Avoid deriving CG from a bounding box or discarding large wheels while preserving their original drag as an electric model. As a newly authored test, give a small taildragger an asymmetric datum, movable virtual ballast and separate prop mesh and contact proposals. Preview and source report should show the 20 cm-style revision difference without silently changing its imported CG. A synthetic flaperon should be flagged as an unsupported mixer until the Creator explicitly supports it. Do not promote this aircraft to ground-flight acceptance: the first proposed domain is gearless hand launch/airborne and still requires qualification; contact, taildragger ground behavior and propwash require separately owned numerical work.

**Status / confidence.** High in source dependency and historical author statements; medium in interpretation of cause because there is no independent technical reproduction here. Useful for placement and unsupported-capability diagnostics, not a permissive bundled aircraft or a first-domain flight oracle.

## R10: AS33 Me glider systems

**Question.** AS 33 Me sailplane and B21 soaring behavior

**Question.** Does an apparently complete original glider establish open source, a visually faithful stopped prop, or support for glider physics?

**Sources.** [MADolo and B21 AS 33 Me release page, v2.0.2 and prior version history](https://flightsim.to/addon/15090/as-33-me); [MADolo original-project announcement, 2021-05-26](https://forums.flightsimulator.com/t/alexander-schleicher-as-33-me-18m-sailplane/404952); [B21's v1.8.2 ballast and tow changes, 2022-12-18](https://forums.flightsimulator.com/t/released-as33-18-meter-glider-freeware-on-flightsim-to-madolo-b21/548174/30); [B21 on simulated versus displayed prop rotation, 2023-10-05](https://devsupport.flightsimulator.com/t/props-rotate-in-reverse-when-feathered/3714/10); [B21 and another developer on tow requests and repeat-launch trouble, 2023](https://devsupport.flightsimulator.com/t/how-to-call-for-a-tow-plane-after-you-are-already-in-the-fly-now-mode-of-the-simulator/5557).

**Inspection and evidence.** MADolo identifies the AS 33 Me as a ground-up model rather than a stock-aircraft conversion. The release page credits MADolo for model/animation/interior, B21 for code/flight dynamics/sound, and Chris Bullas for exterior textures. It describes a complete *distributed simulator aircraft* with wing flex, flaperons, water ballast and retractable self-launch motor; I did not inspect its package or establish that an authoring model, all referenced source files, or a source repository is publicly available. The author requests that users wishing to share the model with friends direct them to the original listing. This establishes a preferred sharing route, not a general redistribution license. Treat model, textures and code as **rights unverified; no redistribution grant established** on this evidence. Download availability does not make it an open aircraft.

The v1.8.2 author notes changed water ballast from payload in `flight_model.cfg` to `[WATER BALLAST]` in `systems.cfg`, with control events and aerotow/winch support; the listing also claims CG and trim changes across ballast states. In a separate DevSupport post, B21 reports that the motor glider's prop is visually stopped while MSFS still sees it rotating at roughly 60 rpm, and that the team used an older prop model to avoid simulated drag. That is direct developer evidence of deliberate visual/physical divergence, not proof of actual performance. B21 also says AS33 requests a tow using XML/RPN; another developer independently reports a repeated-tow failure after landing and reset, while a support responder had previously tested event dispatch on a different glider. These are different setups, not a common reproduced AS33 defect.

**Plan change and fixture.** Detect ballast declarations and tow/self-launch/custom-logic indicators wherever their selected source version puts them; list them as unsupported behavior rather than mapping them to RC battery mass or glider handling. Build a licensed synthetic sailplane with a stowed prop, a visual-stop state and a different declared physical prop state, plus empty/full ballast observations. Make those fixture states explicit attributed observations; the importer reports their contradiction without claiming it can infer hidden runtime shaft state from an arbitrary static mesh or CFG. Unknown real dynamic dependencies remain unresolved/unsupported, and XML/RPN stays unexecuted. A neutral preview requires an explicitly supported rigid normalization that passes ordinary GLB admission. Sailplanes, flexible surfaces, ballast, tow and hybrid/retractable propulsion remain outside the first conventional single-tractor flight domain.

**Status / confidence.** High for documented version changes, credits, the sharing request and B21's report of his own workaround. Package closure, code availability, transferable physical accuracy and compatibility of any later port remain unverified.

## R11: VL3 visual and physical discrepancies

**Question.** JMB VL-3 Rotax 915 community modification

**Question.** Can a light-sport, single-tractor source produce a straightforward RC input, and do visual and configuration data necessarily agree?

**Sources.** [VL-3 Rotax 915 repository README](https://github.com/ronalove/fs2020-vl3-rotax915); [v0.42 commit `56301dc3d09761fb292224852d52a74fed97e76c` and diff](https://github.com/ronalove/fs2020-vl3-rotax915/commit/56301dc3d09761fb292224852d52a74fed97e76c); [2020-09-27 contributor CFG proposals](https://forums.flightsimulator.com/t/vl3-rotax-915-mod/239670/109); [first-person cold-start report and suggested fix, 2020-09-27](https://forums.flightsimulator.com/t/vl3-rotax-915-mod/239670?page=4); [open fuel-display issue #17, 2021-09-08](https://github.com/ronalove/fs2020-vl3-rotax915/issues/17).

**Inspection and evidence.** The README calls this a conversion of the stock VL-3 912 and describes a 141 hp, fuel-injected turbocharged Rotax 915 iS and a simulated three-blade variable-pitch prop. It explicitly says the 3D model still shows two blades. Thus this is **a modification requiring a stock base**, even if it adds liveries or its own aircraft selection, and it contains an acknowledged visual-versus-simulated configuration mismatch. The v0.42 GitHub commit diff actually shows `aircraft.cfg`, `layout.json`, an effect file and a livery's DDS metadata; it changes the ICAO designator and adds missing texture metadata. This is evidence of specific patch files, not proof the model and every dependency are available. The root listing exposes no license; the README credits multiple authors and third-party livery contributions. Neither GitHub hosting nor a release establishes a right to redistribute those components.

A 2020-09-27 contributor's proposed configuration lists engine and aerodynamic edits and even gives `max_gross_weight = 1690` with a misleading “Empty weight” comment, next to a separate `empty_weight = 794`. These are a forum proposal at that date, not a verified snapshot of v0.42. The type/field must outrank the erroneous comment, but the importer should retain both and flag uncertainty. GotGravel reported a cold-and-dark start accelerating violently after a patch; contributor CodenameJack447 claimed revised values fixed it. The authors attributed causality speculatively, so do not claim a verified root cause or universal fix. Separately, issue #17 reports a single user's fuel display/refuel behavior after switching camera; the issue contains no independent reproduction.

**Plan change and fixture.** Present author-declared or player-confirmed visual blade count, selected model node, configured propeller type and source revision as separate observations. Do not assume blade count is mechanically recoverable from arbitrary geometry; otherwise mark it unknown. An unresolved two-versus-three blade discrepancy must never become a guessed propeller model or auto-selected RC power system. Add a tiny authored CFG test with independently recognized keys, a misleading unit/comment and values from a later revision; confirm retained comments cannot override typed key semantics. Also exercise the configuration/base missing case and user-supplied prepared GLB association. For flight, let the user explicitly author a compatible fixed-pitch electric installation with its own identity, finite battery, weight and geometry; do not equate a scaled Rotax/variable-pitch system with it.

**Status / confidence.** High in the README's documented prop mismatch and pinned diff, medium in historical forum symptom and proposed remedy. No direct source-package import, license clearance, or claim that the forum's interim values are the v0.42 configuration.

## R12: A32NX custom systems and SU9

**Question.** A32NX SU9 autothrust failure and release-specific systems

**Question.** What can an actual complex-aircraft update failure tell us beyond the existing A32NX geometry and licensing review?

**Sources.** [A32NX aircraft README at the existing inspected revision `753bbdd744d26d76b600c5f23ee59ece4f68341f`](https://github.com/flybywiresim/aircraft/blob/753bbdd744d26d76b600c5f23ee59ece4f68341f/README.md); [merged PR #6996, 2022-04-02](https://github.com/flybywiresim/aircraft/pull/6996); [FlyByWire stable v0.7.5 announcement, 2022-04-26](https://forums.flightsimulator.com/t/v-0-12-3-a32nx-stable-flybywire-simulations/391978/16); [BanziDuck takeoff-thrust report and follow-up, 2022-04-30](https://forums.flightsimulator.com/t/engine-thrust-drops-to-idle-after-to/514417); [Pelice branch-comparison report, 2022-06-05](https://forums.flightsimulator.com/t/a320-fbw-engines-lose-all-power-during-take-off/514222).

**Inspection and evidence.** This is a **substantial aircraft source project**, not merely a repaint or performance-only CFG patch. Its repository has independently developed systems and exterior assets, with a dependency/submodule and model-format limits already examined in the existing source investigation. The pinned README distinguishes GPLv3 original code, CC BY-NC 4.0 original 3D assets, and separately governed Microsoft-derived materials. Those are distinct rights scopes; none authorizes treating the whole aircraft as a permissive RC asset or assuming that checkout equals a complete build. The PR discussed here is historical and is not asserted to be the specific code at the later inspected pin.

In merged PR #6996 the developer reported that on SU9 engine control stopped when 100% was written to the simulator throttle, commonly during TOGA takeoff. The PR specifies a runway/TOGA test and was merged April 2, 2022. The v0.7.5 stable announcement on April 26 identifies SU9 build 1.25.7.0 compatibility and an autothrust fix for engine loss at 100% throttle; this stable release did not contain the new custom FMS. On April 30 BanziDuck independently reported thrust dropping shortly after liftoff in both development and stable builds, but then reported that a clean install *and* changing the target speed to 210 knots resolved the flight. Those simultaneous changes do not prove the PR fixed that user's symptom. On June 5 Pelice reported a similar shutdown in development/experimental but not stable 0.8.1 and cited two build hashes; the report says “I think” the issue was the same and does not prove common cause. This evidence is stronger than a vague claim that an update “broke aircraft,” precisely because simulator, release, controller state and scenario are named separately.

**Plan change and fixture.** Source readers should detect custom/autothrust/flight-control indicators and preserve them as unsupported dependencies, never execute them or claim CFG alone reproduces the installed aircraft. Freeze the simulator version, mod version, selected source hashes and test scenario independently in any compatibility matrix. Write a synthetic event-state fixture where an authored aircraft's apparent thrust depends on a controller and where `100%` is an exact boundary input. For the importer, the acceptance criterion is an accurate unsupported-system/provenance report and no code execution, not replication of this jet's thrust logic. Compare same bytes with distinct declared host versions to ensure neither compatibility nor flight qualification is inferred merely from a package name. Multiengine jet/custom-flight-control flight remains excluded.

**Status / confidence.** High for the merged change and release announcement; medium for any causal link to independent reports. No OpenRC reproduction, automatic fix, or compatibility claim follows. This historical issue adds a systems/version counterexample rather than repeating the existing model-extension survey.
