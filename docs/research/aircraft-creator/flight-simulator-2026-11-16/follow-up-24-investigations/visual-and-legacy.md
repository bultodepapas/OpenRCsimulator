## R01: Source and compiled glTF

**Question.** Does “glTF source” reliably mean ordinary, importable glTF, and how do the importers actually fail?

**Observations.** Asobo's official MSFS 2020 Blender add-on expressly says its import path does not import glTF built into a package using the simulator's Package Builder. It also requires the Khronos glTF add-on, says it conflicts with the old FSX/P3D exporter, and lists supported Blender LTS families. That is a documented tool boundary, not a rule that every compiled JSON necessarily has one magic header or that all noncompiled glTF is supported. The previously inspected, pinned A32NX LOD06 is a useful counterexample to a directory-name heuristic: it lives in `src/model` but declares `ASOBO_asset_optimized` 4.2, requires `MSFT_texture_dds`, and references DDS. Its selected bytes and extension declarations are evidence; “source folder” is not proof of a plain, Creator-admissible model.

FlyByWire issue #2 reports a specific Windows 11 / Blender 3.1.2 / msfs-blender-tools 0.0.1 attempt to import a compiled model, ending in `KeyError: -1` while resolving bone ancestors. This is an issue report, and the original issue was available to this search only through its indexed result; the precise cause and current behavior were not independently verified. In a different July 2025 issue on an unofficial fork, a reporter describes a Blender 4.5.0 import exception and a local code change that allowed that file to load. The issue is closed, but the retrieved record does not establish a merged fix, exact asset class, or safety of applying that change generally. In January 2026, another developer first suspected textures for drawing/transparency problems and later reported that reverting from a Blender 4.5.x/exporter combination to their 3.6.x combination resolved the observed result. This is version-specific field evidence, not a general failure verdict on either family.

**Plan edit and acceptance.** Amend AC-FS-03/04's intake report to separate *author-declared source form*, *detected encoding and required/optional extensions*, and *conversion outcome*. Display the Blender/add-on/converter versions used only when the author supplies them; no plugin may be assumed present. Keep first release as an author-prepared, rigid GLB through existing preflight. For the normalization spike, use independently authored pairs with identical geometry: plain glTF/PNG; a synthetic source carrying an unsupported required extension; a synthetic optimized marker plus unsupported accessor encoding; and an author-supplied prepared GLB. Assert complete admission only for a semantically supported closure, a precise refusal at the first unsupported feature for the others, and continued success of the prepared-GLB route. Do not infer either acceptability or incompatibility from path, extension string alone, or a sample importer's exception.

**Unverified / confidence.** High confidence in the official importer's documented exclusion; medium in the reported failure modes, which remain unreproduced and do not justify a universal compiled-glTF classifier. No conversion spike or new compiled-asset decoder is established.

## R02: DDS and material fidelity

**Question.** What separates successful DDS decoding from correct normals, ORM, color and transparency?

**Observations.** Microsoft's 2020 modelling guidance specifies DirectX normal packing and combined roughness, metal and occlusion. Its 2024 FlightSim material documentation specifies, for the named material slots, sRGB base-color RGB with linear alpha coverage and linear ORM channels R=occlusion, G=roughness, B=metallic; it separately warns that detail maps have specialized compression. These are scoped descriptions: do not infer that every Asobo material or compiled texture uses exactly the same packing. Microsoft's DirectXTex `texconv` documentation provides image/DDS conversion, distinct input/output sRGB options, alpha handling and compression formats, but an image decoder alone cannot determine a material's intended shader, texture coordinate convention or which channel contains data.

In a March 2024 FSDeveloper discussion, an author trying to recover their own scenery normal texture from a packaged DDS observed a vertical mismatch and transparency/channel differences between export paths. The MCX author recommended targeting glTF rather than FSX normal-map layout, and other participants disputed where any flipping occurred. The author later obtained a visually close image using additional manual operations. That thread supports testing the whole pipeline, not a universal “flip every DDS” or “always paint blue white” rule. In a separate December 2023 thread, the initial reporter described a gray blue channel, while MCX's author said a later compilation on his machine yielded black instead. These apparently conflicting observations are exactly why the decoder's version, actual source encoding, and interpreted semantic must be tested together. Separately, the January 2026 drawing/transparency case in R01 was initially misdiagnosed as a texture problem before the reporter changed their diagnosis.

**Plan edit and acceptance.** In AC-FS-04, publish a per-slot *material conversion profile*: recognized source material/extension, texture codec, channel use, color space, UV set and transform, normal handedness, alpha mode/cutoff and factor, and explicit omitted detail effects. Select a core fallback only when it is present and valid; required unknown extensions still refuse. Build an independently authored small UV-asymmetric quad with four distinct corners, a directional tangent-space normal, known linear ORM values, an sRGB base color and OPAQUE/MASK/BLEND samples. For every admitted profile compare decoded numeric channels and final rendered lighting/alpha against an independent known answer, with explicit tolerated block-compression error. Verify the same model under two UV orientations; intentionally invert the green channel and swap ORM channels to ensure the test fails. If a compressed normal reconstruction rule is not evidenced for the actual encoding, refuse that semantic conversion or label a permitted omission as partial; do not silently choose a flip. Quantify decode workspace and output pixel bounds before allocating.

**Unverified / confidence.** High for the documented named source material semantics and tool options; medium for the field reports. Whether any specific DDS variant, 2020 processed normal packing, alpha behavior, and color pipeline can be converted within Creator's limits remains an AC-FS-04 measurement, not current support.

## R03: LOD selection and completeness

**Question.** Which LOD is an importable exterior, and what can invisibility or an overly cheap model conceal?

**Observations.** Microsoft's 2020 LOD documentation describes model XML entries referencing glTF models at different detail levels; repeated or missing references must still be diagnosed. A lower level is intended to reduce geometry, material and texture cost. Its 2024 selection documentation describes a bounding-sphere screen ratio plus a vertex-count modifier and identifies exceptions, including the user-aircraft root and modular attachments. These are simulator rendering rules, not instructions to import the last, smallest or numerically named LOD into OpenRC. The existing pinned C-17 LOD01 has one node, no image textures and no animations; it proves only that this particular LOD's contents are not a complete textured moving aircraft. Conversely, a highest-detail LOD may exceed the current bounded Creator admission. A triangle count alone also misses draw calls, image pixels, material complexity, and unsupported bindings.

An FSDeveloper user converting an FSX object with MCX in August 2021 reported an invisible object when the generated XML referred to an empty LOD2; changing that reference to LOD0 made it visible. That is a scenery case and the discussion involves multiple possible settings; it should not be generalized as the sole cause of aircraft invisibility. In a December 2025 iFly 737 MAX8 lighting-mod report, the author said loading an otherwise unchanged interior XML from their package altered effective LOD thresholds and made the cabin disappear at distance even though all LOD files loaded. Another participant's VFS/load-order explanations were guesses, and no conclusive fix is established. The case demonstrates that existence of all files and an XML threshold alone do not prove what a source simulator renders. An aircraft model may depend on an interior visible through exterior windows, while the desired OpenRC exterior can also legitimately omit a cockpit by policy.

**Plan edit and acceptance.** Expand AC-FS-03/04/05's LOD chooser to list every resolved model XML entry, source-relative path/hash, role (exterior, interior, helper, or unresolved), primitive/triangle/node/material/image counts, animation/skin presence, supported extension set and missing dependencies. Flag an empty or shadow-only candidate and present estimated resource admission before selection. An explicit user-confirmed exterior LOD must have a visible, nonempty qualified closure; no “smallest wins.” For a fixture, author three LODs: a fully textured asymmetric exterior with separate rudder; a reduced exterior intentionally missing the rudder/paint; and a zero-mesh entry. Supply the same missing-file and interior-only variants and an independently specified expected-part/paint inventory. Loss assertions compare against that inventory or explicit source correspondence; without such evidence, completeness remains unknown. Assert that the first can pass only within budgets, the second is explicitly limited rather than advertised as complete, the empty/missing selections are refused as complete, and an unrelated interior/helper is never silently used as the exterior. Render silhouette, paint, and part inventory for a human review as well as checking counts.

**Unverified / confidence.** High on documented LOD structure; medium on individual reporter symptoms. How much interior geometry is essential for a particular aircraft is a user-visible completeness judgment; no source simulator's culling behavior has been recreated or required in OpenRC.

## R04: Controls and animation semantics

**Question.** How should glTF keyframes, model XML, SimVars, control pivots and RC movement be related?

**Observations.** Microsoft documents model behaviors as components assigned to a glTF node and/or animation, driven by SimVars or RPN, with templates and included behavior definitions. Its model-definition documentation also permits embedded or separate animation definitions. A matching node name alone therefore does not describe full motion, visibility, dependencies, range, or neutral pose. Neither a valid animation array nor an exported keyframe sequence proves how the simulator drives that animation. The current Creator visual contract rotates selected mesh-bearing nodes or proper-subset groups with mesh descendants about their own origins and selected local cardinal axes. It prohibits overlapping bound ancestors/descendants and does not pass animation or skin through. Simulator behavior is evidence for proposals, not executable input. [Current binding contract](../../../../../app/workshop/creator/visual_parts.gd), [GLB admission](../../../../../app/workshop/creator/glb_preflight.gd).

In a 2023 FSDeveloper ASK-13 glider project, its author reported that one XML worked for elevator, rudder and airbrakes while wing flex and ailerons did not, even though they expected names to match. The author suspected missing behavior links; a respondent suggested isolating a wing animation and explicitly called the skinning explanation uncertain. No root cause was established. In an older FS9-to-FSX conversion, a user reported control surfaces moving correctly in MCX but snapping back during one side of travel in the simulator. The same reporter later said changing the animation tag resolved their case and sometimes an axis needed reversal. That is evidence against treating a preview in a converter as proof of in-simulator mechanics, not proof a tag rename fixes other aircraft. In a Pilatus PC-7 example, the author reported nose-wheel rotation, compression and steering began working after setting the center contact point's X value to zero; this is an example of a behavior depending on physics configuration as well as visual data.

**Plan edit and acceptance.** Extend AC-FS-06 to store proposed role, source node identity, local/global transform, candidate hinge, animation name, XML definition/source line, declared SimVar/units/scale/bias where statically visible, missing include, and player confirmation separately. Do not execute or emulate arbitrary XML templates/RPN. A binding must be validated by OpenRC input and an independent expected pose at neutral and both extremes, including measured hinge position and sign. Create an asymmetric fixture with opposite-moving ailerons, one elevator, one rudder and a propeller; include transformed parents and a nonzero hinge origin. Verify endpoints and midpoint against independently specified coordinates, including two independent preview instances and mirrored/rotated source frames. Add a hinge that cannot be expressed by the supported local-axis binding, overlapping bound groups, a skinned wing and an essential neutral pose controlled by unsupported RPN. Refuse unsupported motion. A static preview is available only after an explicit, evidenced rigid pose normalization produces a GLB that passes ordinary admission; skin or animation cannot be passed directly through preflight. The player-approved bindings make the admitted visual respond to actual OpenRC control/shaft state; they do not change compiled physical controls or forces.

**Unverified / confidence.** High for the documented behavior architecture and current Creator boundary; medium for the user reports. We have not evaluated real XML templates or validated a reusable algorithm for extracting pivots from animations.

## R05: ModelConverterX preparation

**Question.** What can an author actually prepare from an FSX MDL using ModelConverterX, and where does the route stop?

**Observations.** ModelConverterX (MCX) author Arno Gerretsen lists FS2004/FSX/P3D MDL and glTF read/write, material editing, texture conversion and LOD creation; the current page lists stable 1.8 and a separately moving development build. A listed input/output pair is not a claim that all material, animation, physics, or dependencies round-trip. During initial 2020 glTF support, a user reported a regular FSX MDL imported and exported to glTF; in that thread the author identified and fixed a separate material draw-order writer bug. This establishes one historical success report and a real bug, not a qualified OpenRC GLB. Another author describes importing their own FSX/MDL via MCX and FlyByWire Blender tooling with permission for the restricted export; the 2023 workflow discusses animation timing and Blender version differences. It does not show that an ordinary public user can export arbitrary aircraft with all animation.

In October 2025, MCX's author explicitly said MDL-to-glTF animation export is restricted and that complete animation export is made available to developers converting their own work, because of piracy concerns. In January 2026 he described a development build's skin/bone export limitations, including a narrow simple ambient-animation exception for compiled MDL/BGL and remaining displacement issues when importing package-processed glTF. Those claims concern particular MCX features/builds; they must not be interpreted as permission, instructions to circumvent restrictions, or a blanket ban on author-created static exports. The target here is an authorized, Creator-admissible exterior prepared by the author, not necessarily an MSFS package.

**Plan edit and acceptance.** In AC-FS-12, describe MCX as an optional, author-operated *preparation candidate*, not a bundled dependency or automatic conversion guarantee. Ask for an independently prepared self-contained rigid GLB, along with source and converter version, source rights, selected exterior/LOD, transformed units, texture repair and a declared list of lost controls or effects. The author may use any tools they are entitled to use; do not require an SDK/compiler, distribute tool binaries or bypass author restrictions. Verify the GLB using current admission and test controls through manually confirmed rigid bindings. A project-authored synthetic legacy-model surrogate should exercise the external workflow contract: one prepared GLB with its own asymmetric hinge parts and embedded material passes the ordinary bounded GLB checks; another lacking one texture or merging rudder into fuselage reports the loss against the fixture's independently specified source-to-output inventory, and a non-self-contained glTF is refused at the Creator boundary. A real owner-authorized optional case must record exact tool version/settings and before/after visual and movement evidence before any compatibility claim.

**Unverified / confidence.** High for the tool author's stated current-format list and dated restrictions; medium for historical user conversions. No MCX version has been run, no MDL→GLB pipeline or animation retention has been verified, and no change to the existing first-release boundary is justified.

## R06: Legacy MDL and AIR dialects

**Question.** Can FS2004, FSX and Prepar3D be treated as one MDL/AIR dialect or mapped reliably from CFG alone?

**Observations.** Prepar3D v6's Flight Models documentation states that AIR carries many aerodynamic coefficients and refers to it from aircraft configuration; the SDK overview also describes coefficients and tables. This confirms why readable CFG alone is not a complete legacy flight model, but it does not establish that every FS2004, FSX and P3D AIR record shares meaning, precedence or target physics. The MSFS Legacy Importer author explicitly limits its support to native FSX aircraft, excluding FS9/FS2004 and P3D-only models; its AIR migration uses an externally generated text dump and comparison table, and its own instructions call for visual validation and manual repair of untouched modern values. This tool is not an OpenRC FDM oracle, and merely running its conversion would not qualify RC aerodynamics.

A Microsoft Flight Simulator forum participant in 2021 described `MDL8` and `MDLX` patterns in specific FS9 and FSX inputs while discussing an invisible Just Flight port. That observation can be a *diagnostic hint* only: the post also discusses protected content, which this project must not circumvent, and the alleged marker does not prove the complete dialect, integrity, version, rights or successful conversion. Record the byte evidence only if a bounded, reviewed detector is later implemented; never change a marker or execute a legacy model. MCX's author says certain FS2004 animation names differ from FSX names and describes configurable mapping to its internal FSX/P3D names. A 2017 FSDeveloper user importing an Alphasim P-51 FS9 model reported that MCX's preview animated but the P3D v4 exported propeller did not spin; the exchange shows nontrivial assignment steps, not a universal compiler failure or guaranteed cure.

**Plan edit and acceptance.** In AC-FS-12 retain separate axes for declared product/edition, observed model family/signature, config layout, AIR presence/version if determinable, and externally prepared visual result; unknown or conflicting evidence remains `legacy/unknown`. Show AIR as *present but not interpreted* until a separately bounded, versioned whitelist is substantiated, and label CFG observations as incomplete. Never manufacture missing coefficients, reroute them as measured RC data, or equate an external conversion's visual success with flyability. Freeze two tiny independently generated binary-header diagnostic fixtures plus truncated, conflicting, unknown and malicious-length samples; verify routing provides an evidence-backed candidate or unknown and never claims full validity from a prefix. Pair with a synthetic CFG specifying a missing AIR file and a declared external GLB: the source report names the absent dependency, the visual can enter only ordinary GLB admission, and RC trial remains blocked until separately authored fields and the existing physics gate pass. Add distinct FS9-, FSX- and P3D-version cases only when genuine fixtures, rights and record semantics are independently documented.

**Unverified / confidence.** High for P3D's documented AIR role and the importer's stated scope; medium/low for generalization from the community model examples. No complete cross-version MDL detector, AIR parser, simulator-equivalent FDM mapping or user aircraft conversion has been demonstrated.
