# Phoenix RC aircraft: package and importer research

Research date: 2026-11-17. Scope: public author/community documentation, seven selected PKG files, six outer ZIP archives, one separate legacy PHX and one public VAR reference. Third-party aircraft assets were inspected locally and are not included in this repository. No Phoenix executable, installer or emulator was run.

The [AC-PX implementation plan](../../plans/phoenix-aircraft-import.md) owns proposed work and acceptance. The [machine-readable inventory](phoenix-source-inventory-2026-11-17.json) owns exact source URLs, sizes, member paths and SHA-256 receipts. The [research probe](../../../research/aircraft-creator/phoenix/inspect_pkg.py) is a read-only package inspector, not an aircraft importer.

## 1. Decision and evidence boundary

**Phoenix is now a concrete importer research candidate.** The package layer can be inspected reproducibly, several current aircraft definitions are readable, and released files include explicit object/control references. The critical unsolved stage is full `.geo` geometry/material/hierarchy decoding. A later stage must interpret source units and physical semantics within OpenRC's actual authoring and qualification contracts.

This advances the [earlier RC source survey](rc-simulator-sources-2026-11-17.md#phoenix-rc), which had verified author offers but could not inspect their downloads. It does not retroactively change that survey's evidence. The new samples come from direct creator attachments and other public hosts; the separate SupermotoXL Pitts OBJ offer still returned HTTP 403 to the binary client, so its source contents remain unverified.

| Stage | What this investigation establishes | What remains unproven |
| --- | --- | --- |
| Acquisition | Exact public URLs and captured bytes for the selected files | A complete catalog, deduplication or blanket asset permissions |
| Outer ZIP | Entry metadata and CRC checks on six distinct archives | A production ZIP admission/cancellation implementation for Phoenix |
| PKG | Seven samples pass framed zlib and file-tree inspection | Every Phoenix package/version or hostile-input hardening |
| Definition | Six readable user-model `.mod` files contain concrete declarations | A complete safe parser or a validated translation of all units/laws |
| Geometry | Binary `.geo` members and some matching object/texture strings | Vertices, triangles, UVs, hierarchy, transforms and visual fidelity |
| Motion | Source hinge endpoints, sides, inputs and travel are present | Correct OpenRC binding, signs, neutral/end poses and actuator physics |
| Flight | Source capabilities can guide an honest missing-capability report | Flyable import, numerical qualification or RC realism |

### The actual Freewing SU-35 contents

The captured ZIP is 1,622,088 bytes, SHA-256 `cca61f719a796b2378d2c7b7f74df579a5b8b1065c6348ff4f3fdef8cf6e0e03`. Its sole PKG member has SHA-256 `2111d5c87704eb7670e5888c6a2303933c45f203b6a02a986c500e22373d785e`.

| Member basename | Bytes | Observed role |
| --- | ---: | --- |
| `SU_35_v23.geo` | 6,657,997 | Binary geometry container; no mesh decoder established |
| `SU_35_v23.mod` | 15,382 | Readable aircraft definition |
| `SU-35 Paint 2.png` | 642,602 | PNG header reports 2,047 × 2,047 pixels |
| `SU_35_v23_preview.bmp` | 16,440 | BMP header reports a 64 × 64 preview |

Its MOD identifies Freewing SU-35 and declares two propulsion entries named `EDF LEFT` and `EDF RIGHT`, both with `type = "turbine"`. They contain separate positions, `Max_Thrust = 30.0`, `Spool_Time = 0.5` and the engine/sound label `Medium electric`. These are raw source declarations; their units, executable behavior, independent control and physical accuracy were not validated. Phoenix's turbine label cannot establish compatibility with OpenRC's kerosene/turbine law.

The same definition provides aileron/elevator/rudder hinge data and four retract-enabled assemblies: nose gear, main gear, nose linkage and nose doors. It contains named NACA 0009 references. No explicit vectored-nozzle configuration was established. Neither appearance nor the actual RC aircraft's features can fill that evidence gap.

## 4. Observed PKG framing and tree

The selected PKGs do not begin with ZIP magic. They were decoded without executing Phoenix and without attempting to decode opaque/unclassified member data. All multibyte integers in the following observed profile are little-endian:

```text
package:
    u8 marker = 0
    u16 numeric_label_byte_length
    numeric_label_bytes
    u16 chunk_count
    repeat chunk_count:
        u32 compressed_byte_length
        u32 inflated_byte_length
        zlib_stream[compressed_byte_length]
    exact end of captured package

concatenated inflated body:
    bytes 01 00 01 00
    child_list
    observed zero padding, if present

child_list:
    u16 entry_count
    repeat entry_count:
        u8 kind                 # observed: 1 directory; 0 file
        u16 name_byte_length
        name_bytes
        if directory:
            child_list
        if file:
            u16 stored_source_path_byte_length
            stored_source_path_bytes
            u32 content_byte_length
            content_bytes
            u16 child_count = 0  # observed file-leaf profile
```

Each zlib block passed checksum/EOF, declared-size and exact-consumption checks. The largest observed inflated block was 1,024,000 bytes. Body padding was 0, 208, 240, 264, 292 or 306 zero bytes depending on the specimen. These observations are not an official specification; the probe rejects unknown structures instead of claiming that every such structure is invalid Phoenix data.

The tree exposes both relative installation paths and author-local source strings. It must be indexed virtually. Do not extract using raw path strings, follow embedded local paths or disclose author-machine paths in routine output. The probe reports raw member-name bytes, separate display text/decoding and offsets but suppresses stored source-path strings. Different byte encodings can display identically; production must diagnose aliases. The probe does not implement production path normalization, collision policy, archive extraction, cancellation or resource qualification.

### The numeric header is not a simulator version

For six readable models, the numeric header string correlates with `.mod` `revision`: Extra `7.000000` / `7.0`, AW109 `1.200000` / `1.2`, and the other four `1.000000` / `1.0`. Correlation suggests a package/model revision field but does not prove its meaning. The reader can parse a structurally valid synthetic `9.999999` label; it does not interpret that field. Use `pkg_header_numeric_string`, not `phoenix_version` or a confirmed encoding-version key.

MOD `formatVersion`, MOD `minProgramVersion`, author release names such as v23 and a Builder executable version are different identifiers. All six readable MODs declare minimum `5.0.a`; none was executed to validate that minimum or cross-version behavior.

### PHX and VAR need different treatment

The separate [Goblin 700 PHX](https://www.freakware.de/technik/Phoenix-Sim/Modelle/phoenixRC_goblin700.phx) begins with `PHOENIX_UPDATE_FILE` plus NUL and has a zlib stream at offset 40. Its 2,081,589 input bytes inflate to 6,008,201 bytes with EOF and no unused compressed bytes. It contains program-folder/path strings, but its member grammar was not parsed. The PKG probe does not support it.

A pinned [AFSL EasyStar VAR](https://github.com/uwafsl/AFSL/blob/c284e970ae6e669ccf0492647cafe7f81d2b6662/ComputingInfo/PhoenixRC/Airplanes/easystar_AFSL_Skywalker_Trainer.var) identifies itself as a Phoenix v5 variant and assigns values against `modelTypes.easystar`. It depends on a base model and is neither a complete visual aircraft nor merely a paint. Its restricted assignment grammar differs from a MOD's top-level table. Preserve base/override provenance and reject missing bases; never execute these files as scripts. Older PXM/FLY forms and airfoil SIM files remain outside inspected support.

## 5. Definitions contain valuable data, with incompatible semantics

Readable MODs contain a `modelTypes.<name>` assignment, nested tables, string object references and symbolic physics references. This is sufficient to design a static parser, not to justify executing them. The complete runtime grammar, duplicate-key behavior and alternate encodings are still open.

| Source information actually seen | Potential OpenRC use | Required interpretation |
| --- | --- | --- |
| Aircraft name, revision, format/minimum strings | Identity and compatibility report | Keep independent version dimensions and exact bytes |
| `Size`, `Weight`, CG position | Source observations; later authoring candidates | Establish units and scaling per field before adoption |
| Airfoil positions, lengths, root/tip chords, incidence, sweep, mirroring | Authored aerodynamic layout | Distinguish mirrored half-panels from whole span, source axes and dimensional fields |
| Geometry lists and `root_pivot` / `tip_pivot` | Control-to-object mapping and hinge proposals | Preserve exact object IDs, frame, axis, sign, neutral pose and membership |
| Inputs, travel, expo, low rates and mixes | Control review | Phoenix and OpenRC may apply these at different stages; avoid double expo or reversed mixing |
| Propeller/EDF positions and parameters | Capability/dependency report | Source laws, power/energy and physical data are not interchangeable |
| Gear, wheel, collision and door declarations | Future binding proposals | Visual and physical mechanisms require their respective owners and tests |
| NACA names, engine labels, tuning percentages | Unresolved references/tuning evidence | A label is not a polar, motor curve or calibration dataset |

Important concrete pitfalls:

- The Extra uses `Size = 2.67`, `Weight = 12.9` and positional values near 50, while its main-wing `Length` is about 1.23. The Queen Wasp likewise mixes positions near 50 with lengths below one. Do not apply one scale factor to all values.
- Phoenix's `Inertia` fields are labeled yaw/pitch/roll and often near one; no evidence here establishes a dimensional OpenRC inertia tensor. A valid-looking number is insufficient.
- The Wasp's exact geometry references include an `ELEBATOR_LEFT...` spelling. Matching source references is more reliable than expecting canonical English names.
- The Extra declares a gasser; the Wasp has multiple wings/flaps and an amphibious configuration. These do not fit the current gearless, single tractor-electric Creator compiler simply because their definitions are readable.
- The package samples do not supply matching airfoil `.sim` files. A named NACA profile does not provide the source simulator's full polar, Reynolds behavior or tuning model. Recent forum authors report difficulty constructing additional `.sim` airfoils, but their discussion is not a decoded SIM specification.

## 6. Authoring evidence and geometry unknowns

RickP's [Stik Tutorial v2.4](https://www.dropbox.com/s/v4dhhleaaj5qw5s/Stik%20Tutorial%20v2.4.pdf?dl=0) was downloaded: 132 pages, 39,493,962 bytes, SHA-256 `8c741bea2c9241b32ab3418e36e84a6e00d8e7a8e994c6442fadf2db69a2ba31`.

Pages 64–66 describe a 100-unit visual wingspan and OBJ export with normals. The screenshot uses `-Z Forward`, `Y Up`, scale 1.00 and object preservation. Page 69 shows a Builder v1.0.m file filter listing `.geo` and `.obj`; the tutorial demonstrates OBJ import, not a tested GEO import. Blender's other export-menu entries do not prove Builder support. Builder then separately authors physics, controls, materials and collision. Page 75 separates size scaling and weight; page 89 identifies the propeller's Engine choice as sound. The PDF mentions `.blend` attachments but contains no embedded files. None of those editable sources was obtained.

The tutorial and an [author's later axis discussion](https://www.rcgroups.com/forums/showpost.php?p=53477917&postcount=19379) suggest a Builder-aligned frame of +X left, +Y up, +Z forward. This is an example-derived hypothesis, not a universal decoded GEO contract. Geometry conversion needs owned asymmetric known-answer exports to establish units, transforms and handedness.

The [Builder v1.0.q author guidance](https://www.rcgroups.com/forums/showpost.php?p=55013937&postcount=5) describes forcing user-made status and format `5.0.a` for visibility in Phoenix 5.5.l. That is a visibility recipe, not proof that all v6-generated behavior works in v5.5. The [legacy Creator 2.5a archive](https://www.flugsimulatoren.ch/Files/PhoenixCreator_25a.zip) contains one executable and no separate documentation; it was not run and must not be conflated with Builder v1.x.

### What GEO inspection does and does not tell us

The Freewing geometry begins with bytes `01000000200000002000000070a60000`. Its paint filename occurs at byte 177. In the Extra GEO, strings corresponding to `WingLeft`, `Fuselage` and its paint filename are present. These are raw byte observations and do not establish record boundaries, vertex layouts, material graphs or a supported mesh reader.

The next useful experiment is a source/export pair with known topology, UVs, materials, nonidentity transforms and a hinge, followed by an independently authored second case. It should establish a concrete decoder profile before UI or fleet-scale compatibility work. No trustworthy ready-to-use open Phoenix GEO decoder was established by this investigation's searches; that limited finding is not a claim that none exists.

### Schemes and image encodings

The Extra has a base PNG, cockpit PNG, three `#` scheme PNGs, a prop-blur BMP and distinct preview/thumbnail files. The Wasps share identical paint bytes but have different GEO and MOD members. The Su-37 includes PNG/JPEG signatures and a TGA-named member requiring its own decoder investigation. Some BMP-named Yak members do not begin with BMP magic; they were left opaque, without guessing whether they are encrypted, encoded or another dialect.

This supports a base-aircraft-plus-scheme model and independent content inspection. It does not support assuming every image is a diffuse texture, deriving material connections from filenames alone or using a thumbnail as the aircraft skin.

The [current aircraft contract](https://github.com/bultodepapas/OpenRCsimulator/blob/3c91936ab8f9064daa798311b5fb3e89e28d3754/docs/AIRCRAFT_CONTRACT.md) excludes multiple propulsion units and EDF duct/fan momentum from active physical v2. The broader runtime already supports retractable gear, including an F4U rig; the remaining issue is Creator/import authoring and the specific aircraft's valid binding. Dynamic vectored thrust is separate from existing fixed thrust angles. The SU-35 therefore supplies useful source evidence and a future capability case, not a claim of present flight support.

Creator admission ceilings at this pin include 32 MiB source model, 200,000 triangles, 600,000 expanded vertices, 512 nodes, 32 materials, 16 images and 16,777,216 aggregate image pixels. They are policy ceilings, not achieved Phoenix capacity or performance measurements. Desktop exports and the numerical/physical qualification gates remain necessary.

## 8. Rights and delivery scope

The direct creator posts establish provenance of the public download, not a blanket grant to redistribute assets or modified versions. The research inventory marks redistribution/conversion permission as unestablished unless separately evidenced. Included pilot meshes, textures, logos and sounds can have additional authors. A community host describing software as abandonware does not resolve those permissions.

SupermotoXL's [Pitts release](https://www.supermotoxl.com/projects-articles/ready-to-drive-fly-models/hobby-king-pitts-special-bi-plane-phoenix-r-c-simulator.html) offers a separate OBJ download with noncommercial distribution terms. Its binary download remained inaccessible here. That is a useful author-source lead, not an unrestricted asset license or proof of a universal decoder.

This commit supplies English research, a proposed engineering plan, metadata and original inspection/check code. It does not bundle models, textures, author-local paths, vendor programs or converted aircraft. An implementation should support authorized user-selected sources and report unsupported/protected data without working around it. Any bundled showcase or export of third-party assets needs its own evidenced rights.

## 9. Reproduction and acceptance boundary

See the [probe guide](../../../research/aircraft-creator/phoenix/README.md) for exact invocation, limits and the [verification receipt](phoenix-probe-verification-2026-11-17.json). The root review re-runs the final probe on all seven pinned inputs and checks output against the inventory. Synthetic checks exercise framing, lengths, truncation, integrity, leaves, padding and bounds without redistributing aircraft files.

The script reads a bounded local PKG and emits JSON. Image classification is a header heuristic, not an image decoder or proof of a complete image. Original-path strings are not emitted; member names are still untrusted strings. Body offsets refer to the concatenated inflated stream, not the original compressed file. Hashes bind captured bytes, not authorship, license or physical accuracy.

No runtime import or flight campaign was run. No mesh was reconstructed. The first implementation decision is to prove GEO normalization on independent fixtures; in parallel, a safe definition/closure reader can expose useful observations. The [AC-PX plan](../../plans/phoenix-aircraft-import.md) then requires automatic in-app integration, truthful states, source retention, controls, flight guards and exported-platform evidence before advertising support.
