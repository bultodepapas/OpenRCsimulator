## 1. What the drone already implements

The existing drone OSD is the primary implementation seed. It has **27 element IDs**, five visibility layouts (`off`, `race`, `freestyle`, `full`, `custom`), two unit choices, two treatments (`hd`, `analog`) and four crosshairs. The default is Freestyle, metric, HD and the default crosshair. These are legacy OpenRC choices; there is no independent INAV/ArduPilot profile, positionable character grid or universal vehicle adapter yet. The element registry and defaults are in [osd_model.gd](../../../app/vehicles/multirotor/osd_model.gd), `ELEMENTS`, `LAYOUT_ELEMENTS` and `DEFAULTS`.

### All 27 elements: disposition

This table covers the entire current registry. “Adapt” means retain useful logic or graphics behind the new contract; it does not claim the existing function already accepts every family.

| Current IDs | Reuse and required change |
| --- | --- |
| `crosshair`, `horizon`, `ladder`, `updown` | Extract the drawing primitives. Separate body-attitude instruments from actual-camera projection; current horizon geometry accepts body attitude plus fixed pitch tilt. Declare dependencies explicitly. |
| `sidebars`, `compass` | Reuse recorded strips, clipping and transform-only movement. Separate speed/height semantics, units and palette; expand cache identity beyond viewport and UI scale. |
| `altitude`, `vario`, `speed`, `angles` | Reuse readouts and formatting with explicit 3-D/horizontal/air speed, height datum and body attitude. Vario must have an admitted independent element or a declared compound relationship. |
| `gforce` | Reuse the filtering idea with a named measurement kind, source, sampling policy and generation. Quad specific-force magnitude is distinct from the aircraft overlay's signed body-normal load factor. |
| `home` | Reuse local geometry and arrow primitives. Retain home source/reference; a nose-relative arrow and a camera-projected marker are different elements. |
| `gate` | Keep the race source, score and gate ordering in the activity. A reusable projected-marker primitive may consume its detached target. |
| `battery`, `battery_detail`, `power`, `efficiency`, `remaining` | Reuse graphics and appropriate formatters. Supply per-pack observed fields and labelled estimates; expose element dependencies; retain no invented data for an ideal-supply vehicle. |
| `throttle`, `motors`, `rpm` | Reuse bars/readouts. Actual control meaning, actuator count/order and RPM aggregation remain source-specific; do not label steering, collective and motor command as the same quantity. |
| `sticks` | Reuse drawing. Obtain actual raw/conditioned stick identity and mode from the input owner; missing scripted input remains unavailable. |
| `timer`, `on_timer` | Reuse pure clock formatting. Distinguish session time, accepted armed time and family-defined trip/flight duration. |
| `mode`, `craft` | Reuse text presentation. Source actual active controller/mode and accepted vehicle identity instead of the quad's ACRO/ANGL/TRTL branches. |
| `stats` | Reuse bounded summary presentation and suitable calculations. Family lifecycle owns start/end/reset; the OSD cannot invent an airborne requirement for a car or count another flight in the statistics service. |

Warnings, arming status, hints, race lines and transient messages are outside `ELEMENTS`. Off hides flight elements but does not remove that activity presentation. Their menu, race and statistics interactions still matter.

### Concrete compatibility traps

1. **Selected does not always mean independently drawable.** HUD `update` and `_draw_osd_slow` nest battery detail/power/efficiency inside battery, vario inside altitude, and ladder inside horizon. Up/down needs a horizon context that is only built when horizon or crosshair is selected. A Custom singleton can consequently display nothing. Preserve these cases in the legacy baseline; new profiles must either make elements independent or expose a deliberate dependency/compound rule.
2. **Analog is currently an approximation.** `_tone` returns white, but the painter independently colors north, stick dots and nearly saturated motor bars. The painter uses system text and vector primitives, not a firmware glyph atlas. The existing analog assertion checks the arm label only. A new monochrome character profile needs its own complete palette/glyph evidence.
3. **The speed distinction is observable.** At level attitude with body velocity `(0, 0, -10)` m/s, legacy speed is 36 km/h, horizontal speed is zero, climb is +10 m/s and live horizontal efficiency is unavailable. The source paths are session `telemetry`, model `flight_values`/`efficiency_text` and HUD `update`. This is an independent semantic fixture, not a runtime result from this review.
4. **Sampled render state is not an accepted event stream.** HUD `_track_flight` samples arm/home/stats at rendered updates. `GForce.sample` suppresses repeated ticks and resets on a decreasing tick; a reused tick in a new generation is insufficient. A short arm/disarm sequence or force peak between frames needs explicit observation/aggregate policy. Do not promise exact extrema from a renderer's latest sample.
5. **Clocks and visibility differ today.** Wall time drives the 12 Hz analog gate, 30 Hz slow-layer scheduling, 2 Hz blink and armed notice. Simulation time drives postflight timeout; accepted armed duration comes from the scene. Off still derives flight values and schedules drawing work. Preserve baseline behavior during extraction, then implement the plan's explicit presentation clock and hidden-work contract separately.
6. **Energy semantics differ from the aircraft widgets.** The drone directly displays supplied pack SOC/current/consumed charge and uses fixed cell thresholds. The [controlled plant](../../../app/physics/multirotor/controlled_plant.gd), `telemetry`, omits electrical fields for its ideal-supply law. The universal layer must distinguish simulator truth from radio-style observations and estimates, with declared chemistry/source support.

The [model](../../../app/vehicles/multirotor/osd_model.gd), [HUD](../../../app/vehicles/multirotor/multirotor_hud.gd), [painter](../../../app/vehicles/multirotor/osd_painter.gd) and [OSD tests](../../../app/tests/test_mr_osd.gd) support these source-level observations. They are not claims of reproduced visual bugs or performance measurements.

The official [INAV OSD reference](https://inavflight.net/docs/core-features/osd/) confirms that character and canvas capabilities and grids vary by video system; the [ArduPilot OSD reference](https://ardupilot.org/copter/docs/common-osd-overview.html) documents configurable screens and panel units. Their current text is context, not a replacement for the selected source/backend fixture. Godot's [custom drawing guide](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html) and [CanvasItem reference](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html) explain retained draw commands and queued redraws. They support preserving static/moving layers; they do not qualify performance on OpenRC's pinned engine or target hardware.

No external source or font was imported. The earlier survey records repository notices; file-specific terms still govern later reuse. In particular, INAV `osd_grid.c` offers MPL-2.0 or GPL-3.0-or-later alternatives, while related OSD files carry GPL notices. Asset terms are separate.

## 4. Decisions integrated into the execution plan

The authoritative [OSD contracts](../../plans/universal-fpv.md#35-osd-profiles-and-projection) and existing packets now require:

- An explicit reusable pipeline: admitted observations → element evaluation/formatting → profile/screen layout → selected canvas/character renderer. The editor uses the same evaluated state, font/glyph choice and composition for identical inputs.
- Registry requirements and dependencies, explicit G/efficiency/speed kinds, shared source/pack observers, and demand ownership for optional histories. Visibility does not create or reset essential observations.
- A legacy-preserving extraction before separately reviewed semantic/profile changes; complete monochrome validation and reference-specific glyph/grid treatment for new profiles.
- Deterministic screen/override rules, persistent warnings separate from expiring messages, critical presentation through summary/screens, and family-owned flight/trip aggregates without duplicate statistics credit.
- Dirty invalidation for content shrink, move/hide, source availability, old/new footprints, overlap restoration, profile/grid/font/palette/unit/locale/scale/viewport changes; bounded caches with explicit teardown.
- A two-dimensional editor footprint and honest live-preview parity, visible unsupported elements, safe migration of the dedicated drone configuration, retained unsaved edits and direct-route isolation.
