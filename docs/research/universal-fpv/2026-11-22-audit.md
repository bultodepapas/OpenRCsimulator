# Universal FPV source audit and reference register

**Date:** 2026-11-22. **Repository:** `bultodepapas/OpenRCsimulator`. **Pinned source:** `7940a4081e10994f34c858c4acac3d7a1a271464`, verified against remote `main` before the planning branch was created. **Scope:** read-only runtime/source and primary-document review. No Godot sessions, device tests, captures or performance tests were run for this audit. The [implementation plan](../../plans/universal-fpv.md) owns pending steps and acceptance.

## 1. Findings that change the design

1. FPV is present on the multirotor route, including a substantial OSD. Universal FPV and a camera gimbal are the missing features. The transmitter widget's live stick “gimbals” are unrelated to a camera mount.
2. Fixed-wing and helicopter reuse `CameraRig`, but the drone, cars and airship retain separate camera owners. Generalize the pose/mount helpers and lifecycle contract; a second camera update loop would create conflicts.
3. Existing drone OSD is a documented Betaflight/INAV-style mixture. It is not separate, selectable INAV and ArduPilot implementations. Its scalar uptilt and body-attitude inputs do not describe an independently moving three-axis camera.
4. Flight widgets provide useful calculations, alerts, layouts and persistence, but their manager's snapshot directly assumes `session.aircraft`, fixed-wing air/wind observations, radio/trims and fixed auxiliary slots. A shared adapter is necessary before reuse on other families.
5. Current drone height is AGL; ArduPilot's normal OSD altitude panel is home-relative. Both are valid measurements with different meanings. Current model truth, observed battery data and external sensor telemetry also need separate provenance.
6. Camera settings currently live in `display.cfg`, while normal HUD settings use the existing preferences owner and the drone has its own OSD file path. The old camera plan's proposed storage text must not be mistaken for current code.
7. Camera history reset, crash focus and listener handling already have owners. Generalization must preserve final-pose ordering, family pause semantics and the single authoritative physical state.

## 4. Primary reference register

All sources were accessed on 2026-11-22. Statements below are paraphrased. Exact firmware/configurator tags and source hashes are implementation inputs for CAM-FPV-00d; the current live docs are not a promise of parity with every version or device.

| ID | Primary source | What it supports and limits |
| --- | --- | --- |
| S1 | [INAV OSD](https://inavflight.github.io/docs/core-features/osd/) | Official project site served version 9.1.0. Character-based positioned elements, distinct analog/HD grids and capability-dependent elements. PAL is 30×16 and NTSC 30×13; HD grid dimensions depend on the video system. |
| S2 | [INAV standard flight modes](https://inavflight.github.io/docs/core-features/flight-modes-standard/) | Default and ALT1/ALT2/ALT3 OSD screens and OSD switching behavior. Camera/OSD selection and vehicle control modes have distinct purposes. |
| S3 | [ArduPilot OSD overview](https://ardupilot.org/copter/docs/common-osd-overview.html) | Positioned panels, multiple screens, unit systems including aviation; altitude above home, groundspeed versus airspeed, home, attitude, optional sensor panels, warning/statistics options. Firmware/build/backend qualifications apply. |
| S4 | [ArduPilot DisplayPort OSD](https://ardupilot.org/copter/docs/common-displayport.html) | MSP DisplayPort transports text/icon drawing instructions. Receiving telemetry and rendering a native OpenRC overlay is a different integration claim. |
| S5 | [ArduPilot mount controls](https://ardupilot.org/copter/docs/common-mount-targeting.html) | Body/earth frame locks, horizon/FPV behavior, yaw follow/lock, angle/rate RC input and control-source concepts. Some modes/options depend on mount type or firmware. |
| S6 | [ArduPilot servo gimbal](https://ardupilot.org/copter/docs/common-camera-gimbal.html) | Mount orientation, neutral and axis/travel configuration. Reference concepts for a simulated mount, not evidence for a specific hardware response. |
| S7 | [ArduPilot MAVLink gimbal control](https://ardupilot.org/dev/docs/mavlink-gimbal-mount.html) | Version-dependent mount commands, angle/rate targeting, ROI and gimbal-control integration. Relevant to optional interoperability, not required for a visual profile. |
| S8 | [MAVLink common messages](https://mavlink.io/en/messages/common.html) | Fields distinguish airspeed/groundspeed, heading/course and altitude references, with unknown-data sentinel rules. A normalized internal telemetry contract must preserve those meanings. |
| S9 | [INAV next-version HUD/craft radar](https://inavflight.github.io/docs/next/advanced-features/osd-hud-and-craft-radar/) | Camera uptilt/FOV and projected HUD concepts. The URL is explicitly `next`; use as design research only until a stable reference is pinned. |

The proposal to keep vehicle attitude and actual camera pose separate, project markers through the rendered optical geometry and add one capability-aware adapter layer is an OpenRC architectural inference from these sources and the inspected code. It is not a claim that upstream OSDs universally compensate arbitrary gimbals.

## 5. Ownership, dependencies and review disposition

- [Camera plan](../../plans/camera-views.md): CAM-11 onboard view, CAM-13 mount contract, CAM-12 optional lens warp, CAM-16 listener and existing cut/clearance work remain authoritative seams.
- [Flight overlays](../../plans/flight-overlays.md): widget, alert, unit and settings ownership is reused.
- [Drone racing](../../plans/drone-racing.md): DR-31 implementation and its later OSD work are existing inputs; DR retains controller/race/quad semantics. Older FPV handoff descriptions do not override the current implementation.
- [Architecture](../../STACK.md), [decisions](../../DECISIONS.md) and [aircraft contract](../../AIRCRAFT_CONTRACT.md): one accepted physical state, 240 Hz float64 kernel, explicit per-family validation, and model datum/source identity remain unchanged.
- Parallel firmware-integration and vehicle-system-unification work is a coordination dependency, not assumed merged functionality. This plan uses narrow adapters and does not require either initiative to finish first.

Review accepted the common pose/telemetry/profile split and rejected copying the complete drone HUD into every activity. Independent review tightened the release gate to every currently flyable catalog entry, identified the ground session's final-acceptance boundary and separate interpolated basis, required committed-event observation apart from 10 Hz formatting, preserved fixed-eye calibration and family defaults, made the stock mount fixture and gimbal-projection dependencies explicit, retained CAM's crash fallback and corrected the near-plane evidence wording. The lead checked those points against the original source and incorporated them. The remaining integration risks have explicit phase gates and acceptance cases in the plan. Runtime verification, physical fidelity and target-hardware performance remain pending.

## 8. Aircraft positions and cockpit presentation

The [aircraft-by-aircraft audit](2026-11-22-aircraft-camera-mounts.md) reviews all 8 selectable airplanes and 3 hidden technical Stik configurations, their active manifests/builders, cabin/glass and fixed-tail evidence, propulsion clearance and source generation. Existing Turbo Lumber exterior captures establish its cabin shape; they do not qualify an inside view. The target is front/cockpit/tail for Extra, P-51, Corsair, Vantage and Turbo Lumber, with front only for cabinless Stiks and the X99. The legacy X8 alias keeps separate presentation coverage without becoming another aircraft.

The [mount contract](../../plans/universal-fpv.md#32-mounts-frames-and-optical-geometry) now includes the required stock position matrix, fixed-fin tail attachment, body-fixed cockpit eyes, two-axis yaw/pitch, clear/realistic glazing, instance-local material/visibility restoration and per-mount settings. Usable cockpit structure is now included in delivery; interactive cockpit controls remain separate. Shared OSD observations/alerts/statistics survive mount changes, while projection uses the new actual lens. The same 38 packets gain source-specific preparation and qualification gates. No lens coordinate, newly rendered cockpit, runtime implementation or performance result is claimed by this planning update.
