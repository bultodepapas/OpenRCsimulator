# DLSS and AMD FSR integration investigation

2026-10-24 · VQ-07d source and integration audit. Research only; no runtime changes, vendor builds or new GPU measurements. The [advanced graphics plan](../../plans/advanced-graphics.md) owns implementation and acceptance. This supplements the [original vendor audit](README.md#vendor-claims-and-corrections).

## Recommendation

Evaluate stock FSR 2.2 in the existing experimental High profile first. Keep Standard available. Investigate NVIDIA DLSS Super Resolution separately using the vendor engine fork, without coupling that experiment to path tracing or frame generation. Reuse the available implementations; do not write a new upscaler.

No performance improvement is established. The [High diagnostic](../visual-quality-implementation/VQ-07/high-followup-2026-10-21/README.md) measured GPU p95 4.974 ms and wall p95 18.307 ms in its workload; that did not demonstrate a GPU bottleneck. Upscaling is unlikely to fix CPU, loading or presentation pacing limits. Repeat attribution on the intended hardware and scene before adoption.

## What is available

| Technology | Verified availability | Implication for OpenRC |
| --- | --- | --- |
| AMD FSR 2.2 | Built into stock Godot Forward+; suitable GPUs across vendors; temporal reconstruction and AA | Lowest integration cost; no extra SDK, plugin or engine fork. |
| NVIDIA DLSS Super Resolution / DLAA | NVIDIA's Godot fork exposes DLSS scaling and native-resolution DLAA | Separate custom engine and matching export templates; RTX capability detection and fallback required. |
| AMD FSR 3.x / FSR 4.x | External SDK components, distinct from Godot's built-in FSR 2.2 | Engine/render integration investigation; selecting FSR2 does not enable newer FSR or frame generation. |
| DLSS Frame Generation | Streamline has a separate integration and capability query | Additional presentation, latency, HUD and lifecycle work; not implied by working DLSS Super Resolution. |

Godot's [4.7 scaling documentation](https://docs.godotengine.org/en/4.7/tutorials/3d/resolution_scaling.html) requires Forward+ for FSR1/FSR2. FSR2 supplies temporal AA; separate TAA is ignored. Its [AA guide](https://docs.godotengine.org/en/4.7/tutorials/3d/3d_antialiasing.html) describes cross-vendor support and the extra cost of FSR2 at native resolution. A stock Compatibility FSR2 selection is not a valid implementation.

## First bounded candidate: FSR 2.2

After High is active, the stock [Viewport API](https://docs.godotengine.org/en/4.7/classes/class_viewport.html#enum-viewport-scaling3dmode) allows this illustrative main-view configuration:

```gdscript
# Research example only; not integrated or executed by this audit.
if RenderingServer.get_current_rendering_method() == "forward_plus":
    var viewport := get_viewport()
    viewport.msaa_3d = Viewport.MSAA_DISABLED
    viewport.screen_space_aa = Viewport.SCREEN_SPACE_AA_DISABLED
    viewport.use_taa = false
    viewport.scaling_3d_mode = Viewport.SCALING_3D_MODE_FSR2
    viewport.scaling_3d_scale = 2.0 / 3.0
```

Disabling additional AA here isolates the first candidate; it is not a claim that MSAA is forbidden. A real integration must restore the saved native AA settings when reconstruction is disabled, handle unsupported renderers explicitly, and apply consistently to Home-launched and direct-flight sessions. Scale only the main 3D view; retain UI resolution and avoid automatically changing lake, shadow or preview subviewports.

Proposed comparisons at a **1920x1080 output**:

| Candidate | Internal 3D resolution | Purpose |
| --- | --- | --- |
| Standard native / existing AA | 1920x1080 | Shipped renderer control |
| High native / existing AA | 1920x1080 | Isolate renderer cost |
| High FSR2, scale 1.0 | 1920x1080 | Temporal AA quality and overhead |
| High FSR2, scale 2/3 | 1280x720 | Quality reconstruction trial |
| High FSR2, scale 0.5 | 960x540 | Stress test, not a proposed default |

An internal 720p buffer reconstructed to a real 1080p output is a 1080p-output experiment; running the window at 720p is not. Evaluate 1440p/4K next and 720p output last. For RC flight, lower input resolution may erase attitude cues from small distant aircraft; judge moving silhouettes, not just scenery sharpness.

## NVIDIA route: reuse the engine fork

The inspected [`nvidia-pt-dlss` branch](https://github.com/NVIDIA-RTX/godot/tree/135dff3887a3d2ccf45cafbd9bdffa7b718e1e76) resolved to commit `135dff3887a3d2ccf45cafbd9bdffa7b718e1e76`. Its [`version.py`](https://github.com/NVIDIA-RTX/godot/blob/135dff3887a3d2ccf45cafbd9bdffa7b718e1e76/version.py) reports **4.8.0-dev**, not this project's 4.7.2. The repository's [release page](https://github.com/NVIDIA-RTX/godot/releases) had no packaged releases at inspection.

Source evidence at that commit:

- [`SConstruct`](https://github.com/NVIDIA-RTX/godot/blob/135dff3887a3d2ccf45cafbd9bdffa7b718e1e76/SConstruct) defines `use_streamline`.
- [`Viewport.xml`](https://github.com/NVIDIA-RTX/godot/blob/135dff3887a3d2ccf45cafbd9bdffa7b718e1e76/doc/classes/Viewport.xml) exposes `SCALING_3D_MODE_DLSS`, including scale 1.0 for DLAA. This enum is fork-specific and must not be referenced unconditionally by scripts parsed on stock Godot.
- [`streamline_context.cpp`](https://github.com/NVIDIA-RTX/godot/blob/135dff3887a3d2ccf45cafbd9bdffa7b718e1e76/drivers/streamline/streamline_context.cpp) loads `sl.interposer.dll` under `_WIN32`, selects Vulkan/D3D12, and queries individual DLSS/FG/Reflex capabilities. This supports a Windows-first investigation, not a portable-export claim.
- [`dlss.cpp`](https://github.com/NVIDIA-RTX/godot/blob/135dff3887a3d2ccf45cafbd9bdffa7b718e1e76/servers/rendering/renderer_rd/effects/dlss.cpp) contains renderer-level reconstruction integration and optimal-mode queries. Copying DLLs into stock Godot cannot supply those engine changes.

Proposed execution: pin a disposable vendor checkout and matching Streamline package; build its editor and export templates; first establish raster Forward+ parity with DLSS/FG/path tracing off; then enable Super Resolution on a supported RTX adapter and compare against native and FSR2. Keep the production engine pin intact. Treat rebase/backport and ongoing custom-export maintenance as separate costs. The existing [engine upgrade plan](../../plans/godot-4.8-upgrade.md) remains relevant to any production engine change.

[Streamline 2.14.16](https://github.com/NVIDIA-RTX/Streamline) provides binaries through release ZIPs; the DLSS-G plugin is binary-only. Use a version compatible with the fork, retain artifact hashes and component license/redistribution terms, and ship the required production runtime files beside the exported executable. Current upstream Streamline and the fork's bundled headers are not automatically a validated pair. Check application identity configuration before release.

A bespoke native extension remains a higher-risk alternative until it proves access to the required renderer buffers and scheduling. DLSS consumes image/history inputs such as depth, motion vectors, jitter and exposure; this is not a screen-only sharpening shader. Prefer the already implemented engine integration. [NVIDIA integration guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS.md)

## Newer AMD components and frame generation

AMD's [FSR SDK 2.3.0 README](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/main/readme.md) lists separate FSR 2.3.4, 3.1.5 and ML upscaling 4.1.1 components. Despite its broad introductory wording, its known-issues table says Vulkan is currently unsupported in that SDK. The [SDK requirements](https://gpuopen.com/amd-fsr-sdk/) list DirectX 12 / Windows and component-specific GPU support. Therefore do not infer FSR4 Vulkan availability from the SDK name, from older FSR3.1 Vulkan documentation, or from driver/mod announcements. Recheck an exact released SDK before scheduling that path. FSR4 is not simply a replacement DLL for Godot's embedded FSR2 implementation.

The [current DLSS-G guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md) documents both D3D12 and Vulkan integration. It requires suitable depth, motion and HUD-separated buffers plus presentation synchronization and Reflex integration. It also specifies disabling FG during pauses, menus, loading and display transitions. Dynamic Multi Frame Generation and VSync with FG retain D3D12 restrictions in the inspected guide. SDK capability does not prove the Godot fork handles all OpenRC transitions.

Keep FG off for the first comparison. Generated frames do not add simulated states or fresh control samples. Report rendered FPS and displayed FPS separately, and measure control-to-display latency before considering adoption. Ray reconstruction and neural rendering address different problems and are unnecessary for the initial raster upscaling experiment.

## Acceptance evidence before integration

Use the existing [graphics tools](../../tools/graphics.md#frame-diagnosis), [debug bridge](../../../tools/debug/README.md), and [flight logging workflow](../../FLIGHT-LOGGING.md); do not create a competing benchmark harness.

1. Record exact engine/driver/GPU, renderer/API, output and internal resolutions, AA, VSync/cap, aircraft, landscape and optional reflections. Use the same input tape and camera path; verify complete exact replay independently of image quality.
2. Capture matched moving flight: distant aircraft attitude/markings, fast pans and camera cuts, propeller/rotors, smoke, wind-driven vegetation, water, night lights and HUD. Inspect temporal trails, flicker and disocclusions. Static screenshots alone cannot qualify reconstruction.
3. Measure native GPU and CPU/wall frame times, p50/p95/p99, VRAM, warmup and cold-start hitches across repeated runs. Separate renderer overhead from reconstruction benefit. Stop performance adoption when the workload is not GPU-limited or complete-frame results do not improve.
4. Exercise settings Keep/Revert, resizing, fullscreen, pause/resume, restart, activity switches and shutdown. Test GPU/driver/runtime-unavailable fallback. Verify Windows export first for the vendor fork; retain stock fallbacks and qualify Linux/macOS separately.
5. Apply the owning plan's visual/performance gates at 1080p first. Preserve simulation/replay checks and never substitute generated-frame FPS for flight responsiveness.

Open questions: target GPU inventory; quality of motion vectors for shader-driven vegetation/water and procedural aircraft parts; matched 1080p cost; vendor-fork export stability; component packaging; and pilot preference for distant aircraft readability. These require experiments, not additional marketing comparisons.

## Follow-up: practical FSR2 controls (2026-10-24)

The owner requested more options and further Internet research after integration.
The [operating guide](../../../tools/graphics/README.md#fsr2-reconstruction-vq-07d)
now owns the implemented controls; the initial example above remains historical.

AMD's [FSR2 2.2.1 integration guide](https://github.com/GPUOpen-Effects/FidelityFX-FSR2/blob/v2.2.1/README.md#scaling-modes)
specifies Quality 1/1.5, Balanced 1/1.7 and Performance 1/2 per axis and recommends
a sharpening slider. We added Balanced/Performance plus a separately named custom
85% trial. Ultra Performance remains omitted: at 1080p its 640×360 input is a poor
starting point for small-aircraft readability. This last assessment is an OpenRC
engineering judgment, not measured visual qualification.

Godot's [4.7 scaling guide](https://docs.godotengine.org/en/4.7/tutorials/3d/resolution_scaling.html)
explains that lower input resolution primarily helps GPU-limited workloads and
that FSR2 already supplies temporal AA. Its sharpening control runs in the opposite
direction to the user-facing strength. The pinned
[4.7.2 Forward+ caller](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp)
converts it to SDK strength with `1 - fsr_sharpness / 2`. Thus our 0–1 slider maps
to Godot 2–0, preserving its 0.2 default at user strength 0.9. The same caller fixes
`reset_accumulation` to false with an engine FIXME: camera-cut history needs explicit
motion testing, and a normal camera transform change cannot be advertised as an
FSR2 history reset.

The [4.7.2 FSR2 wrapper](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/effects/fsr2.cpp)
disables sharpening when SDK strength is zero. It supplies a reactive texture, but
leaves transparency/composition empty and automatic reactivity disabled. This is
an engine integration boundary, not a missing game-menu checkbox. Smoke, water
and rotating translucent parts remain mandatory motion cases before considering
an engine change. No engine fork or replacement SDK was introduced.

The [4.7 Viewport reference](https://docs.godotengine.org/en/4.7/classes/class_viewport.html#class-viewport-property-texture-mipmap-bias)
documents automatic scale-dependent mip bias in addition to `texture_mipmap_bias`.
Do not copy AMD's full absolute bias formula into that additive property: it would
double-count the scale term. Leave the additional bias unchanged until matched
moving-texture captures demonstrate a need. More negative bias can increase grain
and shimmer.

Dynamic resolution remains research, not a per-frame scale script. The inspected
engine creates the FSR2 context with internal/target sizes and frees it with render
buffer data. Allocation, history continuity and GPU timing feedback must be measured
before implementing a controller; resolution changes alone do not establish smooth
dynamic scaling. Frame generation is separate from FSR2 reconstruction.

### Follow-up: buffer lifetime and capture history

The pinned [Viewport renderer](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_viewport.cpp)
routes changed scale and sharpness through `_configure_3d_render_buffers`.
[RenderSceneBuffersRD::configure](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/storage_rd/render_scene_buffers_rd.cpp)
calls `cleanup`, which frees custom render data, including the Forward+ FSR2 context.
This confirms a reason to avoid naive per-frame dynamic scaling in this engine.
The game now coalesces pointer sharpness dragging into one application on release;
keyboard steps remain immediate. Unchanged properties already short-circuit in the
scene Viewport, so no extra game-side cache is needed.

The same buffer source applies another -0.5 mip offset for temporal scaling,
including FSR2 even with `use_taa=false`. Combined with automatic scale bias,
Quality's zero additional bias is approximately -1.085, not zero effective bias.
An extra negative offset is a separate texture-detail experiment, not a free fix.

[Microsoft's FSR integration sample](https://learn.microsoft.com/en-us/samples/microsoft/xbox-gdk-samples/amdfidelityfxsuperresolution/)
also distinguishes a dynamic-resolution implementation with maximum-size resources
and per-dispatch render dimensions from simply resizing the engine viewport. Its
mask controls are integration examples, not exposed stock-Godot settings.

OpenRC's static capture previously waited two drawn frames after setting its final
pose. FSR2 captures now wait at least two jitter cycles for supported scales,
bounded at 64 frames (Native AA 16, Quality 36, Performance 64), with the existing
capture simulation/visual clock held. This is a capture-history allowance, not a
proof of convergence or moving-image quality. Native captures retain two frames.
The manifest records the wait count and full reconstruction configuration.

### Next targeted quality/performance investigations

1. **Moving shader geometry.** OpenRC's `near_grass.gdshader` deforms vertices with
   custom global `sim_clock` and `wind_vec`. The pinned
   [Forward+ shader](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered.glsl)
   invokes previous/current vertex paths with previous/current engine time, while
   material/global uniforms remain shared inputs. Inference: custom-clock wind
   deformation may lack its previous-frame delta in motion vectors. Test the motion
   vector debug view and matched windy captures before attributing visible trails.
   Preserve the deterministic clock contract; replacing it with `TIME` would break
   capture/replay requirements and is not an acceptable shortcut.
2. **First-use stalls.** The [4.7 pipeline compilation guide](https://docs.godotengine.org/en/4.7/tutorials/performance/pipeline_compilations.html)
   identifies motion vectors and MSAA changes as pipeline triggers. Measure cold
   first activation separately from steady-state FPS, using existing compilation
   monitors. Saved FSR should be active before loading flight resources; warmup must
   not silently remove a player-visible first-use hitch from acceptance evidence.
3. **Sharpening cost versus appearance.** Compare RCAS off against a fixed nonzero
   strength in Native AA and Quality; all nonzero strengths still enable the pass.
   A lower nonzero strength is not evidence of proportionally lower GPU cost. Judge
   oversharpening on the aircraft and vegetation, not just static terrain textures.
