## Finding that changes the previous plan

AMD released **FSR SDK 2.4.0 on October 28, 2026**. The exact tag resolves to `7539ae8b6568ad29ed78a753404351daf3b5cca7`. Its release adds Vulkan upscaling and frame generation, so the earlier SDK2.3 DX12-only restriction must not be reused as a current blocker. SDK version, effect version, driver-provided version and Godot version are separate identities. The old audit remains historical. [Release](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/releases/tag/v2.4.0).

| ML / analytical FG | 4.0.2 / 3.1.6 | Separate presentation integration, not enabled by upscale selection |

## Hardware, driver and distribution distinctions

AMD's current release announcement expands ML upscale to RX6000/7000/9000 discrete GPUs and explicitly enumerated Ryzen AI Max/AI9/Z2 families. It describes full and smaller models selected by hardware. Do not translate that into all Radeon integrated graphics. NVIDIA/Intel analytical fallback is not ML execution. ML FG remains RX9000-class and Windows11-specific. Record hardware support separately for each effect; the SDK number alone proves none of it.

There is a source conflict: the SDK landing page requires Adrenalin 26.10.1+ for new APU/Vulkan upscaling, while the October28 announcement says shipped SDK DLLs need no specific driver version for those features. Use 26.10.1+ as the conservative initial **qualification baseline**, not an asserted universal hard minimum. Query capabilities, retain the discrepancy and test older drivers separately before advertising them. Driver-assisted pacing has its own explicit 26.10.1+ requirement and presentation/VRR conditions. This research did not settle the upscaler driver-minimum conflict.

The API supports driver-provided implementations and exact-version override. Log the provider version/origin actually used, not just the packaged DLL. Explicit overrides opt out of automatic upgrades for the context. This is relevant to reproducibility and the project's exact dependency policy. [API source](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/v2.4.0/Kits/FidelityFX/docs/getting-started/ffx-api.md).

Use AMD's signed distribution for the new path. Existing locally compiled/unsigned SDK1.1.4 runtime fixes do not establish compatibility with 2.4. The license has a binary-only default plus an MIT exception list, including entries under `signedbin` despite a source-files heading. Preserve exact license texts and component provenance; do not resolve that wording by asserting unrestricted source availability. Package notices and redistribution treatment must be verified during intake. No license conclusion beyond the cited text is made here.

FG replaces presentation infrastructure: correct render inputs alone are insufficient. The mandated ML FG sequence is configure, PrepareV2 dispatch, then FG dispatch. SDK2.4's special PresentMon frame-type reporting is DX12-only; Vulkan metrics need another verified route. AMD's real-input-frame recommendations are guidance, not OpenRC acceptance; existing real-frame and latency gates remain. [Announcement](https://gpuopen.com/learn/amd-fsr-sdk-2-4-rx-6000-ryzen-apus/), [swapchain integration](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/v2.4.0/Kits/FidelityFX/docs/techniques/frame-interpolation-swap-chain.md).

### VQ-07d-FSR-02/03: candidate and software checks

The shared application reset submission now covers FSR2, FSR3 and DLSS when the engine explicitly reports the provider. The custom [FSR history patch](../../../tools/graphics/native/fsr_history_reset.patch) carries a viewport generation to the per-view FSR2 contexts and to FSR3 dispatch; successful callbacks acknowledge it. Without explicit FSR reset support, the application records the notification but declines submission; existing stock FSR2 behavior remains available and is not qualified for this reset contract. These are source and software checks, not rendered proof of temporal correctness, previous matrices or Vulkan synchronization.

The isolated SDK 2.4 [adapter](../../../tools/graphics/native/fsr3.cpp) and [builder](../../../tools/graphics/native/build_sdk24.py) stage signed loader/upscaler DLLs and matching headers in a separate cache. Candidate-only `OPENRC_FSR_IMPLEMENTATION=analytical|ml|auto` defaults to analytical 3.1.6; `ml` requests 4.1.2 and `auto` permits SDK selection. Explicit selection uses enumerated IDs, checks the created provider ID and fails closed for unsupported required resources or a missing required reactive mask. These are implementation paths, not observed provider availability. AMD's loader may reuse an already-loaded effect DLL by name; checking for a file beside the executable and querying a provider ID does not prove the loaded DLL's bytes.
