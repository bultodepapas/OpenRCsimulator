Frozen candidate `openrc-r11-b09-r05b-20261015-07` fails the Windows Godot export because its declared Windows GDExtension path has no DLL. The export log reports the missing `app/native/ground_vehicle/openrc_ground_vehicle.dll` at line 1280; the same candidate contains its Linux library and an unchanged descriptor with both platform paths.

The locally retained Windows artifact is the older, matching native v2 / solver v3 build. Its SHA-256 is `adafd1f9682dff147e538fdb7686329c009edf255c639789ac28dc403bc6e65c`. Its original receipt identifies ABI 1, `openrc-ground-vehicle-native-evaluate-v2`, `openrc-ground-vehicle-dynamics-rk4-v3`, and native source SHA-256 `e2ae0a5ffebc8d81636302d66238348035ee92bf51d2f40965db7053bb251541`, which matches frozen-07. The digest covers the frozen `ground_vehicle_native.cpp` and `ground_vehicle_kernel.hpp`; their individual hashes also match the retained v2 build-input record. The lock-file SHA is `4926d2b141bf32d6776b372b36a7fe67e5007813004c4bcfc197a6f2a4aba4a6`, and its godot-cpp commit, MSVC/SDK versions and flags match the Windows receipt. The retained Windows parity log reports 50 passing checks with Godot 4.7.2.

I copied that DLL byte-for-byte into the task-owned staging tree and copied its original Windows receipt and parity log beside it. The original isolated native build-input verification, frozen-07 Linux receipt, lock and extension descriptor are also retained there as inputs. [manifest.json](manifest.json) records their hashes, platform identities, source hashes and origins. Nothing in frozen-07 or `app/native/ground_vehicle/` was changed; the stage contains separate platform receipts and does not fabricate a new aggregate receipt or edit the descriptor.

The old Windows receipt's toolchain fingerprint differs from a recomputation using the frozen-07 shared-builder file hash. The v2 build-input record identifies the historical shared builder as `2d866420…`, while frozen-07 contains `a41a0e1d…`; the lock, native builder, native sources and parity harness match by SHA-256, and the two shared-builder files have identical executable Python ASTs when their module docstrings are excluded. Recomputing with the historical builder hash reproduces the retained Windows toolchain SHA exactly; using the frozen-07 builder hash produces `36095eb2…`. This records the historical build provenance accurately rather than relabeling the binary as a new build.

The receipt's Visual Studio label is `18.9.12128.139`; the repository already records this product-version versus toolset/SDK distinction. No native rebuild or Windows export was run for this staging task. The newer cached DLL is excluded because it is native v3 / solver v5 and was built from a different source SHA.
