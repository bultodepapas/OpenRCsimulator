# Telemetry audit, second pass: operator data paths

**Review date:** 2026-11-22. **Source baseline:** [`7940a4081e10994f34c858c4acac3d7a1a271464`](https://github.com/bultodepapas/OpenRCsimulator/tree/7940a4081e10994f34c858c4acac3d7a1a271464). This is a bounded follow-up to [the first operational audit](operations.md), focused on private GitHub import, source freshness, GA4 validation and archive scaling. It reports two conditional defects, one defensive validation gap and one optimization opportunity. It does not repeat the first-pass findings or treat the latter two as observed production failures.

The counterexamples use disposable SQLite databases and fake GitHub/GA4/SSH responses. They do not contact the deployed receiver, GitHub, Google, SSH hosts or production databases. Fixture dates and counts below are synthetic. The portable [operations probe](../../../../research/telemetry/audit-2026-11-22/round2/evidence/operations-result.json) and [captured result](../../../../research/telemetry/audit-2026-11-22/round2/evidence/operations-result.json) retain the reproduction and its output. They establish code behavior for the constructed inputs, not the deployed version, service schedule, incident frequency, available disk or real-world latency.

## TA22-R2-F03 — Medium: an overlapping public observation discards private community data with a successful task result

**Trigger and impact.** During a private workstation collection, the container may finish a public community collection between the private community collection's start and finish times. The importer intentionally skips that private community observation. The public observation can update public counters and the release catalogue, but it does not contain the private referrer list, popular paths or star-day history. These private series therefore retain their earlier values even though the operator just obtained newer ones. If all three private sources were collected, the push still returns exit status zero; it prints the imported source names but does not indicate that an overlap discarded private community data or request a retry.

The [importer](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/deploy/sync_private_github.py#L168-L199) checks the last public completion against the private start and finish, while the [push result](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/deploy/sync_private_github.py#L241-L263) is based on how many sources were *collected*, not the reasons for non-import. The [public collector](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/analytics/github_history.py#L213-L225) omits private lists, and its [save path](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/analytics/github_history.py#L342-L363) replaces stars and private lists only for a private observation. The archive [tracks private referrer and star-history timestamps separately](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/github_archive.py#L209-L220).

**Offline counterexample.** A prior private referrer count is `1`, the newly collected private count is `14`, and the public observation completes inside that private collection. The real importer, driven through a fake SSH transport, accepts `traffic` and `clones` but discards `community`. The push prints `Imported private GitHub sources traffic clones` and returns `0`; the stored private referrer remains `1`, and its observation timestamp remains `2026-11-21T21:00:00.000000Z`. No real GitHub request or SSH connection occurs.

**Qualification and acceptance.** The overlap check protects an important ordering invariant: simply writing the whole older private catalogue over public data would risk losing a newer public release view. An already-superseded private observation can also be a legitimate successful no-op. The issue is that these distinct outcomes are not conveyed as such and private-only updates can be lost. Existing private-source freshness checks eventually flag the old observation after the documented [twelve-hour budget](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/deploy/README.md#L66-L76); this finding does not say they remain healthy indefinitely.

Return an explicit per-source result distinguishing imported, superseded and overlap-discarded data, and retry or visibly surface the last outcome. Alternatively, safely merge independently ordered private-only data without replacing a newer public catalogue or counters. Test the overlap with changed private referrers, paths and stars; confirm public release state never regresses, an incoming private observation already superseded by a newer stored private observation remains a successful no-op, and an overlap cannot appear as a wholly successful refresh without a retry or actionable indication.

## TA22-R2-F05 — Medium: a stale receiver freezes the overview window for fresh GA4 data

**Trigger and impact.** Dashboard builds can read an old receiver snapshot and independently collect current GA4 data. The overview derives its common clock from the receiver's `generated_unix`, then computes the GA4 comparison window using that stale clock. A sufficiently old receiver snapshot selects GA4 dates outside the newly fetched report, so current website sessions and download requests appear unavailable in the overview. For shorter outages the selected GA4 week can be unnecessarily old. This affects the comparison and chart context, not the existence of the fresh GA4 response itself.

The [overview and its initial UTC windows](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/dashboard.py#L1364-L1370) use the receiver timestamp. The [website window](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/dashboard.py#L1394-L1416) also passes it to the property-local date calculation, whereas the [build fetches GA4 separately](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/dashboard.py#L2292-L2296). The [health report](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/dashboard.py#L2179-L2202) marks the receiver `stale` beyond its configured age, so this counterexample is degraded operation with a stale warning, not a false healthy guarantee.

**Offline counterexample.** A synthetic receiver snapshot is dated `2026-12-06`; a fresh 30-day GA4 fixture spans `2026-12-17` through `2027-01-15` and identifies `2027-01-12` as the latest comparison day. The real overview chooses `2026-11-29` through `2026-12-05` for website sessions and returns `Unavailable`, coverage `0`. Both dates and the long receiver outage are fixture conditions.

**Expected behavior and acceptance.** Choose each source's comparison and display windows using an appropriate build or source collection clock, while continuing to label receiver-derived metrics with their actual snapshot time and honoring GA4's property-local timezone and provisional-day cutoff. Test a fresh receiver, a receiver stale across midnight, and one older than the GA4 lookback; confirm fresh GA4 data remains available without presenting receiver data as current. Cover successful recovery and a stale cached GA4 response separately.

## TA22-R2-G02 — Defensive validation gap: a malformed GA4 day can become an observed zero

**Trigger and impact.** The daily report parser accepts a date string that is missing from or invalid for the requested axis, and the model treats the corresponding absent non-provisional day as zero when GA4 supplied no quality flag. The code does not first validate all returned dates, detect duplicate days or check metric cardinality. A malformed or inconsistent upstream response can therefore produce an apparently observed zero rather than an unknown/error. This is a robustness gap shown with a deliberately invalid fake response; no evidence here establishes that Google actually returns such data for this property.

[Report parsing](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/ga4.py#L248-L255) zips metric values to requested metrics, and [`iso_day`](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/ga4.py#L267-L268) returns `None` for a malformed string without failing the report. The [absent-day fallback and daily map](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/ga4.py#L343-L357) and the [download map](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/ga4.py#L371-L377) then fill missing non-provisional days with zero in the absence of report-quality flags.

**Offline counterexample.** In a normal fake seven-day report, the download count for `2027-01-10` is `4`. Replacing that row's date with `bad-date` produces `0` for January 10, with no `downloads` error or report-quality flag. The correct response to this malformed input is to reject or mark the affected report unknown; the original date cannot safely be inferred from the invalid row.

**Expected behavior and acceptance.** Validate each date as a real, unique day inside the requested property-local range and verify dimensions and metric cardinalities before assigning zero to absent days. Invalid rows should produce a visible report error or quality marker and leave affected values unknown. Regression cases should cover malformed, impossible, duplicate and out-of-range dates, truncated metric arrays, genuine empty reports and provisional/quality-limited reports.

## TA22-R2-O03 — Optimization opportunity: archive reads and writes grow with all historical observations

**Evidence and cost.** Every successful asset collection records the full matching asset list for that observation in [`asset_counts`](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/analytics/github_history.py#L274-L287) through [`save_assets`](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/analytics/github_history.py#L366-L371). The dashboard's [archive loader](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/github_archive.py#L174-L202) queries the asset rows once per historical observation and rebuilds all interval results. The analytics collector's [report generator](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/analytics/github_history.py#L428-L455) separately walks those observations and asset rows again; it runs under a write transaction during [collection](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/analytics/github_history.py#L545-L548).

With three fixed synthetic assets, 20 observations produced 60 asset rows, **20 asset queries** and 19 retained intervals; 200 observations produced 600 rows, **200 asset queries** and 199 intervals. SQLite files in this small fixture were 86,016 and 167,936 bytes respectively; these sizes are not projections for a deployed archive. With a fixed number of assets, the work and stored rows grow with observations times assets. If retained assets themselves grow roughly with age, their repeated snapshots can make cumulative rows grow roughly quadratically with time. The container's [six-hour public refresh](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/deploy/ct/openrc-stats-github.timer#L1-L7) and release-triggered refreshes can both create observations.

The independent backup validator has a [128 MiB archive limit](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/deploy/host/openrc_stats_backup.py#L17-L21) and [rejects larger files](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/tools/telemetry/deploy/host/openrc_stats_backup.py#L32-L34). If archive growth ever crosses that limit, the off-host path cannot accept a new copy until the constraint or archive is addressed. No production archive size, actual latency, failure or near-term threshold date was measured.

**Expected behavior and acceptance.** Measure representative archive size, query count, elapsed time, memory, build-lock duration and backup time before choosing a remedy. Consider a bounded query or streaming pass, incremental interval materialization, or a documented compaction/retention policy. Preserve release milestones, actual observation times, matched-versus-partial interval semantics and restore compatibility. Acceptance should compare old and new outputs on additions, removals, counter decreases, long outages and historical releases; exercise a disposable backup and restore near any configured size limit.
