## TA23-F01 — Medium / P2 (conditional): dynamic internal resolution is invisible to telemetry context and frame-window boundaries

**Distinct from prior TA22-C01.** TA22-C01 concerned a changing *output/window size* whose old/new samples were assigned one context. New graphics work adds automatic **internal 3D render-scale changes at constant output/window size**, so even a fully correct window-size boundary cannot distinguish the renderer's evolving pixel workload.

**Source path.** The new [dynamic GPU-frame controller](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/app/render/flight_dynamic_resolution.gd#L51-L94) and [Compatibility fallback](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/app/render/flight_compatibility_resolution.gd#L155-L191) write `viewport.scaling_3d_scale` when their policies adapt. [AppRoot ticks this path](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/app/app_root.gd#L536-L569) during eligible fixed-wing flights. The [AppRoot telemetry context](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/app/app_root.gd#L3367-L3431) passes `window.size`, persistent graphics-profile/revision, VSync and FPS cap but not the **actual internal scale, change generation or adaptation state**. The [service's boundary key](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/app/telemetry/telemetry_service.gd#L369-L394) likewise cannot see such a change. [Wire context](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/app/telemetry/telemetry_service.gd#L587-L602) labels resolution from `window_size` and `viewport_coordinates`; that basis is **not a claim of native/internal pixels**.

**Constructed scenario, source-only.** Hold the output at 1920×1080, selected graphics configuration and `_telemetry_graphics_revision` constant. A supported controller can move from scale 1.0 (1920×1080 internal) to 0.75 (approximately 1440×810 internal), while the projected context remains identical and an in-progress 30-second cadence window is not split on that reason. Conversely, a whole new window at lower scale has the same reported output class. The number of rendered pixels decreases; frame-cadence changes can consequently be wrongly interpreted as a stable-workload comparison. There is no unbounded privacy leak from this issue because the scaling fact is currently omitted.

**Confidence / boundaries.** High in the producer/consumer omission, **conditional** on the dynamic-resolution feature being enabled and supported. We did **not** execute a Godot viewport, prove a particular adaptation actually happened, measure pixel counts/frame time in a player session, or test UI defaults. Do not infer every player experiences this. The distinction among output, drawable and internal pixels is already required by the [hardware qualification plan](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/docs/plans/telemetry/verification.md).

**Acceptance.** In an isolated qualification build, cause a known internal-scale change with unchanged `window.size`, then verify a telemetry observation boundary or a coarse, privacy-reviewed `mixed/adapting/unknown` classification that prevents pooling incomparable intervals as stable-workload samples. Cover native and Compatibility controllers, suspended/fixed/unsupported paths, adaptation start/stop, warmup, reset, screen resize and off-state collection. Preserve the closed telemetry contract, consent notice/version gating and the prohibition on raw graphics reports or unreviewed exact dimension data. Evaluate the signal's value using paired same-tape, same-hardware off/on and adaptation-enabled/disabled runs before expanding the released payload.

## TA23-G01 — Low / P3 (bounded storage-admission gap): pre-insert quota does not guarantee a post-commit live-page ceiling

**Distinct from existing TA22-R2-F04.** R2-F04 concerned a stored identical retry being rejected when quota is already exhausted. This case concerns **the last new insertion while quota still has a little headroom**: the raw store checks live SQLite pages *before* adding the new batch and dedup rows, and never checks the resulting size before reporting success.

[Current `RawStore._size` and `ingest`](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/services/telemetry/openrc_telemetry/storage.py#L152-L185) compute `(page_count - freelist_count) * page_size`, then test `>= max_bytes` before the `INSERT`. The documented [configuration](https://github.com/bultodepapas/OpenRCsimulator/blob/85fc06ff3ed0074586691c1a7fce70687ea1558a/services/telemetry/README.md) already describes the setting as the size **above which subsequent ingestion** returns 503. Therefore this is a **hard-ceiling/operational-budget qualification gap**, not proof that the implementation violates its currently documented *soft threshold*. It does not demonstrate uncontrolled growth or a full physical disk.

**Local, bounded demonstration.** [Source-equivalent SQL probe](../../../../research/telemetry/audit-2026-11-22/round3/quota_tail_probe.py) reproduces the real schema, WAL/full-sync settings, live-page calculation and precheck insertion ordering in disposable SQLite, with an 8,192-byte synthetic BLOB. On local SQLite 3.46.1, the store starts at **32,768 live bytes**; one-page headroom sets a **36,864-byte limit**. The pre-insert test passes, the insert commits one batch, and subsequent live-page accounting is **40,960 bytes**, an overshoot of **4,096 bytes**. The [machine-readable receipt](../../../../research/telemetry/audit-2026-11-22/round3/evidence/quota-tail.json) preserves the exact result. **This probe does not import the service class or pass a contract-validated HTTP batch**, so it verifies the SQL admission mechanism, not real endpoint status 202 for that constructed BLOB. No production disk use, WAL growth or performance estimate was measured.

**Acceptance / decision.** Decide explicitly whether `MAX_RAW_BYTES` is intentionally a soft admission threshold, a reserved-headroom budget or a strict durable-size ceiling. If soft, document expected single-insert overshoot, plus that live pages exclude WAL/SHM and filesystem overhead; set disk-alert headroom accordingly. If hard, add a bounded rollback/reservation policy with page-allocation tests at threshold-1, exact threshold and threshold+1 and assert final live-page size within policy, preserving transactional sequence dedup, R2-F04 identical retry acknowledgement and 48-hour raw deletion. Include contract-valid near-size ingress fixtures and transient WAL checkpoints in a receiver test. Do not reject a valid previously stored duplicate solely because quota is full.
