## TA24-F01 — Medium / P2 (conditional): missing raw database can silently replace a successful day with no data

**Source path.** [CLI rollup](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/cli.py#L189-L197) constructs a writable RawStore. [_Db._connect](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/storage.py#L44-L74) creates parent directories and connects even if the file does not exist; it creates the schema. [RawStore.records_for_day](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/storage.py#L188-L193) returns an empty list when no rows match. [run_rollup](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/rollup.py#L168-L192) still prepares no-data tables for configured exact release tags (wildcard-only allowlists can yield zero releases). [AggStore.put_rollup](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/storage.py#L318-L327) deletes the existing day's GPU, vehicle, cells, statuses and completion marker, replaces the results, and writes a new completion marker in a single transaction.

If a rollup command is invoked during the valid window with a wrong but writable raw directory, or after a missing volume is replaced with an empty database path, an intact aggregate database can lose an already-computed day. An actual healthy, empty raw database should still produce a legitimate no-data day; the gap is failure to distinguish source identity/availability from no observations. Atomic replacement prevents partial writes but does not ensure the input was authoritative. No missing production mount, accidental path, data loss or actual HTTP behavior was observed.

**Bounded offline model:** create an original raw file with 40 opaque synthetic rows and an aggregate ready marker; open a previously nonexistent wrong raw path using SQLite create-on-open, select zero records, replace the aggregate day in one transaction. The original still contains 40 rows, the wrong file is newly created, and aggregate status changes ready → no_data while release_count remains 1. The reduced model uses one representative status and a simple synthetic ready threshold, not the actual reducers or validated client bodies; see [probe](../../../../research/telemetry/audit-2026-11-22/round4/rollup_boundaries_probe.py) and [receipt](../../../../research/telemetry/audit-2026-11-22/round4/evidence/rollup-boundaries.json).

**Acceptance:** make rollup input fail closed if absent, wrong volume, invalid schema or unexpected store generation; open existing raw input without initialization side effects, and distinguish a verified empty day. Rehearse wrong path, missing mount, replacement with empty database, valid empty day, wildcard-only allowlist, and intact prior rollup; on unavailable input the prior committed aggregate must remain unchanged and the health path must expose a fixed failure category. Do not retain extra raw data, create raw backups, or treat a lower row count by itself as proof of corruption.

## TA24-F02 — Medium / P2 (conditional): eligibility is checked before the raw snapshot, not when it is acquired

**Source path.** [CLI](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/cli.py#L189-L197) samples wall time before contract loading and passes it into [run_rollup](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/rollup.py#L168-L192), which calls [check_eligible](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/rollup.py#L31-L42) once, then reads raw rows, validates/reduces and replaces the day. [Background purge](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/cli.py#L57-L69) subtracts the configured interval plus 60 seconds from 48 hours; [RawStore.purge](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/storage.py#L195-L205) deletes by receipt timestamp. Maximum supported interval 1800 seconds gives the earliest deletion of a day-start row at 47h29m, later than the 47h rollup deadline as intended. But a suspended/delayed rollup can check just before 47h, then resume its read after that first deletion. An aggregate replacement based on a partial snapshot can appear committed. Separately, [weekly closure](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/report.py#L19-L46) assumes no day can change at the end of Sunday's eligibility window; an in-flight eligible worker may still commit after it, including during report materialization (which precedes the closure check in [publish](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/publisher.py#L177-L195)). This latter race is source-only; no incorrect public issue was created.

**Model evidence:** a check at 169199 seconds (47h minus 1s) passes; the worker resumes at 170940 seconds (47h29m), after a logical 1741-second delay. A disposable SQLite purge of 40 synthetic rows (20 at day start, 20 one hour later) deletes 20 early rows; the read sees only 20. The probe does not sleep, run timers, emulate validated sessions or assert integrated CLI success. This is distinct from the prior quota-tail and numeric aggregation findings.

**Acceptance:** acquire a demonstrably complete raw snapshot before the deadline and re-evaluate eligibility at the input boundary with an injected clock; reject delayed reads without overwriting prior results. Specify whether a snapshot acquired before the deadline may commit after it. Ensure publication cannot race an outstanding final-day rollup (e.g. serialize/track outstanding work and read aggregates consistently); test barriers around check, snapshot, purge, final commit, report approval and publication. Do not extend raw retention or hold a long-lived raw reader across the deletion deadline to solve this problem; enforce bounded processing and checkpoint behavior.

## TA24-G01 — P3 operational/scaling gap: repository-wide issue scan can permanently exhaust the reconciliation budget

[GitHub.list_issues](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/publisher.py#L83-L98) scans all issue states, with no label/time filtering, in 100-item pages with MAX_PAGES=50. It accumulates every returned entry in memory; [classification](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/publisher.py#L134-L162) occurs only afterwards, skipping pull requests and non-bot authors. With 50 full pages, the function returns incomplete without checking whether the following page is empty; even exactly 5,000 visible entries cannot establish completeness. [publish](https://github.com/bultodepapas/OpenRCsimulator/blob/19e9e69dda17261a7761625958d038a646608e8c/services/telemetry/openrc_telemetry/publisher.py#L214-L229) refuses to reconcile/create on incomplete discovery unless positive conflict evidence stops it sooner. This is a deliberate safety-first limit, not a duplicate-creation defect. Over time, unrelated issues/PRs could consume that budget, leaving future publication pending, and memory/network work grows with repository history. This is a source-derived boundary, not a measurement of real repository issue count, API responses, memory or rate usage; no live issue enumeration performed.

**Acceptance:** test 4,999/5,000/5,001 synthetic entries, full final page and missing/invalid response, PR-heavy history, edited/removed labels, known-number lookup and timeout after create. Bound response memory (e.g. incremental classification) while preserving detection of every relevant conflicting or exact issue. Use trustworthy narrowing only if completeness is proven under edits/removals; never replace an uncertain search with blind POST. Surface a fixed actionable discovery-exhausted diagnostic and operator recovery path.
