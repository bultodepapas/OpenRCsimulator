## F08 — Can the present token threshold make repeated aggregate releases anonymous?

**Falsifiable question.** Given the planned `>=20` distinct temporary-session tokens per daily GPU cell and 120 eligible windows per token, is it sound to describe the result as anonymous or person-level differentially private across later releases? Would a fixed 19-versus-20 synthetic example or old-versus-new report pair reveal information under explicit auxiliary knowledge?

**Exact English discovery queries.** `OpenDP user guide contribution bounds privacy unit repeated queries sequential composition example`; `site:docs.opendp.org privacy unit "contributions" "identifier" truncate Polars`; `site:docs.github.com issue comment edit history view original edited comment history`.

**Inspected primary evidence.**

- [OpenDP, Typical Workflow](https://docs.opendp.org/en/stable/getting-started/typical-workflow.html), sections 1, 4 and 5: its example identifies a privacy unit, assumes a contribution bound, and divides an epsilon budget across three mediated releases; its `Context.compositor` enforces the example's query allocation.
- [OpenDP, Identifier Truncation](https://docs.opendp.org/en/stable/getting-started/tabular-data/identifier-truncation.html): the example assumes an individual uses at most one identifier, clips records per group, and additionally bounds how many groups that identifier affects. This is a tutorial, not a guarantee for OpenRC's data.
- [OpenDP, Thresholded Noise Mechanisms](https://docs.opendp.org/en/stable/api/user-guide/measurements/thresholded-noise-mechanisms.html): a DP threshold mechanism adds calibrated noise and uses sensitivity and privacy parameters; its threshold value alone is not the mechanism. The examples opt into `contrib`; suitability and vetting must be reviewed before any actual use.
- [GitHub, Tracking changes in a comment](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment) and [Editing an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/editing-an-issue): readers can view edit history; the issue description's history remains available unless appropriately removed. Copies can persist independently.
- Local `data-contract.md` §§ retention/publication and `reference.py::aggregate_daily_gpu`: the proposed daily count is session tokens, not distinct people; tokens rotate after restart, re-enable, day boundary or four hours and can be fabricated. Any small cell suppresses the whole table, and daily outputs include distinguishable `no_data`, `suppressed`, or `ready` status. Weekly pooling and publication are not implemented.

**Inference and applicability.** Do not call the thresholded output anonymous, k-anonymous, or DP. Whole-table suppression prevents one simple total-minus-hidden-cell calculation but does not remove all inference channels. In a synthetic counterexample, assume an observer knows there are exactly 19 eligible tokens in the only populated GPU cell and knows all other relevant contributions. An additional target token changes `suppressed` to `ready` under the current reducer; the visible result distinguishes those cases. This depends on strong auxiliary knowledge and is an illustrative threat, not proof of a practical attack on a deployed system. Separately, if two observable versions have counts 20 and 21 and all other contributions are known unchanged, subtraction reveals one additional session-token observation. A replacement report does not erase an earlier version from history or prior copies. The fixed threshold, data-dependent status, metrics and overlap among daily/weekly outputs must therefore be reviewed together.

OpenDP's assumed one-identifier-per-person model does not map to a rotating session token. The token cap is a per-token workload/disclosure mitigation, not an enforceable bound on all contributions from a person across tokens, days, groups or releases. Adding a stable identifier merely to obtain a stronger mathematical unit would change the privacy design and notice and is not recommended by this finding. A hypothetical token-level DP mechanism would need its own sound token-level assumptions and would still not establish person-level DP or Sybil resistance.

**Concrete next gate and test.** Keep initial reports private and block public automatic publication until a named disclosure reviewer signs off a written inventory of every externally observable report version, rows, values, statuses, covered day sets and correction history. A publication ledger should record immutable report key, scope, input snapshot identifier, destination, public artifact/digest, prior releases and reviewed correction decision; it must not hold session identifiers. The gate should compare a proposed output against all relevant previous visible versions and overlapping outputs under the agreed threat model, including edit history and suppressed/missing coverage. Freeze eligible daily inputs; derive weekly numbers only from already approved fixed daily outputs, and do not release a corrected or additional overlapping table until checked. This is a practical review gate, not a proof that all auxiliary-information attacks are impossible.

Add synthetic boundary tests for 19 versus 20 tokens; `no_data` versus `suppressed`; a correction exposing a 20-to-21 change; overlapping daily/weekly subsets; and changes solely to status or coverage. Tests should demonstrate the potential distinguishing observations and verify that an unreviewed second disclosure is refused. If a formal-DP option remains desirable, run a separate offline OpenDP feasibility study specifying the protected unit, enforced per-unit/per-group bounds, approved predeclared queries, noise, budget composition, utility at realistic cohort sizes, and complete-access mediation. No epsilon, delta, runtime integration or person-level guarantee follows from this investigation.

**Next research lead.** Prototype the publication ledger and a threat-model-based comparison of a frozen weekly report with a proposed correction and its GitHub edit history; compare utility and privacy assumptions with a synthetic OpenDP release.

## F09 — Can generative tests find consent, retry and malformed-input sequences missed by examples?

**Falsifiable question.** Can Hypothesis generate a sequence such as enable → enqueue → failed send → disable → re-enable → stale completion that violates the stated consent or retry contract, and can independently specified hostile payload mutations cause a rejected batch to change ingress state or leak a canary?

**Exact English discovery queries.** `site:hypothesis.readthedocs.io stateful testing rule based state machine tutorial invariant`; `site:hypothesis.readthedocs.io latest quickstart hypothesis shrinking @given strategies tests`; `site:github.com/HypothesisWorks/hypothesis releases hypothesis-python 6.170`.

**Inspected primary evidence.** [Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html) documents `RuleBasedStateMachine`, rules that can be chained, `precondition`, `invariant` after each step, bundles, and a `unittest`-compatible `.TestCase`; it shows a short reproducing sequence after a generated failure. [Hypothesis Quickstart](https://hypothesis.readthedocs.io/en/latest/quickstart.html) documents `@given` and input strategies. The [official release page](https://github.com/HypothesisWorks/hypothesis/releases) listed 6.170.15 (short commit `9ab0be6`) on the access date. This is an observed upstream version, not an installed/tested dependency or an approved lockfile pin. Check current support, transitive dependencies and project policy before adding an exact development dependency. Local `test_reference.py` already has useful individually authored consent, timeout, retry, invalid-UTF-8, nonfinite, duplicate-key, collision and backpressure examples; the proposed value is combinations and boundaries, not reproducing those tests verbatim.

**Inference and applicability.** A state machine suits interactions among valid events and old callbacks; pure payload cases fit `@given` better. The generator must compare the implementation against a small independently stated oracle or externally observable properties, not copy its conditionals. Tests use synthetic values only. The Python `ClientModel` is an offline specification: sequential simulated callbacks do not establish actual thread safety, disk persistence, Godot socket cancellation, behavior across app instances, database transactions, or a real network service.

**Concrete next tests.**

1. Generate rules for grant with valid/invalid notice or eligibility, collect, begin-send, monotonic clock advance, 202/4xx/429/5xx/timeout completions, revoke, re-enable, expire and replay a saved old `(epoch, request-serial)` completion. Track a small independent consent generation, submitted byte strings and active attempt in the harness. After every step assert: without current valid consent no probe factory is called and no new request begins; revoke immediately clears pending bytes, session and active attempt; a stale callback cannot remove a current attempt or enqueue/resurrect data, including after a fresh grant; at most one current request is active.
2. For generated retries assert that each retry of one batch sends exactly the originally previewed bytes and ID; a `Retry-After` cannot cause an earlier resend; an item at or beyond its 600-second lifetime is not sent; attempts and transmitted-byte budgets include retry attempts. Distinguish the initial attempt and the five-retry limit. Generate exact boundary times as well as values around them; keep time monotonic. Test permanence and suspension against the status classes specified in the contract, not arbitrary network status assumptions.
3. Starting from an independently known valid fixture, generate guaranteed-invalid mutations: unknown nested keys carrying a canary, duplicate decoded JSON keys including escaped spellings, invalid UTF-8, overlong bodies, excessive nesting, nonfinite numbers, booleans in integer-only fields, duplicated event sequences and impossible histogram counts. Also retain valid controls. For a rejected body, compare fake-ingress batch/event maps before and after and require no stored payload or canary in the fixed error category. Where size is the defect, verify rejection before JSON processing. Later test server logs and storage separately; the offline model has no actual log sink.
4. For valid bodies inside the stated dedup horizon, generate same-ID/same-bytes retry, same-ID/different-bytes conflict, and new-batch-ID/overlapping-session-sequence conflict. The accepted state is unchanged on retry/conflict; no claim is made beyond the horizon. Retain minimized failures as explicit regression examples after independently checking expectations. Configure bounded test duration and example count for CI; add no real secrets or live endpoints.

**Next research lead.** Implement this test-only harness in a separate reviewed change, pin a verified compatible Hypothesis release, and deliberately mutate a disposable copy's epoch fence and duplicate-key rejection to show the tests catch meaningful faults before treating a green run as evidence.

## F10 — Does a reusable comment action solve publication concurrency and idempotency?

**Falsifiable question.** If two report jobs both look up the same marker before either creates it, or a create succeeds but its response is lost, can the documented reusable action workflow guarantee one logical issue/comment without a separate publication protocol?

**Exact English discovery queries.** `site:github.com/peter-evans/create-or-update-comment/issues "duplicate" "concurrent"`; `site:github.com/peter-evans/find-comment/issues duplicate comments concurrent`; `site:github.com/peter-evans/create-or-update-comment/issues/387 idempotent append mode markers`.

**Inspected primary evidence.**

- Maintainer repository [peter-evans/create-or-update-comment](https://github.com/peter-evans/create-or-update-comment) documents create or update of a comment by ID, `edit-mode: replace`, default `append`, and the returned comment ID. Its README demonstrates `find-comment` followed by create on an empty result or replace on a found result. [peter-evans/find-comment](https://github.com/peter-evans/find-comment) can match an author and text and returns one matching ID; it does not claim an atomic find-or-create or prove uniqueness.
- The original [issue #387](https://github.com/peter-evans/create-or-update-comment/issues/387), open on access, is a user's feature request reporting duplicated appends on reruns and possible interference; the proposed marker-based append is a request, not an implemented guarantee or independent proof of a race. In [issue #395](https://github.com/peter-evans/create-or-update-comment/issues/395), action owner Peter Evans explains the required token permissions for the reported issue. This is an original maintainer discussion, not a concurrency endorsement.
- [GitHub Actions concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency) permits one running job/run per same-repository group. By default only one pending run is retained and a newer pending run replaces it; `queue: max` allows up to 100 pending, beyond which runs are canceled; start order is not a general dispatch-order guarantee. `cancel-in-progress: true` can interrupt a writer.
- Local `delivery.md` already specifies a private trusted store, report-key serialization, timeout reconciliation and deterministic output. These sources add a concrete reusable action and expose its boundary; they do not replace the issue-creation protocol.

**Inference and applicability.** The README's steps are a check followed by a separate create: if A and B both receive no match, both can create. A create that reached GitHub may also have succeeded despite the client timing out. Search returning no visible match is not, by itself, proof that the original write could not still appear. GitHub concurrency is a useful additional guard for cooperating jobs in one repository, but does not serialize a separate service or another repository, persist recovery state, or prevent an old in-flight request after a lease expires. Avoid claiming exactly-once publication in the presence of arbitrary ambiguous failures. The two actions operate on comments within an existing issue; they do not create or uniquely identify the report issue itself.

**Concrete plan and tests.** Keep the existing one-issue-per-period/release recommendation. Before writing, persist a trusted report key, target repository, intended immutable body digest and `creating` state under the service's per-key coordination. A trusted single-writer workflow may add a matching repository concurrency group without canceling an in-progress create; it must still have catch-up logic for dropped pending runs. On a known success, save and verify the destination and issue number. On an ambiguous outcome, reconcile all available paginated candidates by exact controlled marker, expected author and destination; bind only if exactly one verified match exists. If discovery is incomplete, a prior request may still complete, zero matches are inconclusive, or multiple matches exist, stop and alert for reconciliation rather than blindly issuing another create. Marker text alone is not authority. A lease/fencing value protects the trusted store only; it cannot revoke a GitHub request already in flight.

If a **comment** inside an existing issue becomes useful, consider the reviewed and immutably pinned actions as convenience wrappers, explicitly set `edit-mode: replace`, and store/verify the comment ID. Replacing the same deterministic body can be retried on that verified ID, but it neither supplies atomic creation nor makes the history private. Alternatively keep the baseline issue-body renderer and do not add action dependencies. Do not run untrusted PR code in the publishing job. Before adoption, inspect the exact action revision, its dependency/security posture and runtime compatibility.

Use a fake GitHub adapter with barriers to force both writers to observe no match; verify the coordinator admits at most one create while its ownership is valid. Inject timeout after server-side create and ensure the job remains unresolved until a unique verified match is found; simulate delayed visibility, zero results, multiple matching markers, wrong author/repository, process death, lost publication-store response, expired lease and a stale worker's in-flight request. Require no blind second create while uncertain. Verify replay on a known ID, unchanged-digest no-op, deterministic body and that correction authorization is separate from duplicate prevention. Validate real provider behavior later in a disposable private destination; no action or publisher was run here.

**Next research lead.** Design the durable publisher state machine around lost responses and stale writers, including an explicit manual resolution path for irreducible ambiguity; check GitHub search/list consistency and real workflow queue behavior before integration.

## Direction recommendation

For the targeted second wave, prioritize (1) whole-report disclosure composition and irreversible GitHub history, (2) an actual property-based consent/decoder harness with independently grounded invariants, and (3) publisher recovery under indeterminate remote writes. Continue using the existing narrow session-token language. Delay any formal privacy, public anonymity, or exactly-once claim until its precise assumptions, implementation and deployment evidence are available.
