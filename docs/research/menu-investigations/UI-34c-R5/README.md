## Source and mechanism

Frozen baseline: `4ae9fc667da826408f1580d27d697b27e31a90c0`. Runtime candidate: `77fe89a0e38b0a0594d3b43cfadb4a634443a842`. Follow-up `f264536fb` adds failure-only probe diagnostics and isolates the HUD smoke scenario; it does not change successful-path loading timers. [Source identities](source-identities.json) record the unchanged Main/session/trim/cache/contact sources and matching 374 tracked import descriptors. Audio retirement commit `7695f6cb5` and companion identity update `795a7d593` follow this measured runtime cohort; [final identities](final-source-identities.json) distinguish them.

After the loading surface draws, AppRoot finishes the selected model request and waits for the preview broker to drain obsolete work. It reuses a retained flight scene or starts one dedicated `Thread` whose callable is ordinary `ResourceLoader.load(main.tscn)`. A root-owned job pumps main-thread frames, joins only after the worker stops, and transfers the result through the existing two-resource broker. Scene instantiation, validation, world construction and session mutation stay on main. Cancellation drains before rollback and cannot publish its result. AppRoot disposal abandons the sibling job, which drains and frees itself. Thread-start failure retains the former synchronous fallback. There is no pre-Home preload, fleet preload or feature-first-use deferral. Controlled application Quit must drain the transaction; forcing `SceneTree.quit()` during a live job is outside this ownership guarantee.

The earlier `load_threaded_request(..., false)` trials are not re-adopted. [Godot issue #120661](https://github.com/godotengine/godot/issues/120661) includes the same engine version, pure GDScript and default-false request with normally collected results: uncached script preloads can leave count-zero LoadTokens. [Proposed fix #121025](https://github.com/godotengine/godot/pull/121025) repairs ignored final `unreference()` returns. Pinned [ResourceLoader source](https://github.com/godotengine/godot/blob/4.7.2-stable/core/io/resource_loader.cpp) explains the workaround: ordinary loading from a user-created thread avoids the WorkerThreadPool nesting path. This is a source-based mechanism, not an engine patch or a blanket resource-thread-safety claim. Godot supports [resource loading on one thread](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html), with main-thread attachment and controlled shared-resource access.

An isolated three-repeat fixture confirms the relevant signature: all 27 cases complete; ordinary main-thread and dedicated-thread loads are clean for 0/1/11 preloaded resources. Default-false threaded requests are clean at 0, leak 1/1/1 zero-count RefCounteds at 1, and 10/11/11 at 11. All six leaking cases correctly fail warnings-as-errors. The exact-N prediction is therefore not universal. [Fixture summary](load-token-summary.json) retains commands, counts and log identities; it does not establish the identity of the older application's leaked objects.

A separate real-scene attribution run prepares Main after Home has drawn: 3.282 s across 195 observed frames, maximum 33.185 ms, two frames above 33 ms and none above 50/100 ms. It completes three Stik cycles without a count-zero ObjectDB warning. Its first Home-draw-to-flight interval includes the explicit preparation; the smaller subsequent Fly interval is not normal Fly acceptance. [Attribution](scene-attribution.json).
