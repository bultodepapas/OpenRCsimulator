# T10 — Expected-value intent prediction and one-neighbor prefetch

**Researched:** 2026-11-17. Recommendations are proposed; no runtime improvement is measured here. [Twenty-investigation index](README.md).

**Question.** Does predicting one likely next vehicle reduce real selection-to-first-draw time enough to justify the work it may waste or delay elsewhere?

**Search queries used.** `prefetch predictive caching timeliness accuracy coverage pollution wasted bandwidth research paper prefetching`; `site:developer.chrome.com rail idle work schedule idle callback tasks main thread yield input latency`; `site:github.com/Netflix/concurrency-limits limit queue latency little law backpressure`.

**Evidence and limits.** IBM's original [prefetch analysis](https://research.ibm.com/publications/when-prefetching-improvesdegrades-performance) evaluates accuracy, coverage, timeliness and bandwidth, including cases where prefetch hurts. The [USENIX caching/prefetching paper](https://static.usenix.org/publications/library/proceedings/usits97/full_papers/kroeger/kroeger_html/kroeger.html) studies latency tradeoffs under its own web workload and bandwidth assumptions. [Netflix's concurrency-limits overview](https://github.com/Netflix/concurrency-limits/blob/main/README.md) offers a transferable reminder that additional in-flight work competes for finite capacity. These sources motivate measurements; hardware caches and network services are not Godot's resource loader, and their results do not predict OpenRC speedups. Accessed 2026-11-17.

**OpenRC seam.** The [plan](../../../../plans/vehicle-selection-performance.md#8-loading-priority-and-prefetch) already proposes at most one directional neighbor only after selected work is measured. [HomePreviewResources](../../../../../app/ui/home_preview_resources.gd#L48) owns one active and one latest queued request; [HomeScene](../../../../../app/ui/home_scene.gd#L319) uses generation checks; [HomeFlightPreparation](../../../../../app/ui/home_flight_preparation.gd#L70) gates admissions during an active scene job. The broker's queue currently represents latest explicit intent, so optional prediction cannot overwrite it. A prefetched PackedScene is a resource, not proof that builder, appearance, GPU upload or first draw is already done.

**Proposed application.** Keep prediction disabled by default until selected loading, browsing-aware scheduling and byte reservations have been measured. In a conditional experiment nominate at most the next item in the last sustained navigation direction after a short, measured dwell; focus or hover nominates only and never changes selection, preferences or launch identity. Admit one low-priority lightweight resource only when no explicit work is pending, the existing scene safety gate permits admission, frame cadence is healthy and the byte ledger has reserved conservative headroom. Never unpause an active flight-scene job. Keep explicit requests able to supersede *queued* speculation. On reversal, filter/search change, memory pressure, Home exit or accepted launch, drop queued speculation; invalidate the consumer of already active work and drain the owner normally. Retain the result only if still useful and within policy. Do not retain a complete extra model or prefetch a fleet by implication.

Frame the choice as a measured expected-value hypothesis: `P(use before eviction) × expected avoided wait when useful`, compared with the additional wait and frames caused by interference, plus separate resource costs and hard correctness/memory gates. Do not pretend a guessed probability or a converted byte-to-millisecond weight is measured. A result is *useful* only if the user selects the same immutable revision before eviction; distinguish fully ready, partially ready and too-late completions, and record whether it actually reduced the remaining critical-path wait. Define coverage over subsequent eligible selections and accuracy over admitted prefetches. Count unused completions, canceled/drained work, wasted CPU/worker milliseconds, bytes/byte-seconds reserved, evictions and cache pollution, and delay to explicit selection or launch. Compare actual matched control outcomes, not cache-hit counts alone.

**Counterexample and experiment.** Fast directional browsing can reverse before the first load finishes; a wrong prefetch can block the latest explicit choice or evict a useful scene, especially on slow storage or a tight unified-memory device. E7 compares selected-only and one-neighbor policy on the same forward, reversal, random-search and controller/no-hover tapes, with cold/warm states and pressure cases. Alternate randomized candidate/control order; measure event-to-first requested draw, p95/max frame interval, acknowledgement, queue reasons, Fly readiness and retained/peak memory. Record all predictions and outcomes, including failures. Screen with five fresh-process pairs and at least 20 warm transitions, then use the protocol's larger samples for tail claims. Package and renderer identity matter.

**Decision.** **UI-VS-10 is conditional** on **UI-VS-02/05/07** and attribution. Reject if net end-to-end benefit is within variation, wrong predictions worsen explicit browsing or immediate launch beyond gates, memory/ownership fails, or stale content can publish. A correct guess with no avoided latency does not pay for the work. If controls show no stable benefit, keep selected-only loading.
