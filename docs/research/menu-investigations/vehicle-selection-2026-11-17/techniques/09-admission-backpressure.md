# T09 — Browsing-aware admission and backpressure

**Researched:** 2026-11-17. Recommendations are proposed; no runtime improvement is measured here. [Twenty-investigation index](README.md).

**Question.** Can the selector reduce waiting behind optional flight preparation without introducing unsafe overlapping scene/resource work or merely moving latency to Fly?

**Search queries used.** `site:sre.google/sre-book handling overload queues load shedding priority admission control`; `site:github.com/Netflix/concurrency-limits limit queue latency little law backpressure`; `site:docs.godotengine.org ResourceLoader load_threaded_request status get_dependencies thread safe SceneTree loading background`.

**Evidence and limits.** Google's [overload guidance](https://sre.google/sre-book/handling-overload/) discusses priority and bounded demand, and [Netflix's concurrency-limits design](https://github.com/Netflix/concurrency-limits/blob/main/README.md) treats queueing and limited shared capacity as reasons to apply admission control. These are service-system analogies; their adaptive algorithms and numeric limits do not establish a Godot scheduler or a local concurrency target. Godot's [ResourceLoader API](https://docs.godotengine.org/en/stable/classes/class_resourceloader.html) recommends status polling on different frames and documents potential slowdowns when subthreads are used. This is live stable documentation, not a pinned 4.8-beta2 safety guarantee. Accessed 2026-11-17.

**OpenRC seam.** [HomeFlightPreparation.tick](../../../../../app/ui/home_flight_preparation.gd#L70) requires eligible, drawn Home, no pending preview, 350 ms stable intent by default and an idle broker before starting optional scene/trim work. A new dedicated scene load pauses the broker; [completion](../../../../../app/ui/home_flight_preparation.gd#L157) takes the result and releases the gate. [The broker](../../../../../app/ui/home_preview_resources.gd#L82) deliberately gates cached and procedural callbacks too because they can run builders that load shared resources. `adopt()` records accepted Fly ownership of an active scene job. This structure establishes a scheduling dependency; its size on current hardware has not been measured.

**Proposed application.** In the existing preparation owner, add a clear browsing-eligibility input: suppress *new* optional scene and trim admissions while the Vehicles workspace or skin gallery is actively being used; resume only in the Flight workspace after a fresh, settled-intent interval. Define activity and return transitions so keyboard/controller navigation is treated like mouse use and cached identity or thumbnail feedback remains immediate. The priority for not-yet-admitted work is accepted launch, explicit selected model/skin, visible static assets, then speculation. Keep the latest useful explicit intent bounded; optional queued work can be dropped. A priority label is not preemption.

If a scene job has already started, keep its broker pause in force until that job's normal completion and collection; do **not** unpause it simply because the player resumes browsing. A new selection may update its label immediately while its model request waits behind the active job. Preserve drain on Home exit, failed launch and Quit, and the adopted launch's right to the same scene result. Trim retains its own existing ownership and abandonment rules. Do not start an additional loader to simulate priority. Accepted launch captures its immutable tuple before an await under the separate launch-identity work.

**Counterexample and experiment.** A user who opens Vehicles, pauses, and immediately flies may lose the useful 350 ms preparation window; suppressing it might improve one preview yet delay readiness. E2 compares current `scene_trim`, browsing-aware `scene_trim`, and preparation off using identical tapes with 0/350/750 ms dwell, randomization/alternation and matching assets/settings. Include a controlled active-scene job followed by a selection: prove the broker remains paused until the actual completion callback; verify no duplicate load, correct later delivery and launch adoption. Test rapid return, repeated launch, cancel, failure, Quit and activity routes with tuple changes during a controlled drain. Count reasons and durations of queue waits, scene/trim starts, completions, adoptions and waste; report event-to-first-label, requested first draw, frame intervals, Fly acknowledgement and total Fly-ready time including dwell, plus memory peak. Run the native 1080p protocol on named hosts rather than infer effects from a headless test.

**Decision.** This is the first scheduling candidate in **UI-VS-02**, after **UI-VS-00** attribution and alongside **UI-VS-01** immutable launch identity. Reject if it opens the active-job gate early, duplicates/abandons ownership, changes the accepted tuple, or improves browsing only by violating Fly or frame/memory gates. If effects fall within variation, keep the simpler current behavior. **UI-VS-05/07/10** extend admission only after their own prerequisites and evidence.
