# T08 — Cooperatively schedule main-thread finalization

**Researched:** 2026-11-17. Recommendations are proposed; no runtime improvement is measured here. [Twenty-investigation index](README.md).

**Question.** Can the work between resource readiness and the requested first draw be split into safe, measurable steps without hiding a long indivisible operation?

**Search queries used.** `site:docs.godotengine.org SceneTree process_frame signal call_deferred idle time main thread process budget`; `site:developer.mozilla.org requestIdleCallback work deadline timeRemaining timeout non preemptive main thread`; `site:developer.chrome.com rail idle work schedule idle callback tasks main thread yield input latency`.

**Evidence and limits.** Godot's [Object documentation](https://docs.godotengine.org/en/stable/classes/class_object.html#class-object-method-call-deferred) says deferred calls can continue in the same idle cycle; use frame signals when a real frame boundary is required. Its [thread-safety guide](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html) warns that active scene-tree interaction is not thread-safe and that GPU-facing calls can synchronize. The deferred-call behavior was also checked in the pinned [Object.xml](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/doc/classes/Object.xml); the live thread-safety guide still needs the target build/runtime fixture for qualification. Google's [cooperative idle-work discussion](https://developer.chrome.com/blog/using-requestidlecallback) illustrates checking a deadline between small tasks and explicitly notes a callback is not forcibly interrupted when it overruns. This is browser inspiration, not a Godot idle-deadline API or a guarantee that a spare frame budget exists. Accessed 2026-11-17.

**OpenRC seam.** [HomeScene._build_requested_preview](../../../../../app/ui/home_scene.gd#L436) waits for numeric geometry work, then calls `_build_model` synchronously and yields at existing `_preview_frame` boundaries before presentation and geometry phases. `_build_model` delegates to complete vehicle or aircraft builders; no boundary splits an individual builder. [HomePreviewGeometry.Snapshot](../../../../../app/ui/home_preview_geometry.gd#L6) aims for 3,000 µs per `advance`, but checks after a whole `surface_get_arrays` read and records its maximum chunk; initialization and other code may cost time too. Its worker receives private numeric snapshots. This design shows useful cooperative partitioning, not a hard 3 ms frame bound.

**Proposed application.** First time the exclusive main-thread phases and individual largest calls. If a phase with independently resumable units dominates, construct a *private* candidate state machine on main: validate immutable input identity; process a small bounded group of bindings or geometry records; check time and current generation after each unit; yield to a later process frame; then continue. Keep the selected metadata and labeled old/thumbnail preview responsive. Test expiry and tree lifetime at every resumption. Commit the complete valid appearance or candidate once; on cancellation or failure release the private root, temporary arrays and overrides. All active-tree updates and publication remain on main. Preserve validation and rollback: splitting must not expose a partly painted or wrongly posed vehicle.

Budget estimates must leave measured room for input and drawing and be tuned from the target's frame history; a timer cannot predict or stop the next operation. Record the configured target, total elapsed construction, per-slice and largest *individual* duration, first requested draw and retirement. Treat `instantiate`, an asset hash/read, one mesh-surface extraction, image decode/mipmap, texture creation/upload and driver work as indivisible until individually proven splittable. If a single such call exceeds the target, isolate it in the report and consider an authored derivative, smaller bounded source asset or fallback; do not call it frame-budgeted merely because a yield follows it. Avoid relying on repeated `call_deferred` to produce successive frames.

**Counterexample and experiment.** If the builder's one engine call consumes most of the switch, sprinkling yields around it adds latency but cannot eliminate the hitch. Compare current staging against one resumable subphase with identical validation/output. Use five alternating fresh-process screening pairs and 20 warm samples; collect the protocol's larger samples for p95 qualification. Include a deliberately large valid surface, custom texture, slow storage, cancellation during each yield, revision replacement, Home teardown, and no-worker fallback. Measure selection acknowledgement, queue wait, total requested-first-draw, 33/50/100 ms frame counts, longest atomic call, memory peak, failure/recovery and output parity at 1080p on Compatibility and Apple Silicon Mobile where available.

**Decision.** Attribute under **UI-VS-00**, then schedule only a demonstrated resumable hot phase; **UI-VS-03/04** may remove the work more safely than chunking it. Reject if a partial or stale candidate is visible, validation differs, worst frames do not improve beyond variation, or total latency/memory breaches agreed gates. Preserve the existing fallback and report any indivisible remainder honestly.
