# T13 — Bounded prepared-object reuse and staggered retirement

**Research date:** 2026-11-17. **Status:** proposal; no runtime measurements. [Twenty-investigation index](README.md).

**Question.** When a user returns to a recently displayed model, can reusing a safely reset prepared root and scheduling old-root destruction across frames reduce build and retirement stalls without leaving stale mutable state or unbounded owners?

## Search and evidence

Actual queries on 2026-11-17: `site:docs.godotengine.org Godot 4 queue_free end frame remove_child ownership nodes resource reference counted`; `site:docs.godotengine.org Node queue_free free children remove_child ownership scene unique resource duplicate Godot`; `site:docs.unity3d.com Addressables asset churn shared dependencies unload reload asset bundles memory management`.

- [Godot Node](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node-method-queue-free) specifies that `queue_free()` deletes a node and children at frame end, after deferred calls; `remove_child()` does not delete it and can change scene ownership. A detached root needs an owner and eventual free. Stable docs were accessed 2026-11-17; verify on 4.8-beta2.
- [Godot GDScript memory management](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html#memory-management) distinguishes reference-counted `Resource`s from `Node` lifetime; dropping a resource reference does not release it while another owner retains it.
- [Unity Addressables 1.21, asset churn](https://docs.unity3d.com/Packages/com.unity.addressables@1.21/manual/MemoryManagement.html#avoid-asset-churn) documents unnecessary unload/reload of a shared dependency across consecutive uses. This is an analogy, not Godot bundle semantics.

These sources do not establish OpenRC timings or prompt GPU reclamation.

## OpenRC seam and candidate

The existing [HomeScene](../../../../../app/ui/home_scene.gd) already retains three recent vehicle/skin roots, hides/disables the previous root, and removes and queues an evicted root for deletion. Candidate construction and stale-candidate release also happen there. The [resource broker](../../../../../app/ui/home_preview_resources.gd) separately retains two scenes; [AirplaneBuilder](../../../../../app/render/airplane.gd) validates visuals. First measure build, restore and post-frame destruction, including shared dependencies.

If Home recreation repeatedly rebuilds the same visual after the current cache is destroyed, trial carrying **one exact-identity prepared root** across that boundary through an explicit AppRoot/Home ownership transfer. Count it within, not in addition to, the three-root limit and the T12 byte budget; disable carryover when the accepted activity cannot reserve the overlap. The baseline already reuses three roots within Home, so renaming that cache cannot improve its hit rate. Require a measured rebuild and safe transfer; create no second manager. A parked root has one recorded owner, no live flight/session attachment, disabled processing and input, and a known visibility/parent state. Checkout requires matching source/geometry/skin revision, adapter, relevant presentation settings and validated current bindings. Restore its neutral transforms, pose, lighting attachments, visibility and per-instance material overrides, then compare against a fresh build; a root that cannot be reset deterministically is rebuilt. Never mutate shared stock assets, share a root between consumers, resurrect a queued root or skip flight validation. The old Home must relinquish its cache entry and callbacks before teardown; the new recorded owner releases the detached root on eviction or AppRoot shutdown. Roots not explicitly transferred retain ordinary Home teardown. Inactive cached roots may instead stay under their existing Home parent if that is the safer, measured arrangement.

Retire **independent** obsolete roots through a bounded queue, scheduling at most a measured amount of work each frame. A single `queue_free()` recursively retires its subtree and can still cause indivisible frame-end work: splitting a live tree arbitrarily is not safe or a guarantee of a frame budget. Separate observed Node/owner release from an estimated GPU retirement allowance. Qualify a conservative observation window and bounded safety margin per renderer using repeated peak/plateau traces; no exact per-resource GPU reclamation signal is established here. Stop admitting heavy work and keep a thumbnail if observed pressure/backlog exceeds that allowance. Expiry is a pressure/recovery decision, not proof that memory was freed, and cannot leave the UI waiting forever for an unavailable fence. Keep useful immutable dependencies only with explicit owners and bounded retention.

## Falsifiable comparison

A is current three-root/two-resource behavior. Attribute two changes separately with a controlled 2×2: current Home-lifetime retention versus one explicitly transferred root under the same caps with verified reset/reuse, and immediate versus bounded stagger of independent root retirements. Keep selection tape, byte/count caps, versions and loads identical. Exercise A→B→A, rapid A→B→C→A with stale completions, skin A→B→default, Home exit/reentry, failed preparation, accepted launch and 20+ cycles. Measure allocations/build and reset cost, first correct draw, per-frame p95/p99/max including frames after `queue_free`, reload/decode/upload counts, retirement backlog, owner/instance counts and RSS/renderer peaks after a documented drain. Compare output and materials against fresh roots; inspect callbacks, processing and orphan ownership.

**Reject** reuse if reset equivalence fails, any owner leaks or live/flight state is mutated, memory fails to plateau, or end-to-end return latency does not improve beyond baseline variation. Reject stagger separately if it merely moves a worse spike to a later frame, grows backlog/peak pressure, or materially delays a selected request. One indivisible root may require asset simplification instead.

**Recommendation and step:** treat the existing bounded cache as the initial pool; instrument under UI-VS-00, then consider owner-safe reuse and paced retirement only under UI-VS-05 and UI-VS-12 after reservation accounting. Coordinate UI-VS-03 appearance transactions. No runtime test was performed for this note.
