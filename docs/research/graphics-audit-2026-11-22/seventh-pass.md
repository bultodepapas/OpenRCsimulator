## What the new dynamic-resolution experiments establish

Main now contains an **experimental, opt-in controller**, with a 75% experimental floor, Native bilinear scaling and completed-frame feedback. It requires the experiment flag and patched engine methods; the official pinned editor and unsupported renderer path keep fixed rendering. Saved intent, current internal scale, output pixels and actual backend remain separate facts. [Scale owner](https://github.com/bultodepapas/OpenRCsimulator/blob/843f357c07af842054f3ccd6728f93beca9a57ef/app/render/flight_dynamic_resolution.gd) · [Policy](https://github.com/bultodepapas/OpenRCsimulator/blob/843f357c07af842054f3ccd6728f93beca9a57ef/app/render/flight_resolution_policy.gd) · [Owning plan](../../plans/dynamic-resolution.md).

The strongest comparable retained rows use a synthetic fullscreen shader and process callbacks, with VSync off and a 240 FPS process cap. A late callback is above 105% of the target budget. These are not presented-frame rates, recorded flight comparisons or pilot readability tests.

The three fixed-85% controls had zero late callbacks during their heavy phase. Adaptation's demonstrated benefit is recovering full resolution during the light phase while reducing pressure during load; it did not beat the fixed-85% control's heavy-phase tails in these rows.

In particular, the committed Primis/Angela tables do not expose the GPU medians required to recompute the rollout summary's approximate 25% claim. Retain that as author-reported, not independently reproduced here.

At 85% scale the nominal pixel area is `0.85² = 0.7225`, or 27.75% less than native. That is an area calculation, not a frame-time prediction. Fixed CPU work, submission, synchronization, reconstruction, caps and visual readability determine the outcome. Earlier paused-view data and the sixth-pass fitted pixel model remain separate workloads.

## X06 — a controller's disappearance can be absent from its evidence

`_observe_dynamic_resolution` returns when viewport status is empty. The scale owner's `stop()` removes that metadata when its target is Off or its flight owner is absent. The reducer accepts a phase when its recorded trace contains at least one valid completed-frame confirmation and no contradictory later observation. These facts leave a gap if status disappears after confirmation without an appended stop record. [Producer](https://github.com/bultodepapas/OpenRCsimulator/blob/843f357c07af842054f3ccd6728f93beca9a57ef/app/debug/godtest_driver.gd#L916-L923) · [Stop path](https://github.com/bultodepapas/OpenRCsimulator/blob/843f357c07af842054f3ccd6728f93beca9a57ef/app/render/flight_dynamic_resolution.gd#L39-L48) · [Metadata removal](https://github.com/bultodepapas/OpenRCsimulator/blob/843f357c07af842054f3ccd6728f93beca9a57ef/app/render/flight_dynamic_resolution.gd#L90-L98) · [Reducer](https://github.com/bultodepapas/OpenRCsimulator/blob/843f357c07af842054f3ccd6728f93beca9a57ef/tools/godtest/analysis.py#L27-L71).

The offline witness executes that pinned pure reducer: an earlier confirmation alone is accepted; no observations are rejected; adding an explicit later fixed-state observation is rejected. It does not execute Godot, reconstruct the full report, change a real flight's setting, or show that an existing result experienced this transition. A normal fixed tour may never change its target. There is a related timestamp limit: the scale owner caches the first completed frame of each generation without `recorded_usec`, and each phase resets observation deduplication. A phase can therefore record a newly observed status containing an earlier phase's completed frame. The live policy independently checks GPU freshness; this does not demonstrate stale operation, but the receipt alone cannot prove a new frame completed inside that phase. Retain a source-frame timestamp or a phase-local fresh confirmation in that follow-up. The follow-up is a producer lifecycle sentinel or explicit phase-end status, paired with a valid→missing regression and an actual mid-phase Off/owner-loss test. Keep steady-state deduplication; evidence completeness should not require rebuilding large status records every frame.

## Old-hardware acceptance and native choices

Measure the limiting resource before choosing a rewrite. In a simplified overlapped pipeline, `T_frame ≈ max(T_CPU, T_GPU) + exposed synchronization/pacing`; it is an explanatory model, not a replacement for traces. Reducing a 6 ms CPU contribution to 5 ms while the GPU still requires 25 ms need not move a 40 FPS frame rate. Equally, fewer pixels will not fix an overloaded 240 Hz simulation/observer path. Native GPU shaders and Godot's rendering server are already native execution; moving their orchestration to C++ is not automatically the useful optimization.

For each candidate, retain matching source, engine, package, actual backend, aircraft/course, input, camera, settings, output/internal pixels and thermal/cap state. Use interleaved baseline/candidate repeats with warmup, sustained load and recovery; record frame p50/p95/p99, worst transition, CPU/GPU attribution, simulation/wall ratio and memory. Check moving distant aircraft and thin silhouettes. Start at 1920×1080 on standard Windows/Linux displays; qualify Apple Silicon native Retina separately. 720p remains a last target, and 240 Hz/float64 stay intact.

Use exact old/new and independent reference cases for numerical/control candidates, including failures and rollback. Preserve the existing qualified floating-point toolchain; [Clang's primary documentation](https://clang.llvm.org/docs/UsersManual.html#controlling-floating-point-behavior) explains why reassociation, contraction and signed-zero handling are separate choices. A successful C++ build is not numerical or hardware qualification. For batching and shader guards, use the [engine and shading references](seventh-pass-rendering.md#primary-engine-references-and-reproduction), matched images and target-renderer timings.
