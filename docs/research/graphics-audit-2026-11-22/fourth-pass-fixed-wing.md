# Fourth pass — fixed-wing gear presentation

Source-only investigation, with application files identified by the lead as matching main `7940a4081e10994f34c858c4acac3d7a1a271464`. No engine, test or hardware was run. The path below establishes repeated source-level work, not a measured frame-time or FPS gain.

## U13. Fixed-wing retractable-gear visual pose is rebuilt on every process frame

**Entry and normal path.** After the flight session resets, Main attaches `GroundGearMotion` to the aircraft (`app/main.gd:1202-1211`; `app/render/ground_gear.gd:21-32`). On every observer `_process`, provided the session remains valid, the aircraft is valid and it has wheels, the observer obtains current gear contacts and applies the accepted extension to its visual rig (`ground_gear.gd:69-83`). Its `PresentationCadence` guard at `:72-73` only coalesces wheel-spin phase; it does **not** guard the subsequent gear-pose application. Thus the pose path continues on process frames at a fixed extension, including a held/paused flight; an observer with no wheels returns before it. A valid imported rig takes the sampled path; a procedural retractable builder such as the P-51 takes the `set_gear` path. This work occurs independently of whether fixed-wing stage physics actually selected native or reference.

**Source-level work.** `RetractableModel.apply` validates the extension, selects adjacent samples and, for every sampled node, reconstructs both sample positions and quaternions, does a position lerp and quaternion slerp/normalization, and assigns its position and quaternion (`app/aircraft/retractable_model.gd:116-130`). It has no unchanged-extension return. The generated F4U geometry's first sample contains **17 sampled nodes**, and its 101 samples declare the same node set; this is visible from the authored geometry (`assets/aircraft/f4u-corsair-250/model-geometry.json`, `gear.retraction.samples`) and its generated counterpart beginning at `app/aircraft/f4u_corsair_geometry.gd:1158-1179`. `Retraction.validate` requires every sample to have the same node count/set (`retractable_model.gd:24-45`); `app/data/aircraft_models/f4u-corsair-250.json:249-252` selects this gear rig. On each successful F4U pose call that reaches the loop, this is 17 position lerps, 17 quaternion slerps plus normalization work and 34 script-level property assignments, even with gear held fully up or down. At 60 process callbacks/s that is 1,020 node iterations/s; actual renderer-server work and cost are unknown. Avanti also declares the imported sampled retraction route (`app/data/aircraft_models/sebart-avanti-s-a200-p100rx.json:205-213`); do not assume it has the F4U's node count. The P-51 procedural route recalculates gear phases and rewrites two main pivots, one tail pivot, two inner doors and two tail doors (`app/aircraft/p51d_model.gd:1250-1271,1301-1317,1330-1338,1347-1360,1372-1400`). These are seven source assignments on an ordinary complete P-51 rig, not seven proven GPU submissions. Fixed-gear aircraft and the default Stik do not take either retractable pose branch.

**Why a blanket dirty check is wrong.** Sampled F4U main oleo sliders are also per-frame compression carriers (`f4u_corsair_geometry.gd:1158-1165`; the generated first sample includes `gear_compression_left/right`). `Retraction.apply` reestablishes each sampled slider's uncompressed rest transform at `retractable_model.gd:128-130`; `GroundGearMotion` subsequently computes the current interpolated compression and writes an offset relative to `rig.rest` (`ground_gear.gd:88-111`). Between those operations the observer updates any following night-kit lights (`:84-87`), which can make the intermediate base pose observable to a following light. Simply skipping the call can leave last frame's compression attached while lights follow; refreshing the rest from an already compressed node would additionally risk accumulating offsets. The synthetic sampled-slider case explicitly checks the rest at down and mid-travel (`app/tests/test_retractable_gear.gd:108-122`).

**Small experiment.** If profiling attributes material time to this path, keep the public `Retraction.apply` contract and add a scene-owned dirty fast path for a *proven unchanged accepted extension and the same live rig/generation*. On an unchanged sample, restore the stored uncompressed bases of sampled compression carriers **before** the existing light-follow pass, then run current wheel spin, steer and terrain-dependent compression exactly as before. When extension or rig identity changes, apply all sampled nodes and rebuild their base transforms first. P-51's independent pivot pose could separately use a guarded unchanged-extension application; never stop the wheel/compression/steering updates. This is an ordinary Godot presentation-state optimization, not a reason to lower the 240 Hz simulation, change gear contact or add native arithmetic without profiling. Preserve reset/restore, model replacement, scene reentry and any legitimate external node writes; if sole ownership/invalidation cannot be demonstrated, retain the current full reapplication.

**Validation and attribution.** Extend `app/tests/test_retractable_gear.gd`, `test_ground_gear_clearance.gd`, `test_gear_visual_contacts.gd`, `test_p51_lights.gd`, and the F4U `app/aircraft/verify_f4u.gd`/rendered mechanism and retraction checks. Compare all local/world gear transforms, 0/intermediate/1 and rapidly changing extensions, sampled and unsampled oleos, steering and wheel phase, the light-follow state *at its original point in the frame*, projected-shadow articulation, ground compression in clear/loaded and moving terrain, pause/resume, reset, checkpoint/seek, model replacement and crash transitions. `gear_state()` also returns `extension=0.0, available=false` for invalid/unavailable actuator AUX (`flight_session.gd:4485–4495`), and the current observer applies that fallback: retain its behavior and invalidate correctly on failure/recovery. Add a call-count fixture showing unchanged poses avoid interpolation but slider bases and compression remain correct. Measure gear observer time, slerp/assignment counts and complete paired process/frame tails on matching F4U/Avanti/P-51 routes, both static and deploying, with actual backend/renderer recorded. An engine property setter may internally detect equal values, so source assignment counts are not rendering cost.

**Prior coverage and identity.** This is visual gear presentation rather than F11/S03's accepted-contact/incident work, T04's flap advisory, or the coalesced Stik control-linkage solve at `app/render/airplane.gd:347-371`. The superficially similar native physics `tick_.posed_ground` / `retractable_pose` double assignment is already tracked as **D08**, with warm-allocation counterevidence, in `docs/plans/apple-silicon-performance.md:836`; it is not a new lead here. The prior audit already documents the visual wheel observer's high-air compression fast path, which remains intact (`docs/research/graphics-audit-2026-11-21/runtime-native.md:83`; `ground_gear.gd:88-95`). Avoid modifying a checked model builder merely to reach this optimization if an observer-owned solution suffices: `retractable_model.gd`, `imported_model.gd`, and `p51d_model.gd` are hashed manifest dependencies (`app/data/aircraft_models/f4u-corsair-250.json:205-208,223`; `app/data/aircraft_models/p51d-mustang-120.json:157`), so changes there require the owning source-generation and identity gates.
