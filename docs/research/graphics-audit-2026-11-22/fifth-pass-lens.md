# Fifth pass — first rain, warm-up coverage and lens lifecycle

[Fifth-pass overview](fifth-pass.md). Source references are pinned to [main `0f859b5f358f`](https://github.com/bultodepapas/OpenRCsimulator/tree/0f859b5f358f4807877ec8bd7fe8009bc3856d3f). The final lead report incorporates two independent source reviews.


This is a source-confirmed construction/warm-up coverage gap and a hardware investigation, not a measured hitch or a measured FPS result. `LensSettings.DEFAULTS` enables rain and Automatic effects for ordinary sessions (`app/render/lens/lens_settings.gd:14-30,58-99`). The supported clear/classic presets supply zero local rain and electrical storm 14 mm/h (`app/render/lens/rain_model.gd:24-33`); the source still allows an explicit zero or positive override. Standard capture/scripted/trace resolution can suppress the stack. First distinguish the enable setting, active weather and actual material/node state; none implies a GPU bottleneck.

## V09 — First positive rain builds a separate spatial streak resource synchronously

**Source-confirmed first-positive-rain transition.** During `configure`, `_warm_up` builds the enabled 2D drop, stamp and film nodes and arranges their warm-up draws, but does not call `_ensure_streaks` or prepare a spatial streak draw (`app/render/lens/lens_stack.gd:178-206,209-226`). The first `advance` with rain enabled and positive resolved rate calls `_ensure_streaks` (`:552-565,746-757`). This may be the first presented frame when the flight starts in rainy conditions; it can also follow a dry flight via a paused sky edit on fixed wing (`app/main.gd:2762-2784`), or `debug_rain` (`lens_stack.gd:527-529`). Passing `paused=true` sets `dt=0`, but does not bypass rate evaluation or resource creation. For fixed wing the caller passes `not session.holds.is_empty()` (`main.gd:1605–1606`), so a normal Pause-menu sky edit freezes lens delta through its menu hold (`screen_stack.gd:96`); a simulation pause/crash without such a hold can still advance lens presentation. Other activity/aftermath pause routes must be checked separately. The helicopter has no sky provider and is dry without an override (`app/helicopter_main.gd:304-319`); the car/quad/airship pass sky providers, and their relevant setup must actually be enabled (`app/vehicles/ground/ground_scene.gd:790-812`; `app/vehicles/multirotor/multirotor_scene.gd:990-1012`; `app/vehicles/airship/airship_scene.gd:243-264`).

The synchronous builder creates one quad, a 3D MultiMesh, its full identity-transform buffer, a shader material and a node, assigns the buffer, then attaches the node (`lens_stack.gd:1079-1108`). The tier's declared streak count is multiplied by `STREAK_ZOOM_DENSITY=4`; visible instances subsequently depend on zoom and rate (`:63-64,770-793`). This is existing native bulk submission with a doubling-built array, not a per-instance setter loop. At declared stock tiers, the source-level capacities and float32 buffer payloads are:

| Tier | Tier count | MultiMesh instance capacity | 12-float final buffer | Largest doubling length before resize |
| --- | ---: | ---: | ---: | ---: |
| Low | 2,000 | 8,000 | 96,000 floats / 384,000 bytes | 98,304 floats |
| Medium | 5,000 | 20,000 | 240,000 floats / 960,000 bytes | 393,216 floats |
| High | 9,000 | 36,000 | 432,000 floats / 1,728,000 bytes | 786,432 floats |
| Ultra | 14,000 | 56,000 | 672,000 floats / 2,688,000 bytes | 786,432 floats |

These are logical source lengths and format payloads, **not** proven allocations, RSS, GPU transfers, GPU-resident memory, or actual visible/drawn counts. The doubling lengths follow `12 * 2^ceil(log2(instance_capacity))` for these tiers. `reset()` zeros travel and clears pools but leaves `_streaks` installed, so repeated rain after a mere reset is warm with respect to node construction (`:234-259,1079-1081`); a settings/scene stack rebuild can recreate it (`app/main.gd:306-320,354-359`). A dry frame after rain retains but hides existing streaks (`lens_stack.gd:767-769`).

**Prior evidence, limitation and plan mismatch.** The owning `docs/plans/lens-screen-effects.md:444-456,604-612` calls for warming enabled shader channels and describes invisible setup draws; it does not explicitly account for the separate 3D streak draw in the current `_warm_up` implementation. This establishes a source-level warm-up coverage gap, not that a GPU compiler will run, that a shader failed to warm elsewhere, or that a hitch occurs: the `STREAK_SHADER` resource is preloaded (`lens_stack.gd:21-24`), driver/engine caches and shader variants are unknown, and creation, server synchronization, compilation and first draw need individual attribution. The 2026-11-12 RTX 3090 / Compatibility 1080p FPV rain result in `docs/plans/lens-screen-effects.md:591-599` is a noisy prior sustained comparison from before later optimizations, not a first-transition measurement. The existing bench turns on rain then waits six seconds before its 240-frame measurement (`tools/lens/bench.py:32-35,60-65`), so it cannot establish first-rain latency. The prior first-crash warm-up investigation `docs/research/visual-quality-implementation/VQ-07/ladder-analysis-2026-11-19/README.md:284-298` is about crash variants, not this rain streak shader.

**Smallest discriminating experiment.** On a fresh, admitted real-device session, record first positive-rain transition with source identity and timer spans for `_ensure_streaks`, buffer fill, `multimesh.buffer` assignment, scene insertion, first visible submission and presented frame tails. Compare first startup in storm versus dry→storm while paused/resuming, with fresh and warm shader/driver caches and repeated rain, at actual Low/Medium/High/Ultra and lens Off. Use at least five cold-process and five warm-transition repetitions where feasible; record actual renderer/backend, 1080p output/internal sizes and Apple Silicon native Retina separately. Instrument and test a tiny matching-instanced-material warm-up versus full capacity preparation separately so a CPU buffer change is not credited to a shader change. A simple offscreen node or resource preload is not evidence of an actual renderer warm-up; verify the intended spatial/MultiMesh variant draw and cache behavior. Compare first-rain visual frame, coverage, zoom/count, motion phase, storm flash, pause/resume, reset, settings rebuild, disabled features and resource release. Do not automatically preallocate the full 56,000-instance tier on every dry flight: that shifts startup and memory costs into the default dry case and changes the existing dry setup contract (`test_lens_effects.gd:325–326` expects one child, the 2D LensLayer). Warming must also account for hidden screen-copy/draw side effects; a hidden node is not proof of pipeline compilation. No implementation choice is justified until the transition is attributed.

## Rejected dry shortcut and lower-priority stamp work

**Dry path and stamp counterevidence.** For a dry rate with no droplets, the existing function still reads the sky, flash and (for fixed wing) wind callbacks; fall speed is computed from the fixed `max(rate,0.5)` and `_streak_travel` advances and can rebase before the no-drop return (`:746-803`). The travel is later sent as the shader phase on first rain, so simply skipping dry wind/fall work changes first-rain positions, including the never-yet-rained case. `_advance_wetness` must also retain `_wet_clock` and any wetness decay, while rain can wash blood/mud (`:847-867,903-927`). Fixed-wing `_render_wind` reads session wind; its built-in `_lens_flash` is a read-only storm-level lookup (`app/main.gd:298-301,323-330,362-367`), whereas arbitrary supplied callables could have side effects. A *smaller* future experiment could reuse the dry constant fall-speed computation or defer flash only when neither raining streaks nor residual lens drops consume it, with callable-observability and transition tests; this would not remove the wind integral.

`_write_stamps` is a separate, lower-priority potential submit reduction: an empty/warm case already returns (`lens_stack.gd:967-969`); otherwise it reorders cracks first and makes two instance setter calls per live stamp, bounded by tier count (12/24/36/48), plus three material uniform writes (`:970-1006`; `lens_settings.gd:25-30`). A live crack, pause, camera/viewport or settings transition can keep it reachable. In the code directly, the transform uses current viewport **height**, the current stamp rows, `_blood_dry` and color settings; camera pose is not directly consulted there, though camera/event changes may alter those inputs through other paths. A dirty cache must therefore prove unchanged input values and mesh/material generation, correct crack-first ordering, color/dryness and external/rebuild invalidation. Existing drop pooling already has its own `_dirty`/mesh/height/rain/gravity guard (`app/render/lens/drop_pool.gd:235-245`); do not mistake that for a stamp cache or promise GPU-upload reduction from setter counts.

The existing rendered shader-compilation probe and historical LENS checks are acknowledged above; this report does not claim the shader was never tested. The open question is current-source first-transition cost in the production route. The dry shortcut and stamp work are not counted as additional V findings.
