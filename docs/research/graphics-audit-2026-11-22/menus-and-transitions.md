## T03. Controls constructs and decorates hidden action rows on every open

**Confirmed source path; duration unmeasured.** Pause/Home/Settings → Controls calls `ControllerSetup.new()`, configures it, and pushes it (`app/app_root.gd:2257–2273,2319–2321`). Its constructor builds all five sections and finally selects Devices (`app/ui/controller_setup.gd:303–306,720–820,918–980,1069,1400,1543–1549`). The Buttons section alone iterates all **37** `ControllerActions.ACTIONS` and creates a Clear, Learn axis and Remap `Button` for each: **111 buttons** (`app/input/controller_actions.gd:44–83`; `app/ui/controller_setup.gd:1443–1497`; `app/ui/widgets.gd:49–50`). This count is source arithmetic, not a timing or GPU-resource measurement.

The 111 buttons already receive their internal `CrystalSurface` during detached construction through `_button → Widgets.button` (`controller_setup.gd:5102–5103`, `widgets.gd:49–56`). After `configure`, `ScreenStack.push` attaches the complete tree (`screen_stack.gd:43–62`). The effects then initialize through `_ready`, creating per-effect `ShaderMaterial` and `ColorRect` resources, signal hooks and up to five stylebox duplicates (`crystal_surface.gd:51–77,94–116`). Only afterwards does `Screen.open` recursively call `Crystal.decorate`; `attach` returns for existing effects (`screen.gd:63–67`, `crystal_surface.gd:33–48`). This later traversal is additional work, but does not recreate those 111 effects. Hidden page visibility is not a construction/initialization guard. `_ready` also updates profile, axis, AUX, action and preview controls (`controller_setup.gd:2037–2055`); `configure` can update the draft first, and a current live selected profile may be loaded after push. Closing normally disposes the screen (`screen_stack.gd:66–81`), so a later open repeats construction.

**Counterevidence and constraints.** Hidden children being instantiated/decorated does not prove hidden rows are drawn, and the count does not show what dominates 400–800 ms. The keyboard path hides editable pages but must permit selection of a controller without losing drafts; all sections also support validation, focus, accessibility, translations, responsive layout, device/connection changes and dynamic visibility (`controller_setup.gd:1814–1850,4888–4917,4966–4981`). Crystal effects are event-driven after setup and stop ordinary/physics processing (`crystal_surface.gd:74–77`), so do not call them continuous per-frame processing. Existing style overrides and user preferences require attention, and first opening of Buttons must not silently lose feedback or merely move the same severe freeze to an unmeasured step.

**Smallest experiment.** In an isolated diagnostic run on the same pinned source/engine, time the separately marked `ControllerSetup.new`, `configure`, attach/`_ready`, `Screen.open`/decoration, first drawn frame, first actual presentation, first Buttons activation and close. Count controls/effects/materials/style duplications, and include keyboard-only, known gamepad and radio, one versus many connected devices, first and repeat opens. If effect creation/initialization dominates, compare a deliberately scoped mechanism that defers the hidden-page `Widgets.button` effect creation or initialization until activation, preparing the visible page before it draws. Changing only `Screen.open` traversal would miss the pre-attached effects. Handle raw-created eligible controls, dynamic children and theme changes; preserve idempotence and visible feedback, and measure the first-use work moved into each page activation. Lazy page construction is a larger option only if needed and if validation and draft ownership survive absent controls. Native/built-in scene/UI operations are the first candidates, not a new framework.

**Validation.** Exercise `test_ui_crystal.gd`, `test_ui_screen_stack.gd`, `test_controls_workspace.gd`, `test_controller_sections.gd`, `test_controller_responsive.gd`, `test_controller_setup_safety.gd`, profile save/recovery, radio/menu verification, connection loss and relevant UI integration tests. Compare focus, text scale, translations, skin overrides, navigation, action visibility/filtering and current keyboard/controller behavior. Run real transition traces and first-use checks in alternating matched blocks, preserving paused state, continued physics after resume and actual presentation evidence.

## T08. Settings builds its complete theme twice in a row

**Confirmed source path; duration unmeasured.** Each `open_settings` creates a new `SettingsScreen` (`app/app_root.gd:1988–1993`). Its `_init` invokes `_build`; `_build` calls `Screen.mount(self)` and immediately replaces the surface theme with `ScreenTheme.build()` (`app/ui/settings_screen.gd:178–185,240–242`). `Screen.mount` has already called the same `ScreenTheme.build()` when no shared theme is provided (`app/ui/screen.gd:24–32`). Each build constructs a `Theme` with many native style resources (`app/ui/ui_theme.gd:66–143,167–181,223–286,339–405`). No screen content is built and no explicit theme mutation occurs before the second assignment. The first theme is nevertheless assigned before the surface is anchored and added to the detached host; theme notifications and ownership must be checked rather than assuming zero side effects.

**Counterevidence.** `UiTheme._icon_cache` retains generated SVG textures by string and text scale, so the second build does not necessarily rerasterize or upload the icons (`ui_theme.gd:59–63,289–296`). This is one duplicated theme build, not proof of an extra full screen, frame, or large allocation. Settings creates all six pages and initializes them before showing Display (`settings_screen.gd:240–310,671–680`); attach, decorate, layout, text shaping and first draw remain independent costs.

**Minimal candidate and probe for the lead.** Remove the immediately redundant second assignment, keeping the per-screen theme and all later theme-refresh behavior. Before relying on it, use a small pinned-engine headless component probe that warms the existing icon cache and alternates one versus two `UiTheme.build()` calls with the same scale/compact/opaque flags and equivalent final-theme retention. Record raw per-iteration times and median/tails; a separate process-cold block may include first SVG work. This isolates duplicate construction only; it does not measure whole screen, GPU, scanout or user latency. Compare `SettingsScreen.new` and normal attached Settings before/after separately, with render/presentation on target hosts. No probe was run in this audit.

**Validation.** Run the Settings, shared theme, screen stack, crystal, scale, display trial, reconstruction/Reflex and accessibility integration checks, especially `test_settings_ui.gd`, `test_advanced_graphics_settings.gd`, `test_ui_settings_integration.gd`, `test_ui_scale.gd`, and `test_metalfx_policy.gd`. Check live theme replacement after text-size/opaque-panel changes, translations, focus and Keep/Revert/timeout with identical resulting controls and screenshots.

## T09. Opening Controls can repeatedly acquire the profile-store lease for the same device

**Confirmed conditional path; duration unmeasured.** `ControllerSetup.configure` first calls `_load_profiles`, then `_refresh_devices`, then `_load_profile_for_device` (`controller_setup.gd:320–330`). The menu-device picker iterates connected devices (`:2313–2323,2335–2351`). For a connected, non-verified known gamepad, eligibility can call `match_profile` once from `_radio_menu_profile_for_device` and again directly; an unknown gamepad may reach a third match through `_has_saved_gamepad_profile` (`:2392–2428`). Selecting a device without `profile_id` can perform another match (`:2431–2442`). Every match invokes `profiles_for_device → load_all` (`app/input/controller_profile_store.gd:301–318`), which claims/releases the storage lease and reads/validates the full existing ConfigFile (`:116–140,357–382`). The lease itself makes an atomic directory, writes an owner token, verifies and removes it (`:36–73,76–93`). With a missing profile file, the lease can still be acquired, but the file parse is skipped.

**Counterevidence.** Counts depend on connected-device identity, verified radio state and short-circuit branches; disconnected entries skip matching. The actual `ControllerService.profile_for_device` caches guarded hits and misses (`app/input/controller_service.gd:309–330`), but the picker calls Store's matching API directly. V1 explicitly selects keyboard for flight and UI (`app/debug/godtest_driver.gd:290–294`), although other devices can remain enumerated; without the actual inventory this path cannot explain its Controls interval. Profile data is deliberately revalidated, the lock serializes readers and writers, and serial/ambiguous-device checks affect input authority. Existing `storage_signature` has a hot-file exclusion; it is not permission to reuse stale data.

**Experiment and candidate.** Count store loads, successful/failed lease operations and bytes/parse/validation time per open for zero devices, a known gamepad, an unknown device, a verified radio and several devices with empty, normal and damaged/recovered stores. If material, first consider one fully validated store snapshot for a narrowly bounded refresh transaction and evaluate all device matches against that same snapshot, or share one match result within one eligibility decision. Preserve lock/owner and failure behavior, backup recovery, serial and ambiguous-family uniqueness, fresh connection generations, current-draft priority and externally changed files; do not cache a selection across refreshes without a complete invalidation contract. Exercise `test_controller_store.gd`, `test_controller_audit_concurrency.gd`, `test_controller_audit_identity.gd`, `test_controller_menu.gd`, setup safety and Save/Discard flows.

## T10. Hidden Settings graphics status keeps rebuilding a broad report

**Confirmed source path; impact unmeasured.** Settings starts on Display, yet its `PROCESS_MODE_ALWAYS` `_process` normally calls `_refresh_graphics_info` after about 0.5 s of accumulated process `delta` (`settings_screen.gd:178–180,203–211,671–680`). The Graphics page's label is then hidden. The expired display-trial draw-wait branch can return before this polling block (`settings_screen.gd:188–202`); this is not an unconditional wall-clock timer. The Settings surface can also be covered by Controls while its CanvasLayer remains in the tree; `Screen.set_active(false)` changes visibility and input, not its parent's process callback (`app/ui/screen.gd:113–121`). The status formatter calls `AutoGraphicsReport.runtime(false)`, which gets a full hardware/policy report, reads the saved renderer ConfigFile, and, when the adapter string is nonempty, attempts a calibration ConfigFile read (`settings_screen.gd:1176–1182,1215–1220`; `app/render/auto_graphics_report.gd:54–89`; `app/app_state/renderer_preference.gd:35–40`; `app/render/auto_calibration.gd:270–274`). `player_summary` does not use the saved renderer-state field (`auto_graphics_report.gd:35–51`). These are source-level operations, not measured disk traffic or a demonstrated frame hitch.

**Counterevidence and candidate.** The poll intentionally updates asynchronous Reflex acceptance and reconstruction-failure status, and the display trial has a wall-clock safety deadline. Do not disable `_process`, suspend the trial when covered, cache hardware/viewport status indefinitely, or stop detecting a fallback. If profiling shows a cost, scope the visible Graphics presentation report to when that page is visible and refresh immediately on selection/return, while maintaining the required safety/fallback checks. A narrower report input that avoids the unused saved renderer read is another independent option; retain fresh calibration/reset and external-change semantics. Verify output, capability changes, locale/resize, provider fallback, pending SDK status, cover/reveal, trial timeout and Keep/Revert using `test_metalfx_policy.gd`, `test_advanced_graphics_settings.gd`, `test_settings_ui.gd`, and integration tests. No steady-state FPS improvement is claimed.

## Interpret the new stutter map at its actual boundaries

The new [stutter map](https://github.com/bultodepapas/OpenRCsimulator/blob/7940a4081e10994f34c858c4acac3d7a1a271464/docs/research/god-test/2026-11-21-stutter-map.md) is a one-pass detector on each listed aircraft/host, with native physics and muted sound. Its 281–318 ms Settings and 415–757 ms Controls values are callback intervals during phases, not physical presentation times and not a diagnosis. Each phase first constructs Pause, then opens the target, dwells, closes it and resumes (`app/debug/godtest_driver.gd:427–481`). The map has one interval >100 ms per such phase, but align retained watcher incidents with `menu_open_requested`, `menu_opened`, `menu_closed` and additional operation markers before attributing the interval to a particular constructor or direction.

Likewise `selection` is an entire Home-configuration phase: device selection, aircraft/landscape/start setters, weather dialog, sky seed Apply and time selection (`godtest_driver.gd:290–327`). The 2.798 s first Windows interval does not by itself identify aircraft selection. The `settings` phase includes opening Pause and the lighting dialog, changing a lighting preset and sky to overcast, applying, dwelling and resuming (`:516–562`). Its 1–3 intervals >100 ms cannot all be called Apply without time alignment. The full report's sampling and clock boundaries are in `tools/godtest/PERFORMANCE_TOUR.md:262–270,360–370`.

For changed combined lighting, `_commit_lighting` updates environment/sun/clouds and `_refresh_sky` updates them later in the same transaction (`app/main.gd:2844–2882,2931–2945,2801–2813`). The intervening sky commit, night options and moon publication can change state (`main.gd:2864–2878`; `app/render/world/world.gd:1404–1441`), so this is a measured-attribution follow-up rather than a safe unconditional deletion. Attribute dialog construction, validation, `FieldBuilder.prepare_lighting`, commit, sky publication, persistence and post-draw before considering coalescing. Preserve atomic error handling, paused physical state, visual timeline/recording and live sky/moon correctness.

For selection/loading, retain UI-05-R3's already measured latest-request handling and bounded resource broker; `HomeScene._build_requested_preview` still contains indivisible model build, presentation and shadow-geometry units separated by yields (`app/ui/home_scene.gd:324–359,441–493`; `docs/research/menu-investigations/UI-05-R3/README.md`). UI-05-R3's older 720p Windows component/feedback results are useful history, not this map's current-device diagnosis. The loading and Home-return reports have their own existing audit findings and require matched stage and presentation traces.

See the [audit index](README.md), [phase/focus counterexamples](measurement-integrity.md) and [validation priorities](priorities-and-validation.md). The counters and timings discussed here do not establish a measured FPS improvement.
