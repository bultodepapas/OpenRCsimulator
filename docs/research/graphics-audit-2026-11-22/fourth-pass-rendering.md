## U09. Glare set to zero still builds the pilot skyline

**Route and guards.** With the landscape upgrade enabled (the default), world construction unconditionally attaches `SunGlare` (`app/render/world/world.gd:445–446`). `--sun-glare=off` / `OPENRC_SUN_GLARE=off` makes intensity 0, rather than preventing node creation (`app/render/landscape_upgrade/options.gd:4–23`, `sun_glare.gd:55–63`). With a live camera, environment and shader sky, `_process` computes the source, cloud transmission, and `_skyline_prior` before it multiplies by intensity; it hides the veil only afterwards (`sun_glare.gd:155–195`). Perspective cameras whose optics metadata is anything other than the exact string `lens` enter the eye path in `_skyline_prior`; a live parent `Field` starts a `Skyline`, advances it at 600 samples/frame, and restarts it if the eye moves more than 2 m (`:29–32,212–227`). This includes the normal pilot path; Home's own camera is also a plain camera with no optics metadata in this setup (`app/ui/home_scene.gd:150–165,179–183`, `sun_glare.gd:170–174`). Non-eye and orthographic views do not start it on that frame.

**Work and limits.** Each frame incurs a source query and a cloud cache-key check; `SkyMirror.transmission` recomputes only when that key changes (`sun_glare.gd:241–248`). During skyline creation, `Skyline.step` budgets the `_advance` sample stage, but `_start` traverses nodes and reads a whole eligible `MultiMesh.buffer` or a mesh's surface arrays, constructs/appends full index arrays, and allocates full per-vertex angle arrays without decrementing that sample budget (`app/render/sun/skyline.gd:45–56,89–156`). This is not proof of a current backend GPU readback; getter/driver behavior must be measured. The older SUN-09 evidence explicitly records this existing limitation: default-field llvmpipe VM, 500 frames, 0.45–0.61 s total CPU, worst 8.7–15 ms for an array read; the checked-in example is 606.589 ms total, 15.179 ms worst (`docs/research/sun/SUN-02b-06-09/README.md:40–72`, `skyline-default-field.json`). It is historical, differently sourced evidence, not a current device result. At 60 updates/s, 500 updates would span about 8.33 seconds, not 8.33 seconds of CPU.

**Smallest experiment.** When intensity is exactly zero, consider skipping the skyline request and associated transmission/source work only to the extent no observable consumer needs each value. Keep the node alive and process a lightweight path as necessary: `_process` currently ensures the live sky's `disc_cloud_occlusion` flag, advances/recoveries afterimage state from the accepted shader clock, publishes diagnostic metadata, and exposes `skyline()` to tests/capture tools (`sun_glare.gd:164–166,179–193,230–248,290–306`). Intensity is a mutable property, and captures explicitly change it at runtime. Current Off mode still publishes intensity-independent `background_scale`, `aureole_coeff`, `kappa` and optics; completed scans publish `skyline_elevation`. `capture_landscape_upgrade.gd:419–420,494–496` explicitly finishes/reads the skyline and metadata. Skipping these calculations changes existing observable Off behavior unless identical values and readiness are preserved; this requires a contract/design decision, not merely a visibility early return. Lazy skyline preparation when re-enabled would change the old finished skyline's immediate-visibility behavior and may require hundreds of frames; either preserve first-visible correctness or explicitly accept/measure the changed readiness. Do not simply skip all processing or remove the node. The zero-intensity predicate is distinct from prior F31 zero-opacity sky-shader work and S10 storm-flash work.

**Validation.** Attribute `source`, `_clouds`, `_skyline_prior`, `_start`, sample chunks and actual frame/presentation tails in matched off/on, eye/lens, stable/moving-eye and Home/flight runs. Confirm if zero-mode produces any `Skyline` or live renderer buffer/mesh retrieval. Use `test_sun_optics.gd`, `test_sun_skyline.gd` (the native renderer covers paths absent with the headless dummy), `test_sun_flight.gd`, `test_world_moon_glare.gd`, and landscape captures. Include initially off and on→off→on, cloud changes, moon, resumed/paused clocks, camera/resize changes, scene detach/rebuild, `skyline()`/metadata consumers, and exact sky-disc occlusion. Run matched Windows/Linux 1080p and Apple Silicon native Retina, record drawable/internal/output resolution and GPU/API receipts. No claim is made that a hidden veil currently draws or executes a shader.

## U10. Home preview selection can restart the already-known skyline build

**Route and conditional trigger.** `AppRoot.set_aircraft` and `set_vehicle` request new Home previews (`app/app_root.gd:1155–1168,1177–1186`). On a warm hit or after staged construction, `HomeScene.show_aircraft` positions the model, chooses its bounds, and calls `_frame_aircraft` (`app/ui/home_scene.gd:202–262,324–340,441–492`). `Presentation.fit` positions the camera from the new bounds and viewport (`app/ui/home_presentation.gd:156–183`). If that change moves the camera more than `SKYLINE_REBUILD_M = 2.0`, the next SunGlare eye pass creates a fresh `Skyline` and starts its scan again, including when the previous scan had not finished (`sun_glare.gd:212–225`). This threshold is conditional: the source alone does not prove that any particular selection crosses it, and the Home 3D scene can remain a visible backdrop under a covering screen rather than being absent. The scan can progress with a fixed world clock because it is driven by node process frames, not `World.update`'s advancing simulation time.

**Status and small candidate.** This is a new consumer/trigger to trace for SUN-09's **previously documented** skyline construction and large indivisible start unit, not a new discovery that skyline building is expensive. It is distinct from the prior audit's R3 indivisible field/model construction and S14 root viewport scale. Attribute retries/completed work first. If frequent, evaluate reusing immutable, explicitly versioned CPU geometry across eye-position rebuilds while recomputing eye-relative bins, or splitting one `_start` job into deterministic incremental preparation. Treat full MultiMesh/mesh retrieval as a separate indivisible native call until the pinned engine proves otherwise. Reuse must invalidate on relevant node/resource/transform, visibility/visible-instance-count, field replacement, dynamic scenery and any world ownership change; skyline deliberately excludes the eye's nearby geometry. Maintain the same traversal/triangle stride, max-height/crown rules, and accurately report whether completion timing and constant-horizon fallback change. Do not assume a hidden preview or change optics from eye to lens without design approval.

**Validation.** Log camera identity/position, view mode, reset reason, nodes and bytes retrieved, `_start` duration, samples/frames to completion and first actual presentation during a repeated same-model selection, warm/cold aircraft changes, vehicle changes, resize, Home→Workshop→Home and a field rebuild. Test default and custom fields, moving/hidden/removed geometry and different eye positions against the existing skyline bins and sun/afterimage images. Compare frame-tail timing under controlled matched blocks; the historical 500-frame value must not be applied to Home without measurement.

## U11. Disabled aircraft show effects repeatedly release already-empty buffers and reconcile their budget

**Route.** Only non-inherit, non-disabled authored lighting profiles construct the `LightingVfx` owner; inherited stock lighting returns before it (`app/render/lighting/aircraft_lighting_rig_3d.gd:53–101,121–129`). Workshop trials create and advance the rig from the displayed-pose clock (`app/main.gd:1547–1584,3547–3558`); Workshop playback has its own guarded preview route (`app/ui/workshop_preview.gd:353–385,426–432,1341–1363,1412–1427`). Profiles contribute at most two **enabled, resolved** effect pools to this runtime (`lighting_vfx.gd:83–121`). The player show-effects toggle, reduced flashes or low lighting quality makes `LightingPolicy.effects_allowed()` false (`app/render/lighting/lighting_policy.gd:14–26`).

Each `advance` still clears transient pool records and calls `_refresh_scene_budget` (`lighting_vfx.gd:152–175,186–212,1117–1124`). `_refresh_scene_budget` calls `apply_scene_budget` even for an unchanged grant because individual pool eligibility may have changed (`:395–414`). For each undesired pool, `apply_scene_budget` invokes `_release_effect_buffer` (`:355–392`); even once `instance_count` is zero, that helper repeats five property assignments: node invisible, visible count zero, instance count zero and both MultiMesh and node AABBs empty (`:1103–1108,1169–1177`). Therefore one ordinary steady local `apply_scene_budget` with two undesired non-null pools makes 10 release-helper property assignments, plus two further `instance.visible` assignments in its second loop (`:383–392`). This is not a per-advance upper bound: changed quality/grants and synchronous or reentrant coordinator publication can invoke `apply_scene_budget` additional times. Count five assignments per release-helper call and measure the number of apply/release calls separately, plus bounded array/dictionary work. This is a source-call bound, not proof that Godot allocates, frees or sends a command on every identical assignment. Separate spill lights can remain active when show effects are off; they are not part of that toggle's VFX pool.

**Candidate and independent sublead.** First profile an idempotent release transition: retain/verifiably check the already-released state and skip repeated resource property writes while preserving first revoke and subsequent reallocation. Do not skip CPU residual aging in the normal `effects_allowed` path merely because a scene grant was denied: tests deliberately require particles to age while unallocated (`app/tests/test_lighting_vfx_lod.gd:73–98,481–520`). Preserve current grant eligibility, visible count, both culling bounds, externally replaced/freed nodes, owner teardown, policy changes and the next visible frame. A separate exact-match optimization could avoid the coordinator's full resolution for an unchanged validated request **after** dead-owner pruning and only after a successfully settled resolution and when not resolving/reentrant: currently `submit` synchronously ranks all owners, builds targets and a receipt even for identical input (`lighting_scene_budget.gd:90–118,182–241,260–303`), and a changed distance/priority/request or quality genuinely needs reconciliation. For N registered owners and U ordinary valid non-reentrant submissions from successfully registered owners, the source does U full ranking passes plus several linear scans/receipt constructions; callbacks can request additional passes and a quality change can trigger another resolve. N≤128 is the API ceiling, not the typical active production count. Continue local `apply_scene_budget` even if the numeric grant matches, preserve decrease-before-increase publication, receipt freshness, invalid submissions, owner pruning and reentrancy/fail-closed behavior. In particular, a pathological `_revoke_all` must leave the next external submission able to retry even if the request bytes are unchanged. This addresses buffer/budget lifecycle, not S08's strip-pattern resolution or S06's smoke arrays.

**Validation.** Count per-frame calls and actual allocation/resource state and measure whole-frame time for a two-effect authored profile, effects On/Off, Low, reduced flashes, visible and denied grants, stationary and moving cameras, one and multiple *actually instantiated* owners. Test `test_lighting_vfx_lod.gd`, `test_lighting_scene_budget.gd`, `test_lighting_scene_integration.gd`, `test_lighting_policy.gd`, `test_lighting_flight.gd`, reset, reparent/free, dynamic quality, mode transitions, pool-priority swaps and grant reentrant callbacks. Compare render output and bounds on native 1080p and native Retina. Existing quality gates, culling, grant callbacks and the nonallocated-buffer fast path already bound this work; no material gain is asserted.

Dead-owner pruning must trigger a resolution when it removes an owner: a surviving owner may now deserve freed capacity even if its submitted request is unchanged. Any equality shortcut needs a settled-generation/dirty proof covering register/unregister, quality changes, publication, reentrant pending work and revocation; preserve `grant_for`/`receipt` reconciliation and synchronous ordering. A request-value comparison alone is insufficient.

## U12. Live show effects re-invert the same world transform for each particle or segment

**Route and cost.** Under the same non-inherited authored-rig guard, eligible retained spark/trail state advances from presentation time with birth and residual-lifetime rules, independently of whether its scene buffer is granted (`lighting_vfx.gd:152–212,544–627,630–763`). For each retained visible spark or valid positive-fade trail segment, `_update_sparks`/`_update_trail` invokes `_local_transform`; that helper reads `_world_root.global_transform.affine_inverse()` and multiplies the item transform (`:611,748,1111–1114`). The world-root node is initialized top-level at identity (`:421–434`), but may be externally changed, so do not assume identity without an ownership guarantee. There are at most two pools, each at most 32 spark particles or 63 trail segments (`:10–15`), hence at most 126 inverse calls and 126 transform multiplies per advance for two full trails. This is a structural bound; a real trajectory/normal lifetime may produce fewer, and a denied buffer can still maintain CPU visual state. The independent setter path, when the buffer is allocated, issues two per-instance calls for each live transform/color (`:1140–1156`): at most 252 native API calls for two full trails, not necessarily 252 GPU uploads. Live bounds are then computed and installed on both resources.

**Smallest candidate.** Hoist the actual built-in inverse to one per pool update or, if stable for the entire synchronous owner advance, one per advance; pass it through the already-existing native `Transform3D` multiply. Preserve missing/invalid-root fallback, transform precision/order, owner changes, all dynamic camera-facing bases, visibility and conservative per-segment AABBs. The larger alternative is comparing Godot's native `MultiMesh.buffer` setter with per-instance setters (the lens drop pool already illustrates a separate 2D use at `app/render/lens/drop_pool.gd:235–283`). For 3D transform plus color the source buffer layout is 12 + 4 float32 values, so two 63-slot buffers encode 126 × 16 × 4 = 8,064 bytes of capacity payload per full write; this arithmetic is not a measured upload or guarantee that full-capacity submission beats 2N incremental setters. It can write more data when only few instances are live and can change precision, counters and reallocation behavior. Profile inverse hoisting separately before pursuing buffer redesign.

**Validation.** Compare identical transforms/colors and both bounds on moving camera and changed world-root transforms, sparse/full trails, isolated/mixed spark bursts, low/standard/high, missing anchors, budget denial/regrant, pause, scene destruction, teleports and both main/inset cameras. Run `test_lighting_vfx_lod.gd`, scene-budget/integration, rig and flight tests, including the existing 63-segment and culling-bounds cases (`test_lighting_vfx_lod.gd:211–233`). Attribute inverse, visual construction and setter wall/CPU separately on a production renderer; use paired visual captures and target-device frame/GPU traces. No shader complexity or native speedup is inferred from source.

## Negative coverage and overlap checks

- Field people gaze is not an unguarded per-frame renderer upload: `app/scenery/people_gaze.gd:227–251,355–377` advances only 1/120 s presentation steps, gates `apply` on dirty/initialized, and suppresses sub-epsilon instance changes. Low scene quality does not install the gaze owner (`app/render/field.gd:304–312`). A historical 13-person VM test already reports the struct-of-arrays rewrite and roughly 16–17 µs/tick (`docs/research/scenery-implementation/SC-HUM-03/README.md:23–29`); it is not a new current performance measurement. Do not present a new port as an unqualified win.
- `SunGlare` cloud transmission already caches by sky inputs and direction snapped to `1e-5` (`sun_glare.gd:49–51,241–248`); inactive camera magnifier and still Workshop preview already disable/limit secondary viewport updates. The field-shadow policy disables projected-shadow processing and viewport updates when off (`app/render/shadow_field_policy.gd:396–405`, `app/render/projected_shadow.gd:510–528`). These guards rule out the broader claims that all three always draw or rebuild.
- No analysis here repeats earlier grass/meadow, water, cloud-bake readback, full-sky, hidden smoke arrays, S08 strip patterns, Home shadow rebinding or scale, Library scans/thumbnails, retained trial worlds, T03/T08/T09/T10 menu items. Source count bounds and `gpu_instance_writes` are not platform performance evidence.
