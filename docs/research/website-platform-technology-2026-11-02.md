# Website platform technology options — 2026-11-02

**Scope:** research and implementation plan for the static OpenRC project site. No site feature, publication, browser qualification, or field performance result is claimed here. Source inspected at `3d043377a` on 2026-11-02; concurrent simulator edits were unrelated. The [website guide](../../site/README.md) remains the implementation authority.

## Current baseline and decision

The site has eleven independently rendered language pages, reciprocal language links, a manual language menu, an optional on-demand 3D viewer, WebP turntables, deferred media, reduced-motion behavior, and GTM/GA4. The inspector's six GLBs total 28.6 MB on disk but are selected one at a time; the jet is 8.19 MB. These are current-source facts, not gaps to reimplement: [website guide](../../site/README.md), [model inventory](../../site/MODELS.md), [current site](../../site/index.html).

Current browser evidence is predominantly Chromium at desktop and narrow mobile widths. One older 1024×768 review covers the hero, not the full current tablet experience. Firefox, Safari, physical tablet interaction, and field Core Web Vitals remain unqualified: [website checks](../../site/README.md#search-metadata-and-static-languages-web-0811). The [RC community discussion](https://www.reddit.com/r/RCPlanes/comments/1x8iee8/) gives useful presentation and onboarding leads, but its self-selected comments do not measure web demand or browser share; see the [coded local analysis](reddit-launch-feedback-2026-10-26/insights.md).

The next website work should be a series of independent, measured changes. Keep the primary visual/performance target at **1920×1080**, inspect larger desktop resolutions next, and treat 720p as a later fallback. Include tablet portrait/landscape and narrow mobile in compatibility checks without treating those viewports as substitutes for 1080p.

## Implementation order

1. **Qualification baseline:** record source/deployment identity and cold/warm requests, LCP/INP/CLS, video and inspector load behavior, and visible layout at 1920×1080 first. Repeat at 2560×1440, tablet 768×1024/820×1180/1024×768 and narrow mobile. Use Chromium, Firefox and WebKit automation for repeatable checks; Playwright's browser builds are patched, so real Firefox and Safari/device checks remain separate. [Playwright browsers](https://playwright.dev/docs/browsers). Do not count historical 720p captures as 1080p proof.
2. **Language suggestion:** add one small progressive enhancement. Match supported BCP 47 language/region variants; `fr-CA→fr` and `pt-BR→pt` are reasonable, while explicit Traditional Chinese must not be silently mapped to Simplified Chinese. Never override a direct locale URL. Preserve `#fragment`; explicitly handle the `download`/`release` query because [downloads.js](../../site/downloads.js) can start a ZIP request after navigation, and blindly copying that query could trigger a duplicate. The suggestion remains absent when JavaScript is unavailable; the manual menu remains complete.
3. **Tablet components:** inspect the recorded failures, then convert one affected component at a time to size-aware CSS and touch-aware controls. Review every change at the 1080p primary target as well as tablet and mobile. Keep screenshots in ignored scratch storage unless an evidence image is necessary.
4. **Media experiments:** use disposable outputs from the existing turntable/model generators. Compare one responsive sheet variant; then one Meshopt model; then KTX2 only if texture residency is measured as relevant. Pin exact free tool versions and keep license/provenance receipts. Promote one change only after matched before/after evidence.
5. **Field measurement and optional motion:** add coarse Web Vitals attribution when the analytics scope is agreed, then revisit CSS scroll/view transitions only if measured bottlenecks remain. Small traffic may not support reliable p75 estimates.

## Horizon options deferred by current evidence

- **WebGPU viewer:** WebGPU offers modern GPU rendering and compute, but remains a limited-availability browser API. Replacing the existing lazy `model-viewer` path would add a second rendering stack before an inspector GPU bottleneck has been measured. Reconsider only after a cross-browser, 1080p trace identifies one. [MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API).
- **On-device AI help:** Chrome's Prompt API can answer page questions locally on supported desktop hardware, but its published requirements include substantial free storage and memory and exclude current mobile browsers for foundation-model APIs. It must remain an optional experiment with the existing static help as the universal path, and its answers would need source grounding. [Chrome Prompt API](https://developer.chrome.com/docs/ai/prompt-api).

## Limits

- No current Firefox/Safari or physical-tablet pass is claimed. A source inspection can nominate checks, not certify compatibility.
- No compression, responsive-image, CSS-animation or language feature has been implemented by this note; all performance gains remain hypotheses until matched measurements.
- The website remains a static project showcase. These changes do not make the desktop simulator playable in a browser or validate aircraft physics.

## Follow-up experiment — 2026-11-02

WEB-15 implemented the higher-priority language, responsive-layout, atlas, real-user-metric and low-data-media changes; the [website guide](../../site/README.md#website-platform-web-15) records verification. This paragraph updates the research record without replacing the earlier pre-implementation baseline above.

An isolated jet Meshopt trial used glTF Transform 4.5.0 and meshoptimizer 0.23.0 without quantization. The current public jet GLB transferred 5,220,619 gzip bytes. The candidate transferred an estimated 4,526,040 gzip bytes plus 7,558 gzip bytes for the decoder: 687,021 bytes (13.16%) less model-related transfer, based on local gzip-6 compression for the candidate. A matched local gzip-6 comparison was 5,216,259 versus 4,533,598 bytes (13.09%). Structure checks preserved 70 nodes and matrices, 26 material links, 20 WebP images and 105 indexed primitives; Chromium 151 loaded the candidate with its self-hosted decoder and preserved four camera views. The generic glTF validator reported no errors or warnings but did not validate `EXT_meshopt_compression`. A missing decoder produced a recoverable inspector error, with no automatic uncompressed-model fallback. One local click-to-render timing sample was uncontrolled and cannot establish a speed gain. **Do not promote this candidate yet:** compare controlled network/CPU click-to-render, visual fidelity and decoder failures in Chromium, Firefox and WebKit first. KTX2 was not tested; the current 20 jet WebP images total about 2.01 MB inside the GLB. Scratch scripts, logs and images live in ignored `tmp/web-meshopt-jet-20261102/`.
