# Dynamic resolution and upscaling: source audit and delivery plan

**Snapshot:** 2026-11-15, America/Bogota. **App baseline:** `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`. **Engine:** official Godot `4.8.beta2.official.cafc17a19`, not a stable release; [`app/get-godot.sh:4-5`](../../../app/get-godot.sh) and the [Godot beta 2 announcement](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-2/) agree. [Beta 3](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-3/) was released 2026-11-09 but is not this pin. Custom FSR/DLSS and MetalFX experiments are separately identified below; do not assign their APIs to the official binary. This is a dated investigation and proposed work, not an implementation or platform qualification.

**Recommendation:** preserve the existing static reconstruction controls and complete their temporal/failure qualification first. Treat automatic dynamic resolution as a separate, default-off VQ/PT experiment. Start only where fresh GPU timing, bounded scale changes, buffer lifetime, temporal history, and moving-aircraft readability are proven on the exact engine and device. A runtime `scaling_3d_scale` setter is not itself a dynamic-resolution system. Reduce 3D rendering work only after showing a GPU/pixel-sensitive bottleneck; a lower scale does not repair CPU simulation, draw submission, shader compilation, input, or VSync pacing. Do not change the 240 Hz simulation, input ownership, recorder, flight physics, or audio clocks.

## Terms and present behavior

- **Static scale** fixes internal 3D pixels for a selected mode until a setting or output change. At 1920×1080 output, 0.85 nominally means 1632×918; 0.75 means 1440×810; exact 2/3 means 1280×720; 0.5 means 960×540. Pixel work does not necessarily scale perfectly with area and the upscaler has its own cost. Output and internal dimensions need runtime verification.
- **Dynamic resolution** is a feedback controller changing the internal dimensions within an agreed range in response to a real rendering budget. It needs a reliable delayed measurement, attribution, smoothing, bounded transitions, and an engine/provider able to handle changing input size. It is independent of the reconstruction provider.
- **Spatial upscaling** uses the current image (for example bilinear, FSR1, MetalFX Spatial); **temporal reconstruction** accumulates frames and needs correctly scaled depth/motion, jitter and history handling (FSR2/3, DLSS, MetalFX Temporal). Native-resolution FSR2 is temporal AA with overhead, not a speed mode. MSAA/TAA and sharpening are separate controls; temporal providers already own AA in this app. **Frame generation** creates additional displayed images and is not dynamic render scale, a substitute for real simulation/render rate, or evidence of lower input latency.
- Godot's [4.7 scaling documentation](https://docs.godotengine.org/en/4.7/tutorials/3d/resolution_scaling.html) is useful background, not a 4.8-beta2 guarantee: it describes bilinear, FSR1 and FSR2, runtime scale, AA interaction, and texture mip bias. Current [upstream architecture documentation](https://github.com/godotengine/godot-docs/blob/master/engine_details/architecture/internal_rendering_architecture.rst) warns that scaling changes reconfigure render buffers and says dynamic resolution is not yet supported. At the exact beta2 commit, the [Viewport scale setter](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/scene/main/viewport.cpp#L5113-L5121) clamps and forwards each call. When the RD buffer `configure()` is reached, the [pinned source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_rd/storage_rd/render_scene_buffers_rd.cpp#L127-L212) updates samplers, frees old named textures/custom buffer data and the MetalFX Spatial context, then recreates color/depth and applicable MSAA buffers. The app's isolated-patch test also asserts that the server scale, mode and viewport-size setters call buffer configuration ([`tools/graphics/metalfx/test_engine_patch.py:631-644`](../../../tools/graphics/metalfx/test_engine_patch.py)). The exact [server-side scale setter](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L1097-L1109) returns when the clamped float is exactly unchanged, but a different float calls reconfiguration even if both values produce the same integer pixel dimensions. For a nonzero viewport with valid buffers, the [configuration path](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L136-L310) converts the scaled width/height to integers, recalculates temporal jitter phase count and logarithmic mip bias, and calls buffer `configure()`. This is source evidence of resource work, not a measured hitch or proof of a safe temporal history transition. Do not write the setter every frame or assume vendor dynamic-input support is exposed by Godot.

A controller that directly writes the viewport property without integrating this owner would be overwritten on reapply and leave policy/diagnostic metadata inconsistent; coordinate preview, resize, fault guard and reset receipts through the existing reconstruction owner.

## Existing M1 evidence, with its limits

The later [DT-MAC-11a matched screen](../desktop-delivery-investigations/DT-MAC-11a/README.md#post-pose-temporal-correction-and-matched-m1-screen) used a source-hosted `f5219d7d` plus eight-file overlay and an isolated 19-patch beta2 editor on M1/8 GiB, macOS 27, Forward+/Metal, reported 1920×1080, FG/VSync/cap off. A scripted sky-heavy circle disabled physics/input; each mode had one 30-second sample after 10 seconds' warmup. Native before/after were 42.475/42.478 FPS, Spatial Quality 60.027 and Temporal Quality 57.646. Current-generation GPU completion was observed for both scalers, and Temporal reset serial 1 reached GPU completion. This is a useful, narrowly scoped screen, not a new measurement by this audit: only one sample per mode, no interval of uncertainty, nominal rather than independently verified input dimensions, unequal AA (Native/Spatial used 4× MSAA, Temporal used its own AA), no moving-image quality or physical display/pilot latency proof. Spatial's p95 was 19.553 ms and Temporal's was 19.821 ms, so neither establishes a locked 60 Hz. One 1920×1080 Temporal texture readback corroborates output pixels for that readback, not every sample's physical drawable. A preceding requested-mode screen's Temporal request actually fell back to Native and cannot be counted as a Temporal result.

A separate [corrected development package and moving-instance witness](../desktop-delivery-investigations/DT-MAC-11a/README.md#corrected-development-package-and-moving-instance-witness) observed a diagnostic historical ray-query snapshot and a fresh moved-instance query; it does not establish a complete scene, flight-motion, interpolation or image-quality pass. The same evidence has a fullscreen actual 1920×1080 capture, with four ObjectDB references at immediate exit retained as an unresolved observation. For frame generation, the isolated [native presentation fixture](../desktop-delivery-investigations/DT-MAC-11a/README.md#2026-11-15-pacing-callback-lifetime-and-complete-app-candidate) did record 31 generated OS-presented drawables and 232 real callbacks on its current presenter generation. This is not physical scanout or sustained product FPS. The subsequent full-app R5 correctly rejected FG on transparent geometry without motion vectors and did not activate full-flight FG; an offscreen alpha-input experiment failed eight image gates. A later R3 route reported Temporal reset GPU completion while FG did not activate. Keep these positive bounded results and failures distinct; full-scene interpolation, quality, presentation, latency and endurance remain open.

## Engine and temporal requirements

1. Freeze the **exact** editor/template/patch/SDK and retain the beta2 source result above; inspect each changed custom-engine revision, per-provider context creation/destruction and delayed GPU command/resource lifetime. The stock setter has an exact-float equality guard, but distinct scales can cause reconfiguration despite unchanged integer dimensions. Distinguish a render-buffer generation from a new drawn/presented frame. Benchmark transition cost and memory growth. For any engine fix, prefer an upstream implementation or the vendor SDK and integrate with existing `tools/graphics/native/` or `tools/graphics/metalfx/`; do not create a second scaler/controller.
2. Separate maximum allocation size from active input rectangle only if the exact renderer and scaler support it. Require valid aspect ratio, dimension alignment and size range, correct viewport/scissor, depth/motion inputs, clearing or excluding old pixels, and synchronization. Old allocations retire only after their GPU consumers complete. Resource reuse must be demonstrated, not assumed. If a safe low-hitch route is unavailable, keep this provider static and retain the user's fixed choice.
3. FSR2/3 or DLSS needs correct current/previous transforms, depth, motion-vector units/sign, exposure, jitter sequence and phase across size transitions, reactive/transparency behavior and history lifetime; visible camera cuts, teleport/reset/seek, scene/aircraft replacement, projection/FOV discontinuity and invalid resume require provider-consumed reset or safe context recreation. Do not reset normal movement or automatically reset on every small resize if the provider supports continuous dynamic history; verify the exact provider contract. If reset/size handling cannot be acknowledged, suspend adaptive operation and fall back safely. Godot's automatic mip adjustment applies on its documented Forward+/Mobile paths; any SDK-specific additional bias must be validated, not blindly stacked ([Godot 4.7](https://docs.godotengine.org/en/4.7/tutorials/3d/resolution_scaling.html#mipmap-bias), [AMD FSR 2 guidance](https://gpuopen.com/manuals/fsr_sdk/techniques/super-resolution-temporal/)).
4. Apple exposes a [dynamic-input descriptor switch](https://developer.apple.com/documentation/metalfx/mtlfxtemporalscalerdescriptor/isinputcontentpropertiesenabled), [per-device support and scale limits](https://developer.apple.com/documentation/metalfx/mtlfxtemporalscalerdescriptor), [input content width](https://developer.apple.com/documentation/metalfx/mtlfxtemporalscalerbase/inputcontentwidth) and [history reset](https://developer.apple.com/documentation/metalfx/mtlfxtemporalscalerbase/reset). Confirm Apple's input/output ratio convention versus Godot's normalized `input / output` scale rather than copying numeric limits between APIs. Apple recommends reset on camera cuts ([WWDC23](https://developer.apple.com/videos/play/wwdc2023/10125/)). Existing engine experiments and receipts under [DT-MAC MetalFX](../../plans/apple-metalfx.md) remain separate from the stock pin and do not qualify all dynamic cases.
5. Keep native-resolution 2D HUD/menu composition, cursor, overlays and independent preview/lake SubViewports unchanged. Godot's current architecture explicitly limits its described separate 2D/3D buffer path to Forward+/Mobile; assess Compatibility independently. Confirm actual drawable pixels versus logical/Retina points and no crop, stale borders or mismatched aspect ratio.

## Proposed controller contract — pending proof

The following starting constants are engineering hypotheses for an opt-in prototype, not tuned defaults or a promise of smoothness. Use only a renderer/provider combination that has passed the previous section; do not enable dynamic operation on stock or custom engines by assumption.

- Add a separate `Dynamic resolution: Off / On` setting beside the existing provider and quality choice. Off preserves the exact current behavior. On starts from the user's chosen static scale, never exceeds that choice, and never lowers below a tested quality floor. For 1080p flight, start with 0.85 as an **experimental minimum**, subject to VQ's motion/pilot gate; investigate 0.75 only if 0.85 remains readable and still insufficient. 2/3 and below require an explicit remaining case, not automatic silent selection. Any invalid intersection of user range, provider limits and tested floor disables dynamic operation with a reason and retains the static choice. 1080p has priority over 1440p/4K; 720p output is last.
- Use an explicit target selected from the existing FPS choices or a separately displayed target; `0`/unlimited or an unknown refresh/VSync period must not be treated as a valid target without an explicit policy. For target `f`, `B = 1000/f` ms per **real rendered** frame (60 Hz: 16.67 ms). Reserve initial 10% of `B` for headroom, then calibrate using real whole-frame results. Display effective target, provider, current scale and actual internal/output pixels when available; label estimates. Never count generated frames as real frames.
- Collect timestamped/sequence-associated GPU render timings with validity, freshness and actual drawn viewport identity. Account for all simultaneously drawn viewports and non-scalable passes; avoid double-counting overlapping GPU intervals. An accurate whole-GPU total may require a new engine/GPU timing seam or profiler. The pinned RenderingDevice has a timestamp-result frame identifier, but its render-thread access and connection to per-viewport timing must be validated before using it as the controller's sample identity ([source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L9086-L9109)). Separately record root-scalable GPU time, render CPU, whole process/frame intervals, physics and presentation/cap state. A screen that lacks trustworthy GPU timing runs static. Avoid treating a zero or repeated stale reading as free headroom. Measuring the root viewport alone can be a useful controlled signal only after paired evidence bounds all unmeasured GPU work; it is not total GPU time.
- After warmup, evaluate a rolling **minimum 120 distinct valid real-frame samples** spanning at least 2 seconds. Exclude focus loss, minimized/occluded, pause, loading, reset, resize/provider transition, captures, first-use shader hitches and invalid/stale samples; freeze at the current safe static value, expire the window and warm up anew. Coordinate measurement flags among controller, diagnostics and debug bridge with explicit lifetime ownership. Do not rewrite a pending Settings preview, fight Auto resize, or repeatedly touch disk.
- If GPU p90 exceeds 90% of `B` for two consecutive eligible evaluation windows, the scalable GPU portion has been shown responsive to a lower scale in controlled A/B tests, and contemporaneous CPU/physics and cap evidence does not explain the miss, decrease by one quantized step (initially 0.05) no more often than once per 5 seconds. If GPU p90 stays below 75% of `B` for 10 seconds with sufficient sample validity, raise one step toward the user's setting; do not increase faster than once per 10 seconds. Clamp to provider-supported dimensions and quality floor, with no write if rounded actual dimensions are unchanged. A single hitch causes no reaction. These thresholds, percentile, dwell and step are test parameters to revise using named-device evidence, not measured optima.
- If GPU time is below budget, or CPU/physics alone cannot meet the budget even when GPU time is also high, or cap/VSync explains the missed target, hold scale and report a CPU/pacing bottleneck as applicable; do not degrade aircraft detail based on FPS alone. If the GPU remains over budget at the floor, hold and report that the target cannot be met with the chosen settings. Neither GPU nor CPU scope alone proves end-to-end latency. Restore the saved static state on explicit Off, invalid telemetry, provider failure or settings rollback; preserve MSAA and requested provider exactly as the existing fallback contract requires.

A queued setting change, reset, resize and fault must be serialized with the existing reconstruction policy. The prototype should expose `requested`, `effective`, `held`/reason, viewport generation, measured sample age and scale-change event markers to the established collectors. If renderer buffers need frequent destructive reconfiguration, even a five-second dwell may fail acceptance: do not promote it by merely lengthening the interval.

Verify equal simulation tick/input/recorded replay across presentation settings; use existing recorder/golden identity rather than changing or re-recording physics goldens.

The FSR plan's existing gates are process-loop p95 ≤18 ms, p99 ≤25 ms and simulation/wall 0.99–1.01 for its 60 Hz scenarios; these do not by themselves prove presentation latency or moving-aircraft readability. Do not promote dynamic resolution solely on a GPU-time reduction if total frame behavior, input feel or visual readability worsens. Keep actual generated/displayed frames separate from real rendered frames.
