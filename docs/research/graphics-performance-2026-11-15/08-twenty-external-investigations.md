# Twenty external implementation investigations

**Completed research snapshot: 2026-11-15.** Application baseline: `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`. Continuation of the same `audit/graphics-performance-technologies-2026-11-15` branch. These **20 distinct investigations** inspect existing implementations, official contracts and relevant developer discussions, then map the evidence to OpenRC's files and existing owners. Research completion does not mean the proposed features were implemented or measured.

Read the [bounded implementation plan](05-integrated-implementation-plan.md) for objectives, M0–M5, engineering limits, acceptance and stop decisions. Read [06](06-validation-and-benchmark-plan.md) for the verification funnel. R01–R20 below are local research labels, separate from similarly named entries in other dated reports and from registered project step IDs.

## Method and expected use

Each investigation answers one implementation question and records inspected sources/revisions, what the external code actually does, the relevant OpenRC entrypoints, what to adopt, what to avoid, and the smallest useful next deliverable. Examples are inspected at exact commits where obtainable; current vendor documentation is distinguished from the project's older pins. Developer issue/forum discussions supply real failure cases and context, corroborated against source or an official contract before informing a technical conclusion.

The recommendations are selective. **The immediate action is to strengthen the existing measurement path once, then improve one current provider and finish the existing Reflex path.** A feature that lacks a measured need or required capability closes as deferred/retain baseline. Research on XeSS, XeLL, direct Vulkan latency and path-tracing forks does not turn those technologies into mandatory work.

## Dynamic resolution and reconstruction — R01–R07

| Investigation / existing example | Finding that changes the decision | OpenRC deliverable and boundary |
| --- | --- | --- |
| [R01 · Godot scaling and a real community addon](investigations/R01-godot-dynamic-scaling.md) | Godot's exact changed-scale path reconfigures render buffers. FiveNineGames' addon uses target FPS and writes scale, without proving a GPU bottleneck. Maintainer discussion corroborates the allocation concern. | M1 measures the existing transition; M2 stays conditional on fresh GPU feedback, acceptable transition cost and readability. Avoid adding an independent FPS-based writer. |
| [R02 · Unity's handler and adaptive sample](investigations/R02-unity-dynamic-resolution.md) | The public pipeline handler owns bounds/camera/allocation behavior; a separate sample supplies feedback. That sample's timing assumptions need scrutiny. | Reuse the separation of policy from resource ownership and slower quality recovery. Keep OpenRC's existing reconstruction owner; Unity's resource behavior is not a Godot guarantee. |
| [R03 · AMD FSR sample and dispatch contracts](investigations/R03-amd-fsr-integration.md) | Context maximum dimensions differ from actual dispatch dimensions; dynamic input, motion/depth, jitter and reset must agree. SDK 2.4 sample behavior cannot be assigned to older project providers. | If FSR is selected for M1, close one fixed-size history/transition defect using existing fixtures. M2 adapts only after exact-provider dimensions, reset and lifetime pass. |
| [R04 · NVIDIA DLSS extents](investigations/R04-nvidia-dlss-dynamic-input.md) | The upstream fork's tags use null extents; both pinned/current SDK guides require explicit regions for a subrectangle DRS design. Fixed-size textures are a different case. | Inspect prepared engine/patches, query SDK bounds and pass correct extents if a maximum-allocation design is chosen. Do not copy one extent to differently sized input and output resources. |
| [R05 · Apple MetalFX dynamic input](investigations/R05-apple-metalfx-dynamic-input.md) | Apple's API distinguishes allocation/output dimensions from changing input content; the Godot bridge must actually implement that contract. | Use the existing DT-MAC patch/harness if MetalFX is selected. Verify descriptor, content dimensions and completed history behavior. The full Apple sample archive was inaccessible; its code is not claimed as inspected. |
| [R06 · Intel XeSS guide versus actual sample](investigations/R06-intel-xess-dynamic-input.md) | A newer guide supports bounded dynamic input while an older guide says unsupported; the inspected Vulkan triangle sample still uses a fixed-size flow. | Adopt queried bounds and actual extents as provider requirements. Defer a new XeSS integration until an existing provider demonstrably cannot meet the target and a maintained engine path is justified. |
| [R07 · Vulkan Guide's reusable render targets](investigations/R07-vulkan-render-target-sizing.md) | A real educational renderer retains large targets and varies the active extent; its simple blit and coarse resize waits do not solve temporal rendering or production lifetime. | Consider an isolated engine change only if M1 proves allocation cost is a blocker. Keep output/HUD stable and bound GPU allocations; do not recreate the swapchain for every internal scale step. |

**Shared decision:** a provider's ability to accept a changing input size is only one part of DRS. Godot must handle resource lifetime and all input consumers; OpenRC must own policy, preserve user intent and observe valid GPU feedback. A lower average GPU time with worse transition hitches or small-aircraft attitude clarity fails the feature. The initial 0.85–1.0 range at 1080p is a proposed test range, not a universal provider limit or tuned default.

## Latency and scheduling — R08–R12

| Investigation / existing example | Finding that changes the decision | OpenRC deliverable and boundary |
| --- | --- | --- |
| [R08 · Streamline Reflex integration](investigations/R08-streamline-reflex-integration.md) | Real sample code shows frame-token, Sleep and marker ownership. Pinned 2.11.1 and current 2.14.16 have different Vulkan support/implementation histories. | M3 finishes the existing fork's Off/On/Boost comparison before an SDK upgrade. SDK verification and physical RC response remain separate claims; missing flash verification need not block the existing optical experiment. |
| [R09 · DXVK's Linux implementation](investigations/R09-dxvk-linux-latency.md) | DXVK owns a D3D translation/swapchain path with real latency waits; it cannot infer missing game input calls. Native Godot Vulkan does not run through that D3D interface. | Establish the actual native Linux baseline and simple cap/VSync alternative. Learn from frame/lifetime ownership; do not prescribe DXVK environment settings as native Godot integration. |
| [R10 · Native `VK_NV_low_latency2`](investigations/R10-vulkan-low-latency.md) | Device feature, swapchain creation, sleep/wait and submission attribution are versioned contracts. NV application-frame IDs and KHR present IDs have distinct semantics. | A conditional feasibility note names the exact engine hooks and device. One pacer owns a frame; do not stack a direct extension over Streamline or assume a GDScript control supplies the required hooks. |
| [R11 · AMD Anti-Lag SDK and Dagor Vulkan code](investigations/R11-amd-anti-lag.md) | AMD's inspected SDK sample is DirectX; a real Dagor engine path shows separate Vulkan input/present stages. These are distinct API integrations. | After a measured AMD-specific need, check the exact feature/driver/frame boundary and select one native candidate. FSR does not activate Anti-Lag; Windows support does not prove native Linux support. |
| [R12 · Intel XeLL sample](investigations/R12-intel-xell.md) | The current guide/sample imposes Windows/D3D12, device/display, context and marker requirements. Its example's threading does not identify OpenRC's physical radio event. | Defer without an independently justified D3D12 route. Do not add another SDK or renderer merely for a latency brand, and never place a blocking call at every physics tick. |

**Shared decision:** complete one existing native path before adding another. A fixed 240 Hz physics loop, render frame, SDK marker, OS present and physical stick event are different identities. The F6 optical route uses live input and excludes scripted/frametime/capture flags; collect incompatible diagnostics separately. No PC-latency, mouse or GPU-completion figure is relabeled as RC stick-to-photon latency. A CPU-limited target can reject DRS while still justifying a Reflex/Boost comparison.

## Measurement without tool proliferation — R13–R15

| Investigation / existing example | Finding that changes the decision | OpenRC deliverable and boundary |
| --- | --- | --- |
| [R13 · PresentMon console and source](investigations/R13-presentmon-existing-capture.md) | Existing Windows ETW tooling already distinguishes presentation-related intervals; Vulkan/HWS accuracy and optional frame instrumentation constrain claims. | Attach one bounded capture to the current evidence when useful. No new overlay/service integration; unavailable fields remain unavailable. Half-day schema feasibility fits inside M0. |
| [R14 · Tracy's Vulkan collector](investigations/R14-tracy-bounded-attribution.md) | Existing asynchronous query handling tracks availability and identity; it does not force unfinished queries to complete in its normal collection loop. | Use a narrow existing-tool trace only for an unresolved engine hitch. No new profiler/viewer or mandatory production dependency. A one-day attribution review must end in a concrete change or defer decision. |
| [R15 · Godot timing, maintainer reports and exact Metal code](investigations/R15-godot-timing-contract.md) | Historical Metal timing limitations changed; the exact beta2 Metal3 driver implements conditional timestamps despite base-class stubs. OpenRC's shared measurement ownership and sample identity remain separate problems. | Repair the two existing consumers and reducers; retain unknown freshness when the backend cannot associate samples. Do not build a replacement Mac timer based on an obsolete forum statement. |

**Shared decision:** M0 has **five engineering days total** on the first reference configuration. Its output is a repaired measurement boundary and an implementation decision. The mandatory changes are shared timing ownership, truthful sample/report fields and a reproducible baseline using existing tools. Complete DRS telemetry on every backend, a new dashboard, full physical latency equipment and a universal pass profiler are outside that milestone. Missing evidence narrows the feature claim; it never turns an unknown into a pass.

## Ray tracing — R16–R20

| Investigation / existing example | Finding that changes the decision | OpenRC deliverable and boundary |
| --- | --- | --- |
| [R16 · Godot RD implementation and fixes](investigations/R16-godot-ray-tracing-api.md) | Exact-version Vulkan query fixes are present, while the pinned query-only/SBT route needs proof. Low-level BLAS/TLAS APIs do not create a finished scene shadow. | Two-day capability/scene-access decision on one named device; use a legal supported route or defer. Avoid claiming an old fixed bug still blocks beta2 or inventing an SBT value. |
| [R17 · NVIDIA Vulkan RT tutorial](investigations/R17-nvidia-vulkan-ray-tracing.md) | Concrete BLAS/TLAS/visibility code teaches ownership, but synchronous build waits and opaque geometry are instructional simplifications. | Reuse stable mesh/instance concepts and correct light contribution. Do not block the flight loop with tutorial-style waits or assume control-surface/foliage correctness. |
| [R18 · Khronos ray-query sample](investigations/R18-khronos-ray-query-sample.md) | The real fragment-query example uses opaque geometry; cutout foliage needs candidate traversal and the actual alpha/material rule. Historical validation gaps require exact-version interpretation. | Start with a controlled opaque scope; require complete relevant material/geometry coverage for normal flight or keep whole-viewport raster. A clean validation log is useful but not the entire proof. |
| [R19 · Apple Metal RT and OpenRC's bridge](investigations/R19-apple-metal-ray-tracing.md) | Metal capability, M3-class hardware acceleration, Godot native backend implementation and an executed effect are distinct. M1 API witnesses are limited evidence. | Continue the existing DT-MAC producer/denoise work if justified; avoid a second Mac RT roadmap. Dedicated hardware and actual current-scene execution need separate checks. |
| [R20 · NVIDIA and community Godot path-tracing forks](investigations/R20-godot-ray-tracing-forks.md) | There is substantial renderer code, but shader/material portability, engine divergence, redistribution and reproducible refs matter. A referenced Apple branch was unavailable although a historical commit remained readable. | Consult exact components; defer wholesale engine replacement/path tracing. Deliver one bounded direct-sun experiment only after a visible need/headroom decision. |

**Shared decision:** the first visible RT result must apply visibility once to direct sun, even in a controlled fixture. The two-week checkpoint asks for that useful result or a stop decision. Normal flight additionally needs current aircraft/hinges, vegetation deformation/alpha, off-camera casters, synchronization and recovery. Proposed 2.0 ms additional GPU p95 and 128 MiB incremental peak allocated GPU resources are ceilings for the whole effect, subordinate to measured whole-frame headroom; no hardware result is implied.

## What to execute now, later, and only after new evidence

| Disposition | Action |
| --- | --- |
| **First delivery** | M0: fix timing leases and compatible sample truth in current consumers/reducers; establish an unchanged repeat on one real 1080p host; close the decision within the cap. |
| **Next product change** | M1: select one existing fixed provider and correct a demonstrated failure/transition cost, or confirm the fixed option already meets the goal. M3 can complete the existing Reflex path independently after its relevant baseline. |
| **Conditional feature** | M2: add default-off DRS only with a real pixel-sensitive target miss, safe transitions and valid feedback. Keep a documented static-only result when those conditions fail. |
| **Later visual experiment** | M4: one bounded sun-shadow effect with a visible purpose and budget; M5 qualifies only the accepted package rows. |
| **Deferred unless a specific gap justifies them** | New XeSS/XeLL providers, direct NV/AMD native latency paths, broad persistent-allocation engine redesign, wholesale RT forks and path tracing. They do not block current provider/Reflex delivery. |

Research is sufficient for this first handoff. Revisit a source when the engine/SDK changes, a contradiction affects the selected implementation, or a concrete native result invalidates the assumption. A new round of research or a new tool needs that specific decision; collecting more references is not a milestone outcome.

## Evidence limits and review

All twenty investigations are source/design work. No new target GPU, export, native flight or physical latency measurement was performed. Apple sample archive limitations and the unavailable experimental fork branch are disclosed in their individual studies. No outside demo speedup is presented as an OpenRC benefit. A matching API, successful call or listed setting is distinguished from actual execution, useful output and accepted support.

Independent review of the revised plan resolved concrete risks: vendor flash verification blocking otherwise valid optical work, physical input being confused with replay-compatible diagnostics, unchanged-control repetition, formal optimization versus descriptive latency thresholds, overly strict persistent-allocation prerequisites, and exact-once sun lighting at the first RT checkpoint. The [verification record](07-sources-and-verification.md) and [validation receipt](evidence/validation.json) identify what was actually checked. These reviews improve the plan; they are not hardware evidence.
