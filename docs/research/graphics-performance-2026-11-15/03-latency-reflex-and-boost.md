# Latency, NVIDIA Reflex and Boost: source audit

2026-11-15 · Baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`. This is a source and primary-document review, not a new build, performance run, physical measurement or hardware qualification. Existing retained results are identified below. The owning plans are [VQ-07](../../plans/advanced-graphics.md), [controller F6](../../plans/controller-support.md), [GDU](../../plans/godot-4.8-upgrade.md), and the desktop/performance tracks in the [registry](../../README.md#tracks-plans-and-step-ids).

## Finding

**Reflex is partly implemented in a real, isolated native engine, and its latency benefit is unmeasured.** The normal application has a saved request and an honest capability/status adapter; the optional Windows/Vulkan NVIDIA package has actual Streamline scheduling and markers. The standard official Godot 4.8-beta2 build is a different engine and does not acquire Reflex from the label, preference, DLLs or camera patch. A historical custom-engine RTX 3090 run demonstrated SDK calls, mode transitions, an export and marker progress; it did not establish radio-to-photon improvement, NVIDIA certification, current-source cross-device performance, or a general release gate.

Preserve the owner-selected VQ-07h investigation. The next discriminating work is a matched 1080p latency and pacing comparison on the already built path, including a real RC transmitter and the existing optical marker, before expanding vendor integrations or changing any physics timing. If a safe standard-renderer configuration meets the same measured goal with less maintenance, retain that option. No static source inspection can establish which will win.

## Input is not a render frame

In fixed-wing flight [`main.gd:797`](../../../app/main.gd#L797) disables accumulated input events. [`flight_session.gd:1332`](../../../app/sim/flight_session.gd#L1332) reads radio/joystick values through `Input.get_joy_axis`; at priority −1 its physics callback polls and shapes commands before the simulation step ([flight_session.gd:3059](../../../app/sim/flight_session.gd#L3059)). [`project.godot:44`](../../../app/project.godot#L44) fixes physics at 240 Hz with at most 12 catch-up steps per rendered frame; below about 20 FPS simulation may slow instead of keeping real time. The rendered pose interpolates between accepted tick states ([simulation.gd:658](../../../app/sim/simulation.gd#L658), [main.gd:1862](../../../app/main.gd#L1862)). Other vehicle sessions require their own checks.

One render iteration can contain zero, one or multiple fixed ticks. An engine marker called “simulation start” is a frame-stage marker, not proof that a particular transmitter sample reached a particular visible aircraft pose. A JIT wait placed before a message loop may change when multiple tick samples arrive or are consumed. Moving the sample, changing 240 Hz, extrapolating state, or bypassing interpolation to chase a vendor metric changes an input/simulation contract and requires physics/input-owner review and replay/behavior tests. This research proposes no such change.

The optional [`LatencyPatch`](../../../app/input/latency_patch.gd#L1) is a 192-pixel camera target: after the current flight reader polls, it turns white/black on a chosen raw-axis threshold; gray means inactive ([lines 147–175](../../../app/input/latency_patch.gd#L147)). It neither calls Reflex nor calculates milliseconds. [`test_latency_patch.gd`](../../../app/tests/test_latency_patch.gd) and its route/CLI tests check logic and safety, not optical response. It supports external measurement of *physical stick movement to visible threshold*; a separate first visible control-surface or aircraft response includes different presentation and dynamics. An NVIDIA mouse-click flash/PC latency value cannot qualify an RC-radio path.

## What the technologies actually provide

| Candidate | Applicability and risk as of 2026-11-15 |
| --- | --- |
| Reflex On | NVIDIA's SDK coordinates CPU/GPU work and places the wait before the next useful work/input so a GPU-bound queue can be shortened. Benefit depends on workload and timing. SDK mode, driver control-panel Low Latency, VSync, and the frame limiter are different controls; the in-game SDK has more scheduling context. Neither an FPS increase nor 20% lower latency is guaranteed for OpenRC. |
| On + Boost | Adds a request to maintain higher GPU clocks in underutilized/CPU-bound situations. NVIDIA explicitly describes a potential power cost, with a workload-dependent latency change. Keep Boost opt-in, explain its energy/heat tradeoff, and measure GPU power, clocks, frame pacing and responsiveness. It is not overclocking or Frame Generation. |
| Streamline and Vulkan | Streamline has vendor-specific features; PCL statistics can be available across vendors, whereas Reflex Low Latency/Boost are NVIDIA capabilities. Runtime feature and `lowLatencyAvailable` checks—not a GPU-name guess—govern UI and accepted mode. Current upstream [2.14.0 changelog](https://github.com/NVIDIA-RTX/Streamline/blob/main/changelog.txt) says Vulkan Reflex uses `VK_NV_low_latency2` when exposed and falls back to its NvAPI v1 path otherwise; pre-Turing Vulkan Reflex was removed in that version. Do not apply the generic GeForce 900+ table to all versions/APIs. This project remains on **2.11.1**, and its [2.14.16 trial was rejected](../../../tools/graphics/native/README.md#engine-provenance-and-historical-trial) after startup errors. The [older marketing FAQ](https://developer.nvidia.com/rtx/streamline) saying Vulkan is coming conflicts with later source/changelog; use the exact pinned version's guide, actual capability and observed behavior. |
| Vulkan native option | [Khronos `VK_NV_low_latency2`](https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_low_latency2.html), revision 3, is a non-ratified device extension: configure a supported swapchain, sleep before input, attribute submissions/presents to frame IDs, and use appropriate markers/timings. It is an alternative engine integration path, not proof that the 2.11.1 fork uses this extension or that any Linux driver supports it. Query the extension, features and actual surface/device at runtime; validate the selected OS/driver/GPU. Never run two independent pacers for the same frame. |
| AMD | [GPUOpen Anti-Lag 2 v2.0.6](https://gpuopen.com/anti-lag-2/) lists Windows 10/11, RDNA 1/RX 5000 or newer, and driver minima 24.6.1 DX11, 24.7.1 DX12 and 24.9.1 Vulkan. Its [public SDK repository](https://github.com/GPUOpen-LibrariesAndSDKs/AntiLag2-SDK) exposes DX11/DX12 headers; the [integration guide](https://gpuopen.com/learn/integrating-amd-radeon-anti-lag-2-sdk-in-your-game/) places Update before input polling. Khronos separately specifies [`VK_AMD_anti_lag`](https://docs.vulkan.org/refpages/latest/refpages/source/VK_AMD_anti_lag.html), with input and present frame association. Resolve this documentation/API distinction and validate the actual Windows/Vulkan integration before claiming coverage; no Linux support is established here. Anti-Lag 2 is not included automatically by OpenRC FSR. |
| Intel | The current [XeLL guide](https://github.com/intel/xess/blob/main/doc/xell_developer_guide_english.md) specifies Windows x64, D3D12, DXGI flip model and a display connected to the rendering GPU. [XeSS 3](https://github.com/intel/xess) supports standalone XeLL on eligible Arc hardware; non-Intel support is tied to XeSS-FG, not a universal standalone substitute. The OpenRC trial deliberately disables D3D12, so this is a separate backend and validation project. |
| Non-vendor fallback | Preserve the ordinary engine path on unsupported hardware or SDK failure. Compare VSync, refresh/VRR, a modest cap and scene cost on each real platform; the driver or compositor can change presentation. In [official beta2 RenderingDevice source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L8615), a main-surface frame queue is initialized from its setting with a minimum of two, separate from the requested [swapchain image count](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L5481). Its [Vulkan backend](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/vulkan/rendering_device_driver_vulkan.cpp#L3807) chooses a supported present mode (falling back to FIFO), clamps the desired image count to surface limits, and obtains the actual images. Godot background documentation says double buffering may lower lag but make missed refreshes more disruptive. These details are not a Compatibility or custom-fork guarantee: check the active renderer and effective swapchain before any change. Event accumulation is already disabled for fixed-wing flight. No universal settings default follows from these sources. |
| Reflex 2 / Frame Warp | NVIDIA describes a separate late mouse/camera resampling and frame-warp technology and its [developer page](https://developer.nvidia.com/performance-rendering-tools/reflex) still offers notification for general integration. A public sample may expose a distinct experimental path; that does not establish a distributable, compatible OpenRC integration. It is not a faster physics tick or a demonstrated benefit for RC sticks and aircraft attitude. Treat it as future research only. Frame Generation is likewise separate and currently disabled in the package. |

## Integration boundary and strongest counterexamples

A GDScript timer in `_process` cannot replace the native sleep, register device/queue/swapchain hooks before creation, correctly assign frame tokens across the render thread, bracket actual submissions/presents, or observe scanout. A new native path needs early SDK/extension initialization, a real feature query, device/queue/swapchain creation and recreation, a frame token associated across threads, markers and sleep at the version-specific points, serialized non-thread-safe SDK calls, shutdown ordering, and an explicit policy for background/minimize, resize, device loss and unavailable libraries. The stock engine may need a maintained patch and matched templates; a GDExtension is sufficient only if it proves access to all required lifecycle and ordering points. Do not infer that from a native handle alone. For `VK_NV_low_latency2`, follow the [Vulkan frame-attribution rules](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html), including multiple submissions/presents and out-of-band queues where applicable.

**Good-enemy case:** if the simulator is CPU/physics bound, capped, VSync/compositor bound, or already has a short GPU queue, Reflex may provide little benefit while extra waits, Boost power or render-thread synchronization make pacing worse. A high FPS or a successful marker counter is not a counterexample to that concern. Compare an unmodified standard package at matched effective presentation and real frame rate, the custom fork with Reflex Off, On, and On + Boost, and a simple cap/VSync configuration. The stock/fork comparison also measures engine differences; only the within-fork mode comparison isolates the Reflex request. Keep the same content and tick/input tape where replay is appropriate; a physical stick experiment is separately repeated. Use one SDK pacer at a time.

## Minimum evidence before a broader implementation

1. **VQ-07a/c and F6 baseline:** on an isolated 1080p native host, record exact app/source/engine/template/runtime hashes, GPU, driver, OS, renderer, clocks/power, monitor refresh/VRR, window mode, effective present mode, VSync, cap and input transport. Establish repeated CPU-limited and GPU-limited workloads from actual CPU/GPU timing and queue evidence, not FPS alone. Use the existing VQ plan's warmup, repeated alternating pairs, p95/p99 frame intervals and simulation/wall ratio; capture dropped frames and real versus displayed frame counts only when the instrument can identify them.
2. **F6 physical response:** run at least 30 filmed transitions per qualified primary transmitter transport per condition as the existing F6 minimum, and target at least 100 per condition across repeated sessions for p95 analysis; treat a 30-transition p95 as preliminary. Keep the same threshold, viewport location and display scan position; record camera frame interval, uncertainty and missed/ambiguous transitions. Report median and p95 with per-run distributions, plus stick-to-patch and stick-to-first-control-surface response separately from aircraft movement. Include GPU-bound and CPU-bound cases, cap/VSync/VRR as controlled variables, and retain all trials. GDScript timestamps cannot see peripheral acquisition, queue/present scanout and display response; PC/PCL metrics are complementary, not an optical substitute.
3. **VQ-07h integration verification:** implement and validate NVIDIA's required driver-controlled flash trigger when applicable; follow the exact [Reflex verification checklist](https://developer.nvidia.com/rtx/streamline/get-started) under its stated full-screen, VSync-off, FG-off conditions and inspect marker ordering in Nsight. Repeat representative normal player VSync/window conditions separately. Check Sleep and markers in Off, On and Boost, token-to-present mapping, multiple physics ticks, pause/minimize/restore/resize, hot mode changes and session shutdown. The vendor's pass thresholds are integration tests under specified conditions, not a promise for this simulator or physical RC transport.
4. **VQ-07g/h, GDU and DT decision:** retain the existing supported fallback and saved-request/accepted-mode distinction. Evaluate power, heat, pacing, radio response and visual behavior; keep a result only if repeated paired differences exceed the measurement uncertainty without breaking the 240 Hz/replay contract or existing acceptance gates. Test an exported build on each named target, unsupported device and missing/invalid SDK failure path, with matched editor/template receipts, dependency/license/identity review and long-session evidence. Do not generalize from RTX 3090 or an editor smoke. A later AMD Vulkan or Intel D3D12 prototype needs its own pinned API, capability/packaging and physical A/B evidence; it does not follow automatically from this NVIDIA trial.

## Effort and dependencies

These are order-of-magnitude planning ranges for one experienced graphics engineer, not commitments; access to a quiet native host, transmitter, optical equipment and owner review is assumed. Setup, driver defects, equipment availability and repeated qualification can dominate elapsed time. Stop after any phase if the measured need is absent.

| Existing owner | Work | Rough effort and acceptance |
| --- | --- | --- |
| VQ-07a/c + F6 | Establish 1080p baselines and paired physical/PC measurement protocol on the existing package. | 2–5 engineering days plus host/equipment scheduling; repeatable labeled data and uncertainty before interpreting an effect. |
| VQ-07h | Add and validate the missing flash-trigger integration on the pinned fork, then inspect SDK frame/marker timing. | 2–5 days for a bounded change and fixture if hooks are suitable; vendor verification and failure/lifecycle checks must pass before it is called integrated. This estimate excludes new SDK or engine upgrades. |
| F6 + VQ-07g/h + DT | Repeat Off/On/Boost, power and pacing trials, then test the exported candidate and unsupported fallbacks. | 3–8 days per named host/transport matrix, plus analysis and hardware/pilot availability; only measured and repeatable results support qualification. |
| VQ-07h + GDU/DT | Optional AMD Vulkan, Intel D3D12 or official-engine port after a justified need and an owner decision. | Roughly 2–6+ weeks per new native integration **before** cross-device qualification; first prove versioned API and engine lifecycle feasibility. Unknown platform/SDK constraints can invalidate this range. |
