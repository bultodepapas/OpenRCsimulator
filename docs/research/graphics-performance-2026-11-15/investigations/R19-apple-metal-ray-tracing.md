OpenRC application `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`; inspected Apple documentation and presentation code, exact official Godot beta 2 source, and existing OpenRC native evidence. ## Question and source findings

**Question:** Does an M1 or a Mac with Metal ray tracing automatically execute OpenRC's proposed Godot RT pass? **Decision:** No. Metal API capability, dedicated intersection hardware, Godot's backend implementation and the actual effect are separate gates. Reuse the existing DT-MAC work; do not create a second Mac roadmap.

Apple's [ray-tracing API collection](https://developer.apple.com/documentation/metal/ray-tracing-with-acceleration-structures) describes acceleration structures plus either intersectors or inline intersection queries. Intersectors work in compute kernels on supported GPUs, and in render shaders on Apple silicon; queries return candidate control to a calling shader. Apple's [sample page](https://developer.apple.com/documentation/metal/accelerating-ray-tracing-using-metal) supplies a downloadable sample and documents macOS 11 or later, iOS 14 or later and Xcode 12 or later for that sample. These are sample setup requirements, not sufficient per-device support. Query [`supportsRaytracing`](https://developer.apple.com/documentation/metal/mtldevice/supportsraytracing) and validate actual descriptors and execution.

Apple's 2021 [intersection-query presentation](https://developer.apple.com/videos/play/wwdc2021/10149/) contains concrete shader pseudocode: loop `next()`, inspect candidate type, retrieve geometry/primitive/barycentric data, interpolate UV, sample alpha, and commit an accepted triangle; test the committed intersection after traversal. This is useful evidence for the missing material operation, not a ready-made Godot shader. The separate [per-primitive data example](https://developer.apple.com/documentation/metal/improving-ray-tracing-data-access-using-per-primitive-data) illustrates retrieving data from an intersector or query. Apple's downloadable complete project was not inspected here.

Apple maps M1 to [Apple family 7 and M3/M4 to family 9](https://developer.apple.com/documentation/metal/mtlgpufamily). Its [M3/A17 Pro talk](https://developer.apple.com/videos/play/tech-talks/111375/) identifies the family 9 intersector's hardware acceleration and recommends considering an intersector instead of a query where appropriate. M1 lacks that family 9 dedicated intersection acceleration, yet API capability can exist. OpenRC's [M1 receipt](../../desktop-delivery-investigations/DT-MAC-11a/README.md#rt-and-validation-follow-up) records capability and an isolated RT/denoising witness; it is not an M1 hardware-acceleration or game-performance claim. Do not equate a chip name, `supportsRaytracing`, or a witness with complete coverage or affordable flight rendering.

At official Godot `4.8.beta2.official.cafc17a19`, the [base native Metal driver](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/metal/rendering_device_driver_metal.cpp#L2378) has unsupported BLAS/TLAS, RT pipeline and build-command methods. Its [header marks these RT operations `final`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/metal/rendering_device_driver_metal.h#L495), so the separately inspected [Metal 3 subclass](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/metal/rendering_device_driver_metal3.cpp) cannot replace them; it separately overrides timestamp operations. The base RT stubs remain the relevant implementation. This does not mean all Metal functionality is absent. The broader [Godot proposal discussion](https://github.com/godotengine/godot-proposals/discussions/5162) contains user interest and requests for Apple support; it is discussion, not proof of an implemented backend.

## OpenRC bridge and finite next step

The existing isolated [MetalFX engine work](../../../../tools/graphics/metalfx/README.md#renderer-owned-scene-geometry-diagnostic) has opt-in 0005 immutable opaque triangle build/query and 0018 one-shot renderer-owned scene input. [Native evidence](../../desktop-delivery-investigations/DT-MAC-11a/README.md#native-scene-input-prerequisite-and-conditional-reset) records ground and aircraft-component hit/readback; the [moving-instance witness](../../desktop-delivery-investigations/DT-MAC-11a/README.md#corrected-development-package-and-moving-instance-witness) proves a historical snapshot can remain valid after motion, not that it reflects the current frame. Its synchronous readback is not a render loop. A current producer must track instance and material generations, removal, wind/alpha, off-camera casters and lifetime. [Aircraft hinges](../../../../app/render/airplane.gd), [propeller presentation](../../../../app/render/propeller_blur.gd), and [vegetation](../../../../app/scenery/imported_vegetation_wind.gdshader) are explicit coverage requirements.

Keep [DT-MAC-13d1–d3](../../../plans/apple-metalfx.md) responsible for producer, denoising and product gates with VQ/GDU; VQ-07h path tracing remains deferred. If a measured 1080p defect and headroom justify it, reuse that work: within two days record actual device/OS, capability, creation, known hit/miss and clean fallback; within two weeks show a bounded visible direct-sun result or stop. Apply visibility once to the existing direct-sun term, retain full raster when scene coverage is incomplete, default Off, and keep physics unchanged.
