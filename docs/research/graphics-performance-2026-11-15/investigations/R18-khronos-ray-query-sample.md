# R18 — Khronos inline ray queries: portable concept, opaque sample

Research snapshot: **2026-11-15**. OpenRC application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`. Inspected the public Khronos Vulkan-Samples `main` at [`b4fb432b80234e54cf7be7411f20b65494a5b0f5`](https://github.com/KhronosGroup/Vulkan-Samples/commit/b4fb432b80234e54cf7be7411f20b65494a5b0f5), dated 2026-11-12, plus specification and issue history. Source-only; no sample, GPU, or validation layer was run.

## Question and code findings

**Question:** Does a standard Vulkan ray query provide a portable, ready-made alpha-correct shadow for OpenRC? **Decision:** It is a useful API-level pattern when separately supported; the sample itself is opaque and is not a complete Godot scene renderer. Check actual backend and features and preserve raster fallback.

The [sample description](https://github.com/KhronosGroup/Vulkan-Samples/blob/b4fb432b80234e54cf7be7411f20b65494a5b0f5/samples/extensions/ray_queries/README.adoc) says it casts shadows from a fragment shader over Sponza with ordinary vertex/fragment stages. Its [host code](https://github.com/KhronosGroup/Vulkan-Samples/blob/b4fb432b80234e54cf7be7411f20b65494a5b0f5/samples/extensions/ray_queries/ray_queries.cpp#L81) requests `VK_KHR_ray_query`, acceleration structures, buffer device addresses and dependencies, then requires the corresponding device features. It builds triangle BLAS and an instance TLAS and binds the latter as an acceleration-structure descriptor. No separate RT pipeline/SBT is used by this Vulkan sample; that does **not** settle the [Godot beta 2 SBT validation concern](../04-ray-tracing-in-godot.md#exact-version-and-technical-boundary). Query and pipeline availability are different capabilities.

The [fragment shader](https://github.com/KhronosGroup/Vulkan-Samples/blob/b4fb432b80234e54cf7be7411f20b65494a5b0f5/shaders/ray_queries/glsl/ray_shadow.frag#L86) initializes a query from surface to point light, requests first accepted hit, proceeds once, and checks the committed intersection; its AO function separately casts nine short rays. It sets the direction to `light_position - position` with `tMax = 1`, rather than normalizing that direction and using distance. Its final sample color combines the toy shadow and AO, not a Godot direct-sun lighting term. Reuse the principle, not those scene-specific values or final-color composition.

Crucially, the [BLAS construction](https://github.com/KhronosGroup/Vulkan-Samples/blob/b4fb432b80234e54cf7be7411f20b65494a5b0f5/samples/extensions/ray_queries/ray_queries.cpp#L241) marks the sample geometry `VK_GEOMETRY_OPAQUE_BIT_KHR`. For nonopaque foliage, the shader must proceed through candidate intersections, fetch the correct instance, primitive, barycentrics, UV and current texture/material, and confirm only candidates passing the same alpha rule. A single `proceed` and committed-hit check from an opaque example cannot provide that. The normative [GLSL ray-query extension](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GLSL_EXT_ray_query.txt) and [Vulkan ray-query reference](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_ray_query.html) describe query traversal; neither executes a Godot material automatically.

The sample's [AS helper](https://github.com/KhronosGroup/Vulkan-Samples/blob/b4fb432b80234e54cf7be7411f20b65494a5b0f5/framework/core/acceleration_structure.cpp#L133) allocates scratch, submits a one-time build and flushes before releasing scratch. A real asynchronous frame needs correctly scoped build-write to shader-read ordering, BLAS-before-TLAS dependencies and safe resource retirement. In [ValidationLayers issue #9076](https://github.com/KhronosGroup/Vulkan-ValidationLayers/issues/9076), a developer reported an unreported TLAS hazard; the maintainer explained the descriptor-access validation setting and [reported a fix](https://github.com/KhronosGroup/Vulkan-ValidationLayers/issues/9076#issuecomment-2702333512) on 2025-03-05. This is historical evidence of a validation blind spot, not a claim that current versions still lack the fix. Use appropriate validation configuration and explicit dependency reasoning, not a clean log as sole proof.

## OpenRC action and stop

[Compatibility is the default](../../../../app/project.godot), so only a verified Forward+/Vulkan combination is an initial candidate. The [shadow owner](../../../../app/render/shadow_settings.gd) must continue to preserve the projected/native aircraft-height cue. [Imported vegetation](../../../../app/scenery/imported_vegetation_wind.gdshader) and [treeline](../../../../app/render/treeline.gdshader) change vertices and can discard pixels; moving [aircraft controls](../../../../app/render/airplane.gd) also need current transforms. If the actual relevant material, offscreen caster or receiver cannot be represented, use the complete raster viewport. Isolate direct sun, apply RT visibility once, and leave ambient/emissive/other lights intact.

Use the existing [VQ/GDU RT plan](../04-ray-tracing-in-godot.md) and [DT-MAC ownership](../../../plans/apple-metalfx.md), not a new sample-specific harness. After proven pilot-visible need and whole-frame headroom, the two-day checkpoint is capability plus a CPU-oracle hit/miss and correct synchronization on a named GPU; at two weeks deliver the already planned visible bounded sun fixture or stop. Full flight requires complete coverage and moving comparisons. At real 1080p, **proposed** screening limits are 2.0 ms GPU p95 and 128 MiB incremental peak allocations for the entire effect, with stricter whole-frame headroom, default Off and unchanged physics. No timing or cross-vendor portability has been measured here.
