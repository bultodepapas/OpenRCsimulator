## Implementation findings

The guide specifies Windows 10/11 x64, D3D12, a DXGI flip-model swapchain and a monitor directly connected to the rendering GPU. Standalone latency reduction is listed for Intel Arc A-Series or later. A non-Intel GPU is eligible only in the XeSS Frame Generation cross-vendor case; the guide requires FG enabled and disables latency reduction if it is unsupported. It also requires other latency-reduction solutions be disabled, controls an active cap via XeLL, and calls for VSync `Present` sync interval 1 when low latency is active. These are version-specific requirements; neither an Intel vendor string nor a source header establishes runtime support.

The actual sample creates a context from an `ID3D12Device`, waits for GPU work before changing sleep mode, and increments a frame counter before `xellSleep`. It emits simulation, render-submit and present markers around its update/render/present paths and destroys the context after GPU work stops. Its Win32 sample has a separate message thread and render loop; the sample's event markers and frame counter therefore do not prove that a fixed-tick RC sample belongs to the subsequently displayed aircraft frame. The guide requires an increasing frame ID, one sleep before any marker for that ID when low latency is enabled, and appropriate per-frame start/end markers; follow the guide and verify the actual application ordering rather than copying sample threading blindly.

The guide recommends calling sleep and markers in pass-through/Off as well, with feature changes via `xellSetSleepMode`. It discourages a second limiter/wait and specifies ordering if an application limiter remains. In issue 40, an Intel developer describes creating a context to check support and says it may create D3D objects. That discussion is a useful lifecycle warning; use the return value and exact newer SDK's rules rather than assuming the 2025 answer is immutable. A context-creation success or a reported software timing is still not proof of a physical control benefit.

## OpenRC mapping, deliverable and stop

OpenRC's [trial build](../../../../tools/graphics/native/build.py#L180) explicitly disables D3D12, and the [standard project](../../../../app/project.godot#L60) selects other defaults. Its [flight reader](../../../../app/sim/flight_session.gd#L1332) samples axes at fixed ticks; the current [Reflex path](../../../../tools/graphics/native/reflex_lifecycle.patch#L98) already owns a native frame wait on its supported route. XeLL therefore needs a separately maintained D3D12 integration with device/context ownership, a correct per-render-frame token across input/update/submit/present threads, fallback on unsupported driver/device/display, safe mode changes and shutdown. It cannot be enabled by a GDScript setting or layered on another active pacer. Do not change 240 Hz physics or input ownership.

The finite next deliverable is an explicit **defer or feasible** note, not an SDK installation. If a D3D12 project is independently selected, verify exact SDK/package/driver, monitor connection, eligibility, context failures, ordered IDs, Off/On and resize/minimize/shutdown using existing diagnostics. Then compare one named 1080p exported build within itself against a simple cap/VSync baseline, under matched CPU- and GPU-limited loads. Preserve frame-time tails and energy/clock data where available.

Use F6's existing [optical patch](../../../../app/input/latency_patch.gd#L147) for actual RC transmitter-to-patch and first-visible-control measurements; do not equate XeLL markers or mouse reports with that endpoint. At least 30 physical transitions per condition screen the setup; target 100 across repeated sessions for p95 with intervals and session variation, adding observations or reporting inconclusive when resolution is insufficient. Retain the baseline if the backend, hardware, attribution or meaningful improvement is missing. No XeLL runtime or physical test was performed for this investigation.
