# R20 — Godot path-tracing forks: real implementation, conditional research only

Research snapshot: **2026-11-15**. OpenRC application `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`; sources and public discussion inspected, no forks built or run. The pinned official engine is `cafc17a192acf67903910a68aeb3c076c0907a4b`. The [existing fork intake](../../desktop-delivery-investigations/metalfx-20-investigations-2026-11-14.md#i13--is-the-experimental-godot-rt-fork-ready-to-adopt) retains additional details.

## Question and evidence

**Question:** Can a third-party Godot path-tracing fork replace OpenRC's engine and immediately solve sun visibility across desktop platforms? **Decision:** No. Both sources contain substantive work worth consulting, but diverge from the official pin and have material, platform, maintenance, packaging and qualification gaps. VQ-07h explicitly defers path tracing; no adoption is authorized by the existence of source code.

NVIDIA's `nvidia-pt-dlss` branch was inspected at [`49a825dc52c0f1892ff5ce5cdbbe7572c638d41a`](https://github.com/NVIDIA-RTX/godot/commit/49a825dc52c0f1892ff5ce5cdbbe7572c638d41a), dated 2026-11-02. This is not merely a README: [`render_raytracing.cpp`](https://github.com/NVIDIA-RTX/godot/blob/49a825dc52c0f1892ff5ce5cdbbe7572c638d41a/servers/rendering/renderer_rd/forward_clustered/render_raytracing.cpp#L93) manages BLAS, scene data, materials and per-resource ownership. Its [path-traced renderer](https://github.com/NVIDIA-RTX/godot/blob/49a825dc52c0f1892ff5ce5cdbbe7572c638d41a/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered_pt.cpp#L35) describes capture, BLAS build/refit, TLAS build, scratch and graph ordering; a non-RT path calls the ordinary renderer. That is a broad renderer effort, not a portable one-effect plugin. The [shadow shader](https://github.com/NVIDIA-RTX/godot/blob/49a825dc52c0f1892ff5ce5cdbbe7572c638d41a/servers/rendering/renderer_rd/shaders/raytracing/raytracing_lights_inc.glsl#L243) has a query alternative alongside a pipeline shadow path, with masks and transmittance. Their correctness for OpenRC materials and this engine pin remains untested.

An actual discussion reveals the tradeoffs. [PR #10](https://github.com/NVIDIA-RTX/godot/pull/10), merged 2026-06-17, adds optional query shadows within path tracing; its author notes differences with dynamic alpha. The reported Bistro speedup is scene/hardware-specific and is **not** an OpenRC result. In [issue #11](https://github.com/NVIDIA-RTX/godot/issues/11), a user reported opaque transmissive materials at an earlier fork revision; NVIDIA's Leroy Sikkes [discussed](https://github.com/NVIDIA-RTX/godot/issues/11#issuecomment-5219538293) how material and alpha support should evolve. This is useful engineering history, not proof the precise defect still exists at the newer inspected head. [Issue #12](https://github.com/NVIDIA-RTX/godot/issues/12) reports a crash on an AMD GPU without shader execution reorder; a reply suggests disabling SER. It illustrates why vendor-neutral extension names and a project switch are not substitute for capability checks and supported fallback.

A separate [Apple Metal fork](https://github.com/josephsmithberger/godot-metal-path-tracing/blob/fa56ac81ac593056e7bd460d46e542cec9097eed/README.md) explicitly warns that it is an experimental demo and must not ship. The README says its implementation is on `metal_rt`, but that advertised branch returned **404** on 2026-11-15; the README/default project page at `fa56ac81ac593056e7bd460d46e542cec9097eed` is not that implementation ref. The referenced historical build [`eeac9e05dbff0b273b6e4c483c4675530ead992b`](https://github.com/josephsmithberger/godot-metal-path-tracing/commit/eeac9e05dbff0b273b6e4c483c4675530ead992b), dated 2026-07-22, remains inspectable: its [Metal driver](https://github.com/josephsmithberger/godot-metal-path-tracing/blob/eeac9e05dbff0b273b6e4c483c4675530ead992b/drivers/metal/rendering_device_driver_metal.cpp#L2410) creates AS descriptors and checks support/limits, while its [renderer](https://github.com/josephsmithberger/godot-metal-path-tracing/blob/eeac9e05dbff0b273b6e4c483c4675530ead992b/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L1228) has an RT opaque route and alpha handling. These are concrete code, not proof of full scene parity or future support. The cited build's older 4.7-rc base and missing advertised branch complicate reproducible maintenance. The README's M5 benchmark is one author's separate scene, not an M1 or OpenRC result. Root MIT licensing does not settle bundled SDKs, notices or redistribution.

## OpenRC integration decision

Do not replace OpenRC's [official engine/template pins](../../../../app/get-godot.sh) with either fork. Relevant evaluation belongs to [VQ-07h](../../../plans/advanced-graphics.md), [GDU](../../../plans/godot-4.8-upgrade.md) and [DT-MAC-13d](../../../plans/apple-metalfx.md). The smallest next deliverable is an exact-commit, component-license and renderer-seam comparison only if an observed 1080p shadow defect and measured headroom justify it; otherwise defer. Reuse the existing RT feasibility work and fixtures where applicable, with the project measurement protocol, rather than making another harness. At two days prove device capability, known hit/miss and rollback; at two weeks deliver a visible bounded sun-only result or stop. A demo/fixture never qualifies normal flight.

Any later product route must handle current [aircraft and hinges](../../../../app/render/airplane.gd), [propeller blur](../../../../app/render/propeller_blur.gd), [alpha/wind trees](../../../../app/render/treeline.gdshader), off-camera casters, material changes and lifetime; otherwise restore the whole viewport's current raster shadow. Apply visibility exactly once to isolated direct sun, not final color. It must be default Off and leave physics unchanged. The initial 2.0 ms GPU p95 and 128 MiB incremental peak allocation ceilings at real 1080p are **proposals**, not measured entitlements; stricter whole-frame headroom wins. Matching editor/templates, package identity, SDK terms, device/driver coverage and native moving-flight acceptance remain prerequisites.
