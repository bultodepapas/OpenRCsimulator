# R01 — Godot runtime scaling and dynamic-resolution cost

Investigated 2026-11-15 against OpenRC application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`. This is source research, not a new hardware test.

**Question and decision.** Does the existing Godot viewport setter constitute a suitable low-cost dynamic-resolution system? **No.** It is an adjustable 3D render scale, but the pinned engine's changed-scale path reconfigures render buffers. Keep fixed reconstruction available and automatic scaling default-off. A source-level allocation path is evidence of work, not proof of a visible hitch. Evaluate a small engine-owned experiment only after the measurement gate, under existing VQ-07 ownership and the [integrated plan](../05-integrated-implementation-plan.md).

## Concrete finding

`Viewport::set_scaling_3d_scale` clamps and forwards the setting. At the server, identical clamped float values return early, but a changed float calls `_configure_3d_render_buffers` even if integer dimensions happen to round to the same values. For a valid nonzero viewport, configuration computes internal size, temporal jitter phase and mip bias; `RenderSceneBuffersRD::configure` clears named textures and custom data, handles the MetalFX Spatial context, and creates needed color/depth and MSAA targets. Therefore an application can trigger generation and lifetime work at every distinct scale. It must not infer cost or GPU completion merely from a setter return.

The maintainer's concern is historical, but the pinned source independently shows a relevant reconfiguration path today. Their suggested API-specific approaches were ideas, not a proved Godot solution; image-view changes alone do not satisfy every shader, postprocess, temporal history and synchronization dependency. The developer's sky flicker is a historical report, not a demonstrated current bug. Temporal reconstruction requires per-provider jitter, motion/depth conventions and discontinuity handling; a changing input size and a camera cut are different events, and whether history can be retained is provider-specific.

The community addon is a concrete alternative worth examining: after ignoring an initial number of frames it polls `Engine.get_frames_per_second()` once per second, multiplies viewport scale by the FPS-to-target ratio and caps the result at its configured maximum. It does not inspect GPU attribution or avoid the engine's changed-scale allocation path. CPU load, a frame cap, or VSync can therefore drive its decision without showing that fewer 3D pixels will help. This is a scope mismatch for OpenRC's gate, not a claim that the addon cannot help its author's use case; do not copy it without a controlled, GPU-sensitive comparison.

The forum thread starts with attempts to change window/stretch settings and later distinguishes 3D scaling from 2D presentation; its eventual editor-preview workaround is not export evidence. For OpenRC this reinforces a concrete UI requirement: show output and internal 3D size separately, keep the HUD readable, and verify the actual exported drawable. It does not establish dynamic adaptation or a measured benefit.

## OpenRC mapping and choice

[`reconstruction.gd`](../../../../app/render/reconstruction.gd) owns settings, nominal scale and history requests; [`camera_rig.gd`](../../../../app/render/camera/camera_rig.gd) requests camera-discontinuity resets. An independent script writing `scaling_3d_scale` would be overwritten on settings reapply and leave diagnostics inconsistent. [`frame_diagnostics.gd`](../../../../app/render/frame_diagnostics.gd) and [`render_probe.gd`](../../../../app/debug/render_probe.gd) share the same viewport timing flag without shared lifetime ownership; positive values currently have unverified freshness. Reuse these and the [debug bridge](../../../../app/debug/debug_bridge.gd), not a new monitoring stack. The audited application and provider distinctions are in [R01's parent audit](../02-dynamic-resolution-and-upscaling.md).

**Adopt:** bounded scale changes, actual-pixel and resource-generation evidence, stable output/HUD, and an explicit fallback for invalid timing or unsupported temporal transitions. Prove GPU/pixel sensitivity first at 1920×1080. Preserve the 240 Hz float64 simulation and user preferences. **Avoid:** every-frame setter writes, using FPS or delayed ambiguous zeros as a control signal, or claiming that a static scale is adaptive.

## Bounded next deliverable and stop

The plan's **M0**, capped at five engineering days total across the project, should repair only the existing timing ownership/freshness seam and run a narrow native fixed-scale/transition screen through the current harness. Its acceptance is a trustworthy fresh-or-unavailable result with recorded engine, renderer, dimensions, timing ownership, and observer cost; partial timing fails DRS closed. **M1** corrects one existing fixed provider/transition only when evidence justifies it. **M2** is conditional: demonstrate acceptable bounded transition/allocation cost, correct history, and moving-aircraft/HUD readability before a default-off controller trial. Persistent allocation is a conditional repair if the existing setter misses the gate, not an automatic prerequisite. If the timing or resource contract cannot be established, stop and retain fixed reconstruction; do not expand M0 into a measurement project.

## Limitations

No hardware run, performance measurement or changed runtime is claimed here. Compatibility and custom provider engines can differ from this exact RD path. Above-1080p is secondary; 720p cannot establish primary-target acceptance.
