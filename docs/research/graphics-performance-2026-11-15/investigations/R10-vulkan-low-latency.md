# R10 — Native Vulkan low latency: ownership before a prototype

2026-11-15 · External source investigation against application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`. **Decision:** `VK_NV_low_latency2` is a conditional native-engine alternative, not an extra switch to stack on the existing Streamline Reflex path. Prototype only after the common [VQ-07h](../../../plans/advanced-graphics.md)/[F6](../../../plans/controller-support.md) baseline shows a need and the exact device and renderer can own the required lifecycle; an unavailable RTX trial need not block a separately justified native-device study.

## Implementation findings

The extension requires Vulkan 1.2 or timeline semaphores, plus `VK_KHR_present_id` or `VK_KHR_present_id2`. An application must query and enable the relevant available features and extension on the selected physical/logical device, create a suitable swapchain with `VkSwapchainLatencyCreateInfoNV`, and handle surface/present-mode capabilities and recreation. It sets sleep mode for that swapchain, calls `vkLatencySleepNV` before input work, and waits on the requested timeline-semaphore value via `vkWaitSemaphores` to delay the CPU. The sleep command and the host wait are distinct operations. Report return values and avoid treating a passed extension-name check as evidence that pacing happened.

DXVK's presenter puts the latency-create structure on swapchain creation, keeps sleep mode and a timeline semaphore, and performs that host wait outside its surface lock. It wraps `vkQueuePresentKHR` with start/end latency markers. Its code also handles absent support and a dirty/recreated swapchain. This is an actual implementation reference; it does not establish that OpenRC's pinned engine exposes these hooks or that an NVIDIA Linux driver has them. Nor does this investigation establish a separate, official standalone `VK_NV_low_latency2` sample for direct reuse.

Frame attribution needs care. The spec says the application-rendered frame ID in `VkLatencySubmissionPresentIdNV` is **not** the `VkPresentIdKHR`/`VkPresentId2KHR` present ID. Implicit attribution suffices for many applications. If the actual multi-queue submission pattern needs explicit attribution, track IDs monotonically per queue and follow the specification's reset and inheritance rules; implementations advertising extension `specVersion` below 3 ignore this structure. Do not conflate marker IDs, KHR presentation IDs, a simulation tick and a physical input event. Out-of-band queues and multiple presents require their own specified attribution.

## OpenRC mapping and bounded decision

The [existing native fork](../../../../tools/graphics/native/reflex_lifecycle.patch#L98) already has one Streamline sleep owner and [frame-token handoff](../../../../tools/graphics/native/dlss_frame_lifecycle.patch#L69). The [official project](../../../../app/project.godot#L60) can use a different renderer and backend. A script with a native handle is not evidence that it can intercept device creation, queue submission, input, swapchain recreation and present on the correct threads. First write a short ownership/feasibility result for the exact engine build; preserve unsupported and initialization-failure fallback. Never run Streamline and a direct NV extension as independent pacers on the same frame.

Only if this boundary is demonstrated, implement one small isolated, off-by-default candidate on one named Vulkan device. Reuse current diagnostics and lifecycle checks to record feature/revision, active swapchain, mode, sleep/wait result, marker/frame attribution, resize, minimize/restore, failure and shutdown. A 1080p within-build Off/On comparison must include a simple cap/VSync baseline, actual presentation conditions, CPU/GPU/frame-time distributions and unchanged 240 Hz input/simulation behavior. Use [F6's optical patch](../../../../app/input/latency_patch.gd#L147) for real transmitter-to-patch and transmitter-to-visible-control endpoints; GPU/PCL timings do not include the whole physical path. Screen at 30 transitions per condition, target 100 across sessions for p95, and report uncertainty rather than claiming the count guarantees precision.

Stop before implementation if the swapchain or render/input boundary cannot be owned safely; retain the ordinary path if capability is absent, marker attribution is wrong, lifecycle fails or paired improvement does not exceed uncertainty. This dated source review supplies no hardware result or Linux-support promise.
