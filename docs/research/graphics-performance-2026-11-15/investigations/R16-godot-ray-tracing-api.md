# R16 — Godot's ray-tracing API is plumbing, not a finished shadow

Research snapshot: **2026-11-15**. OpenRC application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`; documentation branch began at `b0f1dca56cdb926c42f609c72b6ca88df48d8a77`. External code and discussion inspected on 2026-11-15. This is source analysis, not a new run or hardware qualification.

## Decision and evidence

**Question:** Can the pinned engine produce a portable, correct directional-sun RT shadow merely by enabling a setting? **Decision:** No. A conditional Vulkan experiment is technically grounded, but needs real scene inputs, material coverage, direct-light integration and device-specific proof. Keep the current raster route and make any eventual effect opt-in.

The exact editor and templates are [4.8 beta 2](../../../../app/get-godot.sh), official engine commit [`cafc17a192acf67903910a68aeb3c076c0907a4b`](https://github.com/godotengine/godot/commit/cafc17a192acf67903910a68aeb3c076c0907a4b). The [4.7 RenderingDevice reference](https://docs.godotengine.org/en/4.7/classes/class_renderingdevice.html) documents BLAS, TLAS, pipeline and shader-binding-table (SBT) primitives and separate query/pipeline feature flags; the experimental interface is unavailable in Compatibility and headless. The versioned documentation is context; conclusions about the pin below come from its source.

At the exact pin, [Vulkan device setup](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/vulkan/rendering_device_driver_vulkan.cpp#L594) requests and enables `VK_KHR_ray_query` when available. In [issue #121286](https://github.com/godotengine/godot/issues/121286), an actual 4.7 user reported the query flag false even where the Vulkan device advertised support. Godot member Calinou [reproduced](https://github.com/godotengine/godot/issues/121286#issuecomment-4972431377) this on Linux/NVIDIA, then reported both flags true with [PR #122051](https://github.com/godotengine/godot/pull/122051), merged 2026-08-04. That is a real version distinction, not evidence the checked device will work. The same PR fixed the reported ray-generation push-constant issue [#121285](https://github.com/godotengine/godot/issues/121285); the pinned [shader container](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_shader_container.cpp#L310) uses the RT stage **bit** constants. The issue's differing NVIDIA/RADV reports show why identical API calls need real-driver tests.

A separate unresolved feasibility question exists at this pin: [`tlas_build`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L582) requires a nonzero hit-SBT range when an instance references a BLAS, while its normal [`hit_sbt_create`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L692) route requires a ray-tracing pipeline. Vulkan inline query conceptually needs no pipeline or SBT, but this RD validation may obstruct a query-only device. This is a source finding, **not a reproduced failure**; inventing a nonzero value is not a demonstrated supported solution. Until independently resolved, require query plus pipeline and a normally created SBT, or declare query-only unsupported. The inspected [Vulkan build code](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/vulkan/rendering_device_driver_vulkan.cpp#L6406) uses `BUILD`; exposed flags alone do not prove a working refit/compaction route.

## OpenRC integration and bounded next decision

The project's [Compatibility default](../../../../app/project.godot), Forward+-gated [High profile](../../../../app/render/high_graphics_profile.gd), and [shadow settings](../../../../app/render/shadow_settings.gd) must remain usable. A `CompositorEffect` can request some render buffers, but it does not provide the complete scene acceleration structure or isolate directional sunlight. Simply multiplying final color would darken ambient, emissive and other lights and can apply the sun shadow twice. A viable engine seam must apply visibility **once to the existing direct-sun term**, in linear HDR. The [moving hinges](../../../../app/render/airplane.gd), [propeller blur](../../../../app/render/propeller_blur.gd) and [wind-deformed alpha-scissored trees](../../../../app/render/treeline.gdshader) make an opaque static subset insufficient for normal flight. Missing relevant casters or receiver/material support means full raster fallback for the viewport.

Under [VQ-04b/VQ-07](../../../plans/advanced-graphics.md), [GDU](../../../plans/godot-4.8-upgrade.md) and, separately, [DT-MAC-13d](../../../plans/apple-metalfx.md), first establish an attributed pilot-visible defect and measured 1080p whole-frame headroom. At the two-day capability checkpoint, record engine/driver/GPU, both features, shader compilation, BLAS/TLAS creation and known hit/miss with identity against a CPU oracle; specifically document the SBT constraint, failure handling and Off cost. Reuse the existing RT effort, not a new permanent harness. At two weeks deliver a visible bounded sun-only result in a bounded fixture using the existing tools or stop; a fixture is not normal-flight qualification. Continue to production only with complete scene coverage or raster fallback, matched moving evidence, unchanged physics and [existing acceptance protocol](../06-validation-and-benchmark-plan.md).

The **proposed**, unmeasured screening ceilings are 2.0 ms GPU p95 and 128 MiB incremental peak GPU allocations for the entire effect at actual 1080p; stricter measured whole-frame headroom wins. Failure, unsupported backend, material uncertainty or no visible improvement means defer. No editor, template, shader, product code or simulation was changed in this investigation.
