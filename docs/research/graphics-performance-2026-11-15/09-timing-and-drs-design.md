# Timing leases and dynamic-resolution handoff

**Status:** proposed design and source inspection, 2026-11-15; no runtime implementation, new benchmark, GPU measurement or engine upgrade. Application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`; audit branch `725cb17585475999d3c5ef01f0af41643b3d0c36`. This deepens [02](02-dynamic-resolution-and-upscaling.md), [M0–M2](05-integrated-implementation-plan.md) and [R15](investigations/R15-godot-timing-contract.md); it does not replace their gates. VQ-07 owns reconstruction, PT owns measurement, UI/DT owns display and recovery, CAM owns camera discontinuities, and GDU owns any engine patch ([registry](../../README.md#tracks-plans-and-step-ids)). The application remains 240 Hz float64 simulation; all proposed state and feedback below is presentation-only.

**Decision:** the first bounded patch is a shared, viewport-lifetime-aware timing lease used by the two existing in-app callers, with focused lifecycle tests. Add truthful compatible sample status in the same patch only if it stays coherent and reviewable. Stock `viewport_get_measured_render_time_gpu()` does not supply the associated completed render ID, generation or age. A positive value, changing poll count, advancing `Engine.get_frames_drawn()` or render-post-draw callback cannot fill those gaps. **Do not feed stock polls to DRS.** M0 can finish static-only if fresh associated feedback cannot be established inside its existing **five-engineering-day total cap**, including the named-host screen and overhead check. No new profiler/platform is required or authorized by this design.

## 2. Lease contract — first patch proposal

Use one shared helper loaded by both consumers; no singleton service, polling daemon or new executable. A helper with static shared state must be the **same loaded script resource** in both callers and remain alive for all leases. Serialize acquisition, reconciliation, release and `tree_exiting` handling on the main thread; debug network work is queued into the existing main-thread bridge. The helper owns only participating clients' measurement flag, not GPU results or settings.

### Data and invariants

- `ViewportKey = (weak node reference, Object instance ID, captured RID, lease-epoch)`. Each new live viewport entry receives a monotonically unique epoch even if a RID or instance ID is reused. Never retain the node strongly. Verify the live object and its current RID match immediately before a server write; a freed/queued-for-deletion viewport is retired **without** sending to its old RID.
- `LeaseToken = (epoch, unique token nonce)`, opaque to callers. Each active interest owns one token; releasing the same, unknown, retired or old-epoch token is harmless. A refcount alone without token identity allows duplicate release to disable somebody else's lease.
- For a live participating viewport the first lease requests `viewport_set_measure_render_time(rid, true)` and the last lease requests `false`. No further setter for intermediate acquisitions/releases. A returned token means **owner requested enable**, not that native timestamps are supported, produced, fresh or complete; the public setter is void. Per-consumer capability/availability policy remains distinct from ownership.
- `FrameDiagnostics.start()` retains one token; `stop()` releases it on all paths and remains one-shot. It may keep memory monitors when timing is unavailable. Preserve the existing conservative headless/macOS Compatibility policy rather than silently broadening it.
- The probe owns one root token and a token per currently discovered SubViewport, not just a RID set. Repeated `set_measure(true)` reconciles without reacquiring unchanged entries; discovery during `sample()` acquires additions and releases removed/reparented live nodes. `set_measure(false)` releases the **stored** token set, independent of the current tree. Bridge shutdown always releases the probe's regular interest; an ablation gets a separate interest/token or an equivalent explicit nested lease and releases only what it acquired. A user `measure=false` request during ablation must not silently make the active ablation look measured; it can drop the user's interest while the ablation retains its own.
- Admit only viewports already inside the tree; an unparented viewport is unavailable until a caller explicitly retries after attachment. Connect its `tree_exiting` signal with an epoch-only callable that does not strongly capture the node. On exit, retire its tokens and tell owners they are inactive; a still-live detached node is disabled only after checking the captured object and RID. Re-entry/reparent requires explicit reconciliation and a new epoch. Also sweep dead weak entries on normal acquire/release/reconcile, and test actual `free()` and `queue_free()` without relying on another poll. `tree_exiting` alone does not notify an object that was never in a tree, which is why that case is rejected. In every case, old-token release never writes to a replacement RID.

The following pseudocode describes required behavior, not existing GDScript or a claim that a particular deletion hook already exists:

```text
acquire(view, client_interest):
    require main_thread and live(view) and view.inside_tree and valid(view.rid)
    retire_dead_entries_without_server_calls()
    key = matching_live_entry_by_weak_identity_and_rid(view)
    if key absent:
        key = fresh_epoch(view.weak, view.instance_id, view.rid)
        connect_tree_exiting_with_epoch_only(key)
    token = fresh_nonce(key.epoch)
    if key.active_tokens is empty:
        recheck_live_identity_and_rid(key)
        server.set_measure(key.rid, true)
    key.active_tokens.add(token)
    return token

release(token):
    key = lookup_exact_epoch_and_nonce(token)
    if key absent: return
    remove token exactly once
    if key.active_tokens is empty:
        if same_live_object_and_rid(key) and not deleting(key):
            server.set_measure(key.rid, false)
        erase_entry_and_disconnect_lifetime_observation(key)

on_lifetime_end(key):
    if same_live_object_and_rid(key) and not deleting(key):
        server.set_measure(key.rid, false)  # a live detach
    invalidate_all_tokens(key)  # no write if object/RID is no longer live
    erase_entry_and_disconnect_lifetime_observation(key)
```

Treat failure to connect the lifecycle observation as unavailable, not an excuse to hold a strong node reference. Explicitly handle an error/interruption between registration and the first enable so it cannot leave a phantom owner. Clients still release explicitly on teardown; any optional `RefCounted` token predelete cleanup must avoid strong cycles and be main-thread/shutdown safe. Tests inject a fake backend which logs setter calls; a fake does not prove driver support or GPU completion.

## 3. Timing identity: what the pinned engine actually exposes

The [pinned API documentation](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/doc/classes/RenderingDevice.xml#L553-L564) describes `RenderingDevice.get_captured_timestamps_frame()` as the index of the last rendered frame with timestamp results. That is an **available RD-level API**, unlike a completed ID returned by the viewport timing getter. It is not enough to pair independently polled GDScript values with a given viewport result.

The exact beta2 source raises a further question that needs a narrow engine proof, not an assumed answer:

1. [`RendererViewport::_draw_viewport`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L341-L345) records `vp_begin_<RID>` and at [773–776](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L773-L776) `vp_end_<RID>`. [`draw_viewports`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L795-L797) clears its name-to-RID map every draw; skipped or disabled viewports do not refill it.
2. [`RenderingServerDefault::_draw`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_server_default.cpp#L76-L165) draws viewports, calls `end_frame`, then iterates returned timestamp names and calls `handle_timestamp`. That [handler](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L1710-L1729) independently updates cached begin/end fields; the public getter returns their difference without an ID. Its current map describes the current draw, whereas the returned slot can describe earlier work; no application generation or extent is paired there.
3. [`RendererCompositorRD::end_frame`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_rd/renderer_compositor_rd.cpp#L136-L138) calls `RD::swap_buffers`. [`swap_buffers`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L8115-L8128) advances the ring and `_begin_frame` waits for/retrieves the prior slot's timestamp results, then sets `frames[frame].index = Engine::get_frames_drawn()` at [8289–8340](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L8289-L8340). The getter at [9086–9110](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L9086-L9110) returns that slot's `index`; timestamp getters require the render thread. The apparent overwrite before retrieval warrants a targeted test of the documented index against the timestamp slot and engine frame increment order. Source ordering is not a live reproduction and does not by itself prove an upstream bug.

**Smallest potential engine seam, if it fits the existing M0 budget:** on the render thread retain a separate immutable `result_frame_id` before reusing a slot, and retain the viewport lifetime identity, actual render configuration generation and active input/output extent captured with that recording. Pair exactly one begin and end for the same viewport and slot; publish a single atomic immutable result only after the matching returned timestamps are available. Reject missing/duplicate/out-of-order endpoints, unknown/recycled RID, invalid timestamp support, nonpositive/overflowed time and an unknown generation. Publish a conservative same-clock age bound using the recording's associated monotonic CPU timestamp only if its clock relationship and ordering are verified; `now − poll_time` or `now − first_seen_time` does not bound sample age. This is a **proposed native seam**, not a new API already present in any package. Do not add a synchronous fence, assume one backend implements it, or promise it fits M0; if it does not, leave that row static-only.

The record needed by a future controller is conceptually:

```text
GpuObservation {
    status: unavailable | invalid | freshness_unverified | fresh_associated
    scope: root_viewport | qualified_whole_gpu | other_explicit_scope
    viewport_epoch, native_viewport_identity, configuration_generation
    completed_render_id?       # backend-associated, not the process/poll number
    recorded_monotonic_usec?   # associated same-domain age bound, not poll time
    gpu_duration_ms?           # finite, > 0, same valid begin/end pair
    active_input_extent?, output_extent?, provider_identity?
    poll_sequence, poll_monotonic_usec  # observation metadata only
}
```

The controller rejects missing completion identity, missing/expired age, unexpected scope, unknown actual extents, old generation, invalid sample or nonadvancing completion ID. A duplicate ID never contributes to a second window; distinct completion IDs with equal numeric durations both count. The first observation after a generation change cannot be assumed to describe that generation. Root viewport timing is neither all GPU work nor presentation: only admit it for control after a paired fixed-scale experiment bounds independent viewports and other non-scalable work. Do not sum possibly overlapping or stale viewport intervals. A reset submitted/encoded serial, render-server draw progress, a changing GPU value or a successful SDK enqueue is not GPU-completion identity.

### Compatible reporting

Keep existing raw `render_gpu_ms` and zero/invalid counters for legacy readers; add explicit versioned status and scope. For the existing fixed numeric sample schema, one viable encoding is finite integer status/presence flags plus fixed numeric fields, with a documented codebook in `frame_diagnostics` metadata. Never equate the numeric zero sentinel with a valid zero-duration sample. A genuinely associated 64-bit backend ID must stay exact: use two 32-bit numeric halves and a presence flag, or a separately versioned lossless record; do not round it through `PackedFloat64Array` above `2^53`. Unknown values stay absent by presence flag, not fabricated from `poll_sequence`. Keep names and metric count fixed for the run. `main.gd` **and** `godtest_driver.gd` must continue recording successfully, including streamed v3 chunks.

Update both `frame_diagnose.py` and `native_summary.py` only in their existing reporting path: v2/v3 legacy input remains readable, raw polling data remains visible with `freshness_unverified`, and observed render progress remains a separate gate rather than promoting freshness. A present-but-malformed or unknown new status must fail the new feedback claim closed; do not retroactively claim old data is associated. Preserve incomplete/invalid diagnostics and existing stream size/integrity checks. If a safe representation or engine seam needs a larger schema/platform project, retain static-only rather than expanding M0.

## 4. Provider legality and one scalar actuator

The only current application actuator is `Viewport.scaling_3d_scale`, not independently writable width/height. For the pinned official server, positive dimensions are computed from target size and float scale then converted to integers; bilinear/nearest additionally clamp to 1–16384. The OFF, compatibility and internal-fallback paths differ ([server configuration](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L136-L295)). The exact fork, effective provider and float32 conversion must be verified. [`nominal_input_size`](../../../app/render/reconstruction.gd#L663) is explicitly an estimate, not proof of texture allocation or SDK dispatch. At apply/ack, compare observed active output and input dimensions to the proposed pair; mismatch invalidates the generation.

For one qualified output `W × H`, derive a bounded ladder of *scalar values* with engine-equivalent rounding. Verify each resulting `(w,h)` against the exact provider/version/device's queried integer minima, maxima, alignment and aspect/active-rectangle constraints; the tested readability floor; and the user's fixed-choice ceiling **on both axes**. The intended 1080p floor is at least `ceil(0.85*W) × ceil(0.85*H)` as a proposed strict per-axis policy, not a measured quality guarantee. Keep actual engine-clamped float values and eliminate duplicate resulting pairs *before* any setter; select a single stable representative so toggling two floats that produce the same dimensions cannot force redundant buffer reconfiguration. Reject unknown limits, empty intersections or a single rung as unavailable/no adaptive range. Fixed reconstruction remains usable.

Counterexamples that a float-only clamp misses:

- At 1919 × 1079, naive `0.85` nominally truncates to 1631 × 917, below the strict integer floor 1632 × 918. Validate the representable value and both rounded dimensions, especially at endpoints; don't quietly label it 85% compliant.
- At 101 × 51, desired 86 × 44 can satisfy separate per-axis provider bounds yet cannot be produced by a single scalar: `s ∈ [86/101, 87/101)` and `s ∈ [44/51, 45/51)` have no intersection. Nominal real-number intervals are helpful for screening, but final evaluation must match the exact engine floating-point multiply/truncate path and then confirm actual dimensions.
- With a 0.85 floor, a requested fixed `*_85` ceiling normally leaves just one rung; Quality at 2/3, Balanced at 1/1.7 and Performance at 0.5 are below the floor. Do not silently raise the user's ceiling or lower the floor just to admit DRS. Auto's current fixed selection is not an adaptive request.

The current pinned server recalculates jitter phase count and mip bias and can recreate render buffers on a distinct float, even for unchanged rounded pixels. A persistent maximum allocation with active subrect is a **separate conditional engine change**, not an app-only switch. It requires correct viewport/scissor, old-region exclusion/clears, all passes and resource lifetime, plus per-provider transition/history proof. Do not reset history on every small scale step merely by habit; a camera cut, context replacement and legal same-context dynamic step are different events.

## 5. Serialized control, settings and history — proposed M2 contract

No controller runs before M0 feedback and M1 fixed-provider/transition gates pass. Off is the new feature's initial value and preserves existing app defaults, including `reconstruction=auto`, `max_fps=0`, VSync enabled and saved MSAA. The separate requested/effective fields never overwrite user selection, and `Auto` continues to select a fixed provider by capability/output rather than meaning dynamic resolution. A distinct numeric real-render target must be explicitly selected; unlimited/zero cap and unknown refresh are not valid target budgets, and generated frames are not real renders. A static choice, rejected adaptive request or runtime fallback must remain visible with its reason.

**Single writer and transactions.** Only the reconstruction policy owner may set mode/scale. Add an owner state containing `requested_config`, `effective_policy`, viewport lifetime epoch, output/provider/config generation, `committed_static_scale`, active ladder index and one `pending_transition_id`. AppRoot's guard runs before any MetalFX transition. Every settings preview, resize/Retina change, camera discontinuity, provider failure, transition completion and debug ablation enters this serialized owner; an independently running `@half_res` ablation must suspend the controller and use its existing conditional restoration/ownership rules. Reapply of unchanged presentation config must not reset an active scale to the fixed choice, unless an explicit restore/fallback/preview requires it. Never persist adaptive scale changes each frame.

A minimal proposed sequencing contract:

```text
on_event(event):
    if event is settings_open_or_trial_begin:
        suspend decisions; clear timing windows; cancel/invalidate any pending proposal
        finish/restore a safe fixed baseline through guarded owner before preview
    if event changes viewport/output/provider or signals a camera cut:
        suspend; bump application config epoch; clear timing windows
        invalidate older observations and pending proposal IDs
        resolve current requested/preview config through existing guard and provider
        if temporal discontinuity: request the provider's matching reset after final pose
        wait for the required matching provider/reset/configuration acknowledgement
        if missing/rejected/unavailable: follow existing provider fallback; retain request
    if event is qualified fresh observation:
        reject unless viewport, provider, actual extent, configuration generation, ID,
            age, target, drawing state and provider/history gates all match
        ignore duplicate ID; add only a new valid result to the current epoch's window
        if policy threshold + dwell + sensitivity gates pass and no proposal pending:
            propose exactly one adjacent legal scalar/extent and fresh transition_id
            guarded_owner applies once; do not treat proposed as effective
    if event is matching successful transition acknowledgement:
        require same viewport epoch, transition_id, provider, generation and observed extent
        commit effective rung; clear windows; warm up before the next decision
    if event is stale/invalid feedback, rejected/bad/timeout acknowledgement, or Off:
        stop adaptation; discard windows and pending ID
        restore the requested fixed policy through guarded owner once when drawable;
        if not drawable, defer restoration until safe, with effective state unconfirmed
        never save the transient rung
```

A pause/minimize/focus loss/loading/capture prevents new decisions and expires the window; no wall-clock polling count substitutes for a new result. On resume, restore/confirm the fixed safe policy and establish a fresh associated sample window before adapting again. Proposal cancellation is logical: an already enqueued render command cannot simply be revoked. The owner must safely sequence/retire in-flight work before a subsequent apply, and treat any late acknowledgement as stale; if that cannot be done without blocking or violating resource lifetime, the transition is unavailable. A temporary *known pending* transition/reset waits for its bounded correct receipt rather than issuing repeated restores; rejection, mismatched epoch/serial, backend fault or expiry exits adaptive operation and uses the provider's defined safe fallback. `after_pose_before_draw` is valid for MetalFX's special initial-history case only under its existing proven empty-generation conditions; do not call it from a generic scale update. Existing `initial_history`/`encoded` receipts are not themselves proof of GPU completion. If a provider requires a stronger completion gate, enforce it or retain static-only.

For a prospective measured experiment, [02](02-dynamic-resolution-and-upscaling.md#proposed-controller-contract--pending-proof) proposes a 120-distinct-sample window spanning at least two seconds, p90 > 90% of the real-frame budget for two eligible windows before lowering one rung, and p90 < 75% for ten seconds before raising; decreases at most every five seconds, increases at most every ten. These are hypotheses, not calibrated shipping constants. Compare distinct, nonoverlapping evaluation windows; clear them on every relevant epoch change. Require a prior pixel-sensitive fixed-scale ablation and contemporaneous CPU/cap evidence; at the floor or when CPU/cap-bound, hold. Verify transition spikes and pilot readability rather than fixing a failed transition gate with longer dwell. The [executable policy specimen](../../../research/performance/graphics_handoff/README.md) is only a partial deterministic contract illustration: it implements integer legality, exact threshold-count decisions and transaction retirement, while provider/output/scope admission and actual native lifetime remain explicit adapter preconditions. Its compressed test thresholds are not shipping values; it is not app code, a benchmark or a substitute for these gates. A pending-apply timeout also needs an owner-scheduled monotonic deadline independent of new draws/samples; the pure model cannot wake itself when rendering stops.

**Settings Keep/Revert integration.** Freeze dynamic adjustments while the Settings route is open, including the entire 15-second preview/draw wait; provide an explicit owner event before `presentation_changed` is emitted, not an inference from scale or saved config. This protects the existing `_trial_viewport_scale` identity check. A draft preview may change requested DRS/provider settings but applies a stable fixed scale with a clear paused reason. Keep saves the validated draft through the existing `DisplayPreferences.save` and makes it committed only after save succeeds; a save error leaves the draft/preview and rollback possible. Revert or Close reapply `_saved` and cancel the trial, invalidate delayed completions and return to the saved configuration. Timeout restores **only** `DISPLAY_TRIAL_KEYS` from `_trial_baseline`, preserving unrelated draft edits; any new DRS/target keys must be included deliberately. After the settings route closes, re-resolve the latest actual output, revalidate legality/provider/history, and warm up from fresh samples. A resize during preview uses active draft metadata, as today. If provider failure occurs during preview or rollback, the existing recovery marker/fallback wins and saved intent stays intact; an old asynchronous acknowledgement cannot resurrect it. Future schema extensions must default absent DRS to Off and preserve the existing `RECONSTRUCTION_AUTO_KEY` migration and protected newer-file behavior.
