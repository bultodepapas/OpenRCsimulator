**Proposed, source-only work, 2026-11-15.** OpenRC application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc`; documentation branch inspected at `92a16af2ddb5b26951ce4067484a79fb26a7014a`; official Godot `4.8.beta2.official.cafc17a19`, commit `cafc17a192acf67903910a68aeb3c076c0907a4b`. Later `main` is separate. This is an implementation order, not an implemented fixture, a GPU result, or a support/performance claim. Read [04](../04-ray-tracing-in-godot.md), [10](../10-reflex-and-ray-integration-design.md#2-direct-sun-ray-tracing-real-seams-and-limits) and [14](../14-ray-tracing-quality-and-delivery-plan.md) for ownership and acceptance.

M0 remains **five engineering days total**, including existing measurement repair and baseline. Only after a reproducible pilot-visible shadow defect and measured 1080p headroom, the first **two engineering days of M4** decide whether this fixture, the selected-sun seam and resource lifetime are feasible. By two weeks show a useful, correctly lit **opaque fixture** with bounded cost and explicit missing coverage, or stop. This is not permission to ship partial flight coverage. The path stays default-off and leaves 240 Hz float64 simulation, inputs and `sim_clock` unchanged.

**Prepared prerequisite implementation:** the later [patch package](../../../../research/performance/graphics_handoff/vulkan/README.md) now supplies actual address/error and TLAS reservation diffs, compiled function controls and successful compilation of both changed complete translation units. It has not been linked into an editor/template or run on Vulkan hardware. Use its exact identities and remaining native gates; the native fixture and selected-sun image below remain proposed work.

## Card 0 — Correct a pinned Vulkan address mismatch first

**Affected proposed engine paths:** `drivers/vulkan/rendering_device_driver_vulkan.{h,cpp}` in an isolated source tree based on the exact pin; matching editor/templates only for an experiment. No application scene API is added by this card.

The pinned [Vulkan driver](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/vulkan/rendering_device_driver_vulkan.cpp#L6470) writes `buffer_get_device_address(blas_info->buffer)` to `VkAccelerationStructureInstanceKHR::accelerationStructureReference`. The same file creates a **bottom-level** `VkAccelerationStructureKHR` at its `vk_acceleration_structure` field. Khronos requires the instance reference to be the value obtained from [`vkGetAccelerationStructureDeviceAddressKHR`](https://docs.vulkan.org/refpages/latest/refpages/source/VkAccelerationStructureInstanceKHR.html); the [address reference](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetAccelerationStructureDeviceAddressKHR.html) explicitly permits an AS address to differ from its backing-buffer address. See build VUID `vkCmdBuildAccelerationStructuresKHR-pInfos-12281` in the [specification](https://docs.vulkan.org/spec/latest/chapters/accelstructures.html). This is a source/spec mismatch and portability blocker, not a reproduced failure; matching numeric addresses on one device would not establish the general contract.

The exact `.cpp` loads create/destroy/build-size/build commands at lines 1574–1580 but has no `GetAccelerationStructureDeviceAddressKHR` reference. The exact pinned [header](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/vulkan/rendering_device_driver_vulkan.h#L131), Git blob `e7c129c744b0b8c0f085d11decb36a230061b9c7`, likewise declares those four AS function pointers without the address entry point; its `AccelerationStructureInfo` owns the native handle and buffer. Proposed minimal correction: add/load that entry point alongside the AS extension commands, check it before use, and after successful BLAS creation query a `VkAccelerationStructureDeviceAddressInfoKHR` containing the created `vk_acceleration_structure` on `vk_device`. Validate and cache the nonzero AS address **before returning the BLAS ID**; the void instance writer then copies that cached address. An error raised only inside that writer cannot propagate back to creation. Never derive the AS address from the buffer or expose a raw invented value to GDScript. The handle and backing buffer must remain alive through every dependent TLAS use; recreating the native AS requires a fresh address.

Failure handling needs attention in the same isolated change. At the pin, `_acceleration_structure_create` returns `void`: it dereferences the newly allocated buffer without a local check, and a failed `CreateAccelerationStructureKHR` returns from the helper while `blas_create`/`tlas_create` can still return their allocated wrapper. Propagate missing entry point, recoverable storage allocation, creation and address failures back through both callers, destroy only successfully owned native objects, and return an invalid AS rather than an apparently valid RID or a null reference. The [prepared patch](../../../../research/performance/graphics_handoff/vulkan/0001-as-address-and-creation.patch) uses a local native handle until creation succeeds, reports helper failure and checks scratch-size narrowing; Godot host-allocator OOM recovery remains outside its scope. Its compiled controls do not replace validation layers and the triangle witness below. An actual query-only device is a separate investigation, not a workaround for this defect.

## Card 1 — Admit one isolated local device and make a real SBT

**Proposed fixture home:** a new focused native Vulkan test under `tools/graphics/`, with its eventual invocation documented in `tools/graphics/README.md`. The names and arguments do not yet exist. Use a local `RenderingDevice` only for this isolated witness; it cannot share the main viewport's resources. Verify an actual Forward+/Vulkan non-headless device, `SUPPORTS_BUFFER_DEVICE_ADDRESS`, `SUPPORTS_RAY_QUERY` **and** `SUPPORTS_RAYTRACING_PIPELINE`; record device/driver, engine/patch hashes, shader compile errors and validation-layer version. Capability absent, compilation failure or any invalid RID means unavailable, not a hit. Check format support for `R32G32B32_SFLOAT` as an acceleration-structure vertex format on the actual backend. The pinned RD `blas_create` checks the enum range, not this feature. A texture/sampler-format query is insufficient: obtain `VkFormatProperties2.formatProperties.bufferFeatures & VK_FORMAT_FEATURE_ACCELERATION_STRUCTURE_VERTEX_BUFFER_BIT_KHR` for the actual physical device through a verified native/engine seam. If no suitable seam exists, record that feasibility gap; this work order does not invent a GDScript format-query method.

The pinned RD front end admits query **or** pipeline for `raytracing_pipeline_create`, but a query-only device need not expose the Vulkan pipeline entry point. Do not call it on query-only hardware. More subtly, `tlas_build` rejects zero `hit_sbt_range` when an instance has a BLAS. Create an actual ray-tracing pipeline even though this fixture performs traversal in compute:

1. Compile stage-appropriate minimal GLSL raygen, miss and closest-hit shaders with `GL_EXT_ray_tracing`, empty bodies and mutually compatible descriptor/push-constant layouts. `RDShaderSource` has `source_raygen`, `source_miss` and `source_closest_hit`; `shader_compile_spirv_from_source` returns per-stage errors. Create real shader RIDs, wrap each in `RDPipelineShader`, put the closest-hit wrapper in an `RDHitGroup`, and call `raytracing_pipeline_create([raygen], [miss], [hit_group], 1)`. Check every compile, RID and `raytracing_pipeline_is_valid`. Compilation and stage compatibility on this pin remain **to be proven**, not assumed from this recipe.
2. Call `hit_sbt_create(pipeline, 1)`, `hit_sbt_range_alloc(hit_sbt, 1)` and `hit_sbt_range_update(hit_sbt, range, 0, PackedInt32Array([0]))`; check the RID, nonzero opaque returned range and `OK`. Assign that exact range to the instance. Do not fabricate or decode its scalar. RD owns raygen/miss SBT storage and aligns group strides using the device's handle and base alignments; its hit range is updated in RD and the backing handle data is uploaded when a ray-tracing dispatch uses it. The compute query does not consume an SBT or execute these three shaders. No trace call is needed merely to manufacture a range.

The [4.7 RD reference](https://docs.godotengine.org/en/4.7/classes/class_renderingdevice.html) describes these experimental calls but its ray-tracing example is explicitly incomplete. Exact [beta2 RD source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L5211) controls the implementation. Keep the actual allocated range and its owning SBT/pipeline live until the TLAS no longer uses them. For query-only hardware, do not pass a made-up range: report unsupported pending a separately reviewed engine change and real device test.

## Card 2 — One triangle, one instance, explicit packing

Construct the oracle's non-indexed opaque triangle in object coordinates `(0,0,0)`, `(2,0,0)`, `(0,0,2)`, metres, render Y-up. Encode **nine float32 values, 36 bytes**, in vertex order. Create an empty `vertex_buffer_create(36, PackedByteArray(), BUFFER_CREATION_DEVICE_ADDRESS_BIT | BUFFER_CREATION_ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY_BIT)`, then check the result of `buffer_update(vertex_buffer, 0, 36, bytes)` outside open command lists before the build. This must be a **vertex buffer RID**: pinned `blas_create` looks up `vertex_buffer_owner`, so a storage-buffer RID, despite having build-input usage, is not interchangeable. No index buffer is needed. `RDAccelerationStructureGeometry` has `vertex_offset=0`, `vertex_stride=12`, `vertex_count=3`, `vertex_format=DATA_FORMAT_R32G32B32_SFLOAT`, and `flags=ACCELERATION_STRUCTURE_GEOMETRY_OPAQUE_BIT`; create `blas_create([geometry], 0)` and `tlas_create(1, 0)`.

The explicit checked upload addresses another source-only caveat: pinned RD vertex-buffer creation at lines 3947–3949 and storage-buffer creation at 1556–1557 call `_buffer_initialize` without propagating its returned error. A valid buffer RID alone is not evidence that initial content was uploaded. Use the same empty-create/checked-`buffer_update` sequence for the witness sentinel, retain engine error checks, and require the actual output marker. This is a diagnostic recipe, not a claim that an upload failure was reproduced or that `OK` proves GPU completion.

The adapter must select each JSON scene's named mesh. The initial triangle above is `right_triangle`; `tilted_local_y_scale` uses a distinct `tilted_triangle`, `(0,0,0)/(2,1,0)/(0,0,2)`. Give that mesh its own checked 36-byte vertex buffer and BLAS, or replace/rebuild only after verified completion. The flat BLAS would return t=6 for that setup and cannot test the required t=6.75 result. Preserve the one-TLAS-build-before-completion restriction while iterating this initial corpus.

The offset and stride satisfy four-byte component alignment; the Vulkan format must have `VK_FORMAT_FEATURE_ACCELERATION_STRUCTURE_VERTEX_BUFFER_BIT_KHR`. The pin maps `vertex_count-1` to `maxVertex`, uses `VK_INDEX_TYPE_NONE_KHR` and one primitive. RD creates AS storage/scratch internally: its Vulkan driver requests the actual build size, reserves `buildScratchSize + minAccelerationStructureScratchOffsetAlignment` and aligns the scratch device address. The TLAS instance input is RD-owned, not user-packed: it is a tightly packed native instance array, whose device address must meet Vulkan's 16-byte alignment for `arrayOfPointers=false`. The conventional `VkAccelerationStructureInstanceKHR` ABI is 64 bytes: 48-byte transform, two packed 32-bit words and one 64-bit reference; the pin obtains the actual stride from `sizeof(VkAccelerationStructureInstanceKHR)`. Validate the compiled ABI, actual addresses, queried limits and synchronization with the validation layer; never hard-code a vendor's SBT or scratch alignment. See [Vulkan triangle data](https://docs.vulkan.org/refpages/latest/refpages/source/VkAccelerationStructureGeometryTrianglesDataKHR.html), [instance layout](https://docs.vulkan.org/refpages/latest/refpages/source/VkAccelerationStructureInstanceKHR.html), and pinned [BLAS and instance writer](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/vulkan/rendering_device_driver_vulkan.cpp#L6359).

Call `blas_build(blas)` and check `OK` **outside** any open command list. For `RDAccelerationStructureInstance`, set an identity basis with translation `(0,2,0)`, `id=7`, `mask=0xff`, the allocated hit range, `blas`, and `ACCELERATION_STRUCTURE_INSTANCE_TRIANGLE_FACING_CULL_DISABLE_BIT`; then `tlas_build(tlas, [instance])`, also outside lists. This is the JSON's `identity_raised` scene. `id` maps to Vulkan's **24-bit custom instance index**, not the TLAS array index or primitive index; mask is eight bits. The pin writes the mathematical 3×4 transform rows as basis rows plus translation column. The CPU fixture's `transform_rows` uses those same mathematical rows; use the actual Godot `Transform3D` constructor/basis convention when adapting, not a blind byte copy. Next use the affine two-instance cases with `tlas_create(2, 0)` and valid allocated/initialized ranges for both instances; vary ID/mask to expose transposition, identity and culling mistakes. RD's graph tracks BLAS→TLAS→uniform dependencies; **verify** actual build-to-build and build-to-compute ordering and barriers on the patched backend. A returned `OK` only says the operation was accepted, not that GPU execution completed.

There is also a source-only same-frame aliasing concern in pinned [`tlas_build`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/rendering_device.cpp#L539): a newly allocated mapped instance buffer receives its first build at offset zero but initializes `used_size` to zero; another build of that same TLAS in the same frame can select that offset before GPU execution. This has not been reproduced. For the first fixture submit only one TLAS build before completion. Before depending on multiple builds in one frame, fix or disprove the suspected overlap with distinct instance data and inspect the actual offsets and output, including partial failure and retirement.

## Card 3 — Closest-hit diagnostic and independent oracle

Create a compute shader with `#version 460`, `#extension GL_EXT_ray_query : require` and one invocation. Bind set 0 binding 0 as `uniform accelerationStructureEXT` (`RDUniform` type `UNIFORM_TYPE_ACCELERATION_STRUCTURE` with the TLAS RID); binding 1 is a storage-buffer witness (`UNIFORM_TYPE_STORAGE_BUFFER`). Give the shader a 48-byte `std430` push block: `vec4 origin_tmin`, `vec4 direction_tmax`, `uvec4 controls`, where `controls.x` is the ray cull mask and unused components are zero. Pack float32 and uint32 explicitly; `origin_tmin.w` is `t_min`, `direction_tmax.w` is `t_max`. Allocate 32 witness bytes: `uvec4 result` at offset 0, `uint marker` at 16 and reserved bytes at 20–31. Initialize to a known sentinel before each dispatch.

The essential shader operation, **not a complete executable fixture**, is:

```glsl
rayQueryEXT q;
rayQueryInitializeEXT(q, scene, gl_RayFlagsOpaqueEXT, pc.controls.x,
                      pc.origin_tmin.xyz, pc.origin_tmin.w,
                      pc.direction_tmax.xyz, pc.direction_tmax.w);
while (rayQueryProceedEXT(q)) {}
bool hit = rayQueryGetIntersectionTypeEXT(q, true) ==
           gl_RayQueryCommittedIntersectionTriangleEXT;
result = hit ? uvec4(1u, uint(rayQueryGetIntersectionPrimitiveIndexEXT(q, true)),
    uint(rayQueryGetIntersectionInstanceCustomIndexEXT(q, true)),
    floatBitsToUint(rayQueryGetIntersectionTEXT(q, true))) : uvec4(0u);
marker = 0x52435431u;
```

Use no `TerminateOnFirstHit` for a **closest** hit/distance/identity oracle; first traversal hit need not be closest. For an eventual binary opaque sun visibility test, a terminate-first traversal may compare only the Boolean occlusion. The shader's `t` is the parameter in `origin + t * direction`, not necessarily metres; report `distance_m = t * length(direction)`. The CPU contract uses world-space `origin`, `direction`, `t_min`, `t_max`, `cull_mask`, triangle vertices, `transform_rows` and `instance_custom_index`; the adapter translates the packed result to `hit`, `t`, `distance_m`, `instance_custom_index` and `primitive_index`, setting all hit-dependent values to `null` on a miss. Decode the four result words as unsigned integers and reinterpret the last word's bits as float32. Never read intersection fields before confirming a committed hit.

In the published `identity_hit` case, origin `(0.5,0,0.5)`, direction `(0,1,0)`, interval `[0.125,12]`, mask `0xff` must yield hit, `t=2`, distance 2 m, custom ID 7 and primitive 0. `side_miss` and `away_miss` must miss. The `affine_nearest` pair selects custom index 66051 at `t=6`; `mask_far` selects 73 at `t=10`; `nonunit_parameter` reports `t=3` but distance 6 m. Compare to the independently calculated [fixture cases](../../../../research/performance/graphics_handoff/rt_fixture_cases.json) and [reference](../../../../research/performance/graphics_handoff/rt_fixture_reference.py), not the shader's own math. Inputs are first rounded to float32, then the reference uses exact rational geometry over those inputs and converts output fields to float64. It also reports barycentrics, which this minimal GPU witness does not. The [reference contract](../../../../research/performance/graphics_handoff/rt_fixture_README.md) deliberately rejects exact triangle edges, equal-distance ties and interval endpoints from strict GPU acceptance; it is not a GPU arithmetic model. Choose and record a float32 tolerance before running and reject NaN, unexpected sentinels or wrong identity. The fixture checks geometry and ABI, not a rendered shadow or real-device qualification.

The existing offline reference check, not a GPU or performance test, is:

```sh
python3 -B -m unittest discover -s research/performance/graphics_handoff -p 'test_rt_fixture_reference.py' -v
```

## Card 4 — Execution, negative cases and retirement

Create the compute pipeline and set only after shader compilation and RIDs succeed. Build BLAS then TLAS, bind compute pipeline/set/push data, `compute_list_dispatch(list, 1, 1, 1)`, and end the list. On the **local** device `submit()` then `sync()`; obtain the witness with `buffer_get_data`. The pin's synchronous readback itself flushes and stalls. These waits/readback are acceptable only in this bounded diagnostic. The main RD has a different owner/render-thread/graph lifecycle; do not call local-device `submit`/`sync` on it or add per-frame CPU readback to the effect.

After completion, free the uniform set and compute pipeline/shader, TLAS, SBT range via `hit_sbt_range_free`, SBT, ray-tracing pipeline/shaders, BLAS, vertex and result buffers, then local device. Respect dependencies and check the actual engine's deferred native destruction; on early error free only resources successfully created, and if submission occurred retain everything until real completion. Never free a range while a TLAS still uses it. Exercise repeat create/build/query/teardown and forced failures in a disposable process; require no engine errors, validation errors, leaks, stale markers or false success. Expected zero-range rejection must be asserted as a **child failure**, since the checked runner rightly treats engine error records as failure. Also cover missing feature, failed shader/AS/pipeline creation, invalid buffer/range, transformed/masked instances and absent device. A no-device run is unavailable, not a failed native GPU or passing rendering test.

## Card 5 — Candidate selected-sun image, only after the witness

**Proposed engine seams:** exact-pin `servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered.glsl` and `forward_clustered/render_forward_clustered.cpp`, with any bounded scene-input ownership in the renderer; app-side sun identity and existing `app/render/shadow_settings.gd` stay coordinated with VQ/GDU. In the pinned directional loop, [shadow attenuation reaches `light_compute`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered.glsl#L2728). Prove a stable designated Sun identity and matching viewport/generation; another directional light can be lightning. Either bind a pre-opaque visibility image after proving matching depth/normal prepass, or evaluate a query at that light point. Neither a public scene TLAS nor public direct-sun buffer is established. Check reverse-Z, projection, jitter, sample coverage/MSAA, extent and receiver material; a pre-opaque callback alone cannot inject a new lighting binding.

For the controlled opaque receiver, **replace** the selected sun's raster visibility in the admitted region and apply its existing shadow opacity/range fade and cloud transmission once. The pinned shader reconstructs packed eight-bit visibility by dividing by 255 before the `shadow_opacity`/`blur_shadow` mix. Specify exactly where the candidate replaces this value and preserve the actual pinned policy; the offline energy oracle is an ideal linear contract, not a bit-exact model of this packing, Godot's BRDF or pixel quantization. Verify both direct diffuse and specular; preserve ambient, emission, other lights and their existing cloud behavior. Extend the existing [`test_shadow_energy.gd`](../../../../tools/graphics/test_shadow_energy.gd) with an actual candidate path: its current 512×256 raster-only unoccluded test is not an RT or 1080p pass. Add blocked/unblocked, nonzero ambient/emission, second directional and partial-opacity/fade cases, plus off-camera and moving rigid casters. Compare raw mask and integrated image to CPU/light-energy references, then use the [existing capture and frame-diagnosis tools](../../../tools/graphics.md) on the real target; the existing [launcher command](../../../../tools/graphics/README.md) is real, whereas a new fixture command must wait for implementation.

The **existing**, not-run raster control is the following, after native host admission and imports; replace the placeholder with a fresh absolute path:

```sh
shadow_energy_output=/absolute/new/capture
python3 tools/graphics/launch.py --profile high --script ../tools/graphics/test_shadow_energy.gd -- --out="$shadow_energy_output"
```

Require its report's `complete` and `passed` fields and inspect errors, rather than treating `--capture-only` as a pass. This establishes the current unoccluded comparison only.

Normal flight needs complete relevant caster/receiver coverage: aircraft and hinges, visible propeller representation, field/ground, structures, off-camera casters, MultiMesh foliage, wind/deformation, cutout alpha, masks, LOD and transparent policy. Unsupported or stale relevant content retains the **whole viewport's raster** result. Rebuild on changes unless an actual pinned backend update route is proven; rebuild invalidates dependent TLAS. Retain all in-flight resources through verified GPU completion, restore raster and invalidate history on failure/resize/world change, and allocate/dispatch nothing new while disabled. Device loss follows engine recovery. The useful-fixture checkpoint includes cost; for later flight the existing proposed ceiling is ≤2.0 ms incremental GPU p95 and ≤128 MiB peak incremental **allocated** GPU resources, with stricter measured headroom controlling. Real 1080p alternating flight/readability and complete coverage gates remain in [14](../14-ray-tracing-quality-and-delivery-plan.md#7-work-sequence-tests-and-exit-decisions).
