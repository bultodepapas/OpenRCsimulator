# Community cases: resolution and temporal upscaling

**Research date:** 2026-11-15. Six distinct first-person developer reports, with primary maintainer/vendor evidence, mapped to application baseline `e488ef7653e8dd0f0a2e7db18e396bb4da0aaccc` on audit branch `audit/graphics-performance-technologies-2026-11-15`, document parent `3dc343bb5d3654c75eee6e4078da1bb0f6e9d9ff`. Official Godot beta2 is pinned at [`cafc17a192acf67903910a68aeb3c076c0907a4b`](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-2/); patched Windows and Metal builds are separate identities. Later `main` is not integrated. These are reports and proposed checks, not OpenRC reproductions or hardware qualifications. Dates and statuses below are as inspected for this research.

**How to use these cases.** Reuse the [timing and DRS design](../09-timing-and-drs-design.md) and [execution playbook](../11-test-and-execution-playbook.md), including its host admission and actual success markers. The proposed checks fit the existing M0 screen or the one selected M1 provider correction; they do not create six new release gates. M0 remains at most **five engineering days total**, with a static-only decision if associated fresh GPU feedback is unavailable. Do not add a telemetry stack. Qualify at 1920 × 1080 first, higher resolutions next, 1280 × 720 last. All decisions preserve the existing 240 Hz, float64 simulation. Compare named engine/provider/device builds and actual observed extents; a requested enum, estimated size, successful CPU encode, or a frame-rate anecdote does not establish GPU execution, completed history, or a whole-game gain.

## C-DRS-01 — Fullscreen and a scaler coincided with persistent frame drops

**Report.** In a [Godot forum thread](https://forum.godotengine.org/t/fps-go-crazy-when-changing-to-fullscreen-with-gi-and-variable-fsr2-scale/124676) opened 2025-10-09, a developer using **Godot 4.5 stable** described a frame-rate-averaging FSR2 scaler that became erratic after a resize/fullscreen change. The drops reportedly continued in later runs with the scaler disabled; clearing shader cache and intermittently removing VoxelGI or a rope addon did not yield a stable diagnosis. GPU, CPU, OS and exact display are **unknown**; the project was not shared. The thread contains no confirmed fix or minimal reproduction. The proposed physics, caching, VRAM and GI explanations in replies are hypotheses, not measured causes.

**Corroboration and limits.** At the [exact beta2 server scale setter](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L1097-L1109), a changed clamped float leads to buffer configuration; the [pinned RD configuration](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_rd/storage_rd/render_scene_buffers_rd.cpp#L127-L212) frees/recreates resources. This supports *possible resource work*, not an allocation stall, causation in the forum report, or a latency estimate. Confidence is high in the inspected code path, low in the forum's unisolated cause; custom engines can differ.

**OpenRC decision and smallest action — adopt a controlled transition comparison; avoid an FPS-only writer.** [`Reconstruction.apply`](../../../../app/render/reconstruction.gd#L246) owns the scale, [`AppRoot._on_ui_window_resized`](../../../../app/app_root.gd#L2064) reapplies the active preview, and [`test_advanced_graphics_settings.gd`](../../../../app/tests/test_advanced_graphics_settings.gd#L418) already checks resize during Auto preview. **Only if transition behavior is the single selected M0 product question**, use its already allocated 1080p native screen on the same frozen workload: repeat a fixed setting without resize, then a matched resize/fullscreen transition with that same fixed setting; record the event, actual output/input where observable, frame-time tails and recovery. Otherwise defer this comparison to the relevant M1/finalist lifecycle review; it is not an extra mandatory M0 campaign. Reuse the existing settings test for the draft/rollback assertion. **Falsifier:** a repeatable transition-specific tail or failure relative to unchanged repeats rejects the assumption that the transition is harmless on that configuration; no difference within the predeclared uncertainty is inconclusive, not proof for other devices. Attribute a cause only after a discriminating follow-up; keep DRS ineligible when timing freshness is unknown.

## C-DRS-02 — Object motion-vector resets are not camera-history resets

**Report.** In a [Godot documentation discussion](https://github.com/godotengine/godot-docs/issues/11119) from 2025-07-18–23, the Terrain3D developer described moving low-level clipmap instances and needing both interpolation and motion-vector handling for TAA/FSR2. The original warning was reported on **Godot 4.5 beta3**; hardware and OS were **not provided**. A maintainer distinguished scene-tree interpolation from rendering motion vectors and explained that `instance_teleport` is the low-level motion-vector path. The developer later reported that gating the obsolete server interpolation call to 4.4 did not break their terrain on 4.5 beta3. That is a scoped compatibility result, not a visual-quality proof. The original documentation issue was closed after the warning was traced to the addon; this does not prove all ghosting is fixed.

**Corroboration and limits.** Upstream [PR #105437](https://github.com/godotengine/godot/pull/105437), merged as `8954125990b80bc09a91e66543e3c0554feb15bd` on 2025-04-25, introduced the explicit object motion-vector reset. This round verified that merge is an ancestor of `cafc17a…` and read the [exact `VisualInstance3D` notification](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/scene/3d/visual_instance_3d.cpp#L106): a reset-physics-interpolation notification forwards to `instance_teleport` when the visual is visible and inside the tree. That is a source contract, not proof of a custom engine or every descendant/visibility lifecycle. AMD's [FSR 2.2.1 guidance](https://github.com/GPUOpen-Effects/FidelityFX-FSR2/blob/master/README.md#camera-jump-cuts) separately describes resetting the *upscaler's accumulated history* on a camera jump cut. Neither operation substitutes for the other, nor does this thread prove OpenRC has a defect. Do not add a redundant engine patch or assume a camera-reset counter verifies object motion vectors.

**OpenRC decision and smallest action — keep the two boundaries separate; defer a patch until observed.** [`Main._render_pose`](../../../../app/main.gd#L3531) moves the aircraft root; [`CameraRig`](../../../../app/render/camera/camera_rig.gd#L277) queues a viewport history request on a target teleport. [`heli_wreck.gd`](../../../../app/render/rotor/heli_wreck.gd#L120) already resets Node interpolation after wreck-body placement. Reuse the existing [`test_camera_history.gd`](../../../../app/tests/test_camera_history.gd#L52) to verify one post-placement camera request and no repeated request on settled motion; it does **not** test object motion vectors. During the existing 1080p finalist motion/cut review, inspect one reset/relaunch sequence with the aircraft moving against the terrain and record whether a trail remains at its old position. **Falsifier:** a persistent old-position trail specific to a proven temporal provider merits inspecting that exact engine's object reset/visibility and vector path; it cannot be repaired merely by asserting the camera-reset counter. Smooth movement must not be made a per-frame reset.

## C-DRS-03 — Moving-camera ghosting survived an Unreal FSR2 plugin workaround

**Report.** A developer's [FSR2 issue #102](https://github.com/GPUOpen-Effects/FidelityFX-FSR2/issues/102), opened 2023-03-13, reported edge ghosting in the third-person sample using **FSR 2.2 and Unreal Engine 5.1.1**, during smooth camera rotation. GPU, OS and driver were **not stated**. The reporter verified that the plugin was active and inspected velocity and temporal lock behavior; they saw a debug warning about the time-delta input. A subsequent near/far parameter change reportedly reduced artifacts but left visible one-frame artifacts on a lit metallic material. The issue remained open in the inspected thread with no maintainer-confirmed fix. The reported time warning, unusual velocity values and lock experiment are leads; their causal relationship was not established.

**Corroboration and limits.** AMD's [FSR 2.2.1 integration guidance](https://github.com/GPUOpen-Effects/FidelityFX-FSR2/blob/master/README.md#input-resources) identifies motion, depth, jitter and history as provider inputs, and its [camera-cut section](https://github.com/GPUOpen-Effects/FidelityFX-FSR2/blob/master/README.md#camera-jump-cuts) calls for a history reset on an actual jump cut. This Unreal report cannot establish the same bug or near/far workaround in Godot, and normal camera rotation is not itself a jump cut. Confidence is moderate that the reported repro was visually observed, low about its cause and transferability.

**OpenRC decision and smallest action — adopt a paired visual/control check, not the workaround.** [`CameraRig`](../../../../app/render/camera/camera_rig.gd#L309) and [`Reconstruction.request_history_reset`](../../../../app/render/reconstruction.gd#L395) are the application seams. [`test_reconstruction_history.gd`](../../../../app/tests/test_reconstruction_history.gd#L54) already rejects unsupported FSR reset submission; the custom Windows [FSR history fixture](../../../../tools/graphics/native/repro/README.md#fsr-temporal-history-regression) tests two-view dispatch/reset isolation. Reuse those on the chosen engine, then include one smooth pan across an aircraft/terrain disocclusion and one explicit cut in the existing 1080p moving-image review. **Falsifiers:** smooth pan generating repeated reset requests, a cut not reaching the supported provider's reset dispatch, or a visible stale silhouette after a cut rejects the corresponding claimed behavior. The fixture's successful dispatch is not an image oracle or proof of GPU completion. Stock/older engines without an advertised reset API must remain explicitly unavailable for that contract; the prior [RTX 3090 fixture result](../../../research/advanced-graphics-2026-10-21/amd-fsr-2026-10-28.md#later-latch-builds-package-and-rendered-fixtures) is historical, not this branch's acceptance.

## C-DRS-04 — Additive billboards shimmer under FSR2

**Report.** In [Godot issue #85123](https://github.com/godotengine/godot/issues/85123), opened 2023-11-20, a developer showed additive lamp billboards shimmering in **Godot 4.2 RC1, Windows 11, RTX 2070 Super** and reported that the comparison with TAA looked correct. Another contributor reported a similar low-resolution effect on Godot 4.3 in 2024; their hardware was not given. The issue is **open** with no linked fixing PR in the inspected thread. An FSR contributor suggested sensitivity to brightness and subpixel effects, explicitly as an uncertain explanation; it is not a proven root cause.

**Corroboration and limits.** AMD's [FSR 2.2.1 reactive-mask guidance](https://github.com/GPUOpen-Effects/FidelityFX-FSR2/blob/master/README.md#reactive-mask) says blended areas without depth or motion data can need separate reactivity information. It does not prove this issue is missing a mask, or establish which mask Godot supplies in `cafc17a…`. Do not copy another upscaler's reactive settings or infer that all additive content fails. Confidence is moderate for the reported scene-specific observation and low for its mechanism and current OpenRC impact.

**OpenRC decision and smallest action — inspect real content before changing a shader or engine.** [`stars.gdshader`](../../../../app/render/world/stars.gdshader#L7) is additive and avoids depth writes; [`campfire.gd`](../../../../app/render/world/campfire.gd#L90) builds transparent camera-facing flames, although those flames use blend-mix rather than additive. In the existing finalist capture/review, hold scene time and exposure consistent, then compare a short matched camera pan at 1080p with Native versus the selected fixed FSR2 mode, including night stars and/or the flame against terrain. [`tools/graphics/capture.gd`](../../../../tools/graphics/capture.gd#L158) can capture FSR2 **native** AA; do not label it as an `fsr2_quality` capture. Use the full-app route for another fixed option. **Falsifier:** effect-linked flicker or background corruption appearing in the selected FSR2 sequence but absent in the matched Native sequence makes that mode/content combination a candidate for focused investigation; a still image or one material alone cannot qualify motion. First inspect the actual provider's masks and vectors; do not preemptively create a mask pipeline.

## C-DRS-05 — Unsupported MetalFX request left temporal jitter active

**Report.** [Godot issue #103782](https://github.com/godotengine/godot/issues/103782), opened 2025-03-08, reported jitter after requesting MetalFX Temporal on an unsupported renderer: **Godot 4.4 stable, Fedora 41/X11, OpenGL Compatibility, RTX 4090, NVIDIA 570.86.16, i9-13900K**. This is a fallback-path report, **not** a test of MetalFX executing on Apple hardware. [PR #103792](https://github.com/godotengine/godot/pull/103792) closed it, merged as `3b66cb5` on 2025-03-12, and was cherry-picked for 4.4.1. The PR describes trying Spatial or FSR alternatives when eligible; its maintainer reported a Linux test.

**Pin check and limits.** The retained exact-beta2 [`renderer_viewport.cpp`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L156-L205) contains capability-dependent MetalFX Temporal → Spatial/FSR2 fallback logic, and the [setter](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L1035-L1055) rejects temporal modes outside Forward+. This round also verified merge `3b66cb5f8dee1ff3af432388671629a13a481309` is an ancestor of the pin. It is not proof of all fallback pixels, a custom patch stack, or Apple's scaler execution. **Do not propose reapplying the historical PR.** Apple documents [distinct Spatial and Temporal inputs](https://developer.apple.com/documentation/metalfx) and creation costs; it does not convert this Linux report into an Apple result.

**OpenRC decision and smallest action — preserve explicit effective/unknown status.** [`metalfx_policy.gd`](../../../../app/render/metalfx_policy.gd#L36) requires Metal, the appropriate renderer/device and Temporal trial/range gates. [`Reconstruction.resolve`](../../../../app/render/reconstruction.gd#L122) falls back to Native when unavailable and deliberately marks selected MetalFX execution unknown pending evidence. Reuse [`test_metalfx_policy.gd`](../../../../app/tests/test_metalfx_policy.gd#L28): unavailable driver or Mobile Temporal must retain the requested preference while resolving Native at scale 1.0; a valid injected selection must still say execution is unknown. **Falsifier:** an unsupported request shown as effective MetalFX, or a lost saved request, fails the policy check. If this provider is the selected M1 correction, reuse its existing [native fixture and GPU status](../../../../tools/graphics/metalfx/README.md#optional-gpu-completion-observation) to distinguish actual fallback, encode and GPU completion; a fake policy result cannot establish those. No independent supported-device community MetalFX Temporal failure was adequately documented in this search.

## C-DRS-06 — Above-native FSR2 fell back to bilinear but kept the wrong type

**Report.** [Godot issue #107704](https://github.com/godotengine/godot/issues/107704), opened 2025-06-19, reported dancing hard edges at **1.25× FSR2** in **Godot 4.4.1**, Solus 4.7/X11, Vulkan Forward+, RTX 3080 Ti/NVIDIA 570.153.02 and Ryzen 9 5950X; the reporter said it was not reproducible in 4.3. [PR #110672](https://github.com/godotengine/godot/pull/110672) identified a fallback that changed the scaler mode but did not update its temporal/spatial type; it closed the issue and merged as `9f4f16c` on 2025-10-06 for the 4.6 milestone.

**Pin check and limits.** The retained [exact beta2 fallback source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp#L211-L230) updates `scaling_type` after switching to bilinear above native. This round also verified merge `9f4f16c58831faf31a37cd9728abc057549c1e5b` is an ancestor of the pin. The source check is not a rendered result, and it does not establish other forks' behavior. Confidence is high in the reported upstream fix and exact-pin source path, not in untested hardware images. **Do not reapply PR #110672.**

**OpenRC decision and smallest action — retain the current legal fixed table.** [`Reconstruction.SCALES`](../../../../app/render/reconstruction.gd#L29) tops out at 1.0 for product FSR2 and MetalFX selections, so the reported 1.25× trigger is outside these choices. Inspect that table alongside [`test_reconstruction.gd`](../../../../app/tests/test_reconstruction.gd#L24) and [`test_metalfx_policy.gd`](../../../../app/tests/test_metalfx_policy.gd#L84); their existing fixed-value and fallback checks cover examples, but comparing `apply` to `resolve` alone does not prove a 1.0 ceiling. If the table changes, add an independent ceiling assertion to that existing policy test; no new provider or super-resolution control follows from the issue. **Falsifier:** a product temporal entry resolving above 1.0, or an unavailable entry not resolving to Native, rejects this policy assumption. If a future change intentionally exposes supersampling, add the 1.0/1.25 transition to the existing native renderer fixture and inspect hard edges and actual effective mode on that exact engine; this is a future conditional regression, not a new current acceptance gate.

## Evidence boundary

The beta2 server and render-buffer statements above were checked against the retained exact-pin excerpts and the audit's [source manifest](../evidence/source-manifest.json). The upstream issue pages, maintainer discussions and vendor documentation were read for their specific claims; the lead verified the three named upstream merge ancestries and the exact object-reset source. No new application test, native fixture, GPU capture, measurement or compilation was run for these case studies. Provider status, implementation fixes and actual image quality must be rechecked for the chosen candidate and host; absence of a reported issue is not a pass.
