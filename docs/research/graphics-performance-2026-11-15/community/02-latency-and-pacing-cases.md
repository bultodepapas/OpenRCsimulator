# Community cases: latency, frame pacing and display boundaries

2026-11-15 · Six additional first-person reports for the [graphics audit](../README.md), mapped to its existing [Reflex design](../10-reflex-and-ray-integration-design.md) and [execution playbook](../11-test-and-execution-playbook.md). These are historical observations on the named stacks, not measurements of OpenRC. A report is not itself a general API contract. The exact [Windows/Vulkan NVIDIA fork and patch order](../10-reflex-and-ray-integration-design.md#1-reflex-actual-ownership-and-ordering) use Godot `135dff3887a3d2ccf45cafbd9bdffa7b718e1e76` and Streamline 2.11.1; the official engine is a separate path. A 2.14.16 trial was rejected at startup; none of these reports authorizes a blind SDK upgrade. No hardware, application or physical-latency test was run for this page.

## C-LAT-01 · Where the limiter waits can change the physical result

**Report and result.** In [gamescope #474](https://github.com/ValveSoftware/gamescope/issues/474), opened 2022-04-25, a Steam Deck owner compared *The Witcher 3* with a 30 fps limit and in-game VSync off. They filmed button bottom-out to the first visible prompt pixels using a Galaxy S22+ at a nominal 960 fps: 77 camera frames (about 80 ms) with the game limiter and 150 (about 156 ms) with the gamescope limiter. The SteamOS/gamescope build, driver, sample count and distribution were not reported. This is a crude observation of that complete setup, not an isolated measurement of limiter delay or a reliable population average.

**Status and corroboration.** A gamescope collaborator said an earlier low-latency limiter had been removed after Xwayland unbounded commits disrupted it. The issue remains open at the research checkpoint; a later comment reported persistent lag on SteamOS 3.6.20. [Gamescope's own documentation](https://github.com/ValveSoftware/gamescope/blob/master/README.md) distinguishes its embedded and nested compositor modes and exposes a separate limiter. It does not establish that this old report describes every current gamescope build or normal native desktop presentation.

**OpenRC seam and smallest check.** [Display preferences](../../../../app/app_state/display_preferences.gd) save `max_fps` and VSync; [AppRoot](../../../../app/app_root.gd#L1970) applies Godot's limit and VSync request. The native Reflex patch initializes SDK `frameLimitUs` to zero in [the lifecycle patch](../../../../tools/graphics/native/reflex_lifecycle.patch#L70). Extend the existing [advanced settings test](../../../../app/tests/test_advanced_graphics_settings.gd) only if that settings behavior changes: preview a supported cap and VSync, revert, then Keep; the saved and applied Godot values must follow the transaction. This headless/settings check cannot establish an effective OS/compositor limit. For a native decision, reuse the [playbook's](../11-test-and-execution-playbook.md#card-4--reflex-and-f6-are-three-different-observations) separate matched F6 and frame blocks with the same build, display, effective cap, VSync and refresh; compare one named cap condition at a time. Log any compositor/external limiter as a distinct condition.

**Decision: adopt** limiter and presentation identity in the existing evidence record. **Avoid** stacking a second pacer or recommending a universal limiter from this report. **Defer** a compositor-specific comparison unless that configuration is the selected native reference or a reproduced problem warrants it; a settings fake cannot prove lower physical latency.

## C-LAT-02 · A clock regression can confound a Boost comparison

**Report and result.** In an [NVIDIA developer-forum thread](https://forums.developer.nvidia.com/t/clocking-issues-in-some-games-with-rtx-5080/322364) and related [open driver issue #781](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/781), users described RTX 5080 clocking stuck around 780 MHz in games with frame generation. The issue reporter identified Arch Linux, kernel 6.13.2, NVIDIA 570.86.16, Cyberpunk 2077 and Proton Experimental/GE or Hotfix; exact Proton and game builds were not specified. They observed 4× frame generation immediately reproduce the low clock after restart, whereas 3× could trigger later; DLSS without frame generation could reach approximately 2737 MHz even with Reflex enabled. Another user reported a temporary disable/re-enable workaround in Hogwarts Legacy, followed by possible recurrence. This was not a controlled Reflex On versus Boost experiment, and FG and restart behavior were important confounders.

**Status and corroboration.** An NVIDIA forum responder reported reproducing the problem internally. [NVIDIA's Linux 570.133.07 release notes](https://www.nvidia.com/en-us/drivers/details/242302/) say a clocking issue in games with DLSS frame generation was fixed; the issue reporter confirmed a fix on 2025-03-26 and closed #781. [NVIDIA's Reflex explanation](https://www.nvidia.com/en-us/geforce/news/reflex-low-latency-platform/) separately describes Boost's clock/power tradeoff, especially under CPU limitation. Neither source measures OpenRC, proves the exact mechanism of every 780 MHz report, or shows that Boost necessarily increases performance or reduces radio latency.

**OpenRC seam and smallest check.** The existing [Reflex adapter](../../../../app/render/nvidia_reflex.gd) distinguishes requested and accepted modes; [`repro/reflex.gd`](../../../../tools/graphics/native/repro/reflex.gd) already runs Off → On → Boost → Off and checks successful SDK state and marker progress on supported hardware. Keep that functional smoke separate from measurements. In the existing matched Off/On/Boost native blocks, record actual driver, clock, power, temperature, frame distribution, cap/VSync and workload/bound status with available host tools. The expected functional outcome is correct mode acceptance and advancing counters without backend failure; the expected physical outcome is **unknown** until F6 distributions clear the predeclared uncertainty. Do not add a recorder.

**Decision: adopt** clock/power/thermal and CPU/GPU-bound attribution for the existing Boost decision. **Avoid** diagnosing a low clock as a Boost defect or prescribing the forum's toggle/driver workaround to OpenRC users. **Defer** FG-specific testing: the OpenRC NVIDIA package has FG disabled.

## C-LAT-03 · Wine translation once lacked a working Vulkan Reflex path

**Report and result.** In [dxvk-nvapi #166](https://github.com/jp7677/dxvk-nvapi/issues/166), opened 2024-03-07, the reporter ran NVIDIA's `vk_streamline` sample on Ubuntu 23.10, with a Reflex-enabled driver and then-current dxvk-nvapi; the GPU, exact driver, Wine, SDK and translation-layer commits were not given. They reported Vulkan low-latency device initialization and Sleep/SetSleepMode errors, so the sample's Reflex frame limiter did not work. This reports failure of a translated Windows sample on that stack, not a measurement of OpenRC native Linux.

**Status and corroboration.** The [implementer's PR #237](https://github.com/jp7677/dxvk-nvapi/pull/237) says the sample worked during development and lists several game checks, with some per-title limitations. It was merged as `91871f9` on 2025-01-24 and closed #166. The report does not contain a post-merge original-reporter latency measurement or establish that all Wine/Proton games support Reflex. The PR is evidence of a translation-layer change and its developer's scoped checks, not evidence about an unrelated SDK release.

**OpenRC seam and smallest check.** Use [the adapter's existing unsupported-path test](../../../../app/tests/test_nvidia_reflex.gd) with a missing singleton/API: the request remains representable, availability is false and On/Boost cannot be reported as accepted. If future product work admits a translated Windows package, use the existing [`repro/reflex.gd`](../../../../tools/graphics/native/repro/reflex.gd) on that *named* build and stack: the required outcome is accepted mode plus Sleep/marker progress or explicit `REFLEX_SMOKE|UNAVAILABLE`/failure, never success inferred from a menu label. Keep the Windows/Vulkan fork, its Wine/Proton translation, and an actual native Linux integration separate in receipts. The [pinned fork's build configuration](../../../../tools/graphics/native/build.py) does not by itself establish native Linux SDK integration.

**Decision: adopt** explicit runtime capability/failure evidence and separate environment identities. **Avoid** inferring native Linux support or lack of support from a 2024 Wine issue. **Defer** a new Linux SDK port or added Wine test matrix until independently owned and justified; reuse the current reference host first.

## C-LAT-04 · Mouse-triggered stutter varied with the compositor path

**Report and result.** [Gamescope #1626](https://github.com/ValveSoftware/gamescope/issues/1626), opened 2024-11-12, reports mouse movement causing severe frame delays in Cyberpunk 2077 on Fedora 41, RTX 4060 Max-Q, NVIDIA 565.57.01 and gamescope v3.15.0 or newer. The reporter bisected to [`dd77e4d`](https://github.com/ValveSoftware/gamescope/commit/dd77e4de10974bdbfe8252f6ec6f4c8723ac3305), associated the effect with a 4K display or sub-1080p game rendering on a 1080p display, and said in-game VSync reduced the stutter. Keyboard and gamepad input did not show the same symptom in that report. The exact game and Proton versions were not supplied; it reported visual stutter, not an optical input-latency distribution.

**Status and corroboration.** The issue remains open at this checkpoint. In a 2024-12-18 follow-up on gamescope 3.16.1, a collaborator observed that WSI and present-wait combinations changed the symptom; another user said disabling `VK_KHR_present_wait` shortened stutters but added perceived input latency, while a different user reported a workaround. These mixed outcomes do not establish a universal fix. [Khronos' `vkWaitForPresentKHR` contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkWaitForPresentKHR.html) explicitly does not require a precise relationship between a successful wait's present-ID update and pixels reaching the user; it does not diagnose the cause of this issue.

**OpenRC seam and smallest check.** [AppRoot's focus handler](../../../../app/app_root.gd#L2979) and the existing [focus-recovery test](../../../../app/tests/test_ui_recovery_dead_ends.gd#L170) distinguish embedded UI focus from OS-window focus; [the simulation test](../../../../app/tests/test_simulation.gd#L54) checks that returning focus leaves the simulation paused. Pair that software test, if this boundary changes, with [the F6 marker test](../../../../app/tests/test_latency_patch.gd): window focus loss must pause, regain must not silently resume, and the marker must be gray while flight is paused. This is a safety/route oracle, not a latency measurement. On a named native host only, follow the existing minimize/restore and normal-Home checks; record active input type, drawable/output size, focus/menu state and compositor. Do not mix paused/menu samples into active-flight optical distributions.

**Decision: adopt** compositor and input/focus state as identity and lifecycle evidence. **Avoid** making the VKD3D environment workaround or VSync a player default. **Defer** expanding the matrix to gamescope or DX translation unless that is an actual supported deployment or an observed regression.

## C-LAT-05 · Present-call spacing is not display spacing

**Report and result.** In [Streamline #65](https://github.com/NVIDIA-RTX/Streamline/issues/65), opened 2025-05-19, a developer saw irregular `Present()` intervals with DLSS frame generation in Streamline 2.7.2 and 2.7.32, while 2.4.10 did not show the same pattern. They reproduced it in the sample and saw different behavior on two reportedly identical monitors. GPU, driver, exact monitor configuration and Windows version were not reported. On one monitor, their first two rows showed roughly 0.498 and 10.905 ms between Present calls but 5.848 and 4.806 ms between display changes. On the other, they reported a mixture of roughly 16.6 ms display changes and zero entries. These are selected example rows, not a statistical comparison or a physical input endpoint.

**Status and corroboration.** A respondent explained that the first case used hardware flip metering; they suspected composition at 60 Hz with dropped frames in the second. The issue was labeled non-bug, and its author closed it on 2025-08-06; the suspected display-path explanation was not independently reproduced here. [NVIDIA's FrameView 1.4 guide](https://images.nvidia.com/content/geforce/technologies/frameview/frameview-1-4-user-guide-web-version.pdf) defines `MsBetweenPresents`, `MsBetweenDisplayChange`, and dropped frames as different fields. NVIDIA's [PC-latency explanation](https://developer.nvidia.com/blog/?p=64245) also distinguishes present-to-display from display scanout. Neither proves physical RC stick-to-photon latency.

**OpenRC seam and smallest check.** [FrameDiagnostics](../../../../app/render/frame_diagnostics.gd) and [frame_diagnose.py](../../../../research/performance/frame_diagnose.py) report application timing, while [the native Reflex smoke](../../../../tools/graphics/native/repro/reflex.gd) observes SDK calls and counters. Their outputs must not be relabeled as display-change or optical measurements. If report interpretation changes, extend the existing [test_frame_diagnose.py](../../../../research/performance/test_frame_diagnose.py) fixture so missing presentation evidence remains unknown and is never fabricated from process or present intervals; the existing v2/v3 compatibility checks still apply. Reuse an already available OS presentation tool only for a separately labeled matched block, including dropped/undisplayed frames and observer overhead; use [F6](../../radio-input/F6a/README.md) for the physical radio endpoint.

**Decision: adopt** separate application, SDK, display/present and physical endpoint labels. **Avoid** treating equal FPS, short Present intervals, or nonzero marker counters as proof of equal visible pacing or pilot latency. **Defer** adding a new presentation profiler; FG is disabled in this package.

## C-LAT-06 · An Off-to-On transition can expose missing frame association

**Report and result.** On 2026-08-20 a developer described an NVAPI-compatible vkd3d-proton implementation in this [NVIDIA forum discussion](https://forums.developer.nvidia.com/t/reflex-marker-association-across-a-low-latency-off-on-transition/380728). Their simulation-start for external frame X ran while low-latency mode was Off, then activation occurred before render-submit-start for X. They reported their implementation had skipped its inactive-frame ledger entry, producing `MAPPING_ABSENT`/`INVALID_RENDER_START` and a sticky pacing bypass for that active epoch. This is an implementation-accounting report, not a measured latency, an OpenRC failure, or proof that the caller or driver violated a contract. GPU, driver, software commit and test hardware were not given.

**Status and corroboration.** A forum respondent answered on 2026-09-03 that marker tracking continues independently of whether `vkSetLatencySleepModeNV` has enabled sleep, and that ordering of those calls does not matter. That answer addresses the Vulkan sleep-mode/marker relationship; it does not prescribe this translator's ledger repair or resolve every Streamline token-lifetime case. [Khronos `VK_NV_low_latency2` revision 3](https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_low_latency2.html) separately describes sleep before input and its own frame-attribution facilities. The [pinned Streamline 2.11.1 guide](https://github.com/NVIDIA-RTX/Streamline/blob/019994e18d256a3e92347888deb527feb7f58bc0/docs/ProgrammingGuideReflex.md) is the relevant guide for the OpenRC fork: supported Sleep and PCL markers continue when the mode is Off. Do not assume the fork uses the direct Vulkan extension merely because the forum discusses it.

**OpenRC seam and smallest check.** In the ordered [frame-token](../../../../tools/graphics/native/dlss_frame_lifecycle.patch) and [Reflex synchronization](../../../../tools/graphics/native/reflex_sync.patch) patches, a draw captures its own token and mode changes apply after synchronization. Extend the proposed RX-04 fake SDK/event seam in [the integration design](../10-reflex-and-ray-integration-design.md#proposed-focused-tests-and-discriminating-oracles), not a shipping recorder: delay draw N until the main thread has token N+1, request Off → On at the boundary, and record actual call order and tokens. Expected: N's render/present command callbacks finish before the post-sync option change is applied (not proof of GPU completion); supported Sleep/markers continue in Off; each drawn frame's render/present markers use its captured live token with starts before ends; a stale token triggers the existing failure/Off path rather than being attributed to N+1. A skipped draw must not invent a present. The current smoke's independent counters prove progress only; they cannot prove same-frame association.

**Decision: adopt** this targeted transition as an RX-04 negative case. **Avoid** inventing token association or replaying a marker solely because numeric IDs match across an epoch. **Defer** a direct `VK_NV_low_latency2` implementation and never run it as a second independent pacer alongside Streamline.

## Decisions and limits for the existing work

- **M0 stays within five engineering days total.** Use the already named 1080p reference configuration, existing collectors and one initial attribution/overhead decision. These community reports add no recorder, profiler, SDK upgrade or platform matrix to M0. If coherent GPU evidence is unavailable, retain the existing static-only/blocked outcome.
- **For VQ-07h, strengthen RX-04 and record actual modes.** Preserve supported Sleep/markers in Off, the captured draw token, serialized state/options and honest requested/accepted/failed status. Run the existing functional smoke and SDK verification on the actual pinned build; their success does not substitute for physical F6. Preserve the established flash-trigger gap and verify it separately when applicable.
- **For F6, distinguish the measured endpoint.** Use at least 30 valid transitions per condition as a screen and target at least 100 across repeated sessions for a descriptive p95. Record rejects and uncertainty. At a 240 fps camera rate, a frame interval is about 4.17 ms before exposure, scanout and annotation uncertainty; it cannot by itself resolve a 1 ms effect. Record stick-to-patch and stick-to-first-visible-control-response separately. The live marker forbids scripted, frame-diagnostic, trace, capture and visual-pose options: use separate matched diagnostic blocks.
- **For comparisons, freeze the real condition.** Save actual package/editor/template/SDK and driver identities, effective 1080p drawable and monitor/refresh, VSync/VRR, cap and any compositor, input/radio, clock/power/temperature, focus/menu state, load and session order. A process frame distribution, SDK marker, display event and filmed stick response each describe different boundaries. Compare Off/On/Boost in the same build; stock-versus-fork comparisons also include engine differences.
- **Preserve simulation and the existing owners.** Do not change the fixed 240 Hz physics, input ownership or replay/golden data to improve a presentation metric. Close a comparison as experimental, retain-baseline or inconclusive if accepted mode, hardware, uncertainty, display path or physical input evidence is missing. No case here qualifies any OpenRC driver, Linux environment, device, mode or performance gain.
