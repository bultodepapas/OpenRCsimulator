# RC blimp investigations I17–I24: simulator integration

**Date:** 2026-11-08. **Scope:** eight decision investigations for the [generic 5 m blimp plan](../../plans/rc-airship.md). This report records source inspection and analytical calculations, not an implemented airship or a simulator qualification run. The source baseline moved during dispatch from `41ce5af6f4a148b4ea101b08883fd4e03878bb07` to `4bda2e4540fc07ebe8eb63d35072fd5aead39cbe`; the findings below use the latter. Unrelated concurrent changes are preserved.

Method: graph search, trace and snippet lookup were attempted first. The graph returned stale symbol ranges: for example, the stored `AircraftData.load_file` range returned coefficient declarations rather than the current function. Graph text search also omitted some existing modules. Current files were therefore inspected directly. Symbol names and paths below are more reliable than the graph's old line numbers. No runtime/source modifications, engine launches, models or captures were made for these investigations.

## I17 — Which application boundaries require explicit airship capability admission?

**Question/method.** Would adding `vehicle: airship` and a scene route isolate airplane assumptions? Inspected `AircraftCatalog.is_rotorcraft`, `airplane_flyable_entries`, `airplane_visual_families`, `AppRoot.flight_script_path_for_aircraft`, failure/companion admission, `weather_for_aircraft`, Home preparation, Help and restart. Sources: [catalog](../../../app/app_state/aircraft_catalog.gd), [AppRoot](../../../app/app_root.gd), [catalog tests](../../../app/tests/test_aircraft_catalog.gd).

**Finding.** The catalog's airplane list means “not rotorcraft”; the scene dispatcher uses the same binary branch. Failure and companion CLI refusal explicitly protects rotorcraft, leaving a hypothetical airship on the airplane path. Help selects the same two families. Home preloading, pause/restart and settings routes also select on this predicate. Thus a new scene dispatcher alone does not contain the change: an unsupported airship may be loaded into airplane solvers, preview factories or options before launch, or misrouted after restart. The previous plan identified this generally; this inspection establishes a concrete admission matrix to use.

**Plan decision.** In BL-02 specify explicit vehicle family plus positive capabilities: start modes, weather domain, finite energy, recording, Workshop, failures and companions. BL-10 must carry a table of every offered surface—Home, CLI, preview, Help, restart, debug setup and package smoke—with supported/refused outcomes. Keep default compatibility for historical airplane entries at the catalog boundary; consumers must not infer “airplane” from `not is_rotorcraft`.

**Discriminator/limit.** Add an airship fixture to catalog/route tests and require exclusion from airplane-only fleets while preserving their existing IDs/order. Exercise restart and refused unsupported CLI combinations. Static inspection proves the branch risk, not completed UI behavior. This need does not authorize redesigning all catalog architecture or broadening unrelated vehicle support.

## I18 — Can airship data reuse the existing validator without inheriting airplane laws?

**Question/method.** Inspected [AircraftData](../../../app/physics/aircraft_data.gd): `load_file`, `validate_and_derive`, physical coefficient checks, normalization and wheel-profile processing; compared [aircraft contract](../../AIRCRAFT_CONTRACT.md), [rotorcraft reader](../../../app/physics/rotorcraft_data.gd) and [mass inventory](../../../app/physics/mass_inventory.gd).

**Finding.** The current file boundary hashes and parses the same bytes, then applies ground wheel profiles after deriving the aircraft model. Its coefficients encode stable airplane signs, conventional/elevon control topology and airplane datum assumptions. Merely accepting another `format` would make unrelated profile and physical checks reachable. Reusable quantity/provenance discipline does not imply a reusable complete reader. A generic airship can also legitimately have an unstable aerodynamic pitch/yaw derivative stabilized by buoyancy/fins/control; copying airplane sign constraints can reject valid designs or conceal compensating terms.

**Plan decision.** BL-02 needs a dedicated closed reader with one-read source identity, independent numerical model identity, semantic control/state layout and independent physical-admissibility checks. Do not subclass by bypassing errors or supply fake wing/gear fields. Reuse mass/inertia utilities only after converting the declared datum and gas inventory. Separate total rigid-body inertia (positive definite) from added inertia (positive semidefinite under the chosen ideal law); zero ideal added rotational inertia on a sphere must remain admissible. Validate both matrix triangles before factorization.

**Discriminator/limit.** Build matching offline-schema/runtime-loader cases for unsupported laws, arbitrary sign-stable/unstable but admissible coefficient combinations, duplicate gas, inconsistent volume and missing motors. Verify a rejected file preserves the accepted session. No airship reader/schema exists yet; exact field names remain BL-02 design work. This investigation narrows reuse rather than proving data quality.

## I19 — What must exact replay identify, and when are logged loads sampled?

**Question/method.** Inspected [FlightLog](../../../app/sim/flight_log.gd) `start`, `_sample`, `_controls`, `solver_identity`, `_replay_identity`; [CLI](../../../app/tools/flight_log_cli.gd) `prepare_replay`; and [Simulation](../../../app/sim/simulation.gd) `last_loads`/accepted publication.

**Finding.** The source-tree solver fingerprint walks `physics`, `sim` and `failures`, whereas future force-relevant mixing or logic placed in `vehicles/airship` would fall outside it. Package identity follows a different executable-bound path. Therefore reusing the container does not automatically identify the whole new law. The existing raw/stick serialization assumes roll/pitch/yaw/throttle. Samples pair accepted tick-end state with **interval-start RK4 k1 loads**, explicitly labeled in the header; interpreting these as simultaneous endpoint force/acceleration data would bias short transient fitting. Calling force evaluators again from the recorder would add cost and risk observational effects.

**Plan decision.** Keep all authoritative airship dynamics/mixing under identified paths or explicitly extend identity coverage. BL-08 must pin family/law/layout, mixer/command roles, source bytes, model data, atmosphere/weather, initial checkpoint and actual backend/engine/package identity. Label every diagnostic quantity with its time boundary and datum. Reuse accepted/k1 observations already available. Any additional accepted-stage transport needs explicit transactional design, or a separate qualified pure bounded postcommit sample. Current `stage_context` feeds substep selection, and `integration_receipt` feeds endpoint transition; neither is an existing general recorder feed. Side-effect caching from trial/rejected stages is invalid.

**Discriminator/limit.** Change only a mixer law and require exact replay refusal; restore midway through a nonzero vector/motor transient; compare complete state/events; reject a same-width but different-role tape. Candidate replay is a declared compatibility relation, not a blanket escape from identity checks. No existing CLI supports these airship cases today.

## I20 — Does a correct GLB automatically satisfy the airship presentation contract?

**Question/method.** Compared [ModelManifest](../../../app/aircraft/model_manifest.gd) validation and `_check_rotor` with [delivery requirements](../../BLENDER-AIRCRAFT-DELIVERY.md) and the [Khronos glTF 2.0 specification, §§3.3–3.5](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units).

**Finding.** glTF defines units, hierarchy/transforms and quaternion storage, but names need not be unique. OpenRC requires stable unique bindings and uses a different simulation/render convention. Its current model manifest requires airplane datum selectors and one `bindings.rotor` with the public `propeller` node; that is not an arbitrary list of motor/vector installations. A valid multi-prop GLB can therefore import successfully while remaining physically misbound. glTF's XYZW quaternion representation also differs from the simulation's WXYZ. Neither a mesh material nor its volume supplies component density or mass.

**Plan decision.** Before BL-09, decide with AS whether to add a versioned multi-instance presentation capability or an airship-specific adapter/manifest. Reference motor, servo, fin and contact IDs explicitly. Preserve existing wrappers for their current consumers without inventing a fake central rotor or wing-leading-edge datum. Test exported transforms using fixed reference landmarks and a signed rotation, not only bounding boxes. Keep editable source, prepared GLB and measured/assumed physics inventories as separate artifacts.

**Discriminator/limit.** A two-motor/vector-axle fixture must retain unique stable node paths, correct pivot motion, spin sense and rest transforms after export/reimport; swappable skins retain those bindings. The user model is still unavailable, so this finds a contract gap and defines intake acceptance without making a model-quality claim.

## I21 — What camera and readability assumptions break for a long envelope?

**Question/method.** Inspected [CameraRig](../../../app/render/camera/camera_rig.gd) `set_span`, `update`, `near_plane`; [camera settings](../../../app/render/camera/camera_settings.gd); [camera collision](../../../app/render/camera/camera_collision.gd); and [graphics tools](../../tools/graphics.md). Calculated pinhole projection with square pixels at 1920×1080 and 50° vertical FOV.

**Finding.** The shared rig scales chase/orbit/flyby from one “span” and uses a sphere of `0.7*span` in an orbit near-plane heuristic. An elongated hull's width, length and offset from CG differ substantially. Reusing diameter as span may let the camera enter the envelope; using length everywhere may produce unnecessarily distant views. Camera collision queries scenery/terrain and does not thereby prove self-occlusion safety. In an **illustrative** 5×2 m craft at 100 m, vertical focal length is 1158 px: broadside length projects to about **58 px**, while a 2 m nose-on diameter is about **23 px**; at 200 m these halve. Shape alone may not communicate heading, vector angle or fin motion.

**Plan decision.** BL-09 derives an actual visual/contact bound and declared camera target; BL-12 evaluates length/width-aware placement or a conservative bound adapter without changing global camera defaults. Review broadside, nose/tail-on, overhead, close orbit and full vector travel. Test attitude/heading cues under sky/ground backgrounds and actual shadow/material settings. Audio/animation must follow accepted actuator state through pause/reset and failure.

**Discriminator/limit.** Reserve 1080p captures at specified distances/FOVs and a human orientation task; record auto-zoom state, as pixel examples above assume it is off. Screenshots and calculations cannot establish pilot readability or GPU performance before the actual model exists. Higher resolutions follow 1080p; 720p is fallback only.

## I22 — Which numerical oracles catch physically wrong equations that remain finite?

**Question/method.** Inspected the complete `body_derivative` replacement, `VehicleModel.events`, `step_policy`, `substeps`, matrix utilities and existing [generalized-coordinate tests](../../../app/tests/test_sf_generalized_coordinates.gd). Derived coordinate-invariant checks using [Featherstone's spatial transform rules](https://royfeatherstone.org/spatial/v2/xforms.html), and a sphere benchmark from [Brennen, chapter 5](https://media.library.caltech.edu/CaltechBOOK:1995.001/chap5.htm).

**Finding.** A finite symmetric positive-definite matrix and a smooth trajectory can still use the wrong force datum, gravity or body-transport terms. The simplest independent translational benchmark is an ideal rigid sphere in an unbounded inviscid incompressible fluid: added mass `m_A=rho*V/2`; with centered horizontal force, no drag/contact and zero rotation, `a=F/(m+m_A)`. This is an equation test, not a blimp coefficient estimate. With `nu=[v;omega]`, a datum shift by body-fixed `r` requires `v_O'=v_O+omega×r`; compare the **same physical point**, including angular/tangential/centripetal acceleration. Under a constant world boost U, body derivatives differ by `-omega×R^T U`; raw `v_dot` equality is not the Galilean oracle.

**Plan decision.** BL-03 starts with analytical sphere/spheroid fixtures and nonzero three-axis rotation. Test physical point trajectories, wrench power and kinetic energy under datum changes. Derive transformation direction/vector ordering explicitly before using a reference library. For `nu_O=X*nu_O'`, require `M_O'=X^T*M_O*X` and `tau_O'=X^T*tau_O`. Add smooth-regime timestep refinement and event-time refinement separately.

**Discriminator/limit.** Multiple event boundaries need one composed policy; current kernel refuses simultaneous custom policy and requested contact substeps >1. Select that integration design before adding cutoff/reversal/contact. At 240 Hz, dt≈4.167 ms; a linear lag `y_dot=-y/tau` under classical RK4 requires dt/tau≲2.785 for negative-real-axis stability (tau≈1.50 ms minimum without substeps), which is only stability, not adequate accuracy. Qualify actual actuator/contact time scales and never conceal instability with clamps.

## I23 — Can existing benchmarks and recorder limits qualify the whole blimp?

**Question/method.** Read [physics tools](../../tools/physics.md), [graphics tools](../../tools/graphics.md), [FlightLog](../../../app/sim/flight_log.gd) byte/tick/buffer bounds and source/presentation separation; checked the [shared performance policy](../../STACK.md).

**Finding.** A fixed-wing benchmark may silently choose its default for an unknown aircraft ID; a blimp string passed to it does not establish a blimp measurement. Spatial-wind reported p95 values are batch means, not individual accepted-tick latency. Recorder limits are independently bounded at 512 MiB and 864,000 ticks: reaching one does not promise reaching the other. The theoretical 512 MiB/hour ceiling is about **621 bytes/tick** at 240 Hz, but `_flush_rows` starts an ordinary byte-limit stop at `MAX_BYTES-2*MAX_PACKET`, or **480 MiB**, leaving closing space. That implies about **583 bytes/tick** before header/event/footer cost as a planning estimate; chunk boundaries, the 16 MiB packet bound and write failures also matter. Body and six loads alone need **36,480 raw bytes/s**; actuator, control, weather, mass and serialization fields add cost. This is arithmetic, not measured airship record size or guaranteed duration.

**Plan decision.** BL-08 measures actual serialized bytes/tick, peak buffered bytes and observer time with maximum admitted layout/events, handles a byte-limit stop explicitly and preserves completeness semantics. BL-17 requires an airship-specific admitted workload with explicit vehicle/law identity, per-tick distributions, cold/warm loading, sustained flight, recording on/off and whole-app 1080p frame/memory evidence. No existing native receipt admits an airship; optimize only after measured cost.

**Discriminator/limit.** Benchmark must fail an unknown airship/configuration instead of silently flying another vehicle. Publish p50/p95 ticks separately from renderer frame time and batch/provider means. Test disk-full/truncation/cutoff on bounded disposable outputs. No timing or endurance result was measured during this documentation investigation; the estimates define what to measure.

## I24 — Which work can start now, and which fidelity must earn its place?

**Question/method.** Audited the existing BL dependency table against available inputs, [contribution/reuse rules](../../../CONTRIBUTING.md#assets-and-research), the shared kernel/data boundaries and the model-intake uncertainty. Challenged prerequisites with the Good Enemy reviewer.

**Finding.** Requiring the real model before the entire schema/6×6 spike would unnecessarily block useful work. An analytical sphere/spheroid with explicit test-only parameters can establish mathematics and contracts without being a replacement asset or a claimed replica. Conversely, adding every surveyed physical effect to the first playable release would make qualification unbounded. Calm-air short-flight assumptions are adequate only if their omitted effects have a stated domain/error budget and no contradictory marketed behavior. The previous “constant pressure” shorthand also needs precision: freeze reference thermodynamic properties while retaining the implicit hydrostatic pressure gradient responsible for buoyancy; a literally gradient-free static pressure field would not yield Archimedes' force.

**Plan decision.** Split BL-02/03 into analytical laboratory work that can begin now and installed-configuration freeze after BL-01. Define an applicability ledger per subsystem: admitted assumptions, parameters/evidence, observable error, source of uncertainty and trigger for added fidelity. Require zero/reverse-speed finite behavior, correct lift/mass/inertia, actual actuator allocation, reset/replay and conservative collisions for the first playable gate. Defer detailed gas, deformation, tether and autopilot unless demanded by intended activity or a held-out discrepancy. Use free data/tools where suitable and preserve license/source identities.

**Discriminator/limit.** Each proposed feature must identify the failed observable it repairs or explicit product activity it enables, its implementation owner and acceptance evidence. Missing measurements stay open, but do not block a clearly estimated experimental generic model. No date/precision claim follows from the number of investigations; unknown hardware/geometry still controls the installed-model schedule.
