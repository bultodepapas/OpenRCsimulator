# Round 2: ten investigations selected from round-one gaps

**D6-HH-00/R2 — completed research, 2026-11-20.** Studies 11–20 follow the completed [first ten](round-1.md). They use the same OpenRC runtime baseline, `a27c44fcaec0401de852c9a2f791041e34e3974d`, and Godot `cafc17a192acf67903910a68aeb3c076c0907a4b`. The lead checked material findings against the underlying source. The [plan](../../plans/handheld-controller-automation.md) owns implementation order; the [acceptance companion](../../plans/handheld-controller-acceptance.md) turns these findings into reviewable gates. None of these studies ran a physical controller, native bridge or exported game.

## R2-11 — Can optional Steam startup precede SDL without an engine replacement?

**Evidence.** The pinned [core registration](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/core/register_core_types.cpp) loads extensions and initializes their CORE phase. In [main startup](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/main/main.cpp), SERVERS initialization also precedes construction of Input and joypad initialization; SCENE initialization follows. That provides a candidate early seam for the Steam-before-SDL requirement established in R1-02. It does not prove an existing binding uses it correctly.

The pinned [extension manager](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/core/extension/gdextension_manager.cpp) can continue after an extension returns a load failure. This is narrower than recovery from arbitrary native code: an ABI-incompatible library can crash during initialization. Export filtering can also remove an extension from the generated extension list; the existing `addons/*` exclusion needs a deliberate packaging decision.

**Decision.** D6-HH-03 first produces a minimal exported-build feasibility spike. A candidate CORE/SERVERS bootstrap initializes only what is valid at that phase; it must not access Input, SceneTree or unavailable display services. Register and pump scene-facing services later. Probe availability dynamically from scripts and keep Steam linkage out of the mandatory application executable. Record one initialization/pump/shutdown owner and the order of partial teardown. The portable path supports missing extension, supported loader/dependency errors and API unavailability; it cannot promise containment of arbitrary native crashes.

**Acceptance / limits.** Trace extension entry → Steam initialization → SDL initialization → scene startup in Windows and Linux exports. Exercise missing dependencies, wrong architecture, returned symbol/load errors, API failure, offline startup, release filtering and shutdown. Qualify actual binaries before adoption. GodotSteam remains a candidate; neither its current upstream implementation nor compatibility with this beta pin was established. No engine fork or second input loop is authorized by this research.

## R2-12 — What would make Steam association genuinely current?

**Evidence.** Pinned [Input](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/core/input/input.cpp), `joy_connection_changed` and `get_joy_info`, stores and returns a cached dictionary. It consumes and removes the internal `mapping_handled` hint; public `known` therefore does not identify a stable mapping representation. The [SDL driver](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/sdl/joypad_sdl.cpp) fills association at addition but has no remap/Steam-handle-update event case.

Vendored [SDL joystick code](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/thirdparty/sdl/joystick/SDL_joystick.c) can emit a Steam-handle update. Its [Steam virtual-gamepad reader](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/thirdparty/sdl/joystick/SDL_steam_virtual_gamepad.c) checks a client-supplied file on an approximately three-second schedule, conditional on file state and successful reading. This is not an upper bound on fresh association.

**Counterexample.** Two controllers exchange slots while both old handles remain enumerated. Re-reading Godot metadata and finding its handle in Steam's live list can validate the wrong pairing. Waiting three seconds does not fix a cache with no refresh path.

**Decision.** Invalidate affected cross-provider association on slot/configuration/continuity changes. Do not requalify it from cached data plus handle presence. The application-only slice can retain the portable provider and treat an unassociated native endpoint separately. If reliable live association is necessary, evaluate a narrow upstream/engine metadata hook using the already owned SDL gamepad and instance map, forwarding remap/handle updates with a revision. That is a separately gated option, not an adopted engine fork. Do not fake disconnects or open a second SDL stack to refresh metadata.

**Acceptance.** Both-live A/B slot swap; unavailable→valid→changed→unavailable handle without unplugging; missed/delayed updates; stale file; absent metadata; and concurrent radio. Assert one command owner only when association is fresh and unambiguous. Repeat native Windows, native Linux and Proton separately. Unknown association cannot establish duplicate suppression or raw-calibration compatibility.

## R2-13 — How do native actions enter, fail and roll back?

**Evidence.** Valve's [action manifest](https://partner.steamgames.com/doc/features/steam_controller/action_manifest_file) and [input API](https://partner.steamgames.com/doc/api/isteaminput?language=english) distinguish release layout configuration, action sets, binding revisions and action activity. An active flag is not proof that an essential action has a usable binding. Native-only endpoints need not have an SDL counterpart. Binary rollback does not itself restore a Steam user's previous custom configuration.

**Decision.** Native-provider selection is initially session-only and opt-in; leave V2 profile bytes unchanged. Enter through baseline → selected/loading → configuration check → usable Menu context. Flight needs its own capability, mapping and activity readiness checks. Distinguish unknown/loading, wrong context, explicitly unbound and unavailable. Preserve semantic action IDs, Mode 1/2 analog intent and one shaping/integration owner. Keep release receipts containing executable, external manifest/layout hashes, SDK/interface and action revision separate from Valve's schema; do not invent manifest keys.

**Hard limit.** A pure native endpoint with essential recovery actions unbound, no working overlay and no SDL peer may have no controller-operated escape. Hold the activity and explain available keyboard, other-controller or external Steam-client recovery. That configuration fails controller-only qualification; a menu that cannot be reached is not a fallback. Arbitrary native-plus-synthetic-keyboard layouts also remain unqualified when event provenance cannot be established. Do not hide these limits with global keyboard blocking or debounce guesses.

**Acceptance.** Use disposable partner configurations to test clean release discovery, missing files, loading, unbinding, context changes, interrupted promotion and major/minor revisions. Test executable plus manifest/layout rollback and record what happens to custom layouts. Keep legacy gamepad/mouse migration-force flags disabled while those baselines remain supported. Test supported fallbacks with the actual controls available; no implicit Continue, profile overwrite or automatic relaunch.

## R2-14 — What Linux recovery can the application substantiate?

**Evidence.** In pinned [Linux SDL discovery](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/thirdparty/sdl/joystick/linux/SDL_sysjoystick.c), `MaybeAddDevice` silently returns after a failed initial read-only open. A later device open tries read/write for feedback and falls back to read-only for events. Thus an empty Godot list is not a permission diagnosis, and working controls do not prove rumble access. Discovery can use udev or a sandbox fallback with inotify/polling; actual template flags and recognized sandbox state matter. The pinned [udev classifier](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/thirdparty/sdl/core/linux/SDL_udev.c) considers more than `ID_INPUT_JOYSTICK`, so that property's absence alone does not establish rejection.

| Observable fact | Defensible message / next step |
| --- | --- |
| No logical endpoint in this process | Cause unknown; offer reconnect, supported launcher/mode and controller selection checks. |
| Endpoint delivers an expected event | That endpoint/control works; other axes, mapping and feedback still need evidence. |
| Correlated host node absent from the app namespace | Visibility differs for that candidate; do not conclude every virtual/HID path failed. |
| Correlated read-only open returns `EACCES`/`EPERM` under the actual app credentials and namespace | That candidate was denied at that time; use device/distribution-specific support. |
| Unexpected udev classification | Investigate the active discovery path before claiming causation. |

**Decision.** Keep recovery with the [Linux delivery owner](../../plans/linux-support-distribution.md). Existing application observations cannot produce every row above. If support tooling later adds a probe, it should open/close only the identified candidate without reading input and return a typed result. A USB listing, `test -r` or package manifest is not an observed application open result. No new privileged discovery service or automatic permission changes are proposed.

**Acceptance / limits.** Test native direct, native Steam, Proton and each offered sandbox separately. Fixtures must report unknown when evidence is insufficient. [Flatpak permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html) expose classes of nodes: input access is not one-controller access or universal hidraw/USB access. No generic root launch, broad group membership, world-writable nodes or all-device permission. Template flags, host ACLs and physical routes remain untested.

## R2-15 — What is the smallest safe saved-calibration change?

**Evidence.** [V2 matching](../../../app/input/controller_profile_store.gd) can accept same-serial/different-representation and sequential serial-less same-family replacements, as R1-06 explains. [Validation](../../../app/input/controller_profile.gd) assigns raw absolute-channel semantics to calibrated joystick as well as radio profiles. In [Controls](../../../app/ui/controller_setup.gd), `radio_mapping_verified` checks a saved UUID and four channel assignments, not the physical unit; `_associate_candidate` can replace association when saving. The preview clamps values and can display zero for invalid samples, so it cannot by itself prove fresh range or low throttle.

**Decision.** Start with a session-only compatibility review; keep the V2 file format and bytes unchanged on review/cancel. Offer an uncertain raw profile as a suggestion, then **Review and use for this connection** or **Calibrate**. Reuse the current picker, draft and live view. Check fresh current-connection motion, primary-channel direction/raw travel, low-throttle polarity and relevant AUX/actions before explicit confirmation. Inconclusive or failed evidence offers calibration; missing serial alone does not force a full calibration wizard. Confirmation is a user judgment, not proof of historical physical identity.

Bind approval to endpoint continuity and the relevant profile snapshot. Recheck before activation and reassociation. For an already selected generic source, a harmless new duplicate can change [registry generation](../../../app/input/controller_registry.gd) without breaking its continuity; preserve the [service's uninterrupted-flight protection](../../../app/input/controller_service.gd) in that case. **JETI is an explicit exception:** ambiguity changes for a JETI identity claim clear selected flight and UI roles because its starter matching requires unambiguous evidence. Retain that invalidation/hold contract; changing it requires separate JETI-owner review and verification. Do not invalidate every generic active flight solely on a generation increment. Uncertain raw calibration must not obtain menu ownership merely from an old saved radio-menu fingerprint. Preserve a keyboard or other eligible menu device until review.

Cover legacy/direct restoration in [fixed-wing](../../../app/sim/flight_session.gd), [helicopter](../../../app/sim/helicopter_flight_session.gd), [quad](../../../app/input/multirotor_input.gd) and [airship](../../../app/input/airship_input.gd), or explicitly constrain those routes. Standard mapped gamepads retain their current startup; no new centered dwell.

**Later persistence.** If durable evidence is justified, prefer one versioned transactional store. A sidecar needs a digest of the committed profile/association/representation and a missing/stale/torn-data fallback; older builds ignore it. A future V3 primary is not a guaranteed downgrade barrier: today's loader can restore a readable V2 `.rollback`. Test downgrade and backup cleanup explicitly before adopting migration. Cloud and persistent trust remain deferred from this first slice.

**Acceptance.** Sequential A→B replacement, changed representation with same serial, calibrated joystick, uninterrupted generic-source duplicate arrival versus JETI ambiguity invalidation, disconnect during review, raw motion versus clamped preview, AUX/menu trust, cancel byte equality and Save/activation refusal. Use Duplicate/new UUID for a different association when appropriate, preserving the original profile.

## R2-16 — What may a shareable diagnostic report honestly claim?

**Evidence.** The [CLI report](../../../app/input/input_report.gd) accepts a duration up to 3,600 seconds, writes stdout by default and can overwrite a specified file. It prints that path in stderr. Its [data collector](../../../app/input/input_report_data.gd) includes arbitrary names, GUID, ephemeral ID and backend hints; it does not explicitly copy serial, but custom names can contain identifying text. Per-connection axes/buttons/transitions are bounded, while total reconnect records have no global cap.

[Controls diagnostics](../../../app/input/controller_diagnostics.gd) defaults to omitting identifiers, but retains VID/PID, calibration endpoints, actions/AUX and axis samples. It is not a report with no profile data. Detailed mode and ordinary flight/engine logs can add identifiers; bundling those logs would defeat a redacted JSON file. Observed event times describe Godot callback arrival, not physical USB timing.

**Decision.** Introduce a versioned shareable report built from an allowlist. Preserve CLI v1 as an explicit local developer format; add a distinct, mutually exclusive shareable route rather than silently changing its schema. Use report-local device ordinals, standardized statuses, bounded counts/seen flags, build/engine and disclosed OS information, provider evidence quality, clock labels and omission counters. Unknown remains unknown. Keep GUID, serial, raw/custom names, handles, OS IDs, paths, arbitrary errors and nested metadata out of the shareable default. Unsalted stable hashes are not anonymity.

Preview retained fields. Detailed calibration, VID/PID and action information require an explicit inclusion choice when needed. Bound total connection records and serialized bytes as well as duration and per-device events; show truncation. Shareable file output uses the existing no-overwrite approach and typed errors, with its race/durability limits documented. No automatic upload or telemetry is proposed. Exact device/firmware/package evidence belongs in a separately controlled qualification record.

**Acceptance.** Inject identifiers into custom names, profiles, paths, errors and nested fields; inspect JSON, stdout and stderr. Test reconnect storms, unknown/invalid values, truncation, write refusal/cancel and unchanged v1 consumers. Verify no calibration or preference writes. A redacted report can still identify a hardware/software configuration; do not label it anonymous or treat it as physical qualification.

## R2-17 — Which missing commands need more than another menu button?

**Evidence.** [Main's](../../../app/main.gd) controller action dispatcher does not cover every keyboard route. Folding wings, canopy and tailhook handlers reject paused operation and retain aircraft capability/state checks. Wing folding also requires a stopped aircraft on its wheels without a crash and holds throttle during transition. Wheel brake has explicit press/release and clearing behavior. Glow start/cut/mixture and log toggle/marker have distinct acceptance rules. Mechanism labels currently embed keyboard hints. These findings concern the inspected routes, not proof that every existing widget is unreachable.

| Command family | Semantic contract to preserve |
| --- | --- |
| Wing fold, canopy, tailhook | One toggle intent, capability and current-state checks, truthful unavailable feedback. |
| Wheel brake | Held or explicitly supported analog intent, immediate release on loss/hold; never an accidental persistent menu latch. |
| Glow starter/cut and mixture | Accepted start/cut intent; bounded validated mixture adjustment through the existing session API. |
| Flight log toggle and marker | One start/stop action; marker only when recording supports it. |
| Existing Workshop camera controls | Reuse focusable view/orbit/zoom controls and prove full/compact reachability. |

**Decision.** Extend [ControllerActions](../../../app/input/controller_actions.gd) and the owning dispatcher with semantic actions, not F-key synthesis. Keep current guards, conflict rules, localization and visible outcomes. Release handling must still work if the input source loses ownership. Derive in-flight mechanism hints from current bindings; keep a separately labeled keyboard reference truthful.

**Pause-menu trap.** Adding a button to Pause does not make a paused-rejected command usable. Before implementation closes this gap, choose a controller-operated interaction that works under the existing guard, or separately review a staged single intent that executes only after explicit Continue and revalidated guards. Do not automatically resume, weaken aircraft checks or introduce a general queued-command system merely to make a menu appear complete. Brake hold must not replay after Continue.

**Acceptance.** Enumerate capability-present/absent vehicles, running/paused/crashed states, remaps, conflicts and feedback. Reach low-frequency functions through sequential navigation without paddles, pointer emulation or mandatory chords. Verify one accepted intent, release across focus/provider loss, and no deferred arm/restart. Existing camera controls need reachability tests, not duplicate widgets.

## R2-18 — Can desktop keyboards preserve real editor transactions?

**Evidence.** Microsoft's [handheld sample guidance](https://learn.microsoft.com/en-us/samples/microsoft/xbox-gdk-samples/handheldbestpractices/) describes the eligible Windows gamepad keyboard. At sample commit `b1e77b6ac10f95b07296025fda171ca2ddc42dbe`, [VirtualKeyboard](https://github.com/microsoft/Xbox-GDK-Samples/blob/b1e77b6ac10f95b07296025fda171ca2ddc42dbe/Samples/Handheld/Snippets/VirtualKeyboard.cpp) uses CoreInputView; [the alternative](https://github.com/microsoft/Xbox-GDK-Samples/blob/b1e77b6ac10f95b07296025fda171ca2ddc42dbe/Samples/Handheld/Snippets/VirtualKeyboardAlt.cpp) dynamically resolves WinRT interfaces. Neither snippet requires a new GameInput polling subsystem. Its [TextEntry example](https://github.com/microsoft/Xbox-GDK-Samples/blob/b1e77b6ac10f95b07296025fda171ca2ddc42dbe/Samples/Handheld/Snippets/TextEntry.cpp) supplies its own native edit dialog; CoreInputView itself does not return submitted text.

[TryShow](https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.core.coreinputview.tryshow?view=winrt-28000) is a conditional system request. Suitable OS/SDK, COM/thread context, window focus and actual Godot export behavior need a spike. The snippets are examples, not a drop-in Godot bridge. A successful request alone does not prove usable editing, language composition or correct focus.

**Decision.** Bind each editing transaction to an editor, window/screen generation, original text/selection and owning draft/validator. Modal results invoke one owner-approved edit/commit path; floating/system keyboards use normal editing events and must not also apply a second submitted payload. [Workshop numeric fields](../../../app/ui/workshop.gd) commit on `focus_exited`, so keyboard focus transfer needs explicit handling to avoid premature commit. Cancel restores that field's draft, without undoing unrelated document changes; a keyboard dismissal is not acceptance. Invalid input remains visible for correction.

Transform Steam's floating-keyboard avoidance rectangle from Godot control/viewport coordinates into the [window-relative pixel coordinates](https://partner.steamgames.com/doc/api/isteamutils?language=english) it expects. Refresh/hide appropriately on DPI, resize, docking and editor changes. Missing interfaces, declined display or unusable focus falls back while preserving the draft; it does not require adopting the full Microsoft sample or GameInput stack.

**Locale and acceptance.** Distinguish translated UI, free text, constrained numeric/hex input, grapheme editing and composition. Establish a provider/locale matrix, including Chinese and Japanese; unsupported input combinations remain open. Do not declare all maintained locales covered by an English/Spanish keyboard. Test selection, accents, surrogate/composite characters, empty/long names, validation, focus-exit commits, late completion, switching editors and cancellation at native panel/DPI settings. A portable file browser still cannot grant access outside authorized roots. Actual Windows/Steam/portable composition remains untested.

## R2-19 — Where must continuity loss stop command consumption?

**Evidence.** Pinned [main iteration](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/main/main.cpp) can flush events before physics; idle `_process` runs later. Pinned [Input](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/core/input/input.cpp) updates global button/axis state before application dispatch. A gate only in an activity tick misses event-driven commands, and clearing an app queue does not clear the global level cache. The SDL bridge also does not preserve the source timestamp in these Godot events, so time stamped on receipt is not proof of generation after resume.

**Decision.** Close the activity-visible command gate synchronously when a relevant boundary is recognized, before either subsequent event dispatch or physics consumption. A tick already executing may finish; no new gameplay command/simulation step may begin through the closed gate. UI opening may be deferred. Native callbacks must use a thread-safe flag/marshal instead of calling SceneTree from an arbitrary thread. Track the owned source's continuity epoch; a harmless generic-source ambiguity update is not itself continuity loss, while JETI's explicit selection invalidation remains a hold boundary.

Release already delivered virtual/menu holds, discard stale semantic edges and prohibit queued arm, restart or Continue across the boundary. Permit readiness observations without permitting gameplay consumption. Preserve the existing standard-gamepad focused-poll recovery after ordinary focus return: [RcInput](../../../app/input/rc_input.gd) and its [pause-recovery regression](../../../app/tests/test_controller_pause_recovery.gd) allow explicit Continue without moving stationary sticks. That application contract is not proof of physical post-sleep sample generation. For actual suspend/provider discontinuity, require a demonstrated drain/repump/evidence mechanism before making that stronger freshness claim; cached zeros, arrival timestamps and unchanged axes do not prove it. Missing evidence leaves qualification pending, not an implicit new focus-return gesture. Changing the established recovery rule requires activity/input-owner review.

**Reason matters.** Fixed-wing ordinary Pause/focus preserves staged rate throttle through its hold path; actual disconnect resets RcInput to idle and clears staged start. Quad ordinary Pause can preserve its unchanged arm state, whereas focus invalidation revokes it before hold and requires fresh low-throttle OFF→ON recovery. Helicopter collective, airship's paused zero-rate-throttle/low-throttle and yaw checks, and ground neutral readiness stay with their adapters. Preserve crash and other independent session holds during Continue. See [the explicit contract table](../../plans/handheld-controller-acceptance.md#continuity-contract).

**Signals / acceptance.** Evaluate [Windows power notifications](https://learn.microsoft.com/en-us/windows/win32/power/wm-powerbroadcast), available Linux [logind PrepareForSleep](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html), and suspend-aware time as complementary signals; optional Steam callbacks do not cover standalone. The guarantee begins when a boundary is recognized, not before a late callback arrives. Test event-flush/tick/Continue interleavings in all activities, actual sleep separately from process freeze, unavailable signal sources and held controls. No motion timeout or auto-resume.

## R2-20 — What finite evidence is enough to qualify a configuration?

**Evidence.** The [parent controller plan](../../plans/controller-support.md#explicit-gaps-and-acceptance-rules) requires physical device evidence and at least 30 filmed transitions per qualified primary transport. Synthetic F6 software cost, F1 callback arrival and physical F6a video answer different questions. The [existing marker](../../../app/input/latency_patch.gd) reads the connected fixed-wing `session.radio.axes` sample; it measures motion-to-that-marker, not post-conditioned pilot command, servo response or aircraft motion. A pure native Steam endpoint without that RcInput peer is outside its demonstrated scope. At 240 fps the camera frame interval is about 4.17 ms; total uncertainty also includes the threshold, display scanout and event identification.

The [240 Hz / 12-step cap](../../../app/project.godot) permits only 180 physics ticks per wall second at a sustained 15 rendered fps. That arithmetic does not prove an observed performance failure or justify changing the kernel. [Quad](../../../app/input/multirotor_input.gd) polls certain button levels: a down/up entirely between polls can be missed. This is a source-derived case for phase-controlled testing, not a measured handheld defect.

**Decision.** Qualify representative provider/OS/transport routes first and expand by measured risk. Pairwise fault coverage reduces redundant combinations; it never waives the core journey and ten reconnect/ten actual-sleep cycles for each promised configuration. Treat native Linux, native Windows and Proton as distinct. Publish exact model/firmware/mode rows, never a family-wide inference.

Record actual render and physics cadence, display cap/VSync, controller transport and activity-entry history. Compare approximately 15/20/30/60/120 fps where attainable, labeling slow simulation below the catch-up threshold separately. Test brief and held presses across frame/tick phases, generated/delivered/sampled/dispatched counts, accumulation ownership and one integration/shaping owner. Do not queue arming actions to make a short-press test pass.

**Acceptance / limits.** After correctness, retain at least 30 valid video crossings per qualified primary transport within each claimed timing-changing OS/provider route, at fixed settings, with median/nearest-rank p95, exclusions and uncertainty. A baseline run cannot qualify a different provider on the same transport. Native-only actions need an appropriate named flight-consumed marker or another qualified measurement; otherwise their timing row stays pending. Compare against a baseline without an unsupported absolute latency promise. Label every clock and measurement boundary. Keep exact private qualification identities separate from shareable reports. The [acceptance companion](../../plans/handheld-controller-acceptance.md) supplies the finite campaign and release gates. All physical rows remain pending; no equipment inventory, compatibility badge or performance result was established.

## Outcome of the two rounds

All twenty research questions are complete as source-based investigations. The main implementation choices are now explicit: preserve the portable path; prove early optional startup and live association before Steam adoption; review uncertain raw calibration within a session before persistent migration; complete semantic commands and transactional text entry; apply reason-specific event-and-tick continuity gates; and qualify named exports with bounded, correctly labeled evidence.

Open items are implementation or real-environment evidence, not missing research counted as completed tests: bridge binaries and startup, Steam partner configuration, live metadata refresh, actual locale/portal behavior, exposed OEM routes and physical device campaigns. Each has an owner and gate in the plan.
