# Engine, world, and presentation assessment

2026-10-28 · Scope: engine architecture, rendering/performance/latency/stability, and field/weather/lighting/audio. Repository baseline `96287766296b3fef6a37dcd4cc3847d7efbe9f19`; findings are read-only. Web sources were checked 2026-10-28.

## Recommendation

Keep Godot as the product engine for the next development year. Do not plan an Unreal rewrite around visual-feature lists, and do not turn the present simulator into a second-engine project before a measured product requirement asks for that. Godot already has a Compatibility baseline and an opt-in Forward+ path; the real uncertainty is whether the accepted 1080p field workload, pilot readability, input timing, and shutdown behavior qualify on intended hardware.

Retain the float64 `VehicleModel`/`Simulation` boundary and keep optional native evaluator work inside its current contract. That is already a useful portability seam. A fully engine-neutral simulation library remains a possible later investment, but it would require more than wrapping the current GDScript callback contract.

This assessment does not replace the root task’s selected first engineering slice, FL-05 exact-replay debrief markers. That slice uses the existing Godot replay runtime without an engine change. For a later small world slice, SC-18 has a contained wind-cue opportunity described below.

## Current implementation and evidence

### Architecture and renderer

- The production app is Godot 4.8-beta1, pinned to official build `4d10419ca`; 4.7.2 is the current stable line in the official archive. The owner explicitly adopted the beta for development on 2026-10-25; export, target-platform, performance, and release gates remain open. See [STACK](../../STACK.md#runtime), [the upgrade record](../engine-upgrade/GDU-03/README.md), and [the upgrade plan](../../plans/godot-4.8-upgrade.md#status).
- The project defaults to the Compatibility/OpenGL renderer, 1280×720 configured viewport, and 4× 3D MSAA. The configured viewport is historical implementation, not the product target: [1080p first, resolutions above 1080p second, 720p last](../../../AGENTS.md#display-resolution-priorities).
- High is already implemented as a temporary, opt-in Forward+ restart with stronger shadows, SSAO and sky reflections. It uses existing assets; it is an image-quality trial, not an FPS optimization. Standard remains the recoverable baseline. Its known Godot 4.8-beta1 issue is seven Texture RID leaks per independent ReflectionProbe world, plus a renderer warning; packaged restart and non-Windows/GPU qualification are still open. See [High profile and limits](../../../tools/graphics/README.md#experimental-high-profile-forward) and the [trial evidence](../visual-quality-implementation/VQ-07/high-trial-2026-10-21/README.md).
- The flight kernel does not use Godot rigid bodies to solve aircraft motion. Float64 scalar/packed-array state, fixed 240 Hz RK4 ticks, detached render conversion, replay/checkpoint identities and the one-`VehicleModel` contract already separate physics state from rendering. Rendering uses `Vector3`/`Basis` only at the boundary. The core is nevertheless written in GDScript; this is an architectural seam, not an engine-neutral binary today. See [kernel contract](../../STACK.md#boundaries-and-data-flow), [`Simulation`](../../../app/sim/simulation.gd), [`VehicleModel`](../../../app/sim/vehicle_model.gd), and [render conversion](../../../app/render/frames.gd).

### Performance, latency and stability

The best directly relevant full-flight measurement is **historical**, not current qualification: one Windows/NVIDIA RTX 3090 pair on Godot 4.7.2 at actual 1920×1080, 4× MSAA, VSync and a 60-second airborne run. Standard measured p95 17.396 ms and High 18.302 ms. A final-source High rerun measured p95 18.375 ms. The High run misses its existing ≤18 ms p95 gate; one pair and one rerun do not estimate stable performance or qualify 1080p60. GDU-03’s 4.8-beta1 production 1080p captures establish image/path checks, not full-flight cost. [VQ-07 timing and limits](../visual-quality-implementation/VQ-07/high-trial-2026-10-21/README.md#initial-flight-cost) and [GDU-03 scope](../engine-upgrade/GDU-03/README.md) preserve the version boundaries.

The gate is meaningful because a 240 Hz physics tick also has a separate 500 µs budget. That budget is an acceptance target, not a guaranteed maximum; below about 20 rendered frames per second the engine caps catch-up at 12 ticks and simulation slows rather than accumulating unbounded work. Keep render-frame and tick cost claims separate. [STACK limits](../../STACK.md#limits-and-upgrades).

Godot’s custom render interpolation is already paired with `physics_jitter_fix=0`. The recorded dev-VM comparison at 50 fps lowered presented-time RMS error from 0.37–0.50 ms to 0.12–0.20 ms. This is a timing observation, not measured input-to-photon latency or hardware acceptance. Godot documents that interpolation presents a past state and may add input latency; the present 240 Hz tick and custom interpolation already address that tradeoff. The existing latency overlay is a visible patch, not an end-to-end measurement. See [`project.godot`](../../../app/project.godot#L44), [CAM audit](../camera-views/CAM-AUD-2026-10-24/README.md#f7), and [Godot input-lag guidance](https://docs.godotengine.org/en/latest/tutorials/rendering/jitter_stutter.html).

For an engine-neutral current measurement, use the existing [`--frametimes`/`--frame-diagnostics` workflow](../../tools/graphics.md#frame-diagnosis). It records the actual Godot version, effective renderer, drawable viewport, frame percentiles, simulation ticks, render CPU/GPU samples, and engine memory context; use a native display/GPU, not headless or llvmpipe. The separate [session baseline](../../../research/performance/session_baseline.py) still requires Godot 4.7.2 and measures headless session callback CPU only. Do not change its historic version gate or use it to claim current-renderer performance. There is no shared exact-engine-pin identity helper across these tools: the historical session baseline pins 4.7.2, the [grass profiler](../../../tools/grass/profile_session.py) has its own 4.8-beta1 pin, and frame diagnosis records the observed runtime identity without enforcing the product pin. Keep those investigations distinct; add a current-version run when its owning performance gate needs it. The 4.8 beta has passed large, bounded Windows software coverage, but current target-GPU, complete lifecycle, packaging, audio-mix and cross-platform evidence remains open.

### Field, weather, lighting and sound

- Physics weather is intentionally separate from visual time and sky. [`Environment`](../../../app/sim/environment.gd#L1) exposes deterministic position/time wind and atmosphere queries to vehicle sessions. Wind v5 adds an experimental finite spatial field; unsupported terrain/rotor/valley modes remain unavailable and physical/spectral qualification is open. [Wind guide](../../WIND-PLAN.md).
- [`render/atmosphere.gd`](../../../app/render/atmosphere.gd#L33) consumes visual sky configuration separately and can use the deterministic mean wind. The field has a cached windsock cue path: [`field.gd`](../../../app/render/field.gd#L367) observes the accepted wind, and [`main.gd`](../../../app/main.gd#L1123) updates presentation at bounded cadence. `motion.gdshader` has a shared `wind_vec` and `sim_clock`. SC-18 is partial: flag, rotors and foliage motion exist; wind-pump, canopy and grazing-head motion remain open. This already demonstrates that current-engine world work can use the existing presentation seam without altering physics. [SCENERY plan](../../SCENERY-PLAN.md#open-steps-and-acceptance).
- Selectable solar time, fixed night, moon/light cues, and a simulation-tick visual timeline exist; target-GPU cost, pilot night readability, and full progression/checkpoint coverage are open. [Time-of-day guide](../../TIME-OF-DAY-PLAN.md).
- Audio already consumes accepted world/vehicle state read-only. Wind, wildlife and installed engine/contact cues share the mix; the glow generator has a bounded worker and passed five 600 ms main-thread stalls during a 125-second native stress run. That proves the stated stress fixture only. Fleet/source matching, combined headroom, human listening, dedicated mixer timing and target-platform budgets remain open. There is no evidence that changing engines would solve those product gates. [Audio guide](../../AUDIO-PLAN.md) and [stress validation](../audio/AUD-15/validation.md#pump-stress).

## Ambitious 12-month transformations

### 1. One field day whose cues agree

**Problem:** A pilot can select physical wind/atmosphere, visual sky/time and audio layers through distinct contracts, but the resulting world is still assembled from several owners. A rich cloud/flag soundscape can imply more meteorological truth than the wind/atmosphere law actually models.

**Mechanism and experience:** Build a versioned, replayable “field day” preset that composes validated wind/atmosphere with an independently authored light timeline and visual weather projection. The same documented wind sample drives the windsock, vegetation/flag motion, cloud drift and wind audio; only measured/validated physical fields drive aero and propulsion. UI exposes clear practice conditions and their limits, and saved flights retain preset and source identities. Keep art direction editable without silently changing physics. Use existing licensed/reusable assets and sound sources; do not create substitute assets or import data without provenance/license review.

**Risks and acceptance:** Weather imagery can falsely imply a calibrated atmosphere; spatial wind is experimental and its thermal field is kinematic. Keep those claims explicit. Require exact replay identity, identical solver trajectories when presentation is toggled, measured site-data comparison before physical claims, native listening/pilot review, clean lifecycle and current-source 1080p frame/memory budgets. Then test 1440p/4K, with 720p last. This is primarily a data/presentation architecture change, not a renderer migration.

### 2. Bring a local flying site into the simulator

**Problem:** Fixed authored landscapes limit training context and do not give clubs a repeatable digital version of their own runway, pilot station and nearby obstacles.

**Mechanism and experience:** Extend the existing `openrc-field v1`/landscape catalog with a source-pinned import pipeline for a small local airfield. Reuse suitable free public elevation/orthophoto datasets and authoring tools where their licenses allow; produce one canonical field representation that drives visible ground, contacts, obstacles, collision proxies and saved scenario identity. Add a user flow to select a site and enter local weather/time. Do not build a generic open-world engine or duplicate freely downloadable assets.

**Risks and acceptance:** Map/elevation rights, georeferencing, LiDAR/imagery gaps, model scale and collision correctness can make a convincing background unsafe as a training aid. Start with one measured site and independent survey/flightline notes. Validate runway dimensions, tree/building keepouts, contacts and local obstacle geometry against source data; review pilot readability; test loading and paired full-flight frame p95/memory at 1080p, then higher resolution. Keep rendering LOD separate from collision truth.

### 3. Portable flight core with two honest adapters

**Problem:** If OpenRC later needs an Unreal visual front end, a trainer CLI or an independent lab tool, GDScript callbacks and Godot types become the porting boundary.

**Mechanism and experience:** Continue the current one-evaluator native route first. Define an engine-free flat-buffer ABI only after that route is integrated and release-host measurements confirm a product need. Implement a reference adapter and a second host adapter over the same state/layout, wind and checkpoint identities. A trainer or research CLI could run identical `.orfl`/input cases without a renderer; users would gain a verified choice of host, while pilots keep the same behavior.

**Risks and acceptance:** Do not duplicate all vehicle laws or relax simulation transactions. Require byte-identical Linux state and error behavior at every tick, platform-specific tolerance policy, malformed-input coverage, exact source/backend identities, unchanged golden/input tapes, fleet route refusals, Release builds and 1080p renderer-independent parity. Cross-backend recordings remain candidates until exact acceptance is designed. The current NK-3 proof is a solid first evaluator, not proof of a whole-core port.

## Suggested world follow-on and measurement protocol

The root task’s selected FL-05 replay/debrief slice remains the recommended immediate implementation. If work next turns to field realism, the smallest existing SC-18 experiment is to make the **existing club flag’s direction follow a steady crosswind** in [`app/scenery/motion.gdshader`](../../../app/scenery/motion.gdshader#L10). The [prefab mesh](../../../app/scenery/prefabs.gd#L510) extends from the hoist along local +X, and mode 1 currently uses only `length(wind_vec)` to vary flex, so east/west or north/south wind magnitudes look alike. Convert the global render-frame wind direction into the flag model frame, following the local-wind pattern already used for [imported vegetation](../../../app/scenery/imported_tree_wind.gdshaderinc#L76), and rotate the existing cloth around its hoist so its long axis points downwind; preserve the current wave phase/amplitude and use the existing +X orientation when horizontal wind is zero. The flag material is created at [the existing motion-node seam](../../../app/scenery/scenery.gd#L733). Limit the first version to steady uniform wind so gust-direction changes cannot make the flag snap. This changes one existing shader, adds no geometry or downloaded asset, does no per-frame tree walk, and does not touch physics. The wind is a global render cue, not local spatial wind at the flag, so this cannot claim local-flow realism. If the model transform, cloth normal, Compatibility shader, or view makes direction ambiguous, retain the old flex cue and defer the slice.

Measure it in two separate ways. First, use the existing single-capture workflow from [`graphics tools`](../../tools/graphics.md#single-capture) on the target GPU at **1920×1080**, same view/time/build, and capture baseline/candidate with equal-speed orthogonal steady winds (for example `--wind-speed=4 --wind-from=0` and `--wind-speed=4 --wind-from=90`). Check that the flag long axis turns with the downwind vector, the calm fallback preserves the current authored direction, and two repeated captures per condition are identical. This is the directional behavior check. Second, measure cost with the existing `--frametimes=<new.json> --frame-diagnostics` flow on the same target GPU, renderer, field and controlled live airborne launch at 1920×1080, using 10 s warmup and 60 s sample, with three serial baseline/candidate pairs in AB/BA order. Run a nonzero steady wind, such as `--quick-flight --start=airborne_half_power --wind-speed=4 --wind-from=90`; omit `--scripted`, because [`main.gd`](../../../app/main.gd#L271) deliberately returns zero render wind for that fixture. Retain all JSON and logs, reduce each with [`frame_diagnose.py`](../../../research/performance/frame_diagnose.py), and report actual viewport, renderer/driver, VSync/FPS, p50/p95/p99/max, render CPU/GPU, memory, tick count, focus/pause/fault and `complete`. Discard incomplete, paused, faulted or wrong-resolution runs. Also verify the change leaves physics traces/replay identities unchanged. Treat the 16.667 ms 60 Hz budget separately from the ≤18 ms High-profile trial gate; keep High qualification separate because it is experimental. Only after 1080p should this be repeated above 1080p; 720p is last and cannot qualify either higher target.
