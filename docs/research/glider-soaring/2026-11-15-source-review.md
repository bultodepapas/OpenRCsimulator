The governing [root instructions][agents], [simulation instructions][sim-agents], [physics instructions][physics-agents], [stack boundary][stack], [aircraft contract][contract], [ownership registry][owners], [tool index][tools], and [consolidated audit][audit] were read.

## Current entry points and limits

- Home chooses a fixed-wing start and passes it into the flight route ([`app_root.gd` L1318–1353][root-start]); the session prepares an aircraft, installs one `VehicleModel`, and configures callbacks ([`flight_session.gd` L2363–2443][session-model]). Its `_physics_process` samples the live controller/keyboard, creates `sim.inputs`, and checks the session before the kernel child steps ([L3070–3148][session-sample]); `_inputs` supplies four standard roles plus conditional gear/brake/flap inputs ([L4262–4271][inputs]). This is a useful input seam but it does not implement control ownership transfer between aircraft.
- A session has explicit airborne, runway, half-power and hand-launch choices. `_reset_airborne_candidate` stages initial body, sampled auxiliaries, weather and continuous states then commits the reset transaction ([L3846–3907][airborne-reset]). The ordinary powered reference or requested throttle-level trim is solved during preparation; `selected_trim_throttle` rejects targets at or below zero for the throttle-driven trim path ([L1004–1044][trim-selection]). A glider needs its own trim/admission semantics and must not assume the level-powered solve can trim a descending, zero-thrust aircraft.
- The existing [`trimmed_glide_across_view`][glide-trim] calls `Trim.solve("glide", ...)`; `FlightSession` exposes a scriptable power-off retrim ([L2932–2947][session-glide]) and [`test_trim.gd`][trim-test] exercises a stopped-engine Stik. These establish power-off glide machinery for an admitted powered aircraft, not an admitted propulsion-free airframe or product sailplane.
- Existing X8 hand launch is a specific powered helper throw. Gearlessness is the offering test, and a runway is used to place and aim the release ([L921–980][hand-support]). It initializes at **1.9 m**, **6.5 m/s ground-relative**, **5° climb** and **full throttle**, then solves a running-motor release RPM and uses the airborne reset transaction ([constants][hand-constants], [release][hand-release]). [`test_hand_launch.gd`][hand-test] contains assertions for location, wind-relative resulting airspeed, replayable restart and a motor-stopped negative control. Do not reuse its values, runway dependency, full-throttle or climb success as a universal glider launch rule; calculate feasible release states against each admitted glider and winds. An in-air glider start should explicitly initialize still-air descent/equilibrium and add local wind to derive ground motion, using a separately validated source-specific airspeed/altitude, and allow fail-closed behavior when no safe start can be established.

## Unpowered aircraft admission

The v2 compiler first validates the shared contract and capability registry, then derives the runtime model ([`aircraft_data.gd` L210–233][data-admission]). `AircraftModules.classify` requires `propulsion` to be an object with a registered selector ([L92–103][modules-selector]). The [registry][modules-registry] has required propulsion-layout and energy capability fields; its propulsion families are `glow_prop`, `electric_prop`, and `turbine`, with no unpowered family or no-propulsion layout. Independently, `_propulsion` rejects a missing block and unrecognized kinds; the legacy glow path requires actual motor/propeller parameters ([L1215–1247][data-propulsion]). Current data therefore rejects a truly propulsion-free v2 aircraft, even though a powered airframe can be flown engine-off.

An explicit unpowered family/layout with clear distinction between propulsion energy and a receiver/servo battery is a **proposal**, not current support. It needs AS-owned registry, schema/contract, loader/derived model and generator/compiler updates; reject contradictory power fields; route through load/trim/continuous-state, crash/contact, audio, rendering, catalog/Workshop, telemetry, native fallback, identity and logging consumers without fabricated zero-thrust motors or dangling prop references. Inventory all actual consumers before deciding exactly which updates are required. Existing AS admission tests reject unknown or contradictory families; extend them to test both valid unpowered and negative cases rather than weaken them.

## Whether a single coupled `VehicleModel` is feasible

**Feasible as a new reference implementation; not supplied today and not automatically compatible with stock `FlightSession`.** One model owns one kernel transaction. The primary rigid body is 13 float64 values; an additional complete 13-value secondary body and each airframe's continuous subsystems can be laid out in the model's declared continuous tail. An opt-in `framed-sampled-v1` model samples both controller commands, owner/release modes and controller memory from one detached accepted frame per tick and keeps that sample fixed through all RK trials. Its joint `stage_sampled` sees primary body and tail at the same trial time and can compute a cable force from both trial poses, equal and opposite loads and moments at their attachments. It supplies primary body loads or a qualified `body_derivative`, and the complete secondary rigid-body derivative (with its own mass, inertia, gravity, actuator and propulsion states) in the continuous derivative. The kernel commits the resulting frame atomically and restores it on failed stages. Sources: [`vehicle_model.gd` L1–10, L38–46 and L97–115][vehicle-model], [`simulation.gd` L403–490][sim-stage] and [L634–647][sim-commit]. Rigid-body state is world NED position, body FRD velocity/rates and body-to-NED quaternion ([`rigid_body.gd` L1–6][rigid-frames]); cable velocity, force and attachment moment require deliberate transforms at each trial stage.

The existing `FlightSession` configures session-bound callbacks and mutable helpers ([L2398–2443][session-model]); do not simply call two independent `Simulation.step()` methods and assert stage-level coupling, or assume all legacy fixed-wing callbacks are pure/reusable with a framed model. A composite adapter needs explicit pure evaluation contexts or carefully extracted and qualified laws, per-body model/data identities and separate mass/inertia, actuator, controller and environmental state. Native acceleration for this layout is unproven: prefer reference backend and explicit unsupported/fallback admission until separately qualified. A shared deterministic weather provider must answer both positions at each stage time and carry the physical world's seed/epoch correctly; the current companion allocation uses separate session OU seeds, not one coupled spatial world.

### Concrete contract gaps and design choices

1. **Second orientation.** RK's `_finish_step` and `normalize_attitude` normalize only the primary quaternion ([`integrator.gd` L38–49][integrator]). Kernel `_stage_state_is_valid` validates the primary body and only checks the tail for finiteness ([`simulation.gd` L1089–1113][stage-validation]); `state_validator` checks reset/restore/endpoints, not every trial state. A composite must validate the secondary body at all relevant trial evaluations and normalize it at accepted boundaries, including any internal substeps or located events. `endpoint_transition` can return a corrected whole candidate frame ([`simulation.gd` L577–609][endpoint]); endpoint-only normalization is insufficient if the chosen policy needs normalized intermediate accepted substep states. A generic, registered secondary-body projection/validation extension under SF is an option; alternatively a composite-owned policy must explicitly and correctly supply these operations. The correct boundary is an engineering decision and a testable prerequisite, not an existing guarantee.
2. **Two contacts and events.** The old `post_tick` and `post_tick_joint` filters return only a primary body; they cannot themselves update the second body ([`vehicle_model.gd` L60–65][vehicle-model], [`simulation.gd` L555–574][post-tick]). Whole-frame endpoint transitions can update both, but existing individual contact policies are not automatically composable. Only one kernel-declared event is allowed; multiple events require a model-owned whole-tick `step_policy` ([`vehicle_model.gd` L68–90][vehicle-model]); the kernel refuses a tick when that policy and requested contact substeps exceed one ([`simulation.gd` L493–522][sim-events]). A composite policy would have to own any needed internal subdivisions, guard the applicable domains and locate/order simultaneous cable release, both ground contacts, propulsion and failure events. Do not silently suppress substep requirements. Until supported composition is explicitly qualified, admission should refuse ambiguous overlapping events/domains without advancing either aircraft. For ordinary ground towing, choose and qualify an SF-owned generic multi-body layout/projection/event extension or a demonstrably equivalent vehicle-agnostic policy; preserve the kernel's no-vehicle-specific-branch rule. The exact extension is not proven necessary for a bounded airborne prototype. Before any product airborne tow, qualify or explicitly refuse intersections among line, propulsion, energy and failure events; ground contact adds further intersections.
3. **Publication and history.** `Simulation.stepped` and `interpolated` expose the native primary body; the secondary lives in the continuous block ([`simulation.gd` L19–23 and L650–680][publication]). A paired presentation facade needs accepted previous/current secondary poses, interpolation, reset/restore generation handling and two views/camera targets. That presentation history must never become hidden solver state. Logging currently targets a fixed-wing session with a 13-state primary layout and fixed-wing telemetry ([`flight_log.gd` L90–104 and L211–228][flight-log]); recording a tail array alone does not prove interpretable tow telemetry or exact two-aircraft replay.
4. **Atomic control and restore.** Pin layout, protocol and both model/data/law identities. Keep cable attached/slack/released mode, pilot-owner IDs, both AI controller memories, their last sampled commands, pending release, weather RNG/epoch and all needed input-mix ownership in checkpointed frame/envelope; sample changes on declared tick boundaries and make release independent of handoff. `Simulation` has frame reset/checkpoint validation, protocol pin and atomic restore ([L209–299][frame-reset], [L894–983][sim-checkpoint]); a new pair session still must prove complete identity, restore, record and replay of both actors and ownership. Route either one pilot to the tug with a controlled glider or to the glider with a controlled tug, with deterministic ownership switches. Choose and validate any assistance, arming, neutral/safe command and disconnect behavior explicitly; none exists merely because the current UI supports radio inputs.

### Staged recommendation

1. Separately admit a pure glider and demonstrate repeatable unpowered flight, hand release and in-air starts first. The existing power-off trim is a starting seam, not a calibrated sailplane model.
2. Build a **reference-only, contact-disabled, airborne composite proof**, with one primary rigid body and one qualified body in the continuous block. Begin with a simple massless cable inside an admitted stiffness, load and separation envelope, without peak-force clipping; no rigid inextensible constraint or dynamic rope is implied. Start without event intersections, assert no force under slack, equal/opposite world forces, attachment moments, stable outcomes under fixed-step refinement, and atomic refusal/rollback. Keep both actors above terrain and reject unsupported cable/contact/energy states. Document and test exactly when the secondary quaternion is projected. This establishes feasibility, not product-ready ground towing or physical validity.
3. Decide the SF generic layout/projection and policy/event-composition interfaces based on the proof, then qualify joint ground motion and multi-contact/event crossings before enabling takeoff. Release, brake/crash, cable overload, disconnection and recovery need defined semantics and no invented ordering. Design manual-tug/AI-glider, switch to manual-glider/AI-tug and AI-tug/manual-glider as ownership variants of the same coupled world and tick, not as two separately stepped sessions exchanging last-tick forces. The target EG4 manufacturer configuration, mass/CG/polar and tow fitting remain source/measurement questions; the FunCub proposed tug and a development Ugly Stik surrogate each need an explicit admitted tow installation and data, never an invented stock hook.

## Existing AI companions are not tow physics

Each agent constructs an independent `FlightSession`, is externally driven, and is spawned airborne ([`agent.gd` L35–89][agent-setup]). Manager snapshots before the player tick, then after the player commits it prepares all agents and advances each separately ([`manager.gd` L139–140, L167–217][manager-tick]); its observation/control code is useful reference for a bounded AI task, but does not create mutual stage forces or one joint rollback. Runtime admission is Club field, reference atmosphere and bounded gentle wind; spatial weather is refused ([`manager.gd` L46–65][manager-admission]). The [current guide][companion-limits] states 1–3 Ugly Stik airborne circuits, no inter-aircraft contact forces, no fleet checkpoint/decision replay/shared world replay; takeoff/landing remain research. [`fleet_record.gd`][fleet-record] explicitly calls its per-session logs a diagnostic manifest rather than a fleet checkpoint. Reusing it for a physically attached tow without new architecture would misstate capabilities.

## Owners, regression seams, and evidence

Owners from the [track registry][owners]: SF owns kernel/contract and framed protocol; main physics owns sessions/aerodynamics/trim, GP ground/contact, AS aircraft schema/topology, aircraft-specific owners source generators and asset identity, M5 wind/atmosphere, AFC AI behaviors, D6 input/controller, UI shell/HUD and presentation, FL recording/replay, FT flight-test, CR crash/damage, LU/SC landscape and contact, and NK native numerics. Coordinate each shared seam rather than assigning its files to a new plan wholesale. A new plan namespace should be checked against the registry before use.

Relevant **existing** checks to extend or run once an implementation exists:

- [`test_sf_vehicle_model.gd`][test-sf-model], [`test_sf_framed_sampled.gd`][test-framed] (one sample/held stages, purity, rollback, staged reset, layout/protocol checkpoint), [`test_sf_event_protocol.gd`][test-events], [`test_sf_event_refinement.gd`][test-event-refinement] and [`test_sf_contact_substeps.gd`][test-substeps] (event timing/refusal, substep refinement/contact). None currently proves two-body tow.
- [`test_aircraft_contract.gd`][test-contract], [`test_aircraft_modules.gd`][test-modules], [`test_trim.gd`][trim-test], [`test_hand_launch.gd`][hand-test], [`test_flight_session_staged.gd`][test-session], `test_checkpoint.gd`, `test_checkpoint_integrity.gd`, `test_runway_checkpoint_metadata.gd`, `test_replay_integrity.gd`, `test_flight_log_inputs.gd` and `test_golden.gd` cover the corresponding existing single-aircraft boundaries; add explicit paired, ownership and zero-propulsion cases rather than infer support.
- Existing AFC `test_companions_session.gd`, `test_companions_restore.gd`, `test_companions_record.gd`, `test_companions_lifecycle.gd`, `test_companions_external_rejection.gd` and related airspace/pilot/weather tests provide lifecycle regressions, not tow validation. Use the wind track's own thermal, stage-time and spatial-weather tests and accepted-domain policy.
- The [physics verification guide][physics-tools] calls for focused checked Godot scripts, `test_golden.gd` for kernel/session impacts, flight-test battery for response changes, and preserved baseline `.orfl` with exact replay before same-tape candidate comparisons. Enrolled hosts use the test queue and session handle. Keep numerical/regression evidence, physical measurements, native backend equivalence, real-controller and rendered 1080p acceptance distinct. Audit A23 asks for an independent constant-mass energy-height ledger and separates temporal wind, path shear and vertical-air terms; A25 records bounded component studies, not whole-flight proof ([audit wind section][audit-wind]). Current M5 plan explicitly places convincing thermal soaring behind unresolved validation and thermal-boundary work ([M5 roadmap L66–83][wind-roadmap]).

## Current weather inspected for this plan

The lead also inspected the current [preset source](https://github.com/bultodepapas/OpenRCsimulator/blob/ad21070798bfb9658785576a9c0b8bfc9a71fc7f/app/physics/wind_spatial_presets.gd), [spatial admission](https://github.com/bultodepapas/OpenRCsimulator/blob/ad21070798bfb9658785576a9c0b8bfc9a71fc7f/app/physics/wind_spatial_config.gd), [thermal law](https://github.com/bultodepapas/OpenRCsimulator/blob/ad21070798bfb9658785576a9c0b8bfc9a71fc7f/app/physics/wind_thermal_field.gd), [weather wrapper](https://github.com/bultodepapas/OpenRCsimulator/blob/ad21070798bfb9658785576a9c0b8bfc9a71fc7f/app/physics/wind_field.gd), [finite-wing polar](https://github.com/bultodepapas/OpenRCsimulator/blob/ad21070798bfb9658785576a9c0b8bfc9a71fc7f/app/physics/wing_polar.gd), and [current wind reference](https://github.com/bultodepapas/OpenRCsimulator/blob/ad21070798bfb9658785576a9c0b8bfc9a71fc7f/docs/WIND-ATMOSPHERE-REFERENCE.md).

The existing thermal preset is one finite cell: birth 15 s, life 360 s, initial center [220,−120] m, radius 35 m, top 200 m and peak 1.2 m/s. No automatic replenishment is implemented in that preset. The spatial provider explicitly labels ridge lift, terrain rotor and valley channeling unavailable.

Current thermal admission restricts the cell list, overlap, support, lifetime, radius, peak, datum, epoch and horizon. The law samples at world position/time and is a prescribed circulation with surrounding sink. At the center its vertical multiplier is sin²(πh/H) times the finite lifecycle envelope; that directly explains why low hand-toss height receives little lift from a tall cell. This is a source-derived inference, not a flown observation or a newly reproduced defect. The [aircraft/weather dossier](../../plans/glider-soaring/03-aircraft-and-weather.md) derives concrete proposed recipes within the documented bounds; complete schema admission and flight qualification remain pending.

A versioned scenario must store the full field, not only its seed. Translate desired initial cell centers into birth centers using the selected epoch offset; otherwise a drifting cell will start in the wrong place. Keep terrain height and the flat weather datum distinct, and include every aerodynamic station in domain admission.

## Synthesis, review, and evidence limits

The team recommended a pure-glider capability before towing, a configuration-specific trainer, the existing shared spatial weather, and a coupled two-body transaction. The manual-tug journey includes an AI-controlled glider before transfer and an AI-controlled tug afterward; both bodies remain in the same pair transaction until an explicit end transition. These are proposed design decisions.

Independent review checked the draft against the current source and challenged:

- Both-body projection and event composition during airborne as well as ground tow.
- Primary controls, AUX pickup and controller memory at ownership transfer.
- Which installed hook a release command is authorized to operate.
- Aircraft-to-aircraft collision/exclusion scope distinct from terrain contact.
- Receiver/servo supply with absent propulsion.
- Application tick configuration versus kernel refinement capability.
- Symmetric-aileron braking support versus the existing opposite-roll mapping.
- Fixed-CG hook equations versus finite-fuel datum and efflux conventions.
- World-epoch weather horizon versus remaining simulation time.
- Exact primary-body and continuous-tail callback packing.
- Experimental software milestones versus physically qualified named-aircraft claims.

Those corrections are integrated into the [master plan](../../plans/glider-soaring.md), [launch/control guide](../../plans/glider-soaring/01-launch-and-control.md), [physics](../../plans/glider-soaring/02-physics-and-tow.md), [aircraft/weather](../../plans/glider-soaring/03-aircraft-and-weather.md), and [acceptance](../../plans/glider-soaring/04-acceptance-and-delivery.md).

Validation for this planning change consists of document structure, cross-references, requirement coverage, arithmetic examples and the final GitHub diff. No application build, simulator run, physical measurement, real-controller session, rendered target-host test or native-backend qualification was executed. No old test count or historical CI status is represented as current evidence. Proposed test matrices and numerical/physical gates remain work for the implementation team.
