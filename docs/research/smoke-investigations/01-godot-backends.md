# Investigación 01 — Partículas en Godot Compatibility: qué API soporta el proyecto

**Pregunta.** En Godot 4.7.2-stable, ¿puede el renderer Compatibility ofrecer una estela GPU con suficiente control para escape tenue y bomba AUX? ¿Conviene usar `GPUParticles3D`, `CPUParticles3D` o las funciones de bajo nivel de `RenderingServer`?

**Base revisada.** El proyecto fija Godot 4.7.2-stable y selecciona `gl_compatibility` en `app/project.godot`; `.tools/Godot_v4.7.2-stable_linux.x86_64` es el binario instalado por `app/get-godot.sh`. Revisé la documentación 4.7 y el código oficial del tag `4.7.2-stable`, así que las afirmaciones se refieren al backend usado aquí, no a una combinación genérica de “Godot 4”. El repositorio del motor está bajo MIT y no hace falta añadir plugin ni librería externa.

**Hallazgos.** `GPUParticles3D` y `ParticleProcessMaterial` sí tienen implementación en Compatibility. El backend GLES3 de esa versión procesa el estado de partículas con transform feedback y presenta las instancias; por tanto, “GPU” no significa que dependa exclusivamente de compute/Vulkan. La documentación recomienda una malla en `draw_pass_1` y un material de proceso, mientras cada partícula se dibuja como una instancia. Para nuestra nube, una `QuadMesh` con una sola pasada por emisor es una ruta sencilla con coste acotable. [API de GPUParticles3D, Godot 4.7](https://docs.godotengine.org/en/4.7/classes/class_gpuparticles3d.html), [guía de creación 3D](https://docs.godotengine.org/en/4.7/tutorials/3d/particles/creating_a_3d_particle_system.html), [implementación GLES3 4.7.2](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/storage/particles_storage.cpp).

Las limitaciones que afectan este plan son concretas: Compatibility avisa que no admite trails de partículas, subemitters ni `emit_particle()` manual. La colisión SDF 3D de partículas tampoco está disponible en este backend. El efecto de humo no necesita colisiones, secundarios ni ribbon: debe construirse con quads persistentes en coordenadas globales. El aviso de `emit_particle()` importa: una idea de generar cada punto del recorrido desde GDScript con esa función no es compatible con el renderer fijado. [Fuente GLES3 fijada: trails, subemitters y emisión manual](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/storage/particles_storage.cpp), [colisiones Compatibility](https://docs.godotengine.org/en/4.7/tutorials/3d/particles/collision.html).

`CPUParticles3D` simula en CPU y dibuja mediante GPU/MultiMesh; no es el mismo sistema con otro toggle. La conversión oficial documenta pérdida de funciones y diferencias visuales. Puede ser una reserva para un controlador que falle en una GPU concreta, pero no resuelve automáticamente el reloj de captura o el historial del emisor y hace que el coste escale con las partículas en CPU. [API CPUParticles3D](https://docs.godotengine.org/en/4.7/classes/class_cpuparticles3d.html), [diferencias de conversión](https://docs.godotengine.org/en/4.7/tutorials/3d/particles/creating_a_3d_particle_system.html).

**Decisión.** Adoptar la API de alto nivel `GPUParticles3D` + `ParticleProcessMaterial` + una `QuadMesh` por sistema. Reservar `RenderingServer.particles_request_process()` para el caso manual-clock/culling descrito en la investigación 02; evitar administrar buffers o crear el sistema entero a mano. Condicionar cualquier shader de proceso personalizado a una prueba bajo `--rendering-driver opengl3`. Descartar CPU como perfil principal y `trail_enabled`, `emit_particle` y subemitters como soluciones de producto para este renderer.

**Cambios concretos al plan y prueba requerida.** En SM-00, registrar en el manifiesto backend/versión, mostrar dos nodos GPU simples y comprobar que quads translúcidos se dibujan y se limpian sin errores en Compatibility. Mantener el objetivo de un pase por emisor y excluir colisiones/trails del alcance. Para decidir el eventual shader de continuidad, probar la variante mínima en la misma ruta GLES3 antes de incorporarla. La compatibilidad del motor está documentada y localizada en código, pero no se ha medido el rendimiento del humo en equipos de usuario; dos sistemas GPU no garantizan buen frame-time en toda iGPU.

**Herramientas y repositorios.** Godot Engine `4.7.2-stable` (tag fijado, licencia MIT), documentación oficial 4.7 y el backend `drivers/gles3/storage/particles_storage.cpp`. No se recomienda instalar addon de terceros para este efecto.
