# Investigación 02 — Reloj manual, pausas, semilla y cámara

**Pregunta.** ¿Se puede congelar GPUParticles3D y avanzar humo en sincronía con la simulación de 240 Hz, con pausa/reinicio reproducibles, si el emisor sale de cámara o una captura no presenta cada tick?

**Fuentes y base local.** Se contrastaron la API oficial Godot 4.7 de [`GPUParticles3D`](https://docs.godotengine.org/en/4.7/classes/class_gpuparticles3d.html) y [`RenderingServer`](https://docs.godotengine.org/en/4.7/classes/class_renderingserver.html) con `scene/3d/gpu_particles_3d.cpp`, `drivers/gles3/storage/particles_storage.cpp` y `servers/rendering/renderer_scene_cull.cpp` del tag [4.7.2-stable](https://github.com/godotengine/godot/tree/4.7.2-stable). En este repo, `app/main.gd::_capture()` adelanta la física en un bucle y dibuja una sola pose final; `app/capture.sh` produce imágenes con Godot 4.7.2. No ejecuté humo dentro de `app/`.

**Hallazgos.** La vía manual existe en ambos nodos: `speed_scale = 0` congela el avance automático y `request_particles_process(process_time, process_time_residual)` solicita segundos de simulación en un render frame. El primer parámetro avanza con emisión activa; el residual avanza con emisión apagada. Para una transición ON→OFF dentro del intervalo, separar esos dos tiempos conserva el corte mejor que actualizar solo `emitting`. No codifican una secuencia arbitraria OFF→ON→OFF: el harness necesita presentar cada tramo en orden, y la política de vuelo para varias transiciones entre frames debe resolverse en SM-00. En el C++ GLES3 las solicitudes se guardan asignando dos campos; la siguiente llamada los reemplaza, no los suma. El controlador debe acumular duración cuando consume varios ticks físicos por dibujo y mandar una solicitud una vez por frame de render.

La llamada `request_particles_process()` en el nodo no encola por sí sola el RID en la lista de procesamiento. El renderer común agrega partículas a esa lista durante culling cuando el `INSTANCE_PARTICLES` resulta visible. El motor expone el método complementario `RenderingServer.particles_request_process(RID)`, que sí pide actualizar ese sistema en el siguiente frame/culling. Godot crea el RID interno de partículas en `GPUParticles3D` y lo instala como `VisualInstance3D` base (`set_base(particles)`); por eso la ruta respaldada por API es `RenderingServer.particles_request_process(emitter.get_base())`, no `get_instance()`. La documentación de `get_base()` confirma que devuelve el RID del recurso base. Esta llamada evita depender del culling de cámara para encolar, pero sigue necesitando un frame del renderer para consumir el trabajo. [API de cola](https://docs.godotengine.org/en/4.7/classes/class_renderingserver.html#class-renderingserver-method-particles-request-process), [RID de recurso vs. instancia](https://docs.godotengine.org/en/4.7/classes/class_visualinstance3d.html), [constructor de GPUParticles3D](https://github.com/godotengine/godot/blob/4.7.2-stable/scene/3d/gpu_particles_3d.cpp), [culling visible](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/renderer_scene_cull.cpp).

La semilla requiere `use_fixed_seed = true`; `seed` por sí sola no fija la aleatoriedad. `restart(true)` limpia y conserva la semilla para una comparación repetida; un reset de vuelo debe ordenar reinicio explícito, no saltar el reloj de partículas sobre una pose final. El loop GLES3 procesa una duración solicitada en pasos de `1/fixed_fps` (o pasos de 1/30 s si se usa cero), por lo que una solicitud larga puede lanzar muchas iteraciones GPU en un frame. El `inactive` que ya no tiene emisión ni partículas vivas se omite, lo cual es correcto; hay que verificar reinicio/reactivación con emisión en una llamada nueva. [API de semilla y restart](https://docs.godotengine.org/en/4.7/classes/class_gpuparticles3d.html#class-gpuparticles3d-method-restart), [bucle de procesamiento 4.7.2](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/storage/particles_storage.cpp).

**Recomendación.** Adoptar un único `SmokeClock` visual que consume tiempo presentado por frame y opera cada emisor así: actualizar anclaje/transform, configurar `request_particles_process(emitting_dt, residual_dt)` con `speed_scale=0`, y llamar `RenderingServer.particles_request_process(emitter.get_base())`. En pausa voluntaria, pérdida de foco o reset, no dejar delta acumulado. `visibility_aabb` debe cubrir el volumen previsto de la estela para que vuelva a dibujarse en cámara. La cola manual permite procesar fuera de culling; no evita el culling de dibujo ni da poses históricas. Como el RID pertenece a una API de servidor, validar `get_base()` y el orden de operaciones en SM-00 antes de fijar este contrato.

**Cambios concretos y prueba.** SM-00 necesita cuatro casos: 0.5 s emitiendo y luego residual; pausa 2 s sin cambio de edad; reset dos veces con semilla fija y mismo PNG en la misma máquina; emisor fuera de cámara 1 s y vuelta, comprobando envejecimiento y AABB. El harness de humo debe renderizar pose y avanzar un intervalo a la vez; `main.gd::_capture()` actual no conserva poses intermedias y no sirve para capturar el rastro histórico como está. La igualdad entre GPUs/plataformas no se afirma.

**Herramientas/repositorio.** API pública de nodos/servidor y código fuente oficial Godot 4.7.2-stable, licencia MIT. No se propone plugin. El uso de la llamada de cola aún es recomendación de código; falta una captura mínima en Compatibility.
