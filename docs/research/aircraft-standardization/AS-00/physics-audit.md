# AS-00: Aircraft physics and model audit

**Status:** completed audit; findings are inputs to AS-02 migration.  
**Scope:** four catalog aircraft JSON files, their geometry/model pipelines, physics-data loader and current propulsion/controls/gear paths. Read-only review; no aircraft model, physics or generator changes are made by this report.

This is the pre-implementation audit snapshot. The subsequently arriving GP wheel-profile/terrain extension is recorded in the [current contract supplement](../AS-01/module-semantics.md#concurrent-ground-profile-interface); statements about absent wheel dynamics below describe the audited baseline. AS did not introduce that ground-law change.

## Findings at a glance

The four production aircraft express positions in a common leading-edge datum and convert to body FRD about the computed CG. Their different visual origins and physical configurations are deliberate. Their mass properties, aerodynamic estimates, and contact/crash shapes are model-specific, not values that should be forced to match. The main standardization defects are inconsistent/implicit fields and conventions that are descriptive text rather than enforced identifiers, not evidence that the four models share one physical configuration.

All four v1 files have a virtual mass inventory balanced to a plan or sourced target CG. The current loader derives mass, CG and the six entries of a symmetric inertia tensor from that inventory, using axis-aligned component boxes plus the parallel-axis theorem. The rigid-body integrator consumes the full tensor, including products of inertia. These outputs are calculations from a virtual point-mass/box model, not measured aircraft mass properties. The comparison to the shared inertia reference is only a soft plausibility warning: the baseline Ugly Stik Iyy ratio is about 2.11 against that scaled reference, just over its 2.0 warning threshold, and it still loads. The warning should be treated as a prompt to inspect the estimate, not a migration failure.

No physical inertia measurement is claimed. ## Frames, CG and inertia

All v1 JSONs state a physics `le_frame` position as `[x_aft, y_right, z_up]` in metres from a local wing leading-edge datum. They convert to body FRD about the computed CG as `x_forward = -x_aft`, `y_right = y_right`, `z_down = -z_up`. Visual model axes are generally `+X` right, `+Y` up and `+Z` aft, mapped to this physics frame by `[visual.z, visual.x, visual.y]`. The models do not share a visual origin: the Ugly Stik assembly origin is near quarter-chord; Extra uses its nominal CG station; P-51 geometry uses root-wing LE at centreline; Avanti projects root LE beside fuselage onto the symmetry plane. Those are valid source-datum differences when the geometry compiler and physics datum transform agree.

`balance.configuration = virtual-balanced-reference-v1` identifies the current mass inventory as a bookkeeping balance to a manual/plan target, not a physical assembly or ballast prescription. The loader recentres a six-entry symmetric tensor calculation at inventory CG; its point masses and rectangular boxes provide estimated products of inertia as well as diagonal moments. NASA's small-UAV mass-property work explains that products of inertia can remain nonzero in body axes even when aircraft symmetry makes the other two products zero, and describes experimental bifilar-pendulum estimation. See [NASA Armstrong / AIAA, Determining Products of Inertia for Small Scale UAVs](https://ntrs.nasa.gov/api/citations/20170000461/downloads/20170000461.pdf), especially the body-versus-principal-axis discussion and PRANDTL-D test method. The relevant future improvement is measured mass-property evidence for a declared assembly state; the runtime already accepts and uses the full symmetric tensor.

Each model's reference point, CG, inertia, contact positions and hull points differ because each uses a different aircraft, datum, virtual inventory and configuration. Preserve these model-specific quantities. `reference.mean_chord` is the coefficient normalization length, not the geometric MAC on tapered Extra, P-51 or Avanti wings; changing it alters moments. For Avanti, the checked-in serialized value is 0.351137 m, while the current polyline geometry's unrounded `S/b` used in coefficient derivation is 0.35113750000000005 m. The 0.0000005 m serialization difference is retained for exact output parity; it is not a measured chord, physical retune or geometric MAC. `reference.planform` is rectangular for the Stik and tapered for the other three; Avanti uses an equivalent trapezoid for some checks despite a more complex reconstructed outline.

The three derivation scripts duplicate inventory/inertia assembly and consistency checks. Their aero methods remain model-specific textbook estimates, not flight identification. A migration helper should change structural representation only, and generators should pass final output through that helper. Generators that copy Stik data should consume a clean legacy-compatible view or explicitly replace inherited model-specific metadata before v2 upgrade; otherwise capability claims, contact defaults or relocated coefficient metadata can leak into derived aircraft.

## Physics and configuration comparison

**Aerodynamics and controls.** All aircraft carry the same free-text control sign convention: angles/rates in radians; elevator trailing edge down with negative `dCm/dElev`; surface aileron deflection positive trailing edge down; rudder positive trailing edge left; force coefficients in wind axes and moments in body axes about the aerodynamic reference point. Runtime converts pilot surface signs in one helper, but the JSON convention text is not parsed or enforced. A stable convention ID is therefore a useful schema contract. All configs provide aileron/elevator/rudder; flaps are not simulated, even where the visual model has physical flap geometry. The Ugly Stik derivatives borrow from OpenFlightSim UltraStick25e; its stall limit and some cross/rate terms are estimates. Extra, P-51 and Avanti use geometry-based analytical estimates and likewise are not flight-identified. Per-strip stall/incidence fields and surface geometry differ by airframe and must remain distinct. `CLadot` is currently inside the general coefficient map but is not consumed by the runtime; moving the same quantity and evidence under `aero.reference_coefficients` documents its inert/reference role without changing outputs.

**Propulsion and energy.** The Stik and Extra have single O.S. .61-class glow piston engines with 12×6 tractor props. P-51 describes a DLE/DA 120 cc gasoline class engine and a four-blade tractor prop but uses the same generic `glow_prop` branch; that branch is RPM/throttle plus Ct/Cp propeller tables, not a separate gasoline/fuel model. The O.S. MAX-61FX page is a manufacturer equipment anchor for the Stik/Extra glow engine only, not for the P-51 gasoline engine or installed aircraft thrust: [O.S. MAX-61FX catalog](https://www.os-engines.co.jp/english/line_up/engine/air/aircraft/catalog/17750.htm).

The session has a discrete `engine_running` mode. Normal trimmed starts run, a power-off glide start is stopped, runway start runs, and the mode participates in reset/checkpoint state; session code gates the active propulsion source on it. This is an engine on/off state, not a complete hardware start/stop model. For glow/piston propulsion the running shaft follows either the RPM lag or optional shaft-torque balance; off mode removes combustion-produced drive immediately. For a turbine, the running state selects ECU-mapped spool/thrust behavior, while switching off does not model a turbine spool-down, ignition or restart sequence; `fuel_flow` remains telemetry/endurance data and does not decrease simulated mass. Flameout, EGT and turbine start-up sequencing are not modeled. JetCat's current P100-RX-BL page publishes manufacturer anchors such as 100 N max thrust, 44k/154k rpm, 0.23 kg/s mass flow and separately lists 390 ml/min full-load fuel consumption; this supports component-class plausibility only, because the aircraft JSON cites a 2017 non-BL P100-RX and its response curves are separately sourced: [JetCat P100-RX-BL specifications](https://www.jetcat.de/en/productdetails/produkte/jetcat/produkte/RC%20ENGINES/Engines/p100_rx-bl).

The direct-drive electric-prop branch exists in the loader and synthetic fixtures, with equivalent motor parameters, an ideal-motoring ESC, and `fixed_voltage` or `ocv_resistance` battery modes. It has no catalog aircraft and is prototype/code-supported, not production-validated. The UIUC Propeller Database provides measured low-Reynolds-number model/UAV propeller performance and standard `C_T`/`C_P` conventions, a useful source for future data rather than proof that current synthetic tables are physical: [UIUC Propeller Database](https://m-selig.ae.illinois.edu/props/propDB.html). Existing Stik/Extra/P-51 propeller coefficient tables are not consistently measured in-flight/bench data; some are borrowed or analytical.

**Gear, crash and ground contact.** Landing gear is a list of fixed spring/damper contacts with friction. There is no gear deployment state, retract motion, wheel brake, door drag or gear-dependent force model. Ugly Stik is fixed tricycle, Extra fixed taildragger, P-51 retractable hardware deliberately locked down in simulation, and Avanti gear is held up for in-air starts with no wheel contacts. Gear contacts are not crash-hull points; the hull itself is a set of collision points in LE coordinates, not a structural/detachable volume. Avanti's no-contact, gear-up arrangement means any modeled ground contact is treated as a crash. These are coherent simplified configurations, but the v2 capability field must describe what is simulated, not merely what the physical aircraft can do.

## Capability matrix

This matrix records the current app behavior, not the capability of the aircraft hardware or of another flight simulator.

| Capability | Current status | Boundary / next capability needed |
| --- | --- | --- |
| Single glow piston + propeller | Supported; two production models | RPM/throttle and Ct/Cp table model with session on/off mode; no fuel burn or engine-specific ignition lifecycle. |
| Single gasoline piston + propeller | Runs through the generic `glow_prop` branch (P-51) | Session on/off mode exists; no separate gas ignition/fuel model; current parameterization is experimental. |
| Single turbine / centerline jet | Supported; Avanti only | One engine; the session run/off state selects the ECU spool/thrust branch. No engine-specific start/restart sequence, flameout, or modeled spool-down; `fuel_flow` does not change aircraft mass. |
| Single electric motor + direct-drive prop | Code-supported, synthetic fixture only | Ideal ESC, fixed voltage or OCV/resistance battery; no production/catalog acceptance. |
| EDF | Planned / unsupported | Needs ducted fan/thrust model, installation/inlet/nozzle and energy model; direct propeller tables are not EDF. |
| Tractor prop | Supported by current production layouts | No explicit enforced layout field yet; normalize the current fixed direction. |
| Pusher prop | Unsupported as a declared/validated layout | Offset can encode a force line, but wake/installation/prop orientation and signs are untested. |
| Multiple engines / asymmetric failure | Planned / unsupported | Current data and loader normalize one propulsion object; requires per-engine state, placement and failure aggregation. | Fixed tricycle / fixed taildragger contacts | Supported | Static contact geometry only; no steering is currently declared where zero is implicit. |
| Retractable gear | Supported only as a frozen configuration | P-51 held down; Avanti held up. No transition, actuation, drag or collision-state changes. |
| Flaps | Not simulated | No flap controls or aerodynamic deployment state, regardless of visible flap geometry. |

## Standardization recommendations

1. Use v2 structural fields to make existing simulation behavior explicit: one `convention_id` for the LE/FRD signs; explicit `propulsion.kind`; explicit `reference.planform`; explicit initial level speed; capability values for controls, simulated gear state/type, propulsion layout, energy behavior, damage representation and flaps.
2. Treat gear capability as the current simulation state: fixed tricycle, fixed taildragger, locked-down taildragger or locked-up. Keep separate physical-hardware notes if later useful; do not imply retraction dynamics from a physically retractable P-51.
3. Record energy mode separately from engine family. Glow/gas fuel mass remains prescribed/fixed in these configurations; turbine fuel flow remains telemetry; electric batteries can use fixed voltage or OCV/resistance. Do not infer fuel depletion from the presence of a `fuel_flow` number.
4. Keep reference and active fields distinguishable. `balance.firewall` is currently useful physical/installation reference metadata, not a runtime mass point. Glow `peak_power` and `peak_power_rpm` are validation/reference values, not active normalized propulsion inputs. Preserve their evidence without claiming the sim enforces the corresponding output. Keep omitted/default values explicit in v2 where current behavior depends on them (e.g. zero contact steering and empty component size), without changing numerical behavior.
5. Leave the existing aero/mass/gear/crash equations and values unchanged in a migration. Preserve every numeric value and evidence tuple; relocate inert `CLadot` without changing it. Reject unsupported requested dynamics rather than silently mapping EDF, pusher, multiple engines or retract motion onto the nearest existing branch.
6. For a later measured mass-properties gate, record configuration/fuel/gear state and measurement method, then replace virtual inventory-derived values only with data for that documented assembly state. The full symmetric inertia tensor is already consumed by the rigid-body solver; measured evidence is still needed to improve on the present virtual point-mass/box estimate. NASA's UAV procedure uses physical oscillation measurements and fitting, a different evidence class from the current inventory.

## Source scope

- [NASA Armstrong / AIAA, Determining Products of Inertia for Small Scale UAVs](https://ntrs.nasa.gov/api/citations/20170000461/downloads/20170000461.pdf): primary technical source for body/principal axes, nonzero `Ixz`, and bifilar-pendulum measurement. It does not provide values for these RC aircraft.
- [UIUC Propeller Database](https://m-selig.ae.illinois.edu/props/propDB.html): university measurement archive for low-Reynolds-number model/UAV propellers and coefficient conventions. It is a source for future propulsion data, not current validation.
- [O.S. MAX-61FX catalog](https://www.os-engines.co.jp/english/line_up/engine/air/aircraft/catalog/17750.htm): manufacturer listing for the .61-class engine. It does not establish the installed aircraft's thrust curve.
- [JetCat P100-RX-BL product page](https://www.jetcat.de/en/productdetails/produkte/jetcat/produkte/RC%20ENGINES/Engines/p100_rx-bl): current manufacturer page for a related BL variant with published rating anchors. The Avanti input file identifies the 2017 non-BL P100-RX, so this page is not a complete source for that older unit's curves.
- [JSBSim Reference Manual](https://jsbsim.sourceforge.net/JSBSimReferenceManual.pdf): primary software documentation showing one mature architecture with collections of engines/thrusters and mass/fuel state. It establishes a design comparison only; none of those features should be attributed to this simulator unless implemented and tested here.
