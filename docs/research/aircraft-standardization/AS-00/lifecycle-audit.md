# AS-00: Aircraft lifecycle audit

2026-10-11 · Prefix: AS-

**Status: Complete. Bounded read-only audit of the current working tree.** No runtime files were changed and no tests were run.

## Route through the app

Home stores a catalog ID. `main.gd` resolves that ID to the catalog's physics JSON and separately calls the render adapter with the ID. `AircraftData.load_file()` parses and validates the file, hashes its bytes, and derives a normalized model. `FlightSession._prepare_aircraft()` checks mass, inertia, control throws and trim; `_commit_aircraft()` installs that model and its callbacks into the fixed-step simulation. Each tick turns conditioned commands into actual servo outputs, then passes the normalized model to aerodynamic, propulsion and ground-force code. Rendering uses the selected ID's model builder and datum, the session's servo outputs for surface animation, and the simulation RPM for the propeller and engine audio.

The ground path is generic: aircraft data supplies gear contacts and steering limits, the session combines their forces with the field's surface table, and crash detection reads the same model's gear and crash hull. A crash snapshot pauses the simulation; the presentation director derives an estimated component/surface, starts a disposable wreck/effect/audio scene, and hides the intact model. Reset clears the crash and rebuilds the selected start. The reset signal closes a trace and resets audio/wreck presentation. Physics checkpoints fingerprint the normalized aircraft model plus ground/environment/solver configuration and restore paused recorded-input replay; they do not serialize radio or presentation state.

## Findings

| Priority | Finding and evidence | Standardization action |
| --- | --- | --- |
| High | **Identity has two runtime owners.** [`aircraft_catalog.gd`](../../../../app/app_state/aircraft_catalog.gd#L17) maps IDs to data paths, while [`airplane.gd`](../../../../app/render/airplane.gd#L17) repeats the IDs and separately maps each to a builder and datum. [`main.gd`](../../../../app/main.gd#L279) combines those routes. Normal catalog startup does not pass an expected ID into the loader or refuse a loaded `model.id` mismatch; only the research-only polar route checks that equality. A wrong catalog path can therefore pair one model's physics with another model's visuals/CG datum. | Keep one selected ID through loading and reject a model-ID mismatch before it can be flown or recorded. Preserve builder/datum implementations behind a checked adapter; do not rely on the static files staying correctly paired. |
| Medium | **Stik defaults survive outside the catalog.** [`scenarios.gd`](../../../../app/sim/scenarios.gd#L9) and `FlightSession.setup()` default to the Stik JSON path. [`aircraft_data.gd`](../../../../app/physics/aircraft_data.gd#L153) assigns 15 m/s when the optional `start.level_speed` is absent; the Stik file omits it, while Extra, P-51 and Avanti declare 17, 25 and 29 m/s. The session also uses 15 m/s fallback expressions when preparing/refitting a start. The normal app route passes the catalog path, but direct session callers still inherit these conventions. | Make start-speed presence/default policy explicit in the versioned contract and keep legacy v1 behavior named and tested. For ordinary catalog flights, make selected ID and source path/model identity observable at the session boundary. |
| Policy | **Runway start is explicitly Stik-only.** [`flight_session.gd`](../../../../app/sim/flight_session.gd#L230) fixes both the eligible ID and field ID; reset and reload preflight enforce them. [`app_root.gd`](../../../../app/app_root.gd#L141) resets non-default aircraft to airborne start. This is a deliberate product/UI policy and must not be broadened as part of schema work. | Preserve the current UI/session policy and test its refusal cases. Do not add an aircraft capability for runway eligibility. Keep other aircraft's ground-contact physics tests separate from runway-start acceptance. |
| Medium | **The visual contract is partly uniform and partly aircraft-specific.** All four builders return the stable `airplane`, `propeller`, hinge map and aircraft ID contract. The render adapter sends Avanti through a special surface mapping and routes the other aircraft through the shared hinges; only the Stik adds its detailed control-linkage assembly. `main.gd` animates the root, propeller and surfaces, but never calls [`AirplaneBuilder.apply_gear()`](../../../../app/render/airplane.gd#L94). That method and its animation check exist in the model verifier, while runtime wheel state is not connected to visual wheels. Avanti's builder has flap hinges/setter, but the flight command/session path has no flap channel and leaves them at rest. | Keep each builder's hinge names stable. AS-03 should validate actual model throws/directions at the adapter boundary, distinguish visual-only hardware from simulated controls, and mark absent flap/retract/gear-motion capabilities explicitly. Do not imply that model-verifier animation proves live simulation animation. |
| Medium | **Damage is model-data based but has no stable part identity.** Contact detection consumes each data file's crash hull and gear contacts. [`ImpactSnapshot`](../../../../app/physics/impact_snapshot.gd#L12) states that hull indexes are local to that model; the crash director estimates wing/tail/engine/fuselage from reference span/chord and calls the result estimated. Wreck presentation duplicates the full model rather than resolving named aircraft parts, so this is terminal presentation, not persistent per-part damage. Crash fuel presentation currently scans inventory names beginning `kerosene +` in [`director.gd`](../../../../app/render/crash/director.gd#L20), a string convention rather than a propulsion/fuel capability. | Preserve current terminal-crash scope. Give any fuel/damage presentation input an explicit semantic field in the contract; only add per-part damage after builders expose stable part IDs and a separate plan assigns the feature. |
| Medium | **Trace identity is strong for physics inputs, incomplete for visuals.** [`trace_meta()`](../../../../app/sim/flight_session.gd#L1419) records model ID, path, exact file-byte hash, semantic model hash, configuration and solver metadata. Main adds app/build and visual-environment context. It does not record the selected render ID separately or the built model's `visual_revision`/geometry source. Physics checkpoints include the entire normalized model, so changed model data is rejected; visual revisions are outside that boundary by design. | Retain both exact source and semantic physics identities. Add selected render ID/revision to trace or visual evidence before using traces to compare model presentation. Test cross-model checkpoint refusal explicitly. |
| Low | **The physics and most runtime consumers already share normalized data.** Session loads, trim, propulsion, control throws, gear contact forces, crash hull, resets and checkpoint identity all use `aircraft.model`; ground forces combine it with the chosen field's validated surface table. Input UI displays the same session commands/servo outputs/throws. Engine audio consumes propulsion kind/max RPM and actual simulation RPM. | Keep these consumers on the normalized model/capability interface. Avoid new ID switches in UI, audio, ground or crash code. |

## Existing proof and gaps

- [`test_aircraft_catalog.gd`](../../../../app/tests/test_aircraft_catalog.gd#L27) checks all four catalog IDs against the render IDs, builds every model, exercises the shared surface adapter, loads each data file, checks model ID/span/CG agreement, and checks an Extra flight end to end. It does not launch each of the four through the same real-app/model-render path.
- [`test_checkpoint.gd`](../../../../app/tests/test_checkpoint.gd#L123) runs reset, checkpoint restore and deterministic replay for all four catalog aircraft. It also exercises late reset-failure rollback with a test flight. [`test_trace_metadata.gd`](../../../../app/tests/test_trace_metadata.gd#L34) reloads all four models and checks source/semantic hashes, start metadata and propulsion dispatch.
- `test_aircraft_data.gd` is primarily a detailed Stik physics contract with a P-51 gear-support case. Per-aircraft handling tests exist for Extra, P-51 and Avanti; separate tests cover ground contacts/surfaces, crash snapshots/presentation/audio, UI aircraft switching, engine sound and the model verifier. These are useful specialized proofs, but they do not form a single cross-layer acceptance route.
- The model verifier tests `apply_gear()` directly; no runtime caller was found. The shared catalog test applies controls with fixed test throws, so it does not prove each flight JSON's actual throw values produce the same rendered control state.

## Suggested acceptance driver

Use the preserved pre-migration app as the numerical baseline and compare normalized state, not source hashes or metadata. For every catalog entry, assert selected ID = loaded model ID, load success, builder/datum/span/CG agreement, trim at the model's declared start speed, finite trim outputs, deterministic two-second commanded flight samples, reset to the original start/engine/auxiliary state, checkpoint round-trip/replay, cross-aircraft checkpoint refusal, and malformed reload rollback. On the same input sequence, compare float64 state/aux/input/RPM/servo arrays with the baseline; report differences by aircraft and tick.

Run the existing electric variants through the same loader/model-value comparison and a shorter deterministic session, including coupled solver selection and battery state. Check visual surface angles against loaded throws and ensure declared module capabilities remain honest: fixed P-51 gear, Avanti without contacts, no live flap control, and terminal rather than persistent damage. Separately preserve the existing Stik-only runway-start product policy. Pair this driver with the existing per-aircraft handling, ground and crash tests rather than repeating their individual physics assertions. Capture the current working-tree identity and engine version in the AS-04 result; shared `main.gd`, `flight_session.gd`, crash/audio and ground work was already dirty during this audit.

The code graph project `C-DEVELOPMENT-OpenRCsimulator` was ready (15,122 nodes / 51,081 edges). Its stored snippet locations lagged the dirty `main.gd` and `flight_session.gd`; graph search/traces were used to discover boundaries, then current files were read directly. This is a source audit only. It does not establish physical accuracy or prove runtime behavior beyond the referenced existing tests.
