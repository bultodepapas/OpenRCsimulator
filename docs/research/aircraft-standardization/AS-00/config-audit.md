# Aircraft configuration audit (AS-00)

**Status:** Complete; read-only audit of the current production parser, four catalog aircraft and one electric fixture. Findings inform AS-01.

## Scope and runtime path

The requested `app/sim/aircraft.gd` does not exist. Code graph discovery found the production loader in [aircraft_data.gd](../../../../app/physics/aircraft_data.gd), and the session boundary in [flight_session.gd](../../../../app/sim/flight_session.gd). `FlightSession.setup()` and `reload()` call `AircraftData.load_file()`. A successful result becomes `aircraft.model`; reset/trim, dynamics, propulsion, ground contact and crash handling consume that derived model.

The catalog in [aircraft_catalog.gd](../../../../app/app_state/aircraft_catalog.gd) currently contains four aircraft: Jensen Ugly Stik (`jensen_ugly_stik_60.json`), Extra 300S (`gp_extra_300s_60.json`), P-51D (`p51d_mustang_120.json`) and Avanti S (`sebart_avanti_s_a200.json`). The electric comparison below is `synthetic_stik_electric_4s.json`, a non-catalog demonstration fixture.

## Main findings

- All five files declare `openrc-aircraft v1`. The v1 parser requires an exact format string and validates many numeric and cross-field constraints, but it does not close most input objects. `_dictionary()` checks only object type; `_q()` checks the required quantity members and numeric bounds without rejecting extra members. Unknown aero coefficients are warnings and are ignored. The Python JSON Schema is offline-only, 110,319 bytes, and has `additionalProperties: true` throughout the v1 object tree except the optional wing-polar branch. Its README explicitly says ignored metadata remains allowed. It is not a runtime validator.
- Runtime strictness is branch-dependent. Electric propulsion closes its propulsion, motor, no-load context, ESC, propeller, table, battery, and OCV-point objects, and closes each electric quantity to `{value, unit, kind, source}`. Wing-polar input is also closed. Glow, turbine and shared v1 objects remain open. Unknown properties in those branches can survive parsing without warning; a misspelled known field often fails only because the expected field is then missing.
- Several defaults hide absent configuration: omitted `propulsion.kind` means `glow_prop`; omitted `reference.planform` means `rectangular`; absent `start` means 15 m/s; absent `balance.configuration` means `unspecified`; missing inventory-part `size` means `[0,0,0]`; missing gear-contact `max_steering` means 0 degrees. An absent `landing_gear` means any wheel contact is treated as a hull crash. These defaults are backward-compatible behavior, but should be explicit in v2 data or capability rules.
- Across the four catalog aircraft and electric fixture, inventory `size` is absent on 11 of 20 Stik items, 11 of 22 Extra items, 11 of 29 P-51 items, 12 of 36 Avanti items, and 11 of 20 electric-fixture items. The three gear-equipped aircraft and the electric fixture each omit `max_steering` on two of three contacts. Making these fields explicit requires migration of existing files, including zero-size and zero-steering values.
- `aero.coefficients.CLadot` is required, unit/range checked and copied into `model.aero`, but no runtime physics consumer reads it. `propulsion.engine.peak_power` and `peak_power_rpm` are checked by `_q()` but are not copied into the model or used by the simulator. `balance.firewall` is also checked but discarded. These are reference/evidence inputs, not active runtime parameters. Keep their evidence value, but classify or relocate them instead of presenting them as active controls.
- The glow propeller `rotation` value is a descriptive string in all three glow configurations. The loader never reads it. `physics/propulsion.gd` instead hard-codes reaction torque as clockwise viewed from behind. The direction is currently an implicit physics convention and the input string cannot change it. For v2, require `propulsion.propeller.rotation` to equal the constant `clockwise_from_rear` for glow propellers. Electric rotation remains fixed by the v2 convention ID; turbine `rotor_sense` is already numeric and checked as ±1.
- Descriptive inputs also include top-level `description` and `frames`, `aero.source`, `aero.conventions`, propulsion/gear descriptions, engine/propeller names, and inventory names. Most are not flight-model inputs: `id` and `balance.configuration` are copied into model identity/trace metadata; `inventory[].name` and contact names support diagnostics or downstream reporting; `conventions` is retained on the model but has no current physics consumer. `source` and `kind` on quantities are validated evidence metadata and are not retained individually in the derived model; the raw data hash preserves file identity.

## Parameter and consumer inventory

Every numeric leaf below uses a provenance quantity `{value, unit, kind, source}` except table wrappers, which carry the same metadata around `value: [[x,y], ...]`. Accepted `kind` values are `manual`, `measured`, `borrowed`, `estimated`, and `derived`; every source string must be non-empty. The v1 parser checks finiteness, unit, shape, and the listed numeric limits, but most quantity objects still accept extra keys.

## Recommended AS-01 boundary

Use a small, explicit v2 structural contract before the existing physics derivation. The contract should close objects and quantity objects, declare required versus optional fields, describe arrays/items, and select propulsion/battery/planform branches. Keep the structural vocabulary intentionally small enough for both a GDScript preflight and a JSON Schema generator; do not implement general Draft 2020-12 in the game. Let the established physics parser remain the source of numerical bounds and coupled physical checks, then generate the offline v2 schema from that reviewed contract plus the v1 numeric definitions.

Require explicit v2 format, convention ID, capability declarations, propulsion kind, start speed, planform, inventory sizes and per-contact steering values. Select branch requirements from `propulsion.kind`, battery kind and the declared capability set; reject unknown keys recursively and reject null optional modules. Keep v1 acceptance available for research and historical fixtures, and migrate production catalog data explicitly before claiming strictness for it. Keep human-readable source and description fields as an explicit metadata section. Retain `balance.firewall`, `engine.peak_power`, and `engine.peak_power_rpm` at their current paths as explicitly typed reference-only evidence for now; preserve the other validation-only tolerance/reference bands with their documented validation purpose. Move `CLadot` out of the active coefficient map unless a separate model step adds and validates an unsteady lift consumer. Require the glow `rotation` constant `clockwise_from_rear` so contradictory prose cannot pass while the equation stays unchanged.
