# Turbo Timber Evolution integration: code audit

2026-10-08 · TT-00 · **Status: audit complete; no application code changed.**

This read-only audit maps the supplied model files to the current Godot seams. The 134 MB source folder is currently untracked and sits outside the `app/` project. It contains a Blender project, STEP exports, per-part STL meshes, `escena.json`, and gear-generation/audit scripts; it contains no GLB/glTF import product or README/license/provenance sidecar. The manifest maps materials and records contacts and seven hinge axes, including flaps, but has no declared schema/version or model datum. Its contact key names millimetres; hinge positions have no unit field. The gear script says x increases aft from the propeller plane and z is measured from the thrust axis; its geometry mirrors lateral coordinates to make left/right parts. Source filenames and hashes are preserved in [inventory.json](inventory.json); the original package is an external handoff.

This audit inspects files and code paths; it does not import or visually validate the Blender scene, nor does it establish flight realism.

## Priority risks

- **P0 for any flight build — no validated aircraft input or motor model.** The source package does not include an aircraft data file with the loader's required geometry, mass properties, aerodynamics, propeller performance, or electric motor response. The meshes can support geometry derivation, but do not establish those flight parameters by themselves. Keep the first catalog entry preview-only until the input has traceable units and evidence. The missing electric branch aligns with EL1.
- **P0 for correct rendering and physics alignment — unresolved import frame/datum.** The app places the visual model using its data-frame CG and per-model datum. The source gives coordinate clues but no manifest datum or complete axis/unit contract. A wrong transform can make a plausible-looking model fly around the wrong CG; close this before using catalog CG/span checks as evidence.
- **P1 for ground handling — source contact data cannot directly populate the loader.** The manifest has two 2D contact locations; the loader requires at least three 3D support points and validated spring/tyre values. Reconstruct wheel-ground positions from the imported geometry and document the estimates before enabling runway start or landing.
- **P1 for reproducible delivery — source ownership and import output are unsettled.** The model files are untracked, outside the app resource tree, and lack a provenance/license sidecar. Decide which source files are retained and commit or relocate them together with the generated runtime asset before relying on links or export behavior.
- **P2 for completeness and player feedback — flaps, audio, shadow, and package evidence.** The app has no live flap state, its sound is a generic two-stroke cue, and its ground silhouette is generic. These do not block a static preview; each needs its own proof before claiming that the Timber's flight controls, electric sound, or visual cues are represented.

## Integration ownership

The [owning plan](../../../TIMBER-INTEGRATION-PLAN.md) defines the canonical TT step sequence. Asset/frame/viewer work belongs to the Timber model track; catalog hooks require model/menu coordination. Electric powertrain work belongs with EL1, and flight flaps overlap Avanti AV-09 and the input owner. Ground contact, trace and trim changes remain with physics. Sound/shadow/captures remain with visual/audio; packaged per-ID smoke remains with delivery.

Promote preview to experimental only after the aircraft’s own input validates and its trace/handling checks pass. A flyable label must match the catalog’s validation criteria; model contract checks establish verification, not physical validation. No application code changed and no app test suite was run for this static audit.
