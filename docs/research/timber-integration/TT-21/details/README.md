# Turbo Lumber visual setup optimization

The helper keeps the same render result while avoiding repeated paint-surface analysis and 22 hub-bolt draw submissions. The preserved pre-optimization source is `research/timber/optimization/details_baseline.gd`; the final helper is `app/aircraft/timber_visual_details.gd` at SHA-256 `a9bb210dbdb2171a61aaa5e8ab6e301f5209ef47b088525c602fe82ac6c04e2f`.

`final-profile.json` records six alternating baseline/candidate headless construction pairs and isolated cold/warm measurements. Every pair passed an exact signature gate. For unchanged meshes, it compares every surface-array channel, active material properties, instance transform and draw state, and labels. For the batched hub hardware, it compares all winding-preserving triangles after transforming them into their shared `TimberHubFasteners` parent frame, plus material and group state. The candidate has 27 unchanged mesh instances, 63 surfaces and 68,459 vertices, 40 labels, and two fastener groups with 432 triangles each.

Across the six pairs, median full `apply()` time was 552 ms for the baseline and 22.3 ms for the warmed candidate. An isolated first candidate apply took 567 ms, so the repeat-build gain comes from cached derived data and does not establish a startup improvement. Paint repair's median warm phase fell from 409 ms to 4.8 ms; fuselage marking placement fell from 143 ms to 2.0 ms. These are synchronous headless construction measurements, not frame-time or FPS claims.

The paint-template cache is an eight-entry LRU keyed by source surface arrays, active material names, repair configuration, algorithm revision and mesh-to-root transform. The independent marking-sample cache is capped at 256 entries. Warm steady state held five paint entries (1,882,664 logical packed-array payload bytes, an upper bound because unchanged arrays can share copy-on-write storage) and 42 marking samples. Changing the cowl's root-relative transform by 0.137 mm created a sixth paint entry and still matched baseline output. Ten additional transform variants exercised eviction; the cache remained at eight entries and 2,578,712 logical payload bytes.

`native-parity.json` repeats the cold baseline, cold candidate and warm candidate signature comparison after mounting each model and flushing a frame on Windows/NVIDIA with Godot's Compatibility renderer. All signatures matched and the run exited without engine errors. `initial-profile.json` retains the baseline exploratory measurements; failed intermediate cache profiles are kept under `tmp/timber-optimization/exploratory-details/`.

Reproduce the CPU profile with `Godot --headless --path app --script <absolute-repo-path>/research/timber/optimization/details_profile.gd -- --pairs=6 --out=<new-json>`. For post-render native array checks, run the same script without `--headless` and use a fresh output path; it mounts each sampled model, flushes a frame, compares signatures, then defers teardown until after a final flush.

The lifecycle follow-up found that the 17 exit references in the earlier full-crash run were audio-only (7 `AudioStreamWAV`, 10 `AudioStreamPlaybackWAV`). An isolated eight-cycle raw/baseline/candidate build, apply and free probe showed no repeated object/resource growth after its first warm cycle and no ObjectDB leak warning. Exploratory headless helper logs emitted the same null-material diagnostic for both variants; they are retained under `tmp/timber-optimization/exploratory-details-lifecycle/` and are not engine-clean acceptance evidence. The final 660-frame native takeoff fixture now uses a bounded playback drain: all 10 tracked playbacks released within 72.38 ms, with warnings-as-errors and zero engine warnings/errors. The reusable optional probe is `research/timber/optimization/details_lifecycle_probe.gd`.
