# TT-00-R1 — R1 delivery contract review

2026-10-08 · **Status: complete static contract review.** Step: TT-00-R1. Owning plan: [Turbo Timber Evolution integration](../../../TIMBER-INTEGRATION-PLAN.md). Compared the incoming R1 package with the [Blender handoff](../../../BLENDER-AIRCRAFT-HANDOFF.md) and [TT-00 source assessment](../TT-00/README.md).

Incoming package: `Timber turbo evolution/turbo_timber_evolution/r1/` (called R1 below).

## Result

R1 is a well-described internal visual and rig sample. It states its frame, datum, neutral pose, moving-part hierarchy and limitations, and it does not pretend that estimated values are physical validation. The binary GLB audit recorded in this folder independently confirms its hierarchy, pivots, signs, landmarks, meshes and materials. R1 is not ready to serve as a validated flight-data source or a redistributable public asset. Its regeneration instructions are not reproducible from the delivered tree, its submitted verifier is not a failing gate, its mass ledger conflicts with the selected manufacturer reference, and the license remains unset.

## Contract evidence

- **Frame and landmarks:** `r1/metadata.json → frames` defines CAD, Blender and simulator conversions; `datum` names D0; `landmarks` carries measurement definitions and sources. `dimensions.model` identifies span as 1.5479 m including nav-light tips and length as 1.1166 m from spinner tip to rudder trailing edge. It preserves scale and records the 76.6 mm length excess. The comparison to 1.555 m / 1.040 m is sourced to an “integration-team letter,” not directly to the manual in the package. The 42–56 mm photo comparison is plausible and consistent with TT-00, but no source-photo IDs, scale calibration or measurement worksheet are delivered; treat the nose-length explanation as a working hypothesis pending the drawing or scaled photo proposed for r2.

- **Moving-part contract:** `metadata.json → articulations` gives each moving mesh, parent, CAD members, root-frame pivot and axis, local +X hinge convention, rest transform, range, direction and driver. The four primary controls, both flaps, propeller rotor, main gear, wheels and tailwheel are covered. Horns and markings are assigned to their surfaces. `thrust_frame` is documented separately under `metadata.json → thrust`, although README lines 72–75 direct readers to `articulations` for all pivots. All finite control and suspension ranges are explicitly estimated; the contract does not convert the manual’s linear throws to angles at a defined trailing-edge point. Pivot/axis coordinates themselves do not carry per-field evidence/source labels. The handoff convention is explicit, but integration still needs an adapter mapping from R1’s local +X axes and surface signs to the app’s conventions; that conversion is not a defect in the R1 contract.

- **Export map coverage:** `export-map.json` and its generator, `source/scripts/mapa.py` plus `documenta.py`, classify the 112 STL names in the frozen TT-00 inventory exactly once: 83 are assigned to export roles and 29 are excluded, with no overlap or missing names. Exclusions have reasons, and `gear_cables` records the low-poly replacement. This set comparison was performed read-only against `TT-00/inventory.json`. The generator builds the map from hard-coded `ROLES` and `EXCLUIDAS` without asserting that they partition the source inventory, so later revisions can silently omit or duplicate a part.

## Open acceptance items

1. **Regeneration path:** R1 README lines 116–128 describes `modelo_v12.py` as writing the BREP cache, but `source/scripts/modelo_v12.py` writes `stl_v12` and a STEP file (`OUT` and export section); `auditoria2.py` is the script that creates a `.brep/ok.json` cache. README omits that cache step. The exporter expects `source/modelo_v12.py.brep/ok.json`, `source/stl_v12/escena.json` and `source/scripts/stl_juego/*.stl` (`exporta_juego.py`, setup lines 23–25); the CAD script instead writes `source/scripts/stl_v12/escena.json`. None of those generated directories/files is in the R1 source tree. `documenta.py` expects the same paths plus `_export_data.json`, `_informe.json` and `verification.json`. Correct the commands and paths and include or deterministically regenerate all inputs before calling this a reproducible delivery. The README names Blender 5.2.2 and build123d 0.13.0, but supplies no environment lock or complete Blender invocation.

2. **Verification gate:** R1 `verification.json` contains 20 `pass: true` entries. Its `source/scripts/verifica_glb.py` does import the neutral/demo GLBs and calculate structural, mesh, landmark, pivot and sign checks, but `ok()` only stores booleans and the script only writes/prints them; a false check does not produce a failing exit status. Therefore the saved file is an author-reported result, not a CI gate. The separate `TT-00-R1/glb-audit.json` independently records passing binary checks; `audit-mutations.json` shows that audit rejects a shifted pivot and flipped axis. Godot import and live articulation acceptance remain with the integration owner and are outside this contract review.

3. **Mass and CG:** R1 `metadata.json → mass_properties` labels the 1.46 kg total partial and estimated (±15%), and the component masses use class-typical estimates. TT-00’s current B-revision manual reference is 1.860 kg without battery and 2.190 kg with the recommended 4S 3,200 mAh pack (`TT-00/sources.md`, current B manual). R1’s estimated total for that stated battery loadout is 0.730 kg, or 33.3%, below 2.190 kg; even its +15% bound is below the empty-aircraft reference. The estimated CG at 60.6 mm aft of the wing-root leading edge is near the manual’s 60 ± 5 mm, but it comes from the same estimated ledger. Do not use the mass ledger for flight simulation until total mass and component positions reconcile to a measured or declared configuration. The component `x_cad_mm` positions also lack individual evidence/source fields.

4. **Rights and references:** `r1/LICENSE.txt` attributes authorship to Estudiante 4 (Innovaitors SAS) with Claude assistance and user-supplied photos, but says redistribution terms are “NOT YET SET” and limits use to internal evaluation. That blocks public redistribution or a public build until mesh, scripts and photo/reference rights are clarified. The package contains no source-photo list or external reference identifiers; `metadata.json` uses a generic “user-supplied photographs” source string for several estimates.

## Review boundary

No incoming R1 file was modified, and the Blender regeneration script was not run because its documented inputs are absent and it writes into the package. The independent binary evidence does not establish physical-flight accuracy. Godot import and application integration are outside this review.
