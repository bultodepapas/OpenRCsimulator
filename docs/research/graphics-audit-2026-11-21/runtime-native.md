## Findings, ordered by actionable evidence

### N1. Nitro vehicle performs artifact reads on every 240 Hz callback

- **Trigger / path.** MONSTER CAR 2 uses `nitro_4wd` ([app/data/vehicles/ground/monster_car_2.json:7](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/data/vehicles/ground/monster_car_2.json#L7)). `ground_scene.gd:504-515` calls `Session.tick_once` at physics cadence. Before checking `paused`, `app/sim/ground_vehicle/session.gd:469-483,1674-1675,1840-1842` checks the prepared backend identity. That invokes `NitroDynamics.backend_identity()` ([app/physics/ground_vehicle/nitro_dynamics.gd:34-52](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/physics/ground_vehicle/nitro_dynamics.gd#L34-L52)) and asks for the adapter and body artifact identities on each check. `vehicle_dynamics.gd:140-160,163-195` opens, reads and compares each complete artifact even on a digest-cache hit; the nitro identity additionally serializes and hashes a composite on each call.
- **Bound / significance.** These two source files are 21,400 and 103,044 bytes in this tree. At 240 callback checks/s, the direct path implies 480 opens and 29,866,560 bytes/s of logical source reads (~28.5 MiB/s), plus allocation, byte comparison and composite hash. Actual disk IO, buffering, CPU and timings are unknown, and release/remapped bytecode can differ. This work remains even with the optional native ground-body evaluator. `tick_once` checks identity while paused too; verify whether the owning scene is processing in a particular pause route.
- **Contrary evidence / existing repair.** RCV-41 already reduced this deliberate guard cost. Its **Godot 4.7.2 Windows debug, Ryzen 9 5900X, source/headless, native-body** pairs improved whole-session median of round means 6.187 to 5.545 ms/tick; the after profile attributed 0.922 ms/tick to the guard. Shared-host concurrency and instrumentation limit transfer; 5.545 ms already exceeds the 4.167 ms/tick realtime interval, but is not current beta2 or FPS evidence ([docs/research/rc-monster-truck/RCV-41/README.md:3-25](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/docs/research/rc-monster-truck/RCV-41/README.md#L3-L25)). This is not a missing first cache.
- **Next bounded experiment.** Re-run the existing RCV-41 component/pair harness and complete-session benchmark on a named current source+release target, warm and cold, measuring Nitro against the electric MT8 control; then inspect whether an immutable packaged-artifact identity or explicit mutation ownership could preserve the existing per-boundary guarantee. Do not replace byte checks with path, mtime, file size or an unproved cache. Keep same-size/same-mtime edits, truncation, deletion/recreation, remapped payloads, missing/unreadable files, live identity change and exact checkpoint/recording/replay refusal tests. A source change may change solver identity even if equations are unchanged.

### N2. Fleet work is serial and each companion uses the reference evaluator

- **Trigger / path.** [app/ai/companions/agent.gd:35-42](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/ai/companions/agent.gd#L35-L42) instantiates `FlightSession` and calls `setup()` without selecting a backend. Its default is `gdscript_reference` ([app/sim/flight_session.gd:741-742](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/sim/flight_session.gd#L741-L742)); there is no native-selection call in `app/ai/companions`. `manager.gd:137-140,167-185` takes the common pre-tick snapshot only on planning ticks (normally every fourth tick) in `before_step`; that part is inside the player's `step_usec` timer. `manager.gd:190-217` prepares and advances every agent serially from the player's `stepped` callback on every accepted tick, normally 240 times per simulated second; that part is outside `step_usec`. It is a cost hypothesis, not a measured contribution on the current build.
- **Counterevidence.** Planner observations/commands are already limited to every fourth tick (`agent.gd:149-178`, `manager.gd:174-185`); do not re-propose that change. Prior rendered AFC R4 is a real but older **Godot 4.7.2, 720p, Windows/RTX 3090** run: three companions had frame p95 52.017 ms and sim/wall 0.99302. It is neither current 1080p nor an attribution or displayed-frame result ([docs/research/ai-companions/AFC-00-R4/README.md:1-19](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/docs/research/ai-companions/AFC-00-R4/README.md#L1-L19)). On Mac, enabling companions also disables the player's automatic native admission ([app/main.gd:631-635](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/main.gd#L631-L635)).
- **Minimal native alternative / tests.** Measure 0, 1, 2 and 3 agents on the same 1080p release, keeping the exact scripted input/seed, current player and **each agent's actual backend** and native-call counts. Use `manager.timing_status()` before/after decomposition and independent process/frame pacing. If serial reference evaluation dominates, investigate individually preparing/admitting each agent through existing `VehicleModel` callbacks, not blindly copying the player identity or bypassing refusal. Keep full world, weather/seed, spawn, per-agent checkpoints/replay, initial snapshot-before-advance order, faults and fleet records exact; unsupported domain remains reference. Qualification must verify stage calls, fallback, cold launch, removal/restore and all per-agent trajectories. New native routing may require renewed solver/profile identities.

### N3. Accident and statistics observers repeat accepted-state gear queries

- **Trigger / path.** Ordinary non-scripted Main with accident reports on attaches a consumer ([app/main.gd:1343-1358](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/main.gd#L1343-L1358)); `_begin_accident_ledger` enables `cost_observations_enabled` (`main.gd:3099-3104`). Every accepted tick `FlightSession._on_sim_stepped` commits contacts ([app/sim/flight_session.gd:2580-2614](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/sim/flight_session.gd#L2580-L2614)), and `_observe_contact_tick` calls `gear_compressions(sim.state)` before constructing per-contact support records (`flight_session.gd:2752-2769`). This reaches per-wheel terrain/lake/track sampling (`flight_session.gd:3353-3358`, [app/physics/ground_wheels.gd:216-233](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/physics/ground_wheels.gd#L216-L233)). When flight statistics is attached and eligible, `FixedWingAdapter.sample()` separately obtains gear compression near ground (`app/statistics/fixed_wing_adapter.gd:40-45,60-78,140-154`). The Main accident callback also reads and validates contact snapshots each accepted tick (`main.gd:3030-3042`; [app/economy/incident.gd:524-606](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/economy/incident.gd#L524-L606)).
- **Bounds and counterevidence.** The work is demonstrably repeated in these routes, not yet a proven current FPS bottleneck. Statistics already has a conservative far-above-ground shortcut and R2 fixed its former circuit-terrain mistake; do not repeat the old optimization or apply an invalid field-only bound (`UI-FS-08-R1/README.md:50-60`). Support records depend on *both* current and previous compression for `new`, `persistent`, `ended` ([app/sim/aircraft_contact_events.gd:290-305](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/sim/aircraft_contact_events.gd#L290-L305)), including the first clear tick after liftoff. Silence/empty notification can still carry tick, crash, restore and settlement meaning; the signal cannot simply be suppressed. `step_usec` excludes all this observer work.
- **Repair experiment.** First profile per-consumer cost in airborne, runway/taxi, liftoff, landing, lake and raised-circuit scenarios. Test sharing a detached, exact same-tick accepted gear result only where state/configuration/timing and consumer predicates match, or a mathematically conservative far-clear support fast path that preserves previous contact transition and all public/checkpoint semantics. Preserve reset/restore, mutated data, fault, terminal/failure, post-crash settlement and same-tick reads; compare exact event arrays, statistics snapshots, checkpoint bytes and audio. Native/built-in evaluation is optional only after profiling and must remain read-only with reference parity.

### N4. Audio duplicates an accepted wind sample at the frame boundary

- **Trigger / path.** Default FlightAudio runs every process frame ([app/main.gd:1289-1295](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/main.gd#L1289-L1295); [app/audio/flight_audio.gd:440-454](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/audio/flight_audio.gd#L440-L454)). Its `snapshot` calls `session.wind_at(sim.time())`, then `session.air_data(sim.state)` (`flight_audio.gd:234-243`). For spatial wind, `air_data` already performs `WindFlow.stage_air` and its sampler can contain the datum reference wind ([app/sim/flight_session.gd:677-703](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/sim/flight_session.gd#L677-L703)); repeated wind sampling exists by source inspection, with current cost unmeasured. The overlay already uses `observer_air_and_wind` at [app/render/overlays/overlay_manager.gd:593-607](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/render/overlays/overlay_manager.gd#L593-L607).
- **Minimal repair.** Evaluate reusing the existing combined accepted-endpoint `observer_air_and_wind` helper for the audio snapshot's state/time, preserving dynamic/derived-session dispatch, refusal and wind-vs-air ordering. It optimizes the successful spatial sampler path; for nonspatial, fallback or override paths the helper intentionally still performs separate calls. Do not share `main.gd:_observer_air` indiscriminately: that is a datum observation, whereas `session.air_data()` has spatial station semantics, and smoke can request interpolated time (`main.gd:370-372,1646-1668,4288-4302`). Parity-test calm, spatial, turbulence, atmosphere, paused/rewind, invalid samples, audio shaft-load/snapshot bytes and audible transitions; compare current foreground CPU and callback pacing before adoption. Prefer the already implemented helper/built-in operations to a new native subsystem.

This is the runtime side of rendering R3, not a second independent bottleneck.

- **Trigger / path.** Interactive Home starts staged construction, while direct/headless runs keep same-frame construction ([app/app_root.gd:1385-1407](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/app_root.gd#L1385-L1407)). [app/ui/home_preview_geometry.gd:27-68](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/ui/home_preview_geometry.gd#L27-L68) similarly checks its 3,000 µs target after a `surface_get_arrays` and copies a whole surface. Other adapters can still use their synchronous `build` ([app/landscapes/catalog.gd:59-79](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/landscapes/catalog.gd#L59-L79)).

It showed 7.482→1.698 s first click-to-ready but candidate largest loading-frame median 282.173 ms and worst 291.298 ms, uncontrolled OS/import/shader caches ([docs/research/menu-investigations/UI-34c-R5/menu-preparation-2026-10-25/README.md:17-35](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/docs/research/menu-investigations/UI-34c-R5/menu-preparation-2026-10-25/README.md#L17-L35)). - **Next step.** Reproduce 0/2/5 s dwell, 5 fresh-process and 5 warm repetitions using the loading probe on each target; record each stage, maximum uninterrupted main-thread work, first visible feedback and first control-ready frame. Split or prepare only the attributed remaining >100 ms contact/sound/UI unit; avoid deferring it to first flight frame. ### N6. `step_usec` hides committed observers and smooths spikes

- **Trigger / path.** In `app/sim/simulation.gd:387-391,691-704`, `step_usec` is updated at line 700 **before** `_remember_valid_state`, `events_located`, and `stepped`. Synchronous `stepped` listeners include the flight session's contact commit, statistics, audio, crash, recorders and companion manager. It is an exponentially smoothed value (`lerpf` weight 0.05), not a distribution or full tick. As an illustration only, one 4,000 µs sample after a stable 500 µs baseline produces 675 µs in this meter; the residual halves after about 13.5 subsequent samples.
- **Counterevidence.** The timer *does* include `before_step` and much of the transaction; it is not an empty counter. Existing [research/performance/session_probe.gd:214-229](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/research/performance/session_probe.gd#L214-L229) brackets both input/session and `Simulation._physics_process`; however it is a detached session without ordinary Main audio/render/statistics/recorder attachments, and `--observer=on` means instrumentation, not all product observers. [research/performance/README.md:201-267](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/research/performance/README.md#L201-L267) explicitly describes its CPU-only scope. Attachments, real input, scheduler and presented frames need a full-app measurement.
- **Discriminating test.** Record p50/p95/p99 of the complete callback plus input and each synchronous observer for the same ticks, per-tick actual backend and a separate platform process/frame trace. Compare observer-on/off control to detect perturbation, without subtracting a noisy estimate from each frame. Historical 2026-10-27 beta1/shared Linux VM, 30-fps capped detachment saved 33.2–34.9% airborne and 22.7–23.6% runway main-thread CPU per simulated second; it is an attribution ceiling from before later repairs, not an available gain or FPS forecast (`docs/research/visual-quality-implementation/VQ-01c/tick-observers-2026-10-27/README.md:1-8,81-100`).

### N7. The diagnostic stream can generate periodic hitches

- **Trigger / path.** Opt-in `--frametimes-stream` adds base per-frame sampling and every 512 retained frames performs JSON encoding, synchronous file write/flush and SHA-256 in the process callback ([app/main.gd:3831-3874](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/main.gd#L3831-L3874); `app/render/frame_samples.gd:214-220,307-324,334-349`). That is roughly once per 8.53 s at 60 process fps or 3.56 s at 144; work may lengthen the next measured interval. `observer_poll_usec` brackets only the optional `FrameDiagnostics.sample` and merge (`main.gd:3869-3872`), not base metric collection or stream serialization/flush/hash. Stream report `write_total_usec` and `write_max_usec` are separately recorded, but do not themselves timestamp each flush.
- **Bound / tests.** This establishes a perturbation mechanism, not that a reported spike was caused by it. Match capture on/off and diagnostics on/off, use the same workload and backend, align periodic spikes to chunk boundaries, then corroborate with platform tools and process/frame timing. The stream's default 500,000-frame cap (`frame_samples.gd:9-17`) is reached after ~3,472 s at 144 fps; a full 3,600 s at 144 fps needs ~518,400 frames and will be incomplete without a higher allowed cap. Two retained float64 timing series alone occupy ~7.63 MiB at 500,000 entries, before capacity/other data; the 256 MiB sidecar cap is not process RSS or free VRAM. The report explicitly records incompleteness rather than permitting a valid-looking truncated pass.

### N8. Physics catch-up and GPU data must be interpreted separately

- **Trigger / path.** [app/project.godot:47-56](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/project.godot#L47-L56) configures 240 Hz with at most 12 physics steps per frame. Twelve ticks cover 50 ms; sustained process/render cadence below 240/12 = 20 fps cannot maintain one simulated second per wall second under that cap, while an isolated long frame does not prove sustained slowdown. A 12-tick catch-up frame can itself add work. Do not lower 240 Hz or raise the cap blindly; either changes correctness/perceptual or latency tradeoffs and a larger cap can compound stalls. Check whole-run sim/wall ratio, tick counts, frame p95/p99 and *actual presentation*, not the cap alone. Official Engine documentation explains the general cap relationship (4.6 background, not exact pinned-source proof): https://docs.godotengine.org/en/4.6/classes/class_engine.html#class-engine-property-max-physics-steps-per-frame.
- **Measurement boundary.** `app/render/frame_diagnostics.gd:9-24,110-145` samples one viewport: positive GPU readings have unverified freshness, zero is ambiguous, CPU setup is shared, and memory counters are engine estimates. `app/debug/debug_bridge.gd:1790-1834,2138-2145` explicitly records callback wall intervals and correlations, not GPU completion or presentation. Diagnose with platform presentation tools and GPU/CPU traces (Windows ETW/PresentMon, macOS Instruments/Metal and Linux compositor-appropriate tools), and record renderer, viewport/output/internal pixel sizes, VRAM/RSS and power/thermal state. Do not label `Engine.get_frames_drawn`, viewport size or process fps as displayed 1080p or measured scanout; no GPU result exists for this host.

## Retained evidence and misleading shorthand

1. `docs/plans/optimization-priorities.md:29,62,107` reflects earlier Linux-only/Windows math and Mac reference-only decisions; current NK-4 and DT-MAC-11a supersede that platform policy. This is a documentation conflict, not proof today's Windows/Mac artifacts pass current CI.
2. `UI-34c`'s 77.3% first-click improvement required 5 s dwell and is historical; its note claiming immediate-Fly overlap is unimplemented is also superseded by current `main.gd:963-973` and the current optimization-priorities plan. Neither establishes current cold/immediate-Fly targets.
3. `UI-FS-08-R1`'s initial exact far-bound parity excluded the raised circuit; R2 documents and fixes the resulting false no-contact observation. Its component percentages and beta1 headless traces cannot be presented as current full-app FPS gains.
4. Observer detach results and old AFC R4 720p data are useful prioritization, not additive gains, current causes, 1080p acceptance, presented frames or current native physics coverage. The `native` adjective in older rendered captures can mean native desktop renderer, not native NK-3 solver.
5. RCV-41's remaining 0.922 ms/tick guard profile and 5.545 ms/tick session are a compelling measured historical candidate, but occurred on a concurrent, older Windows source/headless host. Do not quote them as current release performance or promise that a safer redesign saves them.

## Disproved or bounded suspects

- **“Implement async loading from scratch.”** Already present: owned ordinary-resource thread never joins while alive ([app/ui/flight_scene_load.gd:18-42](https://github.com/bultodepapas/OpenRCsimulator/blob/57abea025f62b20233ca281d58d2acbee4ab8b8e/app/ui/flight_scene_load.gd#L18-L42)), selected bounded Home preparation (`app/ui/home_flight_preparation.gd:70-116,157-182`), staged construction and cancellation.
