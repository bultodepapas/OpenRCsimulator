# Windows Installer Lifecycle Investigation

2026-10-07 · DT-00-R1 · Scope: Windows x86_64 per-user setup, upgrades, trust, and embedded-PCK signing.

## Question and method

Can a small per-user Setup EXE upgrade the current Godot export safely while preserving user data and keeping Authenticode valid? I read the current DT plan, `app/export.sh`, `app/export_presets.cfg`, project version settings, preference/calibration paths, Godot 4.7 Windows export documentation and the Godot 4.7.2 Windows exporter source. I also read current Inno Setup lifecycle references and Microsoft SignTool/SmartScreen guidance. Accessed 2026-10-07.

## Findings

| Question | Evidence | Consequence for this project |
| --- | --- | --- |
| Does current Windows export embed the PCK? | Preset `Windows` sets `binary_format/embed_pck=true`, `architecture="x86_64"`; product name is `OpenRC Simulator`. Godot’s 4.7 Windows exporter writes the embedded export to a temporary executable path, signs that completed export when signing is enabled, then renames it to `.exe` ([tagged source](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/windows/export/export_plugin.cpp#L2694-L2736)). | The old claim that embedded PCKs inherently invalidate Authenticode is not a current implementation rule. Preserve this one-file layout and test it after signing. |
| Does Godot document signing support? | Godot 4.7 supports Windows SDK SignTool on Windows or `osslsigncode` on other hosts and exposes export-time signing options ([Windows export guide](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_windows.html#code-signing)). Its current tagged exporter builds signer arguments for identity, digest, and timestamp ([source](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/windows/export/export_plugin.cpp#L3081-L3266)). | Successful export is not signature proof. Validate the final `.exe` with Windows Authenticode tools and run it on Windows. |
| What identifies an Inno installation across releases? | Inno treats runs as the same application only when `AppId`, administrative mode, and bitness/install mode agree ([Same Application](https://jrsoftware.org/ishelp/topic_sameappnotes.htm)). `AppId` is stored in uninstall metadata and determines the uninstall registry key ([AppId](https://jrsoftware.org/ishelp/topic_setup_appid.htm)). | Choose one permanent `AppId`; keep it across releases, per-user mode, and x64 layout. Never append a version to it. |
| What does `AppVersion` guarantee? | Inno uses `AppVersion` for displayed version and uninstall registry metadata ([AppVersion](https://jrsoftware.org/ishelp/topic_setup_appversion.htm)); its documentation does not promise a downgrade block. | Treat downgrade rejection as an explicit policy and test. If required, compare canonical release versions in installer code; do not infer ordering from `AppVersion`. |
| Will a reinstall replace this app’s executable? | Inno’s `[Files]` defaults do not replace an existing file with the same version; `replacesameversion` compares contents and replaces a changed same-version file ([Files](https://jrsoftware.org/ishelp/topic_filessection.htm#replacesameversion)). | Current PE `FileVersion` is numeric `0.1.0.0`, while package/app build identity is `git describe`. A new build can retain the same PE version. Use `replacesameversion` for the app-private executable, or an equally deliberate private-file policy; test two different builds with the same numeric version. |
| Can the setup avoid elevation? | `PrivilegesRequired=lowest` keeps Setup in non-administrative install mode ([PrivilegesRequired](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm)); Inno maps `auto` shell folders to the current user in that mode ([install modes](https://jrsoftware.org/ishelp/topic_admininstallmode.htm)). | Use per-user program/Start-menu destinations. Do not write to shared Program Files, HKLM, or system directories. Preserve current-user Start-menu shortcuts. |
| Where is personal state? | Godot 4.7 maps default `user://` to `%APPDATA%\Godot\app_userdata\[project_name]` on Windows ([Godot data paths](https://docs.godotengine.org/en/4.7/tutorials/io/data_paths.html)). Code stores preferences at `user://settings.cfg` and calibration at `user://rc_calibration.cfg` (`app/app_state/preferences.gd`, `app/sim/flight_session.gd`). | Data is outside the install directory under current project settings. Installer and uninstaller must not delete it; prove settings and radio calibration survive upgrade, repair, uninstall, and reinstall. |
| How should an upgrade handle a running simulator? | Inno’s default `CloseApplications=yes` uses Windows Restart Manager to detect/ask to close processes holding files. `force` can lose unsaved work ([CloseApplications](https://jrsoftware.org/ishelp/topic_setup_closeapplications.htm)). Automatic relaunch requires the app to use `RegisterApplicationRestart` ([RestartApplications](https://jrsoftware.org/ishelp/topic_setup_restartapplications.htm)). | Use graceful close and cancellation; never force-kill a running flight. This audit found no proof the Godot app registers for restart, so test and assume manual relaunch until verified. |
| How are Setup and the embedded uninstaller signed? | Inno `SignTool` signs the Setup output and, when `SignedUninstaller=yes`, signs the uninstaller through the compiler-managed build; `SignedUninstaller` defaults to yes when `SignTool` is configured ([SignTool](https://jrsoftware.org/ishelp/topic_setup_signtool.htm), [SignedUninstaller](https://jrsoftware.org/ishelp/topic_setup_signeduninstaller.htm)). Without a configured `SignTool`, Inno’s alternative is to sign its standalone uninstaller stub before compilation so the signature is embedded in Setup. | Sign the Godot EXE before compiling Setup. Configure Inno `SignTool` and `SignedUninstaller=yes` so Inno signs Setup and its generated uninstaller through its supported path; do not manually post-sign or modify those outputs. Verify the installed game EXE, Setup, and extracted uninstaller afterward. |
| Does signing guarantee a quiet first launch? | Microsoft evaluates both publisher and file-hash reputation; new signed downloads may still show SmartScreen, and Smart App Control can impose a separate block ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). SignTool supports Authenticode verification under the default authentication policy with `signtool verify /pa /v` ([verify](https://learn.microsoft.com/en-us/windows/win32/seccrypto/using-signtool-to-verify-a-file-signature)). | Sign the game executable and final installer separately, timestamp both, and capture real browser-download behavior. Signing validity, reputation, and enterprise policy are different checks. |

## Installer prototype invariants

- Keep one fixed `AppId` across all builds; a display-name change or version bump must not create a second uninstall identity.
- Keep install scope (`lowest`), x64 mode, and install directory policy fixed between updates; test any migration deliberately.
- Preserve the prior user-selected install directory on upgrades ([`UsePreviousAppDir`](https://jrsoftware.org/ishelp/topic_setup_usepreviousappdir.htm)) and prove repair targets that same directory.
- Portable and installed builds should resolve to the same Godot `user://` directory; switching package type must not silently fork preferences or calibration.
- Use `AppVersion` for the canonical numeric release version. Keep the `git describe` build identity in the app/package manifest, not in `AppId`.
- Treat all files in `{app}` as app-owned. Apply `replacesameversion` only to private files whose same-version content must be updated; never apply `ignoreversion` to shared system files.
- Keep the user-data directory independent of setup: do not add installer-managed copies, registry redirection, cleanup, or migration there without a separate tested change.
- Keep traces, settings, and calibration out of `{app}` so upgrades can replace only the executable payload and uninstall can leave pilot data intact.
- Default to a Start-menu shortcut. Make a desktop shortcut optional and do not add autorun, file associations, services, or PATH edits for this simulator.
- Sign the Godot app EXE during export and verify it before compiling Setup. Configure Inno `SignTool` in the compiler environment and set `SignedUninstaller=yes`; Inno applies that tool to Setup and its generated uninstaller as part of its compiler flow. Do not manually post-sign or rewrite those outputs. If using Inno’s no-`SignTool` alternative, pre-sign the exact standalone uninstaller stub before compilation; a new stub can be generated when the Inno version or a directive affecting its bytes changes (for example, icon, style, or version metadata), so preserve its exact identity and re-sign any replacement. Verify signatures on the installed game EXE, final Setup, and installed uninstaller, then hash the final distributed Setup.
- Keep early unsigned builds clearly private and document their prompts. Public acceptance requires the final browser-downloaded candidate and must not tell users to disable Windows protections.

## Recommendation for existing DT phases

Keep the DT-00 choice: portable ZIP remains the baseline; prototype Inno Setup only after DT-08’s package manifest is stable. Preserve the Windows preset name, x86_64 architecture, embedded PCK, product name, numeric PE version, and UI-04 `git describe` identity. At DT-06, choose and pin the Inno compiler only after a trial package; set a stable `AppId`, `PrivilegesRequired=lowest`, and a current-user default program folder. Keep installer `AppVersion` separate from `AppId` and the app’s build identity. At DT-09a/b, test the actual setup and uninstaller, not just their scripts.

Add this proof matrix to DT-09a/b acceptance:

| Case | Required evidence |
| --- | --- |
| Fresh install | Standard account; Start-menu launch; path with spaces and non-ASCII characters; no Godot/editor install; no UAC prompt. |
| Upgrade/reinstall | Old and new builds with different `git describe` identities but equal `0.1.0.0` PE version; prove binary replacement, stable uninstall registration, shortcuts, and saved settings/calibration. |
| Downgrade/repair | Explicitly record allowed/blocked result; corrupted/missing executable repair; no accidental second install identity or stale embedded PCK. |
| Scope separation | Verify current-user shortcut and uninstall record; confirm a second Windows account does not inherit the first account’s settings or receive its Start-menu shortcut. |
| Running update | Update while Home is open, while paused, while a flight is active, and during trace recording; accept graceful close or user cancellation; verify no forced loss and document relaunch. |
| Removal | Uninstall removes owned program files/shortcuts only; reinstall rediscovers `user://settings.cfg` and `user://rc_calibration.cfg`. |
| Partial failure | Interrupt or cancel setup during preparation and copying; old install remains launchable or installer reports a recoverable state; no mixed EXE/PCK or orphaned uninstall record. |
| Trust and pack integrity | `signtool verify /pa /v` for installed game EXE, setup EXE, and uninstaller; verify secure timestamps; re-run `check_field_pack.gd` against the signed embedded-PCK EXE and launch it on Windows; browser-download the final setup and portable ZIP; record publisher display, SmartScreen and Smart App Control results. |
