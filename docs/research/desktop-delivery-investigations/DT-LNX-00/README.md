Research and source audit only; no package build, installation, live-app test, publication or hardware qualification was performed. Sources were read through web tools, official source files and Context7's Godot 4.7 documentation. Indexed code discovery was attempted first; its missing/stale results were checked against current source. No agent agreement is treated as runtime evidence.

The tree was clean at initial inspection, then unrelated graphics, trailer, website, skin and Apple Silicon documentation edits appeared. They were preserved. During documentation integration, concurrent commits advanced HEAD through `ff3493da2` to `96e8e7d762e5e275e0136d53242ba7e7540f108f`, including these draft documents. The lead did not commit or publish them. The source comparison retained the baseline identity: export, engine acquisition, native admission and cited runtime files were unchanged; website/debug-tool work remains independently owned. Source paths/line locations below identify inspected behavior, not a clean build receipt. ### Flatpak and Flathub are separate decisions

[Flathub's current requirements](https://docs.flathub.org/docs/for-app-authors/requirements) call for offline source builds, stable-first admission, a current runtime and explicit architecture restriction when needed. Its AI policy prohibits AI-assisted manifests and agent-generated submission/review interactions, and requires disclosure of included generated material. A human maintainer must assess and prepare any compliant future submission. Store acceptance remains unresolved; stable Git tags alone do not settle the application's early-alpha status. Project-hosted Flatpak evaluation can proceed independently. This report and plan are research, not a submission manifest or PR.

| Primary source | Finding / consequence |
| --- | --- |
| [Sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html) | Devices/network/display/audio need explicit access; portals provide selected-file/URI access. `input` permission requires Flatpak 1.15.6; broader old-host fallback is a deliberate tradeoff. PulseAudio socket access includes input, not only playback. |
| [Conventions](https://docs.flatpak.org/en/latest/conventions.html) | Sandbox data paths differ from the existing host application root; migrate only validated user-chosen data, preserve backups and test removal/reinstallation. |

| [Single-file bundles](https://docs.flatpak.org/en/latest/single-file-bundles.html) | A bundle does not contain dependency runtimes or full AppStream delivery. Managed updates require a configured remote/ref; offline installation needs a separate complete dependency-transfer design. |
| [Flathub runtimes](https://docs.flathub.org/docs/for-app-authors/runtimes) | Runtime support has a lifecycle. Pin the selected runtime/SDK for builds, schedule upgrades, and keep SDK distinct from player runtime requirements. |
| [Flathub uninstall guidance](https://docs.flathub.org/docs/for-users/uninstallation) | Normal uninstall and explicit user-data deletion are distinct. Preserve configuration/calibration by default. |

The receipt constraint creates two valid strategies: preserve one exact project-built payload when wrapping it for a private remote, or build the source in the selected SDK and independently finalize/qualify that output. Flathub's requirements favor the latter for this source-available project. Neither approach earns automatic native-radio, NVIDIA-extension or portal acceptance.

## Reconciled recommendations and remaining evidence

The packaging specialist favored qualifying the existing ZIP before adding channels; the release specialist favored a shared immutable payload, and the runtime specialist emphasized native hardware/numerics. The plan combines these: establish the current x86_64 payload/ABI first, add AppImage plus tar recovery, then add managed formats only after their own gates. The existing ZIP remains during transition. A separate source-built Flatpak environment receives independent receipts and qualification. ARM64 cannot be advertised by merely adding matrix entries.

Independent plan review corrected receipt/qualification ordering, Flatpak SDK classification, the distinction between release and debug automation, actual audio permission exposure, eleven-language website coverage, packaging-only revision rules under immutable GitHub releases, and partial publication. It also found the forced-Wayland argument-loss risk during graphics restarts. These are planning/source findings; no runtime regression fix is claimed.

The largest unresolved decisions are the exact production engine, minimum native ABI/distro floor, ARM64 native-versus-reference route, real radio/portal permissions, Linux High disposition, hardware availability, signing/repository maintainer and Flathub eligibility. DT-LNX-01…13 assigns owners and acceptance evidence. The next small implementation is isolated release staging and input verification, followed by all-ELF ABI measurement. No current OpenRC download is newly qualified by this audit.
