# DT-MAC-00-R2: Godot and macOS delivery compatibility

2026-10-28 · Source review on Windows; no Mac or GPU execution. This is research for the [Apple Silicon plan](../../../plans/apple-silicon-performance.md), not a platform qualification. The assigned starting commit was `c953c8c848db7acac4ed33e606ba580e213d4244`; the shared checkout moved to `b56eb5fa3e08ffdb53860a656be7e431b3e2b547` during this review and other paths changed concurrently. Claims about OpenRC describe the inspected current files, not a frozen package. The [GDU plan](../../../plans/godot-4.8-upgrade.md) owns the engine migration and [DT](../../../DESKTOP-DELIVERY-PLAN.md) owns shipping gates.

## Version and source identity

The [official archive](https://godotengine.org/download/archive/) lists **4.7.2-stable**, 18 August 2026, as the latest stable 4.x release and **4.8-beta1**, 15 October 2026, as the latest 4.8 preview at the review date. The [beta announcement](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-1/) identifies engine commit `4d10419ca`; Godot's source page resolves it to `4d10419cacd6d3009976e8f9fd3abd970fd58018`. OpenRC has owner-authorized 4.8-beta1 for development, with release qualification still open. The installed Windows console editor reported `4.8.beta1.official.4d10419ca` in this review. Its [getter](../../../../app/get-godot.sh) pins archive SHA-512 values for Linux x86_64 and Windows x86_64; it explicitly rejects Darwin. The [template getter](../../../../app/get-templates.sh) pins the beta1 template archive SHA-512 and installs the needed macOS ZIP. A Mac editor and its verified architecture-specific archive/digest still need an acquisition path.

The existing Apple plan's 4.7.2 pin and Linux-only-downloader statements predate the GDU adoption and Windows getter support. They are not current instructions. Do not change the engine to obtain a renderer feature without a separate GDU evaluation and matching templates, imports, native bindings and package identities. Beta status is not itself a reason to undo the owner's choice, but it does not close GDU's release gates.

The web source viewer returned the full pinned source commit used below. A direct shell `git ls-remote --tags` query for `4.8-beta1` returned no matching output in this environment; no local source checkout or independent Mac editor/template download was verified here. Resolve that discrepancy and verify official archive checksums when reproducing. Do not infer binary correspondence solely from a documentation page or a version label.

## Driver and feature matrix

**Correction to the older plan:** [Godot's 4.7 architecture documentation](https://docs.godotengine.org/en/4.7/engine_details/architecture/internal_rendering_architecture.html) says Metal 4 is selected automatically on macOS 26+, but the exact [4.8-beta1 source](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/drivers/metal/rendering_context_driver_metal.cpp) unconditionally constructs `MTL3::RenderingDeviceDriverMetal`. The [4.7.2 stable source](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/drivers/metal/rendering_context_driver_metal.cpp) does the same. The pinned [MetalFX implementation](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/servers/rendering/renderer_rd/effects/metal_fx.cpp) encodes its scalers through `MTL3::MDCommandBuffer`. The documentation's linked PR #114484 is a Metal refactor, not evidence of that selection. Apple's [WWDC26 demonstration](https://developer.apple.com/videos/play/wwdc2026/357/) describes adding a Metal 4 backend to an existing Godot Metal 3 backend; it does not establish that the demonstration shipped in these official versions. Treat a Metal 4 command backend as **unavailable in the inspected pinned source**, until a separately identified engine actually proves otherwise. An OS, GPU-family, SDK or reported Metal API/language version is not proof of the command backend.

| --- | --- | --- |
| 4.8-beta1; Apple Silicon; macOS 13+; Compatibility/OpenGL | Current project default. No `RenderingDevice`; no MetalFX | Static preset and prior cross-export only; native launch/visual checks pending |

The prior GDU cross-export's Mach-O load commands declare **macOS 13.0 arm64** and **11.0 x86_64**, SDK 26.5; these are binary metadata, not tested product floors. See [GDU-03 export evidence](../../engine-upgrade/GDU-03/exports/README.md) and [Godot system requirements](https://docs.godotengine.org/en/4.7/about/system_requirements.html). For the available M1 Air, inventory GPU core count and installed OS before testing. Do not require macOS 13 on a later Mac that cannot run it.

Apple's [feature tables](https://developer.apple.com/metal/capabilities/) map M1 to Apple7, M2 to Apple8, M3/M4 to Apple9 and M5 to Apple10. The table lists spatial from Apple3 and temporal from Apple7; it lists interpolation and denoised upscaling separately, with different family thresholds. These are hardware-family indications, not proofs that a particular OS, Godot build, renderer, scaler descriptor or viewport satisfies its full runtime contract. Test the M1 8 GB baseline, then named M2/M3/M4/M5 machines and each machine's oldest actually installable supported OS plus a newer OS; record untested rows explicitly. A capable M3+ does not authorize making denoising mandatory for M1/M2.

## Pinned MetalFX contract

[Viewport's pinned API](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/doc/classes/Viewport.xml) exposes `SCALING_3D_MODE_METALFX_SPATIAL` and `SCALING_3D_MODE_METALFX_TEMPORAL`. Spatial at 1.0 is off; temporal at 1.0 is native-resolution temporal antialiasing; below 1.0 is upscaling. Values above 1.0 use bilinear downsampling. The 3D buffer is scaled, not the full UI. The application's existing [reconstruction adapter](../../../../app/render/reconstruction.gd) has Native, FSR2 and experimental FSR3/DLSS choices; it has no MetalFX provider, capability reporting or product qualification today.

For a candidate, verify the effective renderer and driver first, obtain the main `RenderingDevice`, and query `has_feature(RenderingDevice.SUPPORTS_METALFX_SPATIAL)` and `has_feature(RenderingDevice.SUPPORTS_METALFX_TEMPORAL)`. The exact [device API](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/doc/classes/RenderingDevice.xml) exposes both features and `LIMIT_METALFX_TEMPORAL_SCALER_MIN_SCALE` / `MAX_SCALE`. Divide each `limit_get()` result by `1_000_000.0`; reject nonfinite, invalid, unsupported or out-of-range combinations. The [Metal driver](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/drivers/metal/rendering_device_driver_metal.cpp) converts Apple's supported output/input factors to reciprocal input/output scales. Its [device properties](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/drivers/metal/metal_device_properties.cpp) query descriptor support on macOS 13+; on macOS 14+ they query scaler limits, while older systems use source defaults of 1–3 for the reciprocal ratio. Never assume every device accepts 0.5 or 2/3 without reading the limits. Availability and scaler creation remain separate from a visible correct result.

The pinned [viewport implementation](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/servers/rendering/renderer_viewport.cpp) has important refusal and fallback paths:

- Its setter rejects temporal outside Forward+ and spatial in Compatibility, potentially preserving the previous server state. Its buffer-configuration fallback maps an invalid Mobile temporal state to bilinear. Do not claim that every rejected setter call changes the renderer to bilinear.
- On Forward+, unavailable temporal selects spatial when supported, otherwise FSR2; unavailable spatial selects FSR1. Out-of-range temporal selects FSR2. Subsequent renderer/upscaler restrictions can produce bilinear. A requested mode or viewport property is not sufficient proof of the effective pass.
- Valid temporal disables 3D MSAA internally and takes precedence over separate TAA. OpenRC requests 4× MSAA by default, so compare the actual AA configuration and image, not just a single scale value.
- Capture requested mode, renderer, API/driver, feature bits, queried limits, requested/input/output pixel dimensions, AA and fallback reason. Establish the pass through an engine-visible diagnostic or GPU capture; warnings are once-only and the engine's local fallback variable is not a reliable player-facing status API. If effective selection cannot be proven, report it as unknown and keep the candidate disabled.

The built-in scaler consumes color, depth, motion vectors, jitter, optional exposure and a reset flag through the engine's render graph. Its implementation is evidence that spatial/temporal integration exists; it does not prove correct motion, camera cuts, transparency, resizing or lifetime behavior in OpenRC. Test those against the same flight/camera and at 1080p before higher resolutions or 720p. Reset and history handling require explicit proof for the unmodified official build, rather than assuming an experimental FSR/DLSS patch also controls MetalFX.

## Native boundary and unsupported additions

Godot exposes `RenderingDevice.get_driver_resource()` to extensions. In this pinned [Metal driver](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/drivers/metal/rendering_device_driver_metal.cpp), the logical-device, queue and texture cases return the underlying Metal device, command queue and texture; other kinds can return zero. The public [RenderingDevice contract](https://raw.githubusercontent.com/godotengine/godot/4d10419cacd6d3009976e8f9fd3abd970fd58018/doc/classes/RenderingDevice.xml) does not establish an extension's right to own the engine's current command buffer, insert a pass at the correct stage, synchronize it or present extra frames. The built-in MetalFX path uses an engine-internal driver callback, declared resource usage, fence and retained scaler. A pointer alone is not a supported render-graph or lifetime integration.

Apple separately documents [frame interpolation and denoised upscaling](https://developer.apple.com/videos/play/wwdc2025/211/). Their presence in an Apple SDK or feature table does not make them available through the pinned Godot viewport API. The inspected engine exposes spatial and temporal scalers, not a verified product frame-generation or denoising pipeline. An experiment would first need a source-pinned integration seam, supported resource and motion/depth contracts, GPU synchronization, frame ownership, UI composition, pacing/latency, cancellation and reset proof. It is a separate renderer/engine change with rollback and a maintained upstream or custom-build plan; no native-handle shortcut or generated frame may alter 240 Hz simulation, input, replay or imply lower control latency.

The Windows/Vulkan [experimental graphics builder](../../../../tools/graphics/native/build.py) is not a Mac build path. The native ground-vehicle extension is built for Windows/Linux x86_64 and explicitly excluded by the macOS preset; Mac uses the GDScript reference. The optional native aircraft-kernel lock is Linux x86_64 only. Both native projects pin `godot-cpp` `10.0.0-stable` commit `507ed9d840c01a3c5b2a39af8bb4000bfac30bf5`, extension API 4.7 and SCons 4.10.1. Those pins do not supply or qualify a Mac library. If a native extension is later justified, separately pin its Mac compiler, SDK, deployment target and exact flags, build/load the intended slices and preserve its binary/license/ABI receipts. [GDExtension selection](https://docs.godotengine.org/en/4.7/engine_details/engine_api/gdextension/gdextension_file.html) is feature-tag and architecture based; a universal app executable does not make an x86_64-only dylib universal.

## Package, CI and security gaps

The [macOS preset](../../../../app/export_presets.cfg) selects universal architecture, the project-local beta1 template correction, ad-hoc signing and no notarization. [CI](../../../../.github/workflows/ci.yml) cross-exports on Ubuntu and has Windows/Linux native jobs; it has no macOS runner. [Export checks](../../../../app/tests/check_macos_export.py) inspect the archive's executable mode, slices and ad-hoc signature structure; they do not execute the Mac app or verify Gatekeeper. The checked [GDU-03 package](../../engine-upgrade/GDU-03/exports/README.md) passed cross-export checks, with no Mac execution. The editor downloader rejects Darwin. `app/test.sh` uses the Python checked runner for timeouts and error scanning; its Mac path still needs a verified native editor and platform compatibility. GNU `timeout` remains in `app/export.sh` and `app/capture.sh`; the latter also uses Linux/Xvfb capture paths. A portable timeout alone does not make the exporter a Mac release pipeline: it explicitly requires a Linux host and runs Linux/NK-3 package, replay and trimmed-flight gates. Preserve those Linux gates in the cross-export workflow and add separate native Mac source, package and GUI checks against the exact exported artifact. Do not erase an owner's application data or equate a headless VM with physical-GPU testing.

The 4.8-beta1 universal exporter inverts release/debug payload selection ([#124744](https://github.com/godotengine/godot/issues/124744)). OpenRC's [verified local correction](../../engine-upgrade/GDU-03/macos/README.md) swaps the official payloads in a project-local ZIP and retains their identity; it does not modify the installed official ZIP. [#124757](https://github.com/godotengine/godot/pull/124757) merged upstream on 22 October, after beta1. Use the workaround only for that exact beta1 universal export; recheck and remove it when adopting a build containing the upstream fix. The Compatibility global-uniform bug [#124742](https://github.com/godotengine/godot/issues/124742) was also fixed upstream after beta1 by [#124750](https://github.com/godotengine/godot/pull/124750); closure on master does not change the already published beta1. Run the GDU regression/accepted-workaround check on the actual Mac and proposed engine before promotion.

Before delivery, retain the exact source/dirty identity, editor and template archive hashes, template-correction receipt, import and project settings, native dependency hashes/licenses, compiler/SDK identity if used, final bundle and distribution SHA-256, and `CFBundleExecutable`/version/minimum-OS/slice readback. Verify each Mach-O and nested dylib, architecture, load commands and deployment floor. Inspect release/debug status on both slices. Sign nested code and the final bundle with the intended Developer ID and hardened-runtime entitlements; notarize, retain the accepted submission/log and staple the ticket before final packaging. Test the **downloaded, quarantined final bytes** in a clean Mac account using Finder, Gatekeeper assessment, first launch and an offline/stapled-ticket case. Verify the final hash after packaging. An ad-hoc signature, `codesign` structural check, Linux pack read or terminal launch does not establish downloaded-app trust. Follow [Godot's macOS export guidance](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_macos.html) and [Apple notarization guidance](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

## Promotion gates and stop rules

1. **Source and package:** freeze one revision and actual dirty inputs; verify pins and matching editor/template, corrected beta1 universal payloads, final bundle structure and any native slices. Record exact effective engine and driver; an unknown backend or silently substituted scaler stops the claim.
2. **Native ARM64 logic:** on an isolated ARM64 account, verify the process really runs arm64, run the checked source suite and a complete final-package headless flight trace with error scanning and bounded timeout. The shipped package excludes tests; source testing and final-byte testing are separate. A macOS VM may establish only the capabilities actually observed.
3. **Numerics:** preserve float64 state, 240 Hz schedule and existing solver identity. Use same-host exact replay for presentation-only candidates and existing [H9](../../simulation-state/H9/README.md) cross-platform component budgets for ARM64 versus reference; record maxima, worst checkpoint, discrete differences, data/tape/build identities and completion. Do not re-record goldens, relax tolerances, lower precision or physics frequency to make a renderer pass. Any unexplained mismatch, nonfinite state or partial replay stops promotion. Numerical agreement is not physical validation.
4. **Native presentation:** exercise Compatibility, Mobile/Metal spatial and Forward+/Metal temporal as separate supported candidates, plus unsupported feature, out-of-range, driver change, fallback and return-to-native paths. Verify the actual GPU pass and MSAA, image/readability, flight controls, propellers, thin geometry, smoke/transparency, camera cuts, resets, resize, minimize and world reload. Inspect temporal ghosting, incorrect motion and retained resources. Unknown or wrong effective path, corruption, crash, leak or unresolved shader regression stops that candidate.
5. **Sustained performance and distribution:** apply DT-MAC's paired 1080p/60 Hz trials and active 30-minute soaks on the available 8 GB M1; capture thermal, memory/swap, frame/presentation intervals, tick budget and pilot control evidence. Follow with higher resolutions and the named M2–M5 matrix. Unsupported counters, VM GUI, missing pilots, missing notarization or unavailable machines remain open rather than passing by inference.

No tests, package build, Mac launch, Metal capture, notarization or performance measurement were executed for this report. Context7 4.7 documentation was consulted, then exact 4.8-beta1 source was used where the documentation conflicted. Prior linked evidence retains its own scope and identities.
