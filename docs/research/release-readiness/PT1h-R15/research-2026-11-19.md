## R01 — Godot standard profiler: which work owns the wall gap?

**Evidence.** The [profiler tutorial](https://docs.godotengine.org/en/4.5/tutorials/scripting/debug/the_profiler.html)
distinguishes frame/physics activity and inclusive versus self function time.
Profiling adds work and should be enabled deliberately. Nested inclusive durations
are not independent contributions.

**Decision — adopt workflow, S3/S6.** Use the existing lightweight capture to locate
a repeatable action, then reproduce with `profile`/the engine profiler. Retain
scenario, process frame and profiler-state identity. Inspect inclusive ownership
and self hotspots separately; do not report their sum as a CPU budget. No new
GDScript sampling profiler is needed.

**Check.** A nested-call delay is assigned to the expected self-time owner. Keep
profiled and ordinary runs separate, including their variation. Failure to reproduce
leaves the cause unresolved; this evidence does not measure display latency.

## R02 — Visual Profiler: what part of the CPU/GPU does it measure?

**Evidence.** Godot's [Visual Profiler documentation](https://docs.godotengine.org/en/4.5/tutorials/scripting/debug/debugger_panel.html#visual-profiler)
scopes its CPU view to rendering, excluding script/physics work. GPU stages may
overlap. The versioned guide documents unavailable Visual Profiler support for
Compatibility on macOS.

**Decision — adopt conditional recipe, S1/S3.** Pair script and rendering evidence
only on a supported actual backend. Extend existing `render`/`ablate` receipts with
scope and enabled state; do not interpret low rendering CPU as low total CPU.
Keep parallel GPU stages distinct instead of summing them into serial frame cost.

**Check.** Separate script-heavy and graphics-heavy fixtures select different
follow-ups. Unsupported backend/OS combinations return an explicit limitation.
Recheck the exact installed profiler before claiming availability on a later engine.

## R03 — Exact-pin Performance monitors: are values frame-local?

**Evidence.** The [API source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/doc/classes/Performance.xml)
documents cadence and debug-only limitations. More specifically,
[Main::iteration](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/main/main.cpp)
publishes `process_max`, `physics_process_max` and `navigation_process_max` inside
the `frame > 1000000` reporting block and resets those maxima.
[Performance::get_monitor](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/main/performance.cpp)
returns the stored timing values. They are periodically published window maxima.

**Decision — adopt semantics, S1.** Add aggregation and observation-age semantics to
the metric dictionary. Keep callback intervals as detector input. The existing
monitor readings are contextual, not same-frame script/physics durations or evidence
that the coincident frame caused the maximum. Unknown age stays unknown.

**Check.** A brief known workload pulse and subsequent quiet callbacks demonstrate
the reporting window. An engine upgrade must recheck this source contract. This is
a source finding; no rendered timing experiment was executed in this update.

## R04 — Motion jitter: can timing be clean while motion looks wrong?

**Evidence.** Godot's [jitter/stutter guide](https://docs.godotengine.org/en/4.5/tutorials/rendering/jitter_stutter.html)
separates uneven motion from intermittent delays. The [interpolation guide](https://docs.godotengine.org/en/4.5/tutorials/physics/interpolation/using_physics_interpolation.html)
requires consistent update timing and covers resets after teleportation.

**Decision — adopt scenarios, S3/S6.** Preserve OpenRC's custom interpolation and
240 Hz physics. Add straight flight, steady yaw, chase/pilot camera switches and
reset/respawn observations. Capture actual camera, cap, refresh and time-scale
settings. An operator-reported motion defect remains distinct from measured FPS loss.
Do not enable a second interpolation layer as a generic repair.

**Check.** Stable callback intervals with visible motion discontinuity remain a
camera/interpolation investigation. Native video/pilot review is separate from
headless logic checks. Diagnostic stress settings cannot qualify production physics.

## R05 — Pipeline compilation: which category suggests first-use work?

**Evidence.** The [pipeline guide](https://docs.godotengine.org/en/4.5/tutorials/performance/pipeline_compilations.html)
distinguishes cumulative Mesh/Surface/Draw/Specialization counters, background
specialization, ubershaders and precompilation. Shader Baker prepares intermediate
shader code, not every final driver-specific pipeline; modern renderer support
does not imply Compatibility support.

**Decision — preserve existing deltas, add receipts, S1/S3.** Keep categories separate
and record actual backend and first-use versus warmed phase. Draw compilation is
an investigation lead, not a duration or causal verdict. Shader baking and pipeline
warmup are separate, conditional experiments with VQ/GDU, not automatic fixes.

**Check.** Unchanged totals yield zero deltas; resets retain epoch identity.
Specialization-only activity cannot be labelled a confirmed synchronous compile
stall. A zero counter on an unsupported path cannot exclude shader work.

## R06 — Resource loading: does asynchronous loading remove the whole stall?

**Evidence.** The [background-loading guide](https://docs.godotengine.org/en/4.5/tutorials/io/background_loading.html)
and [ResourceLoader contract](https://docs.godotengine.org/en/4.5/classes/class_resourceloader.html)
explain that `load_threaded_get()` can block when the request is not finished.
Status polling should span frames; additional subthreads can compete for resources.

**Decision — instrument existing phases, S3.** Reuse OpenRC's bounded selected-resource
preparation. Mark request, ready, retrieval, instantiation and scene-tree attachment
separately, including cancellation and first controlled-flight readiness. Audit an
early retrieval or large attach only when a trace identifies it. Do not build a
replacement loader or assume an I/O completion makes `_ready()`/upload inexpensive.

**Check.** A delayed request keeps UI control responsive, and phase timings identify
where the time goes. Preserve latest-selection cancellation and validation while
measuring total handoff time; shifting the stall into flight is not an improvement.

## R07 — Physics catch-up: cause or consequence?

**Evidence.** The [Engine contract](https://docs.godotengine.org/en/4.5/classes/class_engine.html#class-engine-property-max-physics-steps-per-frame)
describes bounded catch-up and slowdown below the sustainable frame rate. OpenRC's
[configuration](../../../../app/project.godot) uses 240 Hz and 12 steps/frame:
their ratio gives a nominal 20 FPS scheduling boundary. This calculation is not
a perceptual stutter threshold or a measured throughput result.

**Decision — adopt symptom interpretation, S1/S3.** Keep existing physics counts;
add actual scheduling/time-scale context and stable active-phase simulation/wall
comparison. Cap pressure can follow rendering delays as well as costly physics.
Preserve simulation rate, RK4, float64 and replay contracts.

**Check.** Both a physics workload and an independent render delay may hit the cap.
Neither gets a physics-root-cause label without scoped evidence. Pause, reset and
intentional slow motion must not appear as unexplained simulation slowdown.

## R08 — Exact-pin GPU readback: can a positive value still be stale?

**Evidence.** The [GLES3 collector](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/drivers/gles3/storage/utilities.cpp)
retrieves older queries; its comment identifies frame-minus-two data.
[Viewport getters](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_viewport.cpp)
derive durations from stored timestamps without a source-frame ID. The measurement
setter toggles a flag without clearing those times. The [RenderingDevice path](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/servers/rendering/renderer_rd/storage_rd/utilities.cpp)
delegates separately, so the GLES3 lag is not a universal Metal/Vulkan rule.

**Decision — preserve guards and unknown freshness, S1/S6.** OpenRC already returns
unavailable when measurement is off. Document that re-enable/sparse viewports still
need freshness evidence. Record coverage; root-only data is not a whole-display
measurement. Do not invent a fixed callback shift.

**Check.** Pulse workloads and on/off/disabled-viewport scenarios on each eligible
backend measure arrival separately. Repeated nonzero readings cannot certify fresh
samples. Source inspection establishes the risk, not its runtime delay distribution.

## R09 — PresentMon: independently observe presentation on Windows

**Evidence.** The [upstream README](https://github.com/GameTechDev/PresentMon) and
[console schema](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)
separate CPU, GPU and displayed timing. They expose QPC timestamps and warn that
`Runtime=Other` paths, common for OpenGL/Vulkan, offer reduced accuracy for some
metrics; hardware GPU scheduling also affects timing interpretation.

**Decision — adopt optional sidecar, S5.** Retain the original CSV, tool version,
PID/swap chain, API/present mode, scheduling setting and clock units. Keep undisplayed
rows and unavailable values. Callback and display samples are separate channels,
not presumed one-to-one records.

**Check.** A named Windows run with a repeatable incident records multiple clock
anchors and uncertainty. Reject frame-level alignment when error is too large.
Disagreement between callback and presentation observations is retained as evidence.

## R10 — CapFrameX: what does “1% low” actually mean?

**Evidence.** CapFrameX's [metric explanation](https://www.capframex.com/blog/post/Explanation%20of%20different%20performance%20metrics)
and [statistics implementation](https://github.com/CXWorld/CapFrameX/blob/master/source/CapFrameX.Statistics.NetStandard/FrametimeStatisticProvider.cs)
distinguish percentiles, low averages and time-integral measures. Overall FPS uses
frame count divided by total duration; slow-tail averaging is a different quantity
from a percentile or an average of instantaneous FPS.

**Decision — adopt comparison identity, S4.** Keep OpenRC's existing formula and
floor-based tail size. Persist source, estimator, rounding, tail count, filters and
window with every comparison. Reuse its budget excess and slow-time share. Similar
labels or similar numbers do not demonstrate equality with CapFrameX output.

**Check.** Known vectors with ties and a few long frames explain metric differences.
Sample counts around 100/1,000 keep short-tail warnings. Formula or timing-source
mismatches block an unconditional improvement percentage.

## R11 — Perfetto: extend a real trace without inventing work

**Evidence.** [External-format support](https://perfetto.dev/docs/getting-started/other-formats)
includes Chrome JSON slices, instants, counters and metadata. Synchronous duration
events on one track must nest; overlapping non-nested slices are ambiguous.
[Clock synchronization](https://perfetto.dev/docs/concepts/clock-sync) uses explicit
clock identities/snapshots rather than assuming equal numeric origins.

**Decision — preserve existing export, S4/S5.** Keep one callback-wall lane. Use
separate logical tracks for independently sampled evidence; do not label fabricated
track IDs as actual OS threads. Emit durations only with observed boundaries.
Keep unaligned external files separate; native multi-clock export is conditional S7.

**Check.** An actual importer checks row count, total duration, units, known markers
and metadata. Concurrent-lane and shifted-clock fixtures must not acquire false
nesting or correlation. JSON syntax alone does not establish useful visualization.

## R12 — Tracy: where would native instrumentation help?

**Evidence.** The [Tracy repository](https://github.com/wolfpld/tracy) and
[manual](https://github.com/wolfpld/tracy/blob/master/manual/tracy.tex) describe native
zones, frame markers, optional profiling facilities and compile-time configuration.
These integrations require instrumentation/build work; macros are not a drop-in
GDScript profiler.

**Decision — defer S7.** Use native zones only for a demonstrated GDExtension/engine
attribution gap after existing profiler evidence. Stable incident/frame IDs can
link a separate trace. Do not add Tracy to ordinary exports or require a custom
engine just to collect existing callback intervals.

**Check.** One known native delay must appear in its intended zone. Compare disabled,
enabled/disconnected and connected configurations, retaining overhead and loss.
A useful isolated zone is not proof that all native or script work is covered.

## R13 — Nsight Systems: characterize the causal detector and API waits

**Evidence.** The [Nsight user guide](https://docs.nvidia.com/nsight-systems/UserGuide/index.html#stutter-analysis)
describes a surrounding-19-frame median, relative threshold and a 4 ms minimum
difference, including alternating-cadence limitations. The [analysis guide](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html)
distinguishes API wall time, scheduling/waits, GPU work and presentation.

**Decision — adopt characterization, S3; conditional profiling, S5.** R15 already
borrowed the two-part detector idea. Retain its preceding-history policy, which
cannot use future frames. Compare against a separately named offline reference,
without rewriting historical flags. Select an eligible OpenGL/Vulkan capture path
for an actual NVIDIA investigation; API and OS features differ.

**Check.** Cover exact threshold boundaries, isolated spikes, persistent slowdown,
alternating cadence and phase changes. A long Present/submit call is not labelled
CPU-bound until scheduling/wait evidence supports that inference.

## R14 — Radeon GPU Profiler: which routes are eligible?

**Evidence.** [AMD's RGP overview and requirements](https://gpuopen.com/rgp/) identify
supported AMD hardware and DirectX 12/Vulkan routes. Its [event documentation](https://github.com/GPUOpen-Tools/radeon_gpu_profiler/blob/master/docs/source/events_windows.rst)
exposes event timing, queues and barrier/shader context.

**Decision — defer targeted S7.** Use RGP for an already justified GPU investigation
on an eligible AMD/Vulkan or D3D12 configuration. Preserve exact driver/tool/API
and reproduction identity. Standard OpenGL Compatibility and Apple Metal do not
gain RGP support from sharing the Godot engine.

**Check.** Unsupported routes remain explicitly unsupported. On suitable hardware,
reproduce the implicated queue/pass and validate one intervention in a separate
ordinary run. Occupancy alone and one instrumented frame cannot establish a
whole-flight bottleneck or a sustained performance improvement.

## R15 — Apple Instruments: correlate CPU, Metal and display observations

**Evidence.** Apple's [Game Performance guidance](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-metal-app/)
combines system/thread, Metal, GPU and display tracks, with optional counters.
Its [GPU visual timeline](https://developer.apple.com/documentation/xcode/analyzing-apple-gpu-performance-using-a-visual-timeline)
shows overlapping work. [Signposts](https://developer.apple.com/documentation/os/recording-performance-data)
can distinguish task instances by ID.

**Decision — adopt native Metal recipe, S5/S6.** Reproduce an existing incident in
Instruments on the named Apple Silicon host. Record power/thermal state, refresh,
actual renderer and counter options. Native signpost integration remains conditional
S7; overlapping passes are not additive frame latency.

**Check.** Independently controlled CPU delay and graphics-load changes remain
distinguishable. Metal-specific analysis does not qualify the OpenGL fallback.
Retain ordinary-run evidence separately from counter-enabled captures.

## R16 — MangoHud: corroborate Linux behavior without changing it

**Evidence.** [MangoHud](https://github.com/flightlessmango/MangoHud) supports OpenGL/Vulkan
overlays and local logs; its vendor matrix identifies sensor differences.
The [configuration](https://github.com/flightlessmango/MangoHud/blob/master/data/MangoHud.conf)
also exposes logging cadence, FPS limits and presentation overrides.

**Decision — adopt optional Linux recipe, S5.** Keep version/configuration and original
log with the incident. Distinguish per-frame values from sampled temperature/power/load
context. Audit caps and present settings so the observer does not become the
intervention being mistaken for a simulator fix. No automatic public upload.

**Check.** Matched overlay-off/on cases record cadence, unavailable sensors and
overhead. Compare incident ordering at supported precision, not exact equality
between independently observed engine and overlay series.

## R17 — RenderDoc: can a post-hitch trigger recover the slow frame?

**Evidence.** RenderDoc's [in-application API](https://github.com/baldurk/renderdoc/blob/v1.x/docs/in_application_api.rst)
triggers capture of a subsequent presented frame. Its [capture options](https://github.com/baldurk/renderdoc/blob/v1.x/docs/window/capture_attach.rst)
describe interception/call-stack overhead.

**Decision — adopt escalation guidance, defer automation S7.** Keep the original
rolling incident and reproduce the relevant action with a targeted graphics capture.
Distinguish detected-frame ID from captured-frame ID. A trigger after the callback
resumes cannot retrospectively capture the completed slow frame; a permanent hang
cannot execute that trigger at all.

**Check.** An intentional CPU sleep followed by capture remains labelled subsequent
graphics evidence. Confirm the installed tool supports the actual backend, and
keep an ordinary run for timing comparison. Basic diagnostics stays usable without it.

## R18 — PIX and WPR/WPA: CPU activity, waiting or I/O?

**Evidence.** [PIX timing captures](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures)
offer CPU/context-switch/file/memory observations with option-dependent overhead.
[PIX graphics scope](https://devblogs.microsoft.com/pix/introduction/) centers on D3D12.
[Windows Performance Recorder](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/windows-performance-recorder)
collects ETW evidence for WPA analysis.

**Decision — adopt conditional Windows workflow, S5.** Use focused WPR/WPA traces for
unexplained waits/scheduling/I/O. Retain process/thread, symbols, clock and recording
configuration. Do not recommend PIX GPU analysis as the standard OpenGL route.

**Check.** A busy CPU loop and an intentional wait yield different interpretation.
Missing symbols or events remain limitations. Wall duration alone cannot classify
CPU saturation, and availability of native stacks does not imply GDScript stacks.

## R19 — Linux perf sched: off-CPU time is not all starvation

**Evidence.** The upstream [perf-sched manual](https://github.com/torvalds/linux/blob/master/tools/perf/Documentation/perf-sched.txt)
distinguishes run time, schedule-out/in wait and runnable-to-running delay.
[Kernel permission guidance](https://docs.kernel.org/admin-guide/perf-security.html)
explains that event access depends on system policy.

**Decision — adopt optional scheduler investigation, S5.** Keep incident IDs and
clock correspondence when collecting a focused trace. Do not call the whole
off-CPU interval scheduler contention: sleep, I/O and synchronization can also
produce it. Unavailable permissions mean missing evidence, not a clean scheduler.

**Check.** A controlled wait and separately controlled CPU contention are interpreted
using their different runnable-delay evidence. Do not silently alter host security
settings or claim displayed-frame timing from a scheduler trace.

## R20 — Python clocks: which timestamps can be subtracted?

**Evidence.** Python's [versioned time documentation](https://docs.python.org/3.11/library/time.html)
defines monotonic/performance counters, their unspecified reference point, integer
nanosecond variants and `get_clock_info()` properties. A high-resolution duration
clock is not a shared epoch with the engine.

**Decision — adopt clock contract, S1/S2/S5.** Use monotonic collector deadlines;
keep UTC descriptive. Store raw engine/collector domains and repeated request-send,
engine-observation and response-receive anchors. Preserve round-trip bounds and
mapping validity; a midpoint estimate has asymmetric-delay uncertainty. Restart
invalidates the mapping. The proposed engine stamp must be sampled during the
identified request; existing `sample_end_usec` may precede it and cannot supply
that bracket by itself.

**Check.** Wall-clock adjustment cannot extend a collection deadline. Delayed or
asymmetric replies widen uncertainty rather than create false precision. Preserve
integer timestamps within each format's exact bounds; never subtract unrelated origins.

## R21 — JSON Lines: useful long-run framing, not automatic durability

**Evidence.** The [JSON Lines specification](https://jsonlines.org/) requires UTF-8,
one valid JSON value per line and newline delimiters. It supports incremental
processing but does not define a capture schema, memory limit or crash guarantee.

**Decision — defer S7.** If longer campaigns require streaming, extend the client
with bounded session/frame/gap/completion records while keeping existing snapshots.
Specify byte/disk limits and incomplete-tail recovery before implementation. JSONL
is not required for the initial two-snapshot incident design.

**Check.** An interrupted final line preserves only complete preceding records and
marks incompleteness. Interior corruption is reported, not skipped silently.
Escaped newlines and Unicode round-trip; the absence of a completion record cannot
produce a fully covered/no-stutter verdict.

## R22 — Robust MAD: better anomaly label or misleading certainty?

**Evidence.** [NIST defines MAD](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/mad.htm)
as median absolute deviation from the median. Its scaled standard-deviation
interpretation assumes a distribution. The [outlier guide](https://itl.nist.gov/div898/handbook/eda/section3/eda35h.htm)
distinguishes candidate labels from identification and discusses assumptions.

**Decision — defer live changes, S3/S7.** Evaluate only an explicitly named offline
alternative against retained v1 flags. Declare window, phase, minimum samples and
zero-MAD fallback. Frame caps and correlated/multimodal timings invalidate a casual
normality assumption. No multiplier becomes a universal visible-stutter threshold.

**Check.** Constant pacing, isolated/repeated stalls, 30 FPS, 60→30 transitions and
loading must remain interpretable. Absolute budget failures persist when the
adaptive baseline settles. Never discard anomalies to improve the reported average.

## R23 — Google Benchmark: repeatability without importing a framework

**Evidence.** [Google Benchmark's guide](https://google.github.io/benchmark/user_guide.html)
supports warmup, repeated measurements, run statistics and randomized interleaving.
It motivates controlling changing system conditions; its microbenchmark API does
not establish an interactive flight qualification protocol.

**Decision — adopt method through existing tools, S4/S6.** Reuse GOD TEST and the
global plan's paired-run policy. Declare one intervention, keep comparable settings,
alternate order, retain per-run dispersion and separate instrumented modes. First-use
loading gets its own campaign; warmup exclusion must not erase the problem of interest.

**Check.** Incomplete or mismatched captures cannot become an unconditional gain.
No claim rests on one run or thousands of correlated frames treated as independent
replicates. Sources support the method; run counts and gates remain project policy.

## R24 — Perfetto buffers: which missing data invalidates the result?

**Evidence.** [Perfetto's buffer documentation](https://perfetto.dev/docs/concepts/buffers)
separates overwritten ring history, discarded new data and producer losses.
Streaming overwrite leaves a real gap; capacity and production rate determine
how much history survives.

**Decision — adopt completeness accounting, S2/S4.** Preserve R15's existing raw,
detail and log accounting. Add requested/observed coverage across snapshots, overlap
deduplication and gap reasons. Eviction before the requested interval is different
from losing part of that interval. A 7,200-sample ring has no fixed duration at
variable or uncapped frame rates.

**Check.** Delayed/repeated/out-of-order snapshots, restart and wrap produce precise
outcomes without fabricated callbacks. Missing coverage prevents a whole-interval
no-stutter statement. A permanent hang leaves timeout/last-observation evidence,
not invented frame durations or a successful recovery capture.

## Review and verification scope

Research used three independent topic groups, followed by lead source inspection
and integration. The lead independently checked the exact engine loop, GLES3 and
viewport source findings, existing branch code and metric/export semantics.
Independent review also identified concrete S2 constraints: summary windows do
not contain cumulative budget episodes; current transport buffers replies before
export validation; a two-snapshot union is not a valid v1 report; reused PID/clock
IDs do not prove session continuity; and last-frame timestamps cannot replace
request-time synchronization anchors. The plan incorporates bounded one-shot
collection, explicit sampled coverage, separate incident representation, receive
limits, verified launch identity and request-observation timestamps.
Sustained-budget screening additionally requires K−1 overlap between examined
windows (or equivalent boundary evidence); contiguous coverage alone can split
a qualifying K-frame run. Empty-window cursors use `frames_total`.
The plan's collector, manifest, comparison and capability extensions remain
proposals. Link/anchor checks and documentation review qualify this update only;
the original R15 test totals are historical and have not been rerun here.

Documentation verification on 2026-11-19: the staged change contains 11 Markdown
files and no runtime changes; R01–R24 are present exactly once with evidence,
decision and check sections. Using the repository's existing `check_docs` parser
and Git-object target resolver, all 46 introduced local links/anchors resolve.
`git diff --cached --check` passes. External sources were read for research;
this local link check does not establish third-party tool compatibility or runtime performance.
