### First-launch policy on main

On a fresh install the game starts at 1920 × 1080 when a window of that size fits a larger desktop. Smaller panels and Apple Silicon Retina displays use native borderless output. A saved window choice determines the pixel budget on subsequent launches. The current implementation does not yet apply the later monitor-fit clamp to that budget; A1-R4 owns this mismatch. Rendering and the 240 Hz simulation clock remain independent.

| Example at 1080p on Windows x86-64 with 12 CPU threads | Initial graphics |
| --- | --- |
| Desktop RTX 5090 | Forward+, Extreme scene detail, 8× MSAA, Ultra shadows at Far distance, High aircraft lighting and Many birds |
| Desktop RTX 3090 | Forward+, Extreme detail, 4× MSAA and the High renderer's standard shadow configuration |
| Desktop RTX 3060 | Forward+, High detail, 2× MSAA and Medium shadows |
| Identified lightweight hardware, including Intel UHD 630 | Standard on integrated graphics, Low scene detail, Simple trees and ground, MSAA off, projected aircraft cue, and minimal optional effects. The first launch explains how to raise settings individually. Compatibility can adapt from 75% toward 67% at a 30 FPS target. |
| Recognized software renderer | Low visual detail, fixed 75% Native scale and first-launch guidance. |
| Unidentified model | The same basic graphics at full 3D render scale, because the GPU may be fast |

GFX-IGPU-01 added fixed bilinear scale for Native reconstruction. Players can
choose 100–50% under Settings → Display. The stock UHD 630 Compatibility profile
starts at 75%. On eligible low-end devices with completed GPU timing, a fresh
profile can instead select a 30 FPS target with a 75–85% range. FSR, DLSS and
MetalFX manage their own scales. [Dynamic resolution policy](dynamic-resolution.md)

Recommendations use the shipped table offline. Public raster tests put a desktop RTX 3060 12 GB at about 0.50 and an RTX 5090 at 1.66 relative to the 3090 at 1080p Ultra. At 4K their ratios differ. OpenRC uses the estimates to order initial graphics choices. Its 3090 and M1 workload measurements, resolution, renderer availability and CPU floor constrain those choices. The 0.75 desktop floor for Extreme and 1.50 floor for maximum effects are provisional policy margins. [Raster measurements and methodology](https://www.tomshardware.com/reviews/gpu-hierarchy,4388.html)

Laptop entries have separate estimates. For example, measured Time Spy Graphics scores for 49 RTX 3060 laptops span 6,285 to 9,235 points. The table also distinguishes exact marketing names from ambiguous chip, workstation and unlisted families. Family-only names use basic graphics. A specific RX model takes precedence over its shared Mesa codename. [Laptop measurements](https://www.notebookcheck.net/NVIDIA-GeForce-RTX-3060-Mobile-GPU-Benchmarks-and-Specs.497453.0.html)

The display store remembers the last automatically applied value for each managed quality option. When the active GPU or renderer changes, the game updates those fields. Keeping a manual change releases that field. Existing files without ownership metadata retain their choices until the player keeps Restore graphics defaults. A successful Forward+ launch that reverses the recommendation falls back to Standard for that build. Explicit renderer restart recovery (F02/F15) and hardware qualification remain open. This build-wide latch is intentionally conservative; do not describe it as device-scoped recovery. The maximum-effects bundle is implemented but its A4 quality, memory and performance acceptance remains unresolved; the [current-main review](../research/visual-quality-implementation/VQ-07/automatic-graphics-main-review-2026-11-22.md#35-the-maximum-bundle-is-intentional-but-acceptance-is-inconsistent) distinguishes the documented policy change from missing qualification.

### 1.3 Weaknesses found

The current priority is bounded correctness, not another broad baseline campaign:

1. **Startup and player intent:** the original F01 reversal is bounded; F02/F15 still leave explicit or early failed restarts without a reliable recovery record. F14 still lacks a return to renderer Automatic. N01 budgets saved oversized windows before the actual fit clamp. F13/F16 are completed repairs, not pending implementation.
2. **Identity and confidence:** the original F04/F05 name/family cases are fixed, while F03–F06 retain variant-prefix, ambiguous legacy-key and model-memory gaps. The 5090 D V2 fixture receives base-5090 capacity and the maximum bundle.
3. **Measurement and application:** F07 persistence is repaired. F08–F12 still permit stale/mixed evidence, lack validation of the resulting tier, omit normal-completion viewport refresh and treat unavailable CPU/interval channels as nonblocking. Renderer, device, display and resource unknowns must stay unknown.
4. **Scope and explanation:** F17/F18/F20 remain open. F19's startup/Settings driver dependency is removed; only diagnostic enrichment remains synchronous. New rendered one-pass evidence identifies menu/loading stalls and M1 GPU pressure, without attributing a cause or qualifying the latest defaults.

The Compatibility and Forward+ fits reproduce their four points within about 5%. The Mobile row joins two points from different run sets, 1080p from the matrix and 4K from the knob benchmark. It has no residual, and it stays out of decisions until 720p and 1440p Mobile rows exist.

**How far the model extends.** For another GPU, the shipped High estimate divides the whole cost by `rel`. The fixed and per-pixel terms may scale differently. The 3090 runs at 450–700 fps, 5–17× under load, so its fixed term probably includes driver, queue and clock-state overhead that does not scale with raster throughput. Dividing that term by a small `rel` alone gives 8–19 ms for Iris Xe. The weak-GPU predictions below are **upper-bound-leaning and unvalidated** on the target device; the separate Linux container observation above is not a real-panel validation.

**The M1 check (DT-MAC-03b) supports that caveat.** Its 1.09 correction is fitted to these same measurements; it is an in-sample cross-check, not independent validation. Its 1080p frames give `rel` 0.059–0.061 on both renderers, now the row's correction. Across 720p, 900p and 1080p (L09, Mobile) its frame time fits 3.1 ms + 4.7 ms/MP within 0.08 ms. Against the 3090's Mobile terms the slope ratio is 0.047 but the fixed ratio 0.10: the M1's fixed share is 24% at 1080p, the 3090's 41%. Dividing the whole 3090 cost by one `rel` therefore overestimates the M1 by 1% at 1080p, 7% at 900p and 18% at 720p. The 720p run was close to CPU-bound, so its true GPU share is smaller still. This is one machine and the 3090's Mobile terms are interpolated, but it is the direction A4's refit (only the slope divided by `rel`) assumes. That refit needs its own per-row value: dividing only the slope would put the M1 at 0.047, not the 0.060 that matches its whole 1080p frame.

## 3. Renderer strategy (Forward+, Mobile, Compatibility)

Keep the shipped strategy and existing [Compatibility decision](../DECISIONS.md#compatibility-is-a-frozen-legacy-renderer) until a narrowly scoped change passes A2. Forward+ offers the High feature set where its **qualified** cost fits. Apple Silicon Standard uses Mobile/Metal; the short M1 evidence does not qualify other Mac configurations. Compatibility remains a supported renderer, a recovery target, the Intel/Rosetta Mac and other weak-hardware path where applicable, and a CI reference. It is not deleted or made fallback-only by this plan.

Mobile is a candidate, not a universal efficient renderer. It has a different feature set; the Intel Linux container comparison favors Compatibility, while the RTX 3090 and M1 measurements have different bottlenecks. Qualify renderer, driver, visual look and recovery on the actual supported class before changing a default. Keep a player's explicit renderer request separate from a temporary fallback. The project renderer keys, `.template` override and guard together form the core startup path.

### A2. Renderer strategy (Efficient = Mobile), behind measurement

**A2-R1 — conditional renderer experiment (medium or unknown ROI, platform-specific).** Do not adopt Efficient = Mobile by general rule. First retain Compatibility as the current weak-GPU path and use the Megatron result as a bounded counterexample. If a specific target presents a real performance or stability problem, compare Compatibility and Mobile on that target with its effective `use_hdr_2d` cost isolated, matching applied settings, frame pacing and visual review. The original Intel-and-AMD integrated-GPU and Windows visual gates remain open; the three hosts in §6 do not supply every one of them. Do not infer Windows or AMD results from a Linux container.
