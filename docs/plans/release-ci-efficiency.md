## 1. Assessment and priorities

The original direction is sound: local preflight, conservative change selection, superseded-run cancellation and separation of the frozen prototype. Four corrections are necessary:

1. A `.md` suffix is not proof of an irrelevant change. Timber and X8 source-delivery README files participate in hashed manifests. Use audited safe paths, not a global Markdown exclusion.
2. A successful report collection does not establish that every intended test ran. Make the expected roster and selected jobs explicit and verify their completion.
3. Optimize the critical path and total execution separately. Three successful October 30 runs took 100–123 minutes in visuals and 78–99 minutes in integration; unit jobs ranged from 13–34 minutes. More unit shards alone cannot fix the observed critical path.
4. Keep release identity and exact artifact verification. Current publication already promotes the export job's bytes without rebuilding within the same run. Reusing an arbitrary earlier main artifact is a different, currently unsupported provenance contract.

**First delivery:** PT1-CI-01 conservative scheduling plus PT1-CI-02 duplicate-check removal. Then partition visuals/integration and balance units using measured costs. Do not begin with a test-framework migration, custom distributed runner, automatic retry-until-green, or broad dependency-graph selection. Reuse Bash, Python, the checked runner, current capture checkers and pinned GitHub Actions; use the free `actionlint` tool for workflow validation with an exact recorded version.

## 2. Target event and gate policy

This is the target policy after PT1-CI-01 acceptance, not the current workflow. Keep one required aggregate check, proposed name **`CI required`**, which always evaluates the plan and results. Introduce it alongside existing checks first; inspect actual branch rules before changing required check names. Do not remove an old required check until the new one has run successfully and the rule migration is verified. Repository settings are a deployment step, not an assumption that YAML changes configure protection.

| Event/change | Production checks | Package/publication |
| --- | --- | --- |
| PR, or push to `main`, containing only explicitly audited documentation | Scope validation and document/content checks; report an explicit production skip reason | No automatic package; no publication |
| PR/main containing only website changes | Website checks from [site guide](../../site/README.md), including download/locale contracts; source/CI changes force full scope | No package unless packaging/release inputs also change |
| PR/main containing only frozen prototype changes | Prototype checks as a job in the same CI workflow; shared CI/tooling paths force full scope | No production package; prototype is no longer an unconditional product-release prerequisite after the explicit gate migration |
| PR containing any production, generated-source, toolchain, CI, unknown or mixed path | Full production software suite, including all unit, integration, native and visual gates, plus every affected site/prototype domain | No routine export; use an explicit full manual candidate run when packaging needs review |
| Push to `main` with production/unknown changes | Full production suite plus every affected site/prototype domain | Preserve candidate export after its native prerequisites; publication still off |
| `v*` tag | Full production suite regardless of diff | Full tag/version/notes preflight, export, package checks, verification and publication only after all required successes |
| Manual dispatch | Full production suite; no default skip option | Preserve candidate export; ordinary branch dispatch does not publish |

Limit ordinary push triggers to `main` and version tags; PR runs cover feature branches, avoiding push-plus-PR duplication. Cancel superseded PR checks only within that PR. Preserve main/tag/manual runs initially: a newer docs-only main commit must not cancel the last full production verification. Manual executions use unique groups. Serialize publication per tag; never use a global group that drops unrelated pending releases. Keep fork checks read-only and publication credentials confined to the trusted tag job. If merge queues are enabled, add and test `merge_group` before requiring the aggregate check there.

Keep the prototype as a normal job in the single workflow. The aggregate depends directly on that job and on site checks. This preserves a simple main-push workflow and avoids cross-workflow synchronization. Removing the prototype's unconditional production dependency remains gated by shadow evidence; no extra workflow is needed.

### Safe selection contract

- The six audited documentation candidates are listed in the [CI guide](../../tools/ci/README.md#current-ci-behavior). New local links and newly broken references within that set are checked against committed revisions. Other plans and skill guides stay full scope until individually audited: `research/fuel-systems/FUEL-00-R1/build_document.py` reads and hashes `docs/plans/fuel-mass-balance.md`, so even `docs/plans/*.md` is not a safe blanket exclusion. Do not allowlist `assets/**`, `app/**`, `research/**`, `docs/research/**`, release notes, notices/licenses, lockfiles or all Markdown by extension.
- Site-only and prototype-only classes need explicit dependency sets including their workflows, lockfiles and generators. Mixed changes select the union of affected domains, not a replacement production-only roster. A shared or uncertain dependency forces full production plus all potentially affected site/prototype checks. Tag/manual runs always include production; also select affected non-production domains, or both when their diff/dependencies are uncertain. Stage these classes only after documentation-only selection passes shadow validation.
- Use full commit IDs, NUL-delimited Git paths and `--no-renames` so both deleted and added paths are classified. For PRs compare the checked-out test merge commit against its first parent and record PR base/head/merge identities; confirm they match the event. If the merge commit is unavailable, force full scope. For main pushes compare event `before` to the checked-out `after`, not merely `HEAD~1` (multi-commit pushes matter).
- Missing history, a zero base, malformed event metadata, an unknown path or an empty/unexpected diff must not yield a cheap green result. Force full checks when comparison is unavailable; a classifier execution/validation failure blocks the aggregate. Fetch only the necessary history, preserving existing historical-source fetches.
- Produce a versioned selection receipt: source/event/base/head, classifier version, changed paths, required job IDs, selected case IDs and reasons. Treat it as data, never shell commands. The implemented v2 receipt independently revalidates source/event/base/head, paths and required jobs from Git; parse/unit case identity remains in separate roster receipts and complete runtime-case inventory remains open.
- The aggregate accepts only `success` for required jobs and exact required-case coverage. `skipped` is acceptable only for a job explicitly excluded by a valid receipt. Missing, failed, cancelled, incomplete or unexpectedly skipped requirements fail. Tags/manual runs must select the full production roster. Workflow-level path filters must not suppress this required check.

## 3. Reduce execution while preserving coverage

### One inventory, existing runners

PT1-CI-00/02 inventory each invocation by **command + arguments + environment + fixture/input identity + platform/backend + completion contract**, with owner and expected outputs. Preserve automatic discovery of `app/tests/test_*.gd`; new tests cannot disappear because a hand-written list is stale. Use one assignment source for both execution and fixed-brake history prerequisites. Timing data is only a scheduling hint: missing/stale timings must not omit new cases.

Remove only duplicates with matching contracts. The P-51, Timber and X8 generator checks repeated by the integration workflow and `app/test.sh` are initial candidates. Preserve checks unique to CI and full local `app/test.sh` behavior. Extract a small common source-check entrypoint rather than keeping diverging copies. If shared orchestration calls a phase once, give its callers an explicit phase contract; do not add an unchecked `SKIP_CHECKS=1` escape hatch.

Do not deduplicate helicopter tests by filename: the integration invocations pass independent `--oracle` inputs while ordinary units do not. Portable diagnostic tests and real-engine tests, and optional resource tests with pinned dependencies, are also distinct. Preserve negative controls and the two explicitly named physical-pending exceptions; do not broaden them. Keep expected-failure logs separate from positive checked evidence.

### Imports and dependencies

The integration job imports before schema probes and `app/test.sh` imports again. The former protects a fresh checkout. Retain it; remove the later import only after same-process orchestration or a validated receipt establishes the same checkout, engine, import inputs and successful completion with no intervening mutations. Other jobs/checkouts still import independently. Default standalone commands continue to import safely.

Cache verified downloads/dependencies by OS, architecture, exact engine/template/toolchain and lock hashes. Replace broad `.tools` caching with audited subpaths; never use a cache hit as a test or native-qualification result. Do not share mutable `.godot` imports, preferences or native build trees across concurrent jobs in the first implementation. Measure cold/warm setup separately before considering import artifacts. Keep pin upgrades out of this refactor.

### Integration and unit execution

Split integration into explicit phases: source/schema/offline checks, complete GDScript parsing, and runtime/CLI/trace/replay checks. Parse **every** application GDScript in the full suite; imports alone do not replace this. Each phase needs its dependencies, isolated outputs/profile and expected roster. Local `app/test.sh` without selectors still runs all phases and units. Avoid repeating source generation/validation in every shard.

Keep eight unit jobs initially. Assign discovered cases deterministically using descending measured duration and stable case-ID tie breaks, or retain modulo assignment if the gain is insufficient. Persist the assignment for the run; history prefetch and execution must consume it. A new expensive test gets a conservative estimate and still runs. Reject duplicate/missing assignments, invalid shard numbers and unexpected empty shards. Do not run multiple Godot tests inside a job until preference/import/native-DLL isolation is proven.

### Visual execution is the main latency opportunity

Profile the existing capture families before dividing them: core atmosphere/field/readability pairs, UI, vegetation/terrain, weather/ground cues and remaining visual-quality checks. Keep comparisons and their reference/candidate outputs together. `app/capture.sh` currently locks a shared output tree and writes a complete manifest only at the end; running several copies against that tree is invalid.

Partition by existing checker boundaries into independent checkouts and output roots. Keep one rendered process at a time per host. Each partition produces a source/engine/config-bound manifest with expected case IDs, verified image/trace hashes and completion. A final reducer rejects missing, duplicate, stale or mismatched parts and validates cross-family dependencies before writing the complete-set result. Local default capture remains the complete suite. Retain failure diagnostics even when aggregation fails; partial captures cannot become a success marker.

Preserve historical pixel baselines at their declared resolution. **1080p remains the primary product target**; include explicit current 1080p smoke/readability coverage using existing checkers, with higher resolutions secondary and 720p fallback. Changing the historical image size or reducing frame counts to obtain speed is not part of this scheduling work. Xvfb/llvmpipe results do not qualify GPU performance.

## 4. Release improvements

1. Run a cheap release preflight before expensive native/package work: tag grammar, project version, notes, exact source commit and pinned build prerequisites. Move the repeated tag-notes check out of all nine app partitions without losing tag coverage.
2. Keep export parallel with other checks once its native dependencies succeed. Publication must depend on the complete production aggregate **and** the successful export/package gate. Test a fast export with a later failing visual/unit job: no publication is allowed.
3. Preserve the six-file set, final archive inspection, source/input drift rejection, native receipts, independent commit/tag/run/repository expectations, remote peeled-tag check and `--verify-tag`. Verify published downloads against the same manifest. Use fresh staging and retain failed outputs; no in-place rewriting of release assets.
4. A publication retry first verifies whether a release already exists. A completed retry requires the identical manifest and six asset hashes, matching current peeled tag/commit, intended notes and expected published/draft and prerelease/channel state. Any missing/different bytes or metadata stop for investigation. Do not overwrite assets or silently promote a prerelease to stable. A version/channel change needs the correct tagged build.
5. Keep build and promotion in the same Actions run for this plan. Reusing a previous main build would require separate producer/promoter identities, qualifying event/commit/tag, immutable artifact ID/digest, successful required checks and retention handling. It is deferred; never edit the old manifest's tag/run fields to make it pass.

Do not skip main verification merely because a nearby tag run exists: pushes and tags may point at different commits and are separate workflow events. Initially accept this bounded duplication. Removing it requires an explicit trusted handoff design and evidence, not tag timing heuristics. Signing, installers and native-device acceptance stay with [desktop delivery](../DESKTOP-DELIVERY-PLAN.md).

## 6. Measurement, stopping rules and rollback

Use existing Actions step/job metadata, checked `report.json`/JUnit and capture manifests. Add only missing phase labels/timing summaries to the existing tools. Distinguish workflow elapsed time (including queue), critical-path execution, summed job execution minutes, setup/import time, artifact bytes, first failure and cancellation waste. Summed minutes are **not billed cost**; runner classes/multipliers and retries differ. Count expected/completed cases and defects caught, not merely test filenames or a green badge.

Provisional acceptance objectives, recalibrated after -00, are: documentation-only validation within 5 minutes without Godot/native/export jobs; at least **30% lower median full-run critical-path time** and **20% lower median summed execution minutes**, on five comparable baseline/candidate runs with equivalent full coverage. For retained eight unit shards, target slowest/mean duration at most 1.25. Report min/median/max and cold/warm cases; five runs do not establish a reliable p95. The October 30 runs orient priorities but are different commits, not a paired optimization baseline. No promised speedup or reduction in release qualification follows from this plan.

Keep a control mode that forces all production checks, and retain unpartitioned local defaults. A missing test, unjustified skip, changed diagnostic verdict, manifest mismatch or release dependency bypass triggers immediate rollback of the affected selector/partition change; keep full production gates on. Revert scheduling without changing physics goldens or accepting failed data. Do not auto-quarantine a failing test or accept its second successful attempt as clean evidence. If rebalancing saves elapsed time but increases total minutes beyond the agreed budget, retain the simpler schedule and record the tradeoff.
