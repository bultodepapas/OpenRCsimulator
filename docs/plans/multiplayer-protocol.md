# MP-01/02: protocol and first LAN delivery contract

**Owner:** MP lead with UI/SF/AFC owners. **Status:** proposed, unimplemented. **Updated:** 2026-11-17. The [multiplayer plan](multiplayer.md) owns product scope, effort and release gates. This document owns the candidate wire layout, adapter, state rules and first implementation slices. [Round-two research](../research/multiplayer-2026-11-15/round-2.md) records the initial design corrections; [round four](../research/multiplayer-2026-11-15/round-4-20-investigations.md) adds parser/transport findings, offline cases and material source drift at `08f948265d40d83fbb4726a302b9e1c9490ccfce`. Re-audit/pin the actual integration source, assets and backend before MP-01a. No provider dependency is needed for MP-01/02.

## 1. One adapter owner, explicit host routing

Add a proposed `MultiplayerSession` child owned by `AppRoot`, outside the replaceable flight subtree, with `PROCESS_MODE_ALWAYS`. It owns one standalone `SceneMultiplayer` and one ENet peer. Set the API's `root_path` to that live child's absolute `get_path()`, `server_relay = false` and `allow_object_decoding = false`; connect callbacks before assigning an already-created CONNECTING/CONNECTED peer. Manually call this API's `poll()` once per render `_process`. Do not register it with `SceneTree.set_multiplayer`, change tree-wide automatic polling, or also consume that peer with `get_packet()`.

This choice follows the pinned engine: [raw packets still require a root path](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L215-L216), [registered APIs are automatically polled](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/scene/main/scene_tree.cpp#L707-L712), and [default relay forwards guest traffic before application validation](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L260-L350). The standalone arrangement must still pass an exact-engine smoke check.

The owner also keeps local attempt generations, monotonic deadlines and owned async resources. Cancel invalidates its generation before cleanup; late completions may dispose only their own unadopted result. A timer/`await` is not worker cancellation. Retire pending controls and reject stale ACKs when changing connection generation. `PROCESS_MODE_ALWAYS` does not run while the main thread is blocked: measure poll gaps, reuse staged loading and leave before unsupported transitions. A sleeping/stalled owner that loses the connection must re-admit rather than flush old traffic. [Cancellation](../research/multiplayer-2026-11-15/round-4-20-investigations.md#30-cancellation-and-stale-async-completions) and [loading evidence](../research/multiplayer-2026-11-15/round-4-20-investigations.md#39-background-loading-does-not-guarantee-continuous-networking)

Resolve bounded host/port input before opening the peer; prefer separate fields and explicit `[IPv6]:port` parsing for pasted endpoints. Reject wildcard/empty remote hosts, invalid ports, controls and unsupported `%zone` suffixes. The pinned ENet connect path can block on DNS. Queued DNS must retain canceled/timed-out IDs until the lookup completes, then discard/erase: immediate ID reuse can misattribute the old result despite a UI generation guard. Bound retained lookups and keep numeric-IP joining available if resolution cannot be qualified. Preserve the original hostname for any future certificate check. [Pinned resolver evidence and test](../research/multiplayer-2026-11-15/round-4-20-investigations.md#25-endpoint-grammar-ipv6-zones-and-dns-cancellation)

Guests send only to transport peer **1**. The host binds each connection generation to one logical entity, validates ingress, then explicitly sends accepted application data to each intended recipient. Guests accept room state only from peer 1 and logical entities in the current host roster. Disabling relay also removes automatic guest announcements; the application owns its roster. Peer ID, room nonce and a cleartext invite capability do not authenticate an Internet host or encrypt ENet.

| Traffic | Logical channel | Transfer mode | Application rule |
| --- | ---: | --- | --- |
| Authentication before mutual completion | 0, selected internally by `send_auth` | Reliable | HELLO → ACCEPT → AUTH_ACK; separate from post-admission control IDs |
| Roster, configuration, baseline, status transitions, acknowledgments | 1 | Reliable | Bounded, idempotent control; apply before acknowledging |
| Pose, clock probes, repeating status/heartbeat | 2 | Unreliable, unordered | Per-entity sequence/revision checks; old data never overwrites new state |

Use explicit channel count **2 on both endpoints**. The [pinned ENet implementation](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/enet/enet_multiplayer_peer.cpp#L53-L104) adds its reserved channels; these application channels map to physical channels 2 and 3. Do not use one unreliable-ordered stream for several aircraft: a later packet for one entity must not discard another entity's useful sample. `peer_packet` reports sender and payload, not incoming mode/channel, so correctness must not depend on checking either in that callback. [Engine raw delivery](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L517-L527)

For two admitted pilots allow one admitted guest plus **one temporary admission slot**; for four pilots allow three guests plus one temporary slot. Permit one compatibility negotiation at a time, bounded to five seconds; additional pending applicants are refused. The extra slot permits a best-effort `ROOM_FULL` response without raising the pilot cap. If transport slots are exhausted, report a generic connection failure/timeout, not a supposedly received refusal.

Perform compatibility/capability exchange through `auth_callback` and `send_auth` on both sides, with `auth_timeout = 5.0`; use HELLO → ACCEPT → AUTH_ACK and call `complete_auth` only after the bounded exchange succeeds. The client sends AUTH_ACK through `send_auth` before completing; the host completes after receiving it, with no remaining auth payload to send. Do not require ordinary `send_bytes`/control ACK while authentication is pending: the engine permits only auth traffic, and [`send_auth` rejects further sends once either side has completed](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L457-L480). REFUSE uses a bounded auth-stage acknowledgment/grace period or is reported as best-effort. This is application admission, not a cryptographic identity claim. Do not wait for asset loading inside authentication. Explicitly clean up authentication failures, kick, close, cancel and timeout: [local disconnect signals can be suppressed](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L429-L437). Callbacks only queue/coalesce work; destructive teardown waits until `poll()` returns and is idempotent.

Bind wire freshness separately from local callback generation. HELLO carries a fresh 128-bit client `attempt`; ACCEPT echoes it and supplies the current 64-bit room incarnation, assigned entity and fresh 128-bit host `connection` nonce; AUTH_ACK echoes the attempt/connection/room. Retain these as pending until local authentication completes; manual joining needs no earlier directory metadata. Use checked cryptographic randomness and strict 32-hex attempt/connection encodings, distinct from the secret invite capability. Validate the expected challenge/context at each phase. Every post-auth JSON frame, including ACK, clock and heartbeat, carries the current room and connection context; the host rewrites the connection context for each forwarded recipient. A local generation token alone cannot distinguish old wire bytes delivered on a new peer. Binary poses retain their 128-byte layout: fresh assigned entity IDs are never reused in a room, ownership is connection-bound, and a current baseline/epoch/sequence is required before motion. Test repeated reconnects and replayed old controls/ACKs/poses; these public nonces provide freshness separation, not authentication against an active plaintext attacker. [Reconnect rationale](../research/multiplayer-2026-11-15/round-4-20-investigations.md#31-reliable-transport-is-not-an-applied-control)

Use separate monotonic phase deadlines, without progress-based extension: proposed DNS deadline **10 s** inside an overall **30 s pre-connect deadline** (including any later DTLS setup), then **5 s application authentication**, then **120 s initial data/loading-to-READY deadline** from local admission. The engine auth timer starts after transport connection; it does not bound DNS/DTLS. Reserve the admitted slot and allow an initial **10 s peer-activity confirmation grace**, included inside the 120 s loading budget: the other endpoint may receive the final channel-0 completion later. Send `SESSION_HEARTBEAT` immediately on local admission and repeat once per second. Before first fresh, context-valid, phase-legal post-auth traffic from the peer, send only this heartbeat, with no ordinary control IDs/ACK deadlines or pose backlog. Receiving that first valid frame confirms remote activity and starts the usual five-second liveness detector; it may be a heartbeat or a fully valid initial ROOM from a peer that confirmed first. Ignore stale/invalid frames without extending grace. Gate subsequent outgoing controls on this confirmation, preventing a ROOM timer from expiring while the other end is still awaiting auth completion.

`SESSION_HEARTBEAT` carries room/connection/its own sequence, no fabricated entity epoch or pose, and never implies READY. Validate freshness using the modular sequence rule below. Keep its 1 Hz repetition through initial loading/READY; afterwards use it only as an idle fallback when no other traffic known valid for the recipient's phase has been sent in the preceding second. Sending a future-epoch pose that the receiver must drop is not liveness evidence. A healthy >5 s asynchronous load can remain live within its 120 s limit; a blocked owner still fails the five-second steady-state detector. Deadlines execute only when the owner can run. Qualify a final auth completion delayed by 4.5 s, immediate/dropped first heartbeats, manual joining without prior room metadata, and cancel/late completion at every phase.

## 2. Candidate snapshot v1: exactly 128 application bytes

This layout supersedes the original 2026-11-15 **proposal**; no shipped protocol is being changed. All numeric fields are little-endian. The room incarnation is now 64 random bits, compared as two `u32` values, and the configuration revision moves into a 48-byte header. The application size remains 128 bytes. [`send_bytes`](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L439-L455) adds one Godot command byte; transport headers, acknowledgments and control traffic are additional.

| Offset | Field | Encoding / rule |
| --- | --- | --- |
| 0–1 | Magic | Bytes `4f 52` (`OR`) |
| 2 | Protocol major | `u8`, 1 |
| 3 | Message kind | `u8`, 1 = pose |
| 4–5 | Header flags | `u16`, zero in v1 |
| 6–7 | Header length | `u16`, 48 |
| 8–15 | Room incarnation | Low then high `u32`; random per new host room, never an authentication token |
| 16–19 | Entity ID | `u32`, host-assigned, nonzero, never reused in that room |
| 20–23 | Flight epoch | `u32`, host-accepted generation, no wrap within a room |
| 24–27 | Sample sequence | `u32`, per entity and epoch |
| 28–31 | Configuration revision | `u32`, must equal the accepted room revision |
| 32–39 | Accepted sample room time | `i64` microseconds, relative to host process monotonic origin; may be negative for an old paused sample |
| 40–47 | Accepted simulation tick | `u64`; high bit zero; no restamping a repeated tick |
| 48–71 | Fixed body datum O position NED | Three `float64`, metres; not the changing live CG |
| 72–87 | Body→NED attitude | Four `float32`, **w,x,y,z** |
| 88–99 | Datum O velocity NED | Three `float32`, metres per simulation-second; rotate accepted O body FRD velocity before encoding |
| 100–111 | Angular velocity body FRD | Three `float32`, rad/s |
| 112–119 | Surface positions | Four `int16` centidegrees: right aileron, left aileron, elevator, rudder |
| 120–123 | Propeller RPM | `float32` |
| 124–125 | Throttle | `u16`; accepted normalized throttle command associated with this tick × 65535, nearest integer with positive half upward; decode = encoded / 65535 |
| 126–127 | Presentation flags | `u16`, zero until an approved model/protocol revision assigns bits |

Surface values are **trailing-edge angles**, not model-axis hinge rotations. Capture [`FlightSession.surface_angles_deg()`](../../app/sim/flight_session.gd); apply [`ControlSurfaces.hinge_rotations_from_surfaces`](../../app/physics/control_surfaces.gd) at the visual boundary. Quantize centidegrees by nearest integer, half away from zero, after validating the admitted aircraft's throws. For throttle, first require finite input in `[0,1]`, then `floor(input * 65535 + 0.5)`; do not clamp malformed inputs. Thus 0, 0.5 and 1 encode as 0, 32768 and 65535.

These are rendered servo-derived angles. Aerodynamic out-of-trim rigging can add offsets separately; disable it in the first approved stock fixture and qualify any later representation. The throttle field is an accepted command, not a claim of effective engine output; do not attach a later mutable input to an older pose. Prove pose/aux/surface/throttle coherence for one accepted tick and generation on the actual backend. [Current source distinctions](../research/multiplayer-2026-11-15/round-4-20-investigations.md#current-repository-repeat-the-integration-audit-before-mp-01)

Position and linear velocity refer to the **fixed body datum O**, defined at the authored reference-state CG; a live fuel CG or the CG at a selected starting fuel fill can differ. Use the accepted body state directly, rotate O velocity into NED, and apply the constant authored model offset through [frame conversion](../../app/render/frames.gd). Legacy helper names/comments mentioning CG do not authorize a live-CG translation. [Source evidence and fixture](../research/multiplayer-2026-11-15/round-3-20-investigations.md#17-flight-logs-ghosts-and-the-correct-aircraft-datum). Never copy a companion's solver/session to represent a remote plane.

The [research vectors](../../research/multiplayer/packet-vectors.json) provide exact synthetic bytes, malformed records and separate sequence/context/quantization cases for an independent MP-01a Godot implementation. They are not an implemented decoder or a passed admission test. Use explicit field widths and byte order, for example a bounded `StreamPeerBuffer` with `big_endian=false`, and check total length before any read. Match pinned-engine results to the vectors/manual anchors; do not use Variant/object serialization as the wire format. [Codec references and generator](../research/multiplayer-2026-11-15/round-3-20-investigations.md#18-binary-codec-references-and-delivered-vectors).

Decode into detached temporary data, validate the whole record, then commit to the replica. Initial outer guards are absolute NED coordinates ≤100,000 m, each velocity component ≤1,000 m/s in magnitude, each body angular-rate component ≤100 rad/s, RPM within 0–250,000, quaternion norm within 0.99–1.01 before normalization, and the approved model's surface limits. These broad engineering caps are not a flight envelope; MP-01a must tighten them for the selected field/aircraft and retain a valid extreme-motion trace. Reject wrong length/magic/version/flags/revision, nonfinite values, illegal IDs and invalid render conversions; do not clamp malformed state into plausibility. No peer-controlled resource paths or engine-object decoding.

## 3. Control, ordering and lifecycle

The proposed control framing is the same four-byte magic/major/kind prefix with kind **2**, followed by UTF-8 JSON, at most **1,024 total bytes**. Authentication frames use the same bounded envelope. Before engine conversion/parsing, validate strict UTF-8 without replacement, reject a leading BOM/raw NUL, and scan JSON grammar, valid escapes/surrogates, decoded-key uniqueness, no decoded NUL and container nesting ≤4 (root object = 1). Consume exactly one object plus permitted whitespace; a regex or post-parse dictionary check is insufficient. Godot's pinned parser overwrites duplicate keys and accepts some nonstandard input. Then validate allowlisted fields, finite numbers, array bounds and exact integer ranges in detached data. [Source and proposed oracle cases](../research/multiplayer-2026-11-15/round-4-20-investigations.md#27-strict-control-json-before-godot-parsing)

Names must be nonempty and at most 32 **decoded UTF-8 bytes**; serialized escaping also counts toward the envelope. Render them literally in separate plain-text controls from trusted status/IDs; do not treat display names as identities. Pin the [international-name policy](../research/multiplayer-2026-11-15/round-4-20-investigations.md#28-international-player-names-and-literal-ui) during UI/schema review. IDs/revisions are `u32`, while microsecond/tick values use validated decimal strings (time may be signed; tick is nonnegative). Represent a room incarnation as 16 hex characters. The [size fixtures](../../research/multiplayer/control-budget.json) compare candidate shapes/encodings, including over-limit messages; they do not finalize schemas or establish valid admission. MP-01a must supply exact schemas, per-family rate bounds and golden **Godot-encoded** bytes before networking is enabled. Keep each BASELINE bounded and separate; do not bundle all room poses or silently enlarge the envelope for eight pilots.

| Message family | Required meaning |
| --- | --- |
| `HELLO`, `ACCEPT`, `AUTH_ACK`, `REFUSE` | Build/protocol/content identities, attempt/connection freshness exchange and optional capability; assign room/entity only through host admission. A refusal is best-effort and bounded, never an indefinite pending connection |
| `ROOM` | Host roster, approved content and configuration revision; transport connection alone does not create a visible aircraft |
| `BASELINE` | Entity, new epoch, current status/revision and a base64-encoded complete 128-byte pose; validate atomically before showing or replacing history |
| `ACK`, `READY` | Acknowledge applied reliable control IDs. READY requires local loading and all required room/baseline data; no remote message resumes the local controller |
| `STATUS`, `HEARTBEAT` | Per-entity epoch, status revision, ACTIVE/PAUSED/DEGRADED state and last accepted sample identifiers; reliable PAUSED includes a final full pose; heartbeat also has its own sequence |
| `SESSION_HEARTBEAT` | Post-auth direct-connection liveness before a baseline or during otherwise idle preparation; room/connection/sequence only, never a READY or aircraft-state claim |
| `CLOCK_PROBE`, `CLOCK_REPLY` | Outstanding probe ID and four-timestamp exchange; no semantic ACK required |
| `LEAVE`, `REMOVE`, `KICK` | Host-controlled roster removal or a guest's request to leave; explicit local cleanup does not depend on receiving a final packet |

Reliable controls carry a contiguous control ID starting at 1 per directed connection generation, except ACK itself. The host assigns separate streams for each recipient; renew the generation before ID wrap. Accept only the next expected ID; an already-applied ID cannot mutate state, and a gap is a protocol failure with bounded teardown. Do not rely on the unseen transfer mode to impose order. Authentication, probes and heartbeat sequences are separate. Keep at most eight unacknowledged controls and 64 KiB of unacknowledged application data per peer; the eight ≤1,024-byte framed controls themselves occupy at most 8,192 bytes. Five seconds without required ACK fails the transition. Reserve the pending entry/ID before invoking the adapter; a send failure fails the generation without leaving a sequence hole. The pinned high-level ENet send ignores lower-send results, so `OK` does not even prove local queue acceptance. [Send-path evidence](../research/multiplayer-2026-11-15/round-4-20-investigations.md#24-throttle-send-results-and-bounded-backpressure)

On receive, atomically commit the operation and next expected ID before notifying observers, then ACK its successful application; an applied duplicate may be re-ACKed without mutation. Unknown/stale ACKs follow the bounded schema policy. ROOM is applied/ACKed after its own validated roster/configuration commit, **without waiting for baselines or READY**. Only then send its dependent BASELINE controls; READY additionally waits for local load and all required baselines. Otherwise the dependency barrier can deadlock. Capacity refusal must not create an unbounded retry list. [Reentrant-ACK cases](../research/multiplayer-2026-11-15/round-4-20-investigations.md#31-reliable-transport-is-not-an-applied-control)

State-transition STATUS is reliable; HEARTBEAT repeats its latest revision unreliably once per second for **application state/liveness**, not as a generic NAT keep-alive recommendation. Measure aggregate ENet ping/probe/status traffic and false timeouts before Internet qualification; add no separate NAT refresh loop without evidence. Initial pose ingress allowance: 30/s with burst 10 per admitted guest; control/probe/heartbeat allowances must be separate and bounded in MP-01a's schema fixtures.

For pose sequences within the same entity/epoch, calculate `d = (new - old) & 0xffffffff`; accept newer only when `0 < d < 0x80000000`. Equality is duplicate; half-range is ambiguous and refused. Apply a maximum forward jump of 10,000 samples before requiring a fresh baseline. Flight epochs/config revisions do not wrap: recreate the room before exhaustion. Every new connection gets a local generation token; stale callbacks cannot mutate a new session even when an engine peer ID is reused.

Drop unknown future-epoch poses until their reliable baseline is accepted; do not accumulate them. Baseline acceptance clears interpolation history atomically. A late join receives each current entity's baseline and status, including an old, intentionally paused pose; it does not wait for another physics tick. Status revisions are scoped to the flight epoch. Old pause messages and old heartbeats cannot override a newer status or new flight. Repeating status changes neither the original pose timestamp nor simulation tick. A PAUSED heartbeat or transition immediately freezes the current display and prevents same-epoch pose traffic from moving it. The reliable PAUSED transition carries the final full pose: allow exactly one atomic final correction for that status revision, even if its heartbeat arrived first, then retain it for late join. Duplicate controls or delayed ordinary poses cannot apply another correction. Only a newer epoch/baseline after successful local resume reopens motion; DEGRADED continues accepting fresh poses but cannot extrapolate.

[`FlightSession.resetting`](../../app/sim/flight_session.gd) also occurs for restore/configuration. Inspect `last_transition().kind` and `.generation`; only a committed `TRANSITION_START` authorizes the reset baseline. Record the receipt in the synchronous callback, then capture/send after the protected transaction and tick-zero publication. A refused reset creates no new epoch. A postcommit observer fault still belongs to the new flight but remains paused. Resume gets a fresh epoch/baseline only after existing local resume succeeds. Unsupported restore, Workshop or configuration changes leave the room through the existing recorder/save flow.

An accepted crash can emit `paused_changed` from FlightSession's earlier `stepped` observer before the network tracker records that tick. Queue/coalesce pause/status there and reconcile only after the complete step/publication stack and tracker update. The final PAUSED correction must use the crash's accepted tick and preserved observed acceptance time, never a previous tracker sample with a fresh timestamp. Include `events_located` ordering, refused ticks and committed-but-faulted tick-zero publication in the fixture. [Pinned current-source ordering](../research/multiplayer-2026-11-15/round-4-20-investigations.md#current-repository-repeat-the-integration-audit-before-mp-01)

Keep direct transport liveness, host-owned membership and per-entity presentation freshness distinct. The host times each directly connected guest; a guest times only its direct host connection. Five seconds without fresh valid direct application traffic closes that connection. The host removes a silent guest and sends authoritative REMOVE to the others; a live host heartbeat cannot refresh another guest's own status/pose evidence. A guest may freeze/mark another aircraft stale, but never edits the host's roster merely because forwarded data stopped. An active pose stale for 500 ms is marked stale; a live intentional pause remains frozen beyond five seconds. Host loss ends the room and invokes the existing safe local hold with explicit offline continuation. Operating-system sleep stops the network owner too. Exercise three processes with host and guest A live, guest B silent, and A receiving only host traffic.

## 4. Time, interpolation and bounded work

Retain 240 Hz local physics. Attach the lightweight accepted-time tracker before the flight's first accepted start, including tick zero. Do not admit a pre-existing flight whose last accepted wall time was never observed: use the existing safe Home/start flow to obtain a fresh accepted sample. Never infer acceptance time from simulation tick or join time. Synchronous accepted-step callbacks may record bounded tick/time/transition bookkeeping and the required detached accepted input scalars; they do not encode, send, call providers, modify physics or reenter transitions. At the 20 Hz monotonic send deadline, copy the latest completed accepted state outside the solver transaction and prove its generation/tick matches the retained input metadata. Preserve its acceptance timestamp; never call an old state fresh because it was sent again. Send one latest state and skip missed deadlines after a stall. Use independent full snapshots and explicitly disable ENet compression for this initial measurement baseline.

With guest timestamps `g0,g3` and host timestamps `h1,h2`, estimate host-minus-guest offset as `((h1-g0)+(h2-g3))/2`; corrected RTT is `(g3-g0)-(h2-h1)`. Match outstanding probe IDs, reject negative/over-two-second RTT and impossible host processing intervals. Start with eight probes at 4 Hz; require at least four valid replies within five seconds, then probe at 1 Hz using the lowest-RTT sample in the last eight. With stable clock rates and nonnegative one-way delays, midpoint offset error can range within ±half the corrected RTT; a symmetric path has zero asymmetry error. Report a conservative uncertainty interval of at least ±RTT/2 plus drift/measurement allowance. This is an estimate under stated assumptions, never proof of one-way delay.

Define the room clock as the host's monotonic microseconds since process startup; do not rebase it when creating a room. `h1/h2` use that origin, and the room incarnation distinguishes restarts. An old guest sample can map before host startup, so the snapshot time is signed `i64`; do not restamp it. Bound clock values and mapped sample times to magnitude below `2^52` microseconds before arithmetic, with nonnegative local probe clocks and overflow checks. This is an implementation guard, not a promise of century-long sessions. Clients stamp accepted sample time using their mapping to the host's room clock; the host preserves that timestamp on forwarding. The receiver maps its own playback target into that clock. Bound active sample timestamps at host ingress to `[host_receive_time - 1 s, host_receive_time + 100 ms]`; do not apply the age lower bound to a legitimate paused baseline or its validated final PAUSED STATUS pose for the current epoch/revision; keep future-time, ownership and one-final-correction checks. A timestamp behind the prior accepted sample or a clock-offset correction >50 ms enters resynchronization: freeze presentation, clear timing history and obtain a fresh clock/baseline before resuming. Smaller changes must not make playback or emitted sample times move backward. Record raw offset, RTT, chosen sample and uncertainty so failures are diagnosable; MP-01c must demonstrate monotonic mapping under bounded corrections.

Start with **200 ms render delay**, linear position interpolation and normalized shortest-path quaternion slerp. **Extrapolation starts disabled.** When the playback target is newer than the newest sample, hold that newest sample. At startup/rebaseline, when the target precedes the earliest buffered sample, retain the first accepted baseline (or remain hidden until ready), not the newest arriving pose. Interpolate only within a same-epoch bracket; never advance to future samples and then move backward when delayed playback catches up. Any later extrapolation is separately qualified, lasts at most 100 ms and cannot multiply simulation velocity by wall time without a demonstrated timing policy. Short stalls can precede DEGRADED detection; include them in the fixture. The previous 100 ms target leaves no bracketing margin on a symmetric guest→host→guest path with two 100 ms RTT legs. At 20 Hz, allowing +20 ms one-way jitter on each traversed leg gives a loss-free worst assumed requirement of 100 + 40 + 50 = **190 ms** before clock error or processing. This is arithmetic, not network qualification; keep gate B's age/error reporting and retune only from evidence. [Reproducible calculation](../../research/multiplayer/capacity_model.py)

Measure simulation/wall-time ratio only over active windows, clearing across pauses/epochs. Below 0.95 over two seconds marks DEGRADED; require two consecutive healthy windows before clearing. PAUSED/DEGRADED replicas never extrapolate. Use shortest-path quaternion interpolation. Keep 64 detached samples per entity and one latest unsent pose per entity/recipient.

Shortest-path slerp can alias fast turns or widened loss gaps. The [analytical rotation cases](../../research/multiplayer/rotation-sampling.json) include a 286.48° true rotation represented by a −73.52° shortest path, within the broad rate guard; this is not a measured aircraft limit. MP-01c must qualify recorded stock motion, timing/slowdown and missing-sample gaps against delayed truth, including a π tie. Endpoint rate checks alone do not bound the intervening path. Define a qualified maximum gap with freeze/stale behavior or revise rate/representation if the motion target fails; do not infer success from normalized endpoints or extra render delay. [Experiment and limits](../research/multiplayer-2026-11-15/round-4-20-investigations.md#38-fast-rolls-can-alias-between-valid-quaternion-snapshots)

These limits bound application-owned data. They do **not** bound ENet reassembly, SDK queues or Godot's drain-all `poll()` work under hostile input. [Pinned polling source](https://github.com/godotengine/godot/blob/cafc17a192acf67903910a68aeb3c076c0907a4b/modules/multiplayer/scene_multiplayer.cpp#L69-L166). Public stranger rooms require separate transport-level size/rate/work limits and adversarial measurements; `max_sync_packet_size` is not a raw-packet firewall. MP-02 is a friendly LAN qualification.
