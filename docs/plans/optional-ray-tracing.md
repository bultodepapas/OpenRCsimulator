## 1. Outcome and instructions to the executing agent

Implement an **optional hybrid ray-traced sun-shadow feature** while preserving the existing raster renderer, flight behavior, settings, and recovery paths. Rasterization continues to produce primary visibility, materials, sky, transparency and UI. Replace only the selected sun's geometric visibility on qualified receivers. First prove deterministic hard visibility; then add finite-sun soft shadows and their denoising. The first player-facing release requires a measurable benefit during an ordinary fixed-wing flight, not merely a successful triangle query or a showcase screenshot.

This is a quality feature with a cost budget. Existing native PCSS already produces soft shadows. Do not promise that RT improves frame rate, fixes unrelated stutter, or makes every scene more realistic.

### 1.1 Execution rules

1. Execute the phase dependency order in section 7. Finish each subphase's specified proof before treating its output as an input to the next dependent subphase. Independent source-only work may proceed in parallel; GPU measurements may not share a host with another benchmark.
2. At task start, compare the working revision with this baseline. Re-read changed integration files and the current repository rules. Record a concise drift table; do not silently apply old line numbers or cherry-pick a whole research branch.
3. All new paths, interfaces and commands explicitly labeled **proposed** below are work to implement. They do not exist merely because this plan names them. Existing commands must be checked against their owning README before execution.
4. Preserve `app/sim/`, `app/physics/`, the 240 Hz fixed step, float64 state, RK4 order, input sampling, aircraft data, collision queries and replay semantics. Rendering consumes already displayed transforms. Do not change these systems to recover an RT budget.
5. Never promote `source-reviewed`, `compiled`, `submitted`, `GPU-completed`, `image-correct`, `performance-qualified`, and `package-qualified` into one interchangeable status. Record each separately.
6. Keep the ordinary official build usable. Build custom editors, templates, imports, caches and player profiles in isolated, named locations using existing intake/packaging patterns. Do not point the production import cache at another engine.
7. Keep RT off by default, including Automatic graphics and Restore graphics defaults. A saved request is distinct from effective execution. Unsupported or failed requests use the existing raster result and retain the user's saved request.
8. If a prerequisite fails, repair that prerequisite within its phase. After two materially different failed approaches to the same gate, write the counterexample and a bounded follow-up; leave that capability blocked and continue independent work. Do not replace the renderer, adopt a new engine fork, change SDKs, or lower acceptance thresholds to escape a failed gate.
9. A blocked hardware row is not a pass. Complete available source, unit, image, package and other-device work; leave the unavailable row explicitly unqualified. Do not extrapolate from an RTX 3090, an M1 diagnostic, software Vulkan, or CI to an untested device.
10. Every implementation commit must name its phase/subphase, changed boundary, verification and unresolved gate. Stage only assigned paths. Do not import historical logs, engine binaries or unnecessary images into Git.
11. Core work is phases 00–15, with the mode-specific dependencies in section 8: Hard can complete without 10–11; Soft additionally requires them. Phases 16–18 extend the qualified matrix independently. Phase 19 closes the delivered matrix and remaining gates. The effects in section 10 are excluded from this execution unless separately commissioned.
12. This planning change adds documentation only. It does not authorize claims that the proposed code, tests, APIs, hardware support or performance results already exist.

### 2.3 External research decisions

Primary references and firsthand issue reports are indexed in Appendix C. The implementation decisions are:

- Use **Vulkan ray queries** for binary sun visibility. They execute within compute/graphics shaders and do not intrinsically require a ray-tracing pipeline/SBT; the latter is a limitation of the inspected Godot API path, not a Vulkan requirement. Enable the actual AS/query feature chain and respect the selected device's limits.
- Prefer the **FidelityFX shadow denoiser** for the first soft-shadow candidate. Its documented contract uses a 32-bit visibility mask for an 8×4 tile and at most one jittered ray per pixel. Implement its real signal conventions rather than feeding it an arbitrary grayscale image.
- Keep **NRD SIGMA** as a documented alternative, not a second parallel integration. Its occluder-distance/penumbra contract differs from binary visibility, and its NVIDIA RTX SDK license is not MIT. An arbitrary first hit is not an adequate closest-distance input. A change of denoiser requires an explicit design update and renewed input/license review.
- Do not use **DLSS Ray Reconstruction, FSR Ray Regeneration, or MetalFX temporal denoised scaling** as a generic shadow-mask filter. They have different radiance/guide/backend contracts; an installed upscaler does not satisfy them.
- On Apple, distinguish **Metal RT API support** from hardware acceleration. `supportsRaytracing` alone does not imply dedicated RT hardware; Apple family 9 introduced hardware-accelerated intersectors. M1 API experiments remain useful evidence without becoming a hardware-RT performance claim.
- Treat community forks and issue reports as implementation leads. Confirm consequential claims in the pinned source and an actual native fixture. Do not replace the pinned application engine with a complete path-tracing fork.

### 3.2 Proposed engine ABI

The following names are **new interfaces to implement and document**, not current Godot methods. Use a versioned ABI, `openrc_rt_sun_v1`; reject a different version rather than guessing method compatibility.

| Interface | Contract |
| --- | --- |
| `RenderingServer.get_openrc_rt_sun_capabilities()` | Immutable typed facts for the active rendering device: ABI, driver/backend, enabled AS/query/pipeline features, limits, supported sampling/receiver modes, build identity and explicit reason codes. Unsupported official builds are detected through `has_method` before any call. |
| `viewport_set_openrc_rt_sun_request(viewport, sun, request)` | Copies a validated request and world generation to the render owner. It cannot mutate simulation or user preferences. A request is not an execution receipt. |
| `viewport_get_openrc_rt_sun_status(viewport)` | Bounded snapshot: requested/effective state, fallback reason, world/view/sun/history generations, submitted/completed frame IDs, admitted coverage, AS/trace/denoise counters and bytes. Unknown measurements remain unknown. |
| `viewport_reset_openrc_rt_sun_history(viewport, epoch, reason)` | Idempotent history invalidation scoped to the current viewport/world. A stale epoch cannot reset a replacement world or confirm a newer activation. |
| `viewport_release_openrc_rt_sun(viewport, epoch)` | Stops future RT submissions immediately and retires GPU resources after their last dependent completion. Repeated release and late callbacks are safe. |

Keep per-frame data inside native renderer structures. Do not serialize mesh arrays, large Dictionaries or JSON across this ABI every frame. Application-side event metadata must be copied before crossing to the rendering thread; no SceneTree traversal from a render callback.

### 3.3 Scene and acceleration-structure contract

1. A world has a monotonic `world_epoch`; a viewport has a separate lifetime/generation. Every geometry, instance, material, AS and history record carries its owning epoch. Object IDs alone are insufficient because IDs/resources may be reused.
2. Identify reusable geometry by mesh resource plus surface, topology/vertex/LOD generation, facing policy and caster-material variant. Share a BLAS across rigid instances of identical geometry. Deformed instances share only when their actual output geometry is proven equivalent at the used precision; source mesh/material equality is insufficient. Distinct hinge parts use the actual visible articulation transforms; rigid movement alone does not rebuild their vertex data.
3. Static geometry enters once during staged preparation. Maintain dirty sets for transforms, topology, deformation, material/alpha, visibility, LOD, instance count and layer/cull-mask changes. A normal RT-off flight never populates these sets through an RT-specific scene walk.
4. Use engine-owned scene/storage information and the same native caster rules as the selected sun. **Race-free age publication.** The classifier must treat the current R32 key image as read-only; writing age bits while another invocation reads the full key word is a race even if its low bits do not change. A zero low key forces the whole word to zero; a nonzero age paired with zero key is an invalid producer record. A valid low key with age zero may retain current-shading identity but is ineligible for future history. No other invocation reads or writes that texel during finalization. Add the explicit classifier-read/write → finalizer-read/write → filter/lighting/next-history-read graph dependencies, including actual queue/image transitions. This dispatch adds cost, not another image. T03/T09 poison the reused moment parity and exercise every shortcut, key-zero, age-zero/31 and inter-workgroup/in-flight case so a stale t−2 `.w` cannot masquerade as a valid update.

**Bounded FP16 moments.** Exact age is independent of FFX's fractional, damped sample count. Initialize rejected/new samples with current visibility, M2 zero, count one and age one. Accept history only if every prior tap age is 1–30; set the new age to `1 + max(prior ages)`. An age-31 tap rejects history and restarts from current data. Thus no accepted chain exceeds 31 submissions. All homogeneous/early-out paths write a consistent initialized record and age or mark the pixel invalid; none bypasses the cap. Keep stock FFX mean/M2/count update, count damping, history clamp, variance boost, filter and contrast remap for accepted histories.

Compute unboosted `M2/(count-1)` only when the updated undamped count is strictly greater than one; initialized count-one samples use variance one without division. A nonpositive denominator, variance outside `[0,1]`, nonfinite value, or damped updated count ≤1 rejects history and reinitializes the current sample. Fractional damping can otherwise place nonzero M2 over an arbitrarily small denominator; the age cap alone is insufficient. For each pixel occurrence, set `L=certainly_lit/n`, `U=1-certainly_blocked/n`; ambiguous samples contribute `[0,1]`. Let candidate visibility be c and `Y=max(abs(c-L),abs(c-U))`, with unbiased sample variance v over K occurrences. Calculate:

```text
B1 = sqrt(2*v*ln(2/delta)/K) + 7*ln(2/delta)/(3*(K-1))
U_MAE = min(1, mean(Y) + B1)
```

Require **`U_MAE <= 0.02`**. Retain interval width and ambiguous-ray counts alongside errors. A low observed mean or a close pair of sample counts is insufficient.

For p95, fix `beta=0.0001`, `epsilon=sqrt(ln(2/beta)/(2*n))`. Expand to the clipped interval `I=[max(0,L-epsilon),min(1,U+epsilon)]`; flag an occurrence unless **every** value of I is within 0.10 of c. Compute the exact one-sided Clopper–Pearson upper bound `U_flag` on the flagged proportion at error delta, including correct zero/all-success endpoints. Require **`min(1,U_flag+beta) <= floor(N_ROI/20)/N_ROI`**. This bounds the fraction of finite-ROI pixels whose true error exceeds 0.10, including the probability of a false clear caused by ray noise, and therefore proves the nearest-rank p95 requirement conservatively. Use the [NIST exact binomial construction](https://itl.nist.gov/div898/handbook/prc/section2/prc241.htm), solved by monotone binomial-CDF inversion with stable log probabilities and tested endpoints. No normal approximation for rare failures. Record N, flags, epsilon, interval widths, bounds and confidence allocation. The beta addition is a bound on bad-pixel fraction, not an additional confidence-budget spend.

For Hard, trace the certified center direction once per sampled pixel and reuse its deterministic visibility interval when that pixel repeats. There is no solar Monte Carlo uncertainty: use epsilon=0 and beta=0 in the flag test directly, without evaluating the Soft logarithmic epsilon formula; the pixel-sampling confidence bound still applies. The **held-response test is an all-pixel requirement**, not the random-ROI reducer. Freeze a total of at most `P=2^20` pixel/frame checks per family and n rays per checked pixel. Silhouette/disocclusion exclusions are fixed before results and cannot be expanded to erase a failed response.

Any additional RT-specific hashing or material/influence census occurs once only after an eligible On request and durable session latch, during bounded native-displaying preparation; ordinary Off loading incurs no new RT asset scan. Use bounded event/generation invalidation afterward, not whole-asset hashing or full-scene scans every frame. Audio/UI/control preferences irrelevant to rendering are not key fields. Size, MSAA, provider, content, mask, light-mode and shader/material changes invalidate admission before new RT work; preserve saved settings. Unknown MSAA or 2×/4×/8× uses `msaa_unsupported` for both modes without changing the preference.

Known configuration vetoes, including MSAA, occur before preparation/latching. Unsupported influential material keeps native selected, retires any temporary ownership, clears the latch only after safe completion and returns `material_alpha_unsupported`. Do not repeat that census each frame; a relevant scene/material/sun event or explicit Retry is required. Unknown eligibility is pending validation, not a fabricated support claim.

The manifest's package construction and exact-byte qualification are defined in 5.3. Candidate admission authorizes a quarantined test, not a release claim. Runtime matching is identical in candidate and delivered packages; no `allow_unqualified_rt` bypass exists.

#### 3.8.2 Durable active-session recovery

Reuse the existing renderer guard and profile ownership boundary. Acquire exclusive ownership of the RT recovery records before enabling; a second process cannot clear another session's latch. Write an atomic replacement record with schema, activation epoch, package/device/driver identity, request/mode, session ID and reason, flush the file and perform the platform's supported directory/replace durability step **before any RT allocation, warmup or submission**. Failure stays native with `rt_persistence_unavailable`. Test actual write/replace/flush failures, not only an in-memory flag.

Keep `rt_session_active` durable through preparation, the first completed frame, Keep confirmation, all active flight and suspended intervals that still own RT resources. Clear it only after native binding is selected and every RT generation is GPU-safely retired, or after that same sequence during clean shutdown. First successful submission/completion does **not** clear it. A failure to clear leaves the next start conservatively inhibited.

At startup, a stale, malformed or interrupted active-session record first creates a durable `rt_recovery_inhibit` while preserving the user's saved request. Start native and expose one explicit Retry action; never auto-retry because the first launch succeeded. Do not remove the old session record before the inhibit is durable. Retry grants one attempt: durably establish the new active-session record before any work, and clear the inhibit only after a valid GPU-completed result and the existing Keep boundary. The active-session record remains. Cancel/disable returns to native and retires before clearing; a failed retry keeps recovery inhibited.

Device loss follows the existing renderer shutdown/restart path with the durable latch retained. If native startup/fallback also fails, retain the diagnostic/inhibit and stop the automatic restart chain; do not relaunch indefinitely. Late completion from an old epoch cannot clear or confirm a new session. T10 covers interruption before first work, during allocation, after confirmation, after 30 minutes, during record replacement/clear, and during native retirement; direct-flight launch, nonwritable profiles and genuine device loss are separate cases. Controlled crash injection uses isolated profiles and expected-exit receipts only.

### 5.2 Frozen sampling, statistics and activation protocol

This supersedes the historical five-pair bootstrap/extension rule in I20. Implement deterministic synthetic reducers in 00.3; calibrate the real GPU joins in 02 before relying on any timing. Preserve the current performance owner's collectors and metric definitions; the newer main callback-interval/cached-monitor fields are not automatic same-submission GPU evidence.

**Submission identity.** Acquire/release the existing `RenderTimingLease`; do not overwrite another consumer's timing enable. Freeze `run_id`, viewport generation, render frame, displayed-state key/hash, scene/history epochs, query slot/generation, dimensions, mode and content generation at submission. Join asynchronous results to that receipt; keep engine profile-frame and polling-frame identities separate until calibrated. Verify actual queue timestamp support, valid bits, period/units/wrap. Use one nonoverlapping whole-causal-frame timing domain covering every RT-induced dependency; overlapping queues/viewports/pass p95s cannot be summed. If the engine's available timer excludes early RT work, extend the existing timing owner to bracket it, then calibrate; do not relabel the narrower timer whole-frame.

Pending results remain attached to their original submission. Missing, duplicate, wrong-slot, stale-epoch, wrong-extent or incomplete results at close are invalid, never zero or a reused value. Unexpected loss blocks the run. Calibration includes alternating known GPU workloads, delayed polling, multiple in-flight frames, epoch/viewport replacement and synthetic wrap/wrong-slot faults. No per-frame fence wait/readback is added to ordinary flight.

**One campaign and fixed statistic.** For each row and required control comparison use **11 independent process pairs** (22 runs). Generate each pair's AB/BA orientation independently from a recorded pre-result random seed; do not choose order from observed timings. A is the named native control, B the RT candidate, with equal payload/content/pixels/settings except the compared feature. Record every attempt. A missing/invalid run blocks that campaign; a changed build/input or formally invalidated campaign starts a fresh preregistered campaign while preserving the old evidence. There is no five-to-ten extension, optional stopping, bootstrap endpoint or favorable rerun selection.

For a pair-level scalar D, sort the 11 values and use **the 10th smallest** (1-based) as a one-sided upper confidence bound for its population median. Under independent, identically distributed stationary pair results, the probability that this bound falls below a true median is at most `(C(11,10)+C(11,11))/2^11 = 12/2048 = 0.005859375`; coverage is at least **99.4140625%**. This is an order-statistic/binomial construction, not a 95% bootstrap estimate ([NIST median intervals](https://itl.nist.gov/div898/software/dataplot/refman1/auxillar/mediancl.htm)). Report all 11 values, median, bound and assumptions. For an all-gates-required row, falsely accepting any truly failing required median is bounded by the same per-row error through the intersection–union rule; no independence between metrics is asserted. Across R advertised rows the simple union bound is `min(1,R*12/2048)`; do not claim 95% matrix-wide confidence for more than eight rows without a newly preregistered design. Default reports state per-row confidence only.

Keep the same host/driver/power/background exclusion and compilation state. Record available temperature, clock and throttle telemetry; start pair measurement lead-ins within 3°C GPU temperature, with no thermal/performance throttle or unexplained control breach. An inability to establish the environmental envelope blocks that campaign. Record natural frequency changes; do not impose diagnostic fixed clocks and call them player conditions. Fresh processes/random order reduce bias but **do not prove independence/stationarity**. Sustained drift/correlation or unexplained operating differences leaves the confidence claim inconclusive.

**Controlled whole-effect cost replay.** Freeze exactly **7,200 logical 60 Hz displayed states** captured from the accepted real-flight tape, plus 600 lead-in states. Each logical step corresponds to four existing 240 Hz simulation ticks; capture the actual post-interpolation aircraft/part transforms, camera/FOV/jitter schedule, sun, material/wind/LOD and source-content generations. Use stable visual-state hashes independent of process-local RIDs, resource epochs, RT history or mode bookkeeping. The calibrated PCSS angle is an explicitly recorded control parameter; compare matching physical solar target and displayed state, without pretending its engine tuning value equals the RT angle. Playback is a separate render fixture: it publishes those states without changing the production physics loop. Same input commands or elapsed seconds alone are not matching displayed states. Store the ordered state roster and content hashes before measuring RT.

Each process warms for at least 30 wall seconds, resets to the same replay/history start, renders exactly 600 unmeasured lead-in states and then renders every one of the same 7,200 measured states once, uncapped, with no generated frames or GPU wait. Run duration may differ or be below 60 wall seconds; report it. “120 logical seconds” is not a wall-time claim. No common-prefix selection, time-based trimming or adaptive state count is permitted. Every A/B state key and required timing joins one-to-one; a dropped/extra/mismatched state invalidates the pair.

For state s in pair i compute `delta_gpu[i,s]=whole_GPU_B[i,s]-whole_GPU_A[i,s]`. Set `D_gpu_all[i]=p95_s(delta_gpu)` and separately `D_gpu_active[i]=p95_s(delta_gpu over completed effective-RT states)`, using nearest-rank `ceil(0.95*N)-1`. Both upper median bounds must be ≤2.0 ms. Keep fallback frames in all-state timing and the ≥95% activity denominator; never assign them an invented zero RT cost. Missing timing on an active state blocks the pair. Record `run_tail_shift_ms=p95(B)-p95(A)` only as a different diagnostic statistic. Its value is not p95 of the per-state increment.

Attribute CPU **active work time** from main/render/worker tasks to their submitting state, including delayed jobs; union duplicate/nested intervals on the same thread, sum distinct thread work and exclude waiting time explicitly. Include all induced collection/packing/guide/build/driver tasks that the measured CPU boundary can cover and record any native-driver blind spot. The shared collector's ordinary overhead is present in both controls. Apply the same all-state/active p95 and upper-bound procedure with a 0.25 ms limit. If complete causal attribution cannot be established, this gate is blocked; do not replace it with a convenient shader dispatch time. Absolute process-loop latency remains separately tested.

For each pair also compute `H[i]=max(0,D_gpu_all[i],D_gpu_active[i])+p95(whole_GPU_A)-1000/60`. Its upper median bound must be ≤0. This is an intentionally conservative **headroom policy**, not an identity for the p95 of a sum. Preserve raw distributions and warm/cold activation costs.

**Actual product cadence and simulation.** Run a separate 11-pair ordinary-flight campaign after ≥30 wall seconds of warmup, measuring the frozen flight interval for **at least 60 wall seconds per process** at intended 60 Hz presentation settings. Keep real production physics, interpolation, input consumption and wind clocks. Every valid run must pass both wall-frame and owner process-loop p95/p99, unpaused sim/wall ratio, activity, coverage and relevant loading/hitch gates; a median cannot hide a failed absolute run. Generated frames do not count. This campaign proves player behavior; the uncapped state replay proves controlled rendering cost. Neither substitutes for the other.

**Off comparisons.** Repeat the fixed matched-state procedure for unused candidate-Off versus used-and-retired candidate-Off, and official baseline versus patched-Off. For each Off comparison define D[i] as the nearest-rank p95 of the 7,200 matched **all-state** deltas for that metric. Active-only deltas and the >=95% RT-activity floor are not applicable when both sides are Off; all zero-RT-work/resource gates remain mandatory. Apply `D[i]-max(0.10 ms,0.01*p95(control_i))` upper bound ≤0 separately for whole GPU and CPU work. In ordinary-flight Off comparisons, apply the same bound to the explicitly named wall-tail shift `p95(candidate_i)-p95(control_i)`; this is a distribution-regression gate, not the effect-cost estimator. Every Off counter/resource gate and absolute owner gate must also pass.

**Cold/warm activation.** Record request, first submitted RT frame, first completed result and first valid displayed effect separately, with cache state and new-kernel compile counts. Keep native display while preparing. No RT allocation/compilation/scene extraction before an eligible On request to conceal startup cost. Record warm re-enable, cancellation and after-retirement bytes separately; generic engine/driver caches are explicitly identified.

M contains no “qualified” status, proof hash or containing-ZIP hash. A canonical self-checksum excluding its own checksum field may detect accidental corruption; it is not an anti-tampering security boundary. Missing/malformed/unknown-schema M or mismatched actual P fails closed. Existing distribution/signature policies still apply; this plan does not invent signing keys.

Include an inert-by-default qualification entry point and required fixture/state manifests in P, with source/payload hashes. Extend the existing diagnostic launch owner with the explicitly proposed game argument `--rt-qualification <case-manifest>`; the phase-00 wrapper invokes it through the normal checked runner. It publishes the frozen displayed states through the normal renderer and admission matcher, with no alternate executable or unqualified-admission flag. Normal play never starts this harness or allocates its resources. Any positive fixture that needs RT has an exact content/configuration entry in M with `row_kind=qualification_fixture`; retail field rows use `row_kind=product`. Q covers both kinds, while user support claims list product rows only. Negative admission cases must still fail normally.

Run all release-critical image, real-flight, cadence, memory, activity, simulation and recovery checks with the **unmodified exported executable** from that exact ZIP and the normal production matcher. The quarantine workflow authorizes testing its provisional rows in isolated profiles; no runtime qualification bypass or editor-only admission path is allowed. Native controls use the same exported candidate with RT disabled, plus the separately identified official-engine control for generic regressions. Instrumented debug/fault evidence supplements release-template evidence; it never replaces it.

15.1 verifies, rather than rebuilds, the frozen ZIP and required member roster. After every row listed in M passes all applicable 14/15 gates, generate an **external qualification receipt Q** containing ZIP SHA-256, M hash, payload/member hashes, row keys, evidence hashes and verdicts. Q is outside the ZIP and not a runtime input. Keep all evidence records hashed by Q immutable, without embedding Q's own hash in them; a separate post-qualification handoff may link Q after it exists. Release-owner promotion may distribute only those unchanged ZIP bytes with Q. No receipt/manifest/archive hash recursion exists. If a row fails, withhold the entire candidate or build a new explicitly narrower candidate and re-execute its required package/row campaign; do not edit M inside a tested ZIP. Any payload/M/ZIP change starts a new candidate. No coherent-local-tampering protection is claimed by these hashes.

Identical shared proof receipts may be referenced by several rows only when their exact ZIP/device/configuration/case identities and scope match. Do not duplicate unchanged source-only checks merely to fill a matrix, or reuse another mode's activation/retirement result where its resources differ.

Separate capability, provisional candidate admission, completed execution, technical qualification, and release-owner promotion. The exact driver/OS/content/configuration matcher leaves an untested changed row native even if the device remains capable. A newly passing row requires a new candidate and its §5.3 proof; runtime cannot extend the support matrix itself.

### 9.2 Implementation completion report format

The final implementation report must state: what is actually playable; exactly which rows are package-qualified; source/package/evidence links; native control versus RT quality and cost; Off and simulation-regression results; unresolved failures/blocked hardware; and the smallest next authorized step. Include real measurements or say unmeasured. Do not restate the plan as if it were implemented.
