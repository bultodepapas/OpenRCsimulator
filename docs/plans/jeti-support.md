# JETI transmitter support plan

Status: evidence intake and source review completed on 2026-10-19; implementation and hardware qualification are pending. [D6-JETI-00](../research/radio-input/D6-JETI-00/README.md) preserves the JETI email, PDF, USB descriptors, controller profile and findings. Jakub Uhlík reports successful basic flight with a DC-16II and identifies switch naming/default assignments as the main problem. This is an external observation with incomplete build/firmware metadata, not full compatibility certification.

## Ownership and scope

This is a subtrack of [controller support](controller-support.md), under the [existing ownership registry](../README.md#tracks-plans-and-step-ids). Input owns D6-JETI-* (identity, profiles and switches), F1-JETI-* (diagnostics), F4-JETI-* (hardware qualification) and F6-JETI-* (optional latency). UI owns UI-15-JETI-* (setup, labels and selection). DT/PT own exported-package acceptance; aircraft, HELI and RCV retain their activity semantics.

Owned changes are focused additions in `app/input/`, controller tests and this evidence directory. Coordinate `app/ui/controller_setup.gd`, `app/ui/controller_prompts.gd`, localization and any `app/app_root.gd`/session hooks with their owners. Reuse the registry, V2 profile store, scalar conditioning, remapping and typed AUX pipeline. No vehicle-specific branch enters the simulation kernel. No aircraft data, solver, golden flight or physical tuning change belongs here.

First delivery: a recognizable JETI USB radio, an explicit Mode 2 starter profile, accurate physical-control labels, conflict-free setup and usable two-/three-position switches. Keyboard/mouse and the separately selected menu gamepad remain recovery paths. Other JETI models, modes and platforms require their own observations. Wireless telemetry, EX Bus, receiver integration and firmware modification are outside this scope.

## Evidence-driven design

1. **Recognize conservatively.** The supplied identity is VID `0x0483` / PID `0xA07C`, manufacturer `JETI model s.r.o.`, product `JETI DC/DS Mass Storage`. The VID belongs to STMicroelectronics and cannot identify JETI by itself. Use the pair with available JETI identity evidence; handle missing/contradictory metadata and duplicate devices explicitly. Preserve raw metadata separately from the display name. The product describes a family, so do not infer DC-16II versus DS-16 or other revisions from it. A saved GUID is an observation, not a portable whitelist.
2. **Offer a versioned radio preset.** Start from the supplied roll=0, pitch=1 inverted, throttle=2 absolute, yaw=3 mapping. Preserve existing calibration, actions, AUX and explicit clears. Offer the preset without silently replacing saved profiles or declaring other stick modes equivalent. Keep transmitter shaping and simulator shaping explicit; do not add gamepad expo to compensate for a radio. Never copy the tester's UUID or device association into a universal preset.
3. **Make a clean action map practical.** `effective_bindings()` currently starts with gamepad defaults even for radios. An empty `actions` dictionary does not clear those defaults. Provide a JETI starter/clear operation that explicitly unbinds inherited switch actions and retains validated, non-conflicting recovery bindings. Apply it to a draft with Save/Cancel and rollback. Existing profiles change only through an explicit user choice.
4. **Name controls physically.** Display a short JETI family/model label and expose the full backend name in details. Use labels such as `Sa — Up`, `Sa — Middle`, `Sa — Down`, with the observed Godot button index available for diagnosis. Unknown controls keep numeric labels. Use text for radio controls rather than face-button/shoulder glyphs. Do not invent the unmeasured Sc–Sj map or the meaning of buttons 31/32.
5. **Separate positions from presses.** A maintained switch has one active position button at rest. Group its observed buttons, allow two-position hardware with an unused middle slot, and distinguish momentary actions, held requests and absolute detents. Use physical positions for smoke off/on, gear up/down and flap detents when the aircraft supports them. Extend the shared AUX contract only as needed; a three-position switch must not be implemented by repeatedly invoking a toggle/cycle action.
6. **Preserve input safety.** Initial enumeration, profile activation, capture completion, focus return and reconnection must not synthesize button presses. Capture consumes the relevant source transition without waiting for every maintained switch to be released simultaneously. Specify a safe activation policy for absolute requests; preserve fresh low-throttle evidence and explicit Continue. Handle old-release/new-press transitions consistently and reject malformed groups or contradictory stable states. Preserve existing radio, gamepad, helicopter and truck rules.

The PDF's Windows button numbers and HID usage IDs are separate from Godot's event indices. Sa=1/2/3 and Sb=4/5/6 are documented at the Windows layer; candidate zero-based indices must be verified through F1 before runtime labels or defaults rely on them. The descriptor exposes eight analog values and 32 button usages; this does not prove eight mapped Godot axes or 32 meaningful physical buttons.

## Verification protocol

Use the commands in [TOOLS: radio diagnostics](../TOOLS.md#radio-diagnostics), the [F1 report contract](../research/radio-input/F1/README.md) and the [controller regression/qualification gates](controller-support.md#automated-verification). Reuse existing free OS controller tools rather than building a new HID inspector. Run focused profile/store/registry/actions/prompts/setup/AUX/RC tests, then the whole-app parse and required `app/test.sh` checks after runtime integration. A synthetic report establishes routing only.

For the physical DC-16II row:

1. Capture all eight analog controls and every installed switch position, including unchanged startup positions. Split reports if bounded transition storage overflows. Compare signs/endpoints with the supplied Mode 2 profile and verify the real low-throttle position before flight.
2. Start with fresh disposable preferences, select JETI, review the preset, map smoke/gear/flaps on supported aircraft and save. Exercise Back/Pause, dirty-draft cancellation and restart persistence. Repeat EN/ES and narrow-window setup.
3. Hold a switch through launch, menu entry, capture and focus changes. Confirm no unintended pause, trim, calibration, restart or equipment action; deliberate movement produces the intended request exactly once or the intended maintained state.
4. Run at least ten disconnect/reconnect cycles, including raised throttle and active switches, plus focus loss and host sleep/resume. Expect a safe hold, fresh radio arming evidence and explicit Continue; no silent takeover or thrust.
5. Connect a gamepad and a second/ambiguous controller. Only the selected radio controls flight; only the chosen menu device navigates. Exercise fixed-wing flight, helicopter safety and truck selection regressions without claiming their full JETI qualification from an airplane circuit.
6. Repeat the core flow outside the editor in the exported Windows package. Record build/engine/OS/firmware/profile identities and `pass`, `limited`, `fail` or `untested`. Redact serial numbers and host identifiers in new shareable reports. Pilot feel, physical aircraft accuracy and latency require separate evidence.

## Open evidence requests and rollback

The next hardware handoff should request the tested simulator version, transmitter firmware and physical switch configuration; confirm Sa–Sj/spare-button mappings, P5–P8 ordering in Godot, stick-mode effects, RF-module behavior in USB mode and whether other models share this descriptor. Jakub offered testing in his free time; schedule no dependency on an immediate reply. The existing thread contains no permission grant for logos or a 3D radio.

Version the preset independently from user profiles. Adding JETI support must not rewrite the tester's original CFG or silently migrate a custom joystick into a different kind. Keep old axis/single-button profiles readable and fail closed on an invalid extended binding. Reverting a step must preserve the previous working profile/store. No physical-support claim closes until its native hardware row passes.
