# Proposed interface contracts for glider and tow

**Status:** design handoff, not an implemented API, accepted schema or evidence of a working pair. **Source baseline:** [main at `ad21070798bfb9658785576a9c0b8bfc9a71fc7f`][baseline]. The [master plan](../glider-soaring.md) owns scope and status; [launch and control](01-launch-and-control.md) owns player flow; [physics and tow](02-physics-and-tow.md) owns the laws and numerical feasibility; [acceptance](04-acceptance-and-delivery.md) owns gates. The responsibilities below require agreement by their existing owners.

## 1. Current seams and limits

These are source observations, not newly implemented glider capabilities.

| Seam | Pinned behavior and implication |
| --- | --- |
| Aircraft data and identity | [AircraftData][aircraft-data] requires propulsion and derives a powered normalized model. For the optional **authored physical identity module**, [PhysicalIdentity][physical-identity] requires and describes a propulsion ID; historical data without that module follows its existing path. [PropulsionRuntime][propulsion-runtime] prepares callbacks for one installation and its accepted observation requires a named propulsion law and an `engine_rpm` aux entry. Absence therefore needs changes through admission, derivation, identity, runtime and observers; an empty dictionary is not sufficient. |
| Kernel and sampling | [VehicleModel][vehicle-model] declares a single body plus continuous, sampled `aux` and discrete `modes`. Its opt-in framed protocol samples a detached accepted frame once per tick; the float64 input snapshot produces only candidate `aux` and `modes`, which stages reuse. It does not provide a general pair object or arbitrary structured intent input. [Simulation][simulation-step] validates the primary body separately and the continuous tail as finite values; secondary-body validity and projection need proof. |
| Events and projection | The model permits one kernel-declared located event or a model-owned step policy. A policy and requested kernel contact substeps greater than one are refused together. The existing post-tick body filter returns only the primary body. An endpoint transition can update the full declared frame, but does not automatically compose individual aircraft policies. See [event protocol tests][event-test] and [contact-substep tests][substep-test]. |
| External control and AI | [FlightSession][external-tick] validates one external command packet and steps one session; its rollback preserves last accepted controls on an uncommitted attempt, although `before_step` can see the attempted inputs. The [companion manager][companion-manager] plans from a shared preceding snapshot and advances separate sessions after the player. It is useful prior art for admission and controllers, not a same-stage coupled solver. |
| Commit and observations | A successful `step()` installs state and tick, then emits located events before `stepped`; `last_events` is diagnostic and excluded from the [kernel checkpoint][checkpoint]. The guarded `reset_observer_fault` behavior in [prepared reset/restore publication][reset-publication] does **not** establish a guarded general tick-observer boundary. The primary-body `stepped` payload alone is not a published pair frame. |
| Logs | Existing [fixed-wing logs][flight-logging] record the accepted endpoint and the k1 loads for the interval, together with post-conditioning commands. Exact replay checks the recorded solver and state; a linked companion capture is not fleet restore or decision replay. |

## 2. Proposed admission and absent-propulsion semantics

AS, aircraft pipeline, physics, FL and presentation owners should define a versioned absence representation across authored capabilities, generated data and the normalized model. It must be distinguishable from a stopped, failed or cut powered installation. Preserve installed receiver, servo, release actuator and battery masses and the declared electrical supply; finite depletion is a separate admitted capability. Reject an absent installation with contradictory thrust, rotor, shaft, fuel or propulsion-energy bindings. This does not imply that the aircraft has no electrical system.

Identity must describe absence explicitly without creating an invented propulsion or rotor installation ID. Keep existing powered identities and historical readers stable. The current `physical_identity.gd` and `aircraft_propulsion_runtime.gd` paths, contact/hull/rotor bindings, trim, stage/load setup, audio, render, trace metadata and checkpoint/restore consumers need a coordinated compatibility review. Route each through its owner and its source/generator pipeline. Do not hand-edit generated aircraft data.

For an accepted unpowered observation, propose an explicit availability/status discriminant, aircraft/configuration identity and relevant layout/law identity. Propulsion-only measurements such as RPM, shaft torque and fuel flow are **not applicable**, not unknown and not fabricated zeros. A consumer may compute a numeric zero force contribution where the admitted law requires it, but must not infer that a motor exists. Distinguish an unavailable/malformed observation from a valid absence; unsupported representation or reader versions refuse before replacing the accepted activity. The exact wire shape, names and compatibility policy remain AS/FL decisions.

## 3. Resolved scenario and identity

The [preflight resolver](01-launch-and-control.md#2-preflight-resolution) should return either a complete immutable resolved scenario or an unavailable reason with the failed capability and owner. It binds actor identities and source/configuration hashes, launch and human/AI roles, input profile and assistance policy, physical installations and line/event policy, aircraft and controller laws/layouts, world/terrain/weather seed, agenda and epoch, solver/backend and recording requirements. Include effective values and explicit assumptions, not only display names or a seed.

A proposed scenario identity identifies the canonical resolved content and its resolver/normalization version; a stable seed alone does not identify aircraft, field, laws or a resolved random agenda. The identity used by Home, direct launch, reset, logs and debrief must be comparable under a defined encoding. Equal explicit inputs should yield the same resolved identity where the owner declares them equivalent; different effective physics, control or world policy must not silently share an identity. A restart either reuses this recipe and realization or resolves an explicitly new challenge. A failed or stale preparation leaves the previous accepted activity and preferences intact. Hash algorithm, canonical encoding, display-only identity treatment and compatibility/migration rules remain owner choices.

## 4. Composite frame and evaluator boundary

The semantic groups below describe what an accepted pair must represent. They are **not executable shapes, storage offsets or a chosen public layout**.

| Group | Required meaning |
| --- | --- |
| Common clock and identity | One accepted tick and fixed timestep; scenario, actor, layout, protocol, law, backend and generation identities. |
| Per actor | Body pose, velocity and rates; continuous installation/contact/actuator state; sampled controls and discrete modes, each interpreted under its own declared layout. Floating state uses float64; discrete modes retain integer types. |
| Shared and coupled | Weather/epoch and any advancing RNG state, line configuration and physical mode, pending admitted event state, and the shared environment needed to continue deterministically. |
| Control | Current owner per actor and role, held effective commands, controller integrators/filters/timers and mode, takeover and pickup state, and the input-edge/intent bookkeeping needed for safe continuation. |
| Publication | A detached coherent pair snapshot and accepted previous/current presentation poses, tagged to an accepted tick and restore generation. Presentation interpolation is derived state and never feeds physics. |

One installed `VehicleModel` and one transaction own the coupled candidate. A candidate stage evaluates both actors, line and world using the **same** stage state and time. The existing joint route requires loads, continuous derivatives and rotor momentum; an optional primary body derivative replaces the kernel’s rigid-body derivative. Sampling, stage evaluation, event preparation and projection must be deterministic and read-only with respect to live session state and live random generators. A sampler may derive candidate RNG state from the accepted state, committing it only with the pair. A sampled controller derives from the preceding accepted pair, advances only at its declared cadence and holds its commands across all stages and internal subdivisions of the tick. See [the numerical contract](02-physics-and-tow.md#6-sg-07-coupling-and-event-feasibility) for secondary attitude, contact and policy obligations.

The existing framed sampler accepts only a float64 array and returns fixed-size aux/modes arrays. It cannot simply accept a dictionary containing actor names or a string intent ID, nor return body changes or a result object. Owners must specify a bounded, validated encoding and where any immutable candidate metadata lives, or pursue a generic SF extension. Do not smuggle mutable controller state or a second independently committed session through a callback closure. Keep state, RNG and intent bookkeeping in kernel-owned arrays or an explicitly staged sidecar. A sidecar is not automatically transactional: prove prepare, atomic commit, rollback, fault recovery and restore at the same boundary, and pin its identity. Publication uses the same accepted boundary but is not a second source of physical state. Candidate evaluation cannot publish a partial pair. The continuous-tail prototype and a generic SF-owned alternative remain under comparison; neither is adopted by this document.

## 5. Arbitration and action results

Each actor/role has exactly one effective command writer at a boundary: human, admitted controller, or the transfer arbiter under its versioned policy. Controllers consume detached accepted observations and propose commands; they do not write physical state. The arbiter produces the final named per-actor command and owns held values, limits, pickup/blend progress and any transfer memory. Distinguish requested input, selected effective command, and achieved physical actuator position. Initialization of a newly active controller uses the accepted post-limit command and separate achieved state; preserve its integrators and saturation rules. The [launch/control document](01-launch-and-control.md#7-manual-tug-followed-by-glider-control) owns user interaction and pickup behavior.

An intent carries, semantically, activity generation, actor and authorized source, action and installed hook if applicable, a stable request identity, and the intended boundary. A result identifies that request and the accepted boundary or a specific refusal. Define authority explicitly for any cross-actor release. Mechanical release and control ownership are independent state changes. At an accepted control boundary:

| Request | Accepted result | Refusal or retry |
| --- | --- | --- |
| Release only | Release the specified available hook and retain ownership; if AI owns the glider, establish its admitted disconnected fallback. | An unavailable hook or unsupported release is refused without transferring control. A separately available release remains offered when takeover readiness fails. |
| Take glider only | Change ownership and initialize tug recovery and the arbiter under the admitted pickup policy. A previous release remains released; attached transfer needs its separately admitted mode. | If readiness, authority, fallback or recovery fails, preserve the pair and ownership. An already completed takeover is a duplicate/no-op result without additional credit. |
| Release and take glider | Prepare and validate both changes, then commit one combined result and ordered accepted event with release and owner changes together. | If either part is refused, neither change commits. The player may submit a **new** release-only request and later a new takeover request. |

A held input generates one edge, not one action per sampled tick. Bind request identity to activity generation and immutable payload. A duplicate must return the original result or a clearly identified duplicate without producing another release, transition, score or controller initialization; reuse with a different payload is refused. Define a bounded retention/high-water policy so an old ambiguous request is refused rather than executed again after eviction. Persist the necessary edge/dedup state across checkpoint/restore, or refuse a restore that cannot preserve it. A new user action after a refusal has a new request identity; retries of the old one must not unexpectedly become a successful action after readiness changes. Refusal receipts may be journaled without committing an accepted physical transition; their storage and lifetime need an explicit bounded owner policy.

## 6. Timing, events and failure boundaries

Owners must choose and version whether an intent sampled at boundary `n` takes effect there or at `n+1`, including how it binds to the accepted interval and event result; no choice is adopted here. Record effective time separately from the accepted endpoint tick. The sampler runs per physics tick even when an AI updates more slowly: define its cadence phase and admit release edges per tick with a bounded response, rather than silently waiting for the next AI update. A release request is not itself proof that the hook opened. A versioned first law may explicitly idealize release as instantaneous; it must not imply a measured actuator delay. A later finite-delay law needs qualified pending, timeout and readiness semantics: combined completion must wait for confirmed opening and honor the admitted mechanical/ownership timing; attached transfer is separately gated. Refuse the combination if that lifecycle cannot satisfy its atomic result. A line-release action is not an overload/break event located within a trajectory. Each accepted event needs stable actor/action identity, causal request if any, tick, effective time, deterministic ordering, old/new relevant state and reason. A combined action is one logical result even if its payload describes both state changes. A repeated key cannot create another accepted event. Consumers deduplicate by event identity; the contract does not promise exactly-once delivery from arbitrary external observers.

Trial stages and abandoned subdivisions are evaluations, not accepted history. Stage-local load peaks alone do not prove an accepted break or contact. A model-owned event policy must qualify localization, ordered composition and any integration receipt against the accepted trajectory, including effects of endpoint filtering. Endpoint events must satisfy the current bounded event transport. In particular, the current merge appends endpoint events after located events; do not assume the kernel sorts them by time or resolves simultaneous priorities. Define a versioned ordering policy, detect unhandled intersections, and refuse the whole candidate if ordering or error bounds are unresolved. The first reference proof excludes such intersections rather than suppressing requested contact subdivisions.

**Before commit:** invalid identities, stale generation, unsupported capabilities/events, nonfinite stage/weather, invalid second body, impure callbacks or failed projection reject the complete candidate. Preserve both accepted bodies, clock, line, controllers, RNG, ownership and accepted event history. Enter the admitted pause/fault or refusal path with a bounded reason; diagnostic attempt, pause, fault or footer I/O may occur but cannot add an accepted physics sample, transition or score. A pre-step observer can see an attempted input in today's session, so no external observer should treat it as proof of acceptance.

**After commit:** a pair publication or recorder observer can fail after the accepted boundary exists. Proposed pair handling must preserve the committed frame and event identity, stop or mark incomplete any affected recording, pause/fault as appropriate, and report an accepted observer fault rather than claim rollback or retry the physical action. Reset/restore already have a narrower guarded precedent; ordinary pair tick publication needs its own implementation and tests. Restore must not create a new launch, release or score. A consumer that cannot establish its own consistent position in the event stream must stop or report incompleteness, not invent missing events.

## 7. Checkpoint, tapes and replay

A proposed pair checkpoint/envelope captures the complete accepted semantic frame above, current inputs and held commands, controller/arbiter and dedup state, actor/configuration and world identities, seed/RNG/epoch, law/layout/protocol/backend and clock. Include enough state to reproduce future decisions; detached visual history can be rebuilt or explicitly rebased on restore and tagged with a new presentation generation. Validate the entire envelope, actor identities, supported versions, sizes, finiteness, clocks and invariants before committing either actor. A rejected restore leaves the existing pair intact; a committed restore publishes the complete pair and its actual paused/fault status. Current kernel checkpoints do not include `last_events`; the pair event stream and action ledger need explicit ownership and a common accepted boundary.

Keep these records distinct, versioned and aligned to the same tick convention:

1. **Intent/attempt record:** actions, request IDs, authorization, refusal/accepted result and boundary. This is not a control-command tape.
2. **Final-command tape:** named per-actor effective commands applied over each accepted interval after arbitration and input conditioning. Solver replay also needs the authoritative, timed external release/transfer interventions; recompute and compare endogenous physical events rather than injecting them as commands. This does not recreate the original device or pilot adaptation.
3. **Decision replay inputs:** initial controller/arbiter state, observations or reproducible world state, sampled inputs and timing, policy identities and relevant RNG. Re-execute controllers and compare decisions separately; a final-command tape cannot prove AI decision replay.
4. **Accepted event and state record:** both endpoint states and relevant internal blocks, located events and timing, plus declared observation timing. Any k1 load is identified as an interval-start value, not mislabeled as an endpoint force.

The current noninitial log row at tick `k` describes the command for `k−1 → k`; its k1 loads belong to the interval start. Give pair records an equally explicit convention. A solver replay that bypasses AI cannot recreate its evolving controller memory: define and compare a versioned physical-state projection plus events for that replay, or run the separate full decision replay and compare controller state too. Label a solver-only result exact only within its declared physical projection; full pair continuation additionally requires the controller-state comparison. Replay requires an admitted matching source, build, solver, layout, laws and input roles, a complete initial checkpoint and the timed interventions; compare the declared state projection and event order. A changed candidate is a separate, explicitly identified comparison, not exact equivalence or physical validation. Truncation, a failed observer, unsupported version or mismatched identity must be reported as incomplete or refused. The [acceptance and delivery plan](04-acceptance-and-delivery.md#7-recording-telemetry-and-debrief-schema) owns evidence and completion criteria.

## 8. Decisions to close before integration

- **AS / aircraft pipeline / FL:** select the absence discriminant, identity evolution, observation availability and compatibility rules; inventory powered-only consumers and prove unchanged powered behavior.
- **SF / physics / GP:** choose the composite layout or generic extension after the bounded reference experiment; define secondary validation/projection, pure evaluator extraction, intent effective boundary, event ordering and contact/substep composition.
- **Session / input / AFC:** define resolver canonicalization, control roles, authority, request identity, bounded duplicate/refusal retention, controller cadence phase versus per-tick release, and how all transaction state crosses the sampler's actual typed boundary.
- **FL / session / UI:** define the pair envelope, accepted publication fault handling, record termination, generation and consumer deduplication. Align replay and telemetry without treating independent flight logs as an atomic pair.

Existing focused anchors include [framed sampled rollback and restore][framed-test], [event protocol][event-test], [session staged start][session-test], [checkpoint][checkpoint-test], [flight-log input roles][log-input-test] and [companion lifecycle][companion-test]. They cover the existing seams, not the proposed two-aircraft behavior. New tests and evidence belong to the owners and gates in [acceptance](04-acceptance-and-delivery.md).
