# CI test effectiveness and coverage inventory

The audit branch adds 185 cases to the Linux offline test runner. The previous native allowlist selected 176 test methods in eight files. The candidate selects 354 methods in 23 native-kernel files and seven mass, center-of-gravity and fuel-trace cases. **All 361 passed** on Linux. Physical flight validation, hardware performance, native builds and exported executable qualification have separate owners and gates. ## How to read the inventory

The baseline is commit `85a2475f60029a4b6b09f23f643119bceea84a45`. A NUL-delimited recursive Git tree listing yielded 52,627 paths. The census includes executable files following the repository's test naming conventions, source files in test directories, the Playwright and shell harnesses, and directly named checkers. It retains dated evidence and supplied source copies as distinct paths. Binary fixtures, computed output, logs, Godot UID sidecars and screenshots are outside the executable-source count. App family tags use filename prefixes to make the roster searchable. Read a test's code before assigning ownership or deleting it.

The JSON distinguishes a successful local verification of a module from a statically established execution route. Rows marked `explicit` have a reviewed invocation, discovery rule or dependency. Suite-level hosted results do not automatically classify every file in the suite as individually verified. Some contain platform-specific skips. Rows marked `not found` have no automatic execution route established by this review. They include manual research tests, imported helpers and candidates needing investigation. A status of `archived` identifies a retained source snapshot or delivery. A file can have several routes. The route catalog identifies the controlling script or workflow and the conditions for execution. The `baseline_linux_offline` field records the old Linux selection for the native and trace changes. [Inventory and route catalog](CI_TEST_INVENTORY.json)

The machine-readable appendix contains **2,012 distinct paths**. It records 29 locally verified modules or drivers, 1,516 files with a source-established route, 130 with no established automatic route, and 337 archived files. The unresolved group includes 102 named tests plus helpers, probes and checkers. This is a routing census, not a code-coverage percentage. [Per-file results](CI_TEST_INVENTORY.json)

The baseline contains 1,163 top-level application GDScript tests, 54 research GDScript tests, seven tooling GDScript tests, two C++ test files and two three.js TypeScript test files by name. Across the tree, 341 Python files have test names, including 16 copies in historical documentation. For the 325 outside documentation the distribution is 167 tooling, 126 research, 19 application, nine telemetry service, three supplied assets and one website. These counts use file names. The inventory also lists test-area helpers, entry points and checkers that use different names.

The review followed the automated entry points, inspected assertion samples in high-risk groups, and ran the new Linux coverage. It did not inspect every assertion in the 1,163 GDScript files. A script appearing in a successful roster, a function being parsed, or a helper being imported does not establish the outcome of every conditional assertion. Historical failure attribution and end-to-end runner durations belong in the main audit.

## Confirmed gaps and limits

**The first hosted attempt exposed an import-fixture regression.** The Linux application integration job at `ce31055c` passed resource import and the telemetry wire check, then failed its offline measurement step in 14 seconds. On the same source, the step's first command reproduced one failure in 14 partition tests. The fixture used the later aircraft-schema step as its end delimiter and fed the intervening telemetry and upload YAML to Bash. The simulated import failed as intended, but Bash returned 127 after executing the extra lines. The corrected fixture stops at the next workflow step and separately asserts that import precedes schema validation. It still checks the failure receipt and the diagnostic upload conditions. An in-memory reordered-schema control failed the explicit ordering assertion. The corrected 14 partition cases and 14 adjacent phase cases passed locally. The successful telemetry step and the later offline failure are distinct results from the same hosted job. [Hosted job and steps](https://github.com/bultodepapas/OpenRCsimulator/actions/runs/45075562784/job/137372676636) · [Partition fixture](../../app/tests/test_ci_partitions.py)

**A unit failure hides later independent results on its shard.** The integration sections honor `OPENRC_KEEP_GOING=1` at baseline `app/test.sh` lines 103–117. Unit commands at lines 545–550 run directly under Bash errexit. Using the repository's disposable partition fixture with the first of 19 units forced to fail, the runner returned exit 7 after one unit and produced zero successful roster receipts. Preserving that failure while recording subsequent independent outcomes would shorten diagnosis. Never issue a complete successful receipt for a failed shard. [Partition fixture](../../app/tests/test_ci_partitions.py) · [Suite runner](../../app/test.sh)

**Some headless visual tests finish before checking a pixel.** Two tree-backlighting tests explicitly return success under the headless display. Their presence in the unit roster does not establish pixel behavior. Neither tree script had a dedicated rendered CI invocation identified. The lighting segment-filter and skin-pattern tests illustrate an existing solution. The visual runner starts them with a display, checks output and requires a positive nonzero assertion count at baseline `app/capture.sh` lines 258–268. Prefer measured, targeted rendered coverage to running every headless test a second time. [Tree-card test](../../app/tests/test_treeline_backlight.gd) · [Imported-tree test](../../app/tests/test_imported_tree_backlight.gd) · [Rendered checks](../../app/capture.sh)

**Telemetry end-to-end coverage has a distinct prerequisite.** At the baseline, the telemetry discovery step loaded the real client/receiver case but omitted `OPENRC_GODOT`, so its class-level guard skipped it. The audit branch invokes this case immediately after checked project import with the pinned editor, `OPENRC_REQUIRE_GODOT_E2E=1`, isolated receiver dependencies, and a 15-minute step cap. It retains diagnostics and checks the client's sent count against actual stored batches. On Linux, Godot 4.8-beta2 sent three batches to a real loopback receiver, which stored all three. The client reported zero queued and zero dropped. The fixture used byte-identical production telemetry components in an isolated project. Required mode rejected a missing editor, while service-only discovery in a sparse checkout skipped exactly one engine-dependent case. PR run 45075562784 at `ce31055c` subsequently completed the full application import in 430 seconds and passed the mandatory telemetry step in eight seconds. Its checked artifact confirms three batches sent, zero queued, zero dropped, zero local drops, exit 0 and zero errors or warnings. [Receiver test](../../services/telemetry/tests/test_godot_e2e.py) · [Client script](../../app/tests/telemetry_receiver_e2e.gd)

**Native graphics and MetalFX have separate owners.** The Windows queue path list includes `tools/graphics/**`, but its run steps select queue, debug, checked-runner, resource, performance and GOD TEST fixtures. The MetalFX job selects `tools/graphics/metalfx/test_engine*.py`. Neither selection executes the seven `tools/graphics/native/test_*.py` files. Portable mutation and packaging controls should gain a measured automatic route. Use hardware for their GPU-dependent conclusions. [Windows queue](../../.github/workflows/testqueue-windows.yml) · [Native graphics tools](../../tools/graphics/native/README.md)

**Source string checks and repeated suites have different purposes.** The workflow policy test matches exact step labels and command strings. The controls reference test extracts named GDScript function bodies and quoted actions. These checks can enforce a published source contract but can also fail after a harmless refactor or pass after a behavior change elsewhere. Add direct execution assertions for behavior before relaxing literal checks. Likewise, Linux, Mac and Windows process tests should retain distinct platform coverage. Repeated `tools/godtest` discovery on Linux and overlapping analytics tests in website and telemetry jobs are narrower opportunities for consolidation after checking triggers and environments. [Workflow assertions](../../tools/ci/test_visual_workflow.py) · [Control-map assertions](../../app/tests/test_controls_reference.gd) · [Offline roster](../../research/test-tools.sh)

**Flake attribution needs a rerun or a reproducible failure.** No literal `randomize()` appeared in the 1,163 top-level GDScript units. Forty-three files reference `RandomNumberGenerator`. Sampled allocator and electric-bus tests set seeds explicitly. Other uses of randomness isolate temporary paths or ports. The debug bridge binds a candidate loopback port and releases it before reuse, leaving a possible race without a measured failure attributable to it. Keep shutdown logs, seeds/inputs, process exit codes and native diagnostic receipts when investigating infrastructure incidents. [Allocator](../../app/tests/test_mr_allocator.gd) · [Electric bus](../../app/tests/test_mr_electric_bus.gd) · [Bridge fixture](../../app/tests/test_debug_bridge.gd)
