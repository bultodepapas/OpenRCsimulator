# Aircraft contract

**Status: current v2 authoring/runtime contract, 2026-10-26.** Revision 5. Authored format: `openrc-aircraft v2`. Convention: `openrc-le-frd-v1`. [Audit](research/aircraft-standardization/AS-00/), [migration](research/aircraft-standardization/AS-05/README.md), [shared admission and fleet verification](research/aircraft-standardization/AS-06-14/README.md#shared-flight-admission-as-0714-r1-2026-10-26).

The [standardization plan](plans/aircraft-standardization.md) records delivered interfaces and remaining gates. The shared module registry, model manifests, presentation adapter and compatibility interfaces below preserve the accepted physical v2 format. Flaps use the conditional `controls.flaps.hinged_trailing_edge.v1` module; repeated propulsion instances and selectable new contact laws remain separate extensions.

## Add an aircraft using supported laws

1. **Choose the installed configuration.** Identify its control topology, propulsion/energy, gear and damage policy from the [capability table](#capabilities-and-conditional-modules). Reuse an existing law only within its declared limits. An aircraft ID, commercial name or mesh does not select a physical law.
2. **Author physical data at its source.** Use the [synthetic template](../research/aircraft-standardization/template/openrc-aircraft-v2.template.json) as a shape example, with a unique ID and explicitly donor/estimated initial evidence. Supply the v2 quantities, evidence, stable physical IDs and complete inventory; use the owning [generator](tools/physics.md#aircraft-data-and-generators). Keep numerical array order stable. `AircraftData.load_file()` must accept the generated file before flight; schema or module classification alone is insufficient.
3. **Bind presentation separately.** Reuse a suitable licensed model and the [model manifest](#model-and-package-contract). Declare datum, hinges, rotor, gear and sections against real nodes in `assets/aircraft/model-bindings.json`. Supported imported families use `imported_glb` and `res://aircraft/imported_model.gd`; procedural families retain their version 1 adapters. Register the configuration once in [AircraftCatalog](../app/app_state/aircraft_catalog.gd); related installations may share a visual family. Declare any finite-pack alternative through `battery_data`.
4. **Generate dependent records.** Refresh manifests and Workshop descriptors through their source pipelines. Follow the existing [Workshop](AIRCRAFT-WORKSHOP.md), [audio](AUDIO-PLAN.md), [smoke](SMOKE.md), [lighting](AIRCRAFT-LIGHTING.md) and [economic dossier](#damage-and-cost-authoring-dossier) contracts where applicable. These records reference physical identity; they do not redefine mass, control travel or force laws.
5. **Verify every offered configuration.** Run the [aircraft conformance workflow](tools/physics.md#aircraft-conformance-and-unchanged-behavior), generator checks and relevant model/start/replay tests. Inspect the rendered aircraft at 1080p. Record physical qualification separately; a successful software test does not justify a realistic-flight claim.

For a genuinely new capability, extend its registry, structural spec/schema, physical consumer and complete reset/checkpoint/replay lifecycle together. Add rejection and known-answer tests before registering an aircraft that uses it. Unsupported capability names remain errors; do not add per-ID exceptions to the shared kernel.

| --- | --- | --- |

| Field shape, units, evidence and physical feasibility | [Structural spec](../app/data/schema/aircraft-contract-v2.json), `AircraftContract`, `AircraftData` and module-specific validators | Closed schema, coupled constraints, no usable model on failure |
| Device response, rates, trim and servo motion | `Commands`, `ControlActuators`, `FlightSession` | Conditioning order, radio bypass, state layout and replay |

| Aerodynamic, engine, energy or contact mechanics | Existing shared physics module and its session adapter | All applicable aircraft/laws, timestep checks, reset/cutoff/contact events |
| An aircraft's measured or estimated parameters | Its physical generator/source | Provenance, regenerated dependents, aircraft-specific validation |

Fix shared logic once at its owning interface and test every affected configuration. Keep aircraft-specific calibration in data. A mechanical or handling correction that changes outputs is a separate change with the [flight-log baseline/candidate workflow](FLIGHT-LOGGING.md); never hide it inside a contract refactor or refresh goldens to make the refactor pass.

## Scope and authority

An aircraft file describes one complete simulated configuration, not every possible build of a commercial airframe. The catalog currently contains ten airplane configurations across seven visual families, nine with a wing and tail and one tailless flying wing (X8); the synthetic electric regression specimens also use this format. The experimental X-Cell rotorcraft is a separate branch below. The catalog controls product availability; the file controls physics. A valid file is not evidence of a realistic aircraft. Preserve the evidence kind and source of every number, particularly virtual balancing mass and borrowed aerodynamic/propeller data.

`app/physics/aircraft_data.gd` is the load/derive boundary. Admission proceeds through the closed structural contract, shared `AircraftModules` classification, coupled physical relations and numerical derivation, then session preparation/start checks. `aircraft_contract.gd` rejects inconsistent capability/module selections before deriving a model; Workshop uses that same classifier. The versioned JSON schema is the offline structural counterpart. Its numeric bounds are loader safety/qualified-model limits, not universal laws of aviation. A structurally valid or classified file can still fail area, CG, inertia, lift/fin, table, gear-support, timestep or trim checks. A failure returns errors and no usable model. No unknown version is downgraded automatically.

V1 is retained for explicit historical experiments. It keeps its documented permissive/default behavior; it is not the standard for a new aircraft. Migration must be explicit and reviewed. The loader hashes the actual source bytes and source version separately from its rounded semantic hash. New data invalidates old checkpoint identity even when numerical trajectories are preserved.

## Three ownership layers

| Layer | Owns | Must not contain |
| --- | --- | --- |
| Authored aircraft | Identity, supported capabilities, reference geometry, component inventory, provenance, coefficients/polars, control limits, propulsion/energy, gear and hull | Current RPM, battery charge, servo positions, contact compression, integrated pose or cached trim |
| Derived model | Total mass, inventory CG, full inertia, transformed arms/hull/contacts, strip geometry and calibrated slopes, stall transitions, radians/servo rate, flattened validated tables | Mutable flight history; separately authored copies of values already derivable |
| Runtime session | Pose/velocity/rates, servo positions, engine mode/RPM, wake/shaft/battery states, ground anchors and qualified ground extensions, commands, trim/start, crash and recorder lifecycle | Hidden per-aircraft constants or edits to the source inventory |

Physics and control consumers use the normalized model. Render vectors are allowed only after the float64 simulation boundary. Numerical strip count, 240 Hz step, gravity, integrator safeguards, weather, field friction and input-device shaping belong to shared systems, not duplicate aircraft fields.

## Stable physical identities

New aircraft sources declare `physical_identity_version: 1` within physical `openrc-aircraft v2`. The module is optional for historical v2 files, but complete whenever present: every inventory item and installed gear contact has `id`; `crash_hull_ids` has one ID in the same order as `crash_hull.value`; `propulsion.id` identifies the installation; `controls.surface_ids` maps exactly `aileron_left`, `aileron_right`, `elevator` and `rudder` to IDs, or exactly `elevon_left` and `elevon_right` for `controls: elevon`. Partial modules, unsupported versions, invalid IDs and duplicate IDs block flight.

IDs use lowercase snake_case, start with a letter, contain at most 80 characters and are unique across all five groups within one aircraft. Author semantic IDs such as `wing_right`, `contact_main_left`, `probe_right_wing_tip`, `propulsion_main` and `surface_aileron_right`. Keep the ID when a component's display name, parameters or array position changes. Do not generate it from a name, index or hash; do not reuse a removed component's ID for a different component. Configuration variants may retain IDs for the same inherited components. Scope external references by aircraft/configuration identity as well as local ID.

IDs identify objects, not physical values, component relationships, detachable sections or active capabilities. A hull probe and an inventory mass item have distinct IDs even when both concern the same wing. Keep point and ID together in the authoring generator before projecting the parallel hull arrays. Renaming or reordering must regenerate source-byte-pinned descriptors. Reordering numerical inputs can change floating-point reduction order; adding IDs must preserve the original order and every nonidentity value. Numerical retuning requires separate evidence.

`PhysicalIdentity` validates authored metadata and builds `model.physical_identity`, including ordered ID lists and `inventory_index_by_id`. Derived controls and propulsion retain their IDs; gear contacts retain both their ID and legacy profile name. Workshop v3 resolves inventory bindings by ID; contact observations and propulsion observations consume authored IDs. Existing GP wheel profiles still use canonical contact names and retain their source/profile hashes: changing those names requires the owning profile update. This module does not change that separate profile format.

ID-less historical v2 and explicit v1 inputs retain their existing compatibility IDs. Authored metadata changes source/model hashes, so checkpoints from prior physical source bytes remain incompatible even when numerical trajectories match. Saved Workshop descriptors use their explicit versioned readers; no saved snapshot is rewritten silently. [Migration and verification](research/aircraft-standardization/AS-08-identity/README.md).

## Coordinates, signs and units

- Authored structural positions are metres in `[x_aft, y_right, z_up]`, referenced to the wing leading-edge datum at the centreline. Each visual builder documents its offset to that datum. `frames` is explanatory metadata; `convention_id` selects the executable convention.
- Body axes are right-handed FRD: forward, right, down. For a finite-resource model, body state is referenced to fixed datum O, the authored reference-inventory CG; the live CG can move. Convert structural point `p` from LE datum to O as `r_O = [-(p.x-c_O.x), p.y-c_O.y, -(p.z-c_O.z)]`. `cg_body_m` is the current CG offset from O, so a live-CG force arm is `r_cm = r_O - cg_body_m` and moments use `r_cm × F`. Propulsion `thrust_line_offset` and `intake_offset` are already relative to O, not `balance.plan_cg` (which can differ under `empty_tanks`); do not subtract the authored CG twice. Slipstream `hub`/piece `root`, tail, gear and hull positions remain O-relative. See [MassInventory](../app/physics/mass_inventory.gd), [FixedDatumBody](../app/physics/fixed_datum_body.gd), the [fuel contract](FUEL-SYSTEM.md) and [glow guide](GLOW-ENGINES.md).
- World position uses NED: north, east, down. Altitude above the flat datum is `-down`; local terrain clearance is a separate ground query. Quaternion order is `[w,x,y,z]`, body to NED. Moments use `r × F` about CG.
- Inertia is `[Jxx,Jyy,Jzz,Jxy,Jxz,Jyz]` in kg·m²; off-diagonal entries are negative products of inertia. Authored inventory inertia is about O. For finite resources, stage inertia and its inverse are about the live CG, while `inertia_origin` remains about O; point masses and aligned boxes use the parallel-axis theorem. A declared plan CG validates the selected fuel state and never overrides the inventory.
- Reference area is m²; span and coefficient chord are m. `mean_chord` means **S/b**, including tapered wings, not mean aerodynamic chord. Changing the coefficient reference length requires transforming the derivatives consistently. Planform/CG studies may retain MAC in evidence.
- Aerodynamic force coefficients use wind axes `[-D,Y,-L]`; moment coefficients use body axes at the aerodynamic reference point, then transfer to CG. `alpha,beta` are radians. Normalized rates are `p b/(2V), q c/(2V), r b/(2V)`; dimensional damping avoids division by zero.
- Authored aerodynamic elevator/aileron derivatives are per radian of trailing-edge **down**; rudder per radian of trailing-edge **left**. Pilot/render surface outputs are degrees trailing-edge up/right. `ControlSurfaces.deflections_from_surfaces()` owns the sign/unit conversion; `Aero.deflections_from_surfaces()` remains its compatibility entrypoint. Steering uses its own signed gear angle: negative tailwheel steering is intentional.
- Angled thrust is `[down,right]` degrees and axis `[cos(down)cos(right), cos(down)sin(right), sin(down)]` in FRD. Supported propeller rotation is clockwise viewed from behind; positive shaft RPM has this sense. A turbine has its existing explicit `rotor_sense` ±1.

The frame split follows standard flight-dynamics practice, while these exact datum/sign choices are OpenRC's contract; do not import another solver's inputs without conversion. [JSBSim frame reference](https://jsbsim-team.github.io/jsbsim-reference-manual/user/concepts/frames-of-reference/)

## Presence, evidence and defaults

Each physical quantity is exactly `{value, unit, kind, source}`. `value` is a finite numeric scalar/vector/table of the specified shape; booleans and numeric strings are invalid. Units are exact symbols, not automatically converted. Evidence kinds are `manual`, `measured`, `borrowed`, `estimated`, `derived`; `source` is nonblank and states the derivation or identifiable source. Uncertainty belongs in the source/report until an uncertainty model has a consumer. A guess remains `estimated` even if the simulation passes.

Missing required data is an error. JSON null never means zero or an inactive subsystem in v2. Absence is allowed only for a documented optional module or default below. Zero is accepted only inside a field's domain: zero steering/offset/incidence/current drain is meaningful; zero mass, capacity, span, servo time or static thrust coefficient is not. Empty optional subsystem objects are invalid. Extra keys, misspelled coefficients and inactive-branch parameters are errors.

Explicit in every v2 file: start speed, planform, propulsion kind, capability selections, convention, inventory size (zero box denotes a point mass), gear steering (zero denotes unsteered contact), and propeller rotation for combustion. The following physically defined defaults remain conditional rather than copied everywhere:

Optional inputs retain all dependencies and limits of their runtime parser. They are not globally interchangeable. In particular a propeller crossflow/P-factor/wake module requires an explicit shaft axis; smooth wake currently requires an axial shaft. Ground effect requires the calibrated local wing (strip induced map) and the horizontal tail's `downwash_gradient`. Negative power coefficient (windmilling) requires a rotor-dynamics path. Electric supports its specified motor/ESC/battery law, not arbitrary combustion wake modules.

## Capabilities and conditional modules

Capabilities are closed selections used to validate configuration consistency and select implemented modules. They are included in model identity; the actual normalized modules drive the force and lifecycle consumers.

| Field | Accepted values and rule |
| --- | --- |
| `controls` | `conventional`: aileron, elevator, rudder and throttle only; `elevon` (X8-03): two elevons and throttle, no rudder (see below); requires `airframe_layout: tailless` |
| `gear` | `fixed_tricycle`, `fixed_taildragger`, `locked_down_taildragger`: deployed contact module required; `retractable_tricycle`, `retractable_taildragger` (P51-11b): contacts plus explicit retraction module and paths required, with the tricycle or taildragger topology checks; `locked_up`: contact module forbidden |
| `propulsion_layout` | `single_tractor` for a propeller; `single_pusher` (X8-05) for an electric propeller aft of the CG; `single_centerline_jet` for turbine |
| `energy` | `prescribed_fuel` for fixed-mass combustion/turbine; `finite_glow_fuel` iff explicit glow installation; `finite_liquid_fuel` with `fuel_consumption` and a bound tank; `fixed_voltage`, `ocv_resistance` or `pack_ecm` must agree with electric battery kind |
| `damage` | `terminal_hull`: no flight with structural part loss. Scripted routes terminate on hull contact; interactive soft contacts can scrape or stop a propeller without ending flight. Gear overtravel remains terminal. `tolerant_hull` (X8-08): the same, with the aircraft's own `crash_tolerance` thresholds (see Ground and damage) |
| `airframe_layout` (optional) | Absent: the wing-tail strip law. `tailless` (X8-04): no horizontal element; `aero.surfaces.tailless` required; requires `controls: elevon`; no ground-effect module yet |
| `flaps` | `not_simulated`: no `flaps` block is allowed and modeled flap meshes remain neutral; `simulated`: the `flaps` block and `controls.flaps.hinged_trailing_edge.v1` law are required |

The v2 schema, numerical loader and closed module registry support `finite_liquid_fuel` and `fuel_consumption`, used by the P-51/Corsair gasoline and Ventage turbine sources. Workshop descriptors retain those fields and their exact source identities. This software integration does not close physical validation; see the [fuel standard](FUEL-SYSTEM.md) and [remaining qualification](plans/fuel-mass-balance.md).

For deployed gear, compare each contact's datum-relative x position with `balance.plan_cg` (x increases aft). `fixed_tricycle` requires at least two contacts aft of the CG and one ahead; both taildragger capabilities require at least two ahead and one aft. Contacts exactly at the CG count toward neither side. This runtime topology check is independent of steering angle, so all-zero steering remains valid; it imposes no maximum contact count.

`propulsion.kind` selects `glow_prop`, `electric_prop` or `turbine`. `glow_prop` is a solver-family name for combustion propellers, including the P-51 gasoline engine; chemistry comes from the installation and fuel registry. Prescribed fuel keeps authored wet mass fixed. A declared tank binds one liquid item and one shell by ID; its blend, volume, residue, reserve and inventory geometry are validated. Glow installations and finite-liquid adapters can consume a bound store. Gasoline uses `gasoline_bsfc_v1` with the legacy shaft model; turbine `fuel_flow` is telemetry unless `turbine_map_v1` binds it to a finite store. Liquid depletion changes mass properties using a fixed, uniform tank box and co-moving efflux; there is no slosh or exhaust thrust. Electric configurations do not consume liquid fuel. Hardware named in inventory contributes mass/inertia but does not by itself enable its dynamics.

Every catalog airplane except the gearless X8 has a runway-start path; an airplane without `landing_gear` is offered the hand launch instead ([X8-07](research/skywalker-x8/X8-07/README.md)), and every airplane can start in the air. Menu/start support is a software availability policy, not physical ground-handling qualification; see the aircraft-specific evidence and [fuel gates](plans/fuel-mass-balance.md).

Still outside the active v2 model: EDF duct/fan momentum, pusher wake orientation (X8-05's `single_pusher` applies axial thrust and moments only), multiple propulsion units/differential throttle, reverse-pitch/geared propellers, moving-gear mass properties, slats/spoilers, fuel slosh and general moving/distributed mass, ESC heating/BEC/receiver failures (pack temperature and low-voltage cutoff are specific to `pack_ecm`), structural flexibility/part loss/persistent damage, distributed mass rotation, water/skis and moving terrain. Finite fuel is limited to the documented glow and finite-liquid adapters with uniform fixed tank geometry; it does not admit general resource mechanics. Add a conditional module, consumer, provenance, complete lifecycle state, versioned schema and independent or analytic test before extending that boundary. Do not copy tractor propeller coefficients to an EDF.

`gear.retractable_tricycle.v1` and `gear.retractable_taildragger.v1` (both on law `gear.retractable_point_contacts.v1`; [P51-11b](research/p51-realism/P51-11b/README.md)) admit a rate-limited deployment fraction (0 stowed, 1 downlocked), a binary accepted target and separate main-wheel brake demand. Authored `landing_gear.retraction` quantities are `extension_time`, `retraction_time`, `drag_area` and datum-relative `drag_center`. Each contact supplies `retraction_path`: a flat sequence of 2..513 uniformly spaced LE-datum XYZ triples; all contacts have the same sample count and their final point equals the deployed `position`. The loader converts every point to body FRD about the inventory CG. Downlocked contacts retain the shared suspension/tire law. Unlocked contacts follow their paths with zero load-bearing stiffness and zero admitted travel, so contact is terminal. Gear drag is `-0.5*rho*CdA*extension*|v_point|*v_point`, with its moment about the CG; stowed drag is exactly absent. This point-contact approximation does not simulate pneumatic pressure, structural multibody dynamics or moving mass properties.

This retractable module retains six inputs: primary roll/pitch/yaw/throttle, gear-down target and brake demand, with optional flaps appended. Its two sampled gear states follow anchors/downwash and precede turbulence. Checkpoints pin the gear law/layout; flight metadata v8 and trace v10 carry the complete deployment/target/brake state. Weight-on-wheels retraction inhibition is a simulator interlock. Airborne reset starts stowed; the qualified runway start begins downlocked. Timing, tire and brake estimates remain evidence-labelled aircraft inputs.

Fixed gear can separately admit a shared brake command through an applied wheel profile with explicit `brake_availability = available`, positive torque and matching quantity provenance. `fixed-gear-shared-wheel-brake-input-v1` adds `wheel_brake` at input index 4, then optional flaps at index 5; it adds no gear target or gear auxiliary state. Session checkpoints/configuration and recording metadata pin that law and index. Main's B key uses hardware availability; zero releases clear demand even when hardware becomes unavailable, while invalid mixed external-input packets remain atomic. Unbraked fixed layouts retain their original 4/5 channels. The existing wheel law owns the torque; this input contract does not qualify airborne or differential braking. Legacy CSV Trace uses outer v17 with its underlying format declared; older physics validators intentionally refuse it. See [implementation and evidence](research/ground-physics/GP-12/evidence/fixed-brake-input/README.md).

## Physical modules and parameter effects

The [machine schema](../app/data/schema/openrc-aircraft-v2.schema.json) specifies exact field shapes and per-field numerical ranges. The generated [parameter register](research/aircraft-standardization/AS-01/parameters.md) lists every quantity with its consumer. The [conditional module semantics](research/aircraft-standardization/AS-01/module-semantics.md) define wake, polar, electric and tire parameters in detail. The following is the physical interpretation used when reviewing or tuning those fields.

**Mass and balance.** Inventory mass/position/box size determine total mass, CG and inertia. `balance.plan_cg` and `cg_tolerance` validate the selected authored fuel state; they do not override the inventory. `plausibility.mass_range` is a guard, while `inertia_reference` is a warning against a mass/span-scaled UltraStick comparator, not measured inertia or a calibration target. `balance.firewall` is reference/validation evidence. Where present, virtual balancing mass is not a claim about installed hardware. Positive/physical tensor and rotor-carrier checks remain mandatory. [Inertia sign reference](https://jsbsim-team.github.io/jsbsim/classJSBSim_1_1FGMassBalance.html)

**Aerodynamics.** `CL0,CLa` define the attached lift intercept/slope. `CLq` supplies pitch-rate lift; `CLde,CLda_each` supply control lift. `CD0,CL_minD,k_induced` define the shifted drag polar; `CDda_each,CDde,CDdr` add absolute control drag. `CYb,CYp,CYr,CYdr` define side force. `Clb,Clp,Clr,Clda_left,Clda_right,Cldr` define roll moment. `Cm0,Cma,Cmq,Cmde,Cmda_each` define pitch moment. `Cnb,Cnp,Cnr,Cnda_left,Cnda_right,Cndr` define yaw moment. The derivatives refer to the specified axes, reference lengths and normalization, not dimensional force gains. Stable-airplane sign restrictions currently constrain the admitted model family. `aero.reference_coefficients.CLadot` is preserved historical reference evidence; no alpha-dot derivative reads it. Downwash lag, when configured, derives its own unsteady response from the local tail law.

**Ground effect (M5-GE-1, optional).** `ground_effect.induced_coefficient/induced_exponent` define σ(h/b) = c·(h/b)^e / (1 + c·(h/b)^e), the fraction of each wing strip's induced angle that survives the ground's image vortex system at the strip's height h above the field; the strip keeps (1 − σ) of that angle as extra attached lift and its induced drag at the same CL scales by σ. `downwash_coefficient/downwash_exponent` define the same form for the wing's downwash at the horizontal tail, evaluated at the strips' mean height. Both reach exactly 1 at two spans. The session supplies the field terrain height under the CG; trim, linearisation and static solves are out of ground effect. Separated (flat-plate) flow and the slipstream tail increment are unchanged. The constants are fitted law coefficients (Raymer/McCormick and Wieselsberger image theory, image-VLM tail fit), not measured on any airplane; [evidence](research/ground-effect/M5-GE-1/README.md).

**Tailless airframe (`aero.tailless_swept_strips.v1`, X8-04).** With `airframe_layout: tailless` there is no horizontal element and the wing strips carry all of CLα. `aero.surfaces.tailless` gives each equal-area strip's quarter-chord station `station_x` (root → tip, LE frame), the elevons' spanwise `elevon_coverage` per strip and their `elevon_chord_fraction`. Each strip acts at its own station, so sweep supplies pitch stiffness and pitch damping, and an elevon shifts its covered strips' angle by τ·coverage·deflection and adds a section camber couple km·coverage·deflection on the strip's chord, faded by the strip's separation. As `_induced_map` does for CLα and CL0, the loader solves τ so the strips reproduce CLδe, one common station shift so their neutral point equals the oracle's (Cmα about the ARP), the strips' section moment for Cm0, and km for Cmδe. It refuses a shift beyond a quarter chord, τ outside 0.2–1.5 of the thin-airfoil value for the chord fraction, a section moment beyond ±0.3 or km outside −2…0.5. Clδa, Cmq and Clp remain geometric predictions. `wing_aileron_effectiveness`, `wing_section_cm_ac`, the horizontal element and `aero.ground_effect` are not authored on this law. The vertical element remains one centreline surface: for the X8 it is both winglets together. [X8-04 evidence](research/skywalker-x8/X8-04/README.md).

`envelope.CL_max/CL_min`, blend width and `CD90` derive positive/negative stall transitions; sideslip blend controls the lateral full-envelope transition. The linear oracle remains valid through its qualified small-angle range. Local tail area/position/slope/incidence/effectiveness set actual lift, control authority and moment arm, with attached/local/stall blend bounds and `tail_CD0/tail_k/tail_CD90` drag. Wing aileron effectiveness and six station incidences control local asymmetric loading. Strip slope, lift offsets and induced-flow map are derived to reproduce the global static oracle, not additional user coefficients. The fin's global force/moment derivatives must match its local force and arm. Optional tabulated wing polars retain separate positive/negative branches with provenance and bounded extrapolation. Low-Reynolds-number and post-stall measurements remain aircraft-specific. [UIUC research/data](https://m-selig.ae.illinois.edu/pd.html)

**Controls.** Max throws bound the physical surface travel used by both aerodynamic and visual mapping. Servo full-throw time is neutral to full deflection, not a 60° manufacturer spec; its inverse is the normalized servo rate. Transmitter expo/dual rates and keyboard response belong to the input layer. The same shaped servo state drives rendered surfaces and physics; no renderer-only retuning. Aileron differential is explicit in Ventage Jet.

**Elevons (`controls.elevon_mixing.v1`, X8-03).** `controls: elevon` declares `max_throw.aileron` and `max_throw.elevator` as the roll and pitch shares of each elevon at full stick and `max_throw.elevon` as the servo end point; `aileron_down` and every rudder field are absent and `rates.normal` has no rudder axis. `ControlSurfaces.elevon_deflections_deg()` mixes like a radio: each elevon takes pitch·elevator ± roll·aileron, clipped at the end point, and returns the exact symmetric (`elevator`) and antisymmetric (`aileron_*`) decomposition of the clipped pair, so aerodynamics and the rendered elevons (elevator + that side's aileron) agree, saturation included. The yaw stick moves no surface. The model has no rudder: `CYdr`, `Cldr`, `Cndr` and `CDdr` are exactly 0, the vertical element's `control_effectiveness` is 0 and the normalized rudder throw is 0. Trim replaces the rudder unknown with the bank angle (steady straight flight; at most 15°) and checks that each elevon's elevator ± aileron fits the end point. Servo rate limits still act on the three logical channels before the mix, so one elevon can move slightly faster than a real servo.

Optional `controls.keyboard` requires `rates.normal` and two evidence-bearing seconds quantities, `pitch_press_time` and `pitch_release_time` (0.05–5 s). They specify neutral-to-full virtual-stick travel and full-to-neutral return before normal-profile expo/rates. Opposite input centers at the return rate before building the reversed input at the press rate. Only live keyboard normal-profile sampling consumes them; full profile, scripted commands and connected controllers retain their existing mappings. These device settings do not change physical servo time, aerodynamic limits or available travel. Missing configuration retains the shared keyboard response.

Optional `controls.gamepad` requires `rates.normal` and evidence-bearing `pitch_scale` (`1`, 0.05–1). In normal mode, a connected gamepad multiplies its already shaped pitch command by this fixed factor after aircraft rates and before trim. Device expo is applied once by the gamepad profile. Full mode, keyboard and physical radios bypass this factor; absence means unity. This is short-stick device travel, not a manufacturer setting, servo change or state-dependent flight assist. Ventage Jet uses 0.4 (±6° before trim); the physical maximum remains ±30°.

The same object optionally declares `yaw_scale` (`1`, 0.05–1; absent = unity) and `yaw_response_time` (`s`, 0.02–0.5; absent = immediate). Armed gamepads in Normal mode apply a first-order yaw-demand response after device conditioning, before aircraft rates, fixed travel scales and trim: `target + (previous-target)*exp(-dt/tau)`. The existing `commands.yaw` is its state and reset centers it; `raw.yaw` retains the conditioned device target. Holds freeze it; unarmed input returns neutral immediately. Physics checkpoints retain the resulting simulation input downstream of conditioning; they restore paused recorded-input replay, not live controller/filter state. Full, radio, keyboard and scripted accepted-input paths bypass the response. It reads no motion or airspeed. The same resulting yaw command feeds any declared nosewheel mix. Ventage Jet uses a 0.10 s time constant and 0.5 yaw scale (±12° before trim).

**Flaps (`controls.flaps.hinged_trailing_edge.v1`, optional).** `capabilities.flaps` must be `simulated` exactly when the closed `flaps` object is present; `not_simulated` forbids it. Runtime state is normalized `[0,1]` over the authored maximum angle. Extension/retraction times are full-range effective installed travel; they are not naked servo speed. `max_speed_mps` is an estimated equivalent-airspeed advisory at reference density, not a flight limiter. The loader integrates flap span against validated tapered chord and six-strip boundaries. Thin-airfoil plain-flap effectiveness shifts local incidence; the authored effective-angle bound limits this estimate before the ordinary coupled stall/polar law runs. The bounded separated-flow lift increment contributes to induced drag and the wing downwash source. `profile_drag_coefficient` is an estimated local drag coefficient applied over covered wing-strip reference area (not flap-panel wetted area) and scaled by deflection. A Glauert thin-airfoil `dCm/dCL` ratio supplies a quarter-chord couple from actual nonlinear strip ΔCL; the whole-wing lift increment is not moved to the aft panel. Only the estimated profile-drag increment uses the flap-centre lever. Total aircraft pitch follows wing, tail and downwash loads and may differ in sign from the local section couple. For AV-09, the SebArt manual sets normal/start/landing flaps to 0°/20°/50° and requests 8%/20% down-elevator mix. That mix is separate from aerodynamic compensation, linear in accepted flap fraction, and measured as a fraction of full elevator travel. This remains an estimated Avanti section/drag law pending aircraft-specific polar and flight data. [AV-09 source and assumptions](../research/avanti-s/av06/derivation.md#flaps-av-09). Two optional fields refine it (P51-11a; absent = the law above, byte-identical): `stall_shift_fraction` (κ, 0..1, strip stall blend only, rejected with a tabulated `wing_polar`) moves a flapped strip's stall onset by κ of its camber shift instead of all of it, so section CLmax rises by slope·(1−κ)·shift as plain-flap data show; `lift_reference_offset_m` applies the flap camber lift that far aft of the strip force point (the wing's quarter chord when the ARP is a wing-body centre). [P51-11a evidence](research/p51-realism/P51-11a/README.md).

**Combustion propeller.** Static maximum/idle RPM and lag define the legacy governor approximation. A shaft module instead supplies indicated peak/idle power, friction torque and its normalized power curve; propeller torque loads the rotating inertia. Brochure `peak_power/peak_power_rpm` are validated reference evidence and never replace the shaft curve. Diameter and Ct/Cp tables define `T=Ct ρ n² D⁴` and `P=Cp ρ n³ D⁵`, where `n=RPM/60` and `J=Vaxial/(nD)`; power/torque must use the same reference convention. Axis/CG-relative application point determine force direction and moment; rotating inertia also supplies gyroscopic/acceleration coupling. Normal-force/P-factor tables and geometric wake pieces are explicit opt-ins with existing dependency checks. Preserve measured versus borrowed propeller identity and Reynolds/RPM limitations. [UIUC coefficient and test definitions](https://m-selig.ae.illinois.edu/props/propDB.html)

**Turbine.** The throttle map, RPM limits, governor time and acceleration/deceleration limits determine spool state; static thrust, installation factor, mass flow and offsets determine force and ram/inlet moment. Optional ram tables are fitted corrections; rotor inertia/sense determine angular-momentum coupling. `engine.fuel_flow` is telemetry by itself; `turbine_map_v1` plus a bound finite store drives consumption and changing mass. This branch has no propeller Ct/Cp/shaft/wake module. See the [fuel-mass plan](plans/fuel-mass-balance.md) for integration and acceptance gates.

AV-20's explicit `spool_integrator: rk4` evaluates RPM, thrust and gyro at each RK stage; `AUX_RPM` is only the accepted endpoint mirror. Prescribed-fuel schedules remain unchanged. The launch preflight rejects a governor/rate-table slope whose timestep ratio exceeds 0.25. Checkpoint v8 identifies this law; collision wrapper v7 carries it as its inner physics format. Unpowered glide starts initialize zero continuous RPM. Changing the running mode at nonzero RPM is refused. The finite-tank fuel adapter is separate from turbine spool dynamics; see the [turbine realism](plans/turbine-realism.md) and [fuel-mass](plans/fuel-mass-balance.md) plans.

**Electric.** Kv, winding-equivalent resistance and no-load current define the DC motor law; no-load voltage/RPM/temperature are evidence context, not a thermal model. The ESC is ideal motoring only, with no active braking or regeneration. Fixed-voltage is an infinite prescribed bus; OCV/resistance evolves charge and delivered energy; `pack_ecm` adds average/weakest-cell Thevenin branches, pack temperature and an ESC low-voltage cutoff. Pack data use generated `openrc-battery v1` bytes pinned to an `openrc-cell-template v1`; the aircraft's mount mass must match the pack, and LiPo mounts need `energy_source: "lipo"`. Regenerate packs from `research/battery/bat-05/build_batteries.py`, never edit generated data. See the [BAT-04 specification](research/battery/BAT-04/specification.md) and [electric propulsion guide](ELECTRIC-PROPULSION-PLAN.md). Catalog pack mode is the default where `battery_data` exists; the ideal-bus variant remains selectable. Carrier inertia and timestep stiffness checks apply before flight.

**Ground and damage.** Each deployed wheel is an undeformed contact point with spring stiffness, damping, compression travel and signed steering angle. Rolling resistance, side friction and peak slip set the existing tire law; optional breakaway enables anchors. Contact support, nonnegative load, damping, heave/slip timestep and sag/travel checks protect the integrator. The field, not the aircraft, selects terrain/surface conditions. Ground-track wheel profiles/spin/brakes are separately versioned interfaces and must be validated where attached; AS does not invent them. Hull vertices locate soft or terminal contact under the selected session policy; wheel support points must not become duplicate hull crash points. Each contact must sit on its rendered wheel bottom through the manifest datum, and its travel must survive the reserve-energy drop; `test_gear_visual_contacts.gd` and `test_gear_reserve_energy.gd` check every geared catalog aircraft ([GP-06](research/ground-physics/GP-06/README.md)). A `tolerant_hull` aircraft (X8-08) declares `crash_tolerance`: `terminal_specific_energy` (J/kg, 2.5–50) and `crash_depth` (m, 0.08–0.3) replace the shared 2.5 J/kg and 0.08 m terminal hull thresholds through `HullContact.prepare()`, and `presentation_durability` (1–10) divides the crash presentation's specific energy; they are estimates for a foam airframe until drop tests exist. Travel exceedance/impact reports and the wreck are not structural damage models. Optional `crash_hull_components` names each hull vertex, in order, from a closed vocabulary (`left_wing_tip`, `right_wing_tip`, `spinner`, `propeller`, `nose`, `tail_end`, `left_stab_tip`, `right_stab_tip`, `fin_top`, `canopy`, `belly`, `engine`, `left_wing_root`, `right_wing_root`; root names identify the inner wing supports separately from tips; left/right by `y_right`). The list length must equal the hull. Only crash presentation reads it; it names the nearest hull vertex, not a structural section. Every shipped aircraft declares it through its generator ([CR-01d](research/crash-damage-investigations/CR-01d/README.md)). An inventory item may carry an optional `energy_source` (`kerosene`, `glow_fuel`, `gasoline`, `lipo`) for crash fire and smoke presentation only; never infer it from a name or the propulsion kind ([CR-22b](research/crash-damage-investigations/CR-22b/README.md)). Visual models from Blender name breakable parts with an `openrc_section` custom property, exported as glTF extras; a model already merged into one mesh uses a generated section map instead ([CR-09c](research/crash-damage-investigations/CR-09c/README.md)).

The concurrent GP-03 interface is `openrc-wheel-profiles v1` in `app/data/ground/wheel_profiles.json`, keyed by exact aircraft ID and unique contact name. `WheelProfiles.apply_to_model()` runs after the aircraft derivation at the file-load boundary; invalid profiles block flight. In-memory aircraft derivation deliberately excludes this attachment. A deployed aircraft without a profile reports `legacy_fallback`; absent gear reports `no_gear` and rejects any matching profile. Neither absence silently enables brakes. Applied profiles carry their own identity into the session; file-backed v1/v2 comparisons must apply the same profile to both. Wheel radius, inertia, relaxation and brake inputs, consumers and limits are documented in the [module supplement](research/aircraft-standardization/AS-01/module-semantics.md#concurrent-ground-profile-interface). This separately owned extension is outside the 152 aircraft-quantity paths and the frozen AS numerical-migration comparison.

## Lifecycle and other consumers

Selected catalog ID, loaded model ID and visual builder ID must agree on normal catalog startup; research electric donors deliberately reuse the Stik visual adapter. A mismatched selection is rejected before trim/flight. Reload validates a complete candidate and preserves the previous model/state if it fails. Reset selects the aircraft's declared trim speed, restores energy/engine/servo states and clears crash/recorder state. Pause holds those states. Checkpoints identify the complete model and solver/environment configuration and reject another model; new auxiliary state requires layout/reset/restore coverage.

Trace metadata records the real input format/hash, model ID, active propulsion/wake/aero law and start state. UI, HUD, camera, sound and crash presentation must consume normalized values or explicit presentation metadata; none may change physical constants. Visual geometry and control-node names remain owned by the model tracks. Future fuel/part effects must not infer hardware from a filename or free-text inventory name.

## Shared module and runtime interfaces

`app/data/schema/aircraft-modules-v1.json` is the shared classification registry consumed by Python `research/aircraft-standardization/modules.py`, GDScript `AircraftModules`, physical flight admission, Workshop descriptor validation and compiler eligibility. It distinguishes capabilities, installed law families and permitted compiler transforms. Classifier diagnostics carry `code`, `path` and `message`; the physical loader preserves its existing error-list interface and renders those paths as `/`-separated source locations. Classification does not mutate the authored data or add fields to the normalized model, replace numerical validation or qualify a combination. Shaft-balance classification leaves the selected split/coupled integration route to the session. Fuel bindings, tailless coupling, gear support topology, inertia and wake constraints remain with their physical validators.

`ControlSurfaces` owns conventional command-to-surface, aerodynamic and visual sign mappings. Existing Commands/Aero entrypoints delegate to it; input shaping, trim and servo dynamics retain their previous state and order. One logical elevator can bind two visual hinges. That does not invent two independent physical actuators.

`ControlActuators` owns the existing sampled rate-limit arithmetic and a detached, validated batch kernel for normalized positions. A batch index is not an authored actuator identity. Current aircraft retain three logical servo states; `FlightSession.surface_angles_deg()` exposes their accepted surface angles to rendering through the same conversion used by aerodynamics. The independent four-position conversion is a software-fixture seam, not an admitted hardware capability. A future topology module must declare actuator-to-surface relationships and complete state ownership before independent jams enter the random pool; split elevators additionally require separate tail loads. [EM-03a boundary and evidence](research/failure-mode/EM-03a/README.md).

`AircraftPropulsionRuntime.prepare_callbacks()` selects the existing single-installation stage callbacks from validated configuration, before endpoint state exists. `FlightSession.propulsion_observation()` exposes the current family, canonical law, RPM and existing family telemetry/layout. Preparation never reads previous-family state; observation does not change it. Existing continuous/sampled laws and checkpoints remain distinct. The compatibility installation ID is scoped to the aircraft; it is not a multi-engine schema.

`FlightSession.contact_contract()` describes support IDs, ordered hull probe IDs, rotor disc, wheel-profile status and selected response policy. Preparation rejects malformed or duplicate support/probe bindings. Authored hull/support IDs are used when present; ID-less data retains ordered `hull_point_NNN` IDs and contact names. `rotor_id` is `propeller/<propulsion.id>` for an authored propeller, with legacy `propeller/single` fallback. Hull labels remain separate from visual sections, which are explicitly unbound. Current friction, terminal thresholds, prop-strike behavior and differences between interactive/scripted routes are preserved.

### Contact observations and checkpoints

`FlightSession.contact_events()` returns a detached `openrc-aircraft-contact-state v1`: the last accepted tick, active hull IDs, that tick's normalized events and the flight's propeller-strike latch. It is a bounded observation buffer, not a cumulative log. `AircraftContactEvents` serializes observations as plain `openrc-aircraft-contact-events v1` records with source/contact identity, tick, lifecycle, selected policy and response. Available positions, velocities and measures retain float64 precision; missing kinematics or impulses are never invented.

Subscribe to `contact_events_changed` and read that snapshot to consume events, including ground/strike decisions between integration steps. Accepted step publication is batched after contact and scenery-damage commit; rejected candidates emit no contact notification. Reset and successful replay restoration also notify readers.

Hull observations use `new`, `persistent` and `ended`; a terminal hull decision replaces that point's observation. An `impact` or `strike` record is a new response decision, not a second hull-onset signal. Scenery and lake events also identify the aircraft probe and swept contact fraction. Pending scenery impulses cannot be recorded as applied responses. Existing typed crash/scenery/lake feeds remain available; ground and strike checks keep their existing entry-route timing.

Swept collision filtering stages presentation and damage. `Simulation.stepped` publishes them only after body and continuous-state validation; rejected steps discard the staged records and roll back water engine-stop modes. Reset seeds already-touching hull IDs without inventing onset events. Failed aircraft reloads restore accepted contact observations and the broken-propeller latch.

Flight checkpoints retain their existing physics versions and add a separately versioned `contact_state`. Save/restore validates tick, active geometry, aircraft/environment references, policy and strike payload before accepting it. Legacy checkpoints without this field still restore: ongoing contacts are seeded from the saved pose, while unrecorded events and the visual strike latch remain unknown/empty. Restore remains paused recorded-input replay and clears transient crash/wreck presentation; it is not a complete live-session save. [Acceptance and compatibility evidence](research/aircraft-standardization/AS-13/README.md).

## Model and package contract

`openrc-aircraft-model` describes presentation independently of physical aircraft v2. Version 1 retains the existing zero-argument model builders; version 2 selects the common imported-scene builder with an explicit `construction` projection. Its source is `assets/aircraft/model-bindings.json`; `research/aircraft-standardization/build_models.py` generates `app/data/aircraft_models/<family>.json`. Catalog `visual_family` resolves a physical configuration to that manifest. The four Stik configurations share one family. Unknown families never borrow a default model.

A manifest pins the builder and adapter, geometry source/revision, datum selectors, asset identity, logical controls, rotor, gear and crash-section provider. Each control declares `hinges: [{key, node, source, geometry_ref}]` and `visual_only`. Control roles are `aileron_left`, `aileron_right`, `elevator`, `rudder`, optional `flap_left`/`flap_right`, and `elevon_left`/`elevon_right` (X8-02): a family declares either the four conventional roles or exactly both elevons and no aileron, elevator or rudder role. The renderer draws an elevon as the elevator plus that side's aileron (degrees, trailing edge up), the exact inverse of the physics decomposition. Timber references its existing geometry articulation records; do not copy pivot/range/sign tables into another source. Scene validation requires the declared nodes beneath `airplane`, retains `propeller` and `*_hinge`, and checks imported asset/crash-map identity. Existing procedural builders are retained. `render/airplane.gd` consumes these bindings without aircraft-ID dispatch.

Version 2 uses `res://aircraft/imported_model.gd` and passes the validated manifest to `build(manifest, livery_id)`; an empty `livery_id` builds the default asset. Its closed construction version 1 declares:

- `hinge_axis: "+X"`: each imported control's local X axis and rest basis define its rotation. Multiple hinges may share a conventional role. Geometry supplies ranges and `app_sign`; physical surface commands are not clamped by the renderer. Visual-only roles have a separate clamped inspector path.
- `rotor: {frame_node, geometry_ref, axis}`: a geometry-backed parent frame and its declared spin child. `axis` is a signed cardinal axis in that frame; the public wrapper still spins through `propeller.rotation.z`. An absent rotor uses `{}` and a compatibility marker. This visual convention does not enable a new physical propulsion layout.
- `gear: [{role, node, geometry_ref, wrapper}]`: fixed gear roles have geometry-backed pivots and named Euler wrappers. Wrappers preserve rest transforms, with ancestors constructed before descendants; wheels use root X and steering root Y at rest.
- Optional `retraction: {geometry_ref}`: selects a version-1 sampled gear rig with explicit local transforms, rest bindings and wheel paths for left, right and one steered nose or tail wheel (F4U-02). In this mode `gear` is empty and the four logical roles are left/right/steering plus `nose` (tricycle) or `tail` (taildragger); the rig's wheels must match the family's gear keys, and imported carriers rest at the fully stowed first sample. Exported helper nodes provide wheel-local +X spin and +Y steering, oriented correctly when deployed; compression moves the declared lower-strut assembly. The compression helper may itself be a sampled carrier, such as an oleo slider that moves during the cycle; compression then offsets its sampled pose (F4U-05). Spin and steering helpers are never sampled. The renderer interpolates carrier quaternions and translations from the accepted physical extension, then applies wheel motion. This extension validates its complete rig before construction and never writes simulation state.
- Optional `folds: [{key, geometry_ref}]`, one or two (F4U-17): folding wings as in-place fold groups. Each geometry record names its `members`; their parents must sit at the model frame, and members are typically a panel mesh and the control hinges it carries. It also gives a `pivot`, a unit `axis`, a `sign`, `max_angle_deg`, the mechanism law (`lock_release_fraction`, `travel_fraction`: angle = max × clamp((q − release) / travel, 0, 1) for a mechanism state q in 0–1) and a cycle `time_s`. The builder turns the members about the axis without re-parenting, so node paths, paint targets and crash sections are unchanged. A control hinge on a folding panel composes its own deflection with the fold. Presentation only: the session holds the throttle at idle through `set_throttle_hold` while the wings are not spread and locked.
- Optional `mechanisms: [{key, geometry_ref}]`, at most one each of `canopy`, `tailhook` and `cowl_flaps` (F4U-21): auxiliary mechanisms the flight scene drives by a 0–1 state. Each geometry record gives a cycle `time_s` and `parts`; a part names its `members` (parents at the model frame) and either slides by an `offset` or turns about a `pivot` and unit `axis` by up to `max_angle_deg`, in proportion to the state. An optional `ground_point` keeps that point of the part above the ground in the flight scene (a lowered tailhook rests on the runway). A member may not be, hold or sit under a node a hinge, fold or other mechanism moves. The builder moves members in place. Presentation only.
- `material_grow: [{node, materials, amount_m}]`: optional per-instance StandardMaterial3D surface offsets, positive and at most 0.01 m. Timber retains its existing 0.8 mm black/red cowl seating correction through this declaration; shared imported resources stay unchanged.

The importer rejects missing or ambiguous nodes, wrapper collisions, mismatched geometry node/parent/rest references, nonfinite transforms and scaled/sheared/reflected articulation ancestry before returning a model. Geometry records expose `node`, `parent`, `rest_translation` and `rest_basis`; measured rest transforms agree within 0.00002 per vector norm to allow six-decimal source measurements. These are presentation checks. Version 2 accepts authored glTF sections or no sections; the legacy generated triangle-map route remains with version 1 builders. Timber's inspector entrypoint is a compatibility facade over the common builder. [Migration and pose evidence](research/aircraft-standardization/AS-09-10-import/README.md).

A version 2 manifest may declare `liveries` (F4U-16): two to sixteen selectable paint schemes of one airframe (eight until F4U-20), each a whole GLB with its own import sidecar. Each entry is `{id, label, path, sha256, import_sha256}`: a unique lowercase ID, a printable label of at most 48 characters, and an aircraft GLB path. The first entry is the default and must be the manifest `asset`. The family's bindings declare `asset.liveries_path`, a reference into its geometry source, where the aircraft generator lists `{id, label, path, glb_sha256}`; the generator proves that every livery is the same airframe (node names, hierarchy, rest transforms, section tags, mesh bounds, triangle count). `describe()` verifies only the default asset; `model_registry.livery()` verifies another livery's GLB and sidecar when it is built, and the importer checks its scene against the same generated geometry. The built root carries `livery` and that GLB's `asset_sha256`. Materials, textures and surface splits may differ between liveries, so Workshop paint slots and markings apply to the default paint only. Home stores one choice per catalog aircraft (`[liveries]` preferences); the direct route takes `--livery=<id>`.

An imported sectioned GLB uses the `gltf_extras` crash provider with empty `metadata_script` and `asset_node`. Every mesh and articulated pivot declares a supported string `extras.openrc_section`; validation rejects missing or invalid IDs and detachable ancestors that would capture another section (for example an engine parent containing the propeller). Timber r2 uses these authored objects directly. The legacy `generated_triangle_map` provider remains supported for merged assets; do not apply an r1 triangle map to a revised mesh.

Manifest validation resolves dependencies freshly at build/trial preparation. UTF-8 source text uses explicitly declared LF-normalized SHA-256; binary assets use raw SHA-256. Generated manifests themselves have canonical LF bytes and Workshop v2 pins their exact hash. A frozen trial passes that binding to the renderer and refuses a changed model. Rendering caches the accepted datum; no source traversal or hashing runs on a physics tick or ordinary rendered frame.

After changing a shared model dependency, refresh every affected family and its downstream bindings in order:

```sh
python research/aircraft-standardization/build_models.py
python research/aircraft-standardization/build_customization.py
python research/aircraft-editor/build_descriptors.py
```

Repeat each with `--check`, then run the affected model/presentation checks. Review the generated diff: unchanged geometry can still require new dependency and manifest hashes. Do not bypass validation or update only the aircraft that exposed the mismatch. Existing saved Workshop variants retain their original identities.

Godot can compile scripts and convert imported resources during export. The aircraft export plugin includes verified source-proof bytes and a package-only proof table, while the runtime also checks that actual compiled/imported resources resolve. These hashes identify exporter inputs, not the byte representation of platform-specific imported scenes. Missing, malformed or incomplete package proofs block model acceptance; they never fall back to adjacent source files. [Godot FileAccess guidance](https://docs.godotengine.org/en/4.3/classes/class_fileaccess.html)

The [reusable Blender handoff](BLENDER-AIRCRAFT-DELIVERY.md) defines common authoring/export coordinates, pivots, sections and all-skin delivery requirements; each aircraft's brief supplies its datum, dimensions, applicable mechanisms and budgets. The [Timber r2 handoff](BLENDER-AIRCRAFT-HANDOFF.md) retains that aircraft's specific requirements. The common preflight adds generated-manifest, dependency, actual neutral/full-travel pose, independent-instance and package checks. It reports mesh counts; it does not establish a universal polygon budget or physical validation.

Aircraft lighting uses the [shared presentation standard](AIRCRAFT-LIGHTING.md): flight-local manual overrides, a configurable 17:30 civil-time default, existing solar policy and per-model light anchors/groups. These bindings do not add simulation state or change the physical aircraft schema.

## Adding and tuning an aircraft

Use the [authoring sequence](#add-an-aircraft-using-supported-laws) for registration and shared checks. Do not copy a donor's generated articulation or crash triangle map: derive the new asset's bindings from its own source and hash-bound metadata.

For physical calibration, establish one structural/visual datum and retain measurements of span, area, chords, CG, component masses/positions and uncertainty in the owning track's research. Set actual control hardware travel/time and propulsion tables. Fit attached aerodynamics with consistent reference quantities, then local stall/tail behavior; keep calibration observations separate from held-out verification. Change one mechanism at a time and compare retained flight logs, state traces and force budgets. Manufacturer limits, independent measurements and qualified pilot feedback decide physical acceptance. Self-consistency and exact software replay do not replace those gates.

## Damage and cost authoring dossier

**Authoring requirement added 2026-10-15; initial runtime economics support implemented.** Every new aircraft/configuration must include a versioned cost and damage dossier outside the physical v2 file. The [CR-28…38 plan](plans/crash-damage-economics.md) owns calculation rules, rollout and remaining acceptance; the [initial USD catalog and evidence](research/crash-damage-investigations/CR-28/README.md) provides examples. Existing configurations migrate through CR-36. Do not insert economic fields into the closed physical v2 schema.

The implemented sidecar is `app/data/economy/catalog.json`, generated by `python research/crash-economics/build_runtime.py` from the researched prices, costing assumptions and current aircraft catalog. Run that command with `--check`, `python research/crash-economics/test_runtime_data.py` and `app/tests/test_economy_catalog.gd` after authoring. `app/economy/catalog.gd` validates route coverage, component quantities, non-overlapping inventory allocation, source hashes, price references and explicit missing coverage. If the physical bytes changed but the generated `physical_signature` (item names, masses, energy sources, contacts, propulsion identity) still matches, the runtime keeps the costs and the report says so. The generator check still requires regeneration. A whole-valued JSON amount is normalized to integer cents before calculation. The current schema supports selected, non-overlapping cost lines. Compatible repair recipes and a bounded replacement-only comparison are supported; package authoring/selection UI and workshop transactions remain pending. See [implementation evidence](research/crash-damage-investigations/CR-29-32/README.md).

The dossier must identify the complete installed build and its assembly basis, itemized quantities and products, covered/included equipment, stable physical inventory/contact/section mappings, replacement and repair packages, salvage/inspection restrictions, sources/dates/currencies and explicit missing prices. Include airframe, covering, propulsion, gear, controls, receiver, onboard power and conditional fuel/electric/turbine systems. A package and its included components must not both contribute their full price. Transmitter/charger/field tools are outside onboard loss; virtual balancing mass is nonpurchasable. Grouped physical inventory must declare real part counts without inventing independent hardware state.

For a baseline-derived configuration, author `inherits` and complete `component_overrides` rows in the research fleet entry. Overrides replace existing economic groups by ID; they must preserve each group's physical inventory bindings and installed quantity. Pin every overridden physical item in `expected_inventory` (`id`, exact `name`, `mass_kg`, `position_m`, `energy_source`), and the installed `id`, `kind`, `engine_name`, `propeller_name` in `expected_propulsion`. The generator rejects unreviewed differences in inherited hardware, missing pins, changed groups, unknown prices or inconsistent propulsion identities. Inventory additions/removals or quantity changes require a separate BOM. This checks correspondence to the authored simulation configuration, not real-world installation safety or fit. Keep shared estimates explicitly labeled; complete inventory coverage does not mean all prices or hardware are physically qualified.

Use exact product revision and installation compatibility when known; label every substitute, estimated allowance and unknown. Market price never establishes structural strength, hardware compatibility or partner status. Preserve damage-material/joint evidence and uncertainty separately from commercial observations. Missing/stale prices leave valuation incomplete; they do not invalidate an otherwise physically valid aircraft or silently become zero dollars.

For an independent build, author a fleet-entry `dossier` with exactly `expected_source_sha256`, `lines`, `contact_components`, `propeller_component_id` and `propeller_inspection_ids`. Do not combine it with `inherits`. Pin the reviewed physical JSON's exact SHA-256; source changes require a BOM review before updating that pin. Lines use the baseline line schema, including quantities, physical IDs, evidence kind, notes and optional offer/estimate/range. Omit both offer and estimate for an unknown price: the generated `unit_minor` remains null and adds an explicit missing reason. Keep nonpurchasable virtual balance excluded; map every installed item once and add assembly labor separately with no salvage binding. Whole-aircraft completeness requires both inventory coverage and resolved prices/missing reasons. Bind prop contacts and required inspections explicitly. Map each hull probe and gear contact in `contact_components` to the economic groups it covers; a retained contact then names those groups as pending inspection ([CR-39](research/crash-damage-investigations/CR-39/README.md)). This authoring data does not itself infer damage. [CR-36b](research/crash-damage-investigations/CR-36b/README.md) demonstrates independent partial coverage for the Extra 300S.

For a composite price estimate, a research line may declare `price_constituents: [{"offer_id": "offer-id", "quantity": 1}]` with `evidence_kind: "estimated"`. Each referenced offer and positive integer count must be explicit and unique; do not combine constituents with a single offer or manual estimate. The generator sums integer cents and retains each source URL, observation date, stock state and quantity in the compiled notes. This is an estimate assembled from separate offers, not a sold package or verified installed hardware. Do not double count servos included in a wing or reuse one wheel-set price for two gear groups. Keep partial assemblies unpriced until all required content is covered. A combined propeller/spinner group is not eligible for automatic propeller-only billing. See [CR-36d](research/crash-damage-investigations/CR-36d/electric.md).

Price observations and report snapshots have their own identities, independent of physical source hashes. Changing an offer cannot change a flight/replay or retrospectively alter a saved accident bill. Installed hardware changes still follow the existing generator, mass/CG/inertia, Workshop and conformance contracts. The separate economics generator and runtime loader enforce dossier coverage; economic completeness does not alter the physical aircraft loader or its flight-validity gates. Active-flight economic checkpoints pin the catalog, repair recipes, physical source and contact bindings; they cannot resume after an incompatible refresh. See [CR-30c](research/crash-damage-investigations/CR-30c/README.md) for native checkpoint and terminal-archive limits.

Economic repair recipes are packaged separately in `app/data/economy/repair-recipes.json` by the same runtime generator. A priced recipe must declare compatible aircraft IDs and economic component IDs, damage class, material package units/price/provenance and explicit labor policy. The planner requires inspected scope, integer material measurements and labor minutes; it never infers them from a mesh, visual fire or price. New aircraft do not inherit recipe applicability from a shared airframe label. Inspection receipts bind the frozen incident/source/catalog identities and revision; see [CR-31b/c](research/crash-damage-investigations/CR-31c/README.md).

Replacement alternatives use explicit `component_id:index` coverage tokens for the requested replacement quantity, integer cents or null, compatibility/availability flags and price/contents provenance. The index enumerates fungible units in that quote; it does not identify a physical servo position, serial number or independent simulation state. Reuse the dossier's economic groups and avoid overlapping package contents. `Incident.compare_replacements()` is read-only and does not apply the selected package or change the accident bill. Every comparison preserves the distinction between parts cost and complete repair/loss; see [CR-31e](research/crash-damage-investigations/CR-31e/README.md).

Service-part research must retain the exact manufacturer model/part crosswalk and whole-unit price reference. A whole-engine price proxy does not grant mechanical compatibility to that engine's crankshaft, silencer or other internals. Keep service offers outside the installed BOM until an explicit repair recipe identifies the applicable component and inspected scope; do not add the service part and whole-unit replacement together. See [CR-31f](research/crash-damage-investigations/CR-31f/service-prices.md).

The research generator preserves service crosswalks in `service_parts`; runtime generation validates them against the authored records before building prices. They grant neither installed-aircraft applicability nor automatic repair selection. Explicit planner repair decisions retain a boolean `replacement_comparable` scope assertion: unlike-scope prices cannot override the selected repair. Legacy decisions without that optional field keep their original comparison behavior. See [CR-31g](research/crash-damage-investigations/CR-31g/README.md) for receipt and report evidence.

Run the [offline price upkeep audit](research/crash-damage-investigations/CR-38a/README.md) with an explicit review date when refreshing or adding an aircraft dossier. Review each observation date, package contents, approximation basis and remaining gap; a recent catalog snapshot does not refresh older offers. A positive affected quantity is required for each explicit assessment row. New replacement-comparison archives retain selected costs and unit coverage for internal consistency checks; old snapshots remain view-only historical estimates.

For a price revision, retain the old audit snapshot and run the [snapshot comparison](research/crash-damage-investigations/CR-38b/README.md). Record product/package/seller and commercial terms before interpreting a delta; a sale quote requires separate rechecking even when recently observed. Pending total-loss inspection leaves aggregate salvage unknown unless explicitly ineligible; confirmed reuse credits remain itemized. See [CR-31h](research/crash-damage-investigations/CR-31h/README.md).

## Workshop authoring standard

The optional `ground` module currently supports explicit legacy selection and authored `coupled_thin_ring_compliance_v1` resources: pinned existing wheel hardware, stable support IDs, LE-frame hubs/unit axles and separate compliance resources. Its optional estimated aggregate rotor partition supplies transverse inertia and reference-pose provenance without duplicating wheel radius, axial inertia or brake ownership. Optional steering resources bind a paired linkage ID/unit hinge axis to each steered support; the fixed hub is the hinge origin, and actual rudder-servo output drives continuous angle/rate states. Travel, response time and rate/acceleration bounds require explicit quantities. The runtime structural contract and generated offline schema both recognize these fields. **Valid coupled authoring remains launch-unavailable until the complete aircraft adapter is qualified**; invalid/unknown data cannot fall back to legacy physics. The [GP-11 record](research/ground-physics/GP-11/README.md#authored-ground-module) owns current resource semantics and limits. Workshop similarity transforms for this law remain disabled rather than silently mis-scaling its physics.

The [Workshop guide](AIRCRAFT-WORKSHOP.md) owns the editor and compiler behavior. `research/aircraft-editor/build_descriptors.py` generates `app/data/workshop/<id>.json`. Identified aircraft use `openrc-aircraft-workshop v3` ID bindings and pin exact aircraft bytes, module assertions, visual family and model-manifest hash; ID-less sources retain explicit v2 index/name-hash and v1 compatibility readers. Saved variants are not silently rewritten, rebased or rebound. Workshop metadata remains outside the physical v2 schema.

The shared compiler selects transformations from classified capabilities, never aircraft names or IDs. Size/weight/virtual-power transforms remain limited to the registered legacy prescribed-RPM propeller family; finite-liquid configurations have registered descriptors, but their size/weight/power transforms remain disabled. Saved variants pin their source, descriptor, compiler and external dependencies; changed dependencies block launch without deleting the library record. See the [AE plan](plans/aircraft-editor.md#21-common-aircraft-editing-standard) for remaining binding, migration and fleet gates.

## Experimental rotorcraft boundary

The explicitly selected `xcell-60-research` vehicle uses `format: "openrc-aircraft v2"` and `vehicle: "rotorcraft"` with the same `{value, unit, kind, source}` quantity conventions. Its closed schema is [openrc-rotorcraft-v2.schema.json](../app/data/schema/openrc-rotorcraft-v2.schema.json), generated with its preset; [rotorcraft_data.gd](../app/physics/rotorcraft_data.gd) validates its main/tail rotor, aggregate body, signed shaft inventory, drive, electronics and skids before flight. It is an experimental vehicle-specific schema branch, not a conventional-airplane module/inventory conformance result. Airplane loaders, manifests, Workshop and conformance tools explicitly select supported vehicle classes.

Rotorcraft authoring remains generated and fail-closed. Signed inertial axes and aerodynamic gearing must agree. Aggregate published body inertia, radial-blade estimates, unknown engine spin and the HX-700/X-Cell visual/physical pairing are declared in the [HELI evidence](research/helicopter/HELI-16/README.md). The current [helicopter guide](HELICOPTER.md) owns controls and qualification. Full component inventory, Workshop transforms and identified rotorcraft hardware extend this branch before acceptance; do not add fake airplane surfaces or reinterpret it through the airplane schema.
