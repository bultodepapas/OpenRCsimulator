# Wind, atmosphere and airflow: phased engineering roadmap

2026-10-31 · Owners: M5-W and M5-ATM, with SF/NK, aircraft/HELI/DR, AFC, UI, FW and AUD at their existing boundaries. Baseline code and finding IDs are in the [technical reference](WIND-ATMOSPHERE-REFERENCE.md). **All engineering steps below are proposed and pending.** This audit delivers documentation and focused verification, not physics fixes or qualification.

The immediate priority is correct inputs and explicit contracts, followed by numerical qualification, measured optimization and physical validation. Do not replace the existing solver, implement a second weather engine, or make spatial weather the default as part of cleanup. Preserve the installed `VehicleModel` boundary; every additional vehicle law belongs to its adapter. Existing legacy wind, column, spatial, thermal and point-inflow identities remain distinct until a deliberate compatibility decision changes them.

## Execution rules and dependencies

Each step is one independently reviewable change with a concrete acceptance record. Use `M5-W-AUD-*` for this remediation sequence and `M5-ATM-AUD-*` for atmosphere closure; existing M5-W00…08/M5-ATM-1…4 identifiers retain their original meaning. Shared-source writers must coordinate through the [ownership registry](README.md#tracks-plans-and-step-ids).

```text
Phase 0: source-bound baseline and acceptance cases
   ├─ Phase 1: route/observer/planner defects
   ├─ Phase 2: receipt, interval and field contracts
   └─ Phase 3: numerical and load qualification
                 ↓
           Phase 4: measured performance
                 ↓
           Phase 5: physical qualification and preset release
                 ↓ only when required by qualified scenarios
           Phase 6: shared worlds and additional physical models
```

Phase 1 fixes can proceed independently with distinct files. A thermal law change in Phase 2 requires Phase 3 validation before release. Phase 4 may start with profiling earlier, but optimization acceptance depends on unchanged Phase 3 contracts. New terrain/vehicle capability must not bypass the earlier gates.

For every force/flight-feel change, follow [flight logging](FLIGHT-LOGGING.md): retain a complete baseline ORFL; verify exact replay with `solver_changed=false`; compare one candidate on the same tick/input tape, explicitly `solver_changed=true`; retain config/source/backend identity, markers, CSV and reports. Recovered prefixes are diagnostic only. No unexplained golden rerecording. For refactors/optimizations require existing exact fixtures and intended load/state equality; for an intentional law change specify expected differences before updating any oracle.

Use existing [tools](tools/README.md), checked runner, field tests, native oracles, flight battery and free analysis packages. Reuse available datasets/tools after checking applicability and license. New physical models require a demonstrated gap; a feature label or visual resemblance is not enough. Keep all evidence within these two documents and existing artifact homes; do not create a third weather narrative or cleanup archive.

Retain that whole-physics target; also report the 4166.67 µs 240 Hz interval separately. A field-only timing or batch mean cannot establish either a per-tick tail guarantee or 1080p qualification. Higher resolutions follow 1080p; 720p is a final compatibility check.

## Completion and maintenance

The remediation sequence is complete when the Phase 1 defects and Phase 2 contract decisions have evidence, advertised Phase 3–5 scopes are qualified or explicitly limited, and both documents match the merged implementation. Conditional Phase 6 work remains pending unless its trigger is satisfied. Do not mark every aspirational feature necessary for a release.

For each completed step, update the corresponding implemented section/finding in the technical reference and retain only unresolved work here. Link raw evidence in the reference's existing evidence index. Delete superseded plan prose instead of accumulating another report. Run documentation-link/path checks in a fresh checkout, targeted tests for the changed owners and the required contribution checks; preserve unrelated concurrent edits. Any physics change must state the intended law/identity change and the baseline/candidate result.
