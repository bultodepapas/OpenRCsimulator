## Findings that materially change the implementation

1. **Version rates and throttle separately.** The inspected Actual-rate expression remains the same, but current BF throttle has a hover point and a different lookup. The extracted host C probe produces 1663 PWM at a 30% input for mid/hover/expo 30/70/0, not the continuous-curve expectation of 1700; scope and all observations are in 09.
2. **Separate source parameters from simulator gains.** Raw firmware PID and feedforward integers cannot be copied into torque gains. Begin with the defined OpenRC SI controller and label other controls as explicit analogues or unavailable.
3. **Do not activate kilohertz filters on a 240 Hz sample stream.** Nyquist is 120 Hz, and BF's own dynamic-notch implementation disables its notch below a 2 kHz update rate. A faster integrator is not automatically a faster sensor/controller.
4. **Use per-firmware mode and profile parsers.** Index bases, scopes, final active selections, AUX Boolean logic and endpoint handling differ.
5. **Require typed units and default provenance.** Alignment can differ by 10×; failsafe timers have distinct units/zero semantics; INAV capacity can be charge or energy; omitted defaults can change even when an older diff still imports.
6. **Only expose working capabilities as active controls.** A VTX setting does not transmit RF; a firmware ESC protocol does not establish a motor time constant; an RPM filter needs a defined telemetry/sensor path; RTH and turtle need new physical/control capabilities.

These are engineering findings, not a claim of Betaflight/INAV firmware emulation. Every setting accepted as active must be represented in the configuration identity and, when stateful, the deterministic checkpoint.

## SET-01 — Rate families and independent profiles

**Evidence.** BF `rates_type` selects `BETAFLIGHT`, `RACEFLIGHT`, `KISS`, `ACTUAL`, or `QUICK`; `quickrates_rc_expo` is an additional Quick option. Reset is `ACTUAL`; a rate-profile array and explicit profile change exist. The common BF build definition gives four profiles but can be overridden by a target. INAV 9.1 instead has three control profiles containing stabilized roll/pitch shared expo, yaw expo, three rates and throttle settings; its inspected settings schema does not expose BF's `rates_type` selector. Those profiles are not interchangeable documents. [B-rate] [B-rc] [B-count] [I-profile] [I-profile-count] [I-settings-rates]

**Racing interaction.** Identically labeled numerical settings can give different center sensitivity, end response and handling when the family changes. A profile switch also changes the throttle curve and may affect feedforward transients; it is not simply a UI label change. The official rate calculator also identifies the five BF models; pinned code supplies the mathematical contract. [BF-doc-rates]

**Disposition and state.** Implement the already-planned 4.5.2 Actual curve first and only mark additional families supported after pinned reference cases pass. Inspecting both commits shows the Actual expression itself is unchanged, including `max(0, max-rate minus center)`; this does not validate the whole firmware pipeline. Reject unknown family/version combinations explicitly; optionally retain them as inert metadata with warnings. Schema must carry firmware/version, family, per-axis parameters, profile identity and supported-feature report; checkpoint the active profile and any stateful switch policy. A mid-race identity change follows the handoff's attempt-abort rule.

**Acceptance.** `SET01-A`: the same raw numbers under Actual and BF family produce their respective independently computed curves; an unknown family must not silently fall back. `SET01-B`: selecting a new profile remains a detached preview until the explicit held reset/apply transaction in 08 commits; invalid preparation preserves the old session/profile, and restoring the accepted new configuration reproduces its next command. If the old session is armed, an explicitly labeled Reset to pad and apply action is required. A sampled hot-switch test belongs to a separately admitted later capability. Confidence: high for the inspected selector and Actual expression, limited to mathematical compatibility; no full-flight equivalence. [B-actual-old] [B-rc] [I-profile]

## SET-02 — Per-axis rate, expo and angular-rate caps

**Evidence.** BF exact rate-profile keys are `{roll,pitch,yaw}_rc_rate`, `{roll,pitch,yaw}_expo`, `{roll,pitch,yaw}_srate`, and `{roll,pitch,yaw}_rate_limit`. Reset Actual values are 7, 0, 67 and 1998 respectively on all three axes. Actual interprets center and configured endpoint in 10 deg/s increments; the separate cap is applied after the curve and spans 200–1998 deg/s. Family-specific validation differs; do not interpret `_srate` uniformly across families. INAV uses `roll_rate`, `pitch_rate`, `yaw_rate` in 10 deg/s units; reset 20 each. `rc_expo` (70) is shared roll/pitch and `rc_yaw_expo` (20) is separate, both 0–100; yaw rate range is 1–180. INAV's manual-mode controls have different `manual_*` keys and meanings. [B-keys] [B-rate] [B-rc] [B-cap] [B-limits] [I-settings-rates] [I-pid-rate]

**Racing interaction.** The endpoint establishes requested angular speed, not a guaranteed physical response; expo changes precision near center while a separate cap can reduce a higher curve endpoint. Input calibration/deadband/transmitter shaping must not be applied twice.

**Disposition and state.** Implement the pinned Actual transform and explicit SI conversion at the simulator boundary; expose clear center, maximum and cap semantics rather than treating raw BF integers as universal units. Later support an INAV-specific map only with its own fixtures. Schema: raw firmware values plus normalized quantities, input-conditioning ownership, version, axis signs and caps. Curves are stateless; active profile and input sample cursor remain checkpointed.

**Acceptance.** `SET02-A`: for BF default Actual on one axis, inputs −1, 0, +1 request −670, 0, +670 deg/s before conversion and symmetric clipping; +0.5 requests 185 deg/s (expo 0, no lower cap). `SET02-B`: request a curve above a 200 deg/s cap and verify clipping on that axis only; independent yaw and pitch settings and signs remain intact. Confidence: high for raw transform, with output quantization and transmitter expo outside the isolated equation. [B-rc] [B-rate] [B-limits] [I-settings-rates]

## SET-03 — Throttle midpoint and expo

**Evidence.** BF current rate-profile keys `thr_mid`, `thr_expo`, `thr_hover` each have 0–100 domain and reset 50, 0, 50. Its current implementation constructs two quadratic Bézier segments around `(thr_mid, thr_hover)`, quantizes a default 12-point PWM lookup and interpolates in integer PWM space. The table length can be build-overridden; the continuous Bézier curve is a mathematical description, not exact firmware output. BF 4.5.2 instead has only `thr_mid` and `thr_expo` in the examined curve and uses a different integer cubic table. INAV keys `thr_mid`/`thr_expo` default 50/0 and range 0–100; its own integer lookup is scaled between configured idle and maximum. An INAV `thr_hover` equivalent was not found in its settings schema. [B-keys] [B-rate] [B-throttle] [B-throttle-lookup] [B-throttle-old] [I-settings-rates] [I-curve]

**Racing interaction.** The curve changes collective resolution near the selected stick region, hence acceleration out of gates and the throttle entering later conditioning/TPA. It does not change motor or prop physics and does not guarantee hover at the chosen point.

**Disposition and state.** Add a simulator-owned normalized throttle curve early with named semantics; compatibility for either exact firmware curve is later and independently versioned. Do not infer a 2026 throttle curve from the 4.5.2 rate-only promise. Schema records throttle-curve family, mid, expo, optional hover, endpoints, quantization and ordering; only active configuration/tape cursor require checkpointing for a stateless curve.

**Acceptance.** `SET03-A`: for current BF with `thr_mid=30`, `thr_hover=70`, `thr_expo=0`, the continuous curve passes through (30%, 70%), but 30% lies between nodes in the default 12-point table. The executed host C probe in 09 returns 1663 PWM (normalized 0.663) under its stated 12-node, 1000–2000 PWM assumptions. Retain that scoped oracle; do not replace it with the continuous value or use it as the historical BF/INAV curve. Target/compiler parity remains a separate qualification. `SET03-B`: across 0, mid, 100 and values just either side of a lookup boundary, compare the declared curve with an independent reference and verify no duplicate hardware/software expo; reject an unsupported curve version. Confidence: high for inspected source, with target scaling and 0/100 edge handling subject to implementation fixtures. [B-throttle] [B-throttle-old] [I-curve]

## SET-04 — RC smoothing and interpolation

**Evidence.** BF keys `rc_smoothing`, `rc_smoothing_auto_factor`, `rc_smoothing_auto_factor_throttle`, `rc_smoothing_setpoint_cutoff`, `rc_smoothing_throttle_cutoff`: upstream reset ON, 30, 30, 0, 0 respectively; zero cutoff selects automatic cutoff. The source processes setpoint, throttle and feedforward filters with PT3 stages and uses receiver-frame timing. INAV `rc_filter_auto=ON`, `rc_filter_smoothing_factor=30` (1–100), `rc_filter_lpf_hz=50` (declared range 15–250); its `rcInterpolationApply` stores new receiver frames and runs PT3 filters each loop with auto cutoff based on measured frame frequency. INAV settings text calls the filter biquad, while the cited implementation uses PT3: behavior follows the pinned implementation, and the apparent 0-disable text versus declared minimum also needs a firmware-level check before importing 0. [B-rx] [B-smooth] [I-smooth-keys] [I-smooth-code]

**Racing interaction.** Input smoothing trades stepped receiver updates and feedforward noise against command latency; effects depend on receiver update timing, jitter, controller sample rate, rate curve and throttle path. Host interpolation is not evidence of radio latency.

**Disposition and state.** Early simulator analogue: explicit sample-and-hold or named deterministic filter with configured sample rate, cutoff, initialization and timing; no claim of exact firmware smoothing. Keep the handoff's 240 Hz hypothesis and 960 Hz fresh-feedback comparison. Reject imported cutoffs at or beyond the simulator's admissible digital filter band instead of silently changing them. Schema and checkpoint hold filter identity/coefficients, history, last accepted frame, timing/phase and any auto-estimator state; recording must identify the input sampling edge.

**Acceptance.** `SET04-A`: for the same timestamped, jittered frame tape, deterministic repeated runs and checkpoint/restore reproduce each filtered output and delay; a failed tick consumes no frame or filter update. `SET04-B`: bypass versus filtering produce predictably different step/phase responses; fixed-rate solver substeps do not advance filter memory, and invalid cutoff is rejected. Confidence: high for cited implementation, medium for host input/latency conclusions. [B-smooth] [I-smooth-code]

## SET-05 — PID terms, units and controller ownership

**Evidence.** BF exposes `p_roll`, `i_roll`, `d_roll`, and corresponding `_pitch`/`_yaw`; range 0–250 in this version. Reset roll P/I/D = 45/80/30, pitch 47/84/34, yaw 45/80/0. INAV exposes `mc_p_roll`, `mc_i_roll`, `mc_d_roll` and corresponding pitch/yaw; reset roll and pitch 40/30/23, yaw 85/45/0. The firmware computes scaled P, accumulated I and filtered gyro-derived D on a normalized motor/mixer path; the actual numerical scaling and output limits are implementation-specific, and INAV further distinguishes multicopter from fixed-wing PIFF. These raw integers are not SI torque gains. [B-pid-keys] [B-pid-default] [B-pid-default-h] [B-pid-run] [I-pid-keys] [I-pid-impl]

**Racing interaction.** P responds to rate error, I accumulates sustained error within authority, and D damps measured rate change; noise filters, sample period, saturation, actuator/prop response and battery state change the observed response. A high requested rate can remain unachievable.

**Disposition and state.** Implement early a simulator-owned, explicitly dimensioned controller with SI `Kp`, `Ki`, `Kd` in the handoff's declared error/torque convention and derivative on filtered measurement. Firmware P/I/D is metadata-only or explicitly unsupported on import; never copy numbers directly into torque gains. Schema identifies per-axis gains and dimensions, sample period, derivative input/filter, integrator/allocator/anti-windup policy, and firmware raw fields separately. Checkpoint integrator, previous measurement and all filter state.

**Acceptance.** `SET05-A`: with a fixed unsaturated one-axis fixture, individually isolate P, I and D; zero error gives zero P, a sustained error accumulates I with the declared `dt`, and a stationary measurement yields zero measurement D. `SET05-B`: a setpoint step with unchanged gyro must not create a derivative kick; a rejected tick or restore preserves controller memory and produces the identical next motor request. Confidence: high for term identities and exposed values; no numeric firmware-to-SI conversion is asserted. [B-pid-run] [I-pid-impl]

## SET-06 — Feedforward and setpoint shaping

**Evidence.** BF per-axis `f_roll`, `f_pitch`, `f_yaw` have 0–1000 range; smoothing/shape keys include `feedforward_transition`, `feedforward_averaging`, `feedforward_smooth_factor`, `feedforward_jitter_factor`, `feedforward_boost`, `feedforward_max_rate_limit`; selected resets are 0, two-point, 65, 7, 15, 90. BF feedforward multiplies a shaped setpoint delta, with distinct smoothing and maximum-rate behavior. INAV multicopter uses `mc_cd_roll`, `mc_cd_pitch`, `mc_cd_yaw` reset 60; `mc_cd_lpf_hz` defaults 30 Hz, range 0–200. It filters a rate-target delta and scales it with sample timing. `rate_accel_limit_roll_pitch` and `rate_accel_limit_yaw` constrain desired angular acceleration in deg/s² (reset 0 and 10000); they are a different mechanism from feedforward. Fixed-wing INAV `fw_ff_*` is distinct. [B-pid-keys] [B-pid-default] [B-ff] [I-pid-keys] [I-cd] [I-pid-impl] [I-i-run] [I-accel]

**Racing interaction.** Fast stick reversals and gate transitions can benefit from a faster response, but aggressive feedforward plus receiver jitter or a hard rate cap changes initial torque and stopping behavior. A slew limiter delays the requested rate; it is not an alternative name for feedforward.

**Disposition and state.** Later simulator analogue only after the base controller and sampling gates pass: define a separate, unit-correct feedforward path and optional slew limit. Do not promise BF/INAV FF or translate its integer gains. Schema stores per-axis analogue gain, units, derivative/filter/slew definition, limits and support status; checkpoint prior setpoint, filters and limiter history.

**Acceptance.** `SET06-A`: compare a steady nonzero setpoint with a setpoint ramp: derivative-based FF decays to zero during the constant part and reverses sign on the reversal; response is reproducible across restore. `SET06-B`: a configured 1000 deg/s² limiter with a 0.01 s sample admits at most 10 deg/s setpoint change per sample, while disabling it leaves the rate transform unchanged; reject unavailable native FF settings. Confidence: high for the source distinction, medium for proposed simulator analogue. [I-accel] [I-pid-impl] [B-ff]

## SET-07 — Integral limits, relaxation and anti-windup

**Evidence.** BF `iterm_windup` reset 80 and range 20–100 sets an I limit relative to `pidsum_limit`/`pidsum_limit_yaw`; `iterm_relax` reset RP, `iterm_relax_type` SETPOINT and `iterm_relax_cutoff` 15 Hz (1–50) change accumulation for rapidly varying setpoints. INAV `iterm_windup=50` (0–90) relates to motor-mix saturation, `pid_iterm_limit_percent=33` (0–200; 0 disables this particular cap), and `mc_iterm_relax=RP`/`mc_iterm_relax_cutoff=15` Hz (1–100). INAV's multicopter source also uses a tracking correction based on limited versus unlimited PID sum, and notes that per-axis mixer-authority feedback is a TODO. Similarly named knobs therefore must not be mapped one-to-one. [B-i-keys] [B-i-init] [B-i-run] [I-i-keys] [I-relax] [I-i-run]

**Racing interaction.** Saturation during throttle/roll/yaw combinations or a rapid flip can accumulate excessive correction, causing delayed recovery and bounce. Relaxing rapid-command integration can also reduce disturbance rejection during the maneuver.

**Disposition and state.** Implement an early explicit bounded I accumulator and allocator-aware anti-windup in simulator units; define whether feedback uses requested versus allocated torque and fix the update order already specified by the handoff. Add relaxation only later as a separately named analogue. Do not claim exact BF/INAV mixer feedback. Schema holds bounds, units, method and gains; checkpoint integrator, relaxation filter history and prior allocation diagnostics where used.

**Acceptance.** `SET07-A`: command prolonged unachievable positive torque, release to zero and then reverse: integral remains bounded and recovers; compare allocated-minus-requested sign with an independent reference. `SET07-B`: identical fast stick maneuver with relaxation on/off must show reduced accumulating I under the declared policy, while a steady disturbance still produces correction; rollback/restore matches the pre-failure history. Confidence: high for the examined source semantics; benefit depends on the selected simulated plant. [B-i-run] [I-i-run]

## SET-08 — Throttle PID attenuation

**Evidence.** BF `tpa_mode`, `tpa_rate`, `tpa_breakpoint` reset D, 65, 1350; `tpa_low_rate`, `tpa_low_breakpoint`, `tpa_low_always` reset 20, 1050, OFF. In the classic curve, high-throttle attenuation begins above the breakpoint; low-throttle behavior is separate and has latch/enable conditions. INAV `tpa_rate=0` (0–200), `tpa_breakpoint=1500`, `tpa_on_yaw=OFF`; for the multicopter source, P, D and control derivative are scaled on roll/pitch, and yaw only when enabled; I coefficient is not scaled on that branch. The INAV description is ambiguous about individual terms, so implementation is authoritative. Fixed-wing TPA/airspeed paths differ. INAV’s current 9.1 documentation states a 0–100 multicopter range whereas its pinned settings schema exposes 0–200; do not resolve this discrepancy by guessing. [INAV-doc-tpa] [B-tpa-keys] [B-pid-default] [B-tpa-run] [I-settings-rates] [I-tpa-run]

**Racing interaction.** A simulated high-throttle change can alter stability and authority while the craft exits a turn; TPA interacts with throttle curve ordering, filtering, supply sag, saturation and I-term. The presence of a knob is not evidence it is needed for a particular simulated craft.

**Disposition and state.** Defer gain scheduling until the base plant/controller is qualified; at first import BF/INAV TPA as metadata with an unsupported warning. If added, define simulator-specific throttle signal, affected terms, breakpoint/curve and clamp. Schema identifies controller version and each term mask; checkpoint any low-TPA latch/filter and accepted throttle sample.

**Acceptance.** `SET08-A`: a classic analogue at/below its breakpoint leaves specified gains at unity; at full throttle with rate 40% the designated terms are multiplied by 0.60, while I and unselected axes retain their declared behavior. `SET08-B`: verify the same raw rate with different BF/INAV term masks cannot silently import as identical; checkpoint around any low-throttle activation latch and reproduce it on restore. Confidence: high for inspected multicopter branch; no source-default value is a recommended tune. [B-tpa-run] [I-tpa-run]

## SET-09 — Anti-gravity transient compensation

**Evidence.** BF keys `anti_gravity_gain`, `anti_gravity_cutoff_hz`, `anti_gravity_p_gain` reset 80, 5 Hz, 100; ranges 0–250, 2–50 Hz, 0–250 respectively. Its code filters throttle derivative and adjusts I acceleration and P response, with axis/setpoint conditions. INAV, when compiled with `USE_ANTIGRAVITY`, instead exposes `antigravity_gain=1` (1–20; 1 disables boost), `antigravity_accelerator=1` (1–20), `antigravity_cutoff_lpf_hz=15` (1–30 Hz); the transient is based on throttle minus filtered throttle and scales multicopter I error. Different names and laws preclude numeric translation. [B-ag-keys] [B-pid-default] [B-ag-run] [I-ag-keys] [I-ag-run]

**Racing interaction.** Throttle punches/chops during a turn may disturb attitude; a transient correction can alter the stop and the integrator state. It also depends on SET-03 throttle shaping and SET-04 smoothing, so extra boost must not be mistaken for changed aircraft inertia.

**Disposition and state.** Defer; only add an explicitly named simulator analogue if controlled throttle-step evidence warrants it. Otherwise retain upstream fields as reported unsupported metadata. Schema distinguishes input location, filter, gain curve and axes; checkpoint previous throttle, filter memory and any decaying boost, all within the sampled transaction.

**Acceptance.** `SET09-A`: after a settled constant-throttle input the boost converges to its defined neutral value; a finite punch and chop produce bounded transients whose timing matches the independent analogue. `SET09-B`: checkpoint during a transient, restore and replay to identical outputs; an invalid tick must not advance either throttle history or boost. Confidence: high for these versions and conditional compilation, medium for physical relevance without measured data. [B-ag-run] [I-ag-run]

## SET-10 — Acro, Angle, Horizon and angle limits

**Evidence.** In Acro the stick supplies a rate target; Angle closes an outer attitude loop on roll/pitch; Horizon blends angle and rate responses. BF exact keys include `angle_limit` (reset 60°, range 10–80°), `angle_p_gain`, `angle_feedforward`, `horizon_level_strength`, `horizon_limit_sticks`, `horizon_limit_degrees`, `horizon_ignore_sticks`, `horizon_delay_ms`. INAV `max_angle_inclination_rll`, `max_angle_inclination_pit` reset 450 with units 0.1°, range 100–900; `mc_p_level`, `mc_i_level`, `mc_d_level` include angle strength, filtering and horizon transition, not three interchangeable attitude PID gains. [B-level-keys] [B-pid-default] [B-level-run] [I-level-keys] [I-angle-limit] [I-level-run]

**Racing interaction.** Acro is needed for unrestricted flips and zero-stick rate holding; an outer level controller is useful for training but changes attitude behavior. Horizon's blending and near-inverted behavior can materially change inputs at a gate, and yaw must not acquire an unintended heading hold during mode transition.

**Disposition and state.** Implement Acro first and bounded Angle as the handoff proposes; Horizon later, only with an explicit blend contract. Reject out-of-domain near-vertical/inverted Angle states until their math and recovery policy are specified. Schema identifies mode, limits with units, estimator assumptions, transitions, outer-loop gains/filter and yaw policy; checkpoint mode, filter/integrator history and transition memory.

**Acceptance.** `SET10-A`: at zero stick and a nonlevel admitted attitude, Acro does not command leveling whereas Angle commands correction toward its neutral attitude; yaw target does not jump. `SET10-B`: an Angle full-stick target respects its configured limit, and near-inverted input is refused or handled by the declared policy; switching and checkpoint restore do not introduce an unexplained derivative kick. Confidence: high for the cited mode structure, bounded by each firmware's other enabled modes. [B-level-run] [I-level-run]

## SET-11 — Airmode, mixer authority and desaturation

**Evidence.** BF has an Airmode feature/mode and `airmode_start_throttle_percent` (reset 25%, range 0–100), plus `mixer_type`; the armed threshold latches until disarm. PID/I activation and motor mixer enable checks are distinct. BF's cited legacy mixer normalizes oversized mixes and constrains collective to preserve feasible motor bounds; other `mixer_type` paths differ. INAV `airmode_type=STICK_CENTER` (alternative `THROTTLE_THRESHOLD`) and `airmode_throttle_threshold=1150` (1000–2000) define different activation/anti-windup policy; its mixer scales an oversized roll/pitch/yaw mix and shifts/clips throttle according to its own algorithm. [B-air-keys] [B-rx] [B-mix-keys] [B-air-core] [B-mix] [I-air-keys] [I-mix]

**Racing interaction.** At low collective a pilot can still request angular correction, but retaining differential authority can raise collective and motor outputs; at high simultaneous demand not all axes can be achieved. Idle, motor stop, arming, disarm and crash cut override behavior must be explicit.

**Disposition and state.** Implement an early simulator analogue with bounded motor allocation, declared collective-shift and axis-priority policy; do not describe it as exact BF or INAV desaturation. Show requested, allocated and produced torque separately, and have disarm/terminal cut override all correction. Schema pins allocation order, idle, bounds, enable and arming policy. Checkpoint mode/activation latch and controller state; record saturation and shift.

**Acceptance.** `SET11-A`: at low collective with a feasible roll request, authority-enabled allocation remains in motor bounds and reports any collective rise; authority-disabled behavior follows its separately declared law. `SET11-B`: command infeasible simultaneous roll/yaw/collective, verify bounded deterministic allocation and anti-windup feedback; disarm and the terminal crash latch always force effective zero drive, including after restore. Confidence: high for source paths; exact motors vary by selected mixer. [B-air-core] [B-mix] [I-mix]

## SET-12 — Launch control

**Evidence.** BF launch-control feature keys are `launch_control_mode` (reset PITCHONLY; modes NORMAL/PITCHONLY/FULL), `launch_trigger_allow_reset` (ON), `launch_trigger_throttle_percent` (20, range 0–90%), `launch_angle_limit` (0°, range 0–80°), `launch_control_gain` (40, range 0–200). In its armed state machine, crossing strictly above the trigger exits launch control and resets I; trigger-reset behavior depends on mode switch/disarm. Its launch controller also changes which terms/axes operate. **Racing interaction.** A start aid that holds attitude until throttle trigger differs from the handoff's proposed countdown that inhibits drive until GO and requires fresh low-throttle authorization. Combining them without explicit precedence could produce premature thrust, an unwanted rate setpoint or a lost race-start event.

**Disposition and state.** Defer BF-like launch control until the existing countdown, arm/cut and replay contracts are independently proven. Reject an INAV fixed-wing launch dump as a quad-launch equivalent. If later added, specify mode precedence, attitude eligibility, thresholds, reset and I handoff separately from the countdown; checkpoint all launch states, trigger latches and I/reset history, plus race authorization.

**Acceptance.** `SET12-A`: under a future BF-like analogue, values just below/equal/above trigger follow the documented strict transition and one-time I reset; disarm/reset and profile changes follow the declared state machine. `SET12-B`: for the current proposed countdown, a high pre-inhibit throttle at GO remains drive-inhibited and clears authorization, and a failed GO tick commits neither launch transition nor race event. **Sampling boundary for all filter cards.** The current proposal samples feedback at 240 Hz, so its Nyquist frequency is 120 Hz. A 250 Hz sinusoid sampled at exactly 240 Hz is indistinguishable from a 10 Hz sinusoid at the same phase; a post-sampling filter cannot recover the original signal. Even a cutoff below Nyquist is not sufficient anti-alias evidence: the physical/synthetic sensor needs a qualified bandwidth and pre-decimation attenuation. For comparison, a 960 Hz sensor path has 480 Hz Nyquist and a 1920 Hz path 960 Hz Nyquist, before design margin. Plant RK substeps are not automatically fresh gyro/PID samples. Where source cutoff, moving notch range, harmonic or required bandwidth is incompatible, report an unsupported/inactive setting or choose a separately qualified faster sampled-event design; do not silently clamp and label it equivalent. BF's own runtime may clamp or disable some filters differently; OpenRC refusal is an explicit product policy, not a claim about firmware behavior.

A zero-noise ideal gyro can qualify the selected controller and clean step response, but it cannot validate a noise filter's attenuation, noise floor, spectral tracking, or effect on physical flight. Later filter promotion needs declared analog/synthetic sensor bandwidth, anti-aliasing and sample timing; reproducible zero, broadband and moving narrow-band traces; representative recorded traces when available; matched unfiltered/filtered spectra, phase/delay and control outputs; held-out flight evidence; deterministic reset/replay, and a stated missing/stale telemetry policy. Include filter histories, coefficient-update clocks, delayed samples, estimator state and any deterministic noise-generator state in the versioned checkpoint. A visual change or a waveform that shares the implementation's own helper is not an independent oracle.

[BF settings](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/cli/settings.c#L787-L791); [maximum](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/dyn_notch_filter.h#L27-L29); [reset](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/pg/dyn_notch.c#L30-L36); [tracker](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/dyn_notch_filter.c#L156-L190). - **SET16-A:** At 240 Hz, importing BF dynamic-notch-on yields a visible unsupported/inactive report; the exact BF source itself disables it below 2 kHz. No manufactured notch motion is presented as equivalent.
- **SET16-B:** At a qualified rate, drive a known moving narrow-band tone plus a separate control-band signal, then remove the tone. Measure tracking lag, attenuation and phase versus an independent reference; zero-input and no-peak behavior, deterministic restore, and absence of false peak claims are also required.

## SET-17 — RPM filtering, telemetry and units

**Verified firmware facts.** BF has `dshot_bidir` and `motor_poles`; its RPM filter keys are `rpm_filter_harmonics`/`weights`/`q`/`min_hz`/`fade_range_hz`/`lpf_hz`. Source resets are 3 harmonics, weights 100/100/100%, Q raw 500 (= 5), min 100 Hz, fade 50 Hz, RPM LPF 150 Hz; the filter does not initialize without bidirectional DShot telemetry or with zero harmonics. [BF RPM reset](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/pg/rpm_filter.c#L30-L38); [activation and bounds](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/rpm_filter.c#L68-L104). INAV exposes different conditional keys `rpm_gyro_filter_enabled`, `rpm_gyro_harmonics`, `rpm_gyro_min_hz`, `rpm_gyro_q`, with resets OFF, 1, 100 Hz and raw Q 500; its update reads per-motor ESC telemetry, rather than BF's `dshot_bidir` key. [INAV settings](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/fc/settings.yaml#L1688-L1718); [telemetry update](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/flight/rpm_filter.c#L181-L200). Both source paths use pole count to convert electrical speed; BF's telemetry decoded value is in units of **100 eRPM**, not raw mechanical RPM. With physical electrical RPM `E` and `P` magnetic poles, mechanical RPM is `E/(P/2)` and mechanical rotation frequency is that divided by 60. For a physically valid even `P`, a true 14-pole/21,000 mechanical RPM motor corresponds to 147,000 electrical RPM, or decoded BF 1,470 units; base rotation is 350 Hz. INAV performs integer division in its `motorPoleCount / 2` expression, while BF divides by `2.0f`; an odd schema value can therefore produce different conversion and is rejected by the proposed physical motor manifest rather than silently normalized. [BF conversion](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/drivers/dshot.c#L183-L191) and [decoded units](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/drivers/dshot.c#L213-L220); [INAV conversion](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/sensors/esc_sensor.c#L126-L149). Both implementations bound their moving notches near `0.48 ×` their sample frequency; clamping does not recreate out-of-band vibration. [BF](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/rpm_filter.c#L84-L89); [INAV](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/flight/rpm_filter.c#L105-L113).

**Racing relevance and disposition.** Moving notches depend on motor identity, pole count, freshness, latency and vibration harmonics. **Early:** use achieved mechanical rotor speed only for plant/visual telemetry; mark source RPM-filter keys unsupported and `dshot_bidir` metadata, never treat ideal shaft RPM as an emulated ESC stream. **Later:** model telemetry acquisition/validity/dropouts and motor-specific notches only with a qualified sensor bandwidth. Do not collapse INAV and BF settings into aliases. **State/schema:** per-motor physical pole count and motor ID, distinct `electrical_rpm`/mechanical RPM or rad/s units, sample/arrival timestamps, validity/age, telemetry filter and notch states.

- **SET17-A:** The 14-pole/147,000 eRPM vector gives 21,000 mechanical RPM and 350 Hz, with second harmonic 700 Hz. Interpreting 147,000 as mechanical RPM or applying the factor 100 twice fails; a wrong configured pole count must visibly shift the derived notch. Reject an odd physical pole count even though the firmware schemas accept integer values in their stated ranges.
- **SET17-B:** Missing, stale or corrupt per-motor telemetry invokes an explicitly versioned unavailable/fallback rule rather than falsely tracking ideal RPM. At 240 Hz neither 350 nor 700 Hz is representable in the gyro input; refuse equivalence even if a 115.2 Hz (`0.48×240`) clamp can be computed.

## SET-23 — Receiver channel map, endpoints and deadband

**Upstream.** Both expose `map`, `rxrange`, `min_check`, `max_check`, `rx_min_usec`, `rx_max_usec`, `deadband` and `yaw_deadband`; mapping, calibrated working range, signal-validity thresholds and centered-axis deadband are different operations. BF maps a larger set of channel letters; INAV maps four primary channels and its source declares AETR as a default. BF reset initializes roll/pitch and yaw deadband to zero; INAV 9.1 YAML sets each to 2 µs. Board/target and firmware can alter assumptions. See [BF receiver mapping](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/rx/rx.c#L76), [BF deadband reset](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/fc/rc_controls.c#L77-L82), [INAV receiver mapping](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/rx/rx.c#L68-L68) and [INAV deadbands](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/fc/settings.yaml#L1792-L1801).

**Racing and disposition.** Correct signs and endpoints prevent unwanted motion and loss of usable rate. Keep the handoff's measured USB-axis calibration separate from firmware receiver PWM/µs metadata; do not blindly apply both `rxrange` and USB endpoint normalization or use `min_check` as an endpoint. Apply at most one declared deadband at the correct adapter stage, followed by the selected rates law; a transmitter's prior expo is not invertible from input samples. Import firmware-specific conversions only with an explicit mapping and sufficient target evidence. An unknown channel map is reported, not guessed from radio name.

**Checkpoint/schema.** Persist adapter law/version, channel assignments, inversion, calibration, µs-to-logical conversion if modeled, selected deadband and source generation in the controller identity; accepted normalized sample belongs to the tape. Changes require a new configuration identity.

**Tests.** **SET23-A:** centered/asymmetric calibration, reversed pitch and each endpoint produce the expected signed logical sticks; throttle is monotonic and stays separate from centered axes. **SET23-B:** same sample through BF-zero versus INAV-2 µs deadband differs near center; unknown transport or pre-shaped input is reported rather than silently shaped twice. **SET23-C:** shuffled channel order and duplicate/missing mapping are either resolved explicitly or rejected, never fly with a guessed mapping.

## SET-24 — AUX mode activation

**Upstream.** Both store `aux` conditions with a permanent mode ID, AUX index and stepped range; their pinned sources use 25 µs steps and compare lower-inclusive/upper-exclusive. **Racing and disposition.** An arm or Angle switch can be unexpectedly active at an endpoint, or depend on multiple switches. Do not convert a complex source into separate independent toggles or claim exact firmware mode behavior. Preserve identifiers and logic in an import report even when not admitted.

**Checkpoint/schema.** Pin the source namespace/version, condition order and operator policy; when a supported mode has a latch, store its accepted state. Record logical AUX samples/events in the accepted tape and reject malformed/reversed/unsupported conditions atomically.

**Tests.** **SET24-A:** for `[1700,2100)`, evaluate 1699, 1700, 2099 and 2100 with each pinned firmware's rules, including the different result at 2100. **SET24-B:** two conditions with only one high distinguish OR from AND; a BF linked condition is either preserved with its semantics or reported unsupported. **SET24-C:** restore on the boundary and replay yields the same accepted mode transition, including after a rejected candidate.

## SET-25 — Arm, prearm and interlocks

Do not advertise exact firmware safety or copy INAV navigation/compass interlocks when no sensor/navigation capability exists.

**Checkpoint/schema.** Pin the arm policy and thresholds. Checkpoint previous arm/prearm levels, current-generation OFF evidence, arm state, reason, optional prearm timer/latch and the accepted action cursor. A held host pause does not age simulation timers.

**Tests.** **SET25-A:** high arm at startup or reconnection cannot arm until fresh OFF→ON with valid source and low throttle; a rejected tick consumes no edge. **SET25-B:** with a configured prearm timer and angle check, expiration or excessive tilt blocks arm; disarm clears drive even with Airmode active. **SET25-C:** checkpoint before/after prearm expiry and restoration reproduce the same next decision.

## SET-26 — Firmware failsafe versus host hold

**Upstream.** BF `failsafe_procedure` offers `AUTO-LAND`, `DROP`, `GPS-RESCUE`, and `failsafe_switch_mode` has `STAGE1`, `KILL`, `STAGE2`. INAV uses `LAND`, `DROP`, `RTH`, `NONE`, with additional distance/navigation logic; it adds an RX failure/recovery base period to configured delays. Critically, the BF 2026.6.2 code interprets `failsafe_landing_time` in **seconds**, with source default 60 s; INAV `failsafe_off_delay` is in deciseconds, source default 200 = 20 s, and zero means no timeout. INAV's default procedure is `LAND`; BF's is `DROP`. Do not infer this unit from similarly named fields or unversioned descriptions. See [BF stage logic and units](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/failsafe.c#L81-L89), [BF landing timer](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/failsafe.c#L240-L254), [INAV settings](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/fc/settings.yaml#L865-L889) and [INAV delay/procedure code](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/flight/failsafe.c#L150-L157).

**Racing and disposition.** Host focus loss, USB disappearance and explicit pause enter the handoff's non-integrating host hold/rearm path; they are not proven RF failures. Separately offer an opt-in, clearly labeled simulated RF-loss exercise that runs in simulation time and explicitly models the chosen subset's stage, substitutions, timer, recovery and actuator consequences. No automatic landing or navigation promise is inferred from a switch name. Report unsupported imported procedures.

**Checkpoint/schema.** Exercise version, configured policy, pending loss/recovery events, accepted link state, phase, timer/deadlines and substitution state must be saved atomically; a host hold pauses the clock. Hold/rearm state remains a separate session authority.

**Tests.** **SET26-A:** a focus-loss hold advances zero physics, race, battery or failsafe-exercise ticks; resume needs the documented fresh arm evidence. **SET26-B:** a deliberately injected RF-loss event advances its own configured stage timer, then DROP disarms; recovery before the deadline cancels the escalation according to the admitted law. **SET26-C:** 60 s BF landing versus 200 deciseconds INAV landing produce their correct different deadlines; zero INAV timeout is never converted to immediate disarm.

**Tests.** **SET28-A:** BF `align_board_yaw=90` and INAV `align_board_yaw=900` normalize to the same 90° declared mount; INAV value 90 normalizes to 9°. **SET28-B:** importing alignment with ideal body feedback changes neither body forces nor camera pose and is reported as metadata. **SET28-C:** enabled sensor model plus nonzero offset retains the same transformed sample after checkpoint/restore.

## SET-34 — Crash recovery, turtle and reverse drive

**Upstream.** BF `crash_recovery` is a PID recovery feature, distinct from flip-over-after-crash (`crashflip_motor_percent`, `crashflip_rate`, `crashflip_auto_rearm` and the CRASHFLIP mode). Its mixer and arm paths change direction and behavior. INAV exposes `TURTLE` and `turtle_mode_power_factor`; its source requires a multirotor and DShot for entry. Neither proves that an arbitrary simulated unidirectional propeller/ESC can produce reverse thrust or escape an obstacle. See [BF recovery/flip settings](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/cli/settings.c#L1050-L1054), [BF PID recovery](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/flight/pid.c#L649-L680), [BF crashflip direction](https://github.com/betaflight/betaflight/blob/e0b7bb01b17b21351057e9ead2d1ab39dd44fa16/src/main/fc/core.c#L608-L609), [INAV turtle entry](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/fc/fc_core.c#L555-L562) and [INAV turtle mixer](https://github.com/iNavFlight/inav/blob/e519b69b02e27c8bdc03b4a0889f1baaae211a54/src/main/flight/mixer.c#L294-L297).

**Racing and disposition.** Preserve terminal crash cut and explicit reset in the first race. Defer auto-recovery and turtle unless reverse-capable propulsion, signed motor/prop aerodynamics, rotor stop/reversal transients, collision/contact friction, arming interlocks and race rules are admitted together. Do not map PID crash recovery, simulated crash reset and turtle to one button; a negative command into the handoff's one-quadrant electrical law is invalid. Recovery practice must state whether it invalidates a race attempt.

**Checkpoint/schema.** Any future recovery mode needs its own actuator-law/layout identity, mode and direction, per-rotor reversal state, contact and rearm latches, recovery controller/timer, and race validity. A terminal cut cannot be silently cleared by import or observer.

**Tests.** **SET34-A:** requesting turtle on the first one-quadrant model is refused with a capability reason; PID `crash_recovery` does not clear a terminal race crash. **SET34-B:** after a crash, disarm/reset follows the handoff transaction; stale arm high, negative thrust or an uncommitted event cannot restore drive. **SET34-C:** a future qualified reverse model reproduces motor direction, contacts and race-validity state across checkpoint/restore.

## Good-enemy review: material corrections to a naive settings UI

1. **Misleadingly similar controls:** `align_board_yaw=90` has a 10× unit difference; `failsafe_landing_time` and `failsafe_off_delay` have different units and zero behavior. Decode using the source version and field semantics.
2. **A slider is not an AUX state machine:** BF clamps 2100 while INAV does not; AND/OR/link semantics differ. Equal-looking end ranges can activate different modes.
3. **`diff all` is not a complete snapshot:** it can omit target-dependent defaults, and 9.1 GPS defaults changed even when a 9.0 diff imports successfully. A known firmware version alone does not establish a board's starting configuration. Never claim an exact imported profile without the target, build and default baseline.
4. **The last profile block is not the active profile:** restoration commands matter, and source families use different index bases. An import report must state exactly which profile is selected and which fields were unrepresentable.
5. **Host loss is not RF loss:** pausing protects the simulator's deterministic transaction and clock; a deliberately injected RF-loss drill requires a separate advancing state machine. A USB-enumerated receiver does not prove its transmitter link is healthy.
6. **A checkbox is not a capability:** GPS/RTH, reverse thrust, blackbox export, current-sensor calibration and VTX power each need their own available model and validation. Treat unsupported settings as metadata, report them, and avoid implying hardware parity.
7. **Firmware source is not physical validation:** even exact parsing or matching a software unit test would not establish that the selected quad's dynamics, calibration, battery, sensors or control behavior match a physical build.
