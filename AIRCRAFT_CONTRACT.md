# Aircraft contract

**Status: current v2 authoring/runtime contract with AS-06–14 foundation interfaces, 2026-10-13.** Revision 3. Authored format: `openrc-aircraft v2`. Convention: `openrc-le-frd-v1`. [Audit](docs/research/aircraft-standardization/AS-00/), [migration and verification](docs/research/aircraft-standardization/AS-05/README.md).

The [standardization plan](docs/plans/aircraft-standardization.md) records delivered interfaces and remaining gates. The shared module registry, model manifests, presentation adapter and compatibility interfaces below preserve the accepted physical v2 format. Flaps, repeated propulsion instances and selectable new contact laws remain separate extensions.

## Scope and authority

An aircraft file describes one complete simulated configuration, not every possible build of a commercial airframe. All seven catalog configurations, their five visual families and the electric regression specimens use this contract. The catalog controls product availability; the file controls physics. A valid file is not evidence of a realistic aircraft. Preserve the evidence kind and source of every number, particularly the virtual balancing mass and borrowed aerodynamic/propeller data.

`app/physics/aircraft_data.gd` is the load/derive boundary. `aircraft_contract.gd` applies the closed structural/module contract before v2 data can fly; the existing loader performs numerical and coupled physical validation. The versioned JSON schema is the offline structural counterpart. Its numeric bounds are loader safety/qualified-model limits, not universal laws of aviation. A structurally valid file can still fail area, CG, inertia, lift/fin, table, gear-support, timestep or trim checks. A failure returns errors and no usable model. No unknown version is downgraded automatically.

V1 is retained for explicit historical experiments. It keeps its documented permissive/default behavior; it is not the standard for a new aircraft. Migration must be explicit and reviewed. The loader hashes the actual source bytes and source version separately from its rounded semantic hash. New data invalidates old checkpoint identity even when numerical trajectories are preserved.

## Three ownership layers

| Layer | Owns | Must not contain |
| --- | --- | --- |
| Authored aircraft | Identity, supported capabilities, reference geometry, component inventory, provenance, coefficients/polars, control limits, propulsion/energy, gear and hull | Current RPM, battery charge, servo positions, contact compression, integrated pose or cached trim |
| Derived model | Total mass, inventory CG, full inertia, transformed arms/hull/contacts, strip geometry and calibrated slopes, stall transitions, radians/servo rate, flattened validated tables | Mutable flight history; separately authored copies of values already derivable |
| Runtime session | Pose/velocity/rates, servo positions, engine mode/RPM, wake/shaft/battery states, ground anchors and qualified ground extensions, commands, trim/start, crash and recorder lifecycle | Hidden per-aircraft constants or edits to the source inventory |

Physics and control consumers use the normalized model. Render vectors are allowed only after the float64 simulation boundary. Numerical strip count, 240 Hz step, gravity, integrator safeguards, weather, field friction and input-device shaping belong to shared systems, not duplicate aircraft fields.

## Stable physical identities

New aircraft sources declare `physical_identity_version: 1` within physical `openrc-aircraft v2`. The module is optional for historical v2 files, but complete whenever present: every inventory item and installed gear contact has `id`; `crash_hull_ids` has one ID in the same order as `crash_hull.value`; `propulsion.id` identifies the installation; `controls.surface_ids` maps exactly `aileron_left`, `aileron_right`, `elevator` and `rudder` to IDs. Partial modules, unsupported versions, invalid IDs and duplicate IDs block flight.

IDs use lowercase snake_case, start with a letter, contain at most 80 characters and are unique across all five groups within one aircraft. Author semantic IDs such as `wing_right`, `contact_main_left`, `probe_right_wing_tip`, `propulsion_main` and `surface_aileron_right`. Keep the ID when a component's display name, parameters or array position changes. Do not generate it from a name, index or hash; do not reuse a removed component's ID for a different component. Configuration variants may retain IDs for the same inherited components. Scope external references by aircraft/configuration identity as well as local ID.

IDs identify objects, not physical values, component relationships, detachable sections or active capabilities. A hull probe and an inventory mass item have distinct IDs even when both concern the same wing. Keep point and ID together in the authoring generator before projecting the parallel hull arrays. Renaming or reordering must regenerate source-byte-pinned descriptors. Reordering numerical inputs can change floating-point reduction order; adding IDs must preserve the original order and every nonidentity value. Numerical retuning requires separate evidence.

`PhysicalIdentity` validates authored metadata and builds `model.physical_identity`, including ordered ID lists and `inventory_index_by_id`. Derived controls and propulsion retain their IDs; gear contacts retain both their ID and legacy profile name. Workshop v3 resolves inventory bindings by ID; contact observations and propulsion observations consume authored IDs. Existing GP wheel profiles still use canonical contact names and retain their source/profile hashes: changing those names requires the owning profile update. This module does not change that separate profile format.

ID-less historical v2 and explicit v1 inputs retain their existing compatibility IDs. Authored metadata changes source/model hashes, so checkpoints from prior physical source bytes remain incompatible even when numerical trajectories match. Saved Workshop descriptors use their explicit versioned readers; no saved snapshot is rewritten silently. [Migration and verification](docs/research/aircraft-standardization/AS-08-identity/README.md).

## Coordinates, signs and units

- Authored structural positions are metres in `[x_aft, y_right, z_up]`, referenced to the wing leading-edge datum at the centreline. Each visual builder documents its offset to that datum. `frames` is explanatory metadata; `convention_id` selects the executable convention.
- Body forces, velocities, angular rates and inertia use right-handed FRD at the inventory CG: forward, right, down. For a structural point `p`, `r_body = [-(p.x-cg.x), p.y-cg.y, -(p.z-cg.z)]`. A propulsion `thrust_line_offset` or `intake_offset` is already a CG-relative structural offset; do not subtract CG again. Slipstream `hub` and piece `root`, tail and gear positions, and the crash hull are datum-relative.
- World position uses NED: north, east, down. Altitude above the flat datum is `-down`; local terrain clearance is a separate ground query. Quaternion order is `[w,x,y,z]`, body to NED. Moments use `r × F` about CG.
- Inertia is the symmetric matrix layout `[Jxx,Jyy,Jzz,Jxy,Jxz,Jyz]` in kg·m² about the inventory CG. Off-diagonal matrix entries are negative products of inertia. Point masses and aligned boxes are summed with the parallel-axis theorem. A declared CG cannot move independently of this inventory.
- Reference area is m²; span and coefficient chord are m. `mean_chord` means **S/b**, including tapered wings, not mean aerodynamic chord. Changing the coefficient reference length requires transforming the derivatives consistently. Planform/CG studies may retain MAC in evidence.
- Aerodynamic force coefficients use wind axes `[-D,Y,-L]`; moment coefficients use body axes at the aerodynamic reference point, then transfer to CG. `alpha,beta` are radians. Normalized rates are `p b/(2V), q c/(2V), r b/(2V)`; dimensional damping avoids division by zero.
- Authored aerodynamic elevator/aileron derivatives are per radian of trailing-edge **down**; rudder per radian of trailing-edge **left**. Pilot/render surface outputs are degrees trailing-edge up/right. `ControlSurfaces.deflections_from_surfaces()` owns the sign/unit conversion; `Aero.deflections_from_surfaces()` remains its compatibility entrypoint. Steering uses its own signed gear angle: negative tailwheel steering is intentional.
- Angled thrust is `[down,right]` degrees and axis `[cos(down)cos(right), cos(down)sin(right), sin(down)]` in FRD. Supported propeller rotation is clockwise viewed from behind; positive shaft RPM has this sense. A turbine has its existing explicit `rotor_sense` ±1.

The frame split follows standard flight-dynamics practice, while these exact datum/sign choices are OpenRC's contract; do not import another solver's inputs without conversion. [JSBSim frame reference](https://jsbsim-team.github.io/jsbsim-reference-manual/user/concepts/frames-of-reference/)

## Presence, evidence and defaults

Each physical quantity is exactly `{value, unit, kind, source}`. `value` is a finite numeric scalar/vector/table of the specified shape; booleans and numeric strings are invalid. Units are exact symbols, not automatically converted. Evidence kinds are `manual`, `measured`, `borrowed`, `estimated`, `derived`; `source` is nonblank and states the derivation or identifiable source. Uncertainty belongs in the source/report until an uncertainty model has a consumer. A guess remains `estimated` even if the simulation passes.

Missing required data is an error. JSON null never means zero or an inactive subsystem in v2. Absence is allowed only for a documented optional module or default below. Zero is accepted only inside a field's domain: zero steering/offset/incidence/current drain is meaningful; zero mass, capacity, span, servo time or static thrust coefficient is not. Empty optional subsystem objects are invalid. Extra keys, misspelled coefficients and inactive-branch parameters are errors.

Explicit in every v2 file: start speed, planform, propulsion kind, capability selections, convention, inventory size (zero box denotes a point mass), gear steering (zero denotes unsteered contact), and propeller rotation for combustion. The following physically defined defaults remain conditional rather than copied everywhere:

| Optional input | Absence means | Consumer |
| --- | --- | --- |
| `controls.max_throw.aileron_down` | Symmetric aileron travel using `aileron` | `_controls`, command surface mapping |
| `controls.rates` (`normal`: travel fraction and expo per axis) | The maximum throws with no expo under every rate profile; a stick-shaping input setting from the manual, never an aerodynamic quantity | `_controls` → `Commands.shape_sticks` in `FlightSession.flown_commands` (keyboard and gamepad only; radios pass through) |
| `landing_gear` | Permitted only for `locked_up`; no tire/suspension loads; the session's explicit hull-response route still applies | Contract → `_landing_gear` → ground/crash |
| `landing_gear.breakaway_factor` | Existing dynamic rolling/slip law without static anchors | Ground/session anchor path |
| `propulsion.engine.shaft` (combustion) | Prescribed equilibrium RPM with first-order lag; no airspeed unloading from a torque-balance engine | Propulsion/session |
| `propulsion.engine.glow_installation` | Historical combustion solver; no inferred cycle family or finite fuel | Explicit `glow_2t`/`glow_4t` installation, finite tank and coupled flight; mutually exclusive with legacy `shaft`; [contract and semantics](docs/GLOW-ENGINES.md) |
| `propulsion.engine.spool_integrator` (turbine: `sampled` or `rk4`) | `sampled`: historical tick-before-body RPM. `rk4`: continuous RPM and stage thrust/gyro; explicit-step envelope required; dynamic wheel profiles and hot cutoff remain unsupported | Turbine/FlightSession; versioned checkpoint and trace identity |
| Propeller/turbine `thrust_angles` | Axial thrust | Propulsion/turbine axis |
| `normal_force`, `pfactor_moment`, `slipstream` (combustion prop) | Corresponding force, moment or wake increment absent | Propulsion, slipstream, local aero |
| `horizontal.downwash_gradient` | No dynamic downwash coupling | Loader/aero/session |
| `wing_station_incidence` | Untwisted six-strip wing | Loader/local aero |
| `aero.surfaces.wing_section_cm_ac` | No section pitching moment on the strips (symmetric sections, or a Cm0 the data folds into the tail incidence) | Loader → `Aero._local_loads` strip couple; the oracle's `Cm0` must carry the same camber moment |
| `aero.wing_polar` | Existing analytic stall blend | WingPolar/local aero |
| `aero.ground_effect` | No ground effect: loads independent of height above the field | GroundEffect → Aero strips/oracle and tail downwash; session terrain height |
| Turbine `ram_flow`, `ram_jet` | No corresponding fitted ram correction | Turbine |
| Slipstream smooth-profile/transport extensions | Existing explicitly selected legacy wake, without that added law | Slipstream/session |

Optional inputs retain all dependencies and limits of their runtime parser. They are not globally interchangeable. In particular a propeller crossflow/P-factor/wake module requires an explicit shaft axis; smooth wake currently requires an axial shaft. Ground effect requires the calibrated local wing (strip induced map) and the horizontal tail's `downwash_gradient`. Negative power coefficient (windmilling) requires a rotor-dynamics path. Electric supports its specified motor/ESC/battery law, not arbitrary combustion wake modules.

## Capabilities and conditional modules

Capabilities are closed selections used to validate configuration consistency. They cannot turn an unimplemented system on. They are included in model identity; the actual normalized modules drive the existing force/lifecycle consumers.

| Field | Accepted values and rule |
| --- | --- |
| `controls` | `conventional`: aileron, elevator, rudder and throttle only |
| `gear` | `fixed_tricycle`, `fixed_taildragger`, `locked_down_taildragger`: deployed contact module required; `locked_up`: contact module forbidden |
| `propulsion_layout` | `single_tractor` for a propeller; `single_centerline_jet` for turbine |
| `energy` | `prescribed_fuel` for legacy combustion/turbine; `finite_glow_fuel` iff explicit glow installation; `fixed_voltage` or `ocv_resistance` must agree with electric battery kind |
| `damage` | `terminal_hull`: no flight with structural part loss. Scripted routes terminate on hull contact; interactive soft contacts can scrape or stop a propeller without ending flight. Gear overtravel remains terminal |
| `flaps` | `not_simulated`: any modeled flap mesh remains neutral |

For deployed gear, compare each contact's datum-relative x position with `balance.plan_cg` (x increases aft). `fixed_tricycle` requires at least two contacts aft of the CG and one ahead; both taildragger capabilities require at least two ahead and one aft. Contacts exactly at the CG count toward neither side. This runtime topology check is independent of steering angle, so all-zero steering remains valid; it imposes no maximum contact count.

`propulsion.kind` selects `glow_prop`, `electric_prop` or `turbine`. `glow_prop` is a historical solver-family name for combustion-driven propellers, including the P-51 gasoline engine; it is not a fuel chemistry claim. Descriptive engine names/provenance identify glow versus gasoline hardware. Prescribed fuel means the loaded wet inventory stays fixed: throttle does not burn mass or migrate CG. Turbine `fuel_flow` is consumption telemetry, not a fuel tank state. Hardware named in an inventory (battery, retract, flap servo, brake or gyro) contributes mass/inertia without enabling its dynamics.

| Aircraft | Configuration preserved |
| --- | --- |
| Jensen Das Ugly Stik 60 | Glow, single tractor, lagged RPM, tricycle contacts, static anchors, 15 m/s start, estimated 20/20/25° throws, borrowed/estimated ground-effect law |
| Great Planes Extra 300S .60 | Glow, single tractor, lagged RPM, fixed taildragger, 17 m/s start, manual-derived throws |
| P-51D Mustang 1/4 | Gasoline, single tractor, shaft balance, thrust angles, P-factor/normal force/tail wake, retract hardware locked down, 25 m/s start |
| Ventage Jet | P100-RX turbine spool/ram model, retract hardware locked up, no ground wheel module, 29 m/s airborne start, aileron differential |
| Turbo Lumber Evolution | Electric 800 Kv tractor, nominal fixed 4S bus, fixed taildragger contacts, flaps up, assists off; estimated hardware losses and borrowed propeller map |
| Synthetic Stik electric specimens | One direct-drive tractor BLDC equivalent, ideal motoring ESC, prescribed voltage or OCV/resistance battery, Stik reference airframe; test fixtures, separate from the catalog |

Runway-start menu availability is a separate qualified product policy, currently Stik (including both experimental glow variants) and Turbo Lumber Evolution. Having valid wheel contacts does not claim runway-start UI qualification. The P-51 and Extra retain their physics ground tests; Ventage Jet cannot taxi on invisible wheels. Existing model wheel/gear articulation helpers are not proof of live suspension/steering animation.

Planned and **rejected as v2 active configuration**: EDF duct/fan and inlet/outlet momentum; pusher installations and wake orientation; multiple propulsion units and differential throttle; propeller reverse sense/pitch/gearing; retract deployment and changing contact/drag/inertia; flaps/slats/spoilers and mixing; fuel slosh and general moving/distributed mass beyond the explicit uniform-tank glow extension; battery temperature/ESC heating/BEC/receiver failures; structural flexibility, part loss and persistent damage; distributed mass rotation; water/skis; moving terrain. Add a conditional module, consumer, provenance, complete lifecycle state, versioned schema and independent or analytic test before admitting any extension. Do not copy tractor propeller coefficients to an EDF.

## Physical modules and parameter effects

The [machine schema](app/data/schema/openrc-aircraft-v2.schema.json) specifies exact field shapes and per-field numerical ranges. The generated [parameter register](docs/research/aircraft-standardization/AS-01/parameters.md) lists every quantity with its consumer. The [conditional module semantics](docs/research/aircraft-standardization/AS-01/module-semantics.md) define wake, polar, electric and tire parameters in detail. The following is the physical interpretation used when reviewing or tuning those fields.

**Mass and balance.** Inventory mass/position/box size determine total mass, CG and the six inertia entries. `balance.plan_cg` and `cg_tolerance` constrain agreement with that inventory; they do not override it. `plausibility.mass_range` rejects implausible totals. `plausibility.inertia_reference` supplies a warning against the existing mass/span-scaled UltraStick reference; it is not a measured inertia tensor or a calibration target. `balance.firewall` is reference/validation evidence only. All four inventories are virtual balanced builds; the balancing mass is not a claim about hardware actually installed. Positive/physical tensor and rotor-carrier checks remain mandatory. [Inertia sign reference](https://jsbsim-team.github.io/jsbsim/classJSBSim_1_1FGMassBalance.html)

**Aerodynamics.** `CL0,CLa` define the attached lift intercept/slope. `CLq` supplies pitch-rate lift; `CLde,CLda_each` supply control lift. `CD0,CL_minD,k_induced` define the shifted drag polar; `CDda_each,CDde,CDdr` add absolute control drag. `CYb,CYp,CYr,CYdr` define side force. `Clb,Clp,Clr,Clda_left,Clda_right,Cldr` define roll moment. `Cm0,Cma,Cmq,Cmde,Cmda_each` define pitch moment. `Cnb,Cnp,Cnr,Cnda_left,Cnda_right,Cndr` define yaw moment. The derivatives refer to the specified axes, reference lengths and normalization, not dimensional force gains. Stable-airplane sign restrictions currently constrain the admitted model family. `aero.reference_coefficients.CLadot` is preserved historical reference evidence; no alpha-dot derivative reads it. Downwash lag, when configured, derives its own unsteady response from the local tail law.

**Ground effect (M5-GE-1, optional).** `ground_effect.induced_coefficient/induced_exponent` define σ(h/b) = c·(h/b)^e / (1 + c·(h/b)^e), the fraction of each wing strip's induced angle that survives the ground's image vortex system at the strip's height h above the field; the strip keeps (1 − σ) of that angle as extra attached lift and its induced drag at the same CL scales by σ. `downwash_coefficient/downwash_exponent` define the same form for the wing's downwash at the horizontal tail, evaluated at the strips' mean height. Both reach exactly 1 at two spans. The session supplies the field terrain height under the CG; trim, linearisation and static solves are out of ground effect. Separated (flat-plate) flow and the slipstream tail increment are unchanged. The constants are fitted law coefficients (Raymer/McCormick and Wieselsberger image theory, image-VLM tail fit), not measured on any airplane; [evidence](docs/research/ground-effect/M5-GE-1/README.md).

`envelope.CL_max/CL_min`, blend width and `CD90` derive positive/negative stall transitions; sideslip blend controls the lateral full-envelope transition. The linear oracle remains valid through its qualified small-angle range. Local tail area/position/slope/incidence/effectiveness set actual lift, control authority and moment arm, with attached/local/stall blend bounds and `tail_CD0/tail_k/tail_CD90` drag. Wing aileron effectiveness and six station incidences control local asymmetric loading. Strip slope, lift offsets and induced-flow map are derived to reproduce the global static oracle, not additional user coefficients. The fin's global force/moment derivatives must match its local force and arm. Optional tabulated wing polars retain separate positive/negative branches with provenance and bounded extrapolation. Low-Reynolds-number and post-stall measurements remain aircraft-specific. [UIUC research/data](https://m-selig.ae.illinois.edu/pd.html)

**Controls.** Max throws bound the physical surface travel used by both aerodynamic and visual mapping. Servo full-throw time is neutral to full deflection, not a 60° manufacturer spec; its inverse is the normalized servo rate. Transmitter expo/dual rates and keyboard response belong to the input layer. The same shaped servo state drives rendered surfaces and physics; no renderer-only retuning. Aileron differential is explicit in Ventage Jet.

**Combustion propeller.** Static maximum/idle RPM and lag define the legacy governor approximation. A shaft module instead supplies indicated peak/idle power, friction torque and its normalized power curve; propeller torque loads the rotating inertia. Brochure `peak_power/peak_power_rpm` are validated reference evidence and never replace the shaft curve. Diameter and Ct/Cp tables define `T=Ct ρ n² D⁴` and `P=Cp ρ n³ D⁵`, where `n=RPM/60` and `J=Vaxial/(nD)`; power/torque must use the same reference convention. Axis/CG-relative application point determine force direction and moment; rotating inertia also supplies gyroscopic/acceleration coupling. Normal-force/P-factor tables and geometric wake pieces are explicit opt-ins with existing dependency checks. Preserve measured versus borrowed propeller identity and Reynolds/RPM limitations. [UIUC coefficient and test definitions](https://m-selig.ae.illinois.edu/props/propDB.html)

**Turbine.** Throttle map, idle/max RPM, governor time and acceleration/deceleration limits determine spool state. Static thrust, installation factor, mass flow and intake/thrust offsets determine installed force and ram/inlet moment. Ram-flow and ram-jet tables are fitted optional corrections. Rotor inertia/sense determine angular momentum coupling. Fuel flow reports consumption at RPM but does not reduce aircraft mass. There is no propeller Ct/Cp/shaft/wake module in this branch.

AV-20's explicit `spool_integrator: rk4` evaluates RPM, thrust and gyro at each RK stage; `AUX_RPM` is only the accepted endpoint mirror. Prescribed fuel and the existing empirical schedules remain unchanged. The launch preflight rejects a governor/rate-table slope whose timestep ratio exceeds 0.25. Checkpoint v8 identifies this law; collision wrapper v7 carries it as its inner physics format. Unpowered glide starts initialize zero continuous RPM. This slice does not define a hot engine's fuel-cut/rundown law: changing the running mode at nonzero RPM is refused. Detailed pending ECU/fuel work: [turbine realism plan](docs/plans/turbine-realism.md).

**Electric.** Kv, motor winding-equivalent resistance and no-load current define the three-constant motor law; the no-load context voltage/RPM/temperature is evidence/validation context, not a thermal model. The ideal motoring ESC maps throttle directly and does not implement active braking or regeneration. Fixed-voltage battery is an infinite prescribed bus. OCV/resistance battery specifies capacity, internal resistance, auxiliary current, initial SOC and ordered endpoint-covering SOC/voltage knots. Charge, delivered energy and pack heat evolve in the coupled event solver; they reset/replay as runtime state. Zero current/resistance values allowed by the specific field do not mean missing data. Carrier inertia and timestep stiffness checks apply before flight.

**Ground and damage.** Each deployed wheel is an undeformed contact point with spring stiffness, damping, compression travel and signed steering angle. Rolling resistance, side friction and peak slip set the existing tire law; optional breakaway enables anchors. Contact support, nonnegative load, damping, heave/slip timestep and sag/travel checks protect the integrator. The field, not the aircraft, selects terrain/surface conditions. Ground-track wheel profiles/spin/brakes are separately versioned interfaces and must be validated where attached; AS does not invent them. Hull vertices locate soft or terminal contact under the selected session policy; wheel support points must not become duplicate hull crash points. Travel exceedance/impact reports and the wreck are not structural damage models. Optional `crash_hull_components` names each hull vertex, in order, from a closed vocabulary (`left_wing_tip`, `right_wing_tip`, `spinner`, `propeller`, `nose`, `tail_end`, `left_stab_tip`, `right_stab_tip`, `fin_top`, `canopy`, `belly`; left/right by `y_right`). The list length must equal the hull. Only crash presentation reads it; it names the nearest hull vertex, not a structural section. Every shipped aircraft declares it through its generator ([CR-01d](docs/research/crash-damage-investigations/CR-01d/README.md)). An inventory item may carry an optional `energy_source` (`kerosene`, `glow_fuel`, `gasoline`, `lipo`) for crash fire and smoke presentation only; never infer it from a name or the propulsion kind ([CR-22b](docs/research/crash-damage-investigations/CR-22b/README.md)). Visual models from Blender name breakable parts with an `openrc_section` custom property, exported as glTF extras; a model already merged into one mesh uses a generated section map instead ([CR-09c](docs/research/crash-damage-investigations/CR-09c/README.md)).

The concurrent GP-03 interface is `openrc-wheel-profiles v1` in `app/data/ground/wheel_profiles.json`, keyed by exact aircraft ID and unique contact name. `WheelProfiles.apply_to_model()` runs after the aircraft derivation at the file-load boundary; invalid profiles block flight. In-memory aircraft derivation deliberately excludes this attachment. A deployed aircraft without a profile reports `legacy_fallback`; absent gear reports `no_gear` and rejects any matching profile. Neither absence silently enables brakes. Applied profiles carry their own identity into the session; file-backed v1/v2 comparisons must apply the same profile to both. Wheel radius, inertia, relaxation and brake inputs, consumers and limits are documented in the [module supplement](docs/research/aircraft-standardization/AS-01/module-semantics.md#concurrent-ground-profile-interface). This separately owned extension is outside the 152 aircraft-quantity paths and the frozen AS numerical-migration comparison.

## Lifecycle and other consumers

Selected catalog ID, loaded model ID and visual builder ID must agree on normal catalog startup; research electric donors deliberately reuse the Stik visual adapter. A mismatched selection is rejected before trim/flight. Reload validates a complete candidate and preserves the previous model/state if it fails. Reset selects the aircraft's declared trim speed, restores energy/engine/servo states and clears crash/recorder state. Pause holds those states. Checkpoints identify the complete model and solver/environment configuration and reject another model; new auxiliary state requires layout/reset/restore coverage.

Trace metadata records the real input format/hash, model ID, active propulsion/wake/aero law and start state. UI, HUD, camera, sound and crash presentation must consume normalized values or explicit presentation metadata; none may change physical constants. Visual geometry and control-node names remain owned by the model tracks. Future fuel/part effects must not infer hardware from a filename or free-text inventory name.

## Shared module and runtime interfaces

`app/data/schema/aircraft-modules-v1.json` is the shared classification registry consumed by Python `research/aircraft-standardization/modules.py`, GDScript `AircraftModules`, Workshop descriptor validation and compiler eligibility. It distinguishes capabilities, installed law families and permitted compiler transforms. Classifier diagnostics carry `code`, `path`, and `message`; classification does not replace the numerical aircraft loader or qualify a new combination. Shaft-balance classification leaves the selected split/coupled integration route to the session.

`ControlSurfaces` owns conventional command-to-surface, aerodynamic and visual sign mappings. Existing Commands/Aero entrypoints delegate to it; input shaping, trim and servo dynamics retain their previous state and order. One logical elevator can bind two visual hinges. That does not invent two independent physical actuators.

`AircraftPropulsionRuntime.prepare_callbacks()` selects the existing single-installation stage callbacks from validated configuration, before endpoint state exists. `FlightSession.propulsion_observation()` exposes the current family, canonical law, RPM and existing family telemetry/layout. Preparation never reads previous-family state; observation does not change it. Existing continuous/sampled laws and checkpoints remain distinct. The compatibility installation ID is scoped to the aircraft; it is not a multi-engine schema.

`FlightSession.contact_contract()` describes support IDs, ordered hull probe IDs, rotor disc, wheel-profile status and selected response policy. Preparation rejects malformed or duplicate support/probe bindings. Authored hull/support IDs are used when present; ID-less data retains ordered `hull_point_NNN` IDs and contact names. `rotor_id` is `propeller/<propulsion.id>` for an authored propeller, with legacy `propeller/single` fallback. Hull labels remain separate from visual sections, which are explicitly unbound. Current friction, terminal thresholds, prop-strike behavior and differences between interactive/scripted routes are preserved.

### Contact observations and checkpoints

`FlightSession.contact_events()` returns a detached `openrc-aircraft-contact-state v1`: the last accepted tick, active hull IDs, that tick's normalized events and the flight's propeller-strike latch. It is a bounded observation buffer, not a cumulative log. `AircraftContactEvents` serializes observations as plain `openrc-aircraft-contact-events v1` records with source/contact identity, tick, lifecycle, selected policy and response. Available positions, velocities and measures retain float64 precision; missing kinematics or impulses are never invented.

Subscribe to `contact_events_changed` and read that snapshot to consume events, including ground/strike decisions between integration steps. Accepted step publication is batched after contact and scenery-damage commit; rejected candidates emit no contact notification. Reset and successful replay restoration also notify readers.

Hull observations use `new`, `persistent` and `ended`; a terminal hull decision replaces that point's observation. An `impact` or `strike` record is a new response decision, not a second hull-onset signal. Scenery and lake events also identify the aircraft probe and swept contact fraction. Pending scenery impulses cannot be recorded as applied responses. Existing typed crash/scenery/lake feeds remain available; ground and strike checks keep their existing entry-route timing.

Swept collision filtering stages presentation and damage. `Simulation.stepped` publishes them only after body and continuous-state validation; rejected steps discard the staged records and roll back water engine-stop modes. Reset seeds already-touching hull IDs without inventing onset events. Failed aircraft reloads restore accepted contact observations and the broken-propeller latch.

Flight checkpoints retain their existing physics versions and add a separately versioned `contact_state`. Save/restore validates tick, active geometry, aircraft/environment references, policy and strike payload before accepting it. Legacy checkpoints without this field still restore: ongoing contacts are seeded from the saved pose, while unrecorded events and the visual strike latch remain unknown/empty. Restore remains paused recorded-input replay and clears transient crash/wreck presentation; it is not a complete live-session save. [Acceptance and compatibility evidence](docs/research/aircraft-standardization/AS-13/README.md).

## Model and package contract

`openrc-aircraft-model` describes presentation independently of physical aircraft v2. Version 1 retains the existing zero-argument model builders; version 2 selects the common imported-scene builder with an explicit `construction` projection. Its source is `assets/aircraft/model-bindings.json`; `research/aircraft-standardization/build_models.py` generates `app/data/aircraft_models/<family>.json`. Catalog `visual_family` resolves a physical configuration to that manifest. The three Stik configurations share one family. Unknown families never borrow a default model.

A manifest pins the builder and adapter, geometry source/revision, datum selectors, asset identity, logical controls, rotor, gear and crash-section provider. Each control declares `hinges: [{key, node, source, geometry_ref}]` and `visual_only`. Timber references its existing geometry articulation records; do not copy pivot/range/sign tables into another source. Scene validation requires the declared nodes beneath `airplane`, retains `propeller` and `*_hinge`, and checks imported asset/crash-map identity. Existing procedural builders are retained. `render/airplane.gd` consumes these bindings without aircraft-ID dispatch.

Version 2 uses `res://aircraft/imported_model.gd` and passes the validated manifest to `build(manifest)`. Its closed construction version 1 declares:

- `hinge_axis: "+X"`: each imported control's local X axis and rest basis define its rotation. Multiple hinges may share a conventional role. Geometry supplies ranges and `app_sign`; physical surface commands are not clamped by the renderer. Visual-only roles have a separate clamped inspector path.
- `rotor: {frame_node, geometry_ref, axis}`: a geometry-backed parent frame and its declared spin child. `axis` is a signed cardinal axis in that frame; the public wrapper still spins through `propeller.rotation.z`. An absent rotor uses `{}` and a compatibility marker. This visual convention does not enable a new physical propulsion layout.
- `gear: [{role, node, geometry_ref, wrapper}]`: every declared gear role has one geometry-backed pivot and a named Euler wrapper. Wrappers preserve rest transforms, with ancestors constructed before descendants; wheels use root X and steering root Y at rest. Tilted/retracting gear needs an extended consumer, not an inferred axle convention.
- `material_grow: [{node, materials, amount_m}]`: optional per-instance StandardMaterial3D surface offsets, positive and at most 0.01 m. Timber retains its existing 0.8 mm black/red cowl seating correction through this declaration; shared imported resources stay unchanged.

The importer rejects missing or ambiguous nodes, wrapper collisions, mismatched geometry node/parent/rest references, nonfinite transforms and scaled/sheared/reflected articulation ancestry before returning a model. Geometry records expose `node`, `parent`, `rest_translation` and `rest_basis`; measured rest transforms agree within 0.00002 per vector norm to allow six-decimal source measurements. These are presentation checks. Version 2 accepts authored glTF sections or no sections; the legacy generated triangle-map route remains with version 1 builders. Timber's inspector entrypoint is a compatibility facade over the common builder. [Migration and pose evidence](docs/research/aircraft-standardization/AS-09-10-import/README.md).

An imported sectioned GLB uses the `gltf_extras` crash provider with empty `metadata_script` and `asset_node`. Every mesh and articulated pivot declares a supported string `extras.openrc_section`; validation rejects missing or invalid IDs and detachable ancestors that would capture another section (for example an engine parent containing the propeller). Timber r2 uses these authored objects directly. The legacy `generated_triangle_map` provider remains supported for merged assets; do not apply an r1 triangle map to a revised mesh.

Manifest validation resolves dependencies freshly at build/trial preparation. UTF-8 source text uses explicitly declared LF-normalized SHA-256; binary assets use raw SHA-256. Generated manifests themselves have canonical LF bytes and Workshop v2 pins their exact hash. A frozen trial passes that binding to the renderer and refuses a changed model. Rendering caches the accepted datum; no source traversal or hashing runs on a physics tick or ordinary rendered frame.

Godot can compile scripts and convert imported resources during export. The aircraft export plugin includes verified source-proof bytes and a package-only proof table, while the runtime also checks that actual compiled/imported resources resolve. These hashes identify exporter inputs, not the byte representation of platform-specific imported scenes. Missing, malformed or incomplete package proofs block model acceptance; they never fall back to adjacent source files. [Godot FileAccess guidance](https://docs.godotengine.org/en/4.3/classes/class_fileaccess.html)

The [Blender handoff](docs/BLENDER-AIRCRAFT-HANDOFF.md) remains authoritative for authoring/export coordinates, pivots and sections. The common preflight adds generated-manifest, dependency, actual neutral/full-travel pose, independent-instance and package checks. It reports mesh counts; it does not establish a universal polygon budget or physical validation.

## Adding and tuning an aircraft

1. Copy the [synthetic template](research/aircraft-standardization/template/openrc-aircraft-v2.template.json); give it a unique ID and clearly mark its initial evidence as donor/estimated. Select only supported capabilities. Do not register it as flyable yet.
2. Establish one visual/structural datum. Measure span/area/chords, CG and component masses/positions; derive the tensor and geometry. Retain raw measurements, uncertainty and provenance in `docs/research/<track>/<step>/`.
3. Set control hardware travel/time and actual propulsion tables. Fit static/attached aero with consistent reference quantities, then local stall/tail behavior. Keep calibration and held-out verification observations separate. Tune one mechanism at a time.
4. Validate schema and Godot load/trim; run model/hinge, force, propulsion, ground, stall/control, lifecycle and performance checks. Compare state traces and force budgets. A passing self-consistency test is not physical validation.
5. Register the physical configuration and its `visual_family` in the catalog. Declare the family's geometry sources and semantic bindings in `assets/aircraft/model-bindings.json`. A Blender family using the supported conventions selects `res://aircraft/imported_model.gd`, adapter `imported_glb`, and the construction projection above; it needs no new model builder. Procedural families retain their version 1 adapters (`euler_hinges`, `axis_hinges`). New capabilities extend the shared contract and consumers before registration.
6. Generate model manifests with `python research/aircraft-standardization/build_models.py`, then Workshop descriptors with `python research/aircraft-editor/build_descriptors.py`. Do not copy Timber's generated articulation or crash triangle map: use the new asset's authoring source and hash-bound metadata.
7. Run the common [aircraft conformance command](docs/TOOLS.md) in source and package modes, inspect the rest/full-travel poses and contact geometry, and retain aircraft-specific physical evidence. The harness discovers catalog entries automatically. Manufacturer limits, independent measurements and qualified pilot feedback decide physical acceptance. Unsupported features require a contract extension before use.

Use the [AS-05 authoring commands and verification](docs/research/aircraft-standardization/AS-05/README.md) for generated-output checks and documented results. The v2 migration preserved force equations and numeric calibration; it does not close physical or target-machine acceptance. Never hand-edit a generated aircraft JSON.

## Workshop authoring standard

The [current Workshop guide](docs/AIRCRAFT-WORKSHOP.md) defines the implemented common editing interface. `research/aircraft-editor/build_descriptors.py` discovers catalog entries and generates `app/data/workshop/<id>.json`. Identified aircraft use closed `openrc-aircraft-workshop v3` with inventory bindings containing only the authored `key`; the resolver finds the current component by ID. The descriptor still pins exact physical source bytes, module assertions, visual family and exact model-manifest hash without duplicating physical values. Regenerate it after changing physical sources or generated model manifests. ID-less sources retain v2 index/name-hash bindings. Explicit v1/v2 readers retain historical descriptor semantics; v1 resolves its catalog visual family when freezing a trial. Missing or changed presentation dependencies prevent launch without hiding the saved variant from the library. Workshop metadata remains outside the physical v2 schema.

The shared compiler selects supported transformations from capabilities, never aircraft names or IDs. All current conventional-airplane catalog entries have descriptors and conventional-control support; size/weight/virtual-power transforms currently support the simple prescribed-RPM family. A saved variant embeds its original aircraft bytes and descriptor and pins compiler/external dependency hashes. Changed external resources are refused rather than silently substituted; self-contained historical dependency replay remains planned. See the [AE standard and remaining gates](docs/plans/aircraft-editor.md#21-common-aircraft-editing-standard) for richer component bindings, family modules, migration and fleet acceptance. Adding another aircraft with existing supported capabilities requires data/assets, a generated descriptor and conformance evidence, with no aircraft-specific Workshop transformation code.

## Experimental rotorcraft boundary

The explicitly selected `xcell-60-research` vehicle uses `format: "openrc-aircraft v2"` and `vehicle: "rotorcraft"` with the same `{value, unit, kind, source}` quantity conventions. Its closed schema is [openrc-rotorcraft-v2.schema.json](app/data/schema/openrc-rotorcraft-v2.schema.json), generated with its preset; [rotorcraft_data.gd](app/physics/rotorcraft_data.gd) validates its main/tail rotor, aggregate body, signed shaft inventory, drive, electronics and skids before flight. It is an experimental vehicle-specific schema branch, not a conventional-airplane module/inventory conformance result. Airplane loaders, manifests, Workshop and conformance tools explicitly select supported vehicle classes.

Rotorcraft authoring remains generated and fail-closed. Signed inertial axes and aerodynamic gearing must agree. Aggregate published body inertia, radial-blade estimates, unknown engine spin and the HX-700/X-Cell visual/physical pairing are declared in the [HELI evidence](docs/research/helicopter/HELI-16/README.md). The current [helicopter guide](docs/HELICOPTER.md) owns controls and qualification. Full component inventory, Workshop transforms and identified rotorcraft hardware extend this branch before acceptance; do not add fake airplane surfaces or reinterpret it through the airplane schema.
