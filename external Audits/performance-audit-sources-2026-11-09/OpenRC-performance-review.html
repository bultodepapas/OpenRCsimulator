Outcome

Two bounded CPU optimizations are implemented in the local branch perf/math-audit-20261109: a controller-button occupancy index and guarded engine-voice interpolation inlining. The passing controller, voice, and audio checks and the component measurements support these changes. The existing engine-sound suite retains the same stale catalog failure on baseline and candidate. They have not been pushed or merged. An apply-ready patch accompanies this report.

The controller resolver is the stronger implemented result: across the tested two-to-five-candidate gamepad fixtures, its measured median cost falls by 36–68%; the five-action airplane capability case falls from 356.339 to 114.228 microseconds per resolution. The audio component falls from 6.435 to 4.937 milliseconds per generated audio second, a much smaller absolute saving of about 1.5 ms/s per active voice.

The real GDScript flight-session benchmark also ran. Its 24-mode spatial-wind workload had a median batch cost of 4.556 ms/tick on this host, compared with a 4.167 ms period at 240 Hz. This identifies a demanding CPU workload and supports prioritizing spatial-wind work; it does not measure the benefit of the proposed phase cache. No GPU, displayed-frame, full-game FPS, physical-controller latency, target-Mac, or sustained release-build performance result was obtained.

The report separates implemented changes, measured unchanged baselines, component prototypes, source-derived operation estimates, existing audit work, and remaining qualification. The patch changes no simulation tick rate, flight law, aircraft data, or native source identity. Exercised audio integration fixtures retained identical simulation checkpoints; patched whole-flight trajectory equivalence remains to be qualified.

3. Implemented: one occupancy index for controller defaults

Executed path and cost

app/input/controller_actions.gd::effective_bindings constructs the effective action map, applies explicit overrides and AUX ownership, then calls _add_automatic_buttons. The original helper scans every current binding for each eligible automatic candidate. The built-in map has 37 actions. An ordinary capability configuration can enable between one and five candidates; all nine declared airplane/helicopter candidates can participate in mixed test configurations.

The cost matters beyond a single call. In Home-launched flight, app_root.gd::_input resolves maps for restart, rates, generic action identities, selected flight/UI observers, dispatch, and throttle cut. A stable selected gamepad can pass through seven resolutions during one event. Flight capabilities are aircraft-dependent; the UI resolver uses the full default airplane capability set. A direct technical/main-scene input benchmark can bypass this shell. Delivered event rate, actual capability sets, profile overrides, and reentrant callbacks must be measured before attributing a total event cost.

Sources: resolver and automatic defaults, binding ownership, event routing, actual flight capabilities.

Original and proposed algorithms

Original, for each eligible candidate c:
    inspect AUX reservations
    for every binding b:
        validate b, check action/context, compare b with c
    insert c if unreserved

Implemented:
    lazily scan bindings once when the first eligible candidate is reached
    occupied = valid button IDs belonging to known flight/both actions
    for each eligible candidate in original declaration order:
        inspect the unchanged AUX reservations
        test candidate.button membership in occupied
        if free: insert candidate and immediately occupy its button

With A bindings, C eligible candidates and U AUX entries, the inner work changes from O(C*A + C*U) to O(A + C + C*U). Five candidates produce 185 binding inspections before versus 37 after: 148 removed. Two candidates produce 74 versus 37. The earlier outer effective-binding/AUX work still exists. Memory adds one short-lived dictionary of valid occupied buttons, bounded by the known action set; allocator bytes were not measured. There is no persistent cache and no invalidation protocol.

Equivalence conditions

For a valid button candidate, the old comparison reduces to equality of integer button IDs when the other binding is also a valid button. Unknown definitions, malformed types, out-of-range values, and menu-only actions must not reserve flight buttons. Explicit Clear, explicit overrides, all AUX switch members, same-channel ownership, and deep-copy ownership of returned bindings remain unchanged. Immediate insertion preserves declaration priority when airplane and helicopter defaults share a button.

The private helper is additive under its sole production caller: automatic candidates start unbound unless explicitly overridden, and explicit ones are skipped. This invariant is documented in the patch. A future arbitrary caller that replaces a nonexplicit existing binding would need occupancy removal or reference counts; the new helper must not silently become a general replacement API.

Reuse the time factor, preserve every spatial sample

Both GDScript spatial wind and native spatial wind evaluate the following expression for each mode and each queried point:

epoch = stage_time + immutable_epoch_offset
spatial_i = kN_i * north + kE_i * east + phase_offset_i
time_i = fposmod(omega_i * epoch, TAU)
phase_i = fposmod(fposmod(spatial_i, TAU) + time_i, TAU)

Only time_i is identical across the datum and station queries at that stage. Compute that exact binary64 value once, then reuse it without reassociation. Keep the spatial remainder, final remainder, four point-dependent trigonometric evaluations, wall taper/derivative, and vector accumulation in their original order. Do not interpolate full winds or reuse between RK trial states.

For M modes, Q qualifying point queries and S independently owned groups per tick, this removes M*(Q-1)*S temporal products and remainders per tick. A Stik-like group has datum plus nine stations. With 24 modes, ten points, four ordinary RK stages and 240 accepted ticks/s, the source-level saving is 207,360 products and 207,360 remainders per simulated second. The 8/64-mode equivalents are 69,120/552,960 of each. Adding the separate pre-step group could raise the 24-mode count to 259,200, but only after implementing that owner's separate context. Extra event trials and invalid/ground/zero-RMS paths change the count.

This is a targeted reduction: for ten queries it removes 90% of the repeated temporal term, but only 30% of the original three-remainder-per-mode work, and none of the four trigonometric calls per point. It cannot honestly be described as a 90% wind or physics speedup. The effect on the measured 4.556 ms reference cost is unknown.

Ownership, prototype, and acceptance

The separate C++ prototype uses at most 64 doubles: 512 bytes of value storage plus identity/metadata. A fresh stage context fills lazily on the first above-ground query reaching turbulence after the initial domain/layout checks; different provider, epoch, or oversized layout takes the original path. It retains strict floating-point compiler flags. The final component comparison reports 38,853 checks and zero unexpected differences, including modes 8/24/64, synthetic 65-mode fallback, gusts, thermals, zero activity, invalid domain, nonfinite/signed-zero inputs, changed time, and provider identity.

An intentional same-pointer mutation is a negative control: a pointer and time alone do not detect modified coefficients. The provider must remain immutable for the context lifetime. New stage, reset, rebind, changed configuration, retry, and replay require new scratch. Preview/retained-sampler ownership must remain detached correctly. The production stage oracles and trajectories have not run on this unintegrated candidate; the native prototype was not timed.

A reference-GDScript implementation needs a separate opt-in stage sampler through WindFlow, Environment, WindField, and SpatialField. It must preserve custom wind_world/sample_world overrides and the existing call/refusal order; test_wind_aircraft_flow.gd exercises these contracts. This reference implementation is particularly relevant to the measured workload and to platforms without the native evaluator. Inspect optimized native assembly/profiles and VM call costs before assigning time savings; compiler removal and scratch/dispatch overhead remain unmeasured.

Required gates are exact stage/load arrays, refusal and rollback behavior, source mutation, preview/wake/gear sampler lifetime, zero RMS, all mode counts, ground boundary, substeps/events, checkpoints/restores, actual-aircraft trajectories, native/reference oracles, then matched session timing. This new opportunity is separate from completed WOPT-01 thermal reuse, WOPT-02 observer datum reuse, A6 O4 pre-step air reuse, and pending A6 O5 geometry preparation.

5. Other CPU and numerical opportunities

Implemented: guarded audio interpolation

The path is companion render -> EngineSound.update -> EngineAudio.refill -> EngineVoice.render. The normal player reaches this oscillator only on legacy soundscape routing. An active voice generates 22,050 stereo frames per second when refill demand exists.

The original loop calls sample(table, phase) per frame. The implemented valid-domain path evaluates the identical interpolation inline:

index = phase * 4096
lo = int(index)
interpolated = table[lo] + (table[lo+1] - table[lo]) * (index-lo)
value = amplitude * interpolated

It preserves update order and the original fposmod phase operation. A block-level guard requires finite phase in [0,1), finite nonnegative frequency, and at least 4,097 table entries; otherwise the original helper remains responsible for behavior. No table, PCM allocation, float precision, or smoothing law changes. Extra memory is constant scalar state. Unconditional inlining was rejected because invalid mutable phase could move an error from the helper to the caller and abort rendering instead of preserving original continuation.

Five alternating ABBA/BAAB rounds, 20 total trials, each 300 blocks x 368 frames, produced baseline/candidate medians 32,220/24,718.5 microseconds. Each round's pair mean favored the candidate. The normalized 6.435 -> 4.937 ms per generated second is a 23.3% component reduction and about 0.15% of one CPU-second per continuously active voice. Three voices would imply about 4.5 ms/s saved only under linear continuously refilled assumptions; this fleet cost was not measured. Maintenance cost includes duplicated interpolation and guard logic, so the benefit is deliberately classified below input and spatial wind.

The exact implementation passed 868 checks, including exact PCM/state comparisons over 422 blocks and 122,633 frames plus pause/resume adapter checks. The permanent voice suite passes 86/86; engine-audio integration passes 147/147, including pause, queueing, accepted-state observation, restore, restart, and simulation noninterference. A separate invalid-phase witness intentionally logs the same original errors in both variants and is classified as an expected-error run, not a passing checked test. The engine-sound suite has one stale catalog expectation out of 27 checks on both variants; after exact required WAV import, its complete baseline/candidate logs are byte-identical. Listening and physical audio-driver tests remain unperformed.

Companion forecast: reduce first, take roots last

pilot.gd::_score_bank computes 33 forecast distances for each threat and keeps the minimum. For finite, nonnegative identically computed squared distances d_j2, monotonicity gives min_j sqrt(d_j2) = sqrt(min_j d_j2). A no-trace path can therefore take one root per threat after reducing instead of 33. Preserve the original distance result and all subsequent meter-based margins; comparing squared scores directly would change the algorithm.

At 60 Hz planning, N healthy companions each considering the player and N-1 peers produce source-derived clear-path counts of 1980*N*N roots per simulated second. N=1/2/3 gives 1,980/7,920/17,820, versus 60/240/540 after reduction. The existing clear-baseline shortcut already avoids eleven extra bank candidates; those candidates must not be charged on every plan. Conflicts and held maneuvers increase work separately. Trace mode still needs every sampled distance. Preserve NaN/overflow/tie/signed-zero behavior with domain checks or fallback; the cost of those guards must be measured.

The same 32-step predictor repeats bank-to-turn-rate evaluation at clamped interpolation endpoints: iterations 1–4 use weight zero, 5–7 are transitional, and 8–32 use weight one. Lazy reuse of the exact endpoint lerpf -> tan -> multiply/divide results reduces 32 such evaluations to five without changing heading accumulation. Do not replace lerpf(a,b,1) with b merely on real-number intuition; preserving the actual endpoint operation avoids a different floating-point rounding path. Two callers also need only roll from a full quaternion-to-Euler conversion; reuse the original roll expression and coordinate convention, leaving base guidance's full Euler requirement intact.

These changes are unimplemented and untimed. They require exact score/result-field comparisons, thresholds and ties, zero threats, avoidance/held/clear scenarios, all commands and decision state, trajectories, replay and a genuine source-identity rebind. Updating a profile hash alone is not qualification. No approximation or reduced planning frequency is proposed.

Native spatial stage: remove discarded legacy air work

In nk_stage.hpp:273–296, legacy wind and air_compute initialize an Air value before the spatial branch replaces it on both success and refusal. Their returned values are overwritten and the examined evaluator has no explicit state mutation. Libm calls can still affect errno or floating-point exception flags; preserve the supported environment and check malformed inputs before removal. Moving that initialization into the nonspatial branch could remove a legacy query plus two square roots and two atan2 calls per qualifying native stage: nominally 960 discarded Air evaluations/s for four stages at 240 Hz.

First inspect the actual optimized build to determine whether dead-store/call elimination already removes this work. Then compare complete native stage arrays, malformed and invalid spatial cases, preview/fuel/wake/gear behavior, rollback, and accepted trajectories. No candidate timing or stage-level parity was obtained, and this native-only proposal does not improve the measured reference path by itself.

6. GPU and memory opportunities

Afterimage support can be outside the viewport while the pass remains active

sun_glare.gd::_show_afterimage enables the layer based on patch alpha rather than projected support. The dose model can remain active outside the visible camera rectangle. A source-derived, checked-engine 1920x1080 fixture at 50-degree vertical FOV produced a 50-degree horizontal patch with alpha 0.941845, center x=2,340.09 pixels, radius=23.164 pixels, and nearest viewport distance=18.136 radii. The layer was shown. A 41.5-degree control lies 2.786 radii from the edge and provides a useful boundary case; whether it remains drawn depends on the chosen validated error budget. Its ideal mask factor is also very small. Add a clearly contributing positive control within one to two radii.

The afterimage shader loops over up to eight patches and requests a mipmapped screen texture. Its radial contribution is m_i = alpha_i * exp(-0.5*x_i^4). It has no finite mathematical support. At the distant witness, its ideal maximum tail is below 10^-23490; at three radii the factor is about 2.577e-18. Neither statement proves an algebraically exact cutoff across GPU formats and compilers.

Proposed experiment: preserve patch state, exposure, decay and time semantics, but hide the rendering item when every packed contribution is outside a validated error envelope. For finite 0<=m_i<=1, the combined alpha satisfies 1-product(1-m_i) <= sum(m_i). This gives a conservative way to allocate a total alpha error budget across at most eight patches, then bound color error using the actual output range. It must include low-alpha patches that render while another patch keeps the layer enabled. Use the exact viewport, aspect, height scaling, FOV and radius clamp; uncertain or nonfinite input stays on the old path. Validate a displayed-channel error budget and pilot-readability policy in each supported format/backend before promotion.

A full-screen item nominally covers 2,073,600 pixels at 1080p or 8,294,400 at 4K. These are work envelopes, not GPU invocation counters or measured bandwidth. Hiding the item may also remove a screen-copy/mipmap dependency if no other consumer requires it. A fragment branch alone does not necessarily remove that material dependency. The exact pinned engine's RD and GLES3 canvas paths were inspected, and Godot's screen-reading documentation describes the copy/mipmap mechanism. GPU capture must establish the actual pass graph and savings.

Test sun/moon, skyline/cloud occlusion, resize/aspect/zoom, overlapping patches, barely visible edges, pause/seek, eyewear, and offscreen transitions on Compatibility and Mobile/Metal. This refines A26 section 2E; it is not a separately counted new GPU defect or an implemented FPS improvement.

Index shadow geometry only after accounting for preparation and consumers

Projected.collect expands model faces into an unindexed position-only shadow mesh. In the exact Stik builder component, the result contains 165,296 triangles and 495,888 positions. Indexing produces 84,428 positions and 495,888 indices. Deindexing the candidate reproduces original position bytes before any second get_faces() conversion; bounds and face streams also match.

Logical position/index payload, assuming 12-byte float32 positions and 4-byte indices, changes from 495888*12 = 5,950,656 bytes to 84428*12 + 495888*4 = 2,996,688 bytes: 49.64%, or 2.817 MiB per such mask. This is not observed RSS, VRAM, drawn-vertex count, or GPU time. The triangle count and tested triangle positions/order are unchanged. Actual fragment-shader invocations were not measured; post-transform cache reuse depends on draw order and hardware.

Seven alternating warm pairs after two warmups measured median collection at 8.950 ms, versus 108.193 ms for collection plus indexing/finalization. Incremental indexing/finalization median was 99.917 ms. A naive synchronous patch would introduce a substantial preparation pause; it was rejected. An offline or bounded prepared-cache artifact can be evaluated later, with source/material/visibility/version identity and dynamic-model fallback. For a redraw-time-only payback screen on a comparable critical-path basis, compare redraw_count * measured_redraw_saving with the incremental preparation cost, while also enforcing the first-interactive-frame budget. Offline preparation, memory residency and upload savings require their own accounting.

There is a concrete consumer trap: field_projected_shadows.gd treats the vertex array as a deindexed triangle stream. Globally indexing Projected.collect would break that interpretation. Use an aircraft-only finalizer or update every relevant consumer deliberately.

The pinned Godot engine also snaps positions to 0.0001 and builds a cached triangle mesh/BVH inside get_faces; a direct source-index shortcut must preserve snapping, strip winding, transforms and invalid-input behavior. Avoid claiming cache-residency savings without measuring who owns and shares those structures. Historical Windows active-roll shadow measurements are context only, not this review's current GPU baseline.

8. Hardware, methodology, and limits

All new elapsed measurements used a Linux x86-64 container on an AMD EPYC 9V74 80-Core Processor host, with nine visible/affinity CPUs, an eight-core cgroup quota, and an 8 GiB memory limit. The host is shared; frequency, contention and thermal isolation are not controlled. The official Godot editor/debug binary reports a headless display and Dummy rendering/audio. No GPU device or physical display/controller was exposed. These are warm software/component screens and short accepted-session baselines, not native consumer-hardware qualification.

Independent agents' CPU tests, imports, compilation and timing runs were serialized so they did not compete with the reported benchmark batches. Raw samples, candidate hashes, fixtures, configuration diffs, checked-runner logs, failed setup attempts, and expected-error controls are retained. The checked runner scans engine logs: an exit-zero script with engine errors is not accepted as a pass. Failure evidence is kept with its classification.

For a component speedup s occupying fraction f of the relevant serial work, Amdahl's law gives S_total = 1 / ((1-f) + f/s). For s=3.1195, f=0.10 gives about 1.073x; f=0.25 gives about 1.205x. The actual f is unmeasured, and a GPU bottleneck or presentation wait can hide CPU savings in displayed FPS. Input-path work can still affect responsiveness when the frame rate does not change. Apply this to measured frame/handler shares, not an invented workload fraction.
